# @speed/i18n

The platform's i18n layer for web packages: one react-i18next-wrapped
instance per host, a negotiated start language, per-package namespaces
registered with parity and coverage validation, and a missing-key
discipline with **no silent cross-language fallback**. It is the
frontend counterpart of `pkgcore/i18n`'s merged Go catalog — the same
rule on both sides of the wire: a key missing in the language asked
for never renders another language's text. The MUI locale helper lives
at the isolated `@speed/i18n/mui-locale` subpath.

## What it is for

Every language decision a browser host makes:

- **Start-language negotiation** — a fixed chain, first match wins:
  URL parameter (`?lang=...`), the persisted manual choice, a profile
  language slot for hosts that resolve a signed-in user's locale (it
  outranks the browser but sits below the URL parameter and the
  persisted choice), navigator languages, then the `zh-CN` default.
  Subtag matching relaxes in both directions, never across languages.
- **Per-package namespaces** — one bare, unscoped namespace per
  package (`ui-kit`, `auth-ui`, ...). A package that ships locale
  resources registers under its base name; your own app bundle
  registers the same way.
- **Registration-time validation** — `registerNamespace` checks before
  any mutation: every supported language must be present, all bundles
  must carry the **same leaf key set**, leaves must be non-empty
  strings, plural families (`key_one`, `key_other`, ...) must cover
  every count category the supported languages can select, and each
  namespace registers exactly once.
- **Visible missing-key behaviour** — the instance is pinned with
  `fallbackLng: false` and `load: 'currentOnly'`, so a key missing in
  the loaded language renders as the key itself and fires a structured
  missing-key handler — visible by default, overridable through
  `onMissingKey` at creation.

Not a translation-management system and not a server-side locale
store: no profile feature ships (the slot is for hosts that have
one), and storage defaults to the host's localStorage — injectable
and best-effort.

## When to choose it

Every host that renders speed components, and every host with
user-facing text of its own. All component packages render their
strings through this instance, so the host bootstraps it once and
registers every namespace before anything renders. Choose it even for
a single-language product: parity turns a missing translation into a
boot-time error, never a silent gap.

## Wiring and minimal use

```ts
import { createI18n, switchLanguage } from '@speed/i18n'

const i18n = createI18n() // negotiates, synchronous; react-ready instance
// language switch UI:
await switchLanguage(i18n, 'en-US') // persists the canonical choice
```

```ts
import { registerNamespace } from '@speed/i18n'
import welcomeZh from './locales/welcome/zh-CN.json'
import welcomeEn from './locales/welcome/en-US.json'

registerNamespace(i18n, 'welcome', {
  'zh-CN': welcomeZh,
  'en-US': welcomeEn,
})
// components: useTranslation('welcome') / t('greeting.hello')
```

The react-i18next bindings are re-exported from the main entry —
`I18nextProvider`, `useTranslation` and the rest — so hosts and
component packages consume the whole surface through one `@speed`
package. Lockstep single-version shipping pins the module identity:
no host can end up with two react-i18next copies, which is what makes
`useTranslation` inside third-party components safe.

## Core API and usage essentials

- **`switchLanguage`'s storage argument is three-state** —
  `undefined` uses the storage bound at creation, `null` persists
  nothing, and a `StorageLike` persists to that store instead. The
  manual language-switch UI persists (the default); a host **applying
  a server-resolved profile locale must pass `null`**, or the stored
  manual slot would shadow later profile changes in that browser.
- **Storage is best-effort by design** — a failing write warns and the
  instance still switches (a rejected promise always means the switch
  did not happen); a throwing read at creation means "no stored
  choice", never a failed creation.
- **Plural forms are suffixed leaves** and count as ordinary keys for
  parity: because bundles carry identical leaf sets, zh-CN ships
  `_one` forms that only en-US counts of 1 select.
- **`muiLocaleFor`** (`@speed/i18n/mui-locale`) maps the active
  language onto MUI's locale table for `createTheme`; it throws on
  unknown tags rather than silently pairing a Chinese UI with English
  locale text, and is identity-stable per language. The subpath keeps
  MUI out of the main entry's import graph — consumers without MUI
  never resolve it.
- **Namespace names are bare keys** — `[A-Za-z][A-Za-z0-9_-]*`. A
  scoped npm-style name like `@speed/tokens` is refused: a namespace
  is a short key hosts write in `useTranslation('...')`, not a package
  identifier.

## Boundaries and pitfalls

- **Never another language's text.** Do not configure fallbacks: the
  instance is pinned against cross-language fallback, and a key
  missing in the loaded language renders as the key itself and fires
  the handler. An unknown *browser language* resolving to the `zh-CN`
  negotiation default is a different rule (a documented, overridable
  negotiation default) — it is not a licence to fall back on
  translations.
- **Register exactly once per instance**, never inside a component or
  provider — the double-registration guard throws. A gap that appears
  after registration cannot be driven through this package's API: no
  per-key removal exists, by design.
- Registration on a **bare i18next instance** is refused — `createI18n`
  is what pins the supported set and the no-fallback options; there is
  no other way to build a compliant instance.
- An empty translation is refused at registration (silence is
  indistinguishable from a dropped key); so is nesting deeper than
  plain records.
