# 示例应用：AI 微笑模拟平台

> `examples/reference-app` 不是可有可无的 demo，而是每个模块的**强制第一消费者**。模块 API 没有被它真实用起来，就不算完成。

脚手架的第一消费者定为一个**真实的商业需求**——牙科 AI 微笑模拟 SaaS（患者上传面部照片，AI 生成换牙后的效果图）。选它不是为了做牙科生意，而是因为它恰好压满了通用 SaaS 的每一条边：多层级组织（DSO 集团/多门店）、按次消费、长耗时 AI 任务、媒体处理、对外分享、敏感数据合规、第三方集成。**压满各条边的需求会在接入时暴露脚手架的设计缺陷——这份需求的验证价值即在于此。**

## 需求归属划分

| 需求 | 由脚手架提供 | 由 reference-app 自研 |
|---|---|---|
| 诊所账号、团队与角色 | `authn` + `rbac` + `org` | — |
| 多门店 / DSO 多层级 | `org` 组织树 + 子树数据范围 | 门店业务字段 |
| 患者照片上传 | `storage` 预签名直传 + EXIF 剥离 | 照片与病例的业务关联 |
| AI 换牙生成 | `ai-gateway` 图生图 + `jobs` 异步 + 进度 | **面部分割/掩膜/inpainting 管线、提示词工程、牙齿色号参数** |
| 重新生成 | `jobs` 幂等与重试 | 重生成的业务规则 |
| Before/After 对比 | `ui-kit` 基础组件 | **对比滑块交互** |
| 信用点 / 用量 | `billing` credits 预扣-退还 + `metering` | 每次生成消耗几点的定价 |
| 订阅计费 | `billing` + Stripe | 套餐设计 |
| 患者分享链接 | `sharing` 令牌 + 过期 + 访问统计 | 分享页视觉设计 |
| 下载 / 分享结果 | `storage` 预签名 | — |
| 管理后台与分析 | `admin` + `admin-shell` + 用量汇总 | 业务专属报表 |
| 白标品牌 | 前端三层主题 + `config` 租户覆盖 | — |
| SMS/邮件自动送达 | `notification` 模板 + 异步投递 | 文案内容 |
| CRM / GoHighLevel 集成 | `integration` 外发 Webhook + API Key | 字段映射 |
| 患者数据合规 | `compliance` 字段加密 + 审计 + 保留删除 | 业务侧的最小必要采集 |
| 案例接受率追踪 | — | **全部业务自研** |

这张表本身就是脚手架的价值证明：**左列一次建设、处处复用；右列才是每个项目真正差异化的部分。**

## 关键验证链路

reference-app 必须完整跑通这条链路：

```
诊所注册（社交登录）→ 创建集团与门店（多层级）→ 邀请医生并分配角色
→ 购买点数包（国内/国际两种支付）→ 上传患者照片（直传+EXIF剥离）
→ 发起 AI 生成（预扣点数 → 异步任务 → 进度展示）
→ 失败自动退点 / 成功产出结果 → 生成患者分享链接（带过期）
→ 短信通知患者 → 用量与账单在后台可见 → 触发外发 Webhook 到模拟 CRM
```

这条链路覆盖了绝大多数模块；链路真正跑通之前，判断"哪里是脚手架 API 设计问题"要以各分段缺口为准（见下），整链验收是 [15 里程碑路线图](15-roadmap.md) M4 行的出口条件。

> **实施状态注记：** 上面这条链路是 [15 里程碑路线图](15-roadmap.md) M4 行（"完整业务闭环全链路跑通"）定义的出口条件，不是当前已跑通的现状——已接通的是 `internal/smilesim/service.go` 的包注释记录的 `go/ai-gateway` + `go/jobs`（经 `go/storage` 存取照片）；链路里的"短信通知患者"一段尚未接上 `go/notification`，"用量与账单在后台可见"一段尚未与 `go/billing`/`go/metering` 及 `admin` 侧展示打通。各分段能力（购买点数、AI 生成、分享链接、外发 Webhook 等）均已各自真实验证，只是尚未串成这一条端到端链路；分段上的缺口记录在各模块 `AGENTS.md` 的 Deferred 清单，属于分段状态，不是脚手架 API 设计问题。

**关于真实 AI 调用的成本控制**：图像生成是要真金白银付费的，且依赖第三方账号与配额。因此分两种运行方式——**端到端测试用录制回放**（首次用真实 API 录制响应与产物，之后回放，既稳定又零成本）；**真实 API 调用只在里程碑人工验收和对外演示时执行**。把真实调用放进每日 CI 会持续烧钱，且第三方限流会让 CI 变得不稳定。

## 明确的边界

reference-app 是**验证工具与演示载体**，不是要做成商业产品。AI 图像管线（分割、掩膜、身份保持）只做到"能产出可信结果"即可，不做效果调优——那是业务项目的核心竞争力，不是脚手架要解决的问题。

## 宿主面：共享组装与宿主专属装配

参考应用的宿主面（`cmd/server` + `internal/app`）与 `saasctl new` 生成的骨架分成两层：

- **宿主中性内核**（平台模块 `github.com/vislake/speed/go/app`）：存活探针端点与其挂载规则、预认证允许列表、挂载路由标签播种、启动与优雅停机生命周期、authn 挂载路径常量，以及固定中间件链（`go/app/chain`）与无导入接缝桥接闭包（`go/app/bridges`）——它们此前是仓库里逐字节双副本的 `internal/hostcore` 文件，现在两份宿主改为共同 import 这一个模块。`tools/check_host_composition.py` 是钉住"单一来源"的门：任一宿主在自己的代码里重新声明内核符号、或在非测试代码里重新长出内核语句（serve 循环、`/healthz`、`/metrics`、`/api/v1/authn` 字面量），都会让它变红。改共享宿主行为＝改 `go/app`；只属于一个宿主的行为不进内核，留在该宿主自己的文件里。
- **宿主专属装配**：装配本身（`BuildServer`/`buildServer`）、中间件链上宿主自有的附加项（租户状态解析器、impersonation 装饰器、rbac/org 路由守卫、demo 身份层）、bootstrap 配置面（参考应用经 `pkgcore/config` 装载器解析，骨架仍手工解析 `APP_*`——两侧**有意不同**，机制对齐留待后续），以及全部业务路由。`SubjectResolver` 家族与 demo 身份层是两个宿主的有意不共享项，不进内核、不被强行统一。

内核调用之外的进程启动时序——信号接线、配置装载、`obs.Init` 与退出清理 defer——同样留在宿主、不进内核：两个宿主的 `run()` 在这几行上只是形状相近（共享形状十二行、宿主专属十三行，同量级），抽成统一启动助手需要配置类型泛型、装配签名适配与观测选项回调等注入槽，把线性可读的启动顺序换成参数框架，不成比例，因此裁决不抽；`ServeUntilShutdown` 已是启动/停机骨架的完整本体，两个宿主的 `run()` 薄到只剩宿主专属装配加一行内核调用。
