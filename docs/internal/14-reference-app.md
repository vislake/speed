# 示例应用：AI 微笑模拟平台

> `examples/reference-app` 不是可有可无的 demo，而是每个模块的**强制第一消费者**。模块 API 没有被它真实用起来，就不算完成。

脚手架的第一消费者定为一个**真实的商业需求**——牙科 AI 微笑模拟 SaaS（患者上传面部照片，AI 生成换牙后的效果图）。选它不是为了做牙科生意，而是因为它恰好压满了通用 SaaS 的每一条边：多层级组织（DSO 集团/多门店）、按次消费、长耗时 AI 任务、媒体处理、对外分享、敏感数据合规、第三方集成。**这份需求已经暴露出原方案 6 个重大缺口，本身就证明了它的验证价值。**

## 需求归属划分

| 需求 | 由脚手架提供 | 由 reference-app 自研 |
|---|---|---|
| 诊所账号、团队与角色 | `authn` + `rbac` + `org` | — |
| 多门店 / DSO 多层级 | `org` 组织树 + 子树数据范围 | 门店业务字段 |
| 患者照片上传 | `storage` 预签名直传 + EXIF 剥离 | 照片与病例的业务关联 |
| AI 换牙生成 | `ai-gateway` 图生图 + `jobs` 异步 + 进度 | **面部分割/掩膜/inpainting 管线、提示词工程、牙齿色号参数** |
| 重新生成 | `jobs` 幂等与重试 | 重生成的业务规则 |
| Before/After 对比 | `ui-kit` 基础组件 | **对比滑块交互** |
| 信用点 / 用量 | `billing` credits 预扣-退还 + `metering` | 每次生成消耗几点的定价 |
| 订阅计费 | `billing` + Stripe | 套餐设计 |
| 患者分享链接 | `sharing` 令牌 + 过期 + 访问统计 | 分享页视觉设计 |
| 下载 / 分享结果 | `storage` 预签名 | — |
| 管理后台与分析 | `admin` + `admin-shell` + 用量汇总 | 业务专属报表 |
| 白标品牌 | 前端三层主题 + `config` 租户覆盖 | — |
| SMS/邮件自动送达 | `notification` 模板 + 异步投递 | 文案内容 |
| CRM / GoHighLevel 集成 | `integration` 外发 Webhook + API Key | 字段映射 |
| 患者数据合规 | `compliance` 字段加密 + 审计 + 保留删除 | 业务侧的最小必要采集 |
| 案例接受率追踪 | — | **全部业务自研** |

这张表本身就是脚手架的价值证明：**左列一次建设、处处复用；右列才是每个项目真正差异化的部分。**

## 关键验证链路

reference-app 必须完整跑通这条链路：

```
诊所注册（社交登录）→ 创建集团与门店（多层级）→ 邀请医生并分配角色
→ 购买点数包（国内/国际两种支付）→ 上传患者照片（直传+EXIF剥离）
→ 发起 AI 生成（预扣点数 → 异步任务 → 进度展示）
→ 失败自动退点 / 成功产出结果 → 生成患者分享链接（带过期）
→ 短信通知患者 → 用量与账单在后台可见 → 触发外发 Webhook 到模拟 CRM
```

这条链路覆盖了 19 个模块中的绝大多数。跑不通的地方，就是脚手架 API 设计有问题的地方。

**关于真实 AI 调用的成本控制**：图像生成是要真金白银付费的，且依赖第三方账号与配额。因此分两种运行方式——**CI 中的 e2e 用录制回放**（首次用真实 API 录制响应与产物，之后回放，既稳定又零成本）；**真实 API 调用只在每个里程碑的人工验收和对外演示时执行**。把真实调用放进每日 CI 会持续烧钱，且第三方限流会让 CI 变得不稳定。

## 明确的边界

reference-app 是**验证工具与演示载体**，不是要做成商业产品。AI 图像管线（分割、掩膜、身份保持）只做到"能产出可信结果"即可，不做效果调优——那是业务项目的核心竞争力，不是脚手架要解决的问题。
