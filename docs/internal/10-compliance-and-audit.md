# 合规与操作审计

> 范围已明确：提供通用合规能力（同时满足 GDPR、国内个保法与医疗类项目的基础要求），不做 HIPAA 认证。
>
> **注意交付分期**：本文档描述的能力不全在 `compliance` 模块、也不全在同一个阶段交付。**加密与脱敏的机制在 `dbkit`（M0）**，**审计采集在 M1**，`compliance` 模块（M4）承担的是治理层——保留策略、归档、检索报表、被遗忘权、数据可携带。这样安排是因为数据保护必须早于数据产生，详见 [15 里程碑](15-roadmap.md)。

## 数据治理能力

按已确认的范围：**做通用合规能力，不做 HIPAA 认证**。这些能力同时满足 GDPR、国内个保法与医疗类项目的基础要求，属于通用资产。

- **字段级加密**：`dbkit` 提供 GORM Serializer，敏感字段（身份证、手机号、健康相关数据）声明 tag 即自动加解密；密钥从环境变量注入，支持密钥轮换（保留旧密钥解密能力）。
- **加密字段的查询：盲索引（必须一并设计，否则加密会直接卡死登录流程）**。加密后的密文无法索引查询，但手机号既要加密存储、又要作为登录标识被查询——这两条要求直接冲突。解法是每个需要等值查询的加密字段配一个**盲索引列**：存 `HMAC(secret, normalize(明文))` 的确定性哈希，加索引，查询时对输入做同样变换后比对。
  - 用 HMAC 而非裸哈希，防止彩虹表反查；HMAC 密钥与加密主密钥分开管理
  - 查询前必须**归一化**（手机号统一 E.164、邮箱小写化），否则同一个值算出两个索引
  - 盲索引只支持**等值查询**，模糊搜索（如"手机号后四位"）需要额外设计，默认不提供
  - 密钥轮换时盲索引需整表重算，属于计划内的迁移任务，走 `jobs` 批处理
- **完整操作审计**：详见本文档「操作审计」一节，这是独立成体系的能力。
- **数据保留与删除**：按租户可配置保留期，到期自动清理（走 `jobs` 定时任务）；支持"被遗忘权"式的按主体删除，级联清理关联的媒体文件与派生资源。
- **数据导出**：按租户/按主体导出全部数据（数据可携带权），异步生成打包文件并经 `sharing` 下发。
- **PII 日志脱敏**：日志与 trace 中的敏感字段自动打码，在 `observability` 的日志封装里默认启用（默认安全，而非默认泄漏）。
- 明确不做：BAA 签署流程、云厂商合规配置、HIPAA 专项审计报告——这些强依赖具体项目的部署环境与法务，留给业务项目。

## 操作审计：记录用户与管理员的所有操作

**先划清边界**（与 [09 可观测性](09-observability.md) 的运维日志是两回事，不能互相替代）：审计日志是**业务合规资产**——长期保留、结构化可检索、可作为追责证据、租户自己也要能看；运维日志是排障用的，短期留存、面向工程师。用 Loki 存审计日志是错的，反之亦然。

**统一事件模型**（六要素齐全，缺一不可）：

```go
type AuditEvent struct {
    Actor      Actor       // 谁：user / platform_admin / api_key / system，含 ID 与显示名
    OnBehalfOf *Actor      // 模拟登录时的真实操作者，见下
    Action     string      // 做了什么："org.member.remove" / "billing.plan.change"
    Resource   Resource    // 对什么对象：类型 + ID + 显示名（删除后仍可读）
    Result     Result      // 成功 / 失败 + 失败原因
    Changes    *Diff       // 变更前后值（敏感字段脱敏）
    Context    Context     // 时间、IP、User-Agent、地理位置、TraceID、租户
}
```

**采集方式：自动为主，声明为辅**
- 写操作由 `dbkit` 的 GORM 回调**自动捕获** before/after 差异，业务代码零侵入。这是关键——依赖开发者手写审计代码，必然会漏。
- 敏感**读**操作（查看患者照片、导出数据）需要显式标注 `audit.RecordAccess(ctx, ...)`，因为读操作太频繁，全记会淹没有效信息。
- 采集经事件总线异步落库，不阻塞主流程；但审计写入失败必须告警，不能静默丢弃。

**管理员操作与模拟登录（最需要审计的场景）**
- 平台运营人员的所有操作全量记录，不做读操作豁免。
- **模拟登录（impersonation）期间的每一条审计记录都必须双重身份**：`Actor` = 被模拟的用户，`OnBehalfOf` = 真实的管理员。否则事后追查会看到"用户自己删了数据"，实际是管理员操作的——这是运营后台最容易出的责任事故。
- 模拟登录的开始与结束本身也是审计事件，且应触发对被模拟用户的通知（对应 [07 平台服务](07-platform-services.md) 中不可关闭的安全类通知）。

**不可篡改**
- 只允许追加写，应用使用的数据库角色被剥夺该表的 UPDATE/DELETE 权限（生产 PG 用权限约束 + 触发器双保险）。
- **与"过期归档"的调和**：禁止 DELETE 与保留期清理看似矛盾，解法是**按时间分区 + 整分区归档**——归档任务由一个独立的、仅有分区管理权限的数据库角色执行：先将整个分区导出到对象存储，再 `DROP PARTITION`。全程不存在"删除某几行"的能力，因此篡改单条记录的路径依然被堵死。归档动作本身也是一条审计事件。
- 可选**哈希链**：每条记录包含前一条的哈希，任何篡改都会断链，提供校验工具。默认关闭（有写入成本），对合规要求高的项目开启。

**查询与留存**
- 按操作者 / 资源 / 动作 / 时间范围 / 结果检索；租户管理员只能看本租户，平台管理员可跨租户。
- 审计量大，按时间分区 + 冷热分离；保留期可配置（默认 1 年），过期归档到对象存储而非直接删除。
- 支持导出审计报告（CSV/JSON），走 `jobs` 异步生成 + `sharing` 下发。
