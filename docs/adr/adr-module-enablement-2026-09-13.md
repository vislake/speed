# 启用与否由模块自己表态

## 状态

已接受

## 背景

一个二进制中被 import 进来的模块，未必都该在本次运行中跑起来：连接信息没有配置的后端实现跑不起来，同一功能的多个实现之间只能有一个生效。因此需要一种机制决定本次运行启用哪些模块。

判断所需的知识分布不均：模块自己清楚它需要哪些配置、齐备到什么程度才能工作，而这份知识不在宿主手里，也不在注册表手里。

同一功能的排他交付已经由交付声明表达。这个约束与启用判断直接相关：一个排他功能有几个提供者要求生效，取决于它们各自是否启用。

## 考虑过的选项

### 配置中的集中清单

配置数据的顶层保留一个模块名列表，注册表读取它得出启用集，未列出的模块不参与任何阶段。

**否决**：清单与模块的配置分处两地，新增一个模块要改两处，漏改一处的表现是模块静默不工作。清单也无法表达"配了远程后端就用它，否则用内存实现"这类默认行为，那需要写清单的人预先知道配置的内容。

### 由宿主在代码中决定

宿主读取配置，自行判断并告知注册表启用哪些模块。

**否决**：判断依据是每个模块各自的配置语义，宿主要为它使用的每个模块重写一遍这套判断；而"依据配置决定启用哪些模块"正是框架要提供的机制，落到宿主头上等于没有提供。

### 模块在 Prepare 阶段自行表态

配置就位后，配置模块之外的每个已注册模块在 `Prepare` 中表态启用、禁用或交由消解决定，注册表据此消解排他冲突得出启用集。

**采纳**，见决策。

## 决策

采纳：`Prepare` 阶段对配置模块之外的全部已注册模块执行，每个模块依据自己的配置表态，注册表消解排他冲突后得出启用集。

表态有三种：`StateEnabled`、`StateDisabled`、`StateAuto`。`StateAuto` 表示不与他人冲突即启用，是零值，未声明 `Prepare` 回调的模块等同于表态 `StateAuto`。

消解只针对排他交付：传播后某功能仍有多个启用的提供者，且其中至少一个声明排他，即为失败。被传播禁用的排他者不再主张独占，余下互不排他的提供者照常并存。

多个排他提供者同时留到裁决时选择失败，而非任选其一或全部禁用：任选会让启动结果不确定，全部禁用则把失败推迟到某个依赖它的模块，届时错误已经离成因很远。传播也只禁用排他的默认实现，不动非排他的，否则一个注定落选的排他实现会连带掐掉同功能里其他非排他的默认实现。

一个模块可以排他地交付多个功能，消解因此先传播后裁决：有显式启用者的功能，其声明排他且取默认表态的提供者被禁用；随后按剩余的启用提供者裁决。待消解的功能与各模块的表态取自表态收齐时的快照，不随传播改变；若让它们在随禁用收缩的集合上求值，结论会取决于遍历顺序。表态禁用的模块不把排他主张带进消解。

禁用必须给出原因，随启动诊断输出。

配置中不存在模块清单，模块名不出现在配置数据里。

## 后果

判断落在掌握判断依据的那一方，模块新增或改名都不牵动任何集中清单。

`StateAuto` 让默认实现成为一等公民：内存实现声明排他并表态 `StateAuto`，远程实现在配置齐备时表态启用，"配了远程就用远程，否则用内存"无需任何人预先编排。退让的一方必须自己声明排他，否则两者会在裁决时判为冲突。

禁用原因使"启动起来了却缺一部分功能且无人察觉"这一失败在启动时即可见。

排他冲突在消解阶段一次暴露，早于任何构造。

**接受的代价：**

- 宿主失去统一的否决点。一个由传递依赖间接引入、宿主并不知情的模块，只要自己表态启用且不与他人冲突，就会真的运行起来。是否提供关闭开关由各模块自行决定，机制不作要求，因此"能不能关掉某个模块"在不同模块之间可能不一致。
- "本次运行启用了哪些模块"无法从配置读出，要从各模块的判断逻辑与启动诊断中得到。
- 判断标准由各模块自行定义，同类模块之间可能给出不一致的判断口径。
- `Prepare` 对配置模块之外的全部已注册模块执行，未启用的模块也付出一次回调的代价。

## 失效条件

若实践中大量模块的表态逻辑退化为读取同一个开关，说明集中清单才是真正被需要的形态，届时该开关应当上升为机制的一部分。
