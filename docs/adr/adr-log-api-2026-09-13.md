# 日志以标准库 slog 为调用面

## 状态

已接受

## 背景

日志被每一个模块使用，调用面一旦确定，全部模块的日志调用点都绑定其上，更换的代价随模块数量增长。

`log/slog` 是标准库，提供结构化日志的记录、属性与后端扩展点 `slog.Handler`。接口包不引入第三方依赖这条架构不变量因此不构成障碍。

主流第三方日志库都提供了 `slog.Handler` 适配，后端的接入点已经收敛到这一个接口上。

功能标识的元素类型必须是接口，`*slog.Logger` 是具体类型，不能直接作为模块之间取用的功能。

## 考虑过的选项

### 定义自有的日志接口

根包定义 `Logger` 接口，方法为 `Debug`/`Info`/`Warn`/`Error` 与 `With`，每种后端各写一层适配。

**否决**：调用点绑定在一套与标准库能力重合的 API 上，而这套 API 要重新定义 slog 已经定义的语义——属性分组、级别判断、记录裁剪。`slog.Attr` 的免分配路径经过 `...any` 适配层后失效。后端适配也要重写一遍：第三方库提供的是 `slog.Handler` 适配，自有接口用不上它们。

### 每种后端各登记一个日志模块，功能接口是按名取 logger 的工厂

`log/text`、`log/json`、`log/file` 各自登记一个模块并实现同一个工厂接口，宿主 import 哪个就用哪个。

**否决**：按模块命名、按模块过滤级别、上下文富化与脱敏都与后端无关，这样划分会让它们在每个后端里各实现一遍并逐渐分化。这些逻辑可以在根包的处理链里实现一次并对全部后端一致生效，后端只需回答"记录怎么编码"与"字节往哪写"，这正是格式与目的地这两处扩展点的划分。该划分还让格式与目的地自由组合，而按后端分模块的做法要为每种组合各准备一个模块。

### 以 slog 为调用面，后端经扩展点接入

模块调用点直接使用 `*slog.Logger`；根包交付按名取 logger 的功能，其实现唯一；后端的多样性由格式与目的地扩展点承载。

**采纳**，见决策。

## 决策

采纳：日志的调用面是标准库的 `*slog.Logger`，本项目不定义自己的日志 API。

模块之间取用的功能是 `log.Logger`，其唯一方法按模块名返回 `*slog.Logger`。该功能的实现唯一，位于 `pkg/log` 根包，处理链在此组装。后端的多样性经格式与目的地扩展点表达，不经由多个日志模块。

## 后果

模块的日志调用点使用标准库类型，不依赖本项目的任何日志 API。宿主已有的 slog 生态——`slog.Attr`、`slog.Group`、第三方 `slog.Handler`——直接可用。

新增一种后端不改动根包，也不新增模块：实现一个格式或一个目的地，以资源声明交付。

**接受的代价：**

- `*slog.Logger` 与 `slog.Handler` 进入模块作者与本模块之间的契约。标准库对它们的演进本项目无从控制，其行为变化会直接到达全部调用点。
- slog 丢弃 `Handler.Handle` 的返回值，写入失败在调用点不可见。失败的处置因此只能由目的地实现自己承担，见 [log](../design/modules/design-log.md) 的错误与失败语义。
- 调用点能够绕过本模块直接构造 `*slog.Logger`。这样得到的 logger 不经过处理链，脱敏与富化都不生效。

## 失效条件

标准库停止演进 `log/slog`，或第三方后端不再提供 `slog.Handler` 适配而转向另一个统一接口，则本记录的前提不再成立。
