# 模块之间按接口类型取用，依赖不满足即启动失败

## 状态

已接受

## 背景

模块在构造时需要取得它所依赖的其他模块的实例。取用方式决定了几件事：`core` 是否需要认识具体功能、类型错误在何时暴露、同一功能存在多个实现时的行为，以及依赖不满足在何时被发现。

`core` 承载模块机制本身，不应认识任何具体功能的接口。一旦认识，每新增一种功能都要修改 `core`。

构造必须按依赖的拓扑序进行，所以依赖关系要在构造开始之前就是已知的。

配置驱动的系统中，最危险的失败不是启动不起来，而是启动起来了但缺失了一部分功能，且无人察觉。

## 考虑过的选项

### 按名称取用

`deps.Get("cache")` 返回 `any`，调用方自行断言类型。`core` 只需处理字符串键，与具体功能完全无关。

**否决**：类型错误全部推迟到运行期；调用方必须知道被依赖模块返回的具体类型，实际上形成了一条不经编译器检查的隐式契约；名称是约定，拼写错误无法被发现。

### 按接口类型取用，依赖不声明

以接口类型为键匹配已构造的实例，但模块不声明自己需要什么：需要哪些依赖，在构造函数实际取用时才体现，构造顺序据此按需推导。

**否决**：依赖关系要到构造执行中才暴露，缺失、歧义与成环都只能在构造途中发现，而此时已有实例存在，需要逆序清理；模块声明什么也无从校验。

### 按接口类型取用，依赖显式声明

以接口类型为键匹配，且模块在描述符中声明自己需要哪些功能、交付哪些功能。接口定义在功能模块的接口包中，依赖方 import 接口包而非实现子包。`core` 借助泛型与反射完成匹配，自身不认识任何具体接口。

**采纳**，见决策。

## 决策

采纳：模块之间以接口类型为键取用彼此，且依赖与交付都在描述符中显式声明。匹配域是声明了该功能的模块：单值取用要求其中恰好一个已构造，多值取用整体返回全部已构造的。

- 声明落在功能上，不落在模块身份上。依赖指向"谁提供这个接口"，替换实现不影响依赖方。
- 声明是唯一权威：一个产物碰巧实现了某功能却未声明，取用时看不到它。装配期校验与运行期取用因此面对同一个集合。
- 交付声明可标注排他，表示本模块独占该功能。排他是提供方对自身的声明，不是对该功能的全局断言，因此不要求各提供者声明一致：任何一个排他声明被违反即启动失败。未声明排他的功能可有多个提供者并存，整体取出，不允许静默挑一个。
- 解析在任何业务模块构造之前完成：必需的功能没有提供者、依赖成环，都在此暴露，此时只有配置模块已构造，按回滚规则关闭。单值取用的唯一性要求发生在取用点，排他冲突则更早，在消解阶段。
- 构造完成后断言声明的每个功能都已交付，声明与实际交付的偏离在产生它的那次构造上暴露。
- 可选依赖显式声明为可选，其缺失是一种合法配置，不构成错误。

## 后果

依赖方只 import 功能的接口包，实现由 import 决定，实现的第三方依赖不会传染给依赖方。

`core` 不认识任何具体功能，新增功能不改 `core`。

缓存这类本应独占的功能声明排他后，同时启用两个实现在启动时即被拒绝，不会静默选中其中之一。多个支付渠道、多个通知通道这类正当的并存需求不声明排他，整体取出，与独占取用互不干扰。

依赖缺失表现为启动失败而非功能缺失，部署错误在第一时间暴露，且暴露在任何资源被建立之前。

**接受的代价：**

- 匹配依赖反射，其代价发生在启动期；错误在编译期不可见，只在启动时暴露。
- 声明与代码可能偏离：声明了却不取用只能由评审发现；取用了却不声明则构造顺序失去保障，这一侧由交付断言覆盖。
- 构造期依赖必须无环，相互引用的模块只能不声明这条关系，改在接线阶段动态取得（[ADR-lifecycle-stages-2026-09-13](adr-lifecycle-stages-2026-09-13.md)）。
- 排他是提供方的声明而非功能自身的属性，功能的定义方无法强制它，违反只能在启动时发现而非编译期。一个本应独占的功能，若它的提供者都没有声明排他，机制不会察觉。
- 并存的实例取出时不带模块名，需要按名字路由时，该名字必须由功能接口自己提供。
- 接口包与实现子包的分离成为贯穿全部功能模块的结构约定，新增模块必须遵守。

## 失效条件

若大量本应独占的功能因无人声明排他而在运行期才暴露冲突，说明排他不该由提供方各自声明，而应随功能定义，届时需要一种让功能定义方表达独占性的机制。
