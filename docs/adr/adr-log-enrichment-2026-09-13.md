# 上下文字段由富化扩展点在 handler 层附加

## 状态

已接受

## 背景

日志需要携带请求级的关联字段：追踪标识、租户标识、请求标识。这些字段让一条日志能被追溯到它所属的请求、追踪与租户，缺了它们，多租户系统的日志无法按事故范围查询。

产生这些字段的是追踪、租户这些模块，它们在依赖图中位于日志之上。日志被每一个模块 import，反向依赖任何一个都会使依赖图成环，而 OTel 这类追踪库是第三方依赖，落进接口包还会违反接口包零第三方依赖这条架构不变量。

字段的取值随每一次调用的上下文变化，同一个 logger 在不同请求中要给出不同的值。

`slog.Handler` 的 `Handle` 方法接收 `context.Context`：不带上下文的 `Logger.Info` 传入的是 `context.Background()`，带上下文的 `Logger.InfoContext` 传入调用方的上下文。

## 考虑过的选项

### 根包认识这些字段并直接读取

`pkg/log` 定义 `trace_id`、`tenant_id` 等字段名，从上下文中直接读出它们。

**否决**：读取追踪标识要 import 追踪库，读取租户标识要 import 租户模块。import 追踪库把第三方依赖带进接口包，import 租户模块使依赖图成环。字段集合还会随新模块增长，每增加一种关联维度都要改动被所有人 import 的根包。

### 取用 logger 时附加

取 logger 的函数接收上下文，当场把该上下文携带的字段附到返回的 logger 上。

**否决**：这样得到的 logger 只对取它的那一个上下文正确，模块因此不能持有 logger，每个进入请求路径的函数都要重新取一次，而一次疏漏就产生一条张冠李戴的关联字段——错误的关联比没有关联更难排查。富化还会按取用次数执行，而不是按记录数执行，级别过滤挡不住它：被级别丢弃的记录同样付出了富化的代价。

### 由 handler 在每条记录上附加

根包定义富化扩展点，实现以资源声明交付；处理链中的一层在 `Handle` 内按该次调用的上下文取字段并附到记录上。

**采纳**，见决策。

## 决策

采纳：`pkg/log` 根包定义富化扩展点 `Enricher`，它从上下文中取出若干属性；实现由产生这些字段的模块以资源声明交付，根包不认识其中任何一个字段。

富化在处理链的 handler 层执行，对每条通过级别过滤的记录执行一次，取的是该次调用传入的上下文。

富化器按声明它的模块名字典序依次执行，属性依次追加，重名属性不去重也不覆盖。

## 后果

`pkg/log` 对 `trace_id`、`tenant_id` 这类字段一无所知，不 import 任何产生它们的模块，依赖方向保持自下而上。

新增一种关联维度不改动 `pkg/log`：新模块交付一个富化器即可，已有的日志调用点自动获得该字段。

模块可以在构造时取一次 logger 并长期持有，字段依然逐条正确。

**接受的代价：**

- 调用点必须使用带上下文的方法（`InfoContext` 等）。用 `Info` 得到的是 `context.Background()`，富化静默缺席——不报错，只是少几个字段。这是一种沉默的失败，只能由评审与文档约束。
- 每条通过级别过滤的记录都要遍历全部富化器。富化器在上下文不含相关值时应当返回 `nil` 以避免分配，但这是对实现方的要求，不是机制上的保证。
- 富化器之间互不知情。多个富化器给出同名属性时，记录中会出现重复的键，消费端看到哪一个取决于它自己的解析规则。
- 富化器以资源声明交付，在 `Run` 之前即固定。运行期新增关联维度不可能，这与配置是启动快照一致。

## 失效条件

若出现一种关联字段，其取值无法从上下文中取得，则本记录对该字段不适用：富化扩展点的输入只有上下文。
