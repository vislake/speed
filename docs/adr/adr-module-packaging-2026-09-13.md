# 发布单元按功能划分，实现拆为子包

## 状态

已接受

## 背景

speed 以库的形式交付：宿主通过 `go get` 引入所需模块，编译进自己的二进制。因此每一个落入 speed 的第三方依赖，都会出现在宿主的 `go.mod` 与 `go.sum` 中。

同一种功能通常有多种实现，各自绑定不同的第三方库。缓存功能的内存实现无外部依赖，Redis 实现需要 Redis 客户端库。只使用内存实现的宿主不应背负 Redis 客户端。

Go 的依赖裁剪按 import 路径可达性计算：`go mod tidy` 后，宿主的依赖清单只包含它实际 import 到的包的传递依赖。这一机制在包粒度上生效，不要求实现位于独立 module。

## 考虑过的选项

### 单一 module 承载全部功能

整个 `pkg/` 树共用一个 `go.mod`。仓库结构最简单，模块间相互引用无需版本协调。

**否决**：该 `go.mod` 的 `require` 列表是全部实现的依赖之并集，任一实现引入的第三方库都会进入每个宿主的依赖图，与库交付形态直接冲突。

### 每种实现各自独立 module

功能与实现都是 module，`pkg/cache` 与 `pkg/cache-redis` 平级。依赖隔离由 module 边界强制。

**否决**：依赖隔离用子包已经达成，独立 module 不带来额外隔离效果，却要为每个实现付出 `go.work` 条目、CI 矩阵行、版本标签与跨 module 版本协调的成本。Go module 是发布的粒度，按发布节奏划分；把它挪用为打包手段会让发布单元的数量随实现数量增长。

### 每种功能一个发布单元，实现为其子包

`pkg/<capability>` 是一个 Go module，根包含接口与不引入第三方依赖的公共逻辑，绑定第三方库的实现位于 `pkg/<capability>/<impl>` 子包。

**采纳**，见决策。

## 决策

采纳：`pkg/` 下每个目录为一个发布单元，即一个独立的 Go module，按功能划分；该功能的多种实现拆为它的子包，每个子包独立承担自身的第三方依赖。

实现升格为独立发布单元需要举证，成立条件是该实现需要独立的发布节奏，或消费者会脱离它所属的发布单元单独使用它。

## 后果

宿主的依赖清单由它 import 的包精确决定：只 import 接口包与内存实现的宿主，依赖图中不出现任何远程后端的客户端库。

新增一种实现不改变任何既有消费者的依赖清单。

**接受的代价：**

- 仓库含多个 Go module，开发期需要 `go.work` 协调，发布期需要一致的版本策略。
- 发布单元之间的相互依赖是 module 级依赖，跨发布单元的接口变更需要版本联动。
- 子包边界没有编译器强制：把第三方依赖误写进接口包，编译不会报错，只能由评审与依赖清单检查发现。

## 失效条件

若出现一个实现，其消费者明确要求单独引入，或其发布节奏必须独立，则该实现升格为独立发布单元，本记录对该实现不再适用。
