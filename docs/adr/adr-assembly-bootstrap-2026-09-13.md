# 由注册表先行构造配置模块打破启动循环

## 状态

已接受

## 背景

每个模块都需要先取得自己的配置才能构造，而配置由配置模块提供。配置模块若与其他模块同等对待，就要求它在自己被构造之前就已经可用。

保持配置模块与普通模块同构有实际价值：同一个注册表、同一份描述符、同一条"import 决定可用集"的规则，使得配置源可以像其他功能一样按需引入，不必为它另建一套加载与选择机制。

配置模块与模块机制紧耦合的程度也高于其他模块：其余模块要依据自己的配置表态是否启用，配置因此必须先于表态就位。

## 考虑过的选项

### 配置不是模块

配置加载内建于 `core`，在模块机制启动之前就已就位。没有循环。

**否决**：配置源的可插拔性需要另建一套注册与选择机制，与模块机制并存；同一件事在项目里有两种做法，每新增一种配置源都要面对"它该走哪一套"的问题。

### 两阶段启动

先用一份最小的内置配置构造出配置模块，再由它加载完整配置驱动其余模块。

**否决**：引入了"最小内置配置从何而来"这一新问题，且启动流程需要完整运行两遍，其中第一遍的语义与第二遍不同。

### 描述符中的引导期标记

在描述符中增加一个字段，声明该模块先于配置而构造。任何模块都可以声明它，代价是放弃依赖与配置。

**否决**：为一个只有配置模块会用到的时机增加一个所有模块都看得见的字段，扩大了描述符这一稳定契约的表面；泛化的形式也暗示会有第二个声明者，而实际上不会有。

### 注册表先行构造配置模块

配置模块与普通模块共用注册表与描述符，不需要任何标记。注册表在 `Prepare` 阶段最先构造它，识别依据是约定的模块名。

**采纳**，见决策。

## 决策

采纳：注册表在 `Prepare` 阶段最先构造配置模块，由它完成命令行参数与环境变量的收集、配置源的读取与全局校验；它同时是所有模块的隐含依赖，无需任何模块声明。

这是 `core` 对配置模块的全部特殊处理。两者都不体现为描述符中的任何字段，识别依据是约定的模块名，实现在注册表内部。

配置模块此后与其他模块一视同仁：它照常出现在查询结果中，其他模块照常通过按功能取用取得它。

## 后果

循环断开，启动流程只需运行一遍。

描述符不因这个时机而增加字段，模块作者面对的契约表面不变。

配置模块在注册、查询、依赖取用等各方面与普通模块一致，项目中只有一套模块机制。配置源作为子包按需引入，未被 import 的源其第三方依赖不落到宿主头上。

**接受的代价：**

- `core` 中存在一处按名称识别的特例。它不在契约表面上，但读实现的人会看到，并可能援引为先例；配置模块是唯一享有特例的模块，必须在代码与文档中都写明这一点。
- 配置模块无法通过 `Requires` 声明依赖：它构造时没有任何其他实例存在。它所需的传输与格式因此经资源通道取得，那是唯一在该时刻已经确定的东西。
- 该阶段的失败发生在配置可用之前，错误信息无法借助配置中的任何上下文。

## 失效条件

若出现第二个需要先于配置构造的模块，按名称识别的特例不再成立，届时这个时机需要一个显式的表达形式。
