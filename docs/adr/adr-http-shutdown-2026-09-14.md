# 停机分两拍，Stop 停止接受，Close 等待排空

## 状态

已接受

## 背景

`Stop` 阶段的语义是停止接收新工作、开始排空，按逆依赖序逐个调用；`Close` 阶段释放资源，同样逆依赖序。注册表不对停机施加超时，这些回调必须自己保证有界（[ADR-lifecycle-stages-2026-09-13](adr-lifecycle-stages-2026-09-13.md)）。

`Stop` 与 `Close` 收到的 context 去掉取消、保留值，因而其中的排空不会因为宿主取消而立即返回。

在途请求可以触达进程内任何模块，它所需要的那些模块此刻尚未 `Close`。

各模块的 `Stop` 是逐个调用的：其中一个耗时多久，其后每一个就推迟多久。

## 考虑过的选项

### Stop 中阻塞直到排空完成

入口模块在 `Stop` 里关闭监听器并等待在途请求走完，然后返回。

**否决**：`Stop` 逐个调用，入口在其中阻塞会把其后每个模块的"停止接收新工作"一并推迟。排空期间，任务执行器一类的模块尚未收到 `Stop`，仍在接收新工作——而排空正是为了让系统安静下来。

### 关闭监听器与排空都放进后台协程

`Stop` 立即返回，关闭监听与排空都在协程中进行。

**否决**：`Stop` 返回即承诺不再接受新请求，而协程何时被调度不受调用方控制。承诺与事实之间因而有一段窗口，其中新请求会进入一个已经开始停止的系统。

### 分两拍

`Stop` 同步关闭监听器后返回，`Close` 等待排空。

**采纳**，见决策。

## 决策

采纳：`Stop` 在调用协程内关闭监听器，随即返回，在途请求在后台继续排空；`Close` 等待排空结束，以本模块配置的排空时限为界。

关闭监听器不放进排空协程：`Stop` 返回时，不再接受新请求这件事必须已经成立。

## 后果

全部模块的"停止接收新工作"快速走完，此后才进入逐个释放。

在途请求排空时，它可能触达的模块都还没有 `Close`。

排空时限由本模块自己的配置承载，满足回调必须有界的要求。

**接受的代价：**

- 排空时限到期时仍在途的请求被切断，调用方看到的是连接中断。
- `Stop` 返回后排空仍在进行，排空本身的失败要到 `Close` 才能报出，因而不出现在 `Stop` 阶段聚合的失败里。
- 未曾绑定监听器的实例也会走这两拍，`Stop` 与 `Close` 都必须容忍一个从未监听过的实例。
