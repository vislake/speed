# 模块以 init 隐式注册到进程级注册表

## 状态

已接受

## 背景

装配需要知道本二进制中存在哪些模块。这个集合由 import 决定：模块的实现子包被 import 进来，该实现才可能被启用。import 它的可能是宿主自己，也可能是宿主的某个依赖。

登记的方式有两条路：模块在 `init` 中自行登记，或由宿主在 `main` 中显式把每个模块交给注册表。两者对宿主 `main` 的形态、对全局状态的引入、以及对测试隔离的影响各不相同。

同一进程内需要能够存在多个互不干扰的装配，测试并行运行时尤为如此。

## 考虑过的选项

### 宿主显式登记

模块导出构造描述符的函数，宿主写 `reg.Add(redis.Module())`。不存在全局可变状态，登记顺序由宿主控制，多个装配天然隔离。

**否决**：宿主 `main` 需要为每个模块写两处（import 与登记），两处必须手工保持一致；与既有习惯不符，且该收益可由"描述符部分不可变"这一约束以更低的成本取得。

### 模块 init 隐式登记

模块在 `init` 中把自己登记进进程级注册表，使用方只需 import。凡被 import 进来的模块自动进入可用集。

**采纳**，见决策。

## 决策

采纳：模块在自身 `init` 中隐式登记到进程级注册表，可用集由 import 决定。

该决定附带以下约束：

- 描述符部分在 `Run` 之前写入，此后不可变。
- 重名登记在登记的那一刻直接 panic，不做覆盖。
- 描述符中不得存在任何依赖登记顺序的语义。

## 后果

宿主代码中一个模块只出现一次，即它的 import。增删模块是增删一行。

隐式登记只决定可用集；实例的建立与持有发生在生命周期驱动中。

重名在进程启动时即刻暴露，不会退化为运行期的行为歧义。

**接受的代价：**

- 引入了进程级全局状态。描述符部分不可变，但它的存在意味着"本进程有哪些模块可用"是全进程唯一的。另建的注册表实例拿不到 `init` 期的登记，其中要装配什么就得手工登记什么。模块可以在自注册之外同时导出一个返回自身描述符的函数，供这条路径取用。
- 一个被 import 但从未启用的模块，其 `init` 仍然执行，其代码仍然编译进二进制。
- 可用集是构建的产物而非宿主的声明：宿主的某个依赖引入了一个模块，该模块即进入注册表，宿主未必知情。它是否运行取决于它自己的表态（[ADR-module-enablement-2026-09-13](adr-module-enablement-2026-09-13.md)），而重名冲突在登记的那一刻 panic，冲突的来源可能不在宿主自己的代码里。
- Go 的 `init` 执行顺序只保证包依赖偏序，同层之间不保证，因此任何顺序敏感的机制都不能建立在登记顺序之上。

## 失效条件

若出现需要在同一进程内让不同注册表看到不同可用集的场景，`init` 期写入单一全局表的做法不再足够，登记需要改为可按注册表区分，本决定失效。
