# 上下文字段由产生方绑定到 logger，经 context 传递

## 状态

已接受

## 背景

日志需要携带请求级的关联字段：追踪标识、租户标识、任务标识。这些字段让一条日志能被追溯到它所属的请求、追踪与租户，缺了它们，多租户系统的日志无法按事故范围查询。

产生这些字段的是追踪、租户、任务这些模块，它们在依赖图中位于日志之上。日志被每一个模块 import，反向依赖任何一个都会使依赖图成环，而追踪库是第三方依赖，落进接口包还会违反接口包零第三方依赖这条架构不变量。

字段的取值按请求变化，同一份代码在不同请求中要给出不同的值。

`slog.Logger.With` 把属性交给 handler 预处理并留在其状态里，此后每条记录复用该结果。`slog.Logger` 的每个级别方法都有带上下文与不带上下文的版本，都是这个类型的正常用法。

## 考虑过的选项

### 根包认识这些字段并直接读取

`pkg/log` 定义 `trace_id`、`tenant_id` 等字段名，从上下文中直接读出它们。

**否决**：读取追踪标识要 import 追踪库，读取租户标识要 import 租户模块。import 追踪库把第三方依赖带进接口包，import 租户模块使依赖图成环。字段集合还会随新模块增长，每增加一种关联维度都要改动被所有人 import 的根包。

### 由 handler 逐条富化

根包定义富化扩展点，实现以资源声明交付，处理链中的一层在每条记录上按该次调用的上下文取字段并附加。

**否决**：它要求调用点一律使用带上下文的方法，而带与不带上下文的方法都是 `slog.Logger` 的正常用法，约定只用其中一套无从检查——写成不带上下文的版本不报错，只是静默地少几个字段。它还放弃了 `With` 的预处理：属性改为每条记录重新求值并追加，而预处理后的属性本可以在全部记录间复用。多个富化器之间互不知情，重名属性也无从协调。

### 由产生方绑定到 logger，经上下文传递

根包提供上下文的存取，产生字段的模块在自己的注入点把字段绑到 logger 上并写回上下文，下游从上下文取 logger。

**采纳**，见决策。

## 决策

采纳：`pkg/log` 根包提供 logger 与 `context.Context` 之间的存取，不提供任何字段。

产生关联字段的模块在自己的注入点——HTTP 中间件、任务执行器——取出上下文中的 logger、绑上自己的字段、把结果写回上下文。根包不认识其中任何一个字段，也不 import 任何产生它们的模块。

请求路径中的日志调用从上下文取 logger，使用不带上下文的普通方法。

## 后果

`pkg/log` 对 `trace_id`、`tenant_id` 这类字段一无所知，依赖方向保持自下而上。新增一种关联维度不改动 `pkg/log`，也不改动任何已有的日志调用点。

字段经 `With` 绑定一次，由 handler 预处理后在该请求的全部记录间复用，逐条记录不重复求值。

调用点使用 `slog.Logger` 的常规方法，不必在两套方法中挑选。

**接受的代价：**

- 沉默失败没有消除，分两级：注入点漏绑一个字段，记录少几个属性；上下文里没有 logger 或直接用了进程根 logger，记录完整却落在进程根 logger 的目的地上。两级都不报错。
- 带上下文的路径不能使用进程根 logger，那一个不带任何请求字段。
- 带上下文的路径依赖上游注入过 logger，而框架无从在装配时校验注入点是否齐备。`FromContext` 在没有 logger 的上下文上回落到进程根 logger：记录照常写出，不中断调用方，但进的是标准输出而非宿主配置的目的地。日志调用因此在任何上下文上都成立，代价是漏了注入表现为日志出现在别处——可察觉，但不产生任何失败信号。
- 注入点的位置决定了字段的覆盖范围。在中间件链中位置靠后的注入点，其字段对更外层已经产生的日志不生效。

## 失效条件

若 `slog` 提供一种由 handler 在记录时读取上下文、且不依赖调用点选择方法的机制，则逐条富化不再有本记录所列的代价，届时应重新评估。
