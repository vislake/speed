# 模块以统一的资源声明对外暴露元数据

## 状态

已接受

## 背景

模块需要向外声明一批只读的元数据，供其他模块或注册表查询：本模块接受哪些启动参数、提供哪些 HTTP API、提供哪些 gRPC 服务、携带哪些国际化资源、带有哪些数据库迁移。

这类需求没有尽头。每支持一种，都会面对同一个问题：它该以什么形式出现在模块的描述符里。

描述符是模块作者与注册表之间的稳定契约，被每一个模块依赖，因此增加字段的代价很高。

## 考虑过的选项

### 每种元数据一个具名字段

描述符上为配置 schema、API spec、国际化资源等各设一个字段，注册表保存，消费方按字段读取。

**否决**：描述符随横切机制的数量线性增长，而每一次增长都改动被所有模块依赖的稳定契约。注册表还要为它不理解的字段留出位置，其中每一个都是一处只对某个特定模块有意义的知识。

### 不设机制，各机制自行收集

不在描述符里留位置，需要元数据的机制各自定义一套登记方式，模块分别向它们登记。

**否决**：同一件事在项目里会有多种做法，模块要在不同机制间重复登记，登记时机也各不相同；配置这类必须在最早期收集齐的元数据，无法保证在它需要的时刻已经登记完毕。

### 统一的资源声明，按类型查询

描述符上只有一个 `Resources` 字段承载全部对外元数据。资源的类型由需要它的模块定义，注册表原样保存，消费方按类型查询。

**采纳**，见决策。

## 决策

采纳：模块以描述符上单一的 `Resources` 字段对外声明全部只读元数据，注册表提供按类型的查询，自身不解释任何一种资源。

- 资源类型由需要它的模块定义，例如 `config.Schema` 由配置模块定义，`http.Spec` 由 HTTP 模块定义。
- 查询结果携带声明它的模块名。资源是被动数据，无法自报身份，而消费方几乎总要用到它。
- 资源是静态声明，在 `Run` 之前确定，此后不变。模块的资源随描述符在 `init` 期登记，宿主自己的资源在 `main` 中登记。需要依赖配置才能决定的内容不是资源，而是运行期交互，走功能取用完成。
- 描述符上保留具名字段的判据是注册表自身是否要解释它：模块名、依赖声明、交付声明与阶段回调是排序和驱动所必需的，其余一律是资源。

## 后果

新增一种横切机制不修改 `core`，也不影响任何无关模块：定义一个资源类型，需要它的模块声明，机制自己收集。

`core` 不认识配置、API、国际化中的任何一个，模块化基础设施与具体机制彻底分离。

判据明确之后，"该不该给描述符加字段"不再逐次争论。

资源的静态性使查询在任何阶段都给出确定结果，配置这类必须在最早期收集齐的元数据因此有保证。

**接受的代价：**

- `Resources` 的静态类型是 `any` 的切片，声明时填入无关类型不会被编译器拦下，只在消费方按类型查询时表现为"查不到"，而非一个明确的错误。
- 资源的语义分散在各个定义它的模块中，描述符本身不再能回答"这个模块对外声明了什么"，要回答这个问题必须遍历全部资源类型。
- 同一模块可以声明同一类型的多个资源，是否允许由消费方各自规定并校验，机制本身不作约束。

## 失效条件

若出现一种元数据必须由注册表自己解释才能完成驱动，它就不属于资源，届时需要为它增加具名字段，判据本身不受影响。
