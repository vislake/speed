# 配置只承载启动必须项，运行期参数归设置

## 状态

已接受

## 背景

应用程序的参数有两类来源不同、变更频率不同的需求：数据库连接信息这类在进程启动前就必须就位的参数，与限流阈值、功能开关这类运行期需要调整、且可能按租户取不同值的参数。

用同一套机制承载两者，会迫使该机制同时满足"启动前可用"与"运行期可变"两个互斥的约束。

缺少判据时，两类参数的边界会随每次新增参数而漂移。

## 考虑过的选项

### 单一参数机制

主配置源承载全部参数，运行期可变的部分通过重新读取它来实现。

**否决**：运行期可变的参数需要按租户取值、需要变更审计、需要不重启生效，这些要求会把配置机制推向一个带存储、带通知、带版本的子系统；而启动期参数恰恰要求机制足够简单，在数据库可用之前就能工作。

### 两套机制，按判据划界

配置承载启动必须项，从文件或远程配置源读取；设置承载运行期参数，存放于数据库，由独立模块承载。

**采纳**，见决策。

## 决策

采纳：配置与设置分为两套机制，划界判据为：

- 一个值属于配置，当且仅当它在数据库可用之前就被需要。
- 需要按租户或按运行时场景取不同值的，一定属于设置。

配置由 `pkg/config` 承载；设置由独立模块承载，依赖数据库模块，位于依赖图上层。模块对设置的依赖是一次普通的模块依赖，不使用任何特殊通道。

## 后果

判据是自举的：设置存放于数据库，则把数据库连接起来所需的一切必然是配置，此外全是设置。边界不随新增参数漂移。

配置机制得以保持简单：单向、只读、无存储。

模块的配置结构体体量本身成为信号：它膨胀，说明其中大部分应当迁往设置。

日志级别、限流阈值、功能开关、通知模板均属于设置。启动阶段所需的日志级别由配置中的引导级别承担，设置就位后接管。

**接受的代价：**

- 同一个模块可能同时需要配置与设置，其参数分散在两处，使用者需要知道去哪里改。
- 设置不可用时（数据库未就绪、查询失败），依赖设置的模块需要各自定义降级行为，这一负担落在模块而非机制上。
- 判据依赖"数据库"这一具体设施作为分界线，模块作者要先知道设置存在何处才能判断一个值归哪边。

## 失效条件

若设置改换存储，"数据库可用之前"这一分界线不再指向同一时刻，划界判据需要重新锚定到新的设施。
