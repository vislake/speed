# 主配置源唯一，环境变量与命令行作为覆盖层

## 状态

已接受

## 背景

配置可以来自文件、远程配置中心、环境变量、命令行等多种来源。来源的组合方式决定了一个配置值的可追溯性。

同层来源合并（多个文件、或文件与远程配置中心同时生效并按优先级合并）会使"这个值究竟来自哪里"成为排障时的常见困难。

与此同时，用环境变量覆盖配置中的个别条目是容器化部署的常规需求，不能取消。

配置定位符必须在读取配置之前就确定，因此不能出自配置本身。这类先于配置的输入要保持贫瘠，一旦膨胀就成为第二套配置系统。

## 考虑过的选项

### 多源同层合并

所有被 import 的配置源全部生效，按各自声明的优先级合并为一份配置数据。

**否决**：一个值的来源需要在多个同层源之间推断；新增一个源会改变既有配置的解析结果，且这种改变不体现在配置源本身。

### 主源二选一，无覆盖层

引导时指定唯一的配置源，此外不接受任何覆盖。

**否决**：取消了环境变量覆盖单个条目的功能，容器化部署下需要为每处差异维护一份配置文件。

### 主源唯一，跨层单向覆盖

主配置源至多一个，由配置定位符以 URI scheme 选定；环境变量与命令行参数各自作为独立的覆盖层，覆盖配置数据中的单个标量条目。

**采纳**，见决策。

## 决策

采纳：配置来源分层，同层不合并，跨层单向覆盖，层次自低向高为：配置声明中的默认值、主配置源、环境变量、命令行参数。

- 主配置源由配置定位符指定，形如 `file:///etc/app.yaml` 或 `etcd://host:port/key`。定位符只能有一个值，主源唯一性因此无需额外校验即成立。定位符也可以不给出，此时没有主配置源，其余各层照常工作。
- 定位符的 scheme 决定由哪个配置源模块解析；scheme 对应的模块未被 import 时，启动失败并指明缺失的 import。
- 每个输入项在声明中标明自己接受哪些来源。环境变量名按前缀与路径映射派生，也可在声明中钉死；命令行长名不派生，接受命令行的输入项必须给出它，因为命令行是人机界面，名字应当刻意选取。
- 容器类型基本不接受这两层覆盖，例外是字符串列表：它可以逗号分隔给出，整体替换而非追加。映射与结构体列表没有同样通行的扁平表达，只认主配置源。

## 后果

任一配置值的来源可以精确定位到唯一一层，排障时不需要在同层来源之间推断。

先于配置的输入只有配置定位符与环境变量前缀。

新增一种配置源是新增一个子包与一个 scheme，不影响既有配置的解析结果。

**接受的代价：**

- 无法表达"基础配置文件加环境覆盖文件"这类多文件分层，需要此形态的部署方只能在生成配置时合并，或改用环境变量层。
- 数组与映射只能整体在主配置源中修改，无法用环境变量或命令行做局部调整。
- 命令行参数处于全局命名空间，两个模块给出同名参数即为冲突，只能由其中一方改名。

## 失效条件

若多文件分层成为多数部署方的常规需求，同层合并的排障代价将小于其带来的便利，主源唯一的约束需要重新评估。
