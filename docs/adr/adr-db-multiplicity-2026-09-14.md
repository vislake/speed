# 配置交付一个库，额外的连接由调用方经接口自建

## 状态

已接受

## 背景

模块之间只按功能取用彼此，不按名称取用（架构不变量 9）。取用一个功能时，`Resolve` 要求恰好一个提供者，多于一个即失败。

数据库功能有多种实现，每种绑定一个方言的驱动。同一个进程 import 了多个实现时，它们都进入可用集。

迁移集由各模块声明，在 `Migrate` 阶段统一应用（[ADR-db-migration-2026-09-14](adr-db-migration-2026-09-14.md)）。一条迁移要施加到某个库上。

访问第二个库是真实需求：读写分离的只读副本、另一个系统的库、一次性的数据迁移来源。这些库与本进程的模块装配无关——没有模块声明它们的迁移，也没有模块需要把它们当作自己的依赖来取用。

## 考虑过的选项

### 多个库都经模块机制交付

多个实现同时启用，取用方用 `ResolveAll` 整体取出后按名路由，名字由功能接口自己提供。

**否决**：按名路由正是架构不变量 9 排除的取用方式，而多库没有别的区分手段——依赖声明落在功能上，表达不了"依赖其中某一个"。迁移随之要回答每一条施加到哪个库，迁移资源因此要带目标库标识，而标识的取值同样只能是名字。整个装配面从"取用一种功能"退化为"取用一个具名实例"。

### 一个进程只连一个库，不提供别的途径

数据库功能排他交付，此外没有建立连接的手段。

**否决**：访问第二个库的需求不会因此消失，只会转移——调用方自己 import 驱动去连，而那样得到的连接不带本模块安装的任何插件，也不带加密序列化器，且脱离任何生命周期管理。把一个真实需求堵在模块之外，换来的是一条没人看得见的旁路。

### 配置交付一个库，额外的连接经接口自建

数据库功能仍然排他交付，配置给出的那个库经模块机制交付；需要另一个库的调用方从交付的实例上自建连接。

**采纳**，见决策。

## 决策

采纳：数据库功能排他交付，配置给出的那个库是唯一经模块机制交付的；额外的连接由调用方从该实例自建。

import 了多个实现而其中多于一个表态启用时，消解阶段判为 `ErrExclusiveViolated`，启动终止。

自建的连接与交付的那个装配一致：同样装好已声明的插件与加密序列化器，取用方因而不会因为换了个库就失去这些。它不施加任何迁移，也不由本模块持有——调用方自己关闭它。

## 后果

取用数据库功能的模块拿到唯一的实例，不需要区分取到的是哪一个。

迁移集有唯一归宿：一条迁移施加到配置给出的那个库上，迁移资源不需要携带目标库标识。

读写分离、访问另一个系统的库、一次性的数据来源，都有一条在模块之内的途径，不必绕过本模块自己 import 驱动。

冲突暴露在消解阶段，不留到取用时。

**接受的代价：**

- 自建连接的生命周期由调用方负责。漏关就是连接泄漏，本模块不持有它们，也就无从代为释放。
- 自建连接的库，其 schema 由调用方保证。迁移机制只覆盖配置给出的那个库，第二个库上缺表的表现是运行期的查询失败。
- 自建连接的方言与被启用的实现相同。连接另一种引擎的库，要求那个引擎的实现也被启用，而排他不允许。
- 自建的连接不出现在任何声明里。谁连了哪些库，从描述符看不出来，只能从代码里看。

## 失效条件

若出现一种部署形态，其第二个库同样需要迁移、需要参与依赖定序、或需要被别的模块按功能取用，则"额外连接在模块机制之外"不再成立，多库需要重新进入装配面。
