# 中间件的顺序由功能标识声明的约束决定，数值只在约束未定之处起作用

## 状态

已接受

## 背景

中间件由彼此独立的模块贡献：追踪、认证、租户、限流、恢复各自是一个模块，各自在链上占一层。层与层的先后影响正确性——按身份分支的层必须位于认证之后，否则它分支所依据的身份尚未确定。

模块之间不按名称取用，入口模块不认识任何具体功能（架构不变量 2 与 9）。新增一种横切机制不应修改入口模块。

中间件的登记发生在 `Init` 阶段，该阶段按依赖序驱动；`Prepare` 阶段内不保证顺序（架构不变量 7）。

进程中存在哪些中间件不由宿主决定：模块的注册发生在 `init`，宿主的某个依赖引入的模块同样进入可用集，宿主未必知情（[ADR-module-enablement-2026-09-13](adr-module-enablement-2026-09-13.md)）。

## 考虑过的选项

### 顺序固定在入口模块内

入口模块按一个写定的顺序组装链，各中间件对号入座。

**否决**：入口模块要认识每一个贡献中间件的功能才能给它安排位置，与"不认识任何功能"相悖；新增一种横切机制要修改入口模块，而入口模块被每一个带 API 的模块依赖。

### 只用数值优先级

每个中间件声明一个整数，链按数值排列。

**否决**：数值的含义来自全局协调，而模块无从知道别人取了什么值。由间接依赖引入的中间件尤其如此——宿主不知道它存在，它也不知道宿主装了什么，两边都给不出一个有依据的数值。取值相同的两层之间先后不定，而这正是需要定的场合。

### 只用功能标识声明的约束

每个中间件声明自己相对哪些功能靠内或靠外，链按拓扑序组装。

**否决**：与任何具体功能都无关的位置诉求表达不出来。恢复层要位于最外层，依据是"任何一层崩溃都应被它接住"，这不指向任何一个具体功能；用约束表达它，等于要求它点名进程中每一个中间件。

### 约束决定先后，数值在约束未定之处起作用

两种表达并存，各自承担一类诉求。

**采纳**，见决策。

## 决策

采纳：中间件以功能标识声明 `After` 与 `Before` 作为硬约束，链按拓扑序组装；以 `Order` 声明数值偏好，它只在硬约束未定的自由度内决定先后。

两种表达在结构上不会冲突：`Order` 只在约束允许的位置之间选择，选不出违反约束的位置。约束之间成环即启动失败，错误点名环上各成员。

约束引用的功能在本次装配中没有提供者时，该约束自动满足。

`Order` 相同且互无约束关系的中间件之间，先后由登记的先后决定。

## 后果

表达相对位置无需协调数值：声明一条指向功能的约束即可，而功能标识是模块之间本就在用的指代方式。

与具体功能无关的位置诉求由数值承担，声明它的中间件不必点名任何人。

入口模块不认识任何具体功能，新增一种横切机制不修改它。

组装出的链在启动时是确定的，可以逐层列出。

**接受的代价：**

- 数值仍是全局协调的量。两个都要求位于最外层的中间件之间，先后只能由数值分出，而它们互相不知道对方取了什么值。
- 约束引用的功能没有提供者时，约束静默消失：声明"位于认证之后"的中间件在没有认证模块的进程里照常运行，位置不再受任何约束，而这不产生失败信号。这与可选依赖缺失时的静默同源。
- 登记先后作为最终裁决，其确定性来自 `Init` 阶段的依赖序。互无依赖关系的模块之间的先后由 `core` 的依赖序线性化给出，不是本模块的承诺，也不是 `core` 对外承诺的契约。
- 一个中间件的位置取决于本次装配中有哪些别的中间件，同一个模块在两个宿主里可能落在不同的层数上。

## 失效条件

若实际装配中绝大多数中间件都只声明数值、不声明约束，则两种表达并存没有换来它所付出的机制复杂度，排序应当收敛为单一表达。
