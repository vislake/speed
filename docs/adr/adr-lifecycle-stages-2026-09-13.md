# 生命周期分为八个阶段

## 状态

已接受

## 背景

模块在启动过程中要做的事分属不同时机，且彼此有先后约束：

- 配置必须先于一切就位，命令行参数与环境变量的收集、校验都发生在其余模块构造之前。
- 构造需要按依赖的拓扑序进行，因此构造期的依赖关系必须无环。
- 模块之间实际存在相互引用。两个模块互相需要对方的情形在业务代码中是常态，而它无法表达为拓扑序。
- 数据库迁移要在全部产物构造完成之后、任何模块开始工作之前完成：更早则构造仍可能失败，而失败的启动不该已经改过库结构；更晚则接线与启动面对的是尚未迁移的 schema。
- 一个对外入口开始接受流量后，请求可以到达进程中的任何模块，不只是该入口声明依赖的那些。
- 关闭要分两步：先停止接收新工作让在途请求排空，再释放资源。

用单一的构造回调承载这些时机，上述约束就只能靠模块之间的口头约定维持。

## 考虑过的选项

### 构造与启动两个阶段

模块只声明构造与启动，关闭时对称地声明停止。最少的概念数量。

**否决**：无法表达循环引用，因为构造是唯一能取得依赖的时机，而构造必须按拓扑序；也无法表达"在所有模块启动之后再接受流量"，入口只能在自己的启动回调里监听，此时其他模块未必就绪。

### 按需增设阶段

先只定义构造与启动，遇到解决不了的时机再加阶段。

**否决**：阶段集合是模块作者与注册表之间的契约，每增加一个阶段都会改变已有模块的假设；渐进增设意味着这个契约长期不稳定，而它被每一个模块依赖。

### 八个阶段

`Prepare`、`New`、`Migrate`、`Init`、`Start`、`Serve`、`Stop`、`Close`，每个阶段对应一个上述约束。

**采纳**，见决策。

## 决策

采纳：生命周期分为 `Prepare`、`New`、`Migrate`、`Init`、`Start`、`Serve`、`Stop`、`Close` 八个阶段，由注册表按固定顺序驱动。

其中几处划分各自解决一个具体问题：

- **`Prepare` 对配置模块之外的全部已注册模块执行，阶段内不保证顺序。** 配置在此最先构造（[ADR-assembly-bootstrap-2026-09-13](adr-assembly-bootstrap-2026-09-13.md)），其余模块随后依据自己的配置表态是否启用，注册表据此消解得出启用集（[ADR-module-enablement-2026-09-13](adr-module-enablement-2026-09-13.md)）。该阶段内模块之间没有先后依赖。
- **`New` 与 `Init` 拆开。** `New` 按拓扑序构造，其依赖必须无环；`Init` 运行时全部实例均已存在，相互引用在此成立。存在环的引用不在依赖声明中出现，改由 `Init` 阶段动态取得。
- **`Serve` 独立于 `Start`。** `Start` 按依赖序启动模块自身的服务，不接外部流量；`Serve` 在全体 `Start` 完成之后运行，入口在此开始接受流量。依赖序表达的是"在其依赖之后"，而入口需要的是"在所有人之后"。

关闭对称地分为 `Stop` 与 `Close`：`Stop` 停止接收新工作并开始排空，其失败不中断该阶段；`Close` 释放资源，失败被聚合后一并返回。

## 后果

循环依赖有了确定的出路，不必为了避免环而扭曲模块边界，也不必让依赖声明支持环。

入口模块无需知道进程中还有哪些模块，就能保证流量到达时全体就绪。

排空与释放分离，在途请求面对的是一个仍然完整的系统。

每个模块只声明自己参与的阶段，未声明的阶段对它没有开销。

**接受的代价：**

- 阶段数量构成模块作者的学习成本：写一个模块要先判断自己的动作属于哪个阶段，放错阶段的后果（在依赖就绪前访问它，或在流量到达后才完成初始化）不会在编译期暴露。
- 环上的引用不出现在依赖声明中，模块之间的这条关系在描述符里看不出来，只能从 `Init` 的代码中读出。
- 阶段集合是稳定契约，新增阶段会改变已有模块的假设，因此后续增设的代价很高。

## 失效条件

若出现第二类必须落在 `Migrate` 的动作而它与迁移无关，说明这个阶段的名字过窄，它承载的其实是"资产收齐之后、开始工作之前"这一更一般的时机；同理，若没有模块声明 `Prepare`，说明配置就位与构造之间不存在需要占位的时机。
