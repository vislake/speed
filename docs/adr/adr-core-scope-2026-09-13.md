# core 驱动生命周期，但不编码应用形态

## 状态

已接受

## 背景

装配一个应用是高度定制的工作。同一套模块可以组成对外提供 HTTP 服务的进程、提供 gRPC 服务的进程，或者不暴露任何入口、只跑后台作业的进程。这些形态在监听什么、何时开始接受流量、如何退出上各不相同。

模块机制本身则是共通的：模块怎么登记、怎么被查询、按什么顺序构造、在哪些时机被回调。

把两者放进同一个包，意味着每支持一种新形态都要修改被所有模块 import 的那个包。

## 考虑过的选项

### core 提供面向宿主的装配入口

`core` 导出 `Assemble` 一类的入口，读取配置、解析启用集、构造模块、驱动生命周期，宿主调用它即可得到一个装配好的应用。

**否决**：这样的入口要交付"一个装配好的应用"，就必须对形态做出决定，而 HTTP、gRPC、后台三种形态的差异会以选项、开关或分支的形式回流到 `core`，使被所有模块 import 的包随形态数量增长。被否的是入口对形态的编码，不是入口本身。

### core 只提供注册表与描述符，不驱动生命周期

`core` 退到纯数据结构：登记、查询，不调用任何回调。生命周期由宿主或上层自行驱动。

**否决**：阶段顺序、依赖排序、失败回滚是模块之间的契约而非某个宿主的偏好；交给宿主各自实现会让同一个模块在不同宿主中被以不同顺序调用，模块也就无法跨宿主复用。

### core 提供注册、查询与生命周期驱动

`core` 承载描述符、注册表、按功能的查询，以及按固定阶段驱动回调，并在需要顺序的阶段按依赖排序。形态由模块与宿主决定：HTTP、gRPC 这类入口自己就是模块，在入口阶段开始监听。

**采纳**，见决策。

## 决策

采纳：`core` 的职责限于模块的核心数据结构、注册、查询与生命周期驱动。它提供一个形态无关的驱动入口，宿主调用它推进全部阶段；入口不认识任何形态，也不为形态提供选项。

应用形态由模块承载：HTTP、gRPC 等入口各自是模块，在入口阶段开始接受流量。宿主的 `main` 决定 import 哪些模块、何时驱动启动与停止。

## 后果

`core` 不随应用形态的增加而变化。新增一种形态是新增一个模块，被所有模块 import 的那个包不受影响。

同一个模块在 HTTP 进程与后台进程中被以相同的顺序、在相同的时机调用，因而可以跨形态复用。

宿主保留对启动流程的控制：`core` 被调用，不调用宿主。

**接受的代价：**

- 宿主拿不到形态模板：路由怎么组织、监听什么地址、退出信号如何转成 `ctx` 取消，都要自己写。
- 「按阶段驱动、消解启用集、按依赖构造」这段共通逻辑虽然由 `core` 驱动，但"组成什么样的应用"没有任何模板，新项目需要自己搭出第一个 `main`。这部分由脚手架而不是由 `core` 承担。

## 失效条件

若绝大多数宿主在 `main` 里写出的形态代码最终雷同，说明形态的差异没有预期的大，届时应当把那个共同形状固化下来，但归宿是一个独立的模块，仍不是 `core`。
