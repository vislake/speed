# 脱敏内置于日志根包，不可关闭

## 状态

已接受

## 背景

明文凭据与令牌进入日志是安全缺陷：日志的留存期长于凭据的有效期，传输与存储的访问控制弱于凭据本身，一次误记录等同于一次泄露。

日志的后端可替换，脱敏必须对每一种后端一致生效，否则换一个目的地就换一套保护。

凭据的命名与形状是通用词汇——`secret`、`token`、`password`、`Bearer` 前缀、JWT 形状——不属于任何一个业务模块的领域概念，识别它们不需要 import 任何模块，也不引入第三方依赖。

明文 PII 的情形不同：键名空间随业务代码增长（联系邮箱、手机号、住址、姓名），且没有一种值形状能把 PII 与普通标识符分开。

关联字段的取值可能形似令牌。按形状匹配的规则会误伤它们，而关联字段被改写等同于失去关联。

## 考虑过的选项

### 作为与富化同机制的可选扩展点

脱敏规则由模块以资源声明交付，根包只提供执行位置。

**否决**：安全属性变成装配选项。没有 import 任何脱敏实现的宿主得到的是一个不脱敏的日志系统，而它与脱敏正常工作的系统在启动时表现完全相同——失败是无声的，只在泄露发生后才被发现。富化缺席只是少几个字段，脱敏缺席是明文凭据落盘，它们不应共用同一种"可以没有"的机制。

### 独立发布单元，由宿主显式装配

脱敏是一个独立的模块，宿主 import 并注册它。

**否决**：与上一条同理，只是把漏装的位置从依赖清单挪到了装配清单。它还要求宿主知道存在这么一个东西并且必须装上，而宿主最可能忽略的恰恰是这类不装也能跑起来的安全组件。

### 内置根包，但提供配置开关

脱敏在根包内实现，配置中可以关闭或调整规则。

**否决**：提供开关等于提供关掉它的途径。关闭脱敏的理由在排查现场总是显得充分——看不到完整值就定位不了问题——而关掉之后重新打开依赖于人记得这件事。规则可配还会让脱敏行为随环境变化，同一份代码在两处的安全边界不同。

### 内置根包，不可关闭

脱敏是处理链中的固定一层，位于扇出之前，无配置开关也无逐调用开关。

**采纳**，见决策。

## 决策

采纳：脱敏是 `pkg/log` 根包内置的处理链一层，位于扇出之前、各目的地之上，因而对每一种目的地与格式一致生效。它没有配置开关，也没有逐调用的豁免途径。

覆盖范围按类别声明，而非声称完整：

- **凭据与令牌**：覆盖。按键名词干匹配（逐段匹配点分路径与属性组名），整条替换；再以值形状作为兜底网，就地遮蔽。
- **明文 PII 与完整 prompt**：不覆盖。这是记录在案的类别级缺口，由调用点负责不把它们写进日志。

关联字段按精确名豁免于值形状匹配，豁免在键名规则之前判定。

## 后果

经由本模块取得的 logger，其输出一定经过脱敏，无论宿主装配了哪些目的地与格式。

脱敏规则的变更是根包的代码变更，经由代码评审，不经由配置。

**接受的代价：**

- 根包维护一套会随凭据命名习惯生长的词干表与形状规则。它被每一个宿主 import，其变更波及全部宿主。
- 每条记录的全部属性都要遍历，属性组要递归进入。这是固定开销，无法按调用点免除。
- 不覆盖明文 PII 与完整 prompt。声称"日志已脱敏"而据此放松调用点的自律，会在这两类上落空。
- 绕过本模块直接构造的 `*slog.Logger` 不经过这一层。该构造途径是标准库的能力，本模块无从禁止。

## 失效条件

若出现一种目的地，其写入路径不经过 `slog.Handler`，则本记录对该目的地不适用：脱敏的执行位置是处理链，绕开处理链的写入不在其覆盖范围内。
