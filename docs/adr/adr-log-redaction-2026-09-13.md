# 脱敏机制内置于日志根包且不可关闭，规则由登记提供

## 状态

已接受

## 背景

明文凭据与令牌进入日志是安全缺陷：日志的留存期长于凭据的有效期，传输与存储的访问控制弱于凭据本身，一次误记录等同于一次泄露。

日志的后端可替换，脱敏必须对每一种后端一致生效，否则换一个目的地就换一套保护。

哪些键与哪些值承载敏感内容，取决于业务与所接入的外部服务：字段叫什么由业务代码决定，凭据的标记形式由各供应方决定，都随时间变化。日志模块不认识任何业务领域的词汇，也无从预知宿主接入了谁。

按字段名匹配与按值形状匹配都可能误伤：关联字段的取值可能形似令牌，而被改写的关联字段等同于失去关联。是否误伤同样只有知道字段含义的一方判断得了。

## 考虑过的选项

### 作为可选的扩展点

根包定义脱敏规则的接口并提供执行位置，实现由模块以资源声明交付，宿主 import 需要的那些。

**否决**：安全属性变成装配选项。没有 import 任何脱敏实现的宿主得到的是一个不脱敏的日志系统，而它与脱敏正常工作的系统在启动时表现完全相同——失败是无声的，只在泄露发生后才被发现。漏掉一个功能模块通常会在取用时暴露为启动失败，漏掉脱敏什么也不暴露：它没有取用方，日志照常写出，只是不再遮蔽。

### 独立发布单元，由宿主显式装配

脱敏是一个独立的模块，宿主 import 并注册它。

**否决**：与作为可选扩展点同理，只是把漏装的位置从依赖清单挪到了装配清单。它还要求宿主知道存在这么一个东西并且必须装上，而宿主最可能忽略的恰恰是这类不装也能跑起来的安全组件。

### 内置根包，但提供配置开关

脱敏在根包内实现，配置中可以关闭或调整规则。

**否决**：提供开关等于提供关掉它的途径。关闭脱敏的理由在排查现场总是显得充分——看不到完整值就定位不了问题——而关掉之后重新打开依赖于人记得这件事。规则可配还会让脱敏行为随环境变化，同一份代码在不同环境下的安全边界不同。

### 机制内置根包，规则全部来自登记

脱敏的机制在根包内实现且不可关闭，但根包不预置任何规则；日志组件实例提供登记接口，知情的模块与宿主把自己的敏感键名与值形状登记进来。

**采纳**，见决策。

## 决策

采纳：脱敏是 `pkg/log` 根包中处理链的固定一层，位于扇出之前、各目的地之上，因而对每一种目的地与格式一致生效。它没有配置开关，也没有逐调用的豁免途径。

**根包提供判定的机制，不提供任何规则。** 规则集初始为空，内容全部来自日志组件实例的登记接口；登记可以发生在任意时刻，**只可追加，不可移除**。

不预置规则的理由是根包没有判断的依据：它不认识任何业务领域的词汇，而凭据的命名与标记形式随生态和业务两头变化。预置清单只能是猜测——猜漏了给出虚假的安全感，猜错了则误伤，而误伤没有补救途径，因为规则不可移除。知情的一方才有资格登记：业务模块知道自己的凭据字段叫什么，宿主知道自己接入了哪些供应方。

由此，本记录保证的是**记录一定经过脱敏层**，而不是敏感内容一定被遮蔽。经过脱敏层由处理链的结构保证，与装配无关；遮蔽什么则取决于登记了什么，由登记方负责。

**判定面的边界由规则的作用对象划定**：键名规则作用于属性的键路径，值形状规则作用于解析后的字符串值与错误文本。不落在这些对象上的内容，判定面够不到，登记也补不上。这是判据，界外的情形不限于已知的那些——记录的消息不是属性；包装值的内部字段不成为独立属性；键名自身承载的内容是比对的对象而非被检查的内容；字符串与错误之外的值不进入形状判定。

应对都在调用点：敏感内容作为独立属性、以字符串或错误的形态写出，键名用固定的名字。

作为独立属性写出的明文 PII 落在判定面之内：它有键名，登记键名即可遮蔽，与凭据走同一条路（塞进包装值的 PII 字段则与凭据一样够不到）。它的特殊之处在登记一侧——PII 中形状明确的那部分（邮箱、按 E.164 写的手机号、可校验的卡号）登记值形状即可覆盖，而姓名、地址、自由文本没有可判定的形状，只能逐个登记键名；PII 的键名空间又比凭据大得多，遗漏的概率因而更高。

## 后果

经由本模块取得的 logger，其输出一定经过脱敏层，无论宿主装配了哪些目的地与格式；该层不可关闭，也无从绕过。

根包不随任何业务的凭据命名习惯变更，它不持有规则。规则的增减是登记方自己的代码变更，波及范围止于登记它的那个宿主进程。

**接受的代价：**

- **没有任何模块登记时，脱敏层什么也不遮蔽。** 这是规则集初始为空的直接后果：机制在位不等于内容被保护。装配一个日志模块并不自动获得任何脱敏覆盖，宿主要自己确认关心的类别都有人登记。
- 覆盖面因而是装配的结果，不是本模块的承诺。"日志已脱敏"这句话在本项目里只意味着记录经过了脱敏层，据它放松调用点的自律会落空。
- 每条记录自带的属性都要遍历并解析，属性组要递归进入，`WithGroup` 打开的组名要进入键路径；绑定的属性只在绑定时走一次。延迟求值的属性因而在脱敏这一层就被解析，即便它最终不含敏感内容。判定之后还要重建记录才能把解析结果带给下游。这些开销无法按调用点免除，规则集为空时也照常付出。
- **登记只对此后的判定生效，而判定发生在两个不同的时刻。** 记录自带的属性按写出时刻的规则集判定，先于登记写出的不会被回溯处理；而经 `With` 绑定到 logger 上的属性在绑定时就已判定完毕，此后每条记录复用那次结果——一个长期持有的 logger，其绑定属性受**绑定时刻**的规则集约束，登记发生在绑定之后就管不到它。模块应当在自己的 `New` 中、取得 logger 之前完成登记。这只保证自己的规则早于自己的绑定；`New` 按依赖序进行，先构造的模块可能已经绑好了 logger，对它而言后来的登记来得太晚。跨模块的完整覆盖没有时机上的保证。
- 登记的值形状判定由登记方实现，它在每条记录的每个字符串值上执行。一个低效或不终止的判定拖慢的是全进程的日志路径，而脱敏层无从校验它。
- 登记得过宽会误伤自己的字段，而规则不可移除，补救只能是改登记方的代码并重启。
- 绕过本模块直接构造的 `*slog.Logger` 不经过这一层。该构造途径是标准库的能力，本模块无从禁止。

## 失效条件

若出现一种目的地，其写入路径不经过 `slog.Handler`，则本记录对该目的地不适用：脱敏的执行位置是处理链，绕开处理链的写入不在其覆盖范围内。

若登记接口出现移除或关闭规则的需求并被接受，"规则集只增不减"这一性质不再成立，本记录采纳的方案随之失效。
