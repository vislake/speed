# web — the reference-app's consumer shell

The reference app's web frontend: the directory where the `@speed` packages get composed the way a delivered consumer project composes them, and the frontend consumer proof of the whole shipped web surface at once. It deliberately lives at `examples/reference-app/web` — outside the `web/` pnpm workspace, at exactly the location a delivered project occupies — and joins that workspace as an external member (`web/pnpm-workspace.yaml` lists it): it shares the workspace's single frozen lockfile while staying `private`, never versioned, with no changesets fixed-group entry and no release tag.

What ships here is the composition and its tests: the vitest suites bind the real packages — a genuine `@speed/api-client` over a scripted fetch stand-in, a real session, the generated hooks, the packages' own components — through the app's own bootstrap, and pin the composed answers. What does not ship yet is recorded rather than half-built (a real browser page served by the reference-app server, among other items — see Evidence boundary and Deferred).

## Layout

## The composition

`src/main.tsx`'s `bootstrapReferenceApp` is the composition root: a pure function with no module-scope side effects (suites and future harnesses import it safely) that mounts into a caller-supplied container and returns `{ root, i18n, queryClient }`. In order it:

- registers the six namespaces the tree renders from — the five namespace-shipping package families (ui-kit, layout-kit, auth-ui, tenancy-ui, account-ui) plus the app's own `reference-app` bundle — through `registerNamespace`, which validates identical leaf key sets across the supported languages before mutating anything;
- wires the memory session: a `createMemoryAccessTokenStore` store feeding `createAuthSession`, attached once via `attachSession`, with `session.refresh()` filling the api-client's `refreshAccessToken` seam — the same wiring a real host builds, though no journey at this tier rides that leg: the demo-server answers no 401, so the single-flight refresh stays dormant here, its in-form exercise living in the packages' own usage-example suites;
- builds the one api-client: `createClient` over the environment's own `fetch` (captured at construction — the package's injection seam, here a genuine dependency-injection point, which is exactly what lets suites substitute the demo-server stand-in), bound into the generated runtime exactly once through `bindRequestFn`, so all API traffic from here on is generated-code traffic;
- composes the provider tree in the documented order — I18next, theme, QueryClient, app services, the view layer — under StrictMode.

The browser page that mounts this bootstrap, served by the reference-app server, is M4 e2e/html-runner work; the bootstrap's doc comment records that deferral, and until it lands "renders under test harnesses" is the whole of the shipped browser story.

## The view layer

`src/app.tsx` renders `ProductShell` (the auth-core-driven three-branch view machine: signed out, the sign-in surface; signed in with a tenant, the frame; a dead session, the session-ended screen) around the `AppShell` frame, with the nav, the header brand and the user menu all host content computed from the app's own namespace and the server's Public config.

Routing is the app's one hand-rolled slice of chrome: `AppShell` nav items are anchors into the location hash (the package never path-matches — each item carries its own `selected`, computed here), and `useHashRoute` feeds the fragment parser, which knows four content kinds: home, notes, account, and the account surface's binding subroute (`/auth/binding/<provider>?code=<code>&state=<state>` — the completion point of a social binding exchange, the provider validated against the demo provider set so no unknown provider ever drives an exchange). Everything else degrades to home with no nav item selected; there is no 404 chrome in this round. The brand in the AppBar and on the sign-in/home headings is the server's own answer — the same Public `brand.site_name` value the config module serves (`useBrandName`), never a local copy.

The five views:

- `home-view.tsx` — the first real-data surface: the heading is the served brand, the intro is app copy, and each feature card exists only while the flag that gates it is on — the card list is data-driven over go/config's feature list, resolved per key through `useFeature`'s composition on the shared Public-config cache (one `/api/config/public` fetch serves the header brand, this view's brand and both flag checks). The two demo flags exercise both shapes the config module ships: a plain flag (`ai.smile_preview`) and a dependent one (`ai.premium_upsell`, enabled only while its dependency is).
- `notes-view.tsx` — the notes surface: the list read through the generated hooks over a tenant-namespaced query key, gated by `RouteGuard`, and a create flow driven by the create mutation (The gate).
- `account-view.tsx` — the account surface: the account-ui family composed over the app's session and the generated authn API. The session-operating sections receive the session as a prop (the boundary rule: a prop exactly where a session operation exists); the read-only sections take none. Reads and mutations go through the generated hooks over the host's QueryClient, invalidating through the exported query-key builders. The binding subroute renders the same surface with the completion handler on top: it exchanges the `(code, state)` pair over the app's client, invalidates the identities list, and cues the host (`onBound`) — here the app's own navigation back to the account fragment, passed down from the view switch; until that cue lands, the handler rests on its pending notice. The add area's channels are host configuration: the five demo providers, each carrying the redirect URI of the app's own callback route for that channel (the `<origin>/callback/social/<provider>` convention a real deployment serves with its SPA fallback).
- `sign-in-view.tsx` — the anonymous branch: the served brand over auth-ui's `SignInScreen`, with the host's own register surface toggled from the footer. Registration is a destination, not a session operation: the created account (handed to the host through `RegisterForm`'s `onRegistered` — the form never signs in, by package contract) lands in a success state with a way back to the sign-in surface. The whole register-to-sign-in turn is view-local state — nothing here calls login, so the auth-core snapshot never flips.
- `user-menu.tsx` — the AppBar's right-hand cluster: tenancy-ui's `TenantSwitcher` over the demo's two tenants and auth-ui's `SignOutButton`, both host-composed over the session from app services. The demo has no roster endpoint (the server seeds exactly two tenants and grants the accounts the web journeys use membership in both), so the roster is the app's own static data with app-namespace display names; the current tenant comes from the auth-core hook (the principal's own claim, never local memory of a previous switch), and a completed switch evicts the previous tenant's cached rows first — the tenant-namespaced-query-key discipline applied to the cache itself — so after switching, this tenant's caches hold only this tenant's rows.

## The gate

The notes surface carries the shell's real permission gate, and the gate is the list query itself. The server's rbac layer answers a caller without `notes:read` with 403 `rbac.permission_denied`, so the query is the real permission fetch — the router-level gate behind real fetches that earlier rounds' notes deferred to this shell. `RouteGuard`'s `status` maps one-to-one onto the query's own states: no answer yet is `pending` (the guard's spinner), an error is `denied` (the surface fails closed — a refused read means no surface; the guard's default denied branch is ui-kit's `EmptyState` in the `noPermission` variant), a served list is `allowed`. A refetch failure with data still on hand stays `allowed` — the stale list keeps rendering — and only a query with no data can be pending or denied.

The create form lives inside the allowed branch, and a refused create (a caller without `notes:write` answers the same 403) stays on the page with its code text: the write gate is probed by the mutation, never pre-empted client-side. The form's required and length rules (the 4000-character limit kept in step with the server handler) are an experience mirror of the server's own constraint, never a gate themselves.

The list query key is tenant-namespaced (`['tenant', tenantId, ...getNotesListNotesQueryKey()]` over the generated bare key), so a tenant switch can never read the previous tenant's cached notes; the create invalidates exactly that namespaced key.

By design the shell consumes no `/me`-derived permission lists: nothing here calls `usePermission` or attaches `setPermissionSet` — no server endpoint serves permission sets (rbac mounts no HTTP routes), and query-as-permission is this round's answer to the "real permission fetch" item earlier notes deferred to the shell. The `setPermissionSet` host-attach path stays reserved for a future ops-console round that has a roster to attach.

## The demo facts

The demo facts the web journeys exercise exist on two tiers, each citing the other:

- **Server side (real).** `SPEED_DEMO_USERS_PASSWORD` gates three real accounts seeded through the real register route at boot: `demo-owner@example.com` (built-in owner — every permission any module declared), `demo-reader@example.com` (custom `note-reader` role, `notes:read` and nothing else) and `demo-acme-only@example.com` (`note-reader` in `tenant-acme` alone — a grant is a fact about a (tenant, user) pair, never about a user). Memberships live in an in-process roster that does not survive a restart, so a boot against an already-seeded database logs a warning and re-grants nothing. The rbac demonstration additionally keeps the pre-authn `X-Demo-User` header — deliberately still taking precedence over a verified token's Principal (it predates authn; removal is deferred to the org-web round) and never able to affect the tenant half of an authorization subject, which always comes from the `tenancy.Middleware` request context. The Go suites pin all of it end to end through the real composed stack: `cmd/server/demo_users_test.go` and `cmd/server/demo_subject_test.go`.
- **Web side (scripted).** `src/test-utils/demo-server.ts` mirrors those facts for the shell's journeys: one responder answering the endpoints a real reference-app server answers, the demo facts baked in as defaults and every answer overridable per suite — and anything else failing the test loudly, because an unpinned request means the journey reached an endpoint the demo does not serve. Its header cites the Go test lines that pin each mirrored fact (the reader's list served, `demo_users_test.go:135-153`; the registered-but-unseeded membership refusal's 403 `authn.tenant_membership_required` in the browser's no-tenant shape, `demo_users_test.go:297`, its named-tenant siblings `:162`/`:233`; a create from a caller without `notes:write` answering `rbac.permission_denied`, `server_test.go:335`).

Two demo accounts stand in for the seeded users: the owner (`owner@example.test`) is the web rig's own account — the Go seed's `demo-owner@example.com` has no web counterpart, because no web journey reads it — while the reader (`demo-reader@example.com`) mirrors the Go seed's identifier and its asymmetry: its notes list is served like any member's, and a note create from its principal answers the rbac write gate's 403. A registered identifier signs in later to the membership refusal of a registered-but-unseeded account, and registering twice answers the same 409 `authn.email_already_registered` a real handler answers. The notes answers mirror the real handler's own refusals (400 `notes.text_required`, 400 `notes.text_too_long` over the 4000-character limit), and the `denyNotesRead` / `denyNotesWrite` switches answer the read and write permission refusals the rbac gate produces — the journeys' gate and error surfaces are driven by genuine 403 answers, never locally stubbed shapes. Notes state is per tenant, so a refetch after a create really shows the new row. The reader option's own day is scripted by the app-journey suite — the list served like any member's, the create refused with the rbac write gate's code text — the account surface intentionally not part of it. One deliberate scope limit is recorded rather than half-built: account-domain state (the session list, the bound identities, the active MFA factor) belongs to the owner story alone — the reader's list answers would show the owner's rows if a journey drove the reader into the account surface, and no journey in this round crosses that line.

## The rig

`src/test-utils/real-client.ts` is the real-client network rig: a genuine `createClient` over a fetch stand-in answering with real `Response` objects (through `jsonResponse` / `errorResponse`), the memory access-token store, and the session's own `refreshAccessToken: () => session.refresh()` — bound into the api-sdk runtime seam exactly as the app's own bootstrap binds it. Because the transport is real api-client machinery, a request answered 401 would drive the client's own single-flight refresh and one retry rather than a scripted leg — but the demo-server answers no 401, so no journey at this tier rides that leg (its in-form exercise lives in the packages' own usage-example suites, where a scripted responder answers 401). `RealCall` records each request as the stand-in observed it — method, path, query, authorization header, body — so a suite can pin what a journey sent, per request. The rig is the app layer's own copy of the same rig the account-ui package's suite ships: layer-local by design, the standing pattern across the workspace (same-layer packages never import one another); extracting a shared rig package is recorded DEFERRED in the file's header.

## Error-code alignment

`src/codes-alignment.test.ts` pins the four surfaces' reachable-error whitelists — the auth-ui sign-in/session family, the account-ui signed-in family, the tenancy-ui switch family and the notes create surface — to the server codes themselves. The server side of the comparison is `GO_PINNED`: a hand-maintained enumeration of the codes this app's server can answer on those surfaces, each entry carrying the source citation of the sentinel that defines it (`go/authn/errors.go`, the `go/rbac` and notes-module sentinels). The shell side is derived, never copied: the packages' whitelists are deep-imported from their own error-text modules (never from package entry points), the notes whitelist from this app's own notes-view. The two directions are asserted separately so a drift names its side: every pinned server code is whitelisted by at least one surface (a server code with no surface text would render a raw key), and every non-client code a surface whitelists has a pin (an entry for a code no server answers is dead copy). The `client.network` / `client.timeout` / `client.protocol` codes sit outside the comparison — each surface whitelists exactly that trio, and never a `client.http.<status>` family, which the api-client contract leaves dynamic for every surface's unknown fallback. `GO_PINNED` is deliberately hand-maintained; a machine-extracted server-side code census is DEFERRED, the reasons recorded in the suite's header.

## The app journey

`src/app-journey.test.tsx` chronicles the composed user story end to end — named for the behaviour it crosses every layer for, the precedent of the packages' session-journey suites. Its first suite keeps one session alive across the whole owner day and pins the ordered trace that session produces: the register turn and the honest display of the registered-but-unseeded account's membership refusal (the server's own 403 code text), the owner sign-in, notes read and written under the token's tenant, the tenant switch away and back proving per-tenant lists, the account day (a session revoked from the list, the first MFA setup answering its recovery codes, a second setup discovering the active factor through the 403 step-up gate — a wrong step-up code answered with its field text — and the replacement codes shown once), sign-out into the session-ended screen, and the re-login that lands back on the account fragment — closing with a bilingual leg and the whole trace pinned request by request: method/path (the login-history `?limit=20` included), every bearer (the access-1..access-5 numbering of the rig's own token-issuing server), and every body. One Public-config fetch served the entire session. Two shorter journeys cover the member days of the accounts whose grants differ: the read-only member's day (its list served like any member's, its create refused with the rbac write gate's code text and the draft kept — the shape the Go suites pin for the reader seed) and the read-denied day (a 403 list answer converging to the no-permission gate, no surface below the heading). The binding exchange itself is not re-driven here — app.test.tsx's travel journey pins a composed held-open exchange against the same account surface — so the suite's header cross-references that journey rather than duplicating it.

## Workspace mechanics and commands

This directory is a workspace member of `web/` that lives outside it, so a run started here does not sit under the web/ workspace root — pnpm discovers its workspace root by walking up from the working directory, and `web/` is not on this directory's ancestor path, which makes it a one-project workspace of its own for any run started here. The app's own `pnpm-workspace.yaml` (settings-only, no packages list) is what carries the one setting that standalone context needs: `verifyDepsBeforeRun: false`, because a dependency sync started here cannot resolve the `workspace:*` specifiers — they resolve only from the web/ root, where the whole workspace is installed once from the frozen `web/pnpm-lock.yaml`. The casing matters: pnpm merges only camelCase keys from a workspace manifest into its config, so the kebab-case `verify-deps-before-run` is silently ignored and falls through to the true default (`install`), which is exactly the failure a real, reproduced CI run exposed — an auto-repair install scoped to this one-project workspace that can never resolve a `workspace:*` dependency, failing with `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`. A plain `.npmrc` does not fix this either: a project `.npmrc` in a directory that is not itself a workspace root is not merged into pnpm's config resolution at all, so the setting keeps resolving to `install` regardless. The `pnpm-workspace.yaml`'s own comment records the full reasoning, including that dead end.

From this directory, each script is a plain package script:

```
pnpm lint        # eslint . -- the flat config, discipline rules included
pnpm typecheck   # tsc -p tsconfig.json
pnpm test        # vitest run -- jsdom, setup from src/test-utils/setup.ts
pnpm build       # tsc -p tsconfig.json -- no-emit until the M4 html-runner
                 # round lands a bundler (see the tsconfig comment)
```

CI runs the same four legs as this directory's row in fast-check's npm matrix: the app is one row of the matrix through the same reusable `npm-package-ci` workflow as the eleven web packages — a frozen-lockfile workspace install from the web/ root first, then each leg with this directory as the working directory (recorded in `.github/workflows/fast-check.yml`). From the web/ root, the workspace-wide `pnpm -r` forms reach this app the same way they reach any member.

Type and test resolution of the `@speed/*` imports map every specifier — subpaths included — onto the workspace sibling's live source (tsconfig `paths`, mirrored in the vitest config's aliases), because a sibling's `dist/` is never committed and may not exist when this app runs; the mapped set covers the transitive graph (tokens, `@speed/i18n/mui-locale`, `@speed/api-sdk/runtime`), with subpath entries ordered before their prefixes.

## Evidence boundary

- The shell's vitest suites prove the composed frontend answers over the scripted demo-server stand-in: a real api-client (real transport machinery — the session's silent refresh bound into the client's `refreshAccessToken` seam as the bootstrap binds it, a leg no journey rides here because the demo-server answers no 401), a real bound session, the generated hooks, the packages' components, and the app's own composition. They touch no network: no fetch leaves the process, and nothing in this directory spawns, connects to, or requires the Go server.
- The real-server leg of the same demo facts is the Go side's: `cmd/server/demo_users_test.go` and `cmd/server/demo_subject_test.go` drive the real composed stack — real register and sign-in routes, real membership and rbac policy, real fail-closed shapes. The demo-server's header cites those tests line by line, which is what keeps the mirror honest.
- The browser-page leg — this bootstrap mounted in a real browser page served by the reference-app server — lands with the M4 e2e/html-runner work (recorded in the bootstrap's doc comment). Until then, rendering under test harnesses is the whole of the shipped browser story.
