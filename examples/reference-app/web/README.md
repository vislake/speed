# web — the reference-app's consumer shell

The reference app's web frontend: the directory where the `@speed` packages get composed the way a delivered consumer project composes them, and the frontend consumer proof of the whole shipped web surface at once. It deliberately lives at `examples/reference-app/web` — outside the `web/` pnpm workspace, at exactly the location a delivered project occupies — and joins that workspace as an external member (`web/pnpm-workspace.yaml` lists it): it shares the workspace's single frozen lockfile while staying `private`, never versioned, with no changesets fixed-group entry and no release tag.

What ships here is the composition and its tests, plus a browser-runner host: the vitest suites bind the real packages — a genuine `@speed/api-client` over a scripted fetch stand-in, a real session, the generated hooks, the packages' own components — through the app's own bootstrap, and pin the composed answers; `index.html` and `vite.config.ts` mount that same bootstrap in a real browser page (Running in the browser), and the reference-app server serves this directory's production `dist/` itself in a deployed shape — the Dockerfile builds it into the image and the Go server serves it from disk under `APP_WEB_DIST` (internal/app/frontend.go), so the deployed product URL is this page. What does not ship yet is recorded rather than half-built (see Evidence boundary and Deferred).

## The composition

`src/main.tsx`'s `bootstrapReferenceApp` is the composition root: a pure function with no module-scope side effects (suites and future harnesses import it safely) that mounts into a caller-supplied container and returns `{ root, i18n, queryClient }`. In order it:

- registers the six namespaces the tree renders from — the five namespace-shipping package families (ui-kit, layout-kit, auth-ui, tenancy-ui, account-ui) plus the app's own `reference-app` bundle — through `registerNamespace`, which validates identical leaf key sets across the supported languages before mutating anything;
- wires the memory session: a `createMemoryAccessTokenStore` store feeding `createAuthSession`, attached once via `attachSession`, with `session.refresh()` filling the api-client's `refreshAccessToken` seam — the same wiring a real host builds, though no journey at this tier rides that leg: the demo-server answers no 401, so the single-flight refresh stays dormant here, its in-form exercise living in the packages' own usage-example suites;
- builds the one api-client: `createClient` over the environment's own `fetch` (captured at construction — the package's injection seam, here a genuine dependency-injection point, which is exactly what lets suites substitute the demo-server stand-in), bound into the generated runtime exactly once through `bindRequestFn`, so all API traffic from here on is generated-code traffic;
- wires `evictQueriesOnSessionEnd(session, queryClient)`: the moment the session goes from authenticated to anonymous — a sign-out or a session death (a silently refused refresh) — it empties the whole query cache. Every row the departing principal's reads cached goes with it: the tenant-namespaced notes rows (the domain the earlier `evictTenantQueriesOnSessionEnd` cleared) and the identity-domain rows the account surface reads through bare spec-path keys (sessions, login history, bound identities — nothing in `@speed/api-sdk` is tenant-namespaced, so no tenant-prefix eviction could ever reach them; reference-app-web.md P1-apisdk-1), plus anything a future surface reads. A different account signing in afterward — into any tenant — starts from an empty cache and never inherits an earlier session's rows (The gate);
- composes the provider tree in the documented order — I18next, theme, QueryClient, app services, the view layer — under StrictMode.

A browser page mounting this bootstrap is no longer deferred work: this directory's `index.html` mounts it, runnable through the vite dev server and the production build (Running in the browser), and served by the reference-app server itself in a deployed shape — the Dockerfile builds this directory's `dist/` into the image and the server serves it from disk under `APP_WEB_DIST` (Serving the built page). What remains M4 e2e/html-runner work is browser automation driving that server-served page.

## The view layer

`src/app.tsx` renders `ProductShell` (the auth-core-driven three-branch view machine: signed out, the sign-in surface; signed in with a tenant, the frame; a dead session, the session-ended screen) around the `AppShell` frame, with the nav, the header brand and the user menu all host content computed from the app's own namespace and the server's Public config.

Routing is the app's one hand-rolled slice of chrome: `AppShell` nav items are anchors into the location hash (the package never path-matches — each item carries its own `selected`, computed here), and `useHashRoute` feeds the fragment parser, which knows the content kinds: home, cases (the clinic list at `/cases`, the one-page creation flow at `/cases/new`, and one case's detail at `/cases/<id>` — the block-A acceptance surface), notes, account, and the account surface's binding subroute (`/auth/binding/<provider>?code=<code>&state=<state>` — the completion point of a social binding exchange, the provider validated against the demo provider set so no unknown provider ever drives an exchange). Everything else degrades to home with no nav item selected; there is no 404 chrome in this round. The brand in the AppBar and on the sign-in/home headings is the server's own answer — the same Public `brand.site_name` value the config module serves (`useBrandName`), never a local copy — and a tenant switch re-asks that host-resolved answer, so the brand and the home feature cards converge on the tenant the page is actually in (The user menu).

The views:

- `home-view.tsx` — the first real-data surface: the heading is the served brand, the intro is app copy, and each feature card exists only while the flag that gates it is on — the card list is data-driven over go/config's feature list, resolved per key through `useFeature`'s composition on the shared Public-config cache (one `/api/v1/config/public` fetch serves the header brand, this view's brand and both flag checks, re-asked on each tenant switch). A surface with no enabled feature renders ui-kit's `EmptyState` with its own copy instead of promising cards it has none (the home-is-self-consistent gate), and every surface that does or reads work renders the clinic-context line (`current-clinic.tsx`) at page-title level under its h1 — the one place in the main content that always says which clinic the person is in (the current-clinic-is-visible gate). The two demo flags exercise both shapes the config module ships: a plain flag (`ai.smile_preview`) and a dependent one (`ai.premium_upsell`, enabled only while its dependency is).
- `notes-view.tsx` — the notes surface: the list read through the generated hooks over a tenant-namespaced query key, gated by `RouteGuard`, a create flow driven by the create mutation (The gate), and the same clinic-context line under its heading — a person writing a record must see where it will land from where they are writing.
- `cases-view.tsx`, `case-create-view.tsx` and `case-detail-view.tsx` — the block-A cases surface, the clinic's reason to use the product: the clinic-wide case list (the server answers every case of the current tenant, never the caller's own subset — the list the acceptance chain requires, titled "Cases" with the current clinic's name in the level-one heading through the shared `CasesSurfaceHeading`), the one-page creation flow (pick the patient's photos — each file uploaded through the generated `cases_uploadPhoto` operation the moment it is chosen, the queue rendered by ui-kit's `FileUploader` from host-owned rows — enter the patient name, submit once: the single `cases_createCase` submission carries the uploaded photos' object ids), and one case's page (its photos rendered from their stored bytes — `cases_getPhotoContent`'s JSON-carried base64 decoded into a Blob of the probe-assigned media type and shown as an object URL, every URL created here revoked when the photo leaves the page). The block-B round grew the detail page into the smile journey: under each photo, `photo-simulation-panel.tsx` offers the documented option set (three smile styles, three tooth shades, an adjustable strength — transmitted verbatim into `smilesim_simulate`), starts the async generation, reports its honest live status (the generated job polled through `smilesim_getJob`, its queued/generating/retrying states rendered in a status live region — never a fake spinner), and once the job completes shows the before/after comparison: the generated image fetched through the new `smilesim_getSimulationContent` operation and rendered beside the original, both over the same blob-URL pattern. All of it reads through the generated hooks over tenant-namespaced keys; there is no rbac gate on the surface (any member of the tenant may work cases), so a failed read is a load failure, never a denial suit. Every refusal renders its code's bilingual text through the shared reachable-error maps in `cases-errors.ts` and `smile-sim-errors.ts` (whose whitelists the codes-alignment suite pins, below).
- `account-view.tsx` — the account surface: the account-ui family composed over the app's session and the generated authn API. The session-operating sections receive the session as a prop (the boundary rule: a prop exactly where a session operation exists); the read-only sections take none. Reads and mutations go through the generated hooks over the host's QueryClient, invalidating through the exported query-key builders. The binding subroute renders the same surface with the completion handler on top: it exchanges the `(code, state)` pair over the app's client, invalidates the identities list, and cues the host (`onBound`) — here the app's own navigation back to the account fragment, passed down from the view switch; until that cue lands, the handler rests on its pending notice. The add area's channels are host configuration: the five demo providers, each carrying the redirect URI of the app's own callback route for that channel (the `<origin>/callback/social/<provider>` convention a real deployment serves with its SPA fallback, with the origin read from the running page — `window.location.origin` — so a callback that lives on this app never points at a host that does not resolve where the app runs). The view's one navigation duty — landing the browser on a channel's authorization URL when the section reports it upward — first refuses any URL whose protocol is not http(s): the coded refusal text renders in an alert and nothing is assigned to the window.
- `sign-in-view.tsx` — the anonymous branch: the served brand over auth-ui's `SignInScreen`, with the host's own register surface toggled from the footer. Registration is a destination, not a session operation: the created account (handed to the host through `RegisterForm`'s `onRegistered` — the form never signs in, by package contract) lands in a success state with a way back to the sign-in surface. The whole register-to-sign-in turn is view-local state — nothing here calls login, so the auth-core snapshot never flips.
- `user-menu.tsx` — the AppBar's right-hand cluster: tenancy-ui's `TenantSwitcher` over the demo's two tenants and auth-ui's `SignOutButton`, both host-composed over the session from app services. The demo has no roster endpoint (the server seeds exactly two tenants and grants the accounts the web journeys use membership in both), so the roster is the app's own static data with app-namespace display names — held in one shared module (`demo-tenants.ts`) so the chrome's trigger and the main-content clinic line can never drift apart; the current tenant comes from the auth-core hook (the principal's own claim, never local memory of a previous switch), and a completed switch first evicts every row the departing access token fetched — the previous tenant's tenant-namespaced cache and the account surface's identity-domain rows, whose bare spec-path keys carry no tenant segment (reference-app-web.md P1-apisdk-1) — so after switching, this tenant's caches hold only this tenant's rows. The same handler then re-asks the host-resolved Public config (its `refresh`, over the shared cache every brand and feature reader subscribes to), because the host switched tenants same-origin: the AppBar brand and the home feature cards must answer the tenant the page is now in, not the one it left (reference-app-web.md P2-refapp-14).

## The gate

The notes surface carries the shell's real permission gate, and the gate is the list query itself. The server's rbac layer answers a caller without `notes:read` with 403 `rbac.permission_denied`, so the query is the real permission fetch — the router-level gate behind real fetches that earlier rounds' notes deferred to this shell. `RouteGuard`'s `status` maps onto the query's own states, classified by the query's error state first: only the rbac read gate's own refusal — the 403 carrying `rbac.permission_denied` — is an authorization fact and maps to `denied` (the guard's default denied branch is ui-kit's `EmptyState` in the `noPermission` variant); every other failed read — a coded transport answer or server 5xx, or a refusal carrying no code at all (a raw `AbortError`, an error thrown before the api-client could normalize it) — renders ui-kit's `EmptyState` in the `error` variant, never the no-permission suit and never a permanent `pending` (reference-app-web.md P2-rnweb-1). A served list is `allowed` only once no error stands, and no answer at all yet is `pending`. The error check runs ahead of the data check on purpose: tanstack query v5 never clears a query's `data` on a failed refetch, so a permission revoked mid-session — or a different account signing into a tenant an earlier account's read already cached — refetches into a refusal whose `data` is still the earlier answer, and the gate must fail closed on that error rather than keep the stale rows on screen. (An earlier version of this gate checked `data` before `isError` and did exactly that, and a later one classified errors by their code alone, which let a codeless refusal fall through to the stale rows or park at `pending`; see reference-app-web.md P1-1 and P2-rnweb-1 and the regression coverage in notes-view.test.tsx and app-journey.test.tsx.)

The create form lives inside the allowed branch, and a refused create (a caller without `notes:write` answers the same 403) stays on the page with its code text: the write gate is probed by the mutation, never pre-empted client-side. The form's required and length rules (the 4000-character limit kept in step with the server handler) are an experience mirror of the server's own constraint, never a gate themselves.

The list query key is tenant-namespaced (`['tenant', tenantId, ...getNotesListNotesQueryKey()]` over the generated bare key, `tenantId` the plain string `useCurrentTenant()` carries — not the hook's own `{ tenantId }` return value, which a prior version of this view embedded directly and which no `removeQueries` call keyed on the bare id could ever structurally match), so a tenant switch can never read the previous tenant's cached notes: `user-menu.tsx` evicts the departing tenant's `['tenant', tenantId]` queries on every switch — and the account surface's identity-domain rows alongside them, since the switch rotated the access token those rows were answered under (reference-app-web.md P1-apisdk-1) — and `main.tsx`'s `evictQueriesOnSessionEnd` empties the whole cache the moment the session ends — a sign-out or a session death (a silently refused refresh) — so a different account signing in afterward, into any tenant, starts from an empty cache instead of inheriting rows an earlier session's reads left behind. The create invalidates exactly the namespaced key.

What this gate does **not** cover: the server read/write refusal itself is the only source of truth this surface trusts (the "gate" is never a client-side permission check), and the eviction above is a defense-in-depth measure over the query cache, not a substitute for the server re-checking access on every request — a caller whose access is revoked mid-session only ever finds out on its next real request.

By design the shell consumes no `/me`-derived permission lists: nothing here calls `usePermission` or attaches `setPermissionSet` — no server endpoint serves permission sets (rbac mounts no HTTP routes), and query-as-permission is this round's answer to the "real permission fetch" item earlier notes deferred to the shell. The `setPermissionSet` host-attach path stays reserved for a future ops-console round that has a roster to attach.

## The demo facts

The demo facts the web journeys exercise exist on two tiers, each citing the other:

- **Server side (real).** `APP_DEMO_USERS_PASSWORD` gates three real accounts seeded through the real register route at boot: `demo-owner@example.com` (built-in owner — every permission any module declared), `demo-reader@example.com` (custom `note-reader` role, `notes:read` and nothing else) and `demo-acme-only@example.com` (`note-reader` in `tenant-acme` alone — a grant is a fact about a (tenant, user) pair, never about a user). Memberships live in an in-process roster that does not survive a restart, so a boot against an already-seeded database logs a warning and re-grants nothing. The rbac demonstration additionally keeps the pre-authn `X-Demo-User` header — deliberately still taking precedence over a verified token's Principal (it predates authn; removal is deferred to the org-web round) and never able to affect the tenant half of an authorization subject, which always comes from the `tenancy.Middleware` request context. The Go suites pin all of it end to end through the real composed stack: `cmd/server/demo_users_test.go` and `cmd/server/demo_subject_test.go`.
- **Web side (scripted).** `src/test-utils/demo-server.ts` mirrors those facts for the shell's journeys: one responder answering the endpoints a real reference-app server answers, the demo facts baked in as defaults and every answer overridable per suite — and anything else failing the test loudly, because an unpinned request means the journey reached an endpoint the demo does not serve. Its header cites the Go tests that pin each mirrored fact (the reader's list served, `TestDemoUsers_SeededAccountsReachTheGateThroughTheirPrincipal` in `cmd/server/demo_users_test.go`; a registered account's sign-in — the browser shape answers the clinic its registration provisioned, never a membership refusal — and the account's one remaining refusal, a sign-in naming a tenant it holds no membership in, answering the unified 401 `authn.invalid_credentials` a wrong password also gets, with the no-membership reason surviving only in the login history, same test, the acme-only account asking for tenant-globex; a create from a caller without `notes:write` answering `rbac.permission_denied`, `TestBuildServer_PermissionGate_EnforcesTheNotesPermissions` in `flowtests/server_test.go`).

Two demo accounts stand in for the seeded users: the owner (`owner@example.test`) is the web rig's own account — the Go seed's `demo-owner@example.com` has no web counterpart, because no web journey reads it — while the reader (`demo-reader@example.com`) mirrors the Go seed's identifier and its asymmetry: its notes list is served like any member's, and a note create from its principal answers the rbac write gate's 403. A registered identifier's later sign-in lands in the clinic its registration provisioned (self-service signup, `internal/app/self_service.go`), never at a membership refusal, and registering twice answers the same 409 `authn.email_already_registered` a real handler answers. The notes answers mirror the real handler's own refusals (400 `notes.text_required`, 400 `notes.text_too_long` over the 4000-character limit), and the `denyNotesRead` / `denyNotesWrite` switches answer the read and write permission refusals the rbac gate produces — the journeys' gate and error surfaces are driven by genuine 403 answers, never locally stubbed shapes. Notes state is per tenant, so a refetch after a create really shows the new row. The cases answers mirror the cases surface the same way (the block-A round's addition): the list and case state are per tenant with a create appending the row later list answers carry, the one-shot photo upload hands out counting object ids, and the `denyCasesList` / `casesCreateRefusal` / `casesUploadRefusal` / `casesPhotoContentRefusal` switches script the refusal codes the surfaces render. The smile-simulation answers mirror the block-B surface the same way: `POST /simulate` accepts a job whose live status advances deterministically per job-status poll (pending, then running, then succeeded — so a journey observes the honest progression and always terminates), the per-photo enumeration and the simulation-content read answer from the same ledger, and the `simulateRefusal` / `simulationContentRefusal` switches script the refusal codes (the 409 `billing.insufficient_credits` journey, the 404 content refusals) the surface renders. The reader option's own day is scripted by the app-journey suite — the list served like any member's, the create refused with the rbac write gate's code text — the account surface intentionally not part of it. One deliberate scope limit is recorded rather than half-built: account-domain state (the session list, the bound identities, the active MFA factor) belongs to the owner story alone — the reader's list answers would show the owner's rows if a journey drove the reader into the account surface, and no journey in this round crosses that line.

## The rig

`src/test-utils/real-client.ts` is the real-client network rig: a genuine `createClient` over a fetch stand-in answering with real `Response` objects (through `jsonResponse` / `errorResponse`), the memory access-token store, and the session's own `refreshAccessToken: () => session.refresh()` — bound into the api-sdk runtime seam exactly as the app's own bootstrap binds it. Because the transport is real api-client machinery, a request answered 401 would drive the client's own single-flight refresh and one retry rather than a scripted leg — but the demo-server answers no 401, so no journey at this tier rides that leg (its in-form exercise lives in the packages' own usage-example suites, where a scripted responder answers 401). `RealCall` records each request as the stand-in observed it — method, path, query, authorization header, body — so a suite can pin what a journey sent, per request. The rig is the app layer's own copy of the same rig the account-ui package's suite ships: layer-local by design, the standing pattern across the workspace (same-layer packages never import one another); extracting a shared rig package is recorded DEFERRED in the file's header.

## Error-code alignment

`src/codes-alignment.test.ts` pins the ten surfaces' reachable-error whitelists — the auth-ui sign-in/session family, the account-ui signed-in family, the tenancy-ui switch family, the notes create surface, the cases surface (its whitelist in `cases-errors.ts` cited against the cases domain and photo-route sentinels), the smile-simulation surface (its whitelist in `smile-sim-errors.ts` cited against the app-side smilesim sentinels, the option-validation sentinels in `internal/smilesim/options.go`, and the jobs/billing/ai-gateway sentinels a simulate call can surface), the two share surfaces (the clinic's share action and the patient page, their whitelists both in `share-errors.ts`, cited against go/sharing's sentinels), the credits surface (its whitelist in `views/credits-view.ts`, cited against go/billing's read sentinels) and the team invite surface (its whitelist in `views/team-view.ts`, cited against go/org's create-operation sentinels) — to the server codes themselves. The suite additionally pins the bilingual-text legs: every reachable code of the smile-simulation, share-action, patient-page and team surfaces renders a non-empty bilingual text in both app bundles, never the unknown fallback and never a raw key. The server side of the comparison is `GO_PINNED`: a hand-maintained enumeration of the codes this app's server can answer on those surfaces, each entry carrying the source citation of the sentinel that defines it — the file plus the sentinel identifier, never a line number (`go/authn/errors.go` and `go/rbac/errors.go` for those modules' codes, the notes/cases/smilesim sentinels in this app's own packages, and the `go/org`, `go/billing`, `go/sharing`, `go/jobs` and `go/ai-gateway` sentinels the surfaces can draw). The shell side is derived, never copied: the packages' whitelists are deep-imported from their own error-text modules (never from package entry points), the app-side whitelists from this app's own views and error maps. The two directions are asserted separately so a drift names its side: every pinned server code is whitelisted by at least one surface (a server code with no surface text would render a raw key), and every non-client code a surface whitelists has a pin or a recorded `WHITELISTED_BEYOND_THIS_APP` exemption (an entry for a code no server answers here is dead copy). The `client.network` / `client.timeout` / `client.protocol` codes sit outside the comparison — each surface whitelists exactly that trio, and never a `client.http.<status>` family, which the api-client contract leaves dynamic for every surface's unknown fallback. Alongside the hand-maintained enumeration runs the machine-extracted server-side code census: `tools/gen_error_code_index.py` (the drift-gated generator behind the docs site's error-codes page) emits `docs/error-codes.json`, one row per code with its construction file, line and bound identifier, and the suite's machine leg requires every pinned code to exist there as a construction at exactly the cited file, bound to the cited identifier — a sentinel whose code string changed, or a citation naming the wrong file, fails the suite. The census is also the machine source of the line numbers a reader may want; what stays hand-maintained is reachability — which codes a surface's own flows can actually draw — which no line-based extractor derives.

## The app journey

`src/app-journey.test.tsx` chronicles the composed user story end to end — named for the behaviour it crosses every layer for, the precedent of the packages' session-journey suites. Its first suite keeps one session alive across the whole owner day and pins the ordered trace that session produces: the register turn, the owner sign-in, notes read and written under the token's tenant, the tenant switch away and back proving per-tenant lists, the account day (a session revoked from the list, the first MFA setup answering its recovery codes, a second setup discovering the active factor through the 403 step-up gate — a wrong step-up code answered with its field text — and the replacement codes shown once), sign-out into the session-ended screen, the re-login that lands back on the account fragment, a bilingual leg, and the register-turn visitor's own closing sign-in landing in the clinic its registration provisioned — never a membership refusal — the whole trace pinned request by request: method/path (the login-history `?limit=20` included), every bearer (the access-1..access-6 numbering of the rig's own token-issuing server), and every body. The Public-config fetch appears three times in that trace: the first paint's anonymous fetch plus one revalidation right after each completed tenant switch. Two shorter journeys cover the member days of the accounts whose grants differ: the read-only member's day (its list served like any member's, its create refused with the rbac write gate's code text and the draft kept — the shape the Go suites pin for the reader seed) and the read-denied day (a 403 list answer converging to the no-permission gate, no surface below the heading). The binding exchange itself is not re-driven here — app.test.tsx's travel journey pins a composed held-open exchange against the same account surface — so the suite's header cross-references that journey rather than duplicating it.

## Workspace mechanics and commands

This directory is a workspace member of `web/` that lives outside it, so a run started here does not sit under the web/ workspace root — pnpm discovers its workspace root by walking up from the working directory, and `web/` is not on this directory's ancestor path, which makes it a one-project workspace of its own for any run started here. The app's own `pnpm-workspace.yaml` (settings-only, no packages list) is what carries the one setting that standalone context needs: `verifyDepsBeforeRun: false`, because a dependency sync started here cannot resolve the `workspace:*` specifiers — they resolve only from the web/ root, where the whole workspace is installed once from the frozen `web/pnpm-lock.yaml`. The casing matters: pnpm merges only camelCase keys from a workspace manifest into its config, so the kebab-case `verify-deps-before-run` is silently ignored and falls through to the true default (`install`), which is exactly the failure a real, reproduced CI run exposed — an auto-repair install scoped to this one-project workspace that can never resolve a `workspace:*` dependency, failing with `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`. A plain `.npmrc` does not fix this either: a project `.npmrc` in a directory that is not itself a workspace root is not merged into pnpm's config resolution at all, so the setting keeps resolving to `install` regardless. The `pnpm-workspace.yaml`'s own comment records the full reasoning, including that dead end.

From this directory, each script is a plain package script:

```
pnpm lint        # eslint . -- the flat config, discipline rules included
pnpm typecheck   # tsc -p tsconfig.json
pnpm test        # vitest run -- jsdom, setup from src/test-utils/setup.ts
pnpm dev         # vite -- the dev server on http://localhost:5173, /api
                 # proxied to the backend (Running in the browser)
pnpm build       # tsc -p tsconfig.json && vite build -- the type-check gate
                 # followed by a real production bundle into dist/
```

CI runs the same four legs as this directory's row in fast-check's npm matrix: the app is one row of the matrix through the same reusable `npm-package-ci` workflow as the eleven web packages — a frozen-lockfile workspace install from the web/ root first, then each leg with this directory as the working directory (recorded in `.github/workflows/fast-check.yml`). From the web/ root, the workspace-wide `pnpm -r` forms reach this app the same way they reach any member.

Type and test resolution of the `@speed/*` imports map every specifier — subpaths included — onto the workspace sibling's live source (tsconfig `paths`, mirrored in the vitest config's and the vite config's aliases), because a sibling's `dist/` is never committed and may not exist when this app runs; the mapped set covers the transitive graph (tokens, `@speed/i18n/mui-locale`, `@speed/api-sdk/runtime`), with subpath entries ordered before their prefixes.

## Running in the browser

This directory ships a browser-runner host: `index.html` mounts `bootstrapReferenceApp` into the `#root` element (the bootstrap stays side-effect-free by design — importing `main.tsx` does nothing, so the page is the host that calls it, exactly once per load), and `vite.config.ts` serves it in dev and bundles it for production. The host is this directory's own concern: the web packages stay bundler-free by discipline, so `vite` is a devDependency here and nowhere else.

```
pnpm dev        # from this directory: the vite dev server on
                # http://localhost:5173, serving index.html and
                # transforming the app's modules on demand
```

The page talks to the same origin it is served from (the api client's `baseUrl` is `window.location.origin`), and every path it uses sits under `/api` — the generated operations under `/api/v1/*`, plus the pre-auth `/api/v1/config/public` and `/api/v1/config/features` — so the dev server proxies `/api` to the reference-app backend: default `http://localhost:8080` (the Go server's own default `PORT`), overridable with `REFERENCE_APP_API_PROXY`. The page loads and renders with the backend down — only the API calls fail — and the proxy is exercised only when a call actually goes out. Signing in needs the backend running with its demo identity layer (the Go server's demo section). With no backend, every network answer is a refused one and the sign-in surface is where the page settles, exactly as its fail-closed design intends.

`pnpm build` runs the type-check gate first, then `vite build` emits the production bundle into `dist/` (gitignored like every `dist/` in the repo). The production `base` stays vite's default `"/"`, so the built `index.html` references its bundles at root-absolute `/assets/*` paths — the exact paths the server's static surface serves (Serving the built page).

## Serving the built page

The image round settled the question this directory used to defer to it: the reference-app server serves this built page itself in a deployed shape. The `Dockerfile`'s `frontend` stage builds this directory exactly the way CI's npm-package-ci leg does (frozen-lockfile install from the `web/` root, `pnpm build` from here), the final image carries `dist/` at `/app/web/dist`, and `internal/app/frontend.go` serves it when `APP_WEB_DIST` names it (the Dockerfile's `ENV` does). The serving is from disk, never `go:embed` — a compile-time embed would force this gitignored, hash-named build output into the committed tree — and the static surface never enters the authn/tenancy middleware chain: `/` and unknown non-API paths answer `index.html` with no tenant, `/assets/*` serves the built files with immutable caching, and `/api/*` keeps the composed chain's answers byte-for-byte (its regressions live in `flowtests/frontend_test.go`, driven through the real composed handler against a fixture dist). The dev story is unchanged: `pnpm dev`'s vite server and its `/api` proxy are untouched by the Go side serving the same page on its own port.
