# dbkit/audit

`audit` is the persistence and declarative-collection home of the audit trail: the `AuditEvent` model, its dual-dialect migrations, `Repository` (the append-only accessor that stores and reads events back), `Emit` (the declarative-secondary collection mechanism), and `Module`, the `pkgcore.Module` persister that subscribes to every collection mechanism's published events and calls `Repository.Insert`. The complementary automatic-collection mechanism — the GORM write-capture plugin — lives one level up, in `go/dbkit` itself (`audit_capture.go`), since it has to be wired into `dbkit.Open`; see `go/dbkit/AGENTS.md`'s own "Audit trail persistence" section for that half.

## Module home

This package lives inside `go/dbkit`, not as its own `go.work` module and not inside `go/compliance`. The audit trail is cross-cutting platform infrastructure every module contributes to, so its persistence sits where the collection mechanisms and the write paths already converge:

- The write-capture plugin is installed by `dbkit.Open` and publishes `dbkit.EventWriteCaptured` on the bus; the persister that subscribes to it must be able to import `dbkit`, which an `audit` subpackage can.
- `go/compliance` owns the governance layer over the trail — retention, archival, search/report, right-to-be-forgotten, data portability — and reads the table; collection itself stays with the write paths, not with the governance layer.
- `go/pkgcore` cannot host persistence (no GORM, no DB) — but it already has the right declaration surface: `Registry.AuditActions`, the vocabulary every audit-writing module populates at `Register` time. This package is the consumer that validates against it.
- `go/tenancy` is not a database-touching home: its production code never touches a database, and it does not implement `pkgcore.Module`.
- `go/dbkit` already owns the one existing GORM-callback plugin (`tenant_scope.go`), `MigrationRegistry`, and — most directly — the "a real, indexed `tenant_id` column that must NOT implement `dbkit.TenantScoped`" precedent this table needs, already shipped twice over: `go/jobs`'s `jobRecord` and `go/config`'s `row`.
- Net new dependency edges this package adds: none. It depends only on `go/dbkit` (root) and `go/pkgcore`, both of which `dbkit` already depends on or is depended on by.

## Data-domain classification

The audit log carries both tenant-level and platform-level entries, so `AuditEvent` is treated as **platform data with a real, non-enforced `tenant_id` column** — the same treatment `go/jobs`'s `jobRecord` and `go/config`'s `row` get. It runs the reverse-and-equally-important proof (`model_test.go`'s `TestAuditEvent_DoesNotImplementTenantScoped` and `TestAuditEvent_VisibilityDoesNotDependOnTenantContext`), never `tenancytest.AssertIsolated` — `AuditEvent` does not, and must not, implement `dbkit.TenantScoped`.

**An emergent safety property of that same decision, recorded because it is load-bearing.** Because `AuditEvent` implements no `TenantScoped` method, `dbkit.Repository[T]` — whose type parameter is constrained to `TenantScoped` — cannot be instantiated for the audit trail at all, which means `Repository[T]`'s `HardDelete` method (`go/dbkit/hard_delete.go`, the compliance-erasure path) fails type-checking the moment anyone writes `Repository[AuditEvent]`. That is one of the two independent application-layer paths that could erase an audit trail — alongside `audit.Repository`'s own deliberate lack of any delete method — closed at compile time rather than by convention. **Adding a `GetTenantID` method to `AuditEvent` for any other reason would silently remove this protection**; `model.go`'s type doc comment records the same warning. (The database-level trigger pair of `0002_append_only_enforcement.sql` is a third, separate backstop beneath both.)

**Why not literally `tenancytest.AssertNotTenantScoped`**, the way `go/config` and `go/jobs` prove the identical property of their own platform-data models: `go/tenancy/tenancytest` imports `go/dbkit` itself, and `go/tenancy` sits *above* `go/dbkit` in the module dependency graph (`pkgcore -> dbkit -> tenancy -> config/jobs -> ...`). This package is a subpackage of `dbkit`, so importing `tenancytest` from here would make `dbkit` depend on `tenancy` — inverting the direction root `CLAUDE.md`'s "Dependencies flow strictly bottom-up" rule requires, and reintroducing exactly the module cycle (`tenancy` already requires `dbkit`) that rule exists to rule out. `model_test.go` reproduces `AssertNotTenantScoped`'s two checks by hand instead, using only `dbkit` and `pkgcore`.

`Repository` exposes no `Update` or `Delete` method at all — append-only is enforced by that absence at the application layer (`repository_test.go`'s `TestRepository_HasNoUpdateOrDeleteMethod`, a reflection-based proof). **A second, database-level backstop sits beneath it**: `migrations/{postgres,sqlite}/0002_append_only_enforcement.sql` installs a `BEFORE UPDATE`/`BEFORE DELETE` trigger pair on `audit_events` (PostgreSQL additionally a `BEFORE TRUNCATE` statement-level trigger — row-level triggers never fire for `TRUNCATE`) that raises on any attempt, regardless of which role or connection issues the statement — see "Append-only enforcement" below for the mechanism, its two named residual risks, and why a trigger, not a REVOKE-based restricted role, is what this codebase can actually guarantee. A hash chain over the table is not implemented (see "What this package does not do" below).

## Append-only enforcement — `migrations/{postgres,sqlite}/0002_append_only_enforcement.sql`

Both dialects install the identical mechanism SHAPE (their trigger syntax cannot be byte-identical — PostgreSQL needs a separate `FUNCTION ... LANGUAGE plpgsql` a trigger then references, SQLite's trigger body is inline SQL with no such indirection): a `BEFORE UPDATE` and a `BEFORE DELETE` trigger on `audit_events`, each unconditionally raising (`RAISE EXCEPTION` on PostgreSQL, `RAISE(ABORT, ...)` on SQLite) before the write ever reaches a row. `INSERT` matches neither trigger's event and is completely unaffected — `Repository.Insert`/`InsertIdempotent` keep working exactly as before. PostgreSQL additionally installs a third, `FOR EACH STATEMENT` trigger bound to `BEFORE TRUNCATE` (see "TRUNCATE is a separate case" below) — SQLite has no `TRUNCATE` statement, so it needs no equivalent.

**Why a trigger, not a REVOKE-based restricted role.** A database role stripped of `UPDATE`/`DELETE` privilege, backstopped by a trigger, is the production answer to tamper-proofing; this package ships the trigger half only, because the role half is not this codebase's to provision here: `go/dbkit`'s `Open` (`open.go`) opens exactly one connection/role per `*gorm.DB` — the same one every other table's reads and writes already go through — and provisioning a second, more restricted role for this one table alone would need this package to start owning role/credential provisioning, which dbkit declines to do even for PostgreSQL RLS's own role and policy ("a deployment-side responsibility this package assumes but does not create"). A REVOKE grant on a role this package never creates or names would either bind to nothing or need inventing that provisioning step here, breaking the identical precedent. A trigger has neither problem: it enforces the guarantee against **any** role that connects — a superuser console session included — with no role-provisioning prerequisite of any kind, which is why it is the mechanism actually shipped.

**TRUNCATE is a separate case, on PostgreSQL only.** PostgreSQL never fires a row-level trigger — `BEFORE UPDATE`/`BEFORE DELETE` included — for a `TRUNCATE` statement; only a trigger declared `FOR EACH STATEMENT` on the `TRUNCATE` event does. Without the third trigger, a single `TRUNCATE audit_events;` would have wiped the entire table with no error and no row-level trigger ever invoked, at no higher privilege than the row-level pair already required — a real gap, closed by `trg_audit_events_reject_truncate`, reusing the same reject-always function. `TestAppendOnlyTrigger_Postgres_RejectsTruncate` (`integration_test/postgres_append_only_test.go`) pins it against a real container.

**Two residual risks a trigger genuinely cannot close, documented rather than silently accepted:**

1. **PostgreSQL: the connecting role can disable or drop its own trigger.** `ALTER TABLE audit_events DISABLE TRIGGER ALL` (reversible — a write goes through unguarded, then `ENABLE TRIGGER ALL` restores appearances) and `DROP TRIGGER trg_audit_events_reject_delete ON audit_events` (permanent) both succeed for the identical role/ownership level that had to `CREATE` the triggers in the first place — there is no privilege tier between "can create this trigger" and "can disable or drop it." Closing this needs the same second, more restricted role the "why a trigger" paragraph above already declines to provision (granted `UPDATE`/`DELETE`/`TRUNCATE` on `audit_events` but withheld `ALTER`/`DROP TRIGGER` and ownership), with the application's ordinary connection going through that role instead of the one migrations run as. This migration's own header comment records the same conclusion inline. A deployment that wants this risk closed provisions that role itself and points `dbkit.Open`'s DSN at it — no code change needed here, since the trigger enforces against whatever role actually connects.
2. **SQLite: `INSERT OR REPLACE` needed `PRAGMA recursive_triggers` to be turned on, and it defaults off.** SQLite only fires a table's `DELETE` triggers for the implicit conflict-row removal the legacy `INSERT OR REPLACE` upsert form performs when the connection's `recursive_triggers` pragma is ON; left at its SQLite default (OFF), an `INSERT OR REPLACE INTO audit_events (...) VALUES (...)` against an existing `id` silently overwrote that row's columns with no error and no trigger firing — reachable only via raw SQL that bypasses `Repository` (which has no `Update` method to begin with), but exactly the threat class these triggers exist to stop. This is now closed, not merely documented: `go/dbkit/dialect/sqlite`'s dialector factory folds the driver's own `_pragma=recursive_triggers(1)` DSN parameter into every SQLite DSN `dbkit.Open` opens, which the underlying driver re-applies on every physical connection it establishes (not once per process), so every connection in `dbkit.Open`'s pool — not only whichever one happens to run first — has it turned on. `TestAppendOnlyTrigger_SQLite_RejectsInsertOrReplace` (this package's `append_only_test.go`) and `go/dbkit/dialect/sqlite`'s own `TestWithRecursiveTriggers`/`TestOpen_EnablesRecursiveTriggersOnEveryPooledConnection` pin it.

**Proof.** `append_only_test.go` (this package, SQLite, no Docker) and `integration_test/postgres_append_only_test.go` (build-tagged `integration`, a real PostgreSQL container via `dbkit/dbtest.NewPostgres`) both open a raw `*sql.DB` from the same migrated connection `Repository` runs through and issue a raw `UPDATE`/`DELETE`/(PostgreSQL also `TRUNCATE`; SQLite also `INSERT OR REPLACE`) directly against `audit_events` — bypassing `Repository` entirely, since it never had a mutating method to bypass in the first place — asserting the database itself refuses each, that the row is provably unchanged (a live `Repository.Get` read-back, not merely that the statement errored), and that ordinary `Insert` traffic is unaffected.

### Collection — `emit.go`, `module.go`

| Signature | Purpose |
|---|---|
| `type Input struct { Action string; Resource Resource; Result Result; Changes *Diff }` (`emit.go`) | What a caller passes to `Emit`; identity is read from `ctx`, not `Input`, so every caller populates it the same way |
| `type Diff struct { Before, After map[string]any }` | An optional before/after change set for `Input.Changes`. Deliberately no `json` struct tags — every event payload type in this package and in `dbkit` relies on `encoding/json`'s default per-field-name behavior, so `module.go`'s wire-decode helpers can look every field up under one consistent capitalized key regardless of type. Its doc comment states the content contract that makes the freeform shape safe: `changesJSON` writes these maps **verbatim** into the changes column with no redaction and no filtering, on the one table in this system with no published path to delete from — so a `Diff` may record that a field changed and how, never plaintext PII, keys/tokens or full prompt/document bodies (see "The changes-column content contract" below) |

| `var ErrActionNotRegistered` | `Emit`'s rejection sentinel, matched with `errors.Is` |
| `func New(db *gorm.DB) *Module` (`module.go`) | Returns the persister `pkgcore.Module`. `db` must come from `dbkit.Open`, with `migrations.FS` already applied — identical contract to `config.NewModule` |
| `func (*Module) Register(reg pkgcore.Registrar) error` | Declares `dbkit.EventWriteCaptured` and `EventRecorded` on `reg.Events` (on `dbkit`'s behalf for the former, since `dbkit` itself is not a `pkgcore.Module`), declares `AuditActionSystemContextEntered` on `reg.AuditActions` (on `go/tenancy`'s behalf — see "Subscribing to `tenancy.system_context.entered`" below), subscribes to all three event types, and captures `reg.AuditActions` on the `Module` for the write-captured vocabulary gate (consulted live at event time, never snapshotted — `Register` runs before other modules have registered their own actions) |
| `const AuditActionSystemContextEntered` | The audit action `Module.Register` declares for `tenancy.EventSystemContextEntered`, since `go/tenancy` has no `pkgcore.Module` of its own to declare it |

**Collection failure contracts — the division of fulfilment, per mechanism.** The rule both mechanisms serve: an audit-write failure must alert and never be silently dropped. Each mechanism's position in the write pipeline fixes which half of the rule it can fulfil, and the other half belongs to whoever is left holding the failure:

- **The automatic capture plugin (`go/dbkit/audit_capture.go`) ALERTS and continues.** Its publish runs only after the write it describes has already durably committed (`tenant_session.go`/`audit_capture.go`'s own docs), so there is nothing left to roll back and no call it can fail — the plugin's whole fulfilment of the rule is the structured `auditPublishFailed` alert, and the drop half of the rule (the audit row that will never exist) is inherent to its post-commit position. It cannot fail closed, and its own doc comment says exactly that and why.
- **`Emit` RETURNS the error.** It runs before the persister's write, so it can fail closed, and it does: the publish error is returned, never swallowed, to the caller. The caller half of the rule is therefore the caller's: a caller that discards the returned error has done the silent drop the rule exists to prevent, and nothing in this package can detect it — the obligation is written into `Emit`'s doc comment because the contract is the only place this package can hold it (the same shape as `go/notification`'s `UserAddressResolver` obligation sentence). The recommended caller half, modeled by the reference app's notes handler and `go/authn`'s `recordAudit`, is a structured log of the failure — never a bare discard.

**The capture-vocabulary gate — every `action` value is validated against the declared enumeration before a row exists, whichever mechanism produces it.** `Emit` validates its own `Input.Action` (see `ErrActionNotRegistered` above). The system-context subscriber's action is declared by this package's own `Register`. The third path is the one the gate protects: `onWriteCaptured` derives `<resource_type>.<operation>` (e.g. `note.create`) in place and refuses — with a structured `log/slog` alert (`auditCaptureActionRefused`, the same dbkit-tier idiom and attribute names `auditPublishFailed` uses), never an error return (the described write has already committed; an error would wedge the event's other subscribers or retry forever on the distributed bus) and never a silent write — any derived string nobody declared on `reg.AuditActions`. The gate exists because the trail's query surfaces filter on the declared enumeration: an undeclared-action row would be invisible to a compliance question, the same answer as no row at all. The contract that makes the gate satisfiable: a host wiring the capture plugin declares each `<AuditResourceType>.<operation>` pair its `Auditable` models produce — `note.create` alongside the qualified `notes.note.create` an `Emit` caller records — in its own module's `Register`, exactly like any other audit action. Declared operations persist; undeclared ones are refused loudly.

### The changes-column content contract

`Diff`'s doc comment (`emit.go`) states the content contract of the `changes` column, and this section records why the contract exists in the form a reader of this table's column inventory can act on. The column's writers are open-ended — any `Emit` caller's freeform `Diff`, any captured model's columns — and `changesJSON` filters and redacts nothing: the maps land in the column byte for byte. Two properties make that acceptable only under an explicit caller contract, and both are stated there:

- **The content rule.** No plaintext PII (emails, phone numbers, names), no keys or tokens, no full prompt or document bodies — a `Diff` records that a field changed and how (identifiers, structural values), never the sensitive content itself. Requiring completeness ("a caller using Emit is expected to know, and state, exactly what changed") does not license recording the sensitive parts of what changed.
- **The landing.** This column is on the only table in the system with no published path to delete from: `Repository` has no `Update`/`Delete`, `dbkit.Repository[T]`'s `HardDelete` cannot be instantiated against `AuditEvent` (no `TenantScoped`), the append-only trigger set refuses `UPDATE`/`DELETE` at the database, and `go/compliance` only reads. Anything written here is effectively permanent.

### Column inventory and population

Every `audit_events` column answered against the same three questions — who fills it, when, and what an unfillable case stores — the standing account both `model.go`'s field comments and the migration files' comments point at:

| Column | Who fills it | When | Unfillable case |
|---|---|---|---|
| `id` | This package (`Repository.Insert` generates a UUID; `Module`'s subscribers derive a deterministic one) | Every insert | N/A — always filled |
| `actor_type` / `actor_id` / `actor_display_name` | `SetActor`, from the `pkgcore.Actor` the emitting code placed on `ctx` (`WithActor`) or on the captured write | Every record | No actor known (an unmatched login attempt): `authn` emits with no actor on `ctx`, and the columns store empty values — a deliberate, documented zero value, not an unfillable-case marker |
| `on_behalf_of_type` / `_id` / `_display_name` | `SetOnBehalfOf`, from the optional `*pkgcore.Actor` the emitting code placed on `ctx` (`WithOnBehalfOf`) | Impersonated actions only | No impersonation: all three stay `NULL` — the column trio's whole reason to be nullable |
| `action` | The emitting module (via `Emit.Input.Action`, validated against the registered vocabulary), or this package (`Module` derives `"<resource_type>.<operation>"` for captured writes — the derived action is validated against the same registered vocabulary before persistence: undeclared is refused with a structured alert, never silently written), or the system-context event's own action, declared by this package's `Register` | Every record | N/A — always filled |
| `resource_type` / `resource_id` / `resource_display_name` | `SetResource`, from the emitting module's `audit.Resource` | Every record | N/A — always filled |
| `success` | `SetResult`, from the emitting module | Every record | N/A — always filled |
| `failure_reason` | `SetResult`, from the emitting module | A failed action only | Successful action: empty string |
| `changes` | `Module`'s `changesJSON`, from `Emit.Input.Changes` or the capture plugin's `Before`/`After` — both written **verbatim**, with no redaction or filtering at this boundary: `Diff`'s content contract ("The changes-column content contract" above) is the caller side of that fact, and the capture plugin's own `[redacted]` marker is the automatic side | An action with a diff only | No diff: `NULL` |
| `tenant_id` | `Emit`/the capture plugin, from `ctx` (`TenantFromContext`); `Module`'s subscribers, from the event | Every record | Platform-level action: empty-string sentinel, never `NULL` |
| `ip` / `user_agent` / `trace_id` | The two collection mechanisms, from the `dbkit.RequestMetadata` context carrier (`WithRequestMetadata`/`RequestMetadataFromContext` in the `dbkit` root package, the shape `pkgcore`'s `WithActor`/`ActorFromContext` already sets for identity): the write-capture plugin reads it from the write's own context (`go/dbkit/audit_capture.go`'s `capture`), `Emit` reads it from the caller's context (`emit.go`), and the values ride the event payloads (`WriteCapturedEvent`/`RecordedEvent` fields) to `Module`'s persisters, which store them on the row | An action whose context carried the carrier | No carrier on the context (a background job, an event subscriber): all three store the empty string; read an empty one as "no request context was carried", never as information about which background process ran |
| `occurred_at` | GORM's `autoCreateTime` | Every insert | N/A — always filled |

The three request-context columns (`ip`, `user_agent`, `trace_id`) are conditionally filled from the `dbkit.RequestMetadata` context carrier (`WithRequestMetadata`/`RequestMetadataFromContext` in the `dbkit` root package rather than `pkgcore`, since both readers — dbkit's own capture plugin and this package's `Emit` — sit at or below dbkit and every producer above it can import dbkit), the shape `pkgcore`'s `WithActor`/`ActorFromContext` already sets for identity: HTTP layers stamp the carrier onto request contexts, and both collection mechanisms read it when present. An empty column means the action's context carried no carrier — never information about which background process ran. The one row-producing path that still stores the empty string unconditionally is the system-context-entered subscriber (`Module`'s `onSystemContextEntered`): tenancy's system-context event payload carries no request context by design — a context grant is not an HTTP request — and the persister's own context on the subscriber side of the bus is never the grant's context. Producers in the HTTP middleware chain are the host side of the same wiring and remain each host's own work.

**Column bounds — the width sweep and the write-boundary enforcement.** A review of every source-to-column width pairing found two real wider-than-target pairings feeding the table, both into `resource_display_name` (VARCHAR(255)): `go/integration`'s webhook URL (source column `url` VARCHAR(2048) — `webhook_service.go`'s `emitWebhookAudit` puts `row.URL` into `audit.Resource.DisplayName`) and `go/sharing`'s `resource_ref` (VARCHAR(512) — `service.go`'s `emitSensitiveAudit`). Every other source is narrower than its target (authn's `users.display_name` VARCHAR(128) vs `actor_display_name` VARCHAR(255); integration's API-key `prefix` VARCHAR(32); UUID ids; short registered vocabularies), so no further pairing needed its own treatment — but a per-site fix would never be complete anyway, since the table's writers are open-ended. The enforcement therefore lives at the one choke point every row passes through — `Repository.Insert`'s `fitEventToColumns`, immediately before the `INSERT` (see `repository.go`'s own doc comment and `model.go`'s column-bounds constants) — and splits the columns by class:

- **Descriptive columns** (`actor_display_name`, `on_behalf_of_display_name`, `resource_display_name`, `failure_reason`, `ip`, `user_agent`, `trace_id`): over-long values are legal content (a URL, a user agent), so they are **cut to the column's width in Go**, rune-safely, with invalid UTF-8 sanitized first — and each cut is recorded in a structured warning naming the field, the limit, the original length and the row context. The cut happens here and not in the schema because a database-layer truncation is an unrecordable integrity loss: the trace is the point. The integration and sharing sites above need no code of their own — the caught pairing (and its family) is closed by this one enforcement point, with the cut's trace logged by the persister that performs it.
- **Identifier and vocabulary columns** (`id`, `actor_type`, `actor_id`, `on_behalf_of_type`, `on_behalf_of_id`, `action`, `resource_type`, `resource_id`, `tenant_id`): an over-wide value there is a caller bug, and cutting it would rewrite the record's own identity (a truncated id no longer deduplicates or reads back), so `Insert` **refuses** with `ErrEventFieldTooLong` before the write, identically on both dialects — never a PostgreSQL-only 22001.

`migrations_test.go`'s `TestMigrations_ColumnWidths_MatchTheColumnBoundConstants` pins the constants to both migration files mechanically, and the enforcement itself is proven by `repository_test.go` (the Go-side cut and refusal, SQLite) and `integration_test/postgres_column_bounds_test.go` (the genuine 22001-fail-before against a real server, which the SQLite-only tier cannot show).

### Subscribing to `tenancy.system_context.entered`

`Module` persists `go/tenancy`'s `EventSystemContextEntered` (`tenancy.system_context.entered`) as an `AuditEvent`, so every use of the system context is itself an audit event. It does this **without importing package `tenancy`**: `go/tenancy`'s `go.mod` requires `go/dbkit` (`tenancy` sits above `dbkit` in the module dependency graph — `pkgcore -> dbkit -> tenancy -> config/jobs -> ...`), and this package is a subpackage of `dbkit` itself, so importing `tenancy` from here would make `dbkit` depend on `tenancy` — the same module-cycle conflict `model_test.go` documents for `tenancytest.AssertNotTenantScoped`. `module.go`'s `tenancySystemContextEnteredEventType` constant duplicates the event-type string by hand instead, and `decodeSystemContextEntered` reads the payload structurally (by field name, via reflection for the concrete struct the standalone in-memory bus delivers, or via a `map[string]any` for the distributed bus's JSON shape) rather than type-asserting to `tenancy.SystemContextEnteredEvent`. Whether `tenancy` should instead gain its own minimal `pkgcore.Module` to declare the action on its own behalf remains an open wiring option; this package's shape does not depend on it.

## Multi-replica delivery

In distributed deployment mode with more than one replica, the broker-backed `pkgcore.EventBus` implementations deliver every published event to **every replica once each** (the Redis implementation's own doc comment: "each event is delivered to every replica exactly once" — once per replica, not once system-wide, since most subscribers hold per-replica state rather than writing into one shared row). `Module`'s three subscribers do the opposite: every replica's `onWriteCaptured`/`onRecorded`/`onSystemContextEntered` writes into the SAME shared `audit_events` table, so a single real action independently reaches every replica's subscriber and, without deduplication, would leave one row per replica instead of one row total.

`Module` deduplicates by giving `AuditEvent.ID` a value **deterministically derived from the event's own content** — `module.go`'s `auditDeterministicEventID(eventType, occurredAt, parts...)`, a `uuid.NewSHA1` hash over the event type, an RFC3339Nano-normalized `occurredAt`, and a handler-specific tuple of fields (tenant, resource, actor, operation for `onWriteCaptured`; tenant, action, resource, actor for `onRecorded`; tenant, actor, purpose, ticket for `onSystemContextEntered`) — instead of leaving `ID` for `Repository.Insert` to generate randomly. Every replica computes the identical `ID` for the identical underlying event (the wire-decode helpers already normalize the concrete-struct and JSON-`map[string]any` shapes into the same Go values before this runs), so the second and any later replica's insert collides on the primary key; each subscriber calls `Repository.InsertIdempotent` rather than `Insert`, which turns that collision into a silent no-op instead of an error. `occurredAt` is taken at nanosecond precision specifically so two *genuinely different* actions essentially never collide — they would need to share tenant, resource, actor and operation AND land in the same nanosecond, which does not happen outside of the exact redelivery this exists to detect.

This only matters in distributed deployment mode with 2+ replicas; the standalone in-memory bus and a single-replica distributed deployment never redeliver, so the derived `ID` and `InsertIdempotent`'s dedup are inert (but harmless) there. See `repository_test.go`'s `TestRepository_InsertIdempotent_DuplicateID_IsANoOp` (the `Repository`-level proof) and `module_test.go`'s three `*_DeliveredToMultipleReplicas_PersistsExactlyOnce` tests (the end-to-end proof, through the real deterministic-ID derivation, one per subscriber).

## The collection-to-persistence crash window (both mechanisms share it)

An audit trail assembled from a published event can never be made atomic with the business write that produced it: the audit row lives in its own `INSERT` (this `Module`'s persister), which runs after — sometimes long after — the business transaction committed. The residual risk is a **crash in the window between the business write committing and the audit row's own `INSERT` committing: the business row survives and the audit row never exists, with no record anywhere that one was owed.** It is recorded here, in the two mechanisms' common home, because BOTH collection mechanisms share the identical window and neither can close it:

- **The automatic capture plugin** (`go/dbkit/audit_capture.go` + `tenant_session.go`): `WithTenantSession` publishes the transaction's buffered events only after its own `db.Transaction` has returned nil (`tenant_session.go`'s commit-then-publish ordering). A crash after that commit returns but before `publishBuffered`'s publishes (and the persister's inserts) land loses the events with no trace. Making the two writes atomic was exactly the route that produced the same-SQLite-file `SQLITE_BUSY` self-deadlock documented in `go/dbkit/AGENTS.md`'s "Audit trail collection" section; the buffer-until-after-commit design is the residue of that trade-off, and the window is its accepted cost.
- **`Emit`** (the declarative path): every real caller invokes `Emit` AFTER its business write has already committed — the notes handler (`examples/reference-app/internal/notes/handler.go`), `go/sharing` (`service.go`'s own comment: "Calling audit.Emit here, AFTER s.shares.Create has already returned"), `go/billing` (`credit_service.go`), `go/integration`, `go/authn`, `go/compliance` and `go/admin` all follow the shape. A crash between the business commit and the persister's insert of the `EventRecorded` row has the same silent result. `Emit`'s returned error does not cover this window either: the crash happens after `Emit` returned nil.

Why it cannot be eliminated: closing it would require the audit row to commit atomically with the business write — the plugin shape that self-deadlocked (above), or an outbox row in the business write's own transaction, which would make every audited table in every consuming module carry one. It is therefore accepted and detected rather than engineered away: **operations can detect it by querying** — a business row existing without its audit row is visible to any audit-query consumer (`compliance.AuditQuery` over this table), and the deterministic event IDs (`auditDeterministicEventID`) mean a manual re-publish of the originating event would deduplicate rather than duplicate.

## What this package does not do

- No query/report API beyond `ListByTenant`: no actor/resource/action/time-range/result search and no console surface over the trail exist. `go/compliance`'s `AuditQuery` is the closest read surface, built over this table.
- No immutability enforcement *beyond* the application-layer absence of a mutating method *plus* the database-level trigger set (`0002_append_only_enforcement.sql`, see "Append-only enforcement" above) — a REVOKE-based restricted role that would also close the "connecting role can disable/drop its own trigger" residual risk is not shipped, for the reason that section gives, and no hash chain exists.
- No retention/archival.

## Reference-app consumer

`examples/reference-app` is this package's mandatory first consumer (root `CLAUDE.md`'s "a module API it does not use is not done" rule): `internal/notes/handler.go`'s `NotesCreateNote` calls `Emit` explicitly (`recordNoteCreatedAudit`) after a note is created, under the already-declared `notes.note.create` audit action; `internal/app/server.go` wires `audit.New(db)` into the app's `Kernel.Bootstrap` module set, sharing the notes module's own database connection — no new infra dependency. `flowtests/server_test.go`'s `TestBuildServer_NoteCreate_PersistsAuditEvent` is the end-to-end proof: a real POST `/api/v1/notes` through the composed HTTP stack, then a second `dbkit.Open` connection to the same SQLite file reading the row back through a real `Repository.ListByTenant` call — not a mock, and not merely an in-memory event assertion (that narrower claim is `internal/notes/handler_test.go`'s `TestHandler_Create_ValidText_RecordsAuditEvent`).

`notes.Note` also implements `dbkit.Auditable` (`AuditResourceType() string { return "note" }`), but the reference app's own `db` deliberately does **not** set `dbkit.Options.AuditBus` on it — see `go/dbkit/AGENTS.md`'s "Audit trail collection" section for the same-SQLite-file deadlock that composition discovered, and `server.go`'s own doc comment on its `dbkit.Open` call for the app-specific write-up. The declarative `Emit` path above is what this app relies on for persistence; `Auditable` stays declared so a host wiring `Options.AuditBus` over a dedicated audit connection captures `Note` writes too.
