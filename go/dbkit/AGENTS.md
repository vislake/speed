# dbkit

dbkit is speed's dual-dialect (PostgreSQL and SQLite) data-access layer: a safety-wrapped way to open a `*gorm.DB` (`Open`), the mandatory generic tenant-scoped `Repository[T]` base every business module's repository embeds instead of holding a raw connection — including its opt-in mark-delete (soft-delete) capability, `SoftDeletable`/`Restore` (`soft_delete.go`), and its system-context-gated physical-erasure path, `HardDelete` (`hard_delete.go`) — `MigrationRegistry` for aggregating and applying each module's own versioned SQL migrations in dependency order, field-level AES-256-GCM encryption with HMAC blind indexes for sensitive columns, and deterministic HKDF-based key derivation (`DeriveKey`) so a host can manage one root secret instead of one independent secret per encrypted column. It sits directly above `pkgcore` in the module dependency graph (`pkgcore -> dbkit / observability -> tenancy -> ...`) and implements the Go-side wiring for all three of the project's mandatory tenant-isolation layers — including layer 3's session-variable step, `WithTenantSession`, though provisioning the PostgreSQL role and RLS policy that step depends on remains a deployment-side responsibility this package assumes but does not create (see Out of scope).

**One dependency, and why there is only one.** dbkit imports exactly one other speed module: `pkgcore` — its root package, for `pkgcore.TenantID` / `pkgcore.WithTenant` / `pkgcore.MustTenantFromContext` and the module-contract surface `MigrationRegistry` aggregates over, plus `pkgcore/apperr` for every error dbkit returns. (`internal/testutil`, used only by dbkit's own tests, also imports `pkgcore`, so its `Widget` fixture can implement `GetTenantID`.) This is architectural, not incidental minimalism:

- **dbkit cannot depend on `tenancy`.** The dependency graph is `pkgcore -> dbkit -> tenancy -> ...`; `tenancy` itself depends on dbkit for `dbkit.Repository[T]` and `dbkit.TenantScoped` (which `tenancytest`'s isolation assertions build on) — the GORM tenant-isolation plugin itself lives entirely in dbkit's own `tenant_scope.go`, not in tenancy — so an import running the other way would be a cycle. This is also why dbkit calls `pkgcore.MustTenantFromContext` directly instead of going through `tenancy`'s audited wrapper: anything at or below dbkit's layer uses the raw `pkgcore` primitives; only code built above `tenancy` gets the audited convenience wrapper around them.
- **dbkit cannot depend on `observability` either**, for the identical bottom-up reason (`pkgcore -> dbkit / observability -> ...` — the two sit at the same graph depth, neither above the other). That is why `Open` silences GORM's own query logger (`gormlogger.Default.LogMode(gormlogger.Silent)`) instead of routing it through the structured logger the rest of the codebase uses — see `Open`'s doc comment in `open.go`. A caller that wants query logs takes them from the returned error and logs it through its own context logger instead.

Beyond `pkgcore`, dbkit's dependencies are exactly the third-party pieces the job requires: `gorm.io/gorm`, the two dialect drivers (`gorm.io/driver/postgres` and the pure-Go, CGO-free `github.com/glebarez/sqlite`), and, for the integration tier only, `github.com/jackc/pgx/v5` and `testcontainers-go`.

**The two dialect drivers live in their own subpackages.** `dbkit.Open`'s dialect selection is a small package-level registry mirroring `database/sql`'s own driver-registration pattern (`open.go`'s `RegisterDialect` / `dialectRegistry`) rather than a hardcoded `switch`. dbkit's root package does not import `github.com/glebarez/sqlite` or `gorm.io/driver/postgres` directly; each driver lives in its own subpackage, importable only for its `init` side effect: `github.com/vislake/speed/go/dbkit/dialect/sqlite` and `github.com/vislake/speed/go/dbkit/dialect/postgres`. A caller blank-imports the one(s) it needs, typically next to its `dbkit.Open` call site or in its module's main package:

```go
import _ "github.com/vislake/speed/go/dbkit/dialect/sqlite"
```

An unregistered dialect fails with `dbkit.invalid_dialect`, with a `hint` parameter naming the fix, mirroring Go's own "sql: unknown driver ... (forgotten import?)". `dbkit/dbtest` blank-imports both subpackages itself, so `dbtest.NewSQLite`/`dbtest.NewPostgres` call sites never need their own imports — bundling both drivers into a test-only package is correct and intentional, since test binaries are never a consumer's production dependency.

Both drivers stay direct requires in dbkit's own `go.mod`, because the dialect subpackages are part of the same module and import them directly. The win is at a *consumer's* `go.mod`: a consumer that imports `dbkit` without blank-importing either dialect subpackage carries neither driver's transitive closure — measurable by the module's own method (a throwaway module requiring only `github.com/vislake/speed/go/dbkit`, `go mod tidy` under `GOWORK=off`, counting `// indirect` entries). `go/saasctl`'s own `go.mod` demonstrates this for real: it needs only `dialect/sqlite` (its `db migrate` command and generated skeletons never touch PostgreSQL), so `gorm.io/driver/postgres` and the whole `jackc/pgx` family stay out of its indirect requires entirely.

**Out of scope.** Business queries beyond create / read-by-id / update / delete / list-all (`Repository[T]` is deliberately minimal — see Known limitations); the audited, business-facing wrapper around the system-context escape hatch (`tenancy.WithSystemContext`); provisioning the PostgreSQL roles and RLS policies isolation layer 3 depends on, which is a deployment-side responsibility this package assumes but does not create; the whitelist that decides which modules may hold a system context at all, and the audited entry through which one is granted — the caller-side obligations of `HardDelete`'s gate, enforced outside this package (see "Hard deletion" below); retention-window enforcement for `Restore` (see "Soft deletion" below — `Restore` enforces no window; the retention window and its sweep orchestration are `go/compliance`'s, not this package's).

## The three-layer tenant isolation defense

Multi-tenant isolation is speed's highest-priority rule: "forgot to filter by tenant" is treated as a security defect, not a style issue, so it is never left to one mechanism alone. dbkit implements the Go-side wiring for all three independent layers; each is designed to hold even if the layer(s) below it were absent, misconfigured, or bypassed.

| Layer | Mechanism | File | Status |
|---|---|---|---|
| **1 — GORM plugin** | The unexported `tenantScopePlugin`, installed automatically by `Open` on every connection it returns. For any model implementing `TenantScoped`, it injects `WHERE tenant_id = ?` ahead of every plugin-covered read or write (reading the tenant from `pkgcore.TenantFromContext(db.Statement.Context)`): on the read side it registers on both read processors — the query processor, which Find/First/Take/Last/Count/Pluck execute, and the row processor, which Scan/Row/Rows execute (a separate callback chain, so the projection shape `db.Model(&M{}).Scan(&dtos)` is plugin-covered too) — and on the write side it covers update/delete, forcing the `tenant_id` column to that tenant on every create, overwriting whatever the caller populated the struct with. Fails the statement closed (`ErrMissingTenantContext`) when the context carries no tenant. | `tenant_scope.go` | Implemented. Unit-tested in `tenant_scope_test.go` (row-path coverage in `TestTenantScopePlugin_RowPath_*`); integration-tested against real PostgreSQL in `integration_test/postgres_tenant_isolation_test.go` |
| **2 — `Repository[T]`** | Resolves the tenant from `ctx` itself, before ever touching the database — it does not trust layer 1 to catch a missing tenant. Scopes every query it issues by `tenant_id` explicitly, re-verifies the tenant on every row it hands back (`FindByID`), and fails closed the same way. Its checks are independently complete: it enforces isolation correctly even given a `*gorm.DB` not obtained from `Open` — which is exactly how dbkit's own unit tests exercise it, against a plugin-less SQLite connection. That is a valid way to unit-test a `Repository[T]`; it is not a valid way to run one in production. Every method's actual database call routes through `WithTenantSession` (layer 3's wiring, below), so every `Repository[T]` call also runs inside an explicit transaction — a real, deliberately accepted overhead, in exchange for layer 3 being reachable through the one sanctioned data-access path instead of only through code that remembers to call `WithTenantSession` itself. | `repository.go` | Implemented. Same test files as layer 1, plus `repository_test.go` |
| **3 — PostgreSQL row-level security** | A restricted, non-`BYPASSRLS` application database role plus a policy keyed on a per-request/transaction session setting (`current_setting('app.current_tenant', true)`), enforced by the database itself, below the Go layer entirely — the backstop meant to hold even if layers 1 and 2 are both bypassed (raw SQL, a `*gorm.DB` not obtained from `Open`, a bug in either layer). | `tenant_session.go` | **Session-variable wiring implemented**: `WithTenantSession` sets the GUC inside an explicit transaction when connected to PostgreSQL. Provisioning the role and the policy themselves remains a deployment-side responsibility (see Out of scope) |

**Layer 3.** `WithTenantSession(ctx, db, fn)` (`tenant_session.go`) resolves the tenant from `ctx` the same fail-closed way everything else in this package does, then runs `fn` inside `db.WithContext(ctx).Transaction(...)`; when `db.Name() == "postgres"`, it first runs `SELECT set_config('app.current_tenant', ?, true)` as the transaction's first statement, before `fn` ever runs. Every `Repository[T]` method routes its actual database call through it (see `repository.go`), and it is exported so the raw-SQL escape hatch below can opt into the same protection.

The database-side mechanism itself is proven in `integration_test/postgres_rls_test.go` — a restricted role and an RLS policy set up entirely by hand over `database/sql`, with no dbkit code involved. `integration_test/postgres_tenant_session_test.go` goes further and proves `WithTenantSession` itself (not hand-written SQL) is what drives a real RLS policy correctly end to end, including that the GUC it sets does not leak across calls sharing one pooled connection.

**Why `SELECT set_config('app.current_tenant', ?, true)`, not `SET LOCAL app.current_tenant = ?`.** PostgreSQL's `SET`/`SET LOCAL` statements do not accept a bound query parameter for the value being set — `SET LOCAL app.current_tenant = $1` is rejected outright with a syntax error (`SQLSTATE 42601`), confirmed against a live server, regardless of driver or ORM. `set_config(name, value, is_local)` is an ordinary function call, so its `value` argument is a normal bound parameter (keeping the tenant id out of the SQL text, with no bespoke escaping to get right), and `is_local = true` gives it the identical transaction-scoped, revert-on-`COMMIT`-or-`ROLLBACK` semantics as `SET LOCAL`. Do not "simplify" `tenant_session.go` back to a literal `SET LOCAL` statement with the tenant id interpolated into the SQL string; see that file's own doc comment for the full detail.

## Public API

### Connections — `open.go`

| Signature | Purpose |
|---|---|
| `type Dialect string`, constants `DialectPostgres`, `DialectSQLite` | The two SQL dialects dbkit supports. Any other value, including the zero value, is rejected |
| `type Options struct { Dialect Dialect; DSN string }` | `Open`'s configuration. `DSN` is driver-specific (a libpq/pgx URL for Postgres; a file path or `file::memory:?cache=shared` for SQLite) and is never logged or included in a returned error |
| `func Open(ctx context.Context, opts Options) (*gorm.DB, error)` | The ONLY sanctioned way to obtain a `*gorm.DB` anywhere in this codebase. Validates `opts.Dialect`, opens the matching driver, applies fixed connection-pool limits (25 max open / 5 max idle / 30 min max lifetime — not configurable through `Options`, on purpose, since every connection in this codebase shares the same pool shape), pings bound to `ctx`, installs the layer-1 tenant-scoping plugin, and only then returns — no caller can end up holding an "unprotected" handle by accident. Returns `apperr.Invalid("dbkit.invalid_dialect")` for a bad dialect, `apperr.Internal("dbkit.connect_failed")` for a driver or connectivity failure |
| `func Close(db *gorm.DB) error` | The one sanctioned way to release a connection's underlying database handle, the counterpart of `Open` being the one sanctioned way to obtain one — business modules never reach for `db.DB()` themselves. Resolves the `*sql.DB` inside the handle and closes it, so every pooled connection is released and a later use fails (`sql: database is closed`) instead of silently opening fresh ones; idempotent (a second call is a nil-returning no-op, database/sql's own contract), so a repeated shutdown step cannot fail. A nil handle is a plain error ("requires a non-nil *gorm.DB"); a failure closing is `apperr.Internal("dbkit.close_failed")` with the cause. The caller closes once, at the shutdown of whatever owns the connection — for a component-registered connection, the db component's own `Close` callback |

### Components — `component.go`

The two database components a composition configuration selects as the `db` module's implementation, self-registered from this file's `init` (`pkgcore.MustRegister`). Both provide `(*gorm.DB)(nil)` and take one configuration key, `dsn`; the dialect is pinned by the component's own name.

| Name | Dialect | Capabilities | Lifecycle |
|---|---|---|---|
| `db.sqlite` | `DialectSQLite` | 0 | `New` connects only; `Verify` applies the assembled migration sets; `Close` releases the connection |
| `db.postgres` | `DialectPostgres` | `MultiReplicaSafe\|SurvivesRestart` | same three callbacks |

`db.sqlite` declares no capabilities on purpose — a distinct SQLite file is not shared state a second replica may use, so a distributed-mode assembly selecting it must fail the capability check — while `db.postgres` declares what the distributed deployment mode requires. `New` deliberately connects only: construction of other components may still fail, and a failed assembly must not have touched the database; migrations run in `Verify`, where every product exists and the selected component set is complete. A distributed-mode assembly may select at most one of the two (two `*gorm.DB` providers make every consumer's resolution ambiguous).

### Tenant scoping — `tenant_scope.go`

| Signature | Purpose |
|---|---|
| `type TenantScoped interface { GetTenantID() pkgcore.TenantID }` | Marker interface opting a model into both isolation layers. `GetTenantID` is never actually called by the plugin — it is used purely as a marker, and the tenant to filter or populate by always comes from context, never the model. That is what makes `Create`'s tenant-forcing real: a caller cannot get a row inserted under a different tenant by populating the struct differently |
| `type TenantModel struct { TenantID string }` — tag `` `gorm:"column:tenant_id;not null;index:,priority:1"` `` | Embeddable base satisfying `TenantScoped` and giving the plugin its known column, for a model that does not need `tenant_id` in its primary key. Note: the tag does **not** include `primaryKey` (see Known limitations) — do not "fix" that by shadowing the field from the embedding struct; that silently breaks `GetTenantID` instead (see the type's own doc comment and `tenant_scope_tenantmodel_test.go`, which embeds it and proves both the working path and that failure mode). `internal/testutil.Widget` needs the composite key, so it declares `TenantID` directly instead, with its own `primaryKey` tag, rather than embedding `TenantModel` |
| `func (TenantModel) GetTenantID() pkgcore.TenantID` | Satisfies `TenantScoped` |
| `var ErrMissingTenantContext = apperr.Internal("dbkit.tenant_context_required")` | The plugin's own fail-closed error (with the `pkgcore` error attached via `WithCause`) when a tenant-scoped statement runs on a context carrying no tenant |
| `var ErrTenantIDImmutable = apperr.Invalid("dbkit.tenant_id_immutable")` | Returned when an `Update`/`Updates` payload against a tenant-scoped model tries to set `tenant_id` to a different tenant than the context's |

### `Repository[T]` — `repository.go`

| Signature | Purpose |
|---|---|
| `type Repository[T TenantScoped] struct { ... }` | Generic, tenant-scoped data-access base (isolation layer 2). The zero value is not usable — construct with `NewRepository`. `T` must additionally have exported `ID` and `TenantID` string fields by those exact names — a documented convention `TenantScoped` cannot express in the type system, enforced at first use instead of at compile time |
| `func NewRepository[T TenantScoped](db *gorm.DB) *Repository[T]` | `db` is expected to come from `Open` (for layer 1 underneath); `Repository[T]`'s own checks are independently complete regardless of how `db` was obtained |
| `func (r *Repository[T]) Create(ctx context.Context, m *T) error` | Resolves the tenant from `ctx`, overwrites `m`'s `TenantID` field with it regardless of what the caller set, inserts. No tenant in `ctx` → `pkgcore`'s error returned unmodified, before the database is touched |
| `func (r *Repository[T]) FindByID(ctx context.Context, id string) (*T, error)` | Tenant-scoped lookup by `id`. `ErrRecordNotFound` for both "no such id" and "that id belongs to another tenant" — deliberately indistinguishable, so a caller can never learn from the response alone that an id exists under a tenant it cannot access |
| `func (r *Repository[T]) Update(ctx context.Context, m *T) error` | Full-record save (`Select("*")`, never a partial patch) over the row identified by `m`'s `ID`, scoped to `ctx`'s tenant; overwrites `m.TenantID` the same way `Create` does. `ErrMissingID` for an empty id (checked before touching the database); `ErrRecordNotFound` when nothing matches, including a cross-tenant id. For a `SoftDeletable` `T`, the WHERE additionally requires `deleted_at IS NULL` — a soft-deleted row is as unreachable by `Update` as a missing one, collapsing to `ErrRecordNotFound` without touching the mark (see the "Soft deletion" section below); a live row's save is unaffected. For a `T` whose only columns are `id` and `tenant_id` (a pure marker/link record with no other field), a successful call is a verified no-op touch rather than a real write — see the Rules section below |
| `func (r *Repository[T]) Delete(ctx context.Context, id string) error` | Tenant-scoped delete by `id`, branching on `T`'s own capability (see "Soft deletion" below): a `T` implementing `SoftDeletable` gets a mark-delete (one UPDATE setting `deleted_at`/`deleted_by`); every other `T` keeps the real, physical `DELETE`. `ErrRecordNotFound` when nothing matches either way |
| `func (r *Repository[T]) Restore(ctx context.Context, id string) error` | Clears `deleted_at`/`deleted_by` on a row a `SoftDeletable` `T`'s `Delete` previously soft-deleted, making it visible to ordinary queries again. `ErrNotSoftDeletable` when `T` does not implement `SoftDeletable`; `ErrRecordNotFound` when no currently-soft-deleted row matches `id` under `ctx`'s tenant (collapsing "no such id", "wrong tenant", and "exists but was never deleted" into one signal, for the same information-leak reason `FindByID`/`Update`/`Delete` already collapse theirs). No retention-window enforcement — see "Soft deletion" below |
| `func (r *Repository[T]) HardDelete(ctx context.Context, id string) error` | Physically removes the row with the given `id`, scoped to the ctx tenant — an irreversible DELETE, never a mark-delete, for a `SoftDeletable` `T` included (a soft-deleted row is as removable as a live one; see "Soft deletion" and "Hard deletion" below). System-context-gated: refuses with `ErrHardDeleteRequiresSystemContext` before the database is touched when `ctx` carries no system context. Even with the gate passed, the tenant stays mandatory and binding — no tenant → `pkgcore.ErrNoTenant` unmodified, and the delete never widens beyond the ctx tenant's rows. `ErrRecordNotFound` when nothing matches, including under another tenant. No migration or DDL involved |
| `func (r *Repository[T]) List(ctx context.Context) ([]T, error)` | Every row belonging to `ctx`'s tenant. No filter or pagination parameters — see Known limitations |
| `var ErrRecordNotFound = apperr.NotFound("dbkit.record_not_found")` | |
| `func IsRecordNotFound(err error) bool` | Reports whether `err` is, or wraps, `ErrRecordNotFound` — matched by code through `apperr.HasCode`, since the sentinel a Repository method returns is always the decorated (WithParam) instance. `gorm.ErrRecordNotFound` is not matched: the Repository layer is what translates it |
| `var ErrMissingID = apperr.Invalid("dbkit.missing_id")` | |

### Soft deletion — `soft_delete.go`

| Signature | Purpose |
|---|---|
| `type SoftDeletable interface { GetDeletedAt() *time.Time }` | Marker interface opting a model into `Repository[T]`'s mark-delete capability, mirroring `TenantScoped`'s exact idiom. `GetDeletedAt` is never actually called by the plugin or by `Repository[T]` — it is a pure marker; the field *writes* (`DeletedAt`, `DeletedBy`) go through reflection on fixed field names, exactly like `setTenantID`. A model implementing it must carry exported `DeletedAt *time.Time` and `DeletedBy string` fields by those exact names — same run-time-checked convention as `Repository[T]`'s own `ID`/`TenantID` requirement |
| `var ErrNotSoftDeletable = apperr.Invalid("dbkit.not_soft_deletable")` | Returned by `Restore` when `T` does not implement `SoftDeletable` |
| The unexported `softDeleteScopePlugin`, installed automatically by `Open` on every connection it returns, alongside `tenantScopePlugin` | For any model implementing `SoftDeletable`, auto-appends `deleted_at IS NULL` ahead of every read, on both read processors — `Before("gorm:query")` for the Find/First/Take/Last/Count/Pluck family and `Before("gorm:row")` for the Scan/Row/Rows family, the row registration matching `tenantScopePlugin`'s own row-path registration — deliberately narrower than `tenantScopePlugin`, which also covers create/update/delete. `db.Unscoped()` (GORM's own general bypass) skips the filter entirely, for an admin-style "see soft-deleted rows" read path. A model implementing neither `TenantScoped` nor `SoftDeletable` is untouched by either plugin |

**What "soft delete" means here, precisely.** `Repository[T].Delete` branches on `T`'s own capability, splitting the delete semantics into mark-delete/recoverable and hard-delete/compliance-erasure. A `T` implementing `SoftDeletable` gets one `UPDATE ... SET deleted_at = ?, deleted_by = ?` — the row stays in the table, hidden from ordinary reads only by `softDeleteScopePlugin`'s read-time filter. Every other `T` keeps the real, physical `DELETE`, byte for byte — this is an **additive, per-model opt-in capability**, never a new implicit default, and never a breaking change to `Delete`'s existing signature or meaning for a non-`SoftDeletable` model. `Restore` is the mark-delete's inverse, clearing both columns.

`softDelete`/`Restore` write through `tx.Where(...).Select(deletedAtFieldName, deletedByFieldName).Updates(&m)` with a real, freshly built `*T` — never `tx.Model(&zero).Updates(map[string]any{...})`. This is load-bearing: whenever a write's `Model` and `Dest` differ, gorm's `SetupUpdateReflectValue` (`gorm.io/gorm/callbacks/update.go`) can leave `Statement.ReflectValue` resolved to the wrong value depending on the payload shape, and `audit_capture.go`'s `fieldValuesMap` reads exactly that `ReflectValue` to populate `WriteCapturedEvent.After` — keeping `Model == Dest == &m` removes the ambiguity outright rather than relying on the map-conversion path's field-by-field write-back behavior. `TestAuditCapturePlugin_SoftDelete_ClassifiesAsUpdateWithRealDiff` (`audit_capture_test.go`) is the regression test: it asserts a real, non-nil, matching `After["deleted_at"]`, not merely `Operation == "update"`, which a subtler version of this hazard could satisfy while still lying about the diff. A second, related hazard the same test pins together with `TestAuditCapturePlugin_Restore_CapturesOnlyTheColumnsItWrites`: a column-restricted `Select` write's payload carries zero values for every column it does not touch, so capturing the payload whole would fabricate `After` values (`id: ""`, `name: ""` — the real row still holds its values) for columns the UPDATE never wrote. `audit_capture.go` therefore scopes `After` down to the columns the statement actually assigned (`scopeAfterToWrittenColumns`, driven by the statement's own `Select`/`Omit` lists — GORM deletes the SET clause before after-callbacks run, so it cannot be read back), and these tests assert `After` is exactly `{deleted_at, deleted_by}` and cross-check both captured values against the real row.

`softDelete`'s own `WHERE` includes `deleted_at IS NULL`; `Restore`'s includes `deleted_at IS NOT NULL` (plus a defensive, currently-redundant `.Unscoped()` in case the read-only auto-scope is ever broadened to updates). A double-`Delete` therefore returns `ErrRecordNotFound` rather than clobbering the first delete's own `deleted_at`/`deleted_by` attribution with a second, later write — see `TestRepository_Delete_SoftDeletable_AlreadyDeleted_ReturnsNotFound` (`repository_test.go`).

**Not a security boundary, not compliance-grade deletion.** A soft-deleted row is a real row, still plaintext-present in the database (encrypted fields excepted) — hidden from ordinary application reads by a Go-side GORM scope only. SQLite (the standalone deployment mode's dialect) has no RLS at all, so on that dialect hiding is *entirely* a Go-layer property with nothing underneath it. Do not let any caller-facing text, or any future documentation, imply that soft-deleting a row satisfies a "right to be forgotten" request, a retention-policy deletion, or any other compliance obligation that demands the data actually be gone. The deliberately separate **`HardDelete`** (irreversible, system-context-gated physical erasure) is what compliance-grade deletion requires — implemented in this package as `Repository[T].HardDelete` (`hard_delete.go`), behind a system-context gate whose presence-only semantics, refusal ordering and caller-side obligations are spelled out in the "Hard deletion" section below. The *orchestration* around it — retention-window configuration, the cleanup schedule, right-to-erasure intake — is not this package's to build: `go/compliance`'s `RetentionService` sweep and `ErasureService` erasure run it, driving registered participants' `HardDelete`-backed callbacks (the reference app's notes module is the first real participant).

**RLS needs no special handling for a soft-deleted row, and this is proven, not assumed.** `integration_test/postgres_soft_delete_rls_test.go` runs a real restricted role and RLS policy — the identical shape `postgres_repository_rls_test.go` uses for `Widget` — against `testutil.SoftDeletableWidget`, confirming a soft-deleted row is tenant-filtered by RLS exactly like a live one: reachable at the raw-SQL layer by its owning tenant, denied to every other tenant, with `deleted_at` playing no role in the policy at all.

**The unique-index interaction is a per-model decision — this package does not force one answer.** A soft-deleted row still occupies whatever unique constraint it had while live (`go/org`'s `UNIQUE(tenant_id, parent_id, name)` is the repository's own named example). `testutil.SoftDeletableWidgetTableSQL` adopts a **partial unique index** — `CREATE UNIQUE INDEX ... ON <table> (tenant_id, <col>) WHERE deleted_at IS NULL` — as the answer for that fixture: standard SQL, not PostgreSQL-specific, proven dual-dialect-safe by running the identical DDL string against both SQLite (`soft_delete_test.go`) and real PostgreSQL (the RLS integration test above). It lets a name be reused immediately after its holder is soft-deleted, while a duplicate *live* name is still rejected, and the index stays correctly tenant-scoped via its leftmost column. A model that instead wants "no reuse until the row is actually cleaned up" keeps its ordinary, non-partial unique index — also legitimate; this package takes no position on which a given model should pick, only that the choice must be made explicitly, not silently skipped.

**Retention windows are not enforced.** `Restore` succeeds unconditionally for any currently-soft-deleted row under the caller's tenant, with no deadline: retention-window *configuration* does not exist anywhere, so no check could consult one. Do not assume `Restore` enforces a window; a caller that needs one must build the check itself.

**`Update` respects `deleted_at`.** `Repository[T].Update`'s full-record `Select("*")` save writes every column, `deleted_at`/`deleted_by` included, and the soft-delete auto-scope is read-side-only (it registers on the query and row processors, never on update or delete — see the plugin table above), so nothing but the method itself stops a stale in-memory `*T` — a copy captured *before* someone else's `Delete` — from writing its zero `DeletedAt`/`DeletedBy` back over the row and silently "undeleting" it. The guard is not a plugin-side broadening but `Update`'s own WHERE: for a `SoftDeletable` `T`, the write's WHERE chain carries `deleted_at IS NULL`, the same explicit-condition convention `softDelete` and `Restore` follow. A stale pre-delete `*T`'s save therefore matches no row — `RowsAffected == 0` collapses to `ErrRecordNotFound` exactly as a hard-deleted or cross-tenant row does, and the mark (and every other column) stays untouched — while a live row's save matches as before, since its `deleted_at` is already NULL. The guard lives in `Repository[T]` rather than in the plugin because Repository is the design's independently-complete second layer — its unit tests run against a plugin-less connection on purpose — and because a WHERE condition on the statement itself is atomic with the id/tenant scope, leaving no check-then-write race window for a `Delete` landing mid-call. `TestRepository_Update_StaleModelAfterSoftDelete_ReturnsNotFoundAndKeepsMark` (`repository_test.go`) pins the refusal, and `TestRepository_Update_SoftDeletable_LiveRowStillUpdates` pins the guard's scope so it cannot drift into refusing live-row saves.

### Hard deletion — `hard_delete.go`

`Repository[T].HardDelete(ctx, id)` is the restricted, irreversible half of the delete semantics — the compliance-erasure counterpart to the mark-delete. It physically removes the row with the given id: a real `DELETE`, never a mark-delete, and for a `SoftDeletable` `T` a soft-deleted row is just as removable as a live one — `softDeleteScopePlugin` registers on the read processors only, never on delete, so nothing turns the DELETE into a no-op, and `HardDelete` never consults `SoftDeletable` at all. A `T` that never implemented `SoftDeletable` (whose ordinary `Delete` is physical) gets exactly the semantics `Delete` has, behind the gate. Body-wise, `HardDelete` is deliberately byte-identical to `Delete`'s physical branch after the gate — same tenant resolution, same `WithTenantSession` transaction, same `ErrRecordNotFound` on zero rows affected — per the per-file duplication convention `hard_delete.go`'s own doc comment records. No migration is involved: it issues the physical `DELETE` the schema always permitted.

**The gate, and what it is not.** A physical DELETE is irreversible, so `HardDelete` refuses to run on an ordinary tenant-scoped context: `ErrHardDeleteRequiresSystemContext` (`dbkit.hard_delete_requires_system_context`, an `apperr.Invalid` in the same mechanism-level caller-error family as `ErrNotSoftDeletable` — deliberately not a `Forbidden`, because dbkit does no authorization) when `ctx` carries no system context. The check is of *presence* only: `HardDelete` reads `pkgcore.SystemReasonFromContext` once and never asks who holds the grant. Who may hold a system context at all is a caller-side whitelist (admin, compliance, jobs, authn — enforced by code review and by the doc comments on the `WithSystemContext` functions, not by this package), and production grants should enter through tenancy's audited `WithSystemContext` wrapper so the grant itself is recorded; dbkit cannot import tenancy (the dependency graph runs `pkgcore -> dbkit -> tenancy`), which is exactly why the raw `pkgcore` primitive is what `hard_delete.go` consults.

The two failures around the gate are ordered deliberately and both fire before the database is touched: no system context → `ErrHardDeleteRequiresSystemContext` even on a bare context (the gate runs ahead of the tenant check); system context but no tenant → `pkgcore.ErrNoTenant` unmodified — a system context never substitutes for a tenant. And even with the gate passed, the tenant in `ctx` stays mandatory and binding: the DELETE runs with the ctx tenant both in its WHERE clause and in `WithTenantSession`'s session, so `HardDelete` is not the cross-tenant escape hatch and never deletes across tenants, system context or not. The unit suite pins every one of these properties in `hard_delete_test.go` — the plain-tenant refusal, the bare-context refusal ordering, the fail-closed no-tenant case, physical removal of both never-deleted and soft-deleted rows, the cross-tenant non-eraser property (`TestRepository_HardDelete_CrossTenant_SystemContextDoesNotEscapeTenantScope`), and the non-`SoftDeletable` case matching `Delete`'s semantics — and `integration_test/postgres_hard_delete_rls_test.go` re-proves the cross-tenant property against a real restricted role and RLS policy.

**Audit.** Under `Options.AuditBus`'s write-capture plugin, the physical DELETE is captured automatically as Operation "delete" with `After` nil — the row is gone, so there is no after-image to record — exactly like `Delete`'s physical branch, and pinned by `TestAuditCapturePlugin_HardDelete_ClassifiesAsDelete` (`audit_capture_test.go`), which also asserts the *absence* of a duplicate: a successful `HardDelete` publishes exactly one event, so a caller must never hand-emit its own Delete event on top of the automatic capture.

Attribution is the caller's, never the gate's: the capture reads `pkgcore.ActorFromContext` from the write's context, and a system context does not supply an actor — `pkgcore.WithSystemContext` stores only the `SystemReason` (whose `Actor` is a bare string naming who the grant was for, never promoted into the structured `Actor` carrier), and tenancy's audited wrapper returns exactly that context. A hard-delete caller must therefore layer `pkgcore.WithActor` — plus `pkgcore.WithOnBehalfOf` when the erase happens under impersonation, the dual-identity rule — *before* entering system context, or the erasure record (the one audit record whose subject row is about to cease to exist) is attributed to the zero `Actor`. `TestAuditCapturePlugin_HardDelete_SystemContextAlone_DoesNotAttribute` (`audit_capture_test.go`) pins the mechanism behind this warning: with the gate satisfied but no actor on the context, the captured event's `Actor` is the zero `pkgcore.Actor`. `hard_delete.go`'s doc comment carries the same obligation; the reference app's notes consumer (`TestRepository_HardDelete_SoftDeletedNote_PhysicallyRemoved`) demonstrates the compliant shape, layering `pkgcore.WithActor` on the tenant context before it is elevated.

**Callers.** `HardDelete`'s two intended callers — retention-expiry cleanup and compliance right-to-erasure — are both real: `go/compliance`'s `RetentionService.SweepTenant` and `ErasureService.Erase` orchestrate them through registered participants whose callbacks end in `Repository[T].HardDelete`, the reference app's notes module registers the first participant (`examples/reference-app/internal/notes/retention_participant.go`), and `flowtests/compliance_flow_test.go` drives sweep, erasure and export through the real composed stack. The method also stays available to any host that needs a row actually gone behind the gate without an orchestrator. The reference app's notes module is the mandatory first consumer: `examples/reference-app/internal/notes/repository_test.go`'s `TestRepository_HardDelete_SoftDeletedNote_PhysicallyRemoved` drives the promoted `dbkit.Repository[Note].HardDelete` through notes' real, migrated repository (create → mark-delete → enter a system context over the tenant context → `HardDelete` → raw `COUNT` reads 0 → a second `HardDelete` reports `ErrRecordNotFound`), and `TestRepository_HardDelete_PlainTenantContext_Refused` proves the gate refuses on an ordinary tenant context with the row untouched. `ExampleRepository_HardDelete` in `example_test.go` is the compiled, CI-run documentation of the same call sequence. The fragment has since grown that surface — `notes_deleteNote` and `notes_restoreNote` under `/api/v1/notes` — proven end to end by `flowtests/notes_delete_restore_flow_test.go`'s `TestNotesDeleteRestore_HTTPLifecycle` through the reference app's real composed stack (a deleted note disappears from the list, a restored one returns with its text intact, and the refusal legs — a second delete, a restore of a live note, an unknown id, another tenant's id — all answer the same `notes.note_not_found` 404); the two repository-level tests above remain the HardDelete-specific proof, the physical delete and its system-context gate pinned exactly where this paragraph describes them.

### Blind indexes — `blind_index.go`

The companion mechanism for a queryable encrypted field: when a column's values are encrypted at rest (above), the only way to find a row by that value without decrypting the whole table is a deterministic, keyed index of it stored in a separate plain column — `HMAC(secret, normalize(plaintext))`. Equality-only by construction: a deterministic index supports exact matches and nothing else (no prefix, partial, or fuzzy search — building that would leak the structure the encryption exists to hide), and key rotation has no retired-key fallback because a column holds one index per row (unlike `Decrypt`'s chain); both limits are deliberate.

| Signature | Purpose |
|---|---|
| `func BlindIndex(key []byte, normalized string) string` | The raw primitive: deterministic HMAC-SHA256 of `normalized` under `key`, hex-encoded. `normalized` must already be in the column's canonical form — `BlindIndex` performs no normalization of its own, on purpose. Prefer a `BlindIndexer` (below), which bundles normalization, key, and column so the two sides of a lookup cannot drift apart |
| `type NormalizeFunc func(raw string) (string, error)` | A column's canonical form: caller input in, the exact string the index is computed over out, or an error when the input has no canonical form. Must be deterministic and idempotent; erroring — never best-effort "fixing up" — is what keeps a bad value from silently indexing into a value no lookup will ever match. The two built-ins implement the canonical forms the design promises; a different form supplies its own function and documents it next to the model's column declaration |
| `func NormalizeEmail(raw string) (string, error)` | Trims surrounding whitespace and lowercases (`" User@Example.COM "` → `"user@example.com"`). Also refuses input that is not even the shape of a mailbox, in the same written-out syntactic style as `NormalizePhoneE164`: no `@`, an empty local part or domain, a second `@`, a domain with no `.` (or one starting or ending with `.`), whitespace/control or non-ASCII characters anywhere, or more than 254 characters (the RFC 5321 forward-path limit). Whether the mailbox genuinely exists is the caller's input-quality problem. Errors on empty or whitespace-only input too: an absent value has no canonical form and must not be indexed — leave the index column NULL |
| `func NormalizePhoneE164(raw string) (string, error)` | Drops the separators space, `-`, `(`, `)`, `.` (`"+1 555-0100"` → `"+15550100"`). Requires a leading `+` and at most 15 digits — E.164's limit — and errors on a bare national number (no default country is ever assumed), extensions, letters, or anything else that cannot be canonicalized |
| `type BlindIndexer struct { ... }` | The per-column contract: one SQL column, its HMAC key, and its `NormalizeFunc` bound together, so write and query sides of a lookup cannot drift apart by accident. No key accessor (mirrors `Cipher`); zero value not usable; safe for concurrent use. Tenancy is deliberately outside it: the column sits in the same (shared) table as the encrypted field and the surrounding data-access layer's tenant scoping applies to queries on it exactly as to any other column |
| `func NewBlindIndexer(column string, key []byte, normalize NormalizeFunc) (*BlindIndexer, error)` | `column` is the index column's exact SQL name (the model field's `column:` tag); `key` must be exactly 32 bytes — `ErrInvalidKeySize`, the sentinel `NewCipher` shares, so both secrets keep one key shape in the secret manager — and is copied at construction. Empty `column` or nil `normalize` is an error. Construct at bootstrap, next to `RegisterEncryptedSerializer`, where secrets are injected |
| `func (b *BlindIndexer) Index(raw string) (string, error)` | The write side: normalizes `raw` under the column's normalizer and returns the 64-hex value to store in the index column — computed over the same plaintext the serializer encrypts, never over ciphertext. Errors on input with no canonical form; it never yields an empty or best-effort index, so an index column holding `""` is always a write-path bug |
| `func (b *BlindIndexer) Equal(raw string) (clause.Eq, error)` | The query side: normalizes `raw` exactly as `Index` did and returns the column's equality condition, composable straight into `db.Where(...)`. Takes raw input, never a precomputed index value, so a filter under different normalization is impossible except through a second, deliberately constructed `BlindIndexer` on the same column (visible in bootstrap code, not an accident of a call site). The returned clause carries no tenant filter — whatever `WHERE tenant_id = ?` the plugin or `Repository[T]` appends applies as usual |

The model declares the index column explicitly, as an ordinary — never a serializer — indexed column next to the encrypted field (a serializer on it would re-encrypt the index; a blind index column holds plain 64-hex text, and the schema must stay visible to the gorm structs versioned migrations are generated from):

```go
type Account struct {
	Email      string `gorm:"serializer:email_enc"`             // encrypted at rest
	EmailIndex string `gorm:"column:email_index;size:64;index"` // blind index
}
```

Both sides of the lookup funnel through the same `BlindIndexer`, constructed at bootstrap where the secrets are injected — write side via `Index` (store its result in `EmailIndex` when creating or updating, alongside the plaintext being encrypted), query side via `Equal`:

```go
emailIndex, err := dbkit.NewBlindIndexer("email_index", blindKey, dbkit.NormalizeEmail)
if err != nil {
	return err // key misconfiguration: fail the bootstrap, never start with a mechanism that would silently write unusable indexes
}

indexValue, err := emailIndex.Index(form.Email) // normalize, then HMAC — the same value the serializer encrypts
account := Account{Email: form.Email, EmailIndex: indexValue}

cond, err := emailIndex.Equal(form.Email) // normalize identically at query time
var got Account
if err := db.Where(cond).First(&got).Error; err != nil {
	// handle err
}
```

### Key derivation — `key_derivation.go`, `bootstrap_key_derivation.go`

`NewCipher` and `NewBlindIndexer` each need their own 32-byte secret, and the two must never be the same bytes (above) — which, followed literally across every encrypted field and every blind-indexed column a real deployment ends up with, means managing one independent secret per column. `DeriveKey` is the alternative: one high-entropy 32-byte root secret, held once, from which every purpose-specific key a host needs is derived deterministically via HKDF (RFC 5869) with SHA-256 — the full Extract-then-Expand pipeline, with no independent salt (an absent salt is standard-conformant, not a shortcut: RFC 5869 §2.2 replaces it with `HashLen` zero octets — 32 for SHA-256 — and `rootKey` itself already supplies all the entropy the construction needs).

| Signature | Purpose |
|---|---|
| `func DeriveKey(rootKey []byte, purpose string) ([]byte, error)` | Derives one 32-byte key from `rootKey` and `purpose`. `rootKey` must be exactly 32 bytes — `ErrInvalidKeySize`, the identical sentinel `NewCipher`/`NewBlindIndexer` return, kept as one error identity across the package. `purpose` is HKDF's info string and must be non-empty; deterministic given the same `(rootKey, purpose)` pair, so a caller uses distinct, stable, versioned purpose strings (`"speed.dbkit.config.cipher.v1"`, never a bare `"config.cipher"`) — the version suffix exists so a deliberate "derive this differently now" bumps the suffix rather than editing the string in place, which would silently re-derive a different key for whatever it named |
| `func DeriveBootstrapKey(rootKey []byte, keyPath string) ([]byte, error)` | The composition of the two platform contracts, for a declared bootstrap key's material: `pkgcore.BootstrapKeyPurpose(keyPath)` fixes the path's purpose string, and `DeriveKey(rootKey, purpose)` derives under it. Same 32-byte output and same determinism as its two halves; a malformed path keeps `pkgcore.ErrInvalidBootstrapKeyPath` and a wrong-size root key keeps `ErrInvalidKeySize`, each wrapped with the context that names the failed derivation. Its function type fits `go/pkgcore/config`'s `WithKeyDerivation` directly — `WithKeyDerivation(dbkit.DeriveBootstrapKey)` is the whole wiring for a loader whose derive-tagged fields hold declared bootstrap key material — and, because the purpose embeds the declared path verbatim, renaming a declared key path is a rotation of that key's material (see the seat's contract) |

**Why deriving does not violate the never-reuse-key-material rule above.** That rule (`NewCipher`'s and `BlindIndex`'s own doc comments) is about reusing the *same key bytes* across two differently-designed constructions — an AES-GCM cipher and an HMAC index were never designed to share key material. It says nothing about where a key's bytes originally came from. Two keys `DeriveKey` produces under two distinct purpose strings are, for every practical cryptographic purpose, independent secrets: HKDF's output for one info string is computationally indistinguishable from random and reveals nothing about its output for a different info string, even to an attacker holding one derived key but not the root. Deriving a cipher key and a blind-index key from one `rootKey` under two distinct purposes satisfies the never-reuse rule exactly as well as generating and storing the two independently at random — it is how the rule is upheld with fewer secrets to manage, not an exception carved into it.

**The real trade-off, stated plainly, not buried.** Deriving from one root is a deliberate trade against holding every key fully independently, and both costs are real: a leaked root key compromises every key ever derived from it at once (a strictly larger blast radius than independent secrets, where compromising one secret compromises only what it alone protects), and rotating the root key rotates every derived key simultaneously (a coarser rotation granularity than rotating one secret independently of the others). A deployment that needs fine-grained, independent rotation for one specific purpose keeps supplying that one key directly instead of deriving it — see the policy line below for the two supported arrangements. For the key materials modules declare on the registry's bootstrap seat, the purpose convention lives at the seat itself (`pkgcore.BootstrapKeyPurpose` maps a declared key path to its stable, versioned purpose string, with the stability contract that makes renaming a declared path a rotation), and the material is derived by this primitive: `DeriveKey(rootKey, purpose)`, or the pair in one call, `DeriveBootstrapKey(rootKey, keyPath)`, which is what a host wires into `go/pkgcore/config`'s `WithKeyDerivation`. The precedence between a derived material and an explicitly configured one — the supported shape being "explicit beats derived" — is applied by the loader a host drives (its derive-tagged fields resolve explicit > derived > struct default), or host-side where a host composes the two calls itself.

**Policy.** Two supported arrangements: derive every purpose-specific key from one root secret via `DeriveKey`, OR supply each key independently for fine-grained rotation. Both are supported, and derivation does not weaken the never-reuse-key-material rule — it is how that rule is satisfied with fewer secrets to manage. Nothing about `NewCipher`'s or `NewBlindIndexer`'s own key-separation requirement changes — two different purposes still need two different key *values* — `DeriveKey` only changes where those distinct values are allowed to come from.

**No transactional batch-write boundary on `Repository[T]`.** A generic batch primitive was considered for `go/org`'s `Move` non-atomicity and deliberately not built: `WithTenantSession` — already exported, already the mechanism every `Repository[T]` method itself routes through — is sufficient. `go/org` composes its own multi-statement atomic operations directly against the `*gorm.DB` it hands `fn`, using the `tx.Where(...).Select(...).Updates(&m)` idiom its own tree code established, rather than needing a new generic batch primitive from this package. `Repository[T]`'s own promoted methods (`Create`/`Update`/`Delete`/`Restore`, each its own transaction) remain the right choice for a single-statement operation; a caller needing several statements to commit or fail together reaches for `WithTenantSession` directly, exactly as `go/org`'s `tree.go`, `membership.go` and `invite.go` do.

`ResourceID` is best-effort: extracted from the model's own field values when present (`Create`, `Update`), else from a literal `"id = ?"` WHERE condition — the exact shape `dbkit.Repository[T]`'s own `Update`/`Delete`/`FindByID` always build (`Delete`, where the destination carries no field values at all).

**Capture redaction — two classes, one marker convention.** Every value the plugin puts into a `WriteCapturedEvent`'s `Before`/`After` maps ends up written verbatim into the audit trail's `changes` column (via `audit.Module`'s `changesJSON`), which has no redaction of its own and no delete path — so what the plugin redacts at capture time is the trail's only redaction. It redacts two classes of field, both to the same `"[redacted]"` marker, keyed by the column's own name (a reader sees that the write touched the column, never its value):

1. **Serializer fields, automatically.** Any field with a GORM serializer (`gorm:"serializer:<name>"`, dbkit's encrypted-field mechanism included) is captured as the marker — `field.ValueOf` on such a field returns GORM's unmarshalable internal wrapper (a json-marshal cycle), and even unwrapped its value would be the plaintext the serializer exists to keep off disk. `TestAuditCapturePlugin_SerializerField_RedactsRatherThanCrashOrLeak` pins it.
2. **Plaintext columns, by model-side declaration.** A field carrying the capture opt-out tag (`audit:"redact"`, a separate struct-tag key — never an option smuggled into the `gorm:"..."` tag, which GORM parses and this plugin must not stake a meaning on) is captured as the same marker. This is the half no automatic criterion can see: a serializer is the only signal that distinguishes an encrypted/derived column from an ordinary one, so a genuinely sensitive value in an ordinary plaintext column (an email or phone the module chose to store in plaintext) would otherwise leak verbatim the moment its model opted into capture. The marker is read off `schema.Field.Tag` (GORM populates it with the field's complete struct tag), is checked by exact key/value so another tool's unrelated "audit" tag is inert, and is opt-in per field — an unmarked column is captured exactly as before. `TestAuditCapturePlugin_PlaintextMarkedColumn_Redacts` pins it, with an unmarked control column alongside. The same declaration also covers a column that is **not** sensitive in itself but holds a **stable linkable identifier** of a sensitive value — an HMAC blind index of a low-entropy address is the canonical shape: the digest is not the address, but the same address always yields the same digest under the same key (across rows, tenants, time and systems), so a digest recorded in the append-only, wide-audience trail is a correlation handle, and any oracle or key leak makes it equivalent to the address. go/org's `Invitation.EmailIndex` is the first production use of the marker for that kind (`audit:"redact"` in invitation.go; its own doc comment carries the full argument).

**Publish timing — only after the write it describes has genuinely committed, never before.** For a write inside `WithTenantSession`'s transaction (every `Repository[T]` write, and the raw-SQL escape hatch that calls `WithTenantSession` directly), the event is buffered on a per-transaction accumulator carried on the write's own `context.Context` rather than published from inside the GORM callback chain — `WithTenantSession` itself drains and publishes that buffer, and only after its own `db.Transaction` call has returned nil, i.e. only once the surrounding transaction has genuinely committed. This matters because GORM's own per-statement transaction machinery is a no-op for a write already running inside an open transaction: nothing in a single statement's own callback chain can tell whether the transaction *around* it will ultimately commit. For a bare `Create`/`Update`/`Delete` against `Open`'s plain `*gorm.DB` (no real production caller — every `Auditable` model in this codebase besides this package's own test fixtures, `examples/reference-app/internal/notes.Note`, is written exclusively through `Repository[T]`), the event is published by a callback registered `After("gorm:commit_or_rollback_transaction")`, once that Process's own real commit-or-rollback step has resolved. Neither path ever publishes for a write that ultimately rolled back — `audit_capture_test.go`'s `TestAuditCapturePlugin_WithTenantSession_RollbackAfterCapture_PublishesNothing` pins this against a real rollback.

A publish failure can no longer roll anything back — by the time either path calls `Publish`, the write has already durably committed — so it is reported as a structured `log/slog` alert (`auditPublishFailed`; dbkit cannot depend on `go/observability` — see "One dependency, and why there is only one" — so this cannot go through `obs.FromContext` the way every downstream module's own logging does) rather than injected back into the GORM callback chain with `db.AddError`. `TestAuditCapturePlugin_WithTenantSession_PublishFailure_CommitsAndAlerts` pins this: the business write commits and is durably readable on a fresh connection, while the alert fires. This is the plugin's whole half of the never-drop rule: alert-and-continue is all its post-commit position allows, and `audit.Emit`'s own doc comment states the division of fulfilment between the two mechanisms rather than claiming a shared "loud-failure contract" they do not share.

**Residual crash window, shared by both mechanisms.** This publish-timing design closes the phantom-audit-event bug (never publish for a write that rolled back) at the cost of a smaller, accepted residue: a crash between the business transaction committing and the buffered events' own publishes (and the persister's inserts) landing leaves a committed business write with no audit row and no trace that one was owed. `audit.Emit` — whose every real caller invokes it after its own business write committed — sits in the identical window; the record in `audit/`'s own documentation covers both mechanisms: the window's shape, why making the two writes atomic was the route that produced the `SQLITE_BUSY` self-deadlock the section above documents, and how operations detect the residue (a business row existing without its audit row is queryable).

**Same-SQLite-file synchronous persister: not a self-deadlock for the `WithTenantSession`/`Repository[T]` shape.** Wiring `AuditBus` to the same SQLite file a synchronous, same-process persister (typically `audit.Module`, below) writes into was a hazard while the plugin published *during the audited write's own open transaction*: the persister's write on a second connection collided with an uncommitted write lock held by its own goroutine — an unrecoverable self-deadlock, not ordinary contention (the `busy_timeout` pragma cannot help a lock holder waiting on itself). The publish-timing design above removes that root cause for a `Repository[T]`-shaped write: `publishBuffered` runs only after `WithTenantSession`'s own transaction has committed and released its lock, so a persister's own write on a second connection to the same file meets no contention at all — proven closed with two real `*gorm.DB` connections to one real file in `audit_capture_test.go`'s `TestAuditCapturePlugin_WithTenantSession_SameFileSynchronousPersister_NoLongerDeadlocks`. The identical reasoning applies to a bare-write's own persister coupling and to PostgreSQL, though only the SQLite/`WithTenantSession` shape above has a live reproduction proving it. This does not make same-connection wiring a recommended pattern — a genuinely separate database/connection for the persister, or `audit.Emit` called explicitly after the triggering write returns (see `examples/reference-app/internal/notes/handler.go`'s `recordNoteCreatedAudit`), both remain the simpler and clearer choices — but it is no longer a live deadlock hazard for this shape.

## Dual-dialect constraints for models used with dbkit

Every model passed to `Repository[T]`, embedded under `TenantModel`, or otherwise written through a `*gorm.DB` obtained from `Open` is expected to run correctly against both PostgreSQL and SQLite. The dual-dialect constraints that follow are the ones every business model in this repository honours:

- Generate primary keys (ULID/UUID) in the application. Never `gen_random_uuid()` — SQLite has no equivalent.
- Store JSON with `datatypes.JSON`. Never filter on JSONB operators (`->`, `->>`, `@>`, …) — SQLite cannot execute them.
- No native PostgreSQL array columns. Use `datatypes.JSON` or a join table instead.
- Timestamps use the `autoCreateTime` / `autoUpdateTime` gorm tags. Never write `NOW()` into a query, a default, or a migration.
- Full-text search goes through a `SearchProvider` interface at the business-module layer (tsvector on PostgreSQL, `LIKE` fallback on SQLite) — dbkit itself provides no full-text search primitive.
- `tenant_id` is the leftmost column of every composite index, and a tenant-scoped table's primary key should be `(tenant_id, id)`. `TenantModel`'s own tag does not declare `primaryKey` and cannot safely be made to (see its doc comment) — when the composite key matters to you, skip embedding `TenantModel` and declare `TenantID` directly instead, with the tag you need (as `internal/testutil.Widget` does).
- dbkit adds one convention of its own on top of the standard's list: `T` must have exported `ID` and `TenantID` string fields by those exact Go names (declared directly, or promoted from an embedded `TenantModel`), because `Repository[T].Create`/`Update` read and write them through reflection — `TenantScoped` cannot express this in the type system, since it requires only the `GetTenantID()` accessor.
- Sensitive fields (national ID numbers, phone numbers, health-related free text, …) use `` gorm:"serializer:<name>" `` after `RegisterEncryptedSerializer(name, cipher)`, plus a separate, non-encrypted, indexed blind-index column (`` `gorm:"column:<field>_index;size:64;index"` ``, declared next to the encrypted field — never a serializer itself) whenever equality lookup is needed. Both sides of the lookup go through one `BlindIndexer` bound to that column — `Index(plaintext)` on write, `Equal(raw input)` on query — so the column's canonical form (E.164 for phone numbers, lowercase for emails) is applied identically every time; see the "Blind indexes" section above.

## SQLite busy timeout

**Every SQLite connection dbkit opens carries an explicit, bounded `busy_timeout`, applied per physical connection for the pool's lifetime.** The dialector factory this module registers for `dbkit.DialectSQLite` — in `dialect/sqlite`, the subpackage a consumer blank-imports for its init side effect — appends `_pragma=recursive_triggers(1)&_pragma=busy_timeout(5000)` to every DSN before handing it to the driver, and glebarez/go-sqlite (the pure-Go driver underneath `glebarez/sqlite`) re-applies every `_pragma` parameter on each new physical connection its `Open` creates. Folding the pragma into the DSN is what makes it reach every connection of the pool (`Open`'s `defaultMaxOpenConns`), rather than merely the one a post-`Open` `Exec` happened to set it on. The value `5000` ms matches the driver's own default, so the declaration changes no behavior; it turns a default that lives inside a dependency into a contract this package states, documents (`dialect_sqlite.go`'s `withDefaultPragmas`) and tests (`dialect/sqlite/dialect_sqlite_test.go`'s busy-timeout suite), so a future driver change cannot silently strip or alter it. It is appended last in the DSN, and the driver applies `_pragma` params in DSN order with the last application winning, so a caller-supplied `_pragma=busy_timeout(...)` in the DSN is deliberately overridden — one fixed default, in the same spirit as the connection-pool defaults `Open` applies (see the Connections rules), with no `Options` field to override it.

**The wait is bounded, and its expiry is a real error — never a silent retry, never an unbounded hang.** SQLite serializes writers on one database file, and a connection whose write meets another connection's uncommitted write normally loses immediately. This pragma installs SQLite's built-in busy handler instead: the losing connection waits up to the timeout, retrying in progressively longer sleeps, and its write succeeds the moment the holder commits or rolls back — ordinary contention converges. A write that still cannot proceed when the timeout expires fails with the real `SQLITE_BUSY` error (`database is locked`), which the caller — or its own retry layer, e.g. `go/jobs`' backoff — handles like any other error; nothing here retries silently, and nothing waits forever. `dialect_sqlite_test.go`'s busy-timeout suite pins both halves with two real connections to one real file: a contending writer waits out its holder's commit and then succeeds, and a hold that outlasts the timeout ends in the genuine busy error after roughly the full timeout — with the holder's release sequenced by the test itself, never by a sleep race. These tests pin the declared contract rather than a regression: each also passes on a connection carrying only the driver's implicit default, which is exactly the redundancy the declaration buys, and the parameter's own DSN merge (the string, and its append-after-caller order) is pinned string-level by `dialect_sqlite_test.go`'s `TestWithDefaultPragmas`.

**The boundary — a read-then-write upgrade does NOT wait, whatever the timeout says.** Waiting is only safe for a write that starts from no lock (an autocommit write, or a transaction's first write), because it holds nothing the holder needs. A write inside a transaction that has already read — holding the file's SHARED lock — and is upgrading to write is answered with an immediate `SQLITE_BUSY` whenever another connection holds the write lock, and the busy handler is never consulted: waiting could not resolve the cycle, since the holder cannot commit to EXCLUSIVE while this connection's SHARED lock stands, and this connection cannot upgrade to RESERVED while the holder's stands. No `busy_timeout` setting changes that immediate refusal; the caller's own retry layer is the only cure. That is the lock shape of `go/storage`'s derive gate (a read-then-write transaction), which is why that path records fast, retry-converged busy failures under contention rather than waits — and it is also why the AuditBus self-deadlock "Audit trail collection" documents above could never have been fixed by this pragma alone: a same-goroutine self-wait, whose holder can never commit while the subscriber it is itself waiting on stays blocked, only converts from an immediate failure into a bounded one, however long the timeout. The actual fix had to remove the self-wait itself — deferring the plugin's publish until after the write's own transaction commits, for the `WithTenantSession`/`Repository[T]` shape (see "Audit trail collection" above) — not lengthen how long a connection waits on itself.

**The pragma is a bounded wait, not serialization.** It absorbs transient write collisions between short transactions; it does not queue writers, guarantee fairness, or make a long read-then-write transaction safe against a competing writer (those fail fast, per the boundary above). A write-heavy path that contends routinely should shorten its transactions, and a read-then-write decision under contention should expect the immediate `SQLITE_BUSY` and retry — see `go/storage/derive.go`'s doc comment for the canonical treatment.

## Typical integration

Defining a tenant-scoped model and the repository a business module embeds it in:

```go
package billing

import (
	"context"

	"gorm.io/gorm"

	"github.com/vislake/speed/go/dbkit"
	"github.com/vislake/speed/go/pkgcore"
)

// Subscription is billing's tenant-scoped model. ID and TenantID are exactly
// the field names dbkit.Repository[T] requires (see repository.go), and
// tenant_id is the leftmost column of the composite primary key, with the
// tenant first in every composite index.
type Subscription struct {
	ID       string `gorm:"primaryKey;size:26"`
	TenantID string `gorm:"primaryKey;size:26;not null;index:idx_sub_tenant_created,priority:1"`
	PlanID   string `gorm:"size:64;not null"`
	Status   string `gorm:"size:32;not null"`
}

// GetTenantID satisfies dbkit.TenantScoped.
func (s Subscription) GetTenantID() pkgcore.TenantID { return pkgcore.TenantID(s.TenantID) }

// Repository is billing's data-access type. It embeds dbkit.Repository[T]
// instead of holding a raw *gorm.DB.
type Repository struct {
	*dbkit.Repository[Subscription]
}

func NewRepository(db *gorm.DB) *Repository {
	return &Repository{Repository: dbkit.NewRepository[Subscription](db)}
}

// Activate creates an active subscription under ctx's tenant.
func (r *Repository) Activate(ctx context.Context, id, planID string) (*Subscription, error) {
	sub := &Subscription{ID: id, PlanID: planID, Status: "active"}
	if err := r.Create(ctx, sub); err != nil {
		return nil, err
	}
	return sub, nil
}
```

Using it — a full create / read / update / delete sweep:

```go
db, err := dbkit.Open(ctx, dbkit.Options{Dialect: dbkit.DialectPostgres, DSN: dsn})
if err != nil {
	return err
}

repo := billing.NewRepository(db)

// A real request's ctx already carries the tenant, injected by
// tenancy.Middleware from the access token claims. Building it explicitly
// here is only for illustration.
ctx = pkgcore.WithTenant(ctx, "tenant-acme")

sub, err := repo.Activate(ctx, newULID(), "plan_pro") // however this module generates its ULIDs
if err != nil {
	return err
}

got, err := repo.FindByID(ctx, sub.ID) // promoted from the embedded *dbkit.Repository[Subscription]
if err != nil {
	return err
}

got.Status = "past_due"
if err := repo.Update(ctx, got); err != nil {
	return err
}

if err := repo.Delete(ctx, got.ID); err != nil {
	return err
}
```

This exact pattern — a tenant-scoped model, a repository embedding `dbkit.Repository[T]`, `dbkit.Open`, `Create` → `FindByID` — is compiled and run under CI as `Example()` in [`example_test.go`](example_test.go) (package `dbkit_test`, matching `pkgcore`'s own `example_test.go` convention), with an `// Output:` comment asserted against the real printed output, per the Documentation rule below. `repository_test.go`'s own `TestRepository_FullCRUDLifecycle_SingleTenant` covers the same call sequence in more depth — it also exercises `Update` and `Delete` — against `internal/testutil.Widget`.

## Known limitations

**`Repository[T]`'s generic constraint structurally excludes identity and platform data — this is intentional, not an oversight, but it is easy to miss.** Of the four data domains, only two (tenant data, link data) are *supposed* to implement `TenantScoped`; identity data (`users`, `sessions`) and platform data (platform-level plan definitions, global config) must **not** — that is exactly what `tenancytest.AssertNotTenantScoped` exists to assert (see below). Because `Repository[T TenantScoped]` requires the constraint, a model in either of those two domains cannot be used as `T` at all — the compiler rejects it, not a runtime check. This is correct, not a bug: `Repository[T]`'s entire value proposition (the fail-closed tenant check, the forced tenant_id on Create) is specific to tenant-owned data and doesn't make sense for a table with no tenant.

A module modeling identity or platform data uses the plain `*gorm.DB` returned by `Open()` directly, with no `Repository[T]`-style wrapper — and that is safe, not a hole: the isolation plugin already ignores any model that doesn't implement `TenantScoped` (`TestTenantScopePlugin_NonTenantScopedModel_Unaffected` proves this), so there is nothing for such a module to opt out of. Do not build an ad-hoc "safety wrapper" for this case without first checking whether `tenancytest.AssertNotTenantScoped` (`go/tenancy/tenancytest`) already covers what you're trying to guard against — inventing a second mechanism for the same guarantee is how these things drift apart. The identity and platform modules built since — `authn`'s tables and `go/config`'s platform rows among them — all use the plain `*gorm.DB` path directly, and no real need for a shared, non-tenant-scoped repository *pattern* has emerged from their query shapes; none exists, and a speculative generic type with no consumer would still be likely to guess the shape wrong.

**`tenancytest.AssertIsolated` / `AssertNotTenantScoped` live at `go/tenancy/tenancytest`**, built entirely on dbkit's exported material (`Open`, `Repository[T]`, `TenantScoped`) — see `go/tenancy/AGENTS.md` for their full behavior. Every module above `tenancy` in the dependency graph must run one of the two against its own `Repository[T]` usage. dbkit itself is the one exception: sitting below `tenancy`, it cannot import `tenancytest` without the import cycle described under "One dependency, and why there is only one" above, so dbkit's own isolation guarantee rests on its hand-written suite (`tenant_scope_test.go`, `repository_test.go`) rather than `tenancytest`.

**`Repository[T]`'s query surface is minimal on purpose.** `List` takes no filter or pagination parameters — it returns every row for the caller's tenant, full stop. There is no `FindWhere`, `Count`, ordering, or paging. Per `repository.go`'s own doc comment, this is deliberate minimalism, not an oversight. A module with real filtering/pagination needs has two options, in order of preference:
1. Build the query on the same `*gorm.DB` layer 1 already protects, anchored on the `TenantScoped` model itself — `db.Model(&TenantScoped{})` — so the plugin's `WHERE tenant_id = ?` applies as a backstop even though `Repository[T]`'s own re-verification does not run for that call. A model-anchored statement is covered on every read finisher: Find/First/Take/Last/Count/Pluck through the query processor, and Scan/Row/Rows through the row processor (registered like the query processor, so the standard projection/query shape `db.Model(&M{}).Scan(&dtos)` is covered too). On the Find family a destination whose element type is the `TenantScoped` model anchors the filter too; Scan/Row/Rows cannot — their destination is invisible until after the row processor has run — so those need the explicit `db.Model(...)`. A statement the plugin cannot identify as tenant-scoped at all — a bare `db.Table("widgets")` chain, and raw SQL — gets no backstop and belongs under option 2.
2. Use the raw-SQL escape hatch below, when even that is not enough — for example, a query shape the plugin cannot safely rewrite (see the `Or(...)` composition note in Rules).

**The layer-3 warning option 1 owes — and the general rule for every statement shape.** Option 1's protection is layers 1 and 2 only: the statement runs OUTSIDE `WithTenantSession`, so on PostgreSQL nothing sets the RLS session GUC (`app.current_tenant`) for it. On a layer-3-configured deployment — RLS policies whose `USING` clause keys on `current_setting('app.current_tenant', true)`, the exact shape this package's own PostgreSQL integration legs provision (postgres_repository_rls_test.go and its soft-delete and hard-delete siblings create the restricted role and the GUC-keyed policy themselves; production provisioning of RLS roles and policies remains deployment-side) — the option-1 statement is first tenant-filtered by layer 1's injected `WHERE tenant_id = ?`, then filtered to ZERO rows by layer 3: with the GUC unset `current_setting` returns NULL and the policy matches nothing, so the query answers no rows and no error — exactly the quiet "looks like it worked" shape `ErrMissingTenantContext`'s own doc comment (`tenant_scope.go`) says this package's checks exist to refuse. This is not a confidentiality problem and it must not be "fixed" by making layer 3 activate outside `WithTenantSession` — with the GUC unset the comparison matches nothing (fail closed); making RLS skip its policy when the GUC is unset would trade "unset ⇒ zero rows" for "unset ⇒ pass-through". The general sentence spans every statement shape, raw SQL included: **a statement running outside `WithTenantSession`, on a layer-3 deployment, needs either the GUC (a tenant-scoped statement — run it through `fn` in `WithTenantSession`, the pattern option 2 documents below) or a policy admission (a deliberately cross-tenant statement — `go/org/membership_tenants.go`'s `tenantsOfUser` is the positive precedent: a deliberate system-context cross-tenant statement whose own comment states the deployment-side role admission a production RLS deployment must grant it).** `Repository[T]`'s own methods never meet this gap — every one runs inside `WithTenantSession` and so sets the GUC — which is exactly why the gap is only ever reachable through the model-less and raw-SQL statement shapes this section's option 2 documents, never through `Repository[T]`. Doc discipline this guide now holds itself to: a RECOMMENDED option's warning must cover at least the layers the option this section treats as dangerous covers — mechanically checkable by comparing which of the three layers each option's warning names.

**Scan-shaped reads are plugin-covered; what stays unprotected is only the model-less statement.** GORM routes `Scan`/`Row`/`Rows` through its row processor — a separate callback chain from the query processor `Find`/`First`/`Take`/`Last`/`Count`/`Pluck` run through — and both plugins register their query-path handler before `"gorm:row"` as well, so a model-anchored scan is filtered and fails closed exactly like `Find`. Without that registration the standard projection/query shape `db.Model(&Widget{}).Scan(&dtos)` would read every tenant's rows with a nil error — and, with no tenant in the context, everything with a nil error too, with the soft-delete twin surfacing soft-deleted rows. The coverage is pinned by `TestTenantScopePlugin_RowPath_Scan_UnderTenant_OnlySeesOwnTenant`, `TestTenantScopePlugin_RowPath_Scan_NoTenantInContext_FailsClosed` and the soft-delete twin `TestSoftDeleteScopePlugin_RowPath_Scan_SkipsSoftDeletedRows` (with the raw truth-reader's continued bypass pinned by `TestTenantScopePlugin_RawSQLScan_StillBypasses`). Two residual read shapes stay unprotected, both because the statement carries no model the plugin can identify as tenant-scoped: raw-SQL statements (the escape hatch below, whatever finisher ends them) and a bare `db.Table("widgets")` chain finished with `Scan`/`Row`/`Rows` — unlike the `Find` family, whose destination can anchor the filter, the scan destination is invisible to the row processor until after the statement has run, so those chains need the explicit `db.Model(&Widget{})` anchor. One API-shape caveat on the protected side: gorm's single-row `Row()` finisher returns only a `*sql.Row` and discards statement errors, so its fail-closed form (no tenant in the context) is a nil row — never executed, so no leak — rather than a surfaced `ErrMissingTenantContext`, and `Scan` on that nil row panics inside `database/sql`; the sanctioned single-row shapes are `First`/`Take`/`Repository[T]`, which carry the same limit-1 semantics with a real error channel.

**The raw-SQL escape hatch, and how to use `WithTenantSession` from it safely.** A reporting or bulk-maintenance query that genuinely cannot go through `Repository[T]` belongs under the business module's own `internal/query/`, must pass the tenant explicitly, and must ship its own isolation test. Two things matter when you reach for it:
- **You are opting out of layers 1 and 2 for that one statement.** Raw SQL runs through the raw processor, which neither plugin registers a callback on — `db.Raw` / `db.Exec`, however the statement is finished (`db.Raw(...).Scan`, `.Row()`, `.Rows()`), carries no model for the plugin to identify as tenant-scoped, so it bypasses layers 1 and 2 completely — and hand-written SQL obviously never runs `Repository[T]`'s own checks either. (`db.Row` / `db.Rows` / `db.Scan` finished against a model-anchored statement are plugin-covered — `db.Model(&TenantScoped{}).Scan(&dtos)` is as protected as `Find` — and remain bypasses only in their raw or model-less forms.) Every tenant filter in that statement is now hand-written and your responsibility, exactly what every other rule in this document exists to make unnecessary elsewhere. Treat it as a reviewed exception, not a habit, and bind the tenant as a parameter, never build the `WHERE tenant_id = ?` clause with `fmt.Sprintf` or string concatenation.
- **Layer 3 is the intended backstop for exactly this case.** The whole point of isolation layer 3 (PostgreSQL RLS) is that it protects a statement even when layers 1 and 2 were both skipped — which raw SQL always does. The safe pattern is to run the raw statement through `fn` in `WithTenantSession(ctx, db, fn)`, using the `tx` it hands `fn` for the statement itself, so a mistake in the hand-written `WHERE` clause is still caught by the database's RLS policy instead of becoming a silent cross-tenant leak. See `tenant_session.go`'s doc comment and the "RLS session state" entry above for the full contract.

```go
// internal/query/overdue.go — tenant_id is still bound explicitly by hand
// (there is no Repository[T] method for this shape of aggregate query);
// wrapping the call in dbkit.WithTenantSession adds layer 3 as a backstop
// underneath it, so a mistake in this hand-written WHERE clause is still
// caught by the database's RLS policy in production. WithTenantSession
// works the same way on a *gorm.DB not obtained from Open, since it reads
// the dialect from db.Name() rather than any dbkit-specific field.
func OverdueSubscriptions(ctx context.Context, db *gorm.DB, tenant pkgcore.TenantID) ([]Row, error) {
	var rows []Row
	err := dbkit.WithTenantSession(ctx, db, func(tx *gorm.DB) error {
		return tx.Raw(
			`SELECT id, plan_id FROM subscriptions WHERE tenant_id = ? AND status = 'overdue'`,
			string(tenant),
		).Scan(&rows).Error
	})
	return rows, err
}
```

**A commit-time failure inside `WithTenantSession` now gets an explicit rollback attempt of its own — closed, with the cell's residual bounded and recorded.** The original gap, reproduced against a real in-memory SQLite database with a genuine deferred foreign-key violation (`PRAGMA defer_foreign_keys = ON`, real SQLite semantics): a constraint deferred to commit time makes `Commit()` itself fail, and Go's `database/sql` marks a `*sql.Tx` terminally "done" the instant `Commit()` is called, even when the driver reports the commit failed, so a rollback through the transaction handle is a same-call no-op (`sql.ErrTxDone`) that never reaches the driver — while the SQLite driver this package uses leaves the underlying connection holding the uncommitted transaction, so fn's writes stayed visible to any later statement the pool ran on that connection. `WithTenantSession` now owns its transaction lifecycle explicitly (Begin/fn/Commit, `tenant_session.go`) rather than delegating to GORM's `Transaction` wrapper, and when `Commit()` fails it issues its own rollback attempt — `rollbackAfterFailedCommit`, a raw `ROLLBACK` executed through the pool, the only channel that can reach the connection the driver left transacting. Its reach is bounded by the pool (the attempt clears the residue when the statement rides the tainted connection; a "no transaction is active" answer means there was nothing to clear, or the tainted connection was checked out first), so the caller-side obligation this entry's original text and `WithTenantSession`'s own doc comment record is narrowed, not eliminated: a caller that retries on a non-nil return must still be idempotent over its own residue or re-verify what the failed attempt left behind. The regression (`tenant_session_test.go`'s `TestWithTenantSession_SQLite_CommitTimeFailure_RollbackAttemptClearsTheResidue`) failed on the pre-fix delegation — the fn's write remained visible after the returned commit error — and passes after. The audit-capture mechanism's behavior in this cell is unchanged and correct on both sides of the fix: its buffer is only drained after a genuine commit, so a failed commit never publishes.

**`pkgcore.WithSystemContext` does not interact with tenant-scoped models at all.** Neither the plugin nor `Repository[T]` special-cases a system context. `WithSystemContext` and `WithTenant` are orthogonal (per `pkgcore/tenant.go`'s own doc comment: "a system context is orthogonal to a tenant context: it sets no tenant"), so a query against a `TenantScoped` model carrying only a `SystemReason` and no tenant fails closed exactly the same way a request with neither would. A system-context caller that needs a specific tenant's data still supplies it with `pkgcore.WithTenant`; a genuinely cross-tenant admin read (e.g. "search every tenant for X") has no path through dbkit today — it would need either per-tenant iteration through `Repository[T]` or a raw, admin-role-driven query outside it. `Repository[T].HardDelete` is the one deliberate exception to this paragraph's first sentence, and it proves the rule rather than breaking it: it consults `pkgcore.SystemReasonFromContext` exactly once, as a refusal gate that demands the grant's presence (see "Hard deletion" below) — never as an amplifier, never substituting for a tenant, and never widening the delete beyond the ctx tenant's rows. Every other `Repository[T]` method and the plugin itself still never consult it, so composing `WithSystemContext` with them stays inert.

**The blind index column is populated by the writer, explicitly — nothing in dbkit fills it for you.** GORM serializers are per-field and cannot write a second column, and the index cannot be derived from the encrypted field's tag, so a model's blind-index column starts NULL/empty on every insert unless the creating code computes `Index(plaintext)` and stores the result itself (see the "Blind indexes" section's example). Missing that step is invisible in the row's own ciphertext and surfaces only as an equality lookup that returns nothing. A full-population or backfill path is deliberately not built into dbkit — it belongs to each module's create/update code paths (where the plaintext already exists) — and bulk recomputation after a blind-index key rotation is a separate `jobs` batch task by design (see below), not something this package triggers.

**A blind-index key rotation has no retired-key fallback, and dbkit does not run the recompute for you.** `Cipher` keeps retired keys so old ciphertext keeps decrypting across a rotation; a blind-index column cannot — a single equality comparison matches exactly one index value per row, so once the column holds values under the old key, nothing matches under the new one. Rotating therefore means recomputing every row's index as a jobs batch task; no such task exists in this repository yet, and no dual-key machinery exists here to make an ordering seamless. The operator-facing ordering — whether the deployment tolerates a transient mismatch window between "column rewritten under the new key" and "lookups switched to the new key", or carries a second column through the migration — is that future task's design decision, not dbkit's.

**The mechanism is equality-only, and per-column normalization is a caller contract.** A deterministic HMAC index supports exact matches and nothing else: there is no prefix, partial, or fuzzy search over a blind-index column, by design (building one would leak exactly the structure the encryption hides), and no lower-precision variant of the built-in normalizers. The two canonical forms dbkit ships — E.164 phone numbers, lowercased emails — are the ones every encrypted-identifier column in this repository uses; a column whose data needs any other canonical form supplies its own `NormalizeFunc` and documents the form next to the model declaration, because the index is only as consistent as the normalization both sides of every lookup share.

## Rules

**Dependencies**
- Do not add a second speed-module dependency to this package. dbkit sits directly above `pkgcore`; `tenancy` sits above dbkit and will depend on it, so an import running the other way is a cycle, and `observability` is unreachable for the identical bottom-up reason (see "One dependency, and why there is only one" above).
- Do not add a third-party dependency casually. It lands in the `go.sum` of every module built on speed.

**Connections**
- Do not call `gorm.Open`, `postgres.Open`, or `sqlite.Open` directly anywhere in this codebase. `Open` is the only sanctioned entry point; no code path in dbkit ever returns a `*gorm.DB` before the tenant-scoping plugin is installed on it.
- Do not add fields to `Options` to override the connection-pool defaults. That is deliberate — every `*gorm.DB` in this codebase shares the same pool shape, so `open.go`'s constants are the one place to reconsider them.
- Do not put a `_pragma=busy_timeout(...)` in a SQLite DSN passed to `dbkit.Open` expecting it to take effect. The dialect factory appends its own busy_timeout after it, and the driver applies `_pragma` params in DSN order with the last application winning, so dbkit's fixed default always wins — see the "SQLite busy timeout" section. The same goes for `_pragma=recursive_triggers(...)`.
- Do not log `Options.DSN` or let it reach a returned error. `Open` never includes it in one, by design, because it often carries credentials.

**Tenancy**
- Do not hold a `*gorm.DB` in a business module and write queries against it. Embed `dbkit.Repository[T]`.
- Do not expect the tenant-scoping plugin to intercept raw SQL — `db.Raw` / `db.Exec`, however the statement is finished (a `db.Raw(...).Scan(...)` truth-reader runs verbatim; the raw processor carries no callback of either plugin) — or a read finished against a statement with no `TenantScoped` model on it for the plugin to scope, such as a bare `db.Table(...)` chain. It registers on the query, row, create, update and delete processors, so every read of a model-anchored statement — `db.Model(&TenantScoped{}).Find(...)` and the projection shape `db.Model(&TenantScoped{}).Scan(&dtos)` alike — is covered (see Known limitations).
- Do not assume the plugin fails to safely tenant-scope a caller-composed `.Or(...)` condition — it groups the caller's existing WHERE into one `AndConditions` block before appending its own filter, so `db.Where("name = ?", x).Or("name = ?", y)` still ends up as `(name = ? OR name = ?) AND tenant_id = ?` (see `groupExistingWhereConditions` in `tenant_scope.go`). But do treat this as evidence that hand-building multi-condition queries directly against a `*gorm.DB` from `Open` carries more responsibility than it looks; prefer `Repository[T]` wherever its surface suffices.
- Do not assume `pkgcore.WithSystemContext` grants a cross-tenant read against a `TenantScoped` model. It does not — see Known limitations. The single place `Repository[T]` consults `SystemReasonFromContext` at all (`HardDelete`'s gate) is presence-only and still tenant-bound.
- Do not construct or install the tenant-scoping plugin yourself; `tenantScopePlugin` is unexported on purpose, so no `*gorm.DB` in this codebase can exist "unprotected" by accident.
- Do not assume `TenantModel` alone gives you the standard's recommended `(tenant_id, id)` composite primary key — its tag does not include `primaryKey`. Do not "fix" that by embedding `TenantModel` and then redeclaring a same-named `TenantID` field on the embedding struct to shadow it: GORM ends up writing and scanning the shadowing field, but the promoted `GetTenantID` method still reads `TenantModel`'s own, never-populated copy — silently breaking `Repository[T].FindByID` for every tenant, including the row's real owner. Declare `TenantID` directly, with no `TenantModel` embedding at all, when the composite key matters (see `tenant_scope.go`'s `TenantModel` doc comment and `tenant_scope_tenantmodel_test.go`).

**`WithTenantSession`**
- Do not write a literal `SET LOCAL app.current_tenant = ?` (or `SET ... = $1`) against PostgreSQL, in `tenant_session.go` or anywhere else. PostgreSQL's `SET`/`SET LOCAL` grammar does not accept a bound query parameter for the value — it is rejected outright with a syntax error (`SQLSTATE 42601`), independent of driver or ORM, confirmed against a live server. Use `SELECT set_config('app.current_tenant', ?, true)` instead — an ordinary function call, so its value argument is a normal bound parameter — which is exactly what `WithTenantSession` does.
- Do not set `app.current_tenant` with plain `SET` (not `SET LOCAL`, and not `set_config`'s `is_local` left `false`), and do not set it outside an explicit transaction that also contains the query or write it is meant to protect. Either mistake lets the setting persist on a pooled connection past the point it was meant to apply, so it can leak into a later, unrelated request for a different tenant that happens to reuse the same physical connection — the exact bug class this whole mechanism exists to prevent.
- Do not issue a statement meant to be RLS-protected against anything other than the `tx` `WithTenantSession` hands `fn`. A statement issued against the outer `db`, a different session, or a connection obtained some other way inside `fn` never sees the GUC `WithTenantSession` just set — it runs on a different transaction (or no transaction at all) entirely.
- Do not assume a failed GUC-setting step is safe to ignore and fall through to `fn` anyway. `WithTenantSession` aborts the whole transaction and returns the error without calling `fn` when it fails, on purpose: proceeding would silently mean RLS is not engaged for that operation.

**`Repository[T]`**
- Do not build a caller-facing message that distinguishes "no such id" from "that id belongs to another tenant." `FindByID` / `Update` / `Delete` all collapse both to `ErrRecordNotFound` on purpose; surfacing the difference is itself a cross-tenant information leak.
- Do not match `ErrRecordNotFound`, `ErrMissingID`, `ErrMissingTenantContext`, or `ErrTenantIDImmutable` with `errors.Is`/`==` against the package-level var once `WithParam`/`WithCause` may have run on it. Every `apperr` builder derives a *new* `*apperr.Error` instead of mutating the receiver, so identity does not survive decoration. Use `apperr.HasCode(err, code)`, or `dbkit.IsRecordNotFound(err)` for this module's own sentinel.
- `pkgcore.ErrNoTenant` is the one exception in this list — match it with `errors.Is` directly. `Repository[T]` returns it unmodified, and the plugin's `ErrMissingTenantContext` wraps it as `Unwrap`'s cause, so `errors.Is(err, pkgcore.ErrNoTenant)` sees through both shapes uniformly.
- Do not assume `T`'s "ID"/"TenantID" field convention is compile-time checked. A `T` missing either fails the first `Create`/`Update`/`FindByID` call with a descriptive error, not at `go build` time.
- Do not assume `Update`'s `RowsAffected == 0` always means "no such row for this tenant" at the gorm level — it is this package's job to resolve that, not callers'. For a `T` whose only columns are `id` and `tenant_id` (a pure marker/link record with no other field), gorm's own `Update` callback computes an empty SET clause (it excludes every primary-key column, and here every column is one) and returns without issuing any SQL at all, leaving `RowsAffected` at zero whether or not the row exists. `Update` detects this exact case (`gorm did not build a statement at all`, not just `RowsAffected == 0`) and falls back to an explicit, still id-and-tenant-scoped existence check in the same transaction before deciding between success and `ErrRecordNotFound` — so a caller of `Update` never needs to special-case this shape of `T` itself, and a successful call against such a `T` means exactly "this row exists under your tenant", not "some field actually changed", since there is no field left to change. See `Update`'s own doc comment in `repository.go` and `TestRepository_Update_IDAndTenantIDOnlyModel_SucceedsAsNoOp` / `_DifferentTenant_ReturnsNotFound` / `_NoSuchID_ReturnsNotFound` in `repository_test.go`.

**Soft deletion**
- Do not extend the `deleted_at` auto-scope (`softDeleteScopePlugin`) to `Update` or `Delete` without checking whether `Restore`'s defensive `.Unscoped()` call still holds afterward. The plugin is deliberately read-callback-only today — the query and row processors, never update or delete (see the "Soft deletion" section above); `Delete`/`Update`/`Restore` build their own explicit `deleted_at IS NULL` / `IS NOT NULL` conditions instead of relying on it — `Update`'s guard (closing the stale-model hazard the "Soft deletion" section above describes) lives in the method's WHERE chain, matching the other two — and `Restore`'s `.Unscoped()` is currently a no-op kept for exactly this future possibility — broadening the scope without re-checking that interaction could silently make `Restore` unable to reach the very row it means to clear.
- Do not build a caller-facing message assuming `Restore`'s `ErrRecordNotFound` distinguishes "not found" from "found but not currently deleted." Collapsed on purpose, identical rationale to `FindByID`/`Update`/`Delete` above — do not "fix" this into a more specific error.
- Do not call `softDelete`/`Restore`'s underlying write `tx.Model(&zero).Updates(map[string]any{...})`. Build a real `*T`, populate it via `setSoftDeleteFields`, and write through `tx.Where(...).Select(fieldNames...).Updates(&m)` so `Model == Dest == &m` — see the "Soft deletion" section above and `repository.go`'s own doc comment on `softDelete` for exactly what goes wrong with the map-payload shape and why `TestAuditCapturePlugin_SoftDelete_ClassifiesAsUpdateWithRealDiff` exists to catch a regression back into it.
- Do not treat a soft-deleted row as compliance-grade deletion, and do not write documentation, error messages, or product copy that implies otherwise. See the "Soft deletion" section's own warning; `HardDelete` — implemented, system-context-gated, in `hard_delete.go` (see "Hard deletion" below) — is what that actually requires; the orchestration around it (who runs it, on what schedule, against which rows) is `go/compliance`'s — `RetentionService`/`ErasureService` drive registered participants' `HardDelete`-backed callbacks — not a dbkit concern.
- Do not assume `Restore` enforces a retention window. It does not — see "Soft deletion" above.
- Do not treat `HardDelete`'s gate as authorization. dbkit checks only that a system context exists, never who holds it — which module may hold one at all (admin, compliance, jobs, authn) is a caller-side whitelist enforced by code review and doc comments outside this package, and the audited `tenancy.WithSystemContext` wrapper is the entry production grants should go through. Adding an authorization check here would duplicate a mechanism that belongs above dbkit, which cannot import tenancy on pain of a cycle.
- Do not hand-emit an audit Delete event after a successful `HardDelete`. Under `Options.AuditBus` the capture plugin already published one — Operation "delete", `After` nil — and a second, hand-written event would double-count the deletion in the audit trail (see the "Hard deletion" section and `hard_delete.go`'s own doc comment).
- Do not call `HardDelete` on a context with no tenant, and do not expect a system context to supply one. The two refusals are ordered deliberately: no system context → `ErrHardDeleteRequiresSystemContext` (match by `.Code` via `apperr.As`); system context but no tenant → `pkgcore.ErrNoTenant` unmodified (match with `errors.Is`).

**Migrations**
- Do not use `AutoMigrate` anywhere in this codebase — it is neither auditable nor reversible. GORM structs are the schema source of truth Atlas generates versioned SQL from instead.
- Do not put a module's `//go:embed postgres sqlite` directive anywhere but the one file living in the directory where `postgres/` and `sqlite/` are its immediate children — `//go:embed` patterns resolve relative to that file's own directory.
- Do not assume `Register` validates `DependsOn`. A missing or cyclic dependency is reported only by `Apply`, once the full registered module set is known.

**Encryption and blind indexes**
- Do not reuse an encryption key passed to `NewCipher` as a blind-index key, or vice versa. Mixing an AES-GCM key and an HMAC blind-index key is a real cryptographic weakness, not a style nitpick; keep them as two distinct key *values*, whether each is supplied independently or both are derived from one root secret via `DeriveKey` under two distinct purpose strings (see "Key derivation" above) — either way is supported, but the two values must always differ.
- Do not reuse a `DeriveKey` purpose string for a second, semantically different key, and do not edit an already-used purpose string in place to change what it derives. Give every call site its own distinct, stable, versioned purpose (`"...v1"`, `"...v2"` on a deliberate re-derivation) — `DeriveKey` is deterministic, so a collision or an in-place edit silently produces the wrong key for whatever used the old string, with the same blast radius as losing that key outright.
- Do not call `RegisterEncryptedSerializer` from a request path. GORM's serializer registry is process-global; register once per name at bootstrap, alongside other `Module.Register`-time wiring and the matching `NewBlindIndexer` calls.
- Do not skip the column's normalizer on either side of a lookup. Route every write through `(*BlindIndexer).Index` and every query through `(*BlindIndexer).Equal` on the *same* indexer, so both sides apply the column's canonical form automatically; a value stored under one normalization can never be looked up under another. Code calling raw `BlindIndex` directly is responsible for normalizing to canonical form itself, identically at write and query time — `BlindIndex` performs no normalization of its own, deliberately.
- Do not declare a blind-index column as a serializer field, and do not expect the index to be derived from the encrypted field's tag (GORM serializers are per-field and cannot write a second column). Declare it as a plain, indexed column — `` `gorm:"column:<field>_index;size:64;index"` `` — next to the encrypted field, and populate it explicitly on every create/update of that field via `Index(plaintext)`, computed over the same value being encrypted.
- Do not filter on a precomputed index value, and never on one computed under different normalization. `Equal` exists precisely so the query path cannot accept a hand-computed value; hand-building the condition defeats the mechanism and silently returns zero rows for values that are present.
- Do not index an empty or unnormalizable value. `Index` and `Equal` return an error for input their normalizer cannot canonicalize — propagate it, and leave the column NULL for a genuinely absent value; never store `""` or a best-effort guess.
- Do not expect `Decrypt` or an index mismatch to tell you *why* it failed. `ErrDecryptionFailed` covers both a wrong/missing key and a tampered ciphertext by design; a blind-index key rotation has no retired-key fallback and needs every row's index recomputed as a `jobs` batch task (see Known limitations).
- Do not use a blind-index column for anything but exact matches. The mechanism is equality-only by construction; prefix, partial, or fuzzy search over the column would leak the structure the encryption exists to hide.

**Documentation**
- Do not add an exported identifier to this package without a doc comment and an entry in the tables above, in the same pull request — and, for a new public entry point into the package (not every incidental exported type or constant), a compiling `Example` alongside the existing ones in `example_test.go`.

## Error index

| Sentinel | Triggered by | Handling |
|---|---|---|
| `ErrMissingTenantContext` (`dbkit.tenant_context_required`) | The tenant-scoping plugin (layer 1) running a query, scan, update or delete for a `TenantScoped` model on a context with no tenant | Rebuild the context with `pkgcore.WithTenant` (a worker that never rebuilt it is the usual culprit). Also matches `errors.Is(err, pkgcore.ErrNoTenant)`, since it wraps that as its cause |
| `ErrTenantIDImmutable` (`dbkit.tenant_id_immutable`) | An `Update`/`Updates` payload against a `TenantScoped` model trying to set `tenant_id` to a different tenant than the context's | Reject the request; a deliberate cross-tenant transfer needs its own explicit, audited operation |
| `ErrRecordNotFound` (`dbkit.record_not_found`) | `Repository[T].FindByID` / `Update` / `Delete` / `Restore` / `HardDelete` when nothing matches both the id and the caller's tenant (for `Restore`, additionally requiring a currently-soft-deleted row; for `HardDelete`, reported only after the system-context gate has already passed) | Ordinary not-found handling, classified with `dbkit.IsRecordNotFound`. Deliberately indistinguishable from "that id belongs to another tenant" (and, for `Restore`, from "exists but was never deleted") |
| `ErrMissingID` (`dbkit.missing_id`) | `Repository[T].Update` given a model with an empty `ID` field | Caller error — fix the caller; there is no row this call could ever have meant |
| `ErrNotSoftDeletable` (`dbkit.not_soft_deletable`) | `Repository[T].Restore` when `T` does not implement `SoftDeletable` | Caller error — such a `T`'s `Delete` never soft-deleted anything for `Restore` to undo |
| `ErrHardDeleteRequiresSystemContext` (`dbkit.hard_delete_requires_system_context`) | `Repository[T].HardDelete` on a context carrying no system context — checked before the tenant check, and before the database is touched | The caller must obtain a system context first (`pkgcore.WithSystemContext`, or tenancy's audited `WithSystemContext` where importable). Presence-only: dbkit never checks who holds the grant — the caller-side whitelist does that |
| `dbkit.invalid_dialect` (no exported Go sentinel — match on `.Code`) | `Open` given an `Options.Dialect` that is neither `DialectPostgres` nor `DialectSQLite` | Startup misconfiguration; fix the configured dialect |
| `dbkit.connect_failed` (no exported Go sentinel — match on `.Code`) | `Open`'s driver setup, connection-pool retrieval, or `ctx`-bound ping failing | Infrastructure/connectivity problem; the DSN is never included, so check it out of band |
| `dbkit.close_failed` (no exported Go sentinel — match on `.Code`) | `Close` failing to resolve or close the handle's underlying `*sql.DB` | A release-time failure on a shutdown path; the handle is unusable either way, so report and continue the teardown |
| `dbkit.tenant_scope_plugin_failed` (no exported Go sentinel — match on `.Code`) | `Open` failing to install the tenant-scoping plugin on an otherwise-open connection | Should not happen outside a GORM-version mismatch; treat as a startup abort |
| `dbkit.soft_delete_scope_plugin_failed` (no exported Go sentinel — match on `.Code`) | `Open` failing to install the soft-delete auto-scope plugin on an otherwise-open connection | Same cause and handling as `dbkit.tenant_scope_plugin_failed` above |
| `dbkit.audit_capture_plugin_failed` (no exported Go sentinel — match on `.Code`) | `Open` failing to install the audit-capture plugin when `Options.AuditBus` is set | Same cause and handling as `dbkit.tenant_scope_plugin_failed` above |
| *(no error code — see below)* | The audit-capture plugin's `bus.Publish` failing for a captured write, once the write it describes has already durably committed | Not an `*apperr.Error`: by the time either publish path (buffered or bare-write) calls `Publish`, the write has already committed, so there is nothing left to roll back and no code to return through the triggering `Create`/`Update`/`Delete`/`WithTenantSession` call, which reports success. Under the loud-failure rule (an audit-write failure must never be silently dropped), this logs a structured `slog.Default().ErrorContext` alert — message `"dbkit: audit event publish failed after commit"`, attributes `table`/`resource_type`/`resource_id`/`operation`/`tenant_id`/`error` — since dbkit cannot depend on `go/observability`'s `obs.FromContext` (see "One dependency, and why there is only one," above); an operator monitoring for this message has every field needed to reconstruct and manually re-publish or investigate |
| `ErrNilModule` / `ErrEmptyModuleName` / `ErrDuplicateModule` | `MigrationRegistry.Register` given a nil module, an empty `Name()`, or a `Name()` already registered | Fix the registration call; plain `errors.New` sentinels, safe to match with `errors.Is` directly |
| `ErrDependencyCycle` / `ErrMissingDependency` | `MigrationRegistry.Apply`: the registered modules' `DependsOn` graph has a cycle, or names a module never registered | Fix the module's `DependsOn`, or the bootstrap module set; the error names every module involved |
| `ErrUnknownDialect` | `MigrationRegistry.Apply` given a `Dialect` that is neither `DialectPostgres` nor `DialectSQLite` | Same fix as `dbkit.invalid_dialect` above |
| `ErrMigrationLockTimeout` | `MigrationRegistry.Apply` (PostgreSQL only): the cross-process migration advisory lock could not be acquired within its internal wait ceiling, or `ctx` was done first | Retry the call; a concurrent replica is most likely still running its own first-boot `Apply` against the same database and will release the lock when it finishes |
| `ErrInvalidKeySize` | `NewCipher` or `NewBlindIndexer` given a key that is not exactly 32 bytes, or `DeriveKey` given a `rootKey` that is not exactly 32 bytes | Configuration error — AES-256-GCM encryption keys, blind-index HMAC keys, and `DeriveKey`'s root secret are all 256-bit secrets; fix the key material |
| `ErrDecryptionFailed` | `Cipher.Decrypt` when no key, active or retired, authenticates the ciphertext | Wrong/missing key or tampered data, indistinguishable by design; never guess which in a caller-facing message |
| `pkgcore.ErrNoTenant` | `Repository[T]`'s methods and `WithTenantSession`, called on a context with no tenant (returned unmodified in both — see `repository.go`'s and `tenant_session.go`'s doc comments) | Fail closed. In a worker, rebuild the context with `pkgcore.WithTenant`; see `pkgcore/AGENTS.md`'s own error index |
