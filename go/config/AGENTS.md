# config

config is speed's dynamic-configuration module: the schema-first, database-backed settings store whose values can change at runtime and take effect hot — feature-flag enablement, tenant brand items, default limits, AI-model defaults, SMTP parameters. Its scope model has three tiers — `system` (platform-wide) → `tenant` (per-tenant overrides) → `user` (reserved and unimplemented; see Known limitations) — with reads falling back from the concrete tier to the wide one. speed's other configuration layer — process-start bootstrap input (flags/env/files) — is outside this module's scope: it is declared on `pkgcore`'s bootstrap seat (the component descriptors' `BootstrapKeys`), resolved by the general-purpose `pkgcore/config` loader (host-driven against its own target struct, host-declared keys included; a zero-dependency package this module must never import), and its key-material derivation convention — one purpose string per declared key path (`pkgcore.BootstrapKeyPurpose`), composed with `dbkit.DeriveKey` — lives with that seat and toolkit too. This module declares exactly one key on that seat (`config.cipher_key`, below) and owns none of the layer's machinery. On the runtime layer the module also owns feature flags: modules declare feature flags on `pkgcore`'s registry; this module folds those declarations into its schema, walks flag dependency chains at runtime (`IsEnabled`, `EnabledFlags`), and serves the enablement list to the frontend.

It sits directly above `pkgcore`, `dbkit` and `tenancy` — among the always-on modules, with no off switch — depending on nothing else, and it is **required for a multi-tenant host**: every other module's runtime behavior may be governed by a flag or a limit this module serves.

**Dependencies.** The module imports `pkgcore` (registry contracts, tenant context, `EventBus`, `KVStore`, `apperr`, system context), `dbkit` (the `*gorm.DB` wrapper `store.go` reads and writes through, the `MigrationRegistry` its migrations register with, and the field-level AES-GCM `dbkit.Cipher` that Sensitive values are sealed with), `tenancy` (the `Resolver` interface only — the module never maps hosts to tenants itself) and `ratelimit` (the pre-auth endpoints' per-address budget: a pure library with no third-party imports of its own, its `Limiter` built over the registry's already-resolved `KVStore`; `ratelimit.go` records why the budget is a package constant rather than a configuration item). No third-party dependency beyond those modules' own closures: measured with this repository's method (a throwaway module requiring only `github.com/vislake/speed/go/config`, `go mod tidy` under `GOWORK=off`, counting `// indirect` entries), a bare consumer carries **26 indirect entries with the ratelimit import against 25 without it** — the one added line is `go/ratelimit` itself, and no third-party entry is added (21 third-party indirects either way), because every entry of ratelimit's own four-entry closure (`BurntSushi/toml`, `nicksnyder/go-i18n/v2`, `golang.org/x/text`, `pkgcore`) is already in this module's closure. `Locales()` returns an empty `embed.FS`: the module renders no content of its own, and every user-facing string of the endpoints' responses is a structured error code, matching the discipline that user-facing text lives in i18n resources, never in code.

## The Register/Attach interface

The module's wiring is split into two steps, and the split is load-bearing:

- **Register** declares what never needs the assembled registry: the audited system purpose, the two mounted route paths, the change-event declaration, the audit action and the bootstrap key its cipher is built from. It must be called exactly once per host — `pkgcore` fails a host that registers the same module twice.
- **Attach** happens *after* every module has registered (i.e. after the assembly returns its `*ComponentRegistry`): the service's schema is folded from the registry's **combined** item and flag declarations — items and flags owned by other modules are first-class citizens of it — so it cannot exist before registration completes. Attach also demands the runtime dependencies registration must not touch: a `*gorm.DB` with the `configs` table migrated, a `dbkit.Cipher` whenever any registered item is `Sensitive`, and a poll interval (see Hot update below). Attach is idempotence-guarded (`ErrAlreadyAttached`) — the guard is atomic, so under concurrent callers exactly one Attach succeeds and the rest fail the same way, never a second Service with an orphaned poller — and refuses a nil registry or nil database outright.

The two routes mounted by Register resolve `m.service` lazily per request; between Register and Attach — a host wiring bug — they answer with the structured `config.service_not_attached` internal error rather than a nil dereference (a regression test pins this). The `*Service` Attach returns is what a host should keep, not the module. A host that must wire a config-reading module **before** Attach has run (a feature-gate adapter, a duration reader, a typed settings reader) captures `(*Module).Handle()` instead: the handle exists from `NewModule` on, resolves its reads (`IsEnabled`, `TenantDuration`, and the typed `Duration`/`Int`/`String` reads) through the Service per call, and reports `ErrServiceNotAttached` for every read in the same pre-Attach window. The typed reads are the shape the request-time modules consume — authn's and metering's settings readers are the shipped ones — and each resolves the schema default with `ok=false` (the caller's cue to apply its own construction-time fallback) and an explicit row with `ok=true`.

Register also declares one process-start key on the component descriptor's `BootstrapKeys`: `config.cipher_key`, the `hexkey`/Sensitive cipher key whose `dbkit.Cipher` seals every Sensitive item (see "Sensitive values at rest"). It is declared on the bootstrap layer rather than as a `ConfigItem` because the key that encrypts the configs table cannot live in the configs table, and the assembly refuses a key declared on both layers — so this declaration and the schema this module folds can never claim the same identifier. The host resolves the value and passes the cipher through `WithCipher`; config never reads the environment.

The module itself never drives the assembly: it carries the module contract (implementing `Name`, `Migrations()`, `Register` plus its own `Attach`), and hosts boot it beside their own modules, as `examples/reference-app` does.

## Scope, fallback and entitlements

Every stored value lives at exactly one scope tier and is addressed by the triple `(key, scope, tenant_id)` — the `configs` table's primary key, with the system tier stored under the empty-string tenant sentinel (a NOT NULL column; there is no NULL-magic in the row model). Resolution order is narrow-to-wide: a read under a tenant consults the tenant tier first, then the system tier, then the schema default (which the service serves as a value with the zero `Scope`, since no row tier owns it). A tenant-less context never consults the tenant tier: it reads system rows, falling back to defaults.

The service — never the caller, never the HTTP layer — enforces each tier's entitlement on `Set`:

- a tenant write requires a tenant in the context (`ErrTenantScopeRequiresTenant` otherwise), and is attributed to the context's tenant, never to a caller-supplied id;
- a system write requires an audited system context — only `pkgcore.WithSystemContext` (or `tenancy.WithSystemContext`, which adds its own audit event) establishes one, and a write without it fails `ErrSystemScopeRequiresSystemContext` — so no tenant-scoped request path can widen a platform setting. The gate is the context's system-ness, not the purpose's identity: `config.system_write` (`SystemPurposeSystemWrite`, module.go) is the purpose this module's own callers are expected to declare, but any registered purpose's system context passes, matching `pkgcore`'s model of the purpose as an audit attribute, asserted (with the actor) when the context is built;
- `user` scope is reserved and unimplemented; a write to it fails `ErrUserScopeUnavailable` rather than being silently stored at the wrong tier.

The `configs` table is **platform data** (it holds every tenant's rows side by side, distinguished by the `tenant_id` column, with tenant isolation *deliberately* off: a tenant filter would make the system tier — the fallback every tenant reads — invisible). `model.go` therefore never implements `dbkit.TenantScoped`, and `model_test.go` proves it with `tenancytest.AssertNotTenantScoped`. Module repositories of tenant-owned data must *not* copy this: they embed `dbkit.Repository[T]` and run `AssertIsolated`; this module is the documented exception for platform data.

## Canonical values, schema, bounds

A value is stored and transmitted as a **canonical string** per item type: the string itself, `"true"`/`"false"`, decimal for ints, `time.Duration.String()` for durations. `values.go` owns encode and decode; decode is the single choke point that detects stored corruption (a row written by a buggy or older writer, or edited outside the module, never decodes to a wrong-typed `Value`). How a corrupt row surfaces depends on the read path: `Get` reports it (`ErrStorage` carrying the decode error), while the pre-auth public snapshot — per-item tolerance is its contract — skips the item with a Warn naming it and keeps serving the rest (see Endpoints). Ints decode to `int64` uniformly, so a `GetTyped[int]` read fails `ErrTypedValueMismatch` rather than silently truncating on 32-bit hosts — `GetTyped` supports `string`, `bool`, `int64` and `time.Duration`.

The schema (built at Attach from the registry) carries each item's declared `Type`, `Default`, `Min`/`Max`, `Sensitive`, `Public`, `Description` and `Group`. `pkgcore`'s `ConfigSchemaRegistrar.Add` already rejects self-contradictory declarations (`Sensitive` and `Public` together, wrong-typed or out-of-range defaults/bounds, unknown types — all `ErrInvalidConfigItem`); the module's own schema fold additionally enforces what only the whole registry can see: duplicate keys across modules and item/flag collisions fail `ErrSchemaConflict` with the offending `key` in params, a flag dependency on a plain item fails with `depends_on` named, and flag cycles fail `ErrFeatureFlagDependencyCycle` carrying the cycle's keys. Bounds are enforced at write time by the service (`ErrInvalidValue` on a miss). Validation errors never echo the offending value into params, logs or responses — that discipline matters most for Sensitive items and is uniform across the module.

## Sensitive values at rest

A `Sensitive` item is sealed with the host's `dbkit.Cipher` (AES-GCM, the same field-level cipher the AI gateway's credential store uses) before it is stored: the `configs` table holds `base64(ciphertext)`, and Attach refuses to run when a Sensitive item is registered but no cipher was provided (`ErrCipherRequired`) — a host without the key could never write or read such a value without leaking it. The plaintext exists only inside the service's cache and in the response of an entitled `Get`. It is redacted — replaced by the stable `[redacted]` marker — at every boundary the plaintext would otherwise cross: the `config.item.changed` event payload, `Watch` deliveries, and logs/errors (the module never echoes values into its own messages; pkgcore's redaction layer covers the rest). `Public` and `Sensitive` are mutually exclusive by declaration validation, so the pre-auth endpoints cannot leak a Sensitive value by construction — a test asserts the raw response bytes contain neither the key nor a written value.

## Hot update: events, invalidation, and the anti-loss poller

`Set` writes the row, advances the process's own cache **before** publishing, and then publishes the change event (`config.item.changed`, payload type `config.ItemChangedEvent`) with key, scope, tenant, actor, `OldValue`/`NewValue` (redacted for Sensitive items, marker included when no previous row existed), and `ChangedAt`. The event is also the module's declared audit record for the moment of the write: it carries everything a compliance record needs (who, when, what, old→new). Config itself never writes audit rows; the durable record exists only through the optional `compliance` module, which subscribes to this event (see Known limitations). A failed publish does not roll the write back — the row and the local cache have advanced — and `Set` reports `ErrAuditPublishFailed` so a host that treats audit as mandatory can react; the process never serves the value it just overwrote.

Subscribers and peer instances keep their caches coherent through the module's own subscription to the event (invalidation by exact row triple — never a blanket flush), **plus** a bounded TTL-style backstop: the anti-loss poller. Because a single lost event would otherwise leave a replica serving stale configuration until the next write happens to land, every process polls the `configs` table for rows changed since its watermark on the interval the host chose (`WithPollInterval`; the package constant `DefaultPollInterval` is 30s; `0` disables the poller for single-instance hosts). The watermark query is inclusive (`>=`) so a row written *during* a sweep is guaranteed to be seen by the next one, and each sweep invalidates every changed row and advances the watermark to the newest row's timestamp. The poller never fires watchers — its contract is cache convergence, not change notification — and a poll cycle that finds nothing advances nothing. Layered on top: every `fullReconcileEvery`-th (20) `Refresh` cycle also evicts the *entire* cache (see Known limitations for why this exists and what it bounds), independent of the watermark's own position.

`Watch` delivers synchronously on the publishing goroutine for in-process publishers (the standalone mode's memory bus), with per-callback panic containment, and delivers the change as the event saw it: scope-annotated, redacted for Sensitive keys.

## Feature-flag runtime

`pkgcore` owns the declaration side of feature flags — modules register `FeatureFlag`s (key, default, description, `DependsOn`), and `pkgcore`'s `ValidateFeatureGraph` fails a bootstrap in which a flag depends on a flag nobody registered (it proves resolution only). Cycle rejection is this module's job: the Attach-time fold's `detectFlagCycles` (`schema.go`) fails `ErrFeatureFlagDependencyCycle` with the cycle's keys. This module owns the runtime side: the schema fold admits flags beside items (item/flag key collisions are schema conflicts), a flag's effective value at any moment is its tenant-tier override, else its system-tier override, else its declared default, and `IsEnabled` treats the flag as enabled only when **it and every flag it depends on** (transitively) report enabled — a tenant that turns a dependency off disables everything above it, per-tenant, without a data migration. `EnabledFlags` renders the sorted list of enabled keys, serving the `PathSystemFeatures` contract, and answers `config.unknown_flag` (params: `key`) for keys that are not declared flags, including plain config items that merely look boolean.

## Endpoints

Two pre-auth endpoints are mounted at the exported `PathPublic` (`/api/v1/config/public`) and `PathSystemFeatures` (`/api/v1/config/features`) — the versioned, module-scoped prefix every other module's routes use. Hosts name them in tenant-middleware allowlists via the constants, and that is the supported form: a host that had addressed the endpoints by their earlier unversioned paths by hand must re-address them, while a host that named the constants follows the move without an edit.

Both endpoints are declared by this module's OpenAPI fragment, `api/openapi.yaml` (`config_getPublicConfig` and `config_getSystemFeatures`): `*Module` implements the fragment's generated `api.ServerInterface` (the `var _` compile-time assertion at the bottom of `http.go`) and `Register` mounts the fragment's generated wrapper under each path constant, so the fragment — never a hand-written dispatch — is what routes a request, and a spec change without a matching handler change cannot compile. `task api:gen` regenerates `api/config-server.gen.go` (pinned oapi-codegen v2.8.0) from the fragment, which also joins the application-wide `contracts/speed.yaml` merge and the generated `@speed/api-sdk`: the generated hooks (`useConfigGetPublicConfig` / `useConfigGetSystemFeatures`) are the frontend's primary call surface for the pair, and `@speed/api-client`'s `config-fetcher` plus its `./react` hooks remain the per-key mapping layer over the endpoints' dynamic config keys — a generated type for the public-config body can only be a record of dynamic keys, so the per-key typing those hooks expose cannot come from generation. Both answer GET and HEAD only (anything else: 405 with `Allow: GET, HEAD` and the stable `config.method_not_allowed` code), and both resolve the request's tenant through the host-wired `tenancy.Resolver` — custom domain first, subdomain second, platform defaults last, **never an error**: an unmatched host, a failing resolver or no resolver at all reads platform defaults with a 200, because a login page that fails to render is the worst failure mode. `/api/v1/config/public` serves `{"config": {key: value, ...}, "features": [...]}` — only `Public` items, durations as canonical text, an empty feature list as `[]`, never `null` (regression-pinned), and a `Public` item with no value anywhere — no row at any reachable scope and no declared `Default`, a legal declaration whose module serves no value until one is set — **omitted** from the snapshot rather than failing it, so one unset item can never take the endpoint (and with it the login page) down for every tenant. The same tolerance covers an item whose stored row cannot be decoded under its declared type: the item is omitted with a Warn naming it, for the same reason — one corrupt row must not take the login page down for every tenant either. `/api/v1/config/features` serves the enablement list alone, `{"features": [...]}`. Every response is JSON with the stable content type, and every error is the structured envelope `{"code": ..., "params": ...}` that `apperr` codes map to HTTP statuses; a non-classified error folds into the module's `config.storage_error` rather than leaking a raw Go error string. The endpoints are deliberately pre-auth and serve only display decisions, never data.

Because they are pre-auth, these two routes are also the module's whole abuse surface, and both are guarded the same way. A per-address request budget (`ratelimit.go`: one dimension, `preAuthPerIPRate` per `preAuthPerIPWindow`, one key shared by the two paths because together they serve one page load's worth of the same display answer) refuses an over-budget address with `config.rate_limited` (429, params `dimension` and `retry_after_seconds`), and **fails closed** with `config.storage_error` when the limiter's KVStore cannot answer — a check that read as "allow" would leave exactly the volume it bounds unthrottled for the duration of the outage. The budget is keyed on the direct peer address from `RemoteAddr`, never on a forwarded header: an unauthenticated route is exactly the shape a caller can spoof one against, so a host that terminates TLS behind a trusted proxy normalizes `RemoteAddr` itself, ahead of these handlers. A successful answer declares the module's caching decision in the response headers — `Cache-Control: public, max-age=<publicCacheMaxAge>` plus `Vary: Host`. It is cacheable because the answer is display-only, per-tenant content that changes only when an operator writes a row: the module's own `config.item.changed` subscription invalidates the process-local cache the moment a write lands, so an origin replica never answers from a superseded row, and the pinned freshness lifetime is the bound that event cannot reach — a copy already held by a browser or an intermediary cache. That is the deliberate opposite of the sharing module's public access route, where a cached copy outliving a revocation is the failure mode being prevented. Every refusal (405, 429, 500) carries `no-store` instead: a cached 429 would keep refusing past the window it announced, and a cached 500 would hide the recovery.

## Rules

- **Do not read config through the raw `configs` table** from another module. The scope fallback, decryption, cache and flag semantics live in the `Service`; anything that reaches around it re-implements a wrong subset (a common wrong subset is "tenant tier only", which silently ignores platform-wide overrides).
- **Do not hand `Set` a caller-supplied tenant.** The service derives the row's tenant from the context; the API layer never accepts a tenant parameter, per the multi-tenancy discipline.
- **Do not bypass the audited system context** to write the system tier. `WithSystemContext` with a declared purpose is the only entitlement, and it is the same escape hatch every cross-tenant write in this repository must use.
- **Do not log or return a Sensitive value** in this module's own code paths; the redaction points live in `events.go` and the service, and new code that touches value-shaped data should route it through the same two points.
- **Do not add a third scope tier** (user) by editing `scope.go`'s validation alone; the tier's storage, resolution order and entitlement need their own design pass and their own tests.
- **Do not add PostgreSQL-only features** to migrations or queries, and **never use `AutoMigrate`** — versioned SQL per dialect, registered through `dbkit`'s `MigrationRegistry` (`migrations/`), is the only path.

## Known limitations (deliberately deferred)

- **No admin-facing config-editing UI exists.** The read side is delivered: `@speed/api-client`'s `./react` subpath ships `usePublicConfig()`/`useFeature` (`src/react.ts`, tested in `react.test.ts`), and `examples/reference-app/web` is a real consumer of both (`app-services.tsx`, `views/home-view.tsx`) — the frontend startup path genuinely reads public config and resolves feature flags through them, not through a hand-written client. What is not built is a config-*editing* UI (an admin console screen to read/write items and flags).
- **Durable audit rows exist only through the optional `compliance` module.** Config itself never writes audit rows: the per-`Set` record it produces is the published `config.item.changed` event, and that module subscribes to the event and inserts one record per set through dbkit/audit's append-only repository. A host that does not compose it must treat a failed publish (`ErrAuditPublishFailed`) as actionable when audit is mandatory for it.
- **`user` scope is not implemented.** Writes to it fail `ErrUserScopeUnavailable`; reads ignore it. Nothing in the schema model needs to change to add the tier later.
- **Item `Description` is single-language** (English prose in code). The bilingual catalog (`pkgcore/i18n`) renders content, not schemas; item descriptions are not yet localized, and an admin UI rendering schema forms would need them as message ids.
- **Per-flag consumption semantics are the consumers' job.** The design's "disabled feature answers 404, not 403" and "a disabled flag skips route registration and background jobs, never migrations" rules are enforced by the modules that consume flags (authn, billing, ai-gateway, ...), not by this module — it only answers what is enabled. Likewise, whether a module ships in a binary at all is a scaffolding-time concern, not a runtime query.
- **Tenant resolution is delegated, never implemented here.** The module consults a `tenancy.Resolver` if the host wired one; domain→tenant mapping and its cache belong to the tenancy side, and the endpoint tests fake the resolver to prove the fallback behavior.
- **The watermark poller's incremental sweep alone cannot recover a write behind a skewed writer's clock; a periodic full reconciliation bounds — but does not eliminate — how long that leaves a cache entry stale.** `UpdatedAt` (the watermark's ordering column) is an application-supplied `now()` (`service.go`), never a database-generated timestamp, so a genuine cross-replica clock skew — or a single writer's clock stepping backward under an NTP correction — can produce a row whose `UpdatedAt` lands *behind* a watermark this process already advanced past. Combined with the `config.item.changed` event for that same write being lost (the event bus's own best-effort delivery, the poller's whole reason to exist), `changedSince`'s `WHERE updated_at >= watermark` predicate (`store.go`) can never select that row again through the incremental sweep by itself — the watermark only ever grows forward, so without a separate mechanism the row would be invisible forever, not just until the next tick (proved directly, both ways, by `TestService_Refresh_IncrementalSweepAloneNeverRecoversASkewedWrite` and `TestService_Refresh_PeriodicFullReconciliation_RecoversASkewedWrite`). The mechanism that closes the gap: every `fullReconcileEvery`-th (20) `Refresh` cycle evicts the entire process-local cache (`valueCache.invalidateAll`) regardless of the watermark, so the next read of any key — the stuck row included — falls through to the store and observes its true value. The accepted residual: a row hit by this exact combination can still serve a stale cached value for up to `fullReconcileEvery` − 1 `Refresh` cycles (at the default 30s poll interval, under 10 minutes) before the periodic reconciliation catches it — a bounded staleness window where the incremental sweep alone would leave the same row invisible forever. The combination is narrow — it needs simultaneous event loss *and* a specific clock-skew direction on the very write that was lost — but real given multi-replica distributed deployments and genuine NTP corrections. A host that cannot tolerate even that bounded window can always call `Refresh` directly (it is exported exactly for this) after an operation it knows crossed a clock boundary.
- **A read-through backfill racing a concurrent write is closed by a cache mutation-generation guard — the read side pays at most one extra store read.** The read path (`resolveRow`) is read-DB-then-backfill-cache: a reader whose store read completed before a concurrent `Set`'s write could, without a guard, land its pre-write backfill *after* that `Set`'s own cache put and its `config.item.changed` invalidation — planting the pre-write value in the cache until the next event for that key or the periodic full reconciliation evicted it (the same bounded-staleness residual the clock-skew bullet records, reached by a different door). The fix: every cache mutation (`put`, `invalidate`, `invalidateAll`) advances a generation counter, `resolveRow` captures it before its store read, and the backfill lands through `putIfUnchanged`, which drops it when the generation moved meanwhile — a concurrent writer's put, its invalidate, a poller sweep, a remote change event — so a pre-write value can never be cached past the write that superseded it. What the reader gives up: a dropped backfill costs one store read on the next access (the value just read is still served to the caller), and under constant unrelated cache churn backfills may be dropped more often — a correctness-preserving miss rate, never a stale serve. The exact interleavings are pinned deterministically at the cache module (`cache_test.go`'s `putIfUnchanged` tests) and under real concurrency by `TestService_ConcurrentReadBackfill_NeverOutlivesTheWritersInvalidate`. Note this is a different mechanism from the watermark clock-skew bullet above — that one protects against *lost events on writes we never heard of*; this one against *in-flight reads that heard of the write too late* — and unlike that residual this one is closed, not merely bounded.

## Testing

Unit tests live beside the source files they test, named `*_test.go` for `*.go` (`service.go` → `service_test.go`, ...), and run on the standalone modules alone — in-memory SQLite (the `configs` table migrated through the real `MigrationRegistry`), the memory bus and KV store — so `go test ./... -race` needs no Docker. Shared assertions (`assertCode`, `assertParam` — decorated `apperr` errors must be matched on their `Code`, never by identity — plus the schema fixtures, the test cipher, and the tenant/system context helpers) live once in `service_test.go` and are used by the other files' tests, matching the house rule that helpers are never duplicated across test files; each file's DB-open helper is its own, with its own counter, following `dbkit`'s precedent. Sensitive-value tests use a 32-byte random key via `crypto/rand`, never a readable string. The `configs` table's non-tenant-scoped proof runs `tenancytest.AssertNotTenantScoped` (`model_test.go`). The HTTP layer's own pins live in `http_test.go`: the two paths under the module's versioned prefix, the fragment declaring both paths while the handler serves only the paths the fragment declares, the request that pushes an address over its budget answered 429 `config.rate_limited` on either endpoint (with a second address unaffected, and the budget shared across both paths), the check failing closed on a limiter whose store cannot answer, and the caching contract on both methods of both endpoints — `public, max-age=<publicCacheMaxAge>` plus `Vary: Host` on a success, `no-store` on every refusal (405, 429, 500). Pinned timestamps keep watermark and upsert tests deterministic; the poller's own convergence is tested with a millisecond poll interval and a bounded `eventually` loop, which keeps the race detector meaningful.

An `integration_test/` tier (`-tags=integration`) re-runs the same proof surface against real PostgreSQL (both dialect migrations applying, the upsert and watermark query on real server semantics) and real Redis (the event-publish/invalidation path), in the same physical separation the other modules' tiers use — a plain `go test ./...` never touches it.

`example_test.go` carries the module's runnable usage documentation, in the external `config_test` package so it reads as a consumer sees it: one `Example` walking the headline path end to end — a business module declaring a config item and a feature flag during `Register`, an assembly over it and the config module, the single `Attach` that freezes the assembled schema, then a platform-default read, a tenant-scoped `Set` that overrides it for one tenant, and an `IsEnabled` resolution. Its `// Output:` block is checked by `go test`, so the example cannot drift from the API without failing the build, and the house rule that new public surface ships with a compilable example is satisfied by that file rather than asserted here.
