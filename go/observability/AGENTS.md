# observability

The foundational layer only: OTel initialization whose exporter wiring is
chosen by the caller's options rather than any deployment mode, a
context-aware structured logger, and generic HTTP instrumentation. See
`docs/internal/09-observability.md` for the full design intent — including
the per-domain "must-instrument metrics" table (queue depth, metering
outbox lag, notification delivery rate, payment callback success, ...),
which belongs to the modules that own those domains (`jobs`, `metering`,
`notification`, `ai-gateway`) once they exist. None of
them exist yet (root `CLAUDE.md`'s M0 status), so this module does not
speculatively build instrumentation for them.

| Concern | Where |
|---|---|
| `Init` (TracerProvider/MeterProvider wiring, global install, shutdown; exporters chosen by whether `WithOTLPEndpoint` was supplied — no deployment mode involved) + `MetricsHandler` (the local exporters' `/metrics` handler) | `init.go` |
| `FromContext` / `WithLogger` (the context-aware `*slog.Logger`) | `logger.go` |
| Attribute redaction (key-based + value-shaped secret masking on the log channel; the span channel is kept secret-free by construction — see the redaction section below) | `redact.go` |
| `Middleware` (per-request span + request-count/duration metrics) + `AnnotateTenant` | `middleware.go` |

## Public API

### `init.go`

| Signature | Purpose |
|---|---|
| `func Init(ctx context.Context, opts ...Option) (func(context.Context) error, error)` | Wires a `TracerProvider` and `MeterProvider` and installs them as OTel's **global** providers (`otel.SetTracerProvider` / `otel.SetMeterProvider`), so `Middleware`, `FromContext`'s span lookup, and any future module's own `otel.Tracer`/`otel.Meter` calls all reach them with no provider threaded through every call site. Which exporters get wired is decided solely by whether the caller supplied `WithOTLPEndpoint`: with a non-empty one, both signals are pushed over OTLP/gRPC to that endpoint; without one, the local exporters are wired. No deployment mode is passed or consulted — exporter selection is an implementation-composition question (`docs/internal/03-deployment-modes.md`), never a mode question. Returns a shutdown function the caller must invoke during graceful process shutdown |
| `type Config struct { ServiceName, OTLPEndpoint string; OTLPInsecure bool }` + `Option` / `WithServiceName` / `WithOTLPEndpoint` / `WithOTLPInsecure` | `Init`'s tunables. `OTLPEndpoint` is deliberately **not** read from the environment by this package — see `Config.OTLPEndpoint`'s own doc comment for why (the seam a real host wires up, either directly or once `pkgcore/config`'s bootstrap loader is wired in) |
| `func MetricsHandler() http.Handler` | The `/metrics` handler the most recent `Init` call wired up: a real Prometheus scrape endpoint when `Init` wired the local exporters (no OTLP endpoint configured), a 404 explaining metrics are pushed via OTLP when it wired the OTLP exporters — or before `Init` has run at all |

**The no-endpoint wiring needs zero external dependencies.** Traces go to stdout (`stdouttrace`, synchronous — no batching delay). Metrics go to stdout too (`stdoutmetric`, periodic, for a developer tailing the process) **and** to an in-process Prometheus registry exposed via `MetricsHandler` — a fresh `prometheus.NewRegistry()` per `Init` call, never `prometheus.DefaultRegisterer`, so a second `Init` call in the same process (every test in this package that exercises the no-endpoint path does exactly this) never panics with "duplicate metrics collector registration".

**Supplying `WithOTLPEndpoint` pushes both signals over OTLP/gRPC** (`otlptracegrpc` batched, `otlpmetricgrpc` periodic) to `Config.OTLPEndpoint`. Deployment mode plays no role in either wiring: a single-process assembly pointing at a real collector uses the OTLP exporters no less than a multi-replica deployment does, and the local exporters serve a multi-replica process that chose not to push just as they serve a single-process one.

### `logger.go`

| Signature | Purpose |
|---|---|
| `const TraceIDKey, SpanIDKey, TenantIDKey = "trace_id", "span_id", "tenant_id"` | The shared, `snake_case` field/attribute keys, per root `CLAUDE.md`'s logging rule |
| `func WithLogger(ctx context.Context, logger *slog.Logger) context.Context` | Attaches a hand-built logger to `ctx` for `FromContext` to find. The **principal** call site is process startup, before any request/trace context exists to derive a logger from; a genuinely context-less special case (a test, say) may attach one too — see its own doc comment |
| `func FromContext(ctx context.Context) *slog.Logger` | The **only** sanctioned way to get a logger inside request- or job-scoped code (root `CLAUDE.md`'s rule that the logger comes from the context; `backend-coding-standards.md` §11's never-a-fresh-logger-inside-a-request-path rule). Falls back to `slog.Default()` when no `WithLogger` call attached one. Attaches `trace_id`+`span_id` when `ctx` carries an active OTel span, and `tenant_id` when `ctx` carries one (`pkgcore.TenantFromContext`) — each independently optional; a missing one is simply omitted, never an error or a placeholder. Every logger it returns is wrapped in the redaction layer (below), so this API is the whole log-channel redaction story |

### `redact.go`

| Signature | Purpose |
|---|---|
| `const RedactedValue = "[REDACTED]"` | The deterministic marker every masked value becomes — the only form in which a secret ever reaches a sink |

**Redaction is on by default for every logger `FromContext` returns, with no per-call way to disable it** (docs/internal/09-observability.md's "must not be disableable from call sites" rule; docs/internal/10-compliance-and-audit.md's audit logs are a separate M1+ mechanism and out of scope here). The wrap happens once in `redactedLogger` (called by `FromContext`), not per sink: whatever handler a host plugs in, records pass through this layer first.

Two rules, applied at the attribute level:

- **Key-based.** An attribute whose key — or any segment of its key path, for group-nested attributes — case-insensitively **contains** one of `token`, `secret`, `password`/`passwd`/`pwd`, `authorization`, `cookie`, `credential`, `key` gets its **entire value** replaced by `RedactedValue`, regardless of the value's kind (string, number, struct, error, ...). Matching is by substring and deliberately errs on the side of over-redaction: a benign attribute whose key merely contains a stem (`keyboard_events` contains `key`) loses its whole value too, because an over-redacted field costs noise while a leaked secret costs a breach (the tradeoff rationale lives in redact.go's `sensitiveStems` comment). The correlation fields `trace_id`, `span_id`, `tenant_id`, `user_id`, `job_id` are **never** redacted, so a user_id that happens to be JWT-shaped still logs verbatim (redact_test.go's `TestRedact_CorrelationKeysNeverRedacted`).
- **Value-shaped.** A string (or error-text) attribute under a benign key is scanned only when ≥16 bytes long, for five unambiguous secret shapes: `Bearer <token>`, JWTs (the `eyJ` header anchor), provider-prefixed keys (`sk_`/`pk_`/`rk_`/`sk-`, `AKIA`, `AIza`, `ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`/`github_pat_`, `xox*`, `glpat-`), URL query parameters whose names are unambiguous secrets (`access_token`, `api_key`, `client_secret`, `password`, `refresh_token`, `secret`, `session_key`/`session_token`, `sig`/`signature`, bare `token`), and URL userinfo passwords. Matching regions are replaced **in place** — surrounding text survives, so an error like `provider auth failed ... with Bearer [REDACTED]` stays readable — and masking is idempotent: re-scanning masked output is a fixed point (a value class that admits the marker's brackets — the URL query and userinfo classes do — re-matches only to reproduce it, never a new region). There is deliberately **no** generic "long random string" rule, and group/attr keys are only checked against the stems above — a JWT under `user_id` must survive by the exemption rule, not by luck.

**Deliberate boundaries** (all documented in redact.go's header): the log *message* is never scanned; non-error struct values are never introspected; the key set above is exhaustive by design, so a future sensitive-named key is a code-review point in `redact.go`, not a config question. API **responses**, audit-log payloads (M1+, docs/internal/10-compliance-and-audit.md) and dbkit's field-level encryption are separate mechanisms this module does not duplicate. `pkgcore.Registry`'s `ConfigItem.Sensitive` marks config items for the config-reference/admin-console and has no redaction role — that flag and this key set are complementary, and redaction must work pre-registration, which is why it keys off names rather than registry markers.

**Mechanics kept honest** (see redact.go's own doc comment): slog carries `With`-attached attributes in the handler, not the record, so static attributes are redacted once in `WithAttrs` (before delegation, preserving the sink's formatting fast path) and `WithGroup` is mirrored so group names participate in key-path sensitivity; `Handle` then only scans the record's own attributes, forwarding unchanged records with zero allocation (a claim scoped to scalar attribute values — a benign `slog.Group` costs a few allocations per nesting level; see redact.go). Two contract points follow: (1) `FromContext` never returns the exact `*slog.Logger` `WithLogger` attached — the redaction layer always sits between, so a `WithLogger`-attached logger must be built as `slog.New(handler)` with no `With`-attached attributes (they would bypass the layer); static attributes belong on the `FromContext` result instead. (2) A hand-built `slog.Logger` logged through directly, outside `FromContext`, is the documented deliberate escape; this module's own rules confine that construction site to the genuinely context-less sites a hand-built logger is legitimate at — process startup above all (see `WithLogger`'s doc comment). Root `CLAUDE.md` and `backend-coding-standards.md` are not the source of that confinement: they only require the context logger where a context exists. Guarded, not assumed: user code reachable from attribute rendering is recover-guarded, so a panicking value can never crash the logging path.

**The span channel.** This module's span attributes are kept secret-free *by construction* rather than by a second redaction pass: `Middleware` assembles only method/route/status/tenant fields at the attribute-construction site, and both the span name and the `http.route` attribute derive from `URL.Path`, from which net/http has already split the query string — while otelhttp's own server-span semconv omits `url.query`/`url.full` by design. All of that is pinned by negative controls (`middleware_test.go`'s `TestMiddleware_QueryStringSecrets_NeverReachSpanAttributes`) rather than trusted by assumption, so a future otelhttp upgrade or a code edit that starts naming spans from `URL.String()` fails the build instead of leaking silently.

### `middleware.go`

| Signature | Purpose |
|---|---|
| `func Middleware(next http.Handler) http.Handler` | Wraps `next` to start a request span (via `otelhttp`) and record `http.server.request.count` / `http.server.request.duration`, labeled **only** by method, route and status code. The metrics' route label is capped at `MaxRouteLabelValues` distinct values and `MaxRouteLabelLength` bytes each (see the caveat below); the span's own route attribute always carries the exact, uncapped `URL.Path` |
| `func AnnotateTenant(ctx context.Context)` | Records the tenant carried by `ctx`, if any, as a `tenant_id` attribute on `ctx`'s active span. No-op with no tenant or no span |
| `const MaxRouteLabelValues int` / `const RouteLabelOverflowValue string` | The route-label cardinality bound and its overflow sentinel (`"{overflow}"`) — exported so `middleware_test.go`'s negative control, and any consumer auditing this behavior, checks the actual enforced values rather than a hardcoded guess |
| `const MaxRouteLabelLength int` | Bounds, in bytes, the length of any single `http.route` value before `routeLabelLimiter` uses it as a map key or hands it back as the metric label value — an orthogonal bound to `MaxRouteLabelValues` (which caps distinct-value COUNT, not size): closes a narrower, higher-cost resource-exhaustion vector where a bounded number of very long attacker-controlled paths could still bloat the limiter's map and the exported Prometheus series. See `middleware_test.go`'s `TestMiddleware_LongRoutePaths_LabelLengthIsBounded` for the negative control |

**Hard rule, enforced by construction, not just documented: `tenant_id` never becomes a metric label.** `Middleware`'s metric-recording code path never reads `pkgcore.TenantFromContext` at all. See `middleware_test.go`'s `TestMiddleware_MetricsExcludeTenant_NoPerTenantSeries` for the negative control: two tenants' requests collapse into one series, and no gathered metric family ever carries a `tenant_id` label. Tenant correlation instead goes to span attributes (`AnnotateTenant`) and structured log fields (`FromContext`), both of which Tempo/Loki tolerate at high cardinality — `docs/internal/09-observability.md`.

**`Middleware` is meant to be mounted OUTSIDE `tenancy.Middleware`**, per `docs/internal/01-architecture.md`'s fixed chain order (`recover -> request-id/log-context -> observability -> tenancy.Middleware -> ...`, "not to be casually adjusted"). `tenancy.Middleware`'s own doc comment says nothing about tracing middleware specifically, so that fixed order is the tie-breaker — see `examples/reference-app/cmd/server/main.go`'s `run` for the actual wiring and the same reasoning repeated at the call site. The cost of that position: a tenant is not yet known at `Middleware`'s own layer (Go's `http.Handler` chain propagates request state strictly downward — `tenancy.Middleware`'s `(*http.Request).WithContext` fork is invisible back up the chain), which is exactly why `AnnotateTenant` exists as a separate function business handlers (or, once they exist, `authn.Middleware` / `rbac.RequirePermission`) call once a tenant is actually resolved — a trace `Span`, unlike a plain context value, is a shared mutable object that survives that fork.

**Route-label caveat.** The route label is derived from `URL.Path`, not the lower-cardinality `(*http.Request).Pattern` `net/http.ServeMux` (Go 1.22+) populates on a match: `Pattern` suffers the identical fork-visibility problem `AnnotateTenant`'s doc comment describes for the tenant. This is not only a future-parameterized-route risk: it is exploitable *today*, by any unauthenticated caller, via a plain mux 404 or `tenancy.Middleware`'s own pre-mux 403 (an unrecognized `Host`) — neither requires a valid route or credential, and both still reach `Middleware` with the caller's raw path untouched. `Middleware` therefore runs the metrics' route label (only the metrics' — the span attribute stays exact) through a small in-package limiter that tracks up to `MaxRouteLabelValues` distinct values and collapses anything past that into the fixed `RouteLabelOverflowValue`, so an attacker can never grow this metric's series count past `MaxRouteLabelValues`+1 no matter how many distinct paths they send. See `middleware_test.go`'s `TestMiddleware_UnboundedRoutePaths_CardinalityIsBounded` for the negative control. Capping distinct-value COUNT alone does not cap value SIZE: `examples/reference-app`'s `http.Server` sets no `MaxHeaderBytes`, so it inherits `net/http.DefaultMaxHeaderBytes` (1 MiB) as the effective ceiling on a single request's URL length, meaning an attacker could still send up to `MaxRouteLabelValues` distinct, near-1-MiB paths and make both `routeLabelLimiter`'s internal map and the exported Prometheus series themselves retain attacker-controlled data on that order. `Middleware` therefore also truncates every value (`truncateRouteLabel`, cutting on a UTF-8 rune boundary) to at most `MaxRouteLabelLength` bytes before it can become a map key or a label value — an orthogonal bound to the count cap: truncation can only collapse distinct long values together, never increase how many distinct values `routeLabelLimiter` tracks. See `TestMiddleware_LongRoutePaths_LabelLengthIsBounded` for that negative control. This bound is a circuit breaker, not a precision fix: a future parameterized route (e.g. `/api/v1/billing/subscriptions/{id}`) mounted downstream of `tenancy.Middleware` would still burn through the cap one ID at a time before falling back to the overflow bucket, losing per-route granularity rather than collapsing cleanly to the route template. Fixing that precisely still needs a real route-capture mechanism (mirroring `AnnotateTenant`, for the matched pattern) that this foundational round does not build. Flag this explicitly before adding a parameterized route anywhere downstream of `Middleware`.

## Testing

Full runnable versions of `Init`, `FromContext`/`WithLogger` and `Middleware`/`AnnotateTenant` live in `example_test.go` (package `observability_test`, matching `pkgcore`'s and `dbkit`'s own `example_test.go` convention), each with an `// Output:` comment asserted against the real printed output — compiled **and executed** by CI, not just described in prose. `ExampleMiddleware` in particular is a second, independent negative-control proof (alongside `middleware_test.go`'s own) that two tenants calling the same route collapse into one metric series with no `tenant_id` label. `ExampleRedactedValue` demonstrates the redaction layer end to end: key-based replacement, in-place value-shape masking, and benign content passing through untouched.

The redaction contract has its own test file, `redact_test.go`: a 34-row sensitive-key table, correlation keys surviving verbatim, `With`/`WithGroup` attribute paths, a 16-case value-shape table (12 positive shapes, 4 negative controls), masking stability under re-processing, error values masked in place (never dropped whole), JSON-sink behavior, idempotent re-wrapping, and a concurrent logging test run under `-race`. The span-channel half lives in `middleware_test.go`'s `TestMiddleware_QueryStringSecrets_NeverReachSpanAttributes`.

`init_test.go`'s `TestInit_WithOTLPEndpoint_ExportsRealSpansAndMetricsOverOTLP` substitutes for a testcontainers-based OTel Collector integration test: no dedicated testcontainers-go module exists for the Collector, so it instead stands up a real gRPC server implementing the actual generated OTLP collector service interfaces (`go.opentelemetry.io/proto/otlp`) in-process, and proves an `Init` call supplying `WithOTLPEndpoint` — and nothing else, no deployment mode, since `Init` takes none — genuinely serializes and transmits a real span and a real metric to it. The same file's `TestInit_NoEndpoint_WiresWorkingLocalExporters` is the acceptance bar for the other half: a recorded request followed by a real Prometheus-format scrape from `MetricsHandler`. Neither needs Docker, so both stay in the regular unit-test set.
