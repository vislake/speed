# observability

The foundational layer only: OTel initialization whose exporter wiring is
chosen by the caller's options rather than any deployment mode, a
context-aware structured logger, and generic HTTP instrumentation. See
`docs/internal/09-observability.md` for the full design intent — including
the per-domain "must-instrument metrics" table (queue depth, metering
outbox lag, notification delivery rate, payment callback success, ...),
which belongs to the modules that own those domains (`jobs`, `metering`,
`notification`, `ai-gateway`), not to this package. Each of those
modules instruments its own row via
`otel.Meter` on its own package path, with this package supplying only
the global MeterProvider wiring: `go/jobs` (`queue_standalone.go`'s
queue-depth async gauge plus job-duration histogram, attempts and
dead-letter counters on `worker.go`'s real execution path), the
`queue/asynq` subpackage's queue-depth gauge, `go/notification`
(`delivery.go`'s delivery counter and duration histogram),
`go/metering`, `go/billing` (invoice transitions and open-dwell at the
module root, webhook-verify outcomes in each gateway provider) and
`go/ai-gateway` (per-provider calls/errors/duration plus rate-limit
hits) -- the instrumentation lives inline at those sites, never in a
`metrics.go` of this package. The domain table is each owning
module's obligation, never a reason for this package to speculatively
build their instrumentation for them.

## Component declaration (`component.go`)

The module declares its own assembly component, the shape every module
follows: `observabilityComponent` is registered into the global component
set by this package's `init` (`pkgcore.MustRegister`), so every binary
importing `go/observability` carries it — `go/app`'s `kernel.go` (the
pre-auth allowlist's `HealthzPath`/`MetricsPath`) among the importers,
which is how an engine-assembled host gets the component without any
package declaring it on the host's behalf. The engine loader's builtin
composition selects it by name `"observability"`, so it participates in
every assembly unless a higher layer deselects it.

The descriptor's schema (`observabilityConfig`) is exactly the two knobs
`Init`'s options take — `service_name` and `otlp_endpoint` — resolved
through the assembly's five-source chain like any component's block. Its
`Prepare` reads its own resolved block through `pkgcore.OwnComponentConfig`
(so a host that registered a renamed copy gets the copy's block, never a
stale literal lookup), calls `Init` with whichever option halves the block
set, and publishes the returned shutdown function as the runtime value its
`New` hands to the instance; its `Init` callback declares the module's
`Middleware` on the http component's middleware face
(`pkgcore.MiddlewareRegistrar`) — the platform's
one middleware layer outside the fixed chain — so an engine-assembled host
carrying the `http` component gets the
instrumentation applied around the whole chain (every request the chain
handles, including one authn or tenancy refuses) with no hand-wiring — the
declaration is optional, so a pure-background composition carrying no http
component simply leaves it unread
(see `pkgcore.MiddlewareRegistrar` for the face's boundary). A host
that composes a handler of its own with this component deselected — the
reference app's `BuildServer` drive — wraps `Middleware` itself.
`Close` shuts the providers down and flushes on a `context.WithoutCancel`
copy, so a cancelled drain context cannot cut the final export short. The
descriptor declares `MultiReplicaSafe` — each replica exports its own spans
and metrics — and carries no assets, and requires the middleware face
optionally (the dependency a serving composition satisfies with the `http`
component).

Its suite is `component_test.go` (internal `observability` package, the
same white-box placement as `factory_vars_test.go`): the init
self-registration, the descriptor contract (`componenttest.AssertWellFormed`),
the whole lifecycle through the registry's own stages (including the
`Middleware`-seat declaration its `Init` makes), the strict decode
refusal, the no-registered-exporter wiring refusal, the renamed-copy
overlay pin, and the `New`/`Close` refusals. What a successful `Init`
installs stays pinned by the external suite (`init_test.go`).

## Public API

### `init.go`

| Signature | Purpose |
|---|---|
| `func Init(ctx context.Context, opts ...Option) (func(context.Context) error, error)` | Wires a `TracerProvider` and `MeterProvider` and installs them as OTel's **global** providers (`otel.SetTracerProvider` / `otel.SetMeterProvider`), so `Middleware`, `FromContext`'s span lookup, and any module's own `otel.Tracer`/`otel.Meter` calls all reach them with no provider threaded through every call site. Which exporters get wired is decided solely by whether the caller supplied `WithOTLPEndpoint`: with a non-empty one, both signals are pushed over OTLP/gRPC to that endpoint; without one, the local exporters are wired. No deployment mode is passed or consulted — exporter selection is an implementation-composition question, never a mode question. Returns a shutdown function the caller must invoke during graceful process shutdown. Init may be called more than once: each successful Init tears down the provider pair the previous successful Init installed before returning, so a repeated Init cannot leak the earlier pair's exporters or background processors (the superseded shutdown func stays callable afterwards as a once-guarded no-op returning its first run's result -- `init.go`'s `onceShutdown`, pinned by `TestInit_SecondCall_TearsDownThePreviousProviders`); a failed Init leaves the previous pair untouched. An explicitly empty service name (`WithServiceName("")`) is refused with an error before any provider is built, since service.name is the required resource attribute every span and metric is tagged with (pinned by `TestInit_EmptyServiceName_Refused`) |
| `type Config struct { ServiceName, OTLPEndpoint string; OTLPInsecure bool }` + `Option` / `WithServiceName` / `WithOTLPEndpoint` / `WithOTLPInsecure` | `Init`'s tunables. `OTLPEndpoint` is deliberately **not** read from the environment by this package — see `Config.OTLPEndpoint`'s own doc comment for why: the module a real host wires up |
| `func MetricsHandler() http.Handler` | The `/metrics` handler the most recent `Init` call wired up: a real local scrape endpoint when `Init` wired the local exporters **and** a metrics reader was registered via `RegisterLocalMetricsReader`, a 404 explaining why not otherwise (OTLP exporters wired instead, no reader registered, or `Init` never ran) |
| `func RegisterOTLPExporters(f func(ctx context.Context, cfg Config, res *resource.Resource) (func(context.Context) error, error))` | The `database/sql`-style registration hook `Init` calls when `WithOTLPEndpoint` is non-empty. `go/observability/exporter/otlp`'s `init()` function is the one caller in a real binary; without that blank import, `Init` fails with an actionable error naming it. Single registration slot, last-registration-wins — see its own doc comment |
| `func RegisterLocalMetricsReader(f func() (sdkmetric.Reader, http.Handler, error))` | The matching hook for a **local, pull-based** metrics reader: `initLocalExporters` calls it, when registered, to wire a reader onto the `MeterProvider` and install `MetricsHandler`. `go/observability/exporter/prometheus`'s `init()` function is the one caller in a real binary; unregistered, `MetricsHandler` answers the not-configured 404 instead |

**The no-endpoint wiring's TRUE zero-dependency default is stdout only.** Traces go to stdout (`stdouttrace`, synchronous — no batching delay). Metrics go to stdout too (`stdoutmetric`, periodic, for a developer tailing the process). A local, pull-based Prometheus scrape endpoint at `MetricsHandler` is an **opt-in** addition on top of that default (see "Exporter isolation" below) — without registering one, `MetricsHandler` answers 404, naming the import that fixes it.

**Supplying `WithOTLPEndpoint` pushes both signals over OTLP/gRPC** (`otlptracegrpc` batched, `otlpmetricgrpc` periodic) to `Config.OTLPEndpoint`, via the constructor `go/observability/exporter/otlp` registers. Deployment mode plays no role in either wiring: a single-process assembly pointing at a real collector uses the OTLP exporters no less than a multi-replica deployment does, and the local exporters serve a multi-replica process that chose not to push just as they serve a single-process one.

## Exporter isolation (`exporter/otlp`, `exporter/prometheus`)

The two exporter families live in their own subpackages rather than in
this package's root, so a module calling `obs.FromContext()` purely for
logging never inherits `otlptracegrpc`/`otlpmetricgrpc` (and their own
gRPC/protobuf trees) or `github.com/prometheus/client_golang` (plus
`go.opentelemetry.io/otel/exporters/prometheus`). The split follows the
`database/sql` driver-registration pattern this repository's component
packaging also models — a backend implementation never sits
in the same package as the interface it implements — with a single
package-level registration slot per module rather than a name-keyed
registry, since this package ships exactly one implementation of each:

- **`exporter/otlp`** registers `RegisterOTLPExporters(buildProviders)` from its own `init()`. Blank-importing this subpackage is what makes `Init(ctx, WithOTLPEndpoint(...))` succeed instead of failing with `ErrOTLPExporterNotRegistered`.
- **`exporter/prometheus`** registers `RegisterLocalMetricsReader(buildReader)` from its own `init()`. `buildReader` returns the exporter (as an `sdkmetric.Reader` — pull-based, a fresh `promclient.NewRegistry()` per call, never `promclient.DefaultRegisterer`, for the "duplicate metrics collector registration" reason the original code documented) and its `promhttp.HandlerFor` handler, which runs with `promhttp.ContinueOnError`: one unscrapable series (an instrument the exporter cannot translate — an invalid-UTF-8 label value is one instance of the class) must cost only itself, never the whole scrape endpoint (pinned by `prometheus_test.go`'s `TestBuildReader_OneUnscrapableSeries_DoesNotVoidTheScrape`; the label-formation-side defense that keeps the route dimension from ever producing such a series is `Middleware`'s UTF-8 sanitization, above). The package's own declared name (`prometheus`) collides with `github.com/prometheus/client_golang/prometheus`, so that import is aliased `promclient` inside the file to keep the two apart.

**`MetricsHandler` answers 404 by default**: `Init`'s no-endpoint default does not wire a Prometheus scrape endpoint unless a host blank-imports `exporter/prometheus`. `examples/reference-app/internal/app/server.go` and `go/saasctl`'s generated-project template (`cmd/server/main.go`, which also blank-imports `exporter/otlp` for its `APP_OTLP_ENDPOINT` wiring) both do exactly that, which is why their `/metrics` routes serve real scrape output while no OTLP endpoint is set. Any other consumer relying on an unconditional default must add the same blank import; with an OTLP endpoint set, this package's own documented semantics apply — `/metrics` answers 404 by design, since no local registry is kept for scraping.

**Measured isolation** (the method the dependency-justification rule requires): a throwaway module requiring only `github.com/vislake/speed/go/observability`, `go mod tidy` under `GOWORK=off` — re-run the measurement to re-derive current counts; what the split removed from a logger-only consumer's `go.mod`/`go.sum` was the whole gRPC/protobuf stack, every Prometheus package, and both OTLP exporter packages, none of them reachable from the module's own build.

**`.golangci.yml`'s two depguard rules are the regression gate**, narrower than the redis/minio/asynq rules in one deliberate way: those three exempt their *owning module* (`!**/go/pkgcore/**`, `!**/go/jobs/**`), but `otlp-only-in-observability-exporter-otlp` and `prometheus-only-in-observability-exporter-prometheus` exempt only the *owning subpackage* (`!**/go/observability/exporter/otlp/**`, `!**/go/observability/exporter/prometheus/**`) — this package's own root files (`init.go` included) are **not** exempt, which is the whole point: an edit that imports either SDK back into the root package fails lint immediately, rather than silently reintroducing the coupling the split removes.

### `redact.go`

| Signature | Purpose |
|---|---|
| `const RedactedValue = "[REDACTED]"` | The deterministic marker every masked value becomes — the only form in which a secret ever reaches a sink |

**Redaction is on by default for every logger `FromContext` returns, with no per-call way to disable it** — the "must not be disableable from call sites" rule; audit-log redaction is a separate, unimplemented mechanism and out of scope here. The wrap happens once in `redactedLogger` (called by `FromContext`), not per sink: whatever handler a host plugs in, records pass through this layer first.

Two rules, applied at the attribute level:

- **Key-based.** An attribute whose key — or any segment of its key path, for group-nested attributes — case-insensitively **contains** one of `token`, `secret`, `password`/`passwd`/`pwd`, `authorization`, `cookie`, `credential`, `key` gets its **entire value** replaced by `RedactedValue`, regardless of the value's kind (string, number, struct, error, ...). Every stem but `token` and `key` matches by bare substring and deliberately errs on the side of over-redaction: a benign attribute whose key merely contains a stem (a `passwords` count field contains `password`, say) loses its whole value too, because an over-redacted field costs noise while a leaked secret costs a breach (the tradeoff rationale lives in redact.go's `sensitiveStems` comment). `token` alone matches at a word boundary instead (`stemMatches`/`foldContainsWordASCII`): a bare substring rule would also catch "tokens", the ordinary plural for an LLM/usage count (`prompt_tokens`/`completion_tokens`), silently swallowing that legitimate diagnostic field with no warning it had even run — the real case this repository hit, resolved by teaching the redactor the difference rather than renaming the fields: ai-gateway's `gateway.go` logs the counts under their natural `prompt_tokens`/`completion_tokens` names, which the word-boundary rule keeps clear. A match counts only when a word boundary flanks "token" on both sides: the segment's own start/end, a non-letter byte (`_` and the like), or a lowercase-to-uppercase case transition, the marker camelCase leaves between words (`wordBoundaryASCII`). `access_token`/`session_token_duration` and a bare `token` key still redact through the `_`/start-end boundary, camelCase compounds (`accessToken`, `tokenValue`) redact through their case transitions, run-together compounds whose stem is terminal redact through the suffix rule instead (`stemMatches`/`foldSuffixASCII` — `apitoken`, `accesstoken` and the acronym-prefixed `APIToken`/`JWTToken` carry no separator and no case transition at the join, but the stem is the compound's last morpheme, and nothing continues a trailing stem), and a key whose "token" is continued by a lowercase letter (`tokens`, `tokenizer_version`, `promptTokens`, `subtoken_count`, and run-together plurals like `prompttokens`, which end in "...tokens", never the bare stem) does not. `key` matches by the same two rules (`keyStemMatches`), for the mirror-image false-positive class: a bare substring match over-redacts this repository's own correlation fields, whose values an operator must see -- `key_id` (go/integration logs an API-key row's opaque id under it) and `credit_idempotency_key` (examples/reference-app's smilesim logs the derived key of an orphaned credit reservation under it, the value the log line exists for). Secret-shaped key names (`api_key`, `x_api_key`, `private_key`, `signing_key`, `secret_key`, dotted config segments like `stripe_secret_key`, run-together `apikey`, camelCase `apiKey`, bare `key`) all carry "key" as a whole word or terminal run-together suffix and still redact; only the two reference-shaped compound classes escape the key rule -- an `_id`-suffixed segment (a row reference, the naming convention `user_id`/`job_id` follow) and a terminal `idempotency_key` compound (this repository's idempotency-key naming convention: go/jobs' queue metadata, go/metering's outbox, go/billing's credit ledger and go/notification's delivery key all key one business-operation instance by a deterministic id derived from the operation's own identity, never random) -- and their values still pass through the value-shape net, because the exemption narrows only the "key" word stem, never the value net and never the PII boundary. The exemption does not rest on the value being safe by construction, either: of the four conventions the naming covers, only go/notification's delivery key is actually hashed -- go/jobs' is the enqueuing caller's own key text, embedded verbatim in its asynq TaskID, and go/metering's and go/billing's are the calling code's own -- so a caller embedding credentials or PII in a key puts that text under an exempted name, where the value net still masks a secret-shaped value in place (pinned name by name -- key_id and the idempotency_key-suffixed names alike -- by redact_test.go's `TestRedact_KeyStemDoesNotOverRedactCorrelationReferences`) and PII-shaped text passes as caller-declared content, its gate the owning module's field doc, go/jobs' `Task.IdempotencyKey` warning that its text rides verbatim into the logged JobID. An attribute with an **empty key** (slog's `slog.Group("", ...)` inline-group idiom) is never exempt from the value rules: its group children are still visited and its string/error values still scanned, since an empty key merely has no name to match (redact_test.go's `TestRedact_EmptyKeyAttributes_ValueRulesStillApply`) — and an empty-key attribute under a sensitive logger-level group path is not exempt from the PATH rule either: the group-name rule collapses it wholesale exactly as it does any other attribute there (redact_test.go's `TestRedact_EmptyKeyScalarUnderSensitiveGroupPath_RedactedWholesale`). The correlation fields `trace_id`, `span_id`, `tenant_id`, `user_id`, `job_id` are **never** redacted, so a user_id that happens to be JWT-shaped still logs verbatim (redact_test.go's `TestRedact_CorrelationKeysNeverRedacted`).
- **Value-shaped.** A string (or error-text) attribute under a benign key is scanned only when ≥16 bytes long, for the canonical Authorization-header and secret shapes: `Bearer <token>` and `Basic <base64>` credentials, JWTs (the `eyJ` header anchor), provider-prefixed keys (`sk_`/`pk_`/`rk_`/`sk-`, `AKIA`, `AIza`, `ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`/`github_pat_`, `xox*`, `glpat-`), URL query parameters whose names are unambiguous secrets (`access_token`, `api_key`, `client_secret`, `password`, `refresh_token`, `secret`, `session_key`/`session_token`, `sig`/`signature`, bare `token`) -- the parameter may sit at the very start of the scanned text, so a bare query string with no URL (the raw `r.URL.RawQuery`, a captured form body) is masked too -- and URL userinfo passwords, scheme case-insensitive (`HTTPS://user:pass@host` masks like its lowercase twin). Matching regions are replaced **in place** — surrounding text survives, so an error like `provider auth failed ... with Bearer [REDACTED]` stays readable — and masking is idempotent: re-scanning masked output is a fixed point (a value class that admits the marker's brackets — the URL query and userinfo classes do — re-matches only to reproduce it, never a new region). There is deliberately **no** generic "long random string" rule, and group/attr keys are only checked against the stems above — a JWT under `user_id` must survive by the exemption rule, not by luck.

**Coverage against the mandate is partial class by class, stated in redact.go's header.** The mandate names four classes — plaintext PII, keys and secrets, tokens, full prompts — never entering logs, traces or API responses. Against them, the key set above is exhaustive over the *credential and token naming vocabularies* by design — a new sensitive-named key in that class is a code-review point in `redact.go`, not a config question — while **plaintext PII and full prompts are class-level gaps**, recorded as such rather than omissions from the key list: their name space is large and grows with business code (an email, a phone, an address line, an LLM request body), so key-name matching is inherently incomplete against them, and no value shape separates them from ordinary identifiers. The caller declares what is sensitive instead — an explicit sensitive-parameter declaration shape (an apperr `WithSensitiveParam` twin) that is not implemented; until it exists, PII- and prompt-shaped log content is the logging call site's responsibility, and this layer stays the backstop for the credential classes, never the main line for those two. **Deliberate boundaries** (all documented in redact.go's header): the log *message* is never scanned; non-error struct values are never introspected; API **responses**, audit-log payloads (a known limitation) and dbkit's field-level encryption are separate mechanisms this module does not duplicate. `pkgcore.ComponentRegistry`'s `ConfigItem.Sensitive` marks config items for the config-reference/admin-console and has no redaction role — that flag and this key set are complementary, and redaction must work pre-registration, which is why it keys off names rather than registry markers.

**Mechanics kept honest** (see redact.go's own doc comment): slog carries `With`-attached attributes in the handler, not the record, so static attributes are redacted once in `WithAttrs` (before delegation, preserving the sink's formatting fast path) and `WithGroup` is mirrored so group names participate in key-path sensitivity; `Handle` then only scans the record's own attributes, forwarding unchanged records with zero allocation (a claim scoped to scalar attribute values — a benign `slog.Group` costs a few allocations per nesting level; see redact.go). Two contract points follow: (1) `FromContext` never returns the exact `*slog.Logger` `WithLogger` attached — the redaction layer always sits between, so a `WithLogger`-attached logger must be built as `slog.New(handler)` with no `With`-attached attributes (they would bypass the layer); static attributes belong on the `FromContext` result instead. (2) A hand-built `slog.Logger` logged through directly, outside `FromContext`, is the documented deliberate escape; this module's own rules confine that construction site to the genuinely context-less sites a hand-built logger is legitimate at — process startup above all (see `WithLogger`'s doc comment). The context logger is only required where a context exists. Guarded, not assumed: user code reachable from attribute rendering is recover-guarded, so a panicking value can never crash the logging path.

**The span channel.** This module's span attributes are kept free of secret-shaped material *by construction* rather than by a second redaction pass, and every request-controlled string on the span is exporter-safe by construction: `Middleware`'s own span attributes are method/route/status/tenant only, the span's `http.route` attribute and the span NAME both carry the metric side's bounded route value — never the raw path, whose segments carry tenant and resource ids into the tracing backend (see the `Middleware` row below and `TestMiddleware_SpanRouteAttribute_MatchesTheMetricRouteLabel`) — and the query string, where credentials ride, never becomes a span name or attribute at all: every span surface derives from `URL.Path`, from which net/http has already split the query (otelhttp's own server-span semconv omits `url.query`/`url.full` by design). The raw strings otelhttp's own semconv attaches at span creation — `url.path` (which keeps the ACTUAL path under the route label's length and UTF-8 bounds, so per-request search survives), `user_agent.original` and `client.address` — are overwritten by `Middleware` with those bounded copies, because an invalid-UTF-8 byte in any of them (net/http percent-decodes the path byte-wise and applies no byte validation to header values) fails the proto3 marshal of the whole OTLP export batch: the failure class that forced the span NAME off the raw path too (see `Middleware`'s own "Why no span surface carries the raw request path" section). All of that is pinned by negative controls and the invalid-byte regressions (`middleware_test.go`'s `TestMiddleware_QueryStringSecrets_NeverReachSpanAttributes`, `TestMiddleware_SpanRouteAttribute_MatchesTheMetricRouteLabel` and `TestMiddleware_InvalidUTF8Request_SpanNameAndAttributesCarryNoRawByte`, plus exporter/otlp's `TestMiddleware_InvalidUTF8Request_ExportBatchStillArrives`) rather than trusted by assumption, so a future otelhttp upgrade or a code edit that starts naming spans from `URL.String()` fails the build instead of leaking silently.

### `middleware.go`

| Signature | Purpose |
|---|---|
| `func Middleware(next http.Handler) http.Handler` | Wraps `next` to start a request span (via `otelhttp`) and record `http.server.request.count` / `http.server.request.duration`, labeled **only** by method, route and status code. The recording block runs in a defer, so a handler that panics (recovered above the chain, by `net/http`'s per-connection recovery) is still counted, under the 500 this middleware records for a response that never reached the client, with an error-status span. Both attacker-controlled label dimensions are bounded before they reach an instrument (see the caveat below): the method label is collapsed to the nine standard `net/http` methods plus the fixed `MethodLabelOverflowValue`, and the route label is capped at `MaxRouteLabelValues` distinct values, `MaxRouteLabelLength` bytes each, and valid-UTF-8-only (path bytes that percent-decode to invalid UTF-8 are replaced with the Unicode replacement rune before a label value is formed -- an invalid-UTF-8 label value makes the Prometheus exporter refuse the series, which would void the whole /metrics scrape). Instrument-construction errors are routed to OTel's global error handler rather than dropped. The span's method attribute keeps the exact raw request-line token, but its route attribute is NOT exempt from the route bounds: it shares the metric side's bounded route value — `routeLabels.label(...)` computed once per request and fed to both — so a request below a seeded mount carries the mount label on the span too, a path past the distinct-value budget carries `{overflow}`, and every value is length-bounded and UTF-8-valid. A trace is not a Prometheus series, but it IS an exit of the data-protection rule, and raw path segments carry tenant and resource ids into the tracing backend; the bounded route value is the disclosure bound on the span (see `TestMiddleware_SpanRouteAttribute_MatchesTheMetricRouteLabel`). The span *name* (method + the same bounded route value, via the otelhttp formatter) is under the same bound — the raw path was its residual until the invalid-byte class made that an availability defect (see the invalid-byte regressions named in the span-channel section above) — and `url.path` is the one span surface that keeps the actual path, bounded and UTF-8-safe (see `Middleware`'s own "Why no span surface carries the raw request path" section) |
| `func AnnotateTenant(ctx context.Context)` | Records the tenant carried by `ctx`, if any, as a `tenant_id` attribute on `ctx`'s active span. No-op with no tenant or no span |
| `const MaxRouteLabelValues int` / `const RouteLabelOverflowValue string` | The route-label cardinality bound and its overflow sentinel (`"{overflow}"`) — exported so `middleware_test.go`'s negative control, and any consumer auditing this behavior, checks the actual enforced values rather than a hardcoded guess |
| `func RegisterMountedRoutes(routes []pkgcore.MountedRoute)` | The host-side registration that lets the route limiter every `Middleware` constructs survive first-come-first-served pre-emption: call it once at assembly time with the application's real route table (the `pkgcore.MountedRoute` values the assembly's http component accumulated through its route face -- `httpserve.Face.Routes()` -- plus any host-level routes the host mounts directly), and every `Middleware` built afterward seeds its limiter with those entries before any request traffic can exhaust the distinct-value budget. Every entry is a mount PREFIX (`pkgcore.MountedRoute.Path` is "the prefix the handler was mounted at"), so each is seeded as the label of its whole mount subtree: a request at or below a seeded path is labeled with the seeded path itself (net/http ServeMux subtree semantics), which both keeps a real operation requested only after the budget is exhausted on its own measurable series -- under its mount's label, never `RouteLabelOverflowValue` -- and makes garbage sent below a real mount unable to mint a label or consume a budget slot at all. The label's granularity ceiling is the mount: every template under one prefix shares the prefix as its label, the closest the limiter gets to route-template folding without a real route-capture mechanism; a route the host did not register (added after the call) is not covered and stays subject to the ordinary bounded behavior. Without the seed, an attacker sending `MaxRouteLabelValues` distinct garbage paths right after startup collapses every genuine route to `RouteLabelOverflowValue` for the process lifetime. Last registration wins; an empty list clears the seed. `examples/reference-app` is the mandatory first consumer -- the http component's Serve assembly calls it with the module table it accumulated plus the liveness routes `/healthz` and `/metrics`, driven through the real composed stack by `flowtests/obs_route_seed_test.go`; the mechanism's own behavioral proofs are `middleware_test.go`'s `TestMiddleware_RealRoutesSurviveGarbage_WhenSeeded`, `TestMiddleware_RealRoutesBelowSeededPrefixes_SurviveStartupGarbage` (the deep-operation-under-a-prefix regression) and `TestMiddleware_SeededMountPrefix_FoldsRequestsAtOrBelowIt` |
| `const MaxRouteLabelLength int` | Bounds, in bytes, the length of any single `http.route` value before `routeLabelLimiter` uses it as a map key or hands it back as the metric label value — an orthogonal bound to `MaxRouteLabelValues` (which caps distinct-value COUNT, not size): closes a narrower, higher-cost resource-exhaustion vector where a bounded number of very long attacker-controlled paths could still bloat the limiter's map and the exported Prometheus series. See `middleware_test.go`'s `TestMiddleware_LongRoutePaths_LabelLengthIsBounded` for the negative control |
| `const MethodLabelOverflowValue string` | The method-label cardinality sentinel: `"_OTHER"` — the OpenTelemetry semantic-convention reserved value for a method outside its known enum — into which `methodMetricLabel` folds every `http.request.method` metric label that is not one of the nine standard `net/http` methods, exported so `middleware_test.go`'s negative control, and any consumer auditing this behavior, checks the actual enforced value rather than a hardcoded guess. Ships no accompanying count or length cap by design — the collapse is a fixed set-match that retains nothing of the attacker's token, unlike the route limiter's seen-map (see the caveat below) |

**Hard rule, enforced by construction, not just documented: `tenant_id` never becomes a metric label.** `Middleware`'s metric-recording code path never reads `pkgcore.TenantFromContext` at all. See `middleware_test.go`'s `TestMiddleware_MetricsExcludeTenant_NoPerTenantSeries` for the negative control: two tenants' requests collapse into one series, and no gathered metric family ever carries a `tenant_id` label. Tenant correlation instead goes to span attributes (`AnnotateTenant`) and structured log fields (`FromContext`), both of which Tempo/Loki tolerate at high cardinality.

**`Middleware` is meant to be mounted OUTSIDE `tenancy.Middleware`**, per the fixed chain order (`recover -> request-id/log-context -> observability -> tenancy.Middleware -> ...`, "not to be casually adjusted"). `tenancy.Middleware`'s own doc comment says nothing about tracing middleware specifically, so that fixed order is the tie-breaker — see `examples/reference-app/cmd/server/main.go`'s `run` for the actual wiring and the same reasoning repeated at the call site. The cost of that position: a tenant is not yet known at `Middleware`'s own layer (Go's `http.Handler` chain propagates request state strictly downward — `tenancy.Middleware`'s `(*http.Request).WithContext` fork is invisible back up the chain), which is exactly why `AnnotateTenant` exists as a separate function business handlers (or `authn.Middleware` / `rbac.RequirePermission`) call once a tenant is actually resolved — a trace `Span`, unlike a plain context value, is a shared mutable object that survives that fork.

**Metric-label cardinality caveats.** Two of the three metric labels — `http.route` and `http.request.method` — are derived from request inputs an unauthenticated caller controls verbatim, and each is bounded against the cardinality-explosion failure mode the tenant_id rule targets before it can feed an instrument (the third, `http.response.status_code`, is a small bounded integer by construction). The two bounds together cap this metric's series growth at a small fixed multiple — (9 standard methods + 1 overflow) x (`MaxRouteLabelValues` + 1 overflow) x status codes per `Middleware` instance — while the span's method attribute keeps the exact raw token for trace-side correlation; the span's route attribute, by contrast, shares the bounded route value (a trace is still an exit of the data-protection rule — see the route-dimension paragraph below). Each dimension has its own paragraph below.

**The route dimension.** The route label is derived from `URL.Path`, not the lower-cardinality `(*http.Request).Pattern` `net/http.ServeMux` (Go 1.22+) populates on a match: `Pattern` suffers the identical fork-visibility problem `AnnotateTenant`'s doc comment describes for the tenant. This is not only a future-parameterized-route risk: it is exploitable *today*, by any unauthenticated caller, via a plain mux 404 or `tenancy.Middleware`'s own pre-mux 403 (an unrecognized `Host`) — neither requires a valid route or credential, and both still reach `Middleware` with the caller's raw path untouched. `Middleware` therefore runs the route label — the span's `http.route` attribute included, which shares the limiter's result (the bounded value is the disclosure bound on the span: raw paths carry tenant and resource ids into the tracing backend, and a trace is an exit of the data-protection rule; see `TestMiddleware_SpanRouteAttribute_MatchesTheMetricRouteLabel`) — through a small in-package limiter that tracks up to `MaxRouteLabelValues` distinct values and collapses anything past that into the fixed `RouteLabelOverflowValue`, so an attacker can never grow the route dimension past `MaxRouteLabelValues`+1 distinct values no matter how many distinct paths they send. See `middleware_test.go`'s `TestMiddleware_UnboundedRoutePaths_CardinalityIsBounded` for the negative control. Capping distinct-value COUNT alone does not cap value SIZE: `examples/reference-app`'s `http.Server` sets no `MaxHeaderBytes`, so it inherits `net/http.DefaultMaxHeaderBytes` (1 MiB) as the effective ceiling on a single request's URL length, meaning an attacker could still send up to `MaxRouteLabelValues` distinct, near-1-MiB paths and make both `routeLabelLimiter`'s internal map and the exported Prometheus series themselves retain attacker-controlled data on that order. `Middleware` therefore also truncates every value (`truncateRouteLabel`, cutting on a UTF-8 rune boundary) to at most `MaxRouteLabelLength` bytes before it can become a map key or a label value — an orthogonal bound to the count cap: truncation can only collapse distinct long values together, never increase how many distinct values `routeLabelLimiter` tracks. See `TestMiddleware_LongRoutePaths_LabelLengthIsBounded` for that negative control. A third bound guards value VALIDITY: a path whose percent-decoded bytes are not valid UTF-8 (net/http percent-decodes byte-wise, so `%FF` reaches this middleware as a raw invalid byte with no parse error) would hand the Prometheus exporter a label value it refuses to encode on every Gather -- the entire /metrics scrape answers 500 with zero metrics for the process lifetime, an unauthenticated DoS the count and length caps never covered. `Middleware` therefore replaces invalid byte runs with the Unicode replacement rune before a label value is formed (`sanitizeRouteLabel`; the request is still counted, under the sanitized label), and the exporter-side half of the same defense runs `promhttp.ContinueOnError` so one unscrapable series costs only itself (exporter/prometheus, pinned by `TestBuildReader_InvalidUTF8Path_NeverVoidsTheScrape` and `TestBuildReader_OneUnscrapableSeries_DoesNotVoidTheScrape`). Separately, the limiter is seeded at construction from whatever route table the host registered via `RegisterMountedRoutes`, so attacker garbage arriving right after startup cannot exhaust the distinct-value budget and collapse real routes to `{overflow}` before they are ever requested (`TestMiddleware_RealRoutesSurviveGarbage_WhenSeeded`). Because every seed is a mount PREFIX rather than the full path of any one operation (`pkgcore.MountedRoute.Path` is "the prefix the handler was mounted at"), a seed protects its whole mount subtree, not just the request whose whole path equals it: a request at or below a seeded path is labeled with the seeded path itself, so a genuine operation path deeper than its mount -- `/api/v1/authn/login/password` under the `/api/v1/authn` prefix -- keeps a measurable series under its mount's label even when requested only after the budget is exhausted, and garbage sent below a real mount can neither mint a label nor consume a budget slot (`TestMiddleware_RealRoutesBelowSeededPrefixes_SurviveStartupGarbage` pins the deep-route case with the two prefix==path controls the earlier regression already pinned, `TestMiddleware_SeededMountPrefix_FoldsRequestsAtOrBelowIt` the subtree boundary and most-specific-mount matching). This bound is a circuit breaker, not a precision fix: the coarse route-template folding the seeding delivers is at mount granularity, so a parameterized route below a seeded mount (e.g. `/api/v1/billing/subscriptions/{id}` under `/api/v1/billing`) no longer burns the cap one ID at a time -- every ID folds onto the mount label -- but distinct templates under one mount share that one label, losing template-vs-template distinction (`/api/v1/notes/{id}` and `/api/v1/notes/{id}/comments` are indistinguishable), and a route the host did not register is not covered and still records one distinct value per distinct request path up to the cap before falling back to the overflow bucket. True per-template folding would need a real route-capture mechanism (mirroring `AnnotateTenant`, for the matched pattern), which is not built — flag that gap explicitly before adding a parameterized route anywhere downstream of `Middleware`.

**The method dimension.** The `http.request.method` label has the identical hole, one dimension over: it is fed by `(*http.Request).Method` — the request line's raw method token, which net/http accepts from any caller with no set constraint, no normalization and no truncation (RFC 7230 token characters only, but that still leaves the token space effectively unbounded) — and the same pre-auth 404s and 403s the route exploit uses reach the metric-recording code with the raw token untouched. Bounding the route dimension while leaving this sibling raw would only be a half-fix: an attacker sending one distinct token per request would still mint one new, permanent series per token, multiplied against the (bounded) route and status dimensions. `Middleware` therefore runs the metrics' method label (only the metrics' — the span's method attribute stays the exact raw token; the route half's mirror-image raw-path exception was closed when the span's route attribute aligned onto the bounded route value) through the pure, state-free `methodMetricLabel`, which records the nine standard `net/http` method constants (`MethodGet` through `MethodTrace`) verbatim — exact, case-sensitive matching, per RFC 7230's method-token rules — and folds every other token, attacker-chosen or merely exotic, into the single fixed `MethodLabelOverflowValue` (`"_OTHER"`, OTel semconv's own reserved collapse value for a method outside its known enum). Unlike the route half, no distinct-value COUNT cap and no per-value LENGTH bound accompany the collapse, and none is bolted on: `routeLabelLimiter` must retain every seen path as a map key for the process lifetime, which is exactly why its two bounds exist, while a fixed set-collapse never retains the attacker's token at all, so this dimension contributes at most 10 distinct values per `Middleware` instance with constant memory, whatever token is sent. The bound is exact rather than a circuit breaker: the known set is complete by construction, so the method dimension never loses per-token granularity the way a route past the cap does. See `middleware_test.go`'s `TestMiddleware_UnboundedMethodTokens_CardinalityIsBounded` for the negative control: 100 distinct attacker-chosen tokens plus the case-mismatched near-miss `"get"` and the non-standard-but-legal `PROPFIND`/`PRI` all fold into the overflow bucket, GET still records its exact token, and the emitted label set is exactly the nine standard methods plus the overflow value.

## Testing

Full runnable versions of `Init`, `FromContext`/`WithLogger` and `Middleware`/`AnnotateTenant` live in `example_test.go` (package `observability_test`, matching `pkgcore`'s and `dbkit`'s own `example_test.go` convention), each with an `// Output:` comment asserted against the real printed output — compiled **and executed** by CI, not just described in prose. `ExampleInit` blank-imports `exporter/otlp` (exactly the import a real host wanting OTLP export adds) so its `WithOTLPEndpoint` call succeeds. `ExampleMiddleware` is a second, independent negative-control proof (alongside `middleware_test.go`'s own) that two tenants calling the same route collapse into one metric series with no `tenant_id` label — built on a bare `sdkmetric.ManualReader`, needing no exporter package at all, per the "Exporter isolation" section above. `ExampleRedactedValue` demonstrates the redaction layer end to end: key-based replacement, in-place value-shape masking, and benign content passing through untouched.

`middleware_test.go`'s whole suite gathers metrics through a `sdkmetric.ManualReader` (`setupMeterProvider`/`collect`/`findMetric`/`findSum`/`findHistogram`) rather than a Prometheus registry, for the identical isolation reason: this package's own tests must not import `github.com/prometheus/client_golang` any more than its production code may, or the depguard rule described above would fail its own module's tests. The metric names and attribute keys asserted on are therefore the raw OTel ones (`http.server.request.count`, `http.request.method`, ...), not the underscore-and-suffix form a Prometheus exporter would translate them into — a ManualReader has no such translation layer, and none of this file's assertions depend on one.

The redaction contract has its own test file, `redact_test.go`: a 34-row sensitive-key table, a `token`-stem over-redaction regression (`prompt_tokens`/`completion_tokens`/`tokens`/`tokenizer_version` surviving unredacted, `TestRedact_TokenStemDoesNotOverRedactUnrelatedWords`), a two-direction adversarial vocabulary over the word-boundary and terminal-suffix rules (`TestRedact_TokenStemWordBoundary_AdversarialVocabulary` — benign continuation words in both separator styles plus the run-together plurals `prompttokens`/`sessiontokens`, every secret-shaped "token" key, camelCase compounds like `accessToken`/`tokenValue` and terminal run-together compounds like `apitoken`/`APIToken` included), correlation keys surviving verbatim, `With`/`WithGroup` attribute paths, a 16-case value-shape table (12 positive shapes, 4 negative controls), masking stability under re-processing, error values masked in place (never dropped whole), JSON-sink behavior, idempotent re-wrapping, and a concurrent logging test run under `-race`, and an empty-key scalar under a sensitive logger-level group collapsing wholesale exactly as a non-empty key there does (`TestRedact_EmptyKeyScalarUnderSensitiveGroupPath_RedactedWholesale`). The span-channel half lives in `middleware_test.go`'s `TestMiddleware_QueryStringSecrets_NeverReachSpanAttributes`.

`init_test.go` blank-imports `exporter/otlp` so its own `WithOTLPEndpoint` tests succeed against a registered factory, exactly like a real host would. `TestInit_WithOTLPEndpoint_ExportsRealSpansAndMetricsOverOTLP` substitutes for a testcontainers-based OTel Collector integration test: no dedicated testcontainers-go module exists for the Collector, so it instead stands up a real gRPC server implementing the actual generated OTLP collector service interfaces (`go.opentelemetry.io/proto/otlp`) in-process, and proves an `Init` call supplying `WithOTLPEndpoint` — and nothing else, no deployment mode, since `Init` takes none — genuinely serializes and transmits a real span and a real metric to it. It needs no Docker, so it stays in the regular unit-test set. `TestInit_NoEndpoint_MetricsHandlerIsNotConfiguredByDefault`, in the same file, is the acceptance bar for the OTHER half post-split: with nothing but this package's own tests loaded (never `exporter/prometheus`), `MetricsHandler` must answer 404 even on the no-endpoint (local exporters) path — a test built specifically to fail the moment this package's own test suite ever gains a transitive dependency on the opt-in subpackage it exists to keep optional.

The opted-**in** counterpart — a recorded request followed by a real Prometheus-format scrape from `MetricsHandler` once `exporter/prometheus` is blank-imported — moved to that subpackage's own `prometheus_test.go` (`TestBuildReader_WiresWorkingLocalMetricsEndpoint`, `TestBuildReader_MetricsHandlerIsIsolatedAcrossCalls`, the latter re-proving the fresh-registry-per-call design never panics with "duplicate metrics collector registration" across repeated `Init` calls in one process), plus a runnable `Example` there. `exporter/otlp` carries its own runnable `Example` too, proving the registration succeeds end to end against a real (fake) OTLP collector, and its `TestMiddleware_InvalidUTF8Request_ExportBatchStillArrives` — the export-side half of the span invalid-UTF-8 regression (the middleware-side half lives in `middleware_test.go`) — drives `Init` + `Middleware` against an in-process OTLP/gRPC collector and asserts the batch really encodes and arrives when the request path and headers carry an invalid UTF-8 byte (without the bound the proto3 marshal fails and otlptracegrpc drops the whole batch).

`Init`'s negative OTLP path — `WithOTLPEndpoint` supplied with `otlpFactory` still nil — has no test in this package's own binary or in `exporter/otlp`'s, because both blank-import `exporter/otlp` for their own success-path tests, which as a side effect leaves `otlpFactory` registered for every test sharing that binary. It is instead proven in `exporter/prometheus`'s own test binary (`otlp_not_registered_test.go`'s `TestInit_WithOTLPEndpoint_WithoutRegisteredExporter_FailsActionably`), the one binary in this module that imports `exporter/prometheus` but never `exporter/otlp`, so `Init` there genuinely calls into a nil factory and returns the exported `ErrOTLPExporterNotRegistered` (exported specifically so this cross-package test, and any real caller, can assert on it with `errors.Is` rather than matching its message text). The local-metrics-reader default-behavior break gets the mirroring treatment: `initLocalExporters` now logs a one-time `slog.Default().Warn` naming both fixes when `metricsReaderFactory` is nil, on the same non-fatal startup-banner convention `go/pkgcore`'s `warnIfNotDurable` uses, pinned by `init_test.go`'s `TestInit_NoEndpoint_NoLocalMetricsReader_LogsStartupWarning`. Repeated-Init semantics are pinned twice over: `TestInit_SecondCall_TearsDownThePreviousProviders` proves a second Init without a first shutdown flushes and closes the superseded pair (the pending span reaches the fake collector) and that both shutdown funcs remain callable with no goroutines left behind, and `TestInit_EmptyServiceName_Refused` proves `WithServiceName("")` fails Init before any provider is built.
