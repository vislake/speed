# pkgcore

The dependency floor of the monorepo. Every other Go module imports it; it imports no other speed module.

It owns eight things and nothing else:

| Concern | Where |
|---|---|
| The `Module` / `Registry` / `Kernel` wiring contract | `registry.go` |
| Tenant context, and the raw system-context marker (`WithSystemContext`/`SystemReasonFromContext`; the audited wrapper around it lives in `go/tenancy`) | `tenant.go` |
| Infrastructure seam interfaces (`KVStore`, `EventBus`, `Mailer`, `ObjectStore`) plus each one's in-process implementation and its SMTP-backed one (stdlib `net/smtp`, so it earns no dependency-isolation benefit from a subpackage) | `kv.go`, `eventbus.go`, `mailer.go`, `objectstore.go`, `smtp_mailer.go` |
| The shared outbound-SMS contract (`SMS`, `SMSSender`) plus its console implementation and its operator-gateway one (both stdlib-only, so neither earns a dependency-isolation benefit from a subpackage) -- an infrastructure seam like `Mailer`, but deliberately NOT kernel-resolved: no registry, preset or capability declarations exist for it, because no consumer takes its SMS transport from the kernel (see `sms.go`'s own doc comment) | `sms.go`, `http_sms_sender.go` |
| The capability/registry/preset machinery `Kernel.Bootstrap` resolves and validates every seam through, and the five in-process/SMTP built-in `Registration`s the seam built-in files pre-populate (the eight distributed built-ins register themselves from their own subpackages -- see below) | `capability.go`, `seam_registry.go`, `preset.go`, `eventbus_builtins.go`, `kv_builtins.go`, `mailer_builtins.go`, `objectstore_builtins.go`, `registries.go` |
| The merged backend message catalog, assembled by `Bootstrap` from every module's `Locales()` embed.FS | `i18n/` (+ `locales/`, pkgcore's own seed message files) |
| The `DeploymentMode` enumeration (a topology declaration only -- see "Deployment mode and implementation composition" below) | `deployment_mode.go` |
| The mandatory conformance suite for each seam, and the two conformance runs of every in-process/SMTP built-in implementation | `eventbustest/`, `kvstoretest/`, `mailertest/`, `objectstoretest/` (suites); `*_conformance_test.go` (runs; the SMTP leg needs no Docker, see below) |

Three subpackages: `apperr` (the structured application error every module returns), `config` (the bootstrap configuration loader, run once at process startup) and `i18n` (the message catalog backend-generated content is rendered through, on nicksnyder/go-i18n). `locales/` carries pkgcore's own seed messages, which pkgcore's test suites feed through the catalog as its fixture and which serve as the canonical shape example -- pkgcore is not a Module, so nothing in a running application reads them (see the `pkgcore/locales` section).

A further subpackage, `probe`, serves a host's own process shell rather than a seam and is stdlib-only: it issues one container self-probe, a GET request to the process's own HTTP server over loopback -- the HEALTHCHECK pattern a distroless-style image with no shell, no curl and no wget runs by re-invoking its own binary with a sentinel argument. Its loopback host is structural (`Check` dials 127.0.0.1 and nothing else, so the port and path its caller passes can only select which local listener is probed), while everything environment-shaped stays the host's own (which variable holds the port, what an empty port falls back to, which argument diverts the entry point): the package reads no environment variable and carries no port fallback.

Another subpackage, `spa`, serves a built single-page frontend from a directory on disk in front of a host's composed handler: GET/HEAD only, a caller-declared allowlist of server-owned paths (`WithServerPath` for exact paths, `WithServerPrefix` for whole-segment prefixes) that always pass through, the index.html fallback for unknown client routes with a real 404 for a miss under the content-addressed asset prefix, a cache policy keyed on that prefix (`WithAssetPrefix`, defaulting to vite's `assets`; the immutable/no-cache split its package doc comment explains), and a root pinned to an absolute path at construction whose request paths are root-pinned, cleaned and `filepath.IsLocal`-checked before any open. Its package doc comment carries the full contract, including the two file-system decisions that ship with it: a symlink inside the root pointing outside it is followed exactly as net/http's own file server follows one (the directory is the operator's own built output, and guarding symlinks in it would be defending the deployer against themselves), and a root that does not exist is not a construction error -- the handler degrades to 404s for its own surface while every declared server path keeps passing through, so a host can mount it before its dist exists.

Four more subpackages carry the Redis-, S3- and PostgreSQL-backed built-in implementations -- `eventbus/redis` (`EventBus`'s distributed-mode implementation on Redis Streams, registering `"eventbus.redis"`), `eventbus/postgres` (`EventBus`'s OTHER distributed-mode implementation, on PostgreSQL `LISTEN`/`NOTIFY` backed by a durable outbox table, registering `"eventbus.postgres"` -- the genuinely zero-extra-infrastructure option for a deployment that already runs PostgreSQL and does not want to stand up Redis purely for this one seam; see its own package doc comment and `EventBus`'s delivery-semantics note for the full contract, and this file's Public API table below), `kv/redis` (`KVStore`'s, registering `"kv.redis"`), and `objectstore/s3` (`ObjectStore`'s, on any S3-compatible service, registering `"objectstore.s3"`) -- each in its own subpackage because Go resolves dependencies per package: a consumer of this root package must not inherit go-redis, jackc/pgx or minio-go merely by importing `pkgcore` (see this file's own Rules section). Each subpackage self-registers its implementation on the matching package-level `SeamRegistry` through its own `init()`, the `database/sql` driver pattern `seam_registry.go` was already modelled on; a distributed-mode host that wants a built-in Redis, PostgreSQL or S3 implementation through `WithPreset` must import the matching subpackage (a blank import is enough) and, for `eventbus/postgres` specifically, name it in a Preset of its own -- `PresetDistributed` still points the `"eventbus"` seam at `"eventbus.redis"`, unchanged by this addition -- or resolution fails at `Bootstrap` time with `ErrUnknownImplementation` naming the seam and implementation -- the accepted "compile-time error becomes a run-time one" trade every `database/sql` driver makes. Calling a subpackage's own constructor directly and wiring it with `WithEventBus`/`WithKVStore`/`WithObjectStore` needs no import-for-side-effect at all, since that path never goes through the registry. Each subpackage carries its own unit tests, its own `example_test.go`, and its own `integration_test/` (Docker-backed, `-tags=integration`) -- physically separate per package, per this repository's testing-layout rule, not shared with this package's own (Docker-free) unit tier. `eventbus/postgres` additionally carries its own `migrations/postgres/` (a single versioned SQL file for its outbox and cursor tables, embedded and applied through its own `EnsureSchema` rather than `dbkit.MigrationRegistry` -- this package cannot import `go/dbkit`, which sits above it in the dependency graph, so it cannot use that machinery directly; see the migration file's own doc comment) and no `migrations/sqlite/` sibling at all, a deliberate, documented exception (see that file's own header) since the mechanism is inherently PostgreSQL-specific and the standalone deployment mode never runs it.

A fifth subpackage, `eventbus/nats`, is a third distributed-mode `EventBus` implementation, following the identical split and registering `"eventbus.nats"` the same way. It is not part of either built-in `Preset` (`PresetDistributed`'s `"eventbus"` entry still names `"eventbus.redis"`); a host that wants it calls `EventBusRegistry.Build("eventbus.nats", cfg)` or `NewEventBus` directly with `WithEventBus`. Delivery semantics are deliberately identical to `eventbus/redis`'s -- fan-out to every replica, never load-balanced to one -- reached through JetStream's durable pull consumers instead of Redis consumer groups: every bus instance creates its own uniquely-named consumer on each event type's stream, so JetStream's own load-balancing (which only applies between two readers of the *same* consumer name) never triggers between instances. See the package's own doc comment for the full contract and its `integration_test/`'s `TestEventBus_FanOutDeliversToEveryReplica` for the real-server proof.

`kv/postgres` is a sixth such subpackage, registering a *second* implementation of a seam an earlier subpackage already covers — the `"kv"` seam's second, after `kv/redis`: `KVStore` backed by a single PostgreSQL table (`pkgcore_kv_entries`) with a TTL column, registering `"kv.postgres"` on the same `KVStoreRegistry` `kv/redis` registers `"kv.redis"` on -- the genuinely zero-extra-infrastructure option for a deployment that already runs PostgreSQL and does not want to stand up Redis purely for this one seam, mirroring `eventbus/postgres`'s identical rationale for the `EventBus` seam. `PresetDistributed` still points `"kv"` at `"kv.redis"`; a host wanting `"kv.postgres"` instead names it in a `Preset` of its own -- the entry's `Config` carries the `dsn` and the registration builds (and owns) its own pool -- or shares an existing pool by bypassing the preset layer with `kv/postgres.NewKVStore(pool)` and `WithKVStore`. `NewKVStore` takes a `*pgxpool.Pool` directly (never a `*gorm.DB`), so a host already running `dbkit.Open` for its business tables shares the exact same connection credentials at the cost of one small, dedicated second pool rather than reaching into `dbkit`'s own internals for one. Both `IncrByFloat` and `CompareAndSwap` are single, database-arbitrated SQL statements -- an `INSERT ... ON CONFLICT DO UPDATE` upsert for the former, a `WITH` CTE combining an `UPDATE` (the "key exists" path) and an `INSERT ... ON CONFLICT DO NOTHING` (the "key genuinely absent" path) for the latter -- never a Go-level read-modify-write, proved race-free under real concurrent callers by the package's own `TestKVStore_ConcurrentIncrementsLoseNoUpdates` and `TestKVStore_ConcurrentCompareAndSwapSetIfAbsent_ExactlyOneWinner` in its `integration_test/` tier, the same discipline `go/billing`'s `applyBalanceDelta` established for its own single-`UPDATE` arithmetic guard. Unlike `kv/redis` (Redis's native active expiry), PostgreSQL has no equivalent: every read and write treats an expired row as absent (a `WHERE expires_at IS NULL OR expires_at > now()` guard, the same read-side treatment `pkgcore.memoryKVStore` gives an expired entry) but does not physically remove it until something touches the key again or a host calls the package's own `Store.Sweep` -- a plain, one-shot `DELETE` a host runs on its own schedule (no owned goroutine, no automatic call from `NewKVStore`), which is why `NewKVStore` returns the concrete `*Store` rather than the bare `pkgcore.KVStore` interface: `Sweep` is a capability outside what `KVStore` itself has room for. The two stores' reclamation entries differ because their state's lifetime differs: rows in a table outlive the process and are shared across replicas, so the physical reclamation is a host-run, concurrency-safe `Sweep`; `memoryKVStore`'s map dies with the process, so it sweeps itself -- an amortized pass every 1024 write operations reclaims expired entries nothing ever touches again. `pkgcore_kv_entries`' migration (`migrations/postgres/0001_create_pkgcore_kv_entries.sql`) has no `sqlite/` counterpart -- following `eventbus/postgres`'s identical precedent -- since the standalone deployment mode never runs this implementation at all (`pkgcore.NewMemoryKVStore` covers it with no database of its own); `schema.go`'s `EnsureSchema` is this package's own self-contained migration applier (idempotent `CREATE TABLE/INDEX IF NOT EXISTS`, no `schema_migrations` ledger), built the same way `eventbus/postgres.EnsureSchema` is, for the identical reason: `go/pkgcore` cannot import `go/dbkit`, which sits above it.

A further subpackage, `kv/memcached`, is a third distributed-mode `KVStore` implementation, added the identical way -- a package of its own from day one, on `github.com/bradfitz/gomemcache` (a genuinely zero-third-party-dependency client: a throwaway module blank-importing it alone carries no `// indirect` entries at all under `GOWORK=off go mod tidy`, the lowest measured cost of any built-in implementation in this file). Read its package doc comment before choosing it over `kv/redis`: it is honestly declared `MultiReplicaSafe` only, never `SurvivesRestart` -- Memcached is a pure in-memory cache with no persistence mechanism of any kind, so a restart, a rolling upgrade or ordinary LRU eviction under memory pressure silently drops everything it holds. That honest declaration is also why no built-in `Preset` names `"kv.memcached"` (`PresetDistributed`'s `"kv"` entry still names `"kv.redis"`); a host that wants it calls `KVStoreRegistry.Build("kv.memcached", cfg)` or `NewKVStore` directly with `WithKVStore`. Memcached's own primitives are narrower than every other KVStore backend here -- native `incr`/`decr` are 64-bit unsigned integer only, with no float support at the protocol level, and no atomic whole-value compare exists at all -- so `IncrByFloat` and `CompareAndSwap` are both bounded compare-and-swap retry loops over Memcached's native `gets`/`cas`/`add`; and its native per-key expiry is granular only to the whole second, which the shared `kvstoretest.AssertConforms` suite's millisecond-scale TTLs would silently violate without this store's own client-side logical-expiry envelope layered on top of Memcached's coarser physical one (see the package doc comment for the full design and its inherent year-2038 boundary for an extremely long ttl). See the package's own doc comment for the full contract and its `integration_test/` for the real-server proof, including two adversarial concurrency tests (`IncrByFloat` losing no update under many racing goroutines; `CompareAndSwap`'s set-if-absent form letting exactly one racing goroutine win) that only a real server's compare-and-swap primitives can exercise honestly.

Another subpackage, `kv/nats`, carries a fourth distributed-mode `KVStore` implementation (alongside `kv/redis`, `kv/postgres` and `kv/memcached`), on a NATS JetStream KV bucket, registering `"kv.nats"` the identical database/sql-style way `kv/redis` registers `"kv.redis"` -- but, unlike the subpackages above, `"kv.nats"` is **not** named by `PresetDistributed`: this subpackage only makes the name resolvable on `KVStoreRegistry`, it does not change what any existing `Preset` picks by default. A host that wants NATS instead of Redis, PostgreSQL or Memcached for the `"kv"` seam either builds its own `Preset` naming `"kv.nats"` (after blank-importing `kv/nats` so the name resolves) or calls `kv/nats.NewKVStore` directly and wires it with `WithKVStore`. JetStream KV gives only a per-subject last-sequence ("revision") compare, never a native atomic increment or a native compare-by-value, so this implementation's `CompareAndSwap` and `IncrByFloat` are both built on that one revision check (`Update(key, value, revision)` failing `ErrKeyRevisionMismatch`, or `Create` failing `ErrKeyExists`, both mapped to "the swap did not happen" rather than an error) -- `IncrByFloat` wraps the same check in a bounded (200-attempt), exponentially-backed-off retry loop, since no server-side atomic float op exists to lean on instead. Expiry is carried in an 8-byte big-endian Unix-nanosecond header this implementation prefixes onto every stored value itself, never in the bucket's own TTL (a whole-bucket setting that cannot express "an increment keeps a live key's existing expiry, but starts a fresh key with none"), and every opaque `pkgcore.KVStore` key is hex-encoded before it reaches JetStream, since that store's own key charset excludes characters (a colon, notably) this repository's own KVStore tests use freely. Unlike `kv/redis`'s `NewKVStore`, which dials nothing, provisioning a JetStream KV bucket is itself a round trip the server must answer, so `kv/nats.NewKVStore` takes a `context.Context` and can fail. `eventbus/nats` was this repository's first consumer of `nats.go`; this subpackage is the second, sharing the exact same `github.com/nats-io/nats.go v1.53.1` dependency closure `eventbus/nats` put on this module's root `go.mod`. `.golangci.yml`'s `nats-only-in-pkgcore` depguard rule exempts both subpackages under the one rule name rather than a per-subpackage key. Its own `integration_test/` (Docker-backed, JetStream-enabled) runs the shared `kvstoretest.AssertConforms` plus two adversarial concurrency proofs (many goroutines racing `IncrByFloat` on one key with no lost update; many goroutines racing `CompareAndSwap` set-if-absent on one key with exactly one winner) and a real server-restart reconnect proof.

Four more subpackages, `eventbustest`, `kvstoretest`, `mailertest` and `objectstoretest`, hold one `AssertConforms` contract-test suite per infrastructure seam -- the mandatory conformance check every implementation of that seam, built-in or host-supplied, must pass. They play the same role for these four seams that `go/tenancy/tenancytest.AssertIsolated` plays for `dbkit.Repository[T]`: with several registered implementations per seam, drift between them is caught in one shared suite instead of pairwise. See "Contract tests" under Public API below.

**SMS carrier adapters (aliyun, tencent, twilio).** `sms/aliyun`, `sms/tencent` and `sms/twilio` are pkgcore's three real carrier adapters for the `SMSSender` seam -- each a stdlib-only implementation of its vendor's official signing and request shape (Aliyun Dysmsapi RPC HMAC-SHA1, Tencent Cloud SendSms TC3-HMAC-SHA256, Twilio Messages REST with Basic auth), delivering the seam's already-rendered messages to the vendor's fixed gateway over the `pkgcore/safehttp` guarded default client. They live here so every module above the dependency floor can reach a real carrier: go/notification, sitting below go/authn in the module graph, could not import them from their former authn home, which is exactly the reachability gap that made the SMS seam shared. Each adapter carries its own unit tests, its own `example_test.go`, and its own env-gated `integration_test/` live leg (no Docker: the legs need the operator's real carrier credentials, never a container). Their behavioural contracts beyond their own tests are pinned by the consumer suites -- go/authn's phone-login flow and go/notification's delivery pipeline -- since SMS has no `smstest.AssertConforms`: its implementations are not registered on any registry, so there is no shared-suite obligation the way the four kernel-resolved seams have one.

`safehttp` is the outbound-request guard those adapters (and go/authn's own federation client) dial through: it refuses any destination that is not public unicast at the moment of connection, so a DNS-rebinding answer cannot slip past. It moved from go/authn's `internal/` when the SMS transports made it shared -- its package doc records the destinations it fronts and the move.

`httpapi` is the shared HTTP surface convention every module's request handlers answer refusals through: `WriteError` builds the coded error envelope (the `{"code", "params"}` body under the error's own suggested status, with a caller-supplied fallback for an error something below the handler did not classify), and `DecodeJSON` bounds and decodes a JSON request body, mapping every decode failure -- an oversized body included -- onto the calling module's coded invalid-request-body refusal. It is stdlib-and-`apperr`-only, carries its own unit tests and `example_test.go`, and is described under its own section in Public API below.

**Out of scope.** Database access (`dbkit`), tenant enforcement in SQL (`tenancy`), logging and tracing (`observability`), runtime and tenant-overridable configuration (the `config` *module*, not this `config` package), job execution (`jobs`). pkgcore declares contracts; it does not implement business behaviour.

## Public API

### `pkgcore`

**Wiring**

| Signature | Purpose |
|---|---|
| `type Module interface { Name() string; DependsOn() []string; Migrations() embed.FS; Locales() embed.FS; OpenAPISpec() []byte; Register(*Registry) error }` | The contract every module implements |
| `type Registry struct { Routes; Config; Bootstrap; Features; Permissions; Jobs; Notifications; Events; AuditActions; Retention; Schedules }` | Everything a module can contribute, one field per mechanism |
| `func NewRegistry(bus EventBus, kv KVStore, mailer Mailer) *Registry` | A registry wired to the in-memory registrars, to `bus`, `kv` and `mailer`. A nil argument panics |
| `func (*Registry) EventBus() EventBus` | The bus behind `Registry.Events`, so the host publishes into what modules subscribed to |
| `func (*Registry) KVStore() KVStore` | The key-value store the registry was built with |
| `func (*Registry) Mailer() Mailer` | The mailer the registry was built with |
| `func (*Registry) ObjectStore() ObjectStore` | The object store the registry was wired to. Not a `NewRegistry` parameter — the seam post-dates that frozen three-argument signature — so a hand-built registry has none until `Bootstrap` installs one, and only a bootstrapped `Registry` may be used for the store |
| `func (*Registry) Locales() *i18n.Catalog` | The merged message catalog `Bootstrap` assembled from every module's `Locales()` embed.FS. Like `ObjectStore`, not a `NewRegistry` parameter; nil on a hand-built registry, installed by `Bootstrap` after the register loop |
| `func NewKernel(opts ...KernelOption) *Kernel` | With no options, a kernel that behaves like today's zero-configuration standalone default: `DeploymentModeStandalone` composed with `PresetStandalone`. `opts` layer a wider deployment mode, a different `Preset`, or per-seam injection on top |
| `func WithDeploymentMode(mode DeploymentMode) KernelOption` | Set the topology `Bootstrap` validates the resolved composition against |
| `func WithPreset(preset Preset) KernelOption` | Replace the whole seam-name mapping unwired seams resolve against, in place of `PresetStandalone`. Each entry names the implementation its seam resolves to and carries the `Config` that implementation's `Registration.New` is called with, so per-implementation settings travel the same channel as the implementation name. Has no effect on a seam also injected directly: injection always wins, per seam |
| `func WithEventBus(bus EventBus, capabilities Capability) KernelOption` | Inject the host's `EventBus` in place of whatever the active `Preset` would have resolved for the `"eventbus"` seam, declaring what `bus` is capable of. A nil `bus` panics when the option is applied, exactly as a nil `NewRegistry` argument does: nil is the shape of a wiring mistake, never of a choice, and a host that wants the `Preset`'s resolution for a seam omits the option (or appends it only when its value exists) |
| `func WithKVStore(store KVStore, capabilities Capability) KernelOption` | Mirrors `WithEventBus` for the `"kv"` seam |
| `func WithMailer(mailer Mailer, capabilities Capability) KernelOption` | Mirrors `WithEventBus` for the `"mailer"` seam |
| `func WithObjectStore(store ObjectStore, capabilities Capability) KernelOption` | Mirrors `WithEventBus` for the `"objectstore"` seam. A standalone host that must keep objects across restarts injects its own persistent-directory store here, because the built-in `"objectstore.local"` implementation the `Preset` resolves to defaults to a throwaway temporary directory |
| `func (*Kernel) DeploymentMode() DeploymentMode` | The deployment mode the kernel validates the assembled composition against |
| `func (*Kernel) Bootstrap(ctx context.Context, modules ...Module) (*Registry, error)` | Resolve and capability-validate all four seams (preset or injected), dependency-sort modules, register each one, validate the feature graph. Logs one startup Info line naming what every seam resolved to (a preset implementation by its `Registration.Name`, a host-supplied value as `<injected>`), plus a startup warning (never a failure) for any resolved seam that keeps state of its own without declaring `SurvivesRestart`; a `Stateless` implementation is skipped, since a restart drops nothing it holds |
| `func ValidateFeatureGraph(reg *Registry) error` | Reports feature flags depending on flags nobody registered |

**Capability declarations, the seam registry and presets** -- the machinery `Bootstrap`'s seam resolution above is built on; see "Deployment mode and implementation composition" below for the design this implements.

| Signature | Purpose |
|---|---|
| `type Capability uint8`, consts `MultiReplicaSafe` / `SurvivesRestart` / `Stateless` | What an implementation declares about itself at registration or injection time. `func (Capability) Has(want Capability) bool`; `func (Capability) String() string` renders the set bits pipe-joined (`"MultiReplicaSafe\|SurvivesRestart"`), `"none"` for zero. `Stateless` marks an implementation that keeps no state of its own in the process, which suppresses the not-survives-restart banner (`mailer.console` is the built-in example) |
| `type Config map[string]string` | Flat scalar settings a `Preset` entry hands a seam implementation's constructor: what a preset file or environment can naturally provide, keyed by whatever name the implementation documents. A host resolves these from its own koanf/environment layer; pkgcore never reads environment or files itself. Settings the flat strings cannot express (typed TLS configuration, a shared client) reach the implementation by injecting a value the host built, or by registering it through the implementation package's `Registration` factory — all paths are legitimate and none stands in for another |
| `type Registration[T any] struct { Name string; Capabilities Capability; New func(Config) (T, error) }` | One named implementation of a seam |
| `func NewSeamRegistry[T any]() *SeamRegistry[T]`, `func (*SeamRegistry[T]) Register(Registration[T]) error`, `func (*SeamRegistry[T]) Build(name string, cfg Config) (T, Capability, error)` | Name-to-constructor registry for one seam, mirroring `database/sql`'s driver pattern. Safe for concurrent `Register`/`Build` |
| `var EventBusRegistry, KVStoreRegistry, MailerRegistry, ObjectStoreRegistry *SeamRegistry[...]` | The four package-level registries. The seam built-in files (`eventbus_builtins.go`, `kv_builtins.go`, `mailer_builtins.go`, `objectstore_builtins.go`, with the shared registration glue in `registries.go`) pre-populate the five in-process/SMTP built-ins (`eventbus.memory`, `kv.memory`, `mailer.console`, `mailer.smtp`, `objectstore.local`); the Redis-, PostgreSQL-, NATS- and S3-backed built-ins (`eventbus.redis`, `eventbus.postgres`, `eventbus.nats`, `kv.redis`, `kv.postgres`, `kv.nats`, `objectstore.s3`) pre-populate themselves from their own subpackages' `init()` once a host has imported them (see the file-location table above); `eventbus.nats` and `kv.nats` are registered but not named by either built-in `Preset` -- see this file's own subpackage list above. A host registers its own implementation on the matching one before bootstrapping a `Kernel` whose `Preset` names it -- through the matching implementation package's `Registration` factory where one exists (the paragraph below), or by hand |
| `type SeamPreset struct { Implementation string; Config Config }` | One `Preset` entry: the `Registration.Name` its seam resolves through, plus the `Config` that implementation's `New` is called with (the zero value — a nil `Config`, what every built-in preset entry carries — builds from the implementation's documented defaults) |
| `type Preset map[string]SeamPreset` | Seam key (`"eventbus"`, `"kv"`, `"mailer"`, `"objectstore"`) to a `SeamPreset` entry |
| `func (Preset) With(seam string, sp SeamPreset) Preset` | The "config-file per-item override" layer in callable form: returns a copy of the preset with that one entry set, so `PresetStandalone.With("mailer", pkgcore.SeamPreset{Implementation: "mailer.smtp", Config: ...})` derives an override without ever writing through a package-level `Preset` shared by every kernel in the process |
| `var PresetStandalone`, `var PresetDistributed Preset` | The zero-value default (`eventbus.memory` / `kv.memory` / `mailer.console` / `objectstore.local`, none `MultiReplicaSafe`, the two stateless mailers declaring `Stateless`) and pkgcore's own Redis/SMTP/S3 composition (`eventbus.redis` / `kv.redis` / `mailer.smtp` / `objectstore.s3`: `eventbus.redis`, `kv.redis` and `objectstore.s3` declaring `MultiReplicaSafe\|SurvivesRestart`, `mailer.smtp` declaring `MultiReplicaSafe\|Stateless` -- a stateless transport over a relay, per the declaration audit in `mailer_builtins.go`) |

Built-in implementation names: `eventbus.memory`, `eventbus.redis`, `eventbus.postgres`, `kv.memory`, `kv.redis`, `mailer.console`, `mailer.smtp`, `objectstore.local`, `objectstore.s3` -- each a thin `Config`-consuming adapter over an unchanged typed constructor (`NewMemoryEventBus`, ...). `eventbus.memory`, `kv.memory`, `mailer.console`, `mailer.smtp` and `objectstore.local` register here, per seam, in the built-in registration files (`eventbus.memory` in `eventbus_builtins.go`, `kv.memory` in `kv_builtins.go`, the two mailers in `mailer_builtins.go`, `objectstore.local` in `objectstore_builtins.go`); `eventbus.redis`, `eventbus.postgres`, `kv.redis` and `objectstore.s3` register themselves from their own subpackages (`eventbus/redis`, `eventbus/postgres`, `kv/redis`, `objectstore/s3` -- see this file's file-location table above), so they are visible on `EventBusRegistry`/`KVStoreRegistry`/`ObjectStoreRegistry` only once a host has imported the matching subpackage. The Redis-backed adapters fall back to `"localhost:6379"` when `cfg["addr"]` is unset; the SMTP, S3 and PostgreSQL adapters have no safe default credentials and fail with a config error (`ErrMissingSeamConfig` for SMTP/S3; a plain `fmt.Errorf` for `eventbus.postgres`'s required `"dsn"`/`"replica_id"` pair) instead of calling their panicking constructor with an empty field.

A tenth name, `kv.postgres`, is registered by `kv/postgres`'s own `init()` (see the file-location table above): a second registered implementation of the already-existing `"kv"` seam, alongside `kv.redis`. Like the Redis and S3 adapters it has no safe zero-configuration default (no universal PostgreSQL DSN the way `"localhost:6379"` is for Redis) and fails with a plain error naming the missing `cfg["dsn"]` key rather than dialing an empty one.

`eventbus.nats` and `kv.nats`, registered by `eventbus/nats`'s and `kv/nats`'s own `init()`s respectively (see the file-location table above), are the `"eventbus"` seam's third implementation (after `eventbus.redis` and `eventbus.postgres`) and the `"kv"` seam's fourth distributed one (after `kv.redis`, `kv.postgres` and `kv.memcached`). Neither is named by `PresetStandalone` or `PresetDistributed` -- registering either only makes its name resolvable on the matching registry; a host names it in a `Preset` of its own or injects it directly with `WithEventBus`/`WithKVStore`. Both fall back to `nats.DefaultURL` ("nats://127.0.0.1:4222") when a host builds them through their own constructor without a connection already in hand, the same zero-configuration-default posture the two Redis-backed adapters take with `"localhost:6379"`.

**Name registration for typed configuration.** Each distributed implementation package exports its own `Registration` factory beside the built-in one — `eventbusredis.Registration("eventbus.redis.host", client)`, `kvpostgres.Registration("kv.postgres.shared", pool)`, `eventbuspostgres.Registration(name, pool, replicaID)`, `kvnats.Registration(name, conn, bucket)`, `s3.Registration("objectstore.s3.prod", s3cfg)` and their three siblings — taking the client, connection, pool, pool-plus-replicaID or typed `Config` the implementation adapts onto, and declaring the same exported `Capabilities` constant the built-in registration declares (so a host reading the package and assembly validating a composition can never see two different declarations). The host builds the object, wraps it in the factory, registers the result on the matching package-level registry under a name of its own — the built-in name is already taken, and a duplicate fails with `ErrDuplicateImplementation` — and names that name in a `Preset` entry, whose `Config` the factory ignores: everything the implementation needs came in with the object. Ownership stays with the host exactly as with a `WithEventBus`-style injection: the factory's `New` returns the bare implementation with no closable wrapper, so `Kernel.Shutdown` never touches it, and the host closes its own object. This is the recommended form of host registration when the configuration is typed (TLS material, a credential chain, one resource shared across seams): the composition stays switchable from configuration alone — only the preset entry's `Implementation` string differs between deployments — while the object stays in the host's hands. `go/pkgcore/unittest/factory_registration_test.go` drives the whole loop (register under an alias name, reference it from a `Preset`, `Bootstrap` resolves it, `Shutdown` leaves the host's client live) over two seams sharing one client.

**One-step constructors for the bare-injection path.** `eventbus/redis`, `kv/redis` and `objectstore/s3` also export a one-step constructor each -- `FromAddr(addr)` for the two Redis-backed seams, `FromConfig(cfg)` for S3 -- for the host that has only an address or a typed `Config` and wants the `WithEventBus`/`WithKVStore`/`WithObjectStore` pair without hand-assembling the driver client first: one call returns the implementation the package built (over a client it built, or over the store `cfg` describes) together with the same exported `Capabilities` constant the built-in registration declares, so the host never spells capability bits out and the declaration assembly validates cannot drift from the one the constructor reports. The two Redis-backed constructors return an owned value (`eventbusredis.OwnedEventBus`, `kvredis.OwnedKVStore`) whose `Close() error` releases the client the constructor built -- the host that injected the value calls it at shutdown, since the kernel never touches an injected seam; `objectstore/s3`'s returns the bare `ObjectStore`, because the minio-go client exposes no close. An empty address or an unusable `Config` comes back as an error, never a panic, and never a silent fallback. This is not a preset selector: which implementation a seam uses stays kernel wiring, exactly as the routes above. A host that needs credentials, a database index, TLS material or one client shared across seams builds the client itself (`NewEventBus`/`NewKVStore`) or reaches for the `Registration` factory; the one-step constructors serve the host that has nothing but the address, or the typed `Config`.

Registrar interfaces: `RouteRegistrar`, `ConfigSchemaRegistrar`, `BootstrapRegistrar`, `FeatureRegistrar`, `PermissionRegistrar`, `JobHandlerRegistrar`, `NotificationRegistrar`, `EventRegistrar` (`Publishes` / `Published` / `Subscribe` / `Bus`), `AuditActionRegistrar`, `RetentionRegistrar` (`Add` / `Participants`), `PeriodicTaskRegistrar` (`Add` / `Declarations`).

`PeriodicTask` (the `Registry.Schedules` seat) declares one periodic task a module owns — the job type, the window size `Every`, which tenants it runs for, and the two strings an enqueue needs (`KeyPrefix`, the module's own established idempotency-key prefix; `PlatformTenant`, the sentinel tenant a platform-scope task is enqueued under). **Declaring means scheduled**: a host that runs a `jobs.Scheduler` over the finished registry's declarations enqueues every declaration on that declaration's own cadence, and the host's single switch is whether it starts a scheduler at all — there is no per-declaration approval step. A module therefore declares a task exactly where it also registers that task's handler, so every declaration has an executor in the composition that made it, and the scheduler-side key derivation (`jobs.ScheduleWindowStart` + `jobs.ScheduleIdempotencyKey`, the "prefix + tenant segment + window start" shape) resolves the same key the module's own `Enqueue*` path resolves for the same window — a tick and a manual enqueue landing in one window dedupe onto one job. `Add` validates every declaration (a non-empty `Type` and `KeyPrefix`, a positive `Every`, a known `Scope`, and `PlatformTenant` set exactly for `PeriodicScopePlatform`) with `ErrInvalidPeriodicTask`, and rejects a repeated `Type` with `ErrDuplicatePeriodicTask`; nothing is registered when the call returns an error.

`pkgcore.MountRoutes(mux, routes...)` is the one implementation of the mounting rule every module route follows — each route's `Handler` registered at its own `Path` and, unless the path already ends in `/`, at `Path+"/"` as well, so the handler is reachable at the exact path AND below it without ServeMux's redirect-on-missing-slash behavior (a redirect does not preserve a POST's method or body). See its doc comment for the full reasoning; `examples/reference-app` and `go/saasctl`'s generated project are its two consumers, and `ExampleMountRoutes` is the runnable demonstration.

`MountedRoute.Access` (`pkgcore.RouteAccess`) carries a route's authorization decision: `Public` declares it deliberately reachable without a permission check, and `Permission` (a `pkgcore.RoutePermission`, `func(*http.Request) string`) selects the permission each request must hold -- a function because the required permission routinely varies by the request's route (read on GET/HEAD, write otherwise). The zero value declares NOTHING: a module's own `Mount` records none, and the platform's route table (`rbac.GuardRoutes`, which a host wires over `reg.Routes.Routes()`) refuses to serve a mounted route whose decision the host's table does not state, marking public routes with the positive `Public` declaration rather than by omission. `rbac.SplitPermission` reads a three-segment `"<module>:<entity>:<verb>"` permission at its last separator, so the selector may return those as well as two-segment names. `ExampleMountedRoute_access` is the runnable demonstration.

`ConfigItem` declarations are validated when registered: `Type` must be one of `string` / `int` / `bool` / `duration`; a non-nil `Default` must be a Go value of that kind (`string`, `int` or `int64`, `bool`, `time.Duration`; nil is legal and means "no value until one is set"); `Min`/`Max` are declarative ranges defined for `int` and `duration` items only, must satisfy `Min <= Max`, and a non-nil `Default` must fall inside them; `Sensitive` and `Public` are mutually exclusive. A contradictory declaration fails the whole `Add` call with an error wrapping `ErrInvalidConfigItem` -- see the error index below.

`BootstrapKey` declarations (the `Registry.Bootstrap` seat) describe the process-start input a module consumes -- keys a host resolves once, before the process is wired, from command-line flags, the environment, an optional config file and the defaults on its loader target struct (`go/pkgcore/config`). A module declares what it consumes and never reads it: the host resolves the value and injects the result. `Format` is one of `string` / `int` / `bool` / `hexkey` (a 32-byte key's hexadecimal text); `Default` is an operator-facing statement of the fallback behaviour, never a second runnable default -- the authoritative default is whatever the host's target struct carries; a `Sensitive` declaration must carry a `Description`, and a contradictory or repeated key fails the whole `Add` call (`ErrInvalidBootstrapKey`, `ErrDuplicateBootstrapKey`) with nothing registered. By convention `Key`'s first segment is the owning module's name, so the generated reference can group declarations per module.

The seat's key-material derivation convention is one exported function: `func BootstrapKeyPurpose(keyPath string) (string, error)` returns the derivation purpose string of one declared key path -- the literal `"speed." + keyPath + ".v1"`, never a string-surgery transform -- which a host composes with `dbkit.DeriveKey(rootKey, purpose)` to get that key's 32-byte material from one root secret. A path that is empty or carries an empty segment (a leading, trailing or doubled dot) fails with `ErrInvalidBootstrapKeyPath`, a plain sentinel matched with `errors.Is`: derivation runs at boot, before any HTTP surface exists, so it is deliberately not an `apperr` code. The purpose embeds the declared key path verbatim and `dbkit.DeriveKey` is deterministic, so renaming a declared key path is a rotation of that key's material and must ship as one. The six key paths this repository's modules declare today and the purpose each freezes: `authn.blind_index_key` → `speed.authn.blind_index_key.v1`, `authn.pii_cipher_key` → `speed.authn.pii_cipher_key.v1`, `config.cipher_key` → `speed.config.cipher_key.v1`, `notification.contact_index_key` → `speed.notification.contact_index_key.v1`, `org.invitation_email_index_key` → `speed.org.invitation_email_index_key.v1`, `pki.local_key_cipher_key` → `speed.pki.local_key_cipher_key.v1`. Whether a path is a declared key at all, and the precedence between a derived material and an explicitly configured one, are the host's own checks and policy, never this function's.

**One key belongs to one layer.** A dotted key declared on the runtime configuration seat (`reg.Config`) and on the bootstrap seat (`reg.Bootstrap`) at once is refused by `Kernel.Bootstrap` (`validateBootstrapKeySeparation`), naming the key and both layers: the two seats are invisible to each other while modules register, and the two layers carry different meanings, defaults, scopes and edit surfaces for the same identifier. Sharing a module prefix is not a conflict -- `authn.password_min_length` (runtime) and `authn.pii_cipher_key` (bootstrap) coexist.

Declaring zero bootstrap keys is an honest state, not a gap: a module that consumes no process-start input declares none, and nothing asks for a placeholder. The current census: `authn` declares two (`authn.pii_cipher_key`, `authn.blind_index_key`), `org` one (`org.invitation_email_index_key`), `notification` one (`notification.contact_index_key`), `pki` one (`pki.local_key_cipher_key`) and `config` one (`config.cipher_key`); every other platform module declares none.

`NotificationType`'s own annotation: `RecipientVisibleParams` names the parameters a dispatch of the type may carry to its recipient -- the keys of the interpolation values the type's templates reference (see `go/notification`'s `Dispatch.Params`). Anything NOT named is delivery-internal context that must never reach the recipient, and `go/notification` enforces the declaration on the two boundaries it owns: `DeliveryService.Dispatch` refuses a dispatch carrying any parameter outside the list before anything is enqueued (`ErrDispatchParamsNotAllowed`, naming the type and the offending keys), and the delivery path narrows a payload that nevertheless reaches it -- a job enqueued before the declaration restricted its params -- down to the list before anything renders, derives into the delivery key or persists into the row. An EMPTY list is a real declaration: the type's copy is not parameterized, so its dispatches may carry no parameters at all. Nil means "no restriction declared": a type that does not declare the list keeps accepting any parameters, so no existing declaration's behaviour changes. pkgcore itself only carries the field -- the enforcement lives in `go/notification` (that module's `AGENTS.md` has the delivery-side detail); its first real declaration is `go/admin`'s `admin.impersonation_started`, which declares the empty list (that module's documentation records the leak the empty list closes).


**Deployment mode and implementation composition**

These are two orthogonal axes: deployment mode declares topology -- how many replicas may run at once -- and therefore which capabilities every seam's resolved implementation must have; it never selects an implementation. `Kernel.Bootstrap` is the one place that compares the two, per seam, using `validateSeamCapability`.

`type DeploymentMode string`, constants `DeploymentModeStandalone` / `DeploymentModeDistributed`, `func ParseDeploymentMode(string) (DeploymentMode, error)` (trims and lowercases), `func (DeploymentMode) Valid() bool` (exact match, so `"Standalone"` is not valid), `func (DeploymentMode) RequiredCapabilities() Capability` (`DeploymentModeDistributed` → `MultiReplicaSafe`; everything else, including an invalid value `Bootstrap` would have already rejected via `Valid()`, → `0`).

### Seam lifecycle, one-clock TTLs and panicking remote handlers

- `func (*Kernel) Shutdown() error` closes every seam implementation a `Bootstrap` of that Kernel resolved from a Preset whose value implements `Close() error` — the resource-ownership contract `Registration`'s doc comment states. An implementation whose `New` builds resources it owns (a dialed NATS connection, a Redis client or pgx pool built from cfg, a throwaway temp directory) declares the ownership by implementing `Close() error` on the value it returns; `Bootstrap` records it and releases it exactly once — at `Shutdown` on success, or on `Bootstrap`'s own failure path, immediately, so a misconfigured composition never leaks what it already dialed. An injected seam (`WithEventBus` and siblings) is the host's to close and is never touched -- including the owned value a one-step constructor (`eventbus/redis.FromAddr`, `kv/redis.FromAddr`) built for the host, whose own `Close() error` is what releases the client that constructor built. The built-in registrations in `eventbus/redis`, `eventbus/nats`, `eventbus/postgres`, `kv/redis`, `kv/postgres`, `kv/nats`, `kv/memcached` and the `objectstore.local` preset each return such a closeable value over the client/pool/connection/directory the registration itself built (`kv/memcached`'s closer releases the pooled connections `gomemcache`'s `Client.Close` closes); `mailer.smtp` and `objectstore.s3` own no closable resource (the minio-go client exposes no close).
- Expiry arithmetic on the PostgreSQL-backed store (`kv/postgres`) and outbox (`eventbus/postgres`) runs entirely on the database clock: `Set`/`IncrByFloatWithTTL` store `now() + <interval>` computed inside the statement, reads judge against `now()`, outbox `created_at` is stamped by `now()` at insert, and `PurgeOutboxBefore` cuts off at `now() - <interval>` — no application clock is consulted anywhere, so replica/database clock skew cannot shorten or stretch a TTL (a security control must not be judged early by a clock disagreement). `kv/postgres`'s `WithClock` option is the explicit regression seam for that property (the store never calls it). `kv/nats` and `kv/memcached` carry expiry inside the value envelope and judge it on the reading replica's clock — documented per-backend; adopting NATS's server-side per-key TTL is not viable on the pinned nats.go v1.53.1 / nats-server pair because any header-less Put/Update (the only kind the KeyValue API can issue) clears the per-key TTL, which cannot express "increment preserves a live key's expiry" (see `kv/nats`'s package doc comment).
- `kv/nats.NewKVStore` probes first and adopts an existing bucket only when the adopted configuration can satisfy what the `"kv.nats"` registration declares and relies on, refusing a non-compliant one with the exported `ErrUnadoptableBucket` (which the `Registration.New` path propagates out of `Bootstrap` unchanged, so startup fails naming the bucket and the offending configuration instead of silently bypassing the capability checks): memory storage is refused because it cannot satisfy the registered `SurvivesRestart`, a whole-bucket TTL is refused because the server would silently expire `ttl<=0` stores-forever keys, and every other field an operator provisioned (history depth, description, replication, placement) is preserved untouched and never a refusal reason. It creates (never update-overwrites) an absent one — file storage, no TTL, exactly the configuration the adoption checks accept — and resolves a create race by re-probing and verifying the winner through the same check. `kv/memcached` never deletes a logically expired row on the read path — a stale read's unguarded `Delete` used to be able to destroy a concurrent writer's fresh value — and revives an expired-but-physically-present key through the server's compare-and-swap at the token the read returned, exactly like `kv/nats`'s revision-guarded revive.
- A remote event-bus handler that panics is recovered (so one buggy handler cannot take down a replica) and logged, never silently swallowed; the entry is not acked-as-delivered and its redelivery is bounded by each backend's own mechanism: `eventbus/redis` leaves it pending in the consumer group (never refetched — the reader consumes new entries only — so no stall and no sibling re-run), `eventbus/nats` negatively acknowledges it and JetStream redelivers it at `panicRedeliveryDelay` intervals up to the consumer's `MaxDeliver` (`eventMaxDeliver`) budget, each redelivery re-invoking only the panicked handler values — never the message's whole fan-out, so healthy siblings run exactly once — and settling with a terminal log line when the budget is exhausted (see `eventbus/nats`'s `deliverRemote`), and `eventbus/postgres` advances its cursor past the row like a clean delivery — so later same-type rows keep flowing and healthy sibling handlers never re-run — while retrying the still-panicking handler values in-process on a bounded attempt budget, settling with a terminal log line when the budget is exhausted (see `eventbus/postgres`'s `retryPanickedRows`). The in-memory bus — the standalone mode's whole delivery machinery, with no reader goroutine of its own to absorb a panic — contains a subscriber panic inside `Publish` itself, recovered and logged, with the handlers registered after the panicking one still run (see its `Publish`). The broker-backed buses' own same-instance local fan-outs contain panics the same way: `Publish` runs each locally-subscribed handler through the package's own recover (`runLocalHandler` in each of `eventbus/redis`, `eventbus/nats` and `eventbus/postgres`), which logs the panic, drops it (never an error a caller could act on), lets the handler's siblings still run, and keeps the publish a success — the in-memory shape, applied because the local fan-out runs on the CALLER's goroutine (frequently a background goroutine with no recover of its own, the exact caller `runMemoryBusHandler`'s doc comment names), not on a reader goroutine the remote-delivery machinery protects. Each bus's integration tier pins the containment against a real broker (its `panicked_local_handler_contained_test.go`), and `eventbus/postgres`'s version additionally pins that the row whose local handlers ran is still marked delivered, while the poller path's bounded retry of still-panicking handler VALUES keeps covering deliveries that run outside any publisher's stack.

### `pkgcore/apperr`

`type Error struct { Code string; Params map[string]any; Status int }` with `Error()`, `Unwrap()`, `WithParam(key, value) *Error`, `WithSensitiveParam(key, value) *Error`, `SensitiveParams() map[string]any`, `WithCause(error) *Error`.

Constructors and the status each suggests: `Invalid` 400, `Unauthorized` 401, `Forbidden` 403, `NotFound` 404, `Conflict` 409, `Internal` 500. `func As(error) (*Error, bool)` recovers one from a wrapped chain, and `func HasCode(error, string) bool` is its predicate form: it reports whether the chain's outermost `*Error` carries exactly that code -- the way to classify a decorated error, since `WithParam`/`WithCause` never hand back the sentinel a caller might compare against with `==` or `errors.Is`.

`WithParam`, `WithSensitiveParam` and `WithCause` return a *derived* `*Error` and leave the receiver untouched, so a package-level error value can be shared and decorated per request.

The contract on `WithParam`'s write side (its doc comment states it in full, and it must survive into consuming modules): a parameter recorded there is serialized VERBATIM into the HTTP response body and handed to an untrusted caller -- no transport filters or redacts this map, so two prohibitions rest on the caller. Content: never keys, secrets, tokens, personal data, internal hostnames or resolved addresses. Shape: `Params` is `map[string]any` and `WithParam` accepts `any`, so never pass a struct, slice or map whose fields would serialize wholesale -- a field safe today silently rides into every response carrying the error tomorrow. Keep to known-safe scalars. `WithSensitiveParam` is the declared alternative for everything a client must not see or that needs more than a scalar: its value lives in a separate map (`SensitiveParams()`, the only reader) that no transport serializes and that `Error()` never renders; it is for server-side diagnostics only, never a response field. The caller declares; the library never guesses.

### `pkgcore/httpapi`

`func WriteError(w http.ResponseWriter, err error, fallback *apperr.Error)` and `func DecodeJSON(w http.ResponseWriter, r *http.Request, maxBytes int64, dst any, invalid *apperr.Error) bool`.

`WriteError` writes the coded error envelope every HTTP refusal is: the body `{"code": ..., "params": ...}` under the HTTP status the error's `apperr` constructor suggested, with `Content-Type: application/json; charset=utf-8` unless the caller set its own first (an endpoint whose contract pins a different content type sets it before the call). An err that is not, and does not wrap, an `*apperr.Error` is written as `fallback` instead, so raw Go error text never reaches a caller either way; the cause never crosses the wire, and a parameter-less error omits the `params` key rather than emitting `null`.

`DecodeJSON` decodes r's JSON body into dst, reporting whether it did. A positive `maxBytes` bounds the body BEFORE decoding, so an over-limit body fails as soon as the read passes the limit rather than after it has been buffered in full (passing w lets net/http ask the server to close the connection after the oversized request); a non-positive `maxBytes` decodes without a bound, for the endpoints that set no body limit. On any decode failure -- malformed JSON, a value of the wrong shape, or a body past the bound -- it writes `invalid`, carrying the decode error as its cause, through `WriteError` and reports false: the oversize answer is the same coded refusal as malformed JSON.

### `pkgcore/config`

`func New(opts ...Option) *Loader` with `WithConfigFile(path)`, `WithArgs([]string)`, `WithEnviron([]string)`, `WithRootKey([]byte)`, `WithRootKeyEnv(name)`, `WithKeyDerivation(fn)`; `func (*Loader) Load(target any) error`.

Priority, highest first: command-line flags, environment variables, config file, the root-key derivation (derive-tagged key-material fields only), the defaults already on the target struct. `Database.DSN` maps to key `database.dsn` (segments joined by `KeyDelimiter`), flag `--database.dsn`, variable `SPEED_DATABASE__DSN` (`EnvPrefix` + `EnvSeparator`). Per-field options come from the `TagName` struct tag: `config:"required"`, `config:"-"`, `config:"env=NAME"` and the bare `config:"derive"`.

A `derive` field is one 32-byte unit of key material and must be typed exactly `[]byte` (anything else fails the target description with `ErrInvalidTarget`, as does a repeated token). It resolves through the same chain with the derivation standing where the struct default would: an explicit value from any text source must be 64 hex characters and is decoded to the field's 32 bytes (a non-text value, notably a config-file scalar the parser read as a number, is refused naming the key and its source); an emptied variable or empty file entry reads as unset, exactly as `""` does for a string field; a configured root key derives the field -- the loader calls the `WithKeyDerivation` function with the root key and the field's dotted key path, which is the same identifier flags and config files use and the derivation's identity, so renaming a field rotates its material -- and with no root key configured the struct default stands. The root key comes from exactly one option: `WithRootKey` (the 32 bytes) or `WithRootKeyEnv` (the name of the variable holding the key's 64-hex text, read inside the same `Load`, which is what lets a host forbidden from reading the environment itself still wire derivation). A second root-key option in any combination, and an empty variable name, panic. A configured root key that is not a 32-byte key fails `Load` with `ErrInvalidRootKey`, naming the source; derive fields plus a configured root key but no installed deriver fail `Load` with `ErrInvalidTarget`; and a deriver's result that is not 32 bytes is refused like any other unfitting value. Derive-tagged keys never enter the text decode, and every stored value is a freshly allocated slice -- a host's package-level development default pre-filled onto such a field is never written through. The platform composition a host wires is `pkgcore.BootstrapKeyPurpose` (the seat's purpose per declared key path) plus `dbkit.DeriveKey`, in one call: `dbkit.DeriveBootstrapKey`.

`func EnvName(prefix, key string) string` is that variable spelling as an exported pure function -- the prefix, then the key uppercased with each level of nesting marked by `EnvSeparator` -- and the loader reads through it (`derivedEnvName` applies it to the loader's own prefix), so a document or tool that prints a variable name for a key cannot drift from the name the loader actually reads. A field pinned with `config:"env=NAME"` is read from that name whatever `EnvName` derives. The prefix must be a form `WithEnvPrefix` accepts (non-empty, ending in `_`); `EnvName` does not validate it.

### `pkgcore/i18n`

The merged message catalog. `func NewBuilder() *Builder`; `func (*Builder) AddModule(module string, fsys fs.FS) error`; `func (*Builder) Build() *Catalog`. `func (*Catalog) Lookup(locale, code string, params map[string]any) (string, error)`; `func (*Catalog) LookupPlural(locale, code string, count int64, params map[string]any) (string, error)`; `func (*Catalog) Locales() []string`. | `kvstoretest.AssertConforms(t *testing.T, caps pkgcore.Capability, factory func() (pkgcore.KVStore, pkgcore.KVStore))` | `Get` on a never-set key reports a miss, not an error; `Set`+`Get` round-trips the exact bytes; `Delete` removes a key and is a no-op on an absent one; a short-TTL key expires while a no-TTL key set at the same time survives the same wait; `IncrByFloat` starts a missing key at zero and accumulates, and fails with `pkgcore.ErrNotNumeric` on a non-numeric value without changing it; `IncrByFloatWithTTL` attaches its ttl to a missing key and lets that ttl expire it, never extends a live key's existing ttl, behaves exactly like `IncrByFloat` for a ttl <= 0, and fails with `pkgcore.ErrNotNumeric` the same way on a non-numeric value; `CompareAndSwap` is set-if-absent on a missing key, swaps only on a matching old value, and leaves the value untouched on a mismatch; an already-cancelled context fails every operation with that context's error instead of performing it. `caps` must carry the capability bits the implementation under test declares (the same bits its `register.go` `init` declares and its `register_test.go` pins), and the suite is capability-gated: the two cross-instance checks -- a value set on one instance is readable on the other; a delete on one instance is visible on the other -- run only when `caps` declares `MultiReplicaSafe`. An implementation declaring neither bit (the in-memory store) runs the single-instance checks only |
| `kvstoretest.AssertSurvivesRestart(t *testing.T, caps pkgcore.Capability, factory func() pkgcore.KVStore, restart func())` | The contract-suite verification of the `SurvivesRestart` capability bit, for a KVStore implementation that declares it: write a value through a store `factory` built, run `restart`, then read the value back through a store `factory` builds again -- and write and read a second value through it, proving the restarted store fully operational. `caps` must declare `SurvivesRestart` -- the protocol exists to verify that bit, so a call whose caps lack it is refused outright (the refusal is what ties a declaration to a verification it cannot fake; see `checkSurvivesRestartCall`) -- and `factory`/`restart` must be non-nil. `factory` is called exactly twice, once before and once after the caller's single `restart`, and must connect to the same backing data both times; `restart` must be a genuine restart of the service that holds the state (for an integration leg, the real container stop/start), since only that distinguishes durable state from state that merely looks durable inside one process -- the reading `pkgcore.Capability`'s own `SurvivesRestart` doc comment now states. Each `AssertConforms` calls `t.Run` once per property it checks and calls `factory` once per subtest, and a failure's subtest name says which property broke. The `eventbustest` and `kvstoretest` suites are capability-gated: their `caps` argument carries the capability bits the implementation under test declares (the same bits its `register.go` `init` declares and its `register_test.go` pins against the registry), and the cross-instance checks run only when `caps` declares `MultiReplicaSafe` -- a declaration is a promise the gated contract verifies, and an implementation declaring no bit runs the single-instance checks only, so declared-but-unverified cannot exist. The `eventbustest` and `kvstoretest` factory returns a PAIR of instances -- the shape of a deployment, not of a single store. A single-process implementation (the in-memory bus or store) returns the same instance twice: a one-replica deployment's "second instance" is its own one instance (the single-instance checks run against the pair's first instance; the cross-instance ones, for a `MultiReplicaSafe`-declaring implementation, against both). A shared-backend implementation (Redis, PostgreSQL, NATS, Memcached) returns two genuinely independent connections, and the cross-instance assertions become the checks that make the suite able to see what such an implementation exists for: a write or publish made through one connection visible through another. That makes the two-instance shape the contract-suite form of verifying the `MultiReplicaSafe` capability bit -- the bit claims exactly that a second instance of the same deployment observes what the first one wrote or published, and these assertions check that claim against the pair the factory builds, so an implementation that cannot satisfy the claim fails here the same way `Kernel.Bootstrap` fails an assembly whose resolved implementation cannot satisfy the deployment mode's requirements (`ErrCapabilityUnsatisfied`), but at the level of behaviour rather than declaration. Each integration leg passes the declared bits, so which assertion runs follows from the declaration alone: the memory unit legs pass the zero capability, the redis/postgres/nats eventbus legs and the redis/postgres/nats kv legs pass `MultiReplicaSafe\|SurvivesRestart`, and the memcached kv leg passes `MultiReplicaSafe` alone. A `mailertest` or `objectstoretest` factory, whose suite keeps the single-instance shape, may hand in a backend that is not reusable across calls (a fake relay wired to expect one connection, say). `factory` is not required to return an empty-state instance -- every subtest derives its own key/event-type/message from the subtest name (or, for `mailertest`, uses fixed-shape messages that never collide), so several subtests can safely share one long-lived backend (a single Redis container, a single S3 bucket) without colliding, which is exactly what the Redis/RustFS integration legs below do.

The two restart protocols above verify the other KVStore capability bit, `SurvivesRestart`, which no per-subtest factory pair can express because it needs a genuine restart of the service that holds the data between the write and the read. Each KV integration leg runs the protocol matching its implementation's declaration — and its protocol call carries that same declaration as its `caps` argument, so a protocol run whose caps contradict the declaration is refused outright rather than silently verifying nothing: `kv/redis`, `kv/postgres` and `kv/nats` run `AssertSurvivesRestart(t, MultiReplicaSafe\|SurvivesRestart, ...)`, driving the restart against the real container — the state-holding-service restart `pkgcore.Capability`'s own `SurvivesRestart` doc comment names (the redis leg lets a forced one-second RDB snapshot fire before the stop, so the proof rests on a snapshot that demonstrably landed; the nats leg's store runs over the FileStorage bucket `NewKVStore` itself provisions, which survives the container's stop/start — the restart that would expose a MemoryStorage-adopted bucket, which `NewKVStore`'s own refusal makes unreachable through this store), and `kv/memcached` runs `AssertDoesNotSurviveRestart(t, MultiReplicaSafe, ...)`, pinning the factual basis of its honest non-declaration. The unit tier exercises the protocol machinery without Docker: `kvstoretest`'s own tests prove the positive protocol rejects a store whose data dies with its service's restart (the MemoryStorage shape on a unit scale) and accepts one whose data outlives the restart, prove the negative protocol accepts the loss, and pin each caps refusal.

The `SurvivesRestart` declarations of the non-KV seams are verified the same way, at the same service-restart level: `objectstoretest.AssertSurvivesRestart` (above) is the ObjectStore twin of the KV protocol, and `objectstore/s3`'s integration leg runs it against a genuine restart of its real RustFS container — an object stored before the stop/start must read back intact through a fresh store afterwards, and the restarted service must take new writes. The EventBus seam's declarations get per-backend evidence instead of one shared protocol, because an EventBus is the transport, not the record — nothing the shared suite could read back through the bus API would outlive or fail to outlive a restart, so the state that matters (committed entries, cursors) is verified at the state level against each backend's own real container, and the two restart shapes are recorded separately rather than conflated: closing and reopening the bus (eventbus/postgres's catch-up proofs under the same `replicaID`) proves the durable-cursor-across-consumer-restart property and nothing about the server behind the bus, per `pkgcore.Capability`'s own definition, while each declaring eventbus leg's `declared_survives_restart_test.go` drives a genuine restart of its state-holding container — the PostgreSQL container between downtime publishes and the reconnecting replica's catch-up (eventbus/postgres), the Redis container between a committed publish and the read-back of the committed stream entries and group cursor (eventbus/redis, over a fixture that forces the one-second RDB snapshot the operator-configured persistence premise names), and the NATS container between a committed publish and the read-back of the committed JetStream stream state (eventbus/nats, over the file storage that is the zero value of `StreamConfig.Storage` and that this package never overrides). Each backend's package doc comment records what its declaration promises, the operator-provided configuration premise it stands on, and what it does not promise; see those records for the redis and nats persistence-premise details.

Every in-process or SMTP built-in implementation runs its matching suite from this module's `unittest/` directory, the unit-tier home the testing-layout rule assigns to seam-contract drivers of the module root's own built-ins (unit-tier checks with no single source-file target): `unittest/eventbus_conformance_test.go`, `unittest/kv_conformance_test.go`, `unittest/mailer_conformance_test.go` and `unittest/objectstore_conformance_test.go` (package `unittest`, black-box against package `pkgcore` -- each must be an external test package, because each imports the seam's `*test` package, which itself imports `pkgcore`, and an internal `package pkgcore` test file importing that back would be an import cycle) run `NewMemoryEventBus`/`NewMemoryKVStore`/`NewConsoleMailer`+`NewSMTPMailer`/`NewLocalObjectStore` through `AssertConforms`. The SMTP leg needs no Docker: it scripts an in-process fake relay (`internal/testutil/fake_smtp_server.go`), so it lives in the plain unit tier alongside the other three memory/console/local legs. The seven Redis-, PostgreSQL-, NATS- and S3-backed implementations run the identical call against a real Redis/PostgreSQL/NATS/MinIO container from their own subpackage's own `integration_test/` (`-tags=integration`, Docker required) -- `eventbus/redis/integration_test/`, `eventbus/postgres/integration_test/`, `eventbus/nats/integration_test/`, `kv/redis/integration_test/`, `kv/postgres/integration_test/`, `kv/nats/integration_test/` and `objectstore/s3/integration_test/` -- rather than a shared one here: a package's integration tests live in its own `integration_test/` directory. `eventbus/postgres/integration_test/` additionally carries the real-server proofs beyond `AssertConforms` that no other seam's tier needs: an explicit fan-out proof (two bus instances, distinct `replicaID`s, sharing one pool, both Subscribed -- both receive one Publish); an explicit catch-up proof in both of its consumer-restart shapes -- a full restart under the same `replicaID`, and a live listener connection severed and reconnected mid-test (`pg_terminate_backend` against the container) -- since the persisted per-replicaID cursor, durable across the CONSUMER's own restarts, is this implementation's whole reason to exist over `eventbus/redis`'s fresh-instance-at-live-end shape (a claim about the bus's own design, distinct from the `SurvivesRestart` bit both declare, which names the server's durability and which this tier additionally verifies for PostgreSQL by its own `TestEventBus_DeclaredSurvivesRestart_DurableCursorAcrossServerRestart` -- the same catch-up protocol with a genuine stop/start of the PostgreSQL container between the downtime publishes and the reconnecting replica); a re-entrant-publish pair proving a handler may `Publish` on the bus that invoked it without deadlocking on either delivery arm; a cursor-advance-retry proof that a connection loss between a row's delivery and its cursor advance never duplicates the row; and the two no-loss regressions pinning the healthy-path exactly-once guarantee -- same-type publishes serialized into id order by a per-type advisory transaction lock inside every publish transaction, and a local publish never advancing the persisted cursor past same-type rows this replica's own lagging listener has not delivered yet (`TestEventBus_LaggingPoller_LocalPublishMustNotSkipUnseenRemoteRows` and `TestEventBus_ConcurrentMultiReplicaPublish_NoEventLostNoDuplicate`; see the package doc comment's delivery-semantics note for why the crash windows that degrade this to at-least-once are accepted and documented rather than papered over). `eventbus/nats/integration_test/` carries the analogous fan-out proof for its own implementation, `TestEventBus_FanOutDeliversToEveryReplica` (two independent `*nats.Conn`s, one Publish, both replicas' handlers fire), the same property `eventbus/redis` and `eventbus/postgres` are each documented and tested to have. `kv/postgres/integration_test/` runs the same call against a real PostgreSQL container, alongside the two adversarial concurrency proofs `TestKVStore_ConcurrentIncrementsLoseNoUpdates` and `TestKVStore_ConcurrentCompareAndSwapSetIfAbsent_ExactlyOneWinner` that `AssertConforms` alone (effectively single-threaded) cannot exercise. A host registering a new implementation on `EventBusRegistry`/`KVStoreRegistry`/`MailerRegistry`/`ObjectStoreRegistry`, or injecting one directly through `WithEventBus`/`WithKVStore`/`WithMailer`/`WithObjectStore`, is expected to run the matching `AssertConforms` against it the same way, per this file's own Rules section.

`internal/testutil` holds `FakeSMTPServer`, the scripted SMTP relay `smtp_mailer_test.go`'s own wire-level tests and `unittest/mailer_conformance_test.go`'s SMTP leg both drive -- a single home for a helper a second consumer also needed, rather than a second, drifting copy of the same fake. It deliberately does not import `pkgcore` itself (only `package pkgcore`'s own unexported-symbol tests and the `unittest` driver, each outside `testutil`, need `SMTPConfig`/`NewSMTPMailer` to build a `pkgcore.Mailer` around a `FakeSMTPServer`, and `testutil` importing `pkgcore` back would make the `package pkgcore` internal tests an import cycle); each caller therefore builds its own few-line `pkgcore.Mailer` wrapper around `FakeSMTPServer.Addr()`.

## Typical integration

Implementing a module:

```go
func (m *Module) Register(reg *pkgcore.Registry) error {
	reg.Routes.Mount("/api/v1/billing", m.router())

	if err := reg.Config.Add(pkgcore.ConfigItem{
		Key: "billing.invoice_retry_limit", Type: "int", Default: 3,
		Description: "How many times a failed invoice charge is retried.",
	}); err != nil {
		return err
	}
	if err := reg.Permissions.Add("billing:read", "billing:write"); err != nil {
		return err
	}
	if err := reg.Events.Publishes(pkgcore.EventDecl{
		Type: "billing.invoice.paid", PayloadType: "billing.InvoicePaid",
		Description: "An invoice was paid in full.",
	}); err != nil {
		return err
	}
	reg.Events.Subscribe("authn.user_created", m.openCreditLedger)
	return nil
}
```

Booting a host:

```go
// The host's bootstrap target: go/pkgcore/config's loader fills it from
// flags, the environment, an optional config file and the struct's own
// defaults (a field may pin its exact variable name with config:"env=...").
var boot struct {
	DeploymentMode string
}
if err := config.New().Load(&boot); err != nil {
	return err
}
mode, err := pkgcore.ParseDeploymentMode(boot.DeploymentMode)

// A bare NewKernel() -- no options -- is DeploymentModeStandalone composed
// with PresetStandalone and needs nothing else. DeploymentModeDistributed
// requires every seam's resolved implementation to declare MultiReplicaSafe,
// which PresetStandalone's four in-process implementations do not, so a
// distributed host injects its own real ones and declares what they can do.
opts := []pkgcore.KernelOption{pkgcore.WithDeploymentMode(mode)}
if mode == pkgcore.DeploymentModeDistributed {
	const multiReplica = pkgcore.MultiReplicaSafe | pkgcore.SurvivesRestart
	opts = append(opts,
		pkgcore.WithEventBus(broker.NewEventBus(cfg), multiReplica),
		pkgcore.WithKVStore(redis.NewKVStore(cfg), multiReplica),
		pkgcore.WithMailer(smtp.NewMailer(cfg), multiReplica),
		pkgcore.WithObjectStore(s3.NewObjectStore(cfg), multiReplica))
}
reg, err := pkgcore.NewKernel(opts...).Bootstrap(ctx, tenancy.New(), billing.New())
```

A host that wants pkgcore's own Redis/SMTP/S3 implementations instead of
building its own reaches for `WithPreset(pkgcore.PresetDistributed)` in
place of the four `WithEventBus`/`WithKVStore`/`WithMailer`/`WithObjectStore`
calls above -- see `PresetDistributed`'s own doc comment for what it does and
does not source configuration for.

Returning an error:

```go
return apperr.NotFound("billing.subscription_not_found").WithParam("id", id)
```

Full runnable versions of all of the above live in `example_test.go` (the shared wiring and standalone-mode examples, the preset layer -- `ExampleWithPreset`'s per-item override and `ExampleSeamPreset`'s parameterized entry -- the local object store's constructor, and the SMTP mailer's construction; its blank imports of `eventbus/redis`, `kv/redis` and `objectstore/s3` are what let `ExampleWithPreset` and this test binary's internal `PresetDistributed` tests resolve those three built-ins for real, per the doc comment on those imports), each split-out subpackage's own `example_test.go` (`eventbus/redis`'s and `kv/redis`'s each demonstrate their constructor and the package's self-registration, aliasing their own import as `eventbusredis`/`kvredis` against go-redis's same `redis` package name; `objectstore/s3`'s needs no such alias; `eventbus/postgres`'s aliases as `eventbuspostgres`, mirroring the same convention for the same reason: its package name, `postgres`, is common enough (`gorm.io/driver/postgres`, `go/dbkit/dialect/postgres`) that an unaliased import would read ambiguously in a host file wiring more than one), plus `apperr/example_test.go`, `config/example_test.go` and `i18n/example_test.go`, and are executed by CI. `eventbus/postgres` is not among the blank imports pkgcore's own root `example_test.go` uses to resolve `PresetDistributed`'s built-ins for real, since `PresetDistributed` does not name it (see this file's own file-location section above) -- its self-registration is instead demonstrated by its own `example_test.go`'s `Example` function, mirroring `eventbus/redis`'s identical one. `kv/nats`'s own `example_test.go` aliases its import as `kvnats`, the same reason `eventbus/postgres` aliases as `eventbuspostgres`: its package name, `nats`, collides with `github.com/nats-io/nats.go`'s own package name, which the same file also imports unaliased for the `*nats.Conn` type. Unlike `kv/redis`'s example (which dials nothing and runs for real, carrying an `Output:` comment), `kv/nats`'s `ExampleNewKVStore` is compiled but never executed, since provisioning a JetStream bucket is a real round trip no example can perform without a live server -- `kv/nats` is like `eventbus/postgres` in this respect too, and is not among pkgcore's own root `example_test.go`'s blank imports for the identical `PresetDistributed`-does-not-name-it reason. Every subpackage's `example_test.go` also carries an `ExampleRegistration` demonstrating the name-registration factory path (the paragraph above names it); `kv/nats`'s is compiled but never executed, like its `ExampleNewKVStore`, since the factory's `New` provisions a JetStream bucket. `eventbus/redis`'s, `kv/redis`'s and `objectstore/s3`'s example files additionally carry `ExampleFromAddr`/`ExampleFromConfig`, the one-step constructors' runnable documentation, which run for real like their `New*` siblings since none of them dials.

## Rules

**Dependencies**

- Do not import any other speed module here, `dbkit` included -- `go/observability` too, even though it seems tempting for structured logging. pkgcore is the floor; an import from above is a cycle. That is why `Module.Migrations` returns a plain `embed.FS` rather than a `dbkit` type, and why the package's own log calls reach for the standard library's `log/slog` directly instead of `obs.FromContext` -- `warnIfNotDurable`'s `SurvivesRestart` startup warning, Bootstrap's one seam-composition Info line, and the memory bus's contained-panic Error line. The last can fire on any publish path; the floor cannot do better without importing `go/observability`, which would be a cycle (the same accepted trade each `eventbus/*` subpackage records on its own recover sites).
- Do not add a third-party dependency to the root package without arguing for it in the pull request: it lands in every consumer's `go.sum`. **The root package carries no third-party dependencies of its own**: the ones its subpackages need (go-redis, minio-go, jackc/pgx, nats.go, gomemcache) live behind each subpackage's own constructor, and no SDK type crosses a seam -- only a consumer that imports the subpackage itself pays for its dependencies, exactly as the packaging rule below intends. Go resolves dependencies per package, so a consumer of the root package alone inherits none of them; the claim is measurable at any time with a throwaway module that blank-imports only `github.com/vislake/speed/go/pkgcore` and runs `go mod tidy` under `GOWORK=off`. minio-go was chosen over the AWS SDK for the leaner dependency graph and for covering MinIO, Aliyun OSS and AWS S3 with one client.
- `kv/postgres`'s third-party cost is confined to its own subpackage: a consumer who never imports it inherits none of pgx's closure, and a consumer already on `go/dbkit`'s PostgreSQL dialect resolves the identical pgx version Go's minimal version selection already settled on, downloading nothing new. `kv.go` itself imports no `gorm` and no `go/dbkit`, which this package cannot depend on regardless (see the dependency-direction rule below).
- `eventbus/postgres`'s third-party cost follows the same confinement: its pgx/pgxpool closure is already present in any application that depends on `go/dbkit`'s PostgreSQL dialect, so for that consumer -- the ordinary one for a deployment that already runs PostgreSQL -- the subpackage adds no new third-party dependency at all, only a new import inside a module it already carries. That is a real advantage over `eventbus/redis` (which requires go-redis regardless of what else the application depends on) for a PostgreSQL-only deployment that has no other reason to run Redis.
- `kv/nats`'s third-party cost is the nats.go closure it shares with `eventbus/nats` -- the same pinned version, carried once in this module's root `go.mod` -- so the marginal cost of the second NATS subpackage is zero, and a consumer who imports neither pays nothing, per the packaging rule below.

**Interfaces, deployment modes and implementation composition**

- Do not expose a capability on an infrastructure interface that only one implementation can satisfy. Design against the weakest of that seam's registered implementations -- an anchor that moves as implementations are added, not a fixed "the standalone one": no server-side scripting, no pub/sub, no pipelines on `KVStore`.
- Do not branch on `DeploymentMode` outside kernel wiring. Business logic must not contain `if mode == DeploymentModeStandalone`: business code has no global mode value to branch on at all -- it only ever sees the `Registry`'s already-resolved `EventBus`/`KVStore`/`Mailer`/`ObjectStore`.
- Do not write a mock for `KVStore`, `EventBus`, `Mailer`, `ObjectStore` or `SMSSender`. `NewMemoryKVStore`, `NewMemoryEventBus`, `NewConsoleMailer`, `NewLocalObjectStore` and `NewConsoleSMSSender` are the test doubles; the four registry-backed in-process ones are also what `"kv.memory"`/`"eventbus.memory"`/`"mailer.console"`/`"objectstore.local"` adapt onto in the seam built-in files (`kv_builtins.go`, `eventbus_builtins.go`, `mailer_builtins.go`, `objectstore_builtins.go`; SMS has no registry entry -- see the `SMSSender` row above).
- Do not add a new in-process or stdlib-backed built-in's seam registration anywhere but the seam's own built-in file (`eventbus_builtins.go` for an eventbus built-in, `kv_builtins.go` for a kv one, `mailer_builtins.go` for a mailer one, `objectstore_builtins.go` for an objectstore one); that file is the one centralized place its seam's built-in `Registration`s live, mirroring the "single home" instinct the rest of the codebase already applies elsewhere (e.g. `@speed/api-client`'s HTTP seam) -- not a scattered `init()` per built-in. A built-in that pulls in a third-party dependency (a database/sql-driver-style implementation such as `eventbus/redis`, `kv/redis` or `objectstore/s3`) registers itself instead, from its own subpackage's own `init()`, precisely so that registering it does not require the dependency to live in this package -- see the "third-party dependency" rule above and each subpackage's own doc comment. Do not move such a registration into the seam built-in files "to keep them together": that would undo the dependency-isolation split.
- Do not declare a `Capability` an implementation does not actually have, and do not add a new `Capability` bit without updating `String()`. `Kernel.Bootstrap`'s validation trusts the declaration, not the value: `WithEventBus(bus, pkgcore.MultiReplicaSafe)` on a bus that is not multi-replica-safe passes assembly and fails silently later, in production, under real replica count -- the one thing this whole mechanism exists to catch.
- Do not hand-write a `Registration` for a backend whose implementation package already exports one. Every distributed implementation package exports a `Registration` factory beside the `Capabilities` constant its built-in registration declares, precisely so a host's name-registration carries the package's own constructor call and the one declaration assembly validates; a hand-rolled duplicate can drift from both. Hand-write a `Registration` only for an implementation no package owns.
- Do not expect `Kernel.Bootstrap` to fail an assembly for lacking `SurvivesRestart`. It logs a startup warning (via `log/slog`, since pkgcore cannot import `go/observability` -- see the dependency-direction rule below) and proceeds; losing state across a restart is a legitimate, deliberate choice for a throwaway or development composition, never a hard error. A `Stateless` implementation is exempt from even that warning: it holds nothing for a restart to drop, so a banner over it would name no loss (see `warnIfNotDurable`). Every boot also logs one Info line naming what the four seams resolved to -- the durability warnings are not the composition answer; the Info line is, and it must not be removed for the sake of quieting the warnings (a `Stateless` seam like `mailer.console` would otherwise boot in silence, hiding a forgotten `WithMailer(NewSMTPMailer(...))` that prints verification codes to stdout and reports success).
- Do not silently change an interface's semantics when adding an implementation. `kv/redis.NewKVStore` preserves the in-memory store's observable behaviour; where a Redis-backed bus cannot (asynchronous cross-process delivery, JSON payload shape, failures of remote handlers unobservable, no catch-up), the difference is documented on the constructor and spelled out to consumers before they choose it.
- Do not add a new implementation of `KVStore`, `EventBus`, `Mailer` or `ObjectStore` -- built-in or host-supplied -- without running that seam's capability-gated `AssertConforms` against it, passing the same capability bits the implementation declares (its `register.go` `init`, or the host's `With*` call, carries them; the package's `register_test.go` pins the registry to return exactly those). This is the mandatory conformance check the "Contract tests" section above documents; skipping it is how a new implementation quietly diverges from the contract the others honour -- and the gated form is what keeps a declaration a promise the suite verifies: an implementation declaring `MultiReplicaSafe` must run the cross-instance assertions (its pair is the verification), and one declaring no bit runs the single-instance checks only. A `KVStore` implementation that declares `SurvivesRestart` must additionally pass `kvstoretest.AssertSurvivesRestart`, called with those same declared bits, against a genuine restart of the service that holds the state -- its `caps` argument refuses a call that does not declare the bit, so the protocol run and the declaration cannot come apart -- and one that honestly does not declare the bit runs `AssertDoesNotSurviveRestart` (whose `caps` argument refuses the opposite mismatch) instead, pinning the factual basis of the non-declaration.
- Do not build a read-modify-write cycle out of `Get` + `Set`. Use `IncrByFloat`, `IncrByFloatWithTTL` or `CompareAndSwap`; they are the only operations every backend can make atomic. A caller-side `IncrByFloat` followed by a conditional `Set` to attach a ttl on the key's creation is exactly the race `IncrByFloatWithTTL` exists to close — prefer it outright for that case rather than hand-rolling a two-call sequence (see `IncrByFloatWithTTL`'s own doc comment).
- Do not retain or hand out a caller's byte slice in a `KVStore` implementation, and do not perform an operation on a cancelled context — return the context error instead.

**Tenancy**

- Do not treat a missing tenant as "all tenants". `MustTenantFromContext` returns `ErrNoTenant` so callers fail closed; propagate that error rather than defaulting.
- Do not pass a tenant through a bare string context key. Use `WithTenant`.
- Do not invent a system purpose at the call site. Declare it with `RegisterSystemPurpose` from the module's own registration; an undeclared purpose is refused.
- Do not call `WithSystemContext` without an `Actor`, and record a `Ticket` whenever one exists. Every bypass must be attributable.
- Do not treat a system context as an authorization bypass, and do not assume it bypasses tenant filtering either: this package's marker suppresses nothing by itself. The layers that own tenant filtering and data access decide what a system reason changes -- and several of them (dbkit's `Repository[T]` among them) never widen anything on its presence.

**Module contract**

- Do not add a method to `Module`. Under lockstep versioning that breaks all modules at once — add a field to `Registry` instead.
- Do not perform I/O in `Register`. It declares; the kernel decides when anything runs.
- Do not depend on module registration order. Declare the dependency in `DependsOn`; `Bootstrap` sorts, and reports a cycle or a missing dependency rather than guessing.
- Do not call a module's post-Bootstrap attach step before `Kernel.Bootstrap` returns: `config`, `rbac` and `integration` each expose `Attach(reg *pkgcore.Registry) (*<module>.Service, error)` and `admin` exposes `AttachRBAC(*rbac.Service)` — each exactly once, before the first host step that consumes the returned Service. No shared helper batches them: every `Attach` returns its own module's Service type, so no one interface is satisfied by all of them, and each host wires its own sequence (`Kernel.Bootstrap`'s "Post-Bootstrap module steps" section is the contract, including what an un-attached Service does when something reaches it).
- Do not swallow a registrar error. A duplicate key is a bug across modules, not a merge, and nothing is registered when the call returns an error.
- Do not publish a domain event the module never declared with `Events.Publishes`. The declarations are the catalog `integration` maps onto the versioned public event schema.
- Do not decorate a shared `apperr` value expecting the receiver to change. `WithParam` and `WithCause` derive a new error.

**Errors and configuration**

- Do not put human-readable text in an `apperr` code. The code is machine-readable and stable; the client resolves it through its own i18n catalog.
- Do not change or reuse a released `apperr` code. It is part of the public API contract.
- Do not surface a wrapped cause in an API response. `WithCause` is for logs and `errors.Is`.
- Do not put a value a client must not see into `WithParam`, and do not pass a struct, slice or map as a parameter: `Params` is serialized verbatim into the response body, unfiltered. Record server-side-only diagnostics with `WithSensitiveParam` (read back through `SensitiveParams()`), never in `Params`.
- Do not resolve runtime or tenant-overridable settings through `config.Loader`. It handles bootstrap values only: how to reach infrastructure, and which deployment mode is running.
- Do not hand-write the configuration reference. It is generated from the `ConfigItem` declarations.

**Internationalization**

- Do not translate API responses with `i18n`. Handlers return codes; the catalog renders backend-generated content only, in the recipient's locale — never the operator's.
- Do not add a language by editing `pkgcore/i18n`. The catalog's languages are its modules' files: a new language is one new `<language>.toml` file (its name a canonical BCP 47 tag) in every module that ships messages, and nothing else. The catalog's full-coverage guarantee is scoped to zh-CN/en-US; the mechanism itself is deliberately not frozen to those two languages.
- Do not ship a grouping section (`[errors]`) or an unquoted dotted header in a locale file. go-i18n folds the section name into the id; the contract is one flat top-level entry per message, id quoted and prefixed with the module's `Name` plus a dot.
- Do not let one locale drift from another. Every language a module ships must carry the same id set; `Builder.AddModule` fails with `ErrParityMismatch`, and `tools/check_i18n_keys.py` checks the same zh-CN/en-US parity over the raw files -- the docs-check pipeline runs it on doc/i18n-touching PRs (.github/workflows/docs-check.yml).
- Do not render a missing message in a fallback language. An unknown locale or code must surface as an error; the catalog never falls back silently.
- Do not add a third-party dependency to the root package for i18n. All i18n third-party dependencies live in the `i18n` subpackage: nicksnyder/go-i18n/v2 (the catalog machinery), BurntSushi/toml (the locale-file parser -- go-i18n ships no TOML decoder of its own, JSON only, and the flat shape is validated over BurntSushi's decode before go-i18n sees the messages, which is what rejects the [errors]-section id-folding a straight decode would produce), and golang.org/x/text, which the catalog code itself imports for its `language` package.

**Documentation**

- Do not add an exported identifier without a doc comment, an `Example` in the matching `example_test.go`, and an entry in the tables above, in the same pull request.

## Error index

| Sentinel | Triggered by | Handling |
|---|---|---|
| `ErrInvalidDeploymentMode` | `ParseDeploymentMode` on anything but standalone/distributed | Abort startup; the deployment mode is misconfigured |
| `ErrNoTenant` | `MustTenantFromContext` on an unscoped context | Fail closed. In a worker, rebuild the context with `WithTenant` |
| `ErrSystemActorRequired` | `WithSystemContext` with an empty `Actor` | Name the actor; the bypass is audited |
| `ErrSystemPurposeNotRegistered` | `WithSystemContext` with an undeclared purpose | Declare it with `RegisterSystemPurpose` |
| `ErrNotNumeric` | `IncrByFloat` on a key holding a non-number | The key is not a counter; the stored value is left untouched |
| `ErrInvalidMail` | `Mailer.Send` on a message with an empty From, no recipients, an empty recipient, a line break in a header, or no body | Validate the message; nothing reached the wire |
| `ErrInvalidObjectKey` | Any `ObjectStore` operation with a key that breaks the shared grammar (empty, overlong, an empty or `.`/`..` segment, NUL or backslash) | Validate the key before the call; nothing reached the backend. The error names the broken rule, never the key |
| `ErrObjectNotFound` | `ObjectStore.GetObject` on a key no object is stored under, every backend reporting the same sentinel | Handle absence as a normal outcome. `DeleteObject` never returns it: deleting a missing key is a success |
| `ErrDuplicateModuleName` | Two modules reporting the same `Name()` | Rename one; nothing was registered |
| `ErrDependencyCycle` | `DependsOn` forming a cycle | The error names the cycle; break it |
| `ErrMissingDependency` | Depending on a module absent from the bootstrap set | Add the module, or drop the dependency |
| `ErrInvalidConfigItem` | An item whose fields contradict one another: an unknown `Type`, a `Default`/`Min`/`Max` of the wrong Go type, `Min`/`Max` on a `string`/`bool` item, `Min` above `Max`, a `Default` outside its declared range, or `Sensitive` with `Public` | Fix the declaration; nothing was registered (the message never prints a sensitive item's value) |
| `ErrInvalidBootstrapKey` | A bootstrap declaration with an empty `Key`, an unknown `Format`, or `Sensitive` set with no `Description` | Fix the declaration; nothing was registered |
| `ErrDuplicateBootstrapKey` | The same bootstrap key registered twice (same call or across calls) | Two modules own one key; decide which does |
| `ErrInvalidBootstrapKeyPath` | `BootstrapKeyPurpose` on a path that is empty or carries an empty segment (a leading, trailing or doubled dot) | Fix the declaration's key path; nothing is derived under it. The error names the offending path -- declaration text, never secret material |
| `ErrDuplicateConfigKey` / `ErrDuplicateFeatureFlag` / `ErrDuplicatePermission` / `ErrDuplicateJobType` / `ErrDuplicateNotificationType` / `ErrDuplicateEventType` / `ErrDuplicateAuditAction` / `ErrDuplicatePeriodicTask` | The same key registered twice | Two modules own one key; decide which does |
| `ErrInvalidPeriodicTask` | A periodic-task declaration whose fields contradict one another: an empty `Type` or `KeyPrefix`, a non-positive `Every`, an unknown `Scope`, a platform-scope declaration without its `PlatformTenant`, or a per-tenant declaration carrying one | Fix the declaration; nothing was registered |
| `ErrUnresolvedFeatureDependency` | A flag depending on a flag nobody registered | Register the flag, or drop the dependency |
| `ErrCapabilityUnsatisfied` | `Bootstrap` resolving a seam (preset or injected) whose declared `Capability` does not satisfy `DeploymentMode.RequiredCapabilities()` | The error names the seam, the implementation and the missing capability; wire a qualifying implementation with `WithEventBus`/`WithKVStore`/`WithMailer`/`WithObjectStore`, or `WithPreset` a composition that already qualifies. There is no per-mode sentinel family: one error names the seam, implementation, missing capability and mode |
| `ErrUnknownImplementation` | `SeamRegistry.Build`, or `Bootstrap` resolving a `Preset` entry, naming an implementation nothing registered | Register it first, or fix the `Preset`/`Config` typo |
| `ErrDuplicateImplementation` | `SeamRegistry.Register` with a `Registration.Name` already registered on that registry | Pick a different name; the original registration is untouched |
| `ErrMissingSeamConfig` | A built-in `mailer.smtp` or `objectstore.s3` `Registration.New` called with a `Config` missing a field that has no safe default (SMTP host; S3 endpoint, bucket or credentials) | Supply the field in the preset entry's `Config` (see `ExampleSeamPreset`), or inject a hand-built value with `WithMailer`/`WithObjectStore` and an `SMTPConfig`/`s3.Config` |
| `eventbus/redis.ErrEventBusClosed` | `Publish` on an `eventbus/redis.EventBus` after `Close` | Wiring error: a closed bus is out of the deployment; build a fresh one. Lives in the `eventbus/redis` subpackage, not here -- nothing outside the Redis implementation ever referenced it as `pkgcore.ErrEventBusClosed`, so it moved with the implementation rather than staying a root-package sentinel one subpackage's type returns |
| `eventbus/postgres.ErrEventBusClosed` | `Publish` on an `eventbus/postgres.EventBus` after `Close` | Identical wiring-error treatment, mirroring `eventbus/redis.ErrEventBusClosed` exactly; lives in the `eventbus/postgres` subpackage for the same reason |
| `probe.ErrUnexpectedStatus` | `probe.Check` against a server answering a status other than the declared one | The error names the probed URL, the answered status and the expected one; report the container unhealthy. Request failures and an elapsed bound are plain wrapped errors (a `url.Error`/context error), not this sentinel -- only a completed request with the wrong status carries it |
| `config.ErrMissingValue` | A `config:"required"` field left zero | The error names the key and every source consulted |
| `config.ErrInvalidValue` | A supplied value not applicable to its field | The error names the offending key and its source |
| `config.ErrSourceUnreadable` | An unparseable config file or malformed flag | Fix the source; startup aborts |
| `config.ErrInvalidTarget` | `Load` given a non-struct-pointer or a bad `config` tag, or a target with derive fields and a configured root key but no installed deriver | Programming error; fix the target type or the wiring |
| `config.ErrInvalidRootKey` | The configured root key is not a 32-byte key: `WithRootKey` a non-empty key of another length, or `WithRootKeyEnv`'s variable set to a non-empty value that is not 64 hex characters | The error names the source (the option or the variable); an unset or emptied variable is an unconfigured root key, not an error |
| `i18n.ErrEmptyModuleName` | `Builder.AddModule` with an empty module name | Programming error; every module has a `Name()` |
| `i18n.ErrInvalidModuleName` | `Builder.AddModule` with a module name containing a dot | Programming error; the name is the `<module>.` prefix of every message id the module ships, and a dotted name would let two modules' id prefixes nest |
| `i18n.ErrDuplicateModule` | `Builder.AddModule` with a module already added | Register each module's locales exactly once |
| `i18n.ErrMissingLocaleFile` | A module shipping locale files but not one for every language of the catalog | Add the missing file; a module contributes every catalog language or none |
| `i18n.ErrUnsupportedLocale` | A locale file that is not a canonical language tag, or a file for a language the catalog does not serve | Fix the file name, or add the language to every message-shipping module |
| `i18n.ErrUnsupportedShape` | A file violating the flat contract: unquoted or dotted headers, a grouping section such as `[errors]`, reserved-key misuse, a table carrying both `translation` and a plural category, or a plural table with no translation | The error names the file and the entry; fix the TOML shape |
| `i18n.ErrParityMismatch` | The id sets of one module's locale files differing | The error names the languages and the missing ids; `tools/check_i18n_keys.py` checks the same zh-CN/en-US parity over the raw files -- the docs-check pipeline runs it on doc/i18n-touching PRs (.github/workflows/docs-check.yml) |
| `i18n.ErrUnknownLocale` | `Lookup`/`LookupPlural` for a locale no module ships | Programming error; the catalog never falls back to a default language |
| `i18n.ErrUnknownCode` | `Lookup`/`LookupPlural` for a code no module contributed | Programming error; the catalog never falls back to a default language |
