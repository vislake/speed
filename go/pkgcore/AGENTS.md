# pkgcore

The dependency floor of the monorepo. Every other Go module imports it; it imports no other speed module.

It owns seven things and nothing else:

| Concern | Where |
|---|---|
| The `Module` / `Registry` / `Kernel` wiring contract | `registry.go` |
| Tenant context and the audited escape hatch from tenant filtering | `tenant.go` |
| Infrastructure seam interfaces (`KVStore`, `EventBus`, `Mailer`, `ObjectStore`) plus each one's in-process implementation and its SMTP-backed one (stdlib `net/smtp`, so it earns no dependency-isolation benefit from a subpackage) | `kv.go`, `eventbus.go`, `mailer.go`, `objectstore.go`, `smtp_mailer.go` |
| The capability/registry/preset machinery `Kernel.Bootstrap` resolves and validates every seam through, and the five in-process/SMTP built-in `Registration`s it pre-populates (the three Redis- and S3-backed built-ins register themselves from their own subpackages -- see below) | `capability.go`, `seam_registry.go`, `preset.go`, `builtin_implementations.go` |
| The merged backend message catalog, assembled by `Bootstrap` from every module's `Locales()` embed.FS | `i18n/` (+ `locales/`, pkgcore's own seed message files) |
| The `DeploymentMode` enumeration (a topology declaration only -- see "Deployment mode and implementation composition" below) | `deployment_mode.go` |
| The mandatory conformance suite for each seam, and the two conformance runs of every in-process/SMTP built-in implementation | `eventbustest/`, `kvstoretest/`, `mailertest/`, `objectstoretest/` (suites); `*_conformance_test.go` (runs; the SMTP leg needs no Docker, see below) |

Three subpackages: `apperr` (the structured application error every module returns), `config` (the bootstrap configuration loader, run once at process startup) and `i18n` (the message catalog backend-generated content is rendered through, on nicksnyder/go-i18n). `locales/` is the seed bundle `i18n` needs to load pkgcore's own messages.

Four more subpackages carry the Redis-, S3- and PostgreSQL-backed built-in implementations that used to sit in this package's own root -- `eventbus/redis` (`EventBus`'s distributed-mode implementation on Redis Streams, registering `"eventbus.redis"`), `eventbus/postgres` (`EventBus`'s OTHER distributed-mode implementation, on PostgreSQL `LISTEN`/`NOTIFY` backed by a durable outbox table, registering `"eventbus.postgres"` -- the genuinely zero-extra-infrastructure option for a deployment that already runs PostgreSQL and does not want to stand up Redis purely for this one seam; see its own package doc comment and `EventBus`'s delivery-semantics note for the full contract, and this file's Public API table below), `kv/redis` (`KVStore`'s, registering `"kv.redis"`), and `objectstore/s3` (`ObjectStore`'s, on any S3-compatible service, registering `"objectstore.s3"`) -- moved out under issue #1's "put a backend implementation in the same package as the interface it implements" finding (see this file's own Rules section and the implementation-registry section of docs/internal/03-deployment-modes.md): Go resolves dependencies per package, so a consumer of this root package no longer inherits go-redis, jackc/pgx or minio-go merely by importing `pkgcore`. Each subpackage self-registers its implementation on the matching package-level `SeamRegistry` through its own `init()`, the `database/sql` driver pattern `seam_registry.go` was already modelled on; a distributed-mode host that wants a built-in Redis, PostgreSQL or S3 implementation through `WithPreset` must import the matching subpackage (a blank import is enough) and, for `eventbus/postgres` specifically, name it in a Preset of its own -- `PresetDistributed` still points the `"eventbus"` seam at `"eventbus.redis"`, unchanged by this addition -- or resolution fails at `Bootstrap` time with `ErrUnknownImplementation` naming the seam and implementation -- the accepted "compile-time error becomes a run-time one" trade every `database/sql` driver makes. Calling a subpackage's own constructor directly and wiring it with `WithEventBus`/`WithKVStore`/`WithObjectStore` needs no import-for-side-effect at all, since that path never goes through the registry. Each subpackage carries its own unit tests, its own `example_test.go`, and its own `integration_test/` (Docker-backed, `-tags=integration`) -- physically separate per package, per this repository's testing-layout rule, not shared with this package's own (Docker-free) unit tier. `eventbus/postgres` additionally carries its own `migrations/postgres/` (a single versioned SQL file for its outbox and cursor tables, embedded and applied through its own `EnsureSchema` rather than `dbkit.MigrationRegistry` -- this package cannot import `go/dbkit`, which sits above it in the dependency graph, so it cannot use that machinery directly; see the migration file's own doc comment) and no `migrations/sqlite/` sibling at all, a deliberate, documented exception (see that file's own header) since the mechanism is inherently PostgreSQL-specific and the standalone deployment mode never runs it.

A fifth subpackage, `eventbus/nats`, is a third distributed-mode `EventBus` implementation rather than a moved-out one -- docs/internal/03-deployment-modes.md's seam table used to name NATS a candidate; this subpackage makes it real, following the identical split and registering `"eventbus.nats"` the same way. It is not part of either built-in `Preset` (`PresetDistributed`'s `"eventbus"` entry still names `"eventbus.redis"`); a host that wants it calls `EventBusRegistry.Build("eventbus.nats", cfg)` or `NewEventBus` directly with `WithEventBus`. Delivery semantics are deliberately identical to `eventbus/redis`'s -- fan-out to every replica, never load-balanced to one -- reached through JetStream's durable pull consumers instead of Redis consumer groups: every bus instance creates its own uniquely-named consumer on each event type's stream, so JetStream's own load-balancing (which only applies between two readers of the *same* consumer name) never triggers between instances. See the package's own doc comment for the full contract and its `integration_test/`'s `TestEventBus_FanOutDeliversToEveryReplica` for the real-server proof.

`kv/postgres` is a fifth such subpackage, and the first to register a *second* implementation of a seam an earlier subpackage already covers: `KVStore` backed by a single PostgreSQL table (`pkgcore_kv_entries`) with a TTL column, registering `"kv.postgres"` on the same `KVStoreRegistry` `kv/redis` registers `"kv.redis"` on -- the genuinely zero-extra-infrastructure option for a deployment that already runs PostgreSQL and does not want to stand up Redis purely for this one seam, mirroring `eventbus/postgres`'s identical rationale for the `EventBus` seam. `PresetDistributed` still points `"kv"` at `"kv.redis"`; a host wanting `"kv.postgres"` instead builds its own `Preset` naming it, or bypasses the preset layer entirely with `kv/postgres.NewKVStore` and `WithKVStore`. `NewKVStore` takes a `*pgxpool.Pool` directly (never a `*gorm.DB`), so a host already running `dbkit.Open` for its business tables shares the exact same connection credentials at the cost of one small, dedicated second pool rather than reaching into `dbkit`'s own internals for one. Both `IncrByFloat` and `CompareAndSwap` are single, database-arbitrated SQL statements -- an `INSERT ... ON CONFLICT DO UPDATE` upsert for the former, a `WITH` CTE combining an `UPDATE` (the "key exists" path) and an `INSERT ... ON CONFLICT DO NOTHING` (the "key genuinely absent" path) for the latter -- never a Go-level read-modify-write, proved race-free under real concurrent callers by the package's own `TestKVStore_ConcurrentIncrementsLoseNoUpdates` and `TestKVStore_ConcurrentCompareAndSwapSetIfAbsent_ExactlyOneWinner` in its `integration_test/` tier, the same discipline `go/billing`'s `applyBalanceDelta` established for its own single-`UPDATE` arithmetic guard. Unlike `kv/redis` (Redis's native active expiry), PostgreSQL has no equivalent: every read and write treats an expired row as absent (a `WHERE expires_at IS NULL OR expires_at > now()` guard, mirroring `pkgcore.memoryKVStore`'s own lazy-drop precedent) but does not physically remove it until something touches the key again or a host calls the package's own `Store.Sweep` -- a plain, one-shot `DELETE` a host runs on its own schedule (no owned goroutine, no automatic call from `NewKVStore`), which is why `NewKVStore` returns the concrete `*Store` rather than the bare `pkgcore.KVStore` interface: `Sweep` is a capability outside what `KVStore` itself has room for. `pkgcore_kv_entries`' migration (`migrations/postgres/0001_create_pkgcore_kv_entries.sql`) has no `sqlite/` counterpart -- following `eventbus/postgres`'s identical precedent -- since the standalone deployment mode never runs this implementation at all (`pkgcore.NewMemoryKVStore` covers it with no database of its own); `schema.go`'s `EnsureSchema` is this package's own self-contained migration applier (idempotent `CREATE TABLE/INDEX IF NOT EXISTS`, no `schema_migrations` ledger), built the same way `eventbus/postgres.EnsureSchema` is, for the identical reason: `go/pkgcore` cannot import `go/dbkit`, which sits above it.

A further subpackage, `kv/memcached`, is a third distributed-mode `KVStore` implementation, added the identical way -- a package of its own from day one, on `github.com/bradfitz/gomemcache` (a genuinely zero-third-party-dependency client: a throwaway module blank-importing it alone carries no `// indirect` entries at all under `GOWORK=off go mod tidy`, the lowest measured cost of any built-in implementation in this file). Read its package doc comment before choosing it over `kv/redis`: it is honestly declared `MultiReplicaSafe` only, never `SurvivesRestart` -- Memcached is a pure in-memory cache with no persistence mechanism of any kind, so a restart, a rolling upgrade or ordinary LRU eviction under memory pressure silently drops everything it holds. That honest declaration is also why no built-in `Preset` names `"kv.memcached"` (`PresetDistributed`'s `"kv"` entry still names `"kv.redis"`); a host that wants it calls `KVStoreRegistry.Build("kv.memcached", cfg)` or `NewKVStore` directly with `WithKVStore`. Memcached's own primitives are narrower than every other KVStore backend here -- native `incr`/`decr` are 64-bit unsigned integer only, with no float support at the protocol level, and no atomic whole-value compare exists at all -- so `IncrByFloat` and `CompareAndSwap` are both bounded compare-and-swap retry loops over Memcached's native `gets`/`cas`/`add`; and its native per-key expiry is granular only to the whole second, which the shared `kvstoretest.AssertConforms` suite's millisecond-scale TTLs would silently violate without this store's own client-side logical-expiry envelope layered on top of Memcached's coarser physical one (see the package doc comment for the full design and its inherent year-2038 boundary for an extremely long ttl). See the package's own doc comment for the full contract and its `integration_test/` for the real-server proof, including two adversarial concurrency tests (`IncrByFloat` losing no update under many racing goroutines; `CompareAndSwap`'s set-if-absent form letting exactly one racing goroutine win) that only a real server's compare-and-swap primitives can exercise honestly.

Another subpackage, `kv/nats`, carries a fourth distributed-mode `KVStore` implementation (alongside `kv/redis`, `kv/postgres` and `kv/memcached`), on a NATS JetStream KV bucket, registering `"kv.nats"` the identical database/sql-style way `kv/redis` registers `"kv.redis"` -- but, unlike the subpackages above, `"kv.nats"` is **not** named by `PresetDistributed`: this subpackage only makes the name resolvable on `KVStoreRegistry`, it does not change what any existing `Preset` picks by default. A host that wants NATS instead of Redis, PostgreSQL or Memcached for the `"kv"` seam either builds its own `Preset` naming `"kv.nats"` (after blank-importing `kv/nats` so the name resolves) or calls `kv/nats.NewKVStore` directly and wires it with `WithKVStore`. JetStream KV gives only a per-subject last-sequence ("revision") compare, never a native atomic increment or a native compare-by-value, so this implementation's `CompareAndSwap` and `IncrByFloat` are both built on that one revision check (`Update(key, value, revision)` failing `ErrKeyRevisionMismatch`, or `Create` failing `ErrKeyExists`, both mapped to "the swap did not happen" rather than an error) -- `IncrByFloat` wraps the same check in a bounded (200-attempt), exponentially-backed-off retry loop, since no server-side atomic float op exists to lean on instead. Expiry is carried in an 8-byte big-endian Unix-nanosecond header this implementation prefixes onto every stored value itself, never in the bucket's own TTL (a whole-bucket setting that cannot express "an increment keeps a live key's existing expiry, but starts a fresh key with none"), and every opaque `pkgcore.KVStore` key is hex-encoded before it reaches JetStream, since that store's own key charset excludes characters (a colon, notably) this repository's own KVStore tests use freely. Unlike `kv/redis`'s `NewKVStore`, which dials nothing, provisioning a JetStream KV bucket is itself a round trip the server must answer, so `kv/nats.NewKVStore` takes a `context.Context` and can fail. `eventbus/nats` (above) is this repository's first consumer of `nats.go`; this subpackage is the second, and shares the exact same `github.com/nats-io/nats.go v1.53.1` dependency closure `eventbus/nats` already put on this module's root `go.mod` -- see docs/internal/03-deployment-modes.md's implementation-status section for the measured, zero-incremental-cost detail. `.golangci.yml`'s `nats-only-in-pkgcore` depguard rule exempts both subpackages under the one rule name rather than each round adding its own same-named key. Its own `integration_test/` (Docker-backed, JetStream-enabled) runs the shared `kvstoretest.AssertConforms` plus two adversarial concurrency proofs (many goroutines racing `IncrByFloat` on one key with no lost update; many goroutines racing `CompareAndSwap` set-if-absent on one key with exactly one winner) and a real server-restart reconnect proof.

Four more subpackages, `eventbustest`, `kvstoretest`, `mailertest` and `objectstoretest`, hold one `AssertConforms` contract-test suite per infrastructure seam -- the mandatory conformance check every implementation of that seam, built-in or host-supplied, must pass. They play the same role for these four seams that `go/tenancy/tenancytest.AssertIsolated` plays for `dbkit.Repository[T]`: with N registered implementations per seam under the deployment-composition retrofit, drift between them is caught in one shared suite instead of pairwise. See "Contract tests" under Public API below.

**Out of scope.** Database access (`dbkit`), tenant enforcement in SQL (`tenancy`), logging and tracing (`observability`), runtime and tenant-overridable configuration (the `config` *module*, not this `config` package), job execution (`jobs`). pkgcore declares contracts; it does not implement business behaviour.

**Capability declarations, the seam registry and presets** -- the machinery `Bootstrap`'s seam resolution above is built on; see "Deployment mode and implementation composition" below for the design this implements.

A host registers its own implementation on the matching one before bootstrapping a `Kernel` whose `Preset` names it |
| `type Preset map[string]string` | Seam key (`"eventbus"`, `"kv"`, `"mailer"`, `"objectstore"`) to implementation name |

Built-in implementation names: `eventbus.memory`, `eventbus.redis`, `eventbus.postgres`, `kv.memory`, `kv.redis`, `mailer.console`, `mailer.smtp`, `objectstore.local`, `objectstore.s3` -- each a thin `Config`-consuming adapter over an unchanged typed constructor (`NewMemoryEventBus`, ...). `eventbus.memory`, `kv.memory`, `mailer.console`, `mailer.smtp` and `objectstore.local` register here, in `builtin_implementations.go`; `eventbus.redis`, `eventbus.postgres`, `kv.redis` and `objectstore.s3` register themselves from their own subpackages (`eventbus/redis`, `eventbus/postgres`, `kv/redis`, `objectstore/s3` -- see this file's file-location table above), so they are visible on `EventBusRegistry`/`KVStoreRegistry`/`ObjectStoreRegistry` only once a host has imported the matching subpackage. The Redis-backed adapters fall back to `"localhost:6379"` when `cfg["addr"]` is unset; the SMTP, S3 and PostgreSQL adapters have no safe default credentials and fail with a config error (`ErrMissingSeamConfig` for SMTP/S3; a plain `fmt.Errorf` for `eventbus.postgres`'s required `"dsn"`/`"replica_id"` pair) instead of calling their panicking constructor with an empty field.

A ninth name, `kv.postgres`, was added after this retrofit round by `kv/postgres`'s own `init()` (see the file-location table above): a second registered implementation of the already-existing `"kv"` seam, alongside `kv.redis`, neither replacing nor renaming it. Like the Redis and S3 adapters it has no safe zero-configuration default (no universal PostgreSQL DSN the way `"localhost:6379"` is for Redis) and fails with a plain error naming the missing `cfg["dsn"]` key rather than dialing an empty one.

A tenth name, `eventbus.nats`, and an eleventh, `kv.nats`, were added by `eventbus/nats`'s and `kv/nats`'s own `init()`s respectively (see the file-location table above): a second implementation of the already-existing `"eventbus"` seam and a third of the already-existing `"kv"` seam. Neither is named by `PresetStandalone` or `PresetDistributed` -- registering either only makes its name resolvable on the matching registry; a host names it in a `Preset` of its own or injects it directly with `WithEventBus`/`WithKVStore`. Both fall back to `nats.DefaultURL` ("nats://127.0.0.1:4222") when a host builds them through their own constructor without a connection already in hand, the same zero-configuration-default posture the two Redis-backed adapters take with `"localhost:6379"`.

Registrar interfaces: `RouteRegistrar`, `ConfigSchemaRegistrar`, `FeatureRegistrar`, `PermissionRegistrar`, `JobHandlerRegistrar`, `NotificationRegistrar`, `EventRegistrar` (`Publishes` / `Published` / `Subscribe` / `Bus`), `AuditActionRegistrar`.

`ConfigItem` declarations are validated when registered: `Type` must be one of `string` / `int` / `bool` / `duration`; a non-nil `Default` must be a Go value of that kind (`string`, `int` or `int64`, `bool`, `time.Duration`; nil is legal and means "no value until one is set"); `Min`/`Max` are declarative ranges defined for `int` and `duration` items only, must satisfy `Min <= Max`, and a non-nil `Default` must fall inside them; `Sensitive` and `Public` are mutually exclusive. A contradictory declaration fails the whole `Add` call with an error wrapping `ErrInvalidConfigItem` -- see the error index below.


**Deployment mode and implementation composition**

These are two orthogonal axes (`docs/internal/03-deployment-modes.md` is the authority): deployment mode declares topology -- how many replicas may run at once -- and therefore which capabilities every seam's resolved implementation must have; it never selects an implementation. `Kernel.Bootstrap` is the one place that compares the two, per seam, using `validateSeamCapability`.

`type DeploymentMode string`, constants `DeploymentModeStandalone` / `DeploymentModeDistributed`, `func ParseDeploymentMode(string) (DeploymentMode, error)` (trims and lowercases), `func (DeploymentMode) Valid() bool` (exact match, so `"Standalone"` is not valid), `func (DeploymentMode) RequiredCapabilities() Capability` (`DeploymentModeDistributed` → `MultiReplicaSafe`; everything else, including an invalid value `Bootstrap` would have already rejected via `Valid()`, → `0`).

| Signature | Purpose |
|---|---|

**Infrastructure interfaces**

| Signature | Purpose |
|---|---|
| `type KVStore interface { Get; Set; Delete; IncrByFloat; IncrByFloatWithTTL; CompareAndSwap }` | Key-value contract, designed against the weakest backend. `IncrByFloatWithTTL(ctx, key, delta, ttl) (float64, error)` closes the one caller-side TTL-attachment race `IncrByFloat` alone could not: it atomically attaches `ttl` as the key's expiry on the exact call that creates it, and leaves a live key's existing expiry untouched (never extending it), collapsing what used to be a caller-side increment-then-conditionally-Get-then-Set sequence into one atomic step. `go/ratelimit`'s sliding-window counter is the first consumer, converging its window-key creation path onto this primitive; every backend implements it as one atomic operation, never as two calls a caller could still race between |

### Seam lifecycle, one-clock TTLs and panicking remote handlers

- `func (*Kernel) Shutdown() error` closes every seam implementation a `Bootstrap` of that Kernel resolved from a Preset whose value implements `Close() error` — the resource-ownership contract `Registration`'s doc comment states. An implementation whose `New` builds resources it owns (a dialed NATS connection, a Redis client or pgx pool built from cfg, a throwaway temp directory) declares the ownership by implementing `Close() error` on the value it returns; `Bootstrap` records it and releases it exactly once — at `Shutdown` on success, or on `Bootstrap`'s own failure path, immediately, so a misconfigured composition never leaks what it already dialed. An injected seam (`WithEventBus` and siblings) is the host's to close and is never touched. The built-in registrations in `eventbus/redis`, `eventbus/nats`, `eventbus/postgres`, `kv/redis`, `kv/postgres`, `kv/nats` and the `objectstore.local` preset each return such a closeable value over the client/pool/connection/directory the registration itself built; `mailer.smtp`, `objectstore.s3` and `kv.memcached` own no closable resource (the S3 and memcached clients expose no close).
- Expiry arithmetic on the PostgreSQL-backed store (`kv/postgres`) and outbox (`eventbus/postgres`) runs entirely on the database clock: `Set`/`IncrByFloatWithTTL` store `now() + <interval>` computed inside the statement, reads judge against `now()`, outbox `created_at` is stamped by `now()` at insert, and `PurgeOutboxBefore` cuts off at `now() - <interval>` — no application clock is consulted anywhere, so replica/database clock skew cannot shorten or stretch a TTL (a security control must not be judged early by a clock disagreement). `kv/postgres`'s `WithClock` option is the explicit regression seam for that property (the store never calls it). `kv/nats` and `kv/memcached` carry expiry inside the value envelope and judge it on the reading replica's clock — documented per-backend; adopting NATS's server-side per-key TTL is not viable on the pinned nats.go v1.53.1 / nats-server pair because any header-less Put/Update (the only kind the KeyValue API can issue) clears the per-key TTL, which cannot express "increment preserves a live key's expiry" (see `kv/nats`'s package doc comment).
- `kv/nats.NewKVStore` probes first and adopts an existing bucket untouched; it creates (never update-overwrites) an absent one and resolves a create race by re-probing and adopting the winner. `kv/memcached` never deletes a logically expired row on the read path — a stale read's unguarded `Delete` used to be able to destroy a concurrent writer's fresh value — and revives an expired-but-physically-present key through the server's compare-and-swap at the token the read returned, exactly like `kv/nats`'s revision-guarded revive.
- A remote event-bus handler that panics is recovered (so one buggy handler cannot take down a replica) and logged, never silently swallowed; the entry is not acked-as-delivered: `eventbus/redis` leaves it pending in the consumer group (never refetched — the reader consumes new entries only — so no stall and no sibling re-run), `eventbus/nats` leaves it unacknowledged (JetStream redelivers it after the consumer's AckWait), and `eventbus/postgres` advances its cursor past the row like a clean delivery — so later same-type rows keep flowing and healthy sibling handlers never re-run — while retrying the still-panicking handler values in-process on a bounded attempt budget, settling with a terminal log line when the budget is exhausted (see `eventbus/postgres`'s `retryPanickedRows`).

### `pkgcore/apperr`

`type Error struct { Code string; Params map[string]any; Status int }` with `Error()`, `Unwrap()`, `WithParam(key, value) *Error`, `WithCause(error) *Error`.

Constructors and the status each suggests: `Invalid` 400, `Unauthorized` 401, `Forbidden` 403, `NotFound` 404, `Conflict` 409, `Internal` 500. `func As(error) (*Error, bool)` recovers one from a wrapped chain.

`WithParam` and `WithCause` return a *derived* `*Error` and leave the receiver untouched, so a package-level error value can be shared and decorated per request.

### `pkgcore/config`

`func New(opts ...Option) *Loader` with `WithConfigFile(path)`, `WithArgs([]string)`, `WithEnviron([]string)`; `func (*Loader) Load(target any) error`.

Priority, highest first: command-line flags, environment variables, config file, the defaults already on the target struct. `Database.DSN` maps to key `database.dsn` (segments joined by `KeyDelimiter`), flag `--database.dsn`, variable `SPEED_DATABASE__DSN` (`EnvPrefix` + `EnvSeparator`). Per-field options come from the `TagName` struct tag: `config:"required"`, `config:"-"`.

### `pkgcore/i18n`

The merged message catalog. `func NewBuilder() *Builder`; `func (*Builder) AddModule(module string, fsys fs.FS) error`; `func (*Builder) Build() *Catalog`. `func (*Catalog) Lookup(locale, code string, params map[string]any) (string, error)`; `func (*Catalog) LookupPlural(locale, code string, count int64, params map[string]any) (string, error)`; `func (*Catalog) Locales() []string`. Locale constants `LocaleZHCN` / `LocaleENUS`; sentinel errors `ErrEmptyModuleName`, `ErrInvalidModuleName`, `ErrDuplicateModule`, `ErrMissingLocaleFile`, `ErrUnsupportedLocale`, `ErrUnsupportedShape`, `ErrParityMismatch`, `ErrUnknownLocale`, `ErrUnknownCode`.

What it is for, and the file contract, live in the package doc; the summary that must survive into consuming modules: API responses are never translated on the backend — handlers return an `apperr` code plus params, the client resolves them — and the catalog renders the content the backend generates itself (emails, invoices, webhook text, audit descriptions), in the *recipient's* locale. `Kernel.Bootstrap` feeds every module's `Locales()` embed.FS to one `Builder` per bootstrap (mirroring dbkit's `MigrationRegistry` aggregation) and installs the frozen `Catalog` on the registry; a module reaches it through `Registry.Locales()`, nil on a hand-built registry. A built `Catalog` is read-only and safe for concurrent use. Rendering fails loudly: unknown locale or code is an error, never a silent English fallback; template syntax errors surface at render time. Plural categories follow CLDR (zh-CN has only `other`; en-US has `one`/`other`); `count` selects the category while the template reads it from `params`.

### `pkgcore/locales`

pkgcore's own seed message bundle (`zh-CN.toml` + `en-US.toml`, embedded as `locales.FS`): one message per catalog shape (plain, parameterized, plural), phrased as real sentences about pkgcore. pkgcore renders no user-facing content in M0 — the seed set is the honest stand-in that exercises the machinery end to end and templates every module's own bundle; drop the seeds when pkgcore ships real messages.

Each `AssertConforms` calls `t.Run` once per property it checks and calls `factory` once per subtest, so a factory whose backend is not reusable across calls (a fake relay wired to expect one connection, say) is safe to hand in, and a failure's subtest name says which property broke. `factory` is not required to return an empty-state instance -- every subtest derives its own key/event-type/message from the subtest name (or, for `mailertest`, uses fixed-shape messages that never collide), so several subtests can safely share one long-lived backend (a single Redis container, a single S3 bucket) without colliding, which is exactly what the Redis/RustFS integration legs below do.

Every in-process or SMTP built-in implementation runs its matching suite in this package's own unit tier: `eventbus_conformance_test.go`, `kv_conformance_test.go`, `mailer_conformance_test.go` and `objectstore_conformance_test.go` (package `pkgcore_test` -- an external test package, because each imports the seam's `*test` package, which itself imports `pkgcore`, and an internal `package pkgcore` test file importing that back would be an import cycle) run `NewMemoryEventBus`/`NewMemoryKVStore`/`NewConsoleMailer`+`NewSMTPMailer`/`NewLocalObjectStore` through `AssertConforms`. The SMTP leg needs no Docker: it scripts an in-process fake relay (`internal/testutil/fake_smtp_server.go`), so it lives in the plain unit tier alongside the other three memory/console/local legs. The seven Redis-, PostgreSQL-, NATS- and S3-backed implementations run the identical call against a real Redis/PostgreSQL/NATS/MinIO container from their own subpackage's own `integration_test/` (`-tags=integration`, Docker required) -- `eventbus/redis/integration_test/`, `eventbus/postgres/integration_test/`, `eventbus/nats/integration_test/`, `kv/redis/integration_test/`, `kv/postgres/integration_test/`, `kv/nats/integration_test/` and `objectstore/s3/integration_test/` -- rather than a shared one here, per this repository's testing standard that a package's integration tests live in its own `integration_test/` directory. `eventbus/postgres/integration_test/` additionally carries the real-server proofs beyond `AssertConforms` that no other seam's tier needs: an explicit fan-out proof (two bus instances, distinct `replicaID`s, sharing one pool, both Subscribed -- both receive one Publish); an explicit catch-up proof in both of its shapes -- a full process restart under the same `replicaID`, and a live listener connection severed and reconnected mid-test (`pg_terminate_backend` against the container) -- since a durable, genuinely-earned `SurvivesRestart` is this implementation's whole reason to exist over `eventbus/redis`'s; a re-entrant-publish pair proving a handler may `Publish` on the bus that invoked it without deadlocking on either delivery arm; a cursor-advance-retry proof that a connection loss between a row's delivery and its cursor advance never duplicates the row; and the two no-loss regressions pinning the healthy-path exactly-once guarantee -- same-type publishes serialized into id order by a per-type advisory transaction lock inside every publish transaction, and a local publish never advancing the persisted cursor past same-type rows this replica's own lagging listener has not delivered yet (`TestEventBus_LaggingPoller_LocalPublishMustNotSkipUnseenRemoteRows` and `TestEventBus_ConcurrentMultiReplicaPublish_NoEventLostNoDuplicate`; see the package doc comment's delivery-semantics note for why the crash windows that degrade this to at-least-once are accepted and documented rather than papered over). `eventbus/nats/integration_test/` carries the analogous fan-out proof for its own implementation, `TestEventBus_FanOutDeliversToEveryReplica` (two independent `*nats.Conn`s, one Publish, both replicas' handlers fire), the same property `eventbus/redis` and `eventbus/postgres` are each documented and tested to have. `kv/postgres/integration_test/` runs the same call against a real PostgreSQL container, alongside the two adversarial concurrency proofs `TestKVStore_ConcurrentIncrementsLoseNoUpdates` and `TestKVStore_ConcurrentCompareAndSwapSetIfAbsent_ExactlyOneWinner` that `AssertConforms` alone (effectively single-threaded) cannot exercise. A host registering a new implementation on `EventBusRegistry`/`KVStoreRegistry`/`MailerRegistry`/`ObjectStoreRegistry`, or injecting one directly through `WithEventBus`/`WithKVStore`/`WithMailer`/`WithObjectStore`, is expected to run the matching `AssertConforms` against it the same way, per this file's own Rules section.

`internal/testutil` holds `FakeSMTPServer`, the scripted SMTP relay `smtp_mailer_test.go`'s own wire-level tests and `mailer_conformance_test.go`'s SMTP leg both drive -- moved there once a second consumer needed it, rather than a second, drifting copy of the same fake, per the backend coding standard's shared-test-helper rule. It deliberately does not import `pkgcore` itself (only `pkgcore`'s own unexported-symbol tests, which are `package pkgcore`, need `SMTPConfig`/`NewSMTPMailer` to build a `pkgcore.Mailer` around a `FakeSMTPServer`, and `testutil` importing `pkgcore` back would make that an import cycle); each caller therefore builds its own few-line `pkgcore.Mailer` wrapper around `FakeSMTPServer.Addr()`.

```go
	if err := reg.Config.Add(pkgcore.ConfigItem{
		Key: "billing.invoice_retry_limit", Type: "int", Default: 3,
		Description: "How many times a failed invoice charge is retried.",
	}); err != nil {
		return err
	}
	if err := reg.Permissions.Add("billing:read", "billing:write"); err != nil {
		return err
	}
	if err := reg.Events.Publishes(pkgcore.EventDecl{
		Type: "billing.invoice.paid", PayloadType: "billing.InvoicePaid",
		Description: "An invoice was paid in full.",
	}); err != nil {
		return err
	}
	reg.Events.Subscribe("authn.user_created", m.openCreditLedger)
	return nil
}
```

Booting a host:

```go
mode, err := pkgcore.ParseDeploymentMode(os.Getenv("SPEED_DEPLOYMENT_MODE"))

// A bare NewKernel() -- no options -- is DeploymentModeStandalone composed
// with PresetStandalone and needs nothing else. DeploymentModeDistributed
// requires every seam's resolved implementation to declare MultiReplicaSafe,
// which PresetStandalone's four in-process implementations do not, so a
// distributed host injects its own real ones and declares what they can do.
opts := []pkgcore.KernelOption{pkgcore.WithDeploymentMode(mode)}
if mode == pkgcore.DeploymentModeDistributed {
	const multiReplica = pkgcore.MultiReplicaSafe | pkgcore.SurvivesRestart
	opts = append(opts,
		pkgcore.WithEventBus(broker.NewEventBus(cfg), multiReplica),
		pkgcore.WithKVStore(redis.NewKVStore(cfg), multiReplica),
		pkgcore.WithMailer(smtp.NewMailer(cfg), multiReplica),
		pkgcore.WithObjectStore(s3.NewObjectStore(cfg), multiReplica))
}
reg, err := pkgcore.NewKernel(opts...).Bootstrap(ctx, tenancy.New(), billing.New())
```

## Rules

**Dependencies**

- Do not import any other speed module here, `dbkit` included -- `go/observability` too, even though it seems tempting for structured logging. pkgcore is the floor; an import from above is a cycle. That is why `Module.Migrations` returns a plain `embed.FS` rather than a `dbkit` type, and why `warnIfNotDurable`'s `SurvivesRestart` startup warning reaches for the standard library's `log/slog` directly instead of `obs.FromContext` -- the one call site in the package that logs anything, and it runs only at `Bootstrap` time, never on a request path.
- Do not add a third-party dependency to the root package without arguing for it in the pull request: it lands in every consumer's `go.sum`. **The root package carries zero third-party dependencies of its own today** -- measured: a throwaway module that blank-imports only `github.com/vislake/speed/go/pkgcore` and runs `go mod tidy` under `GOWORK=off` picks up exactly the same three `// indirect` entries `pkgcore/i18n` alone costs (BurntSushi/toml, nicksnyder/go-i18n/v2, golang.org/x/text; koanf sits one level deeper, in the `config` subpackage, so it does not even reach a root-package consumer's `go.mod`), down from 23 before this round's split. Go resolves dependencies per package, and go-redis v9 and minio-go v7 used to sit in this package's own root (`redis_kv.go`, `redis_eventbus.go`, `s3_objectstore.go`), so every consumer of `pkgcore` inherited both SDKs' whole dependency closures whether or not it ever wired a Redis- or S3-backed seam -- a 20-dependency gap (23 down to 3), issue #1's widest-blast-radius site since every other module in this repository imports this root package. They now live in `eventbus/redis`, `kv/redis` and `objectstore/s3` respectively (see the file-location table above): minio-go was chosen over the AWS SDK for the leaner dependency graph and for covering MinIO, Aliyun OSS and AWS S3 with one client, and a consumer of any of the three subpackages still never imports the SDK directly, because each subpackage's own constructor builds its own client and no SDK type crosses the seam -- only a consumer that imports the subpackage itself now pays for the SDK behind it, exactly as the packaging rule below intends.
- `kv/postgres` measured its own cost the same way before landing: a throwaway module requiring only `github.com/jackc/pgx/v5/pgxpool` and run through `go mod tidy` under `GOWORK=off` picks up one direct require (`jackc/pgx/v5`) and four `// indirect` entries (`jackc/pgpassfile`, `jackc/pgservicefile`, `jackc/puddle/v2`, `golang.org/x/sync`) -- `golang.org/x/text` needed no bump, since this package's own root already requires a higher version than pgx does. This is the whole of the cost to the root package's own `go.mod`: `kv.go` itself imports nothing but `database/sql`-adjacent `pgx`/`pgxpool` types (no `gorm`, no `go/dbkit`, which this package cannot depend on regardless -- see the dependency-direction rule below), and a consumer who never imports `kv/postgres` inherits none of it, exactly like the Redis/S3 split's own accounting above. For the ecosystem as a whole the marginal cost is closer to zero than the raw numbers suggest: `go/dbkit` already requires the identical `jackc/pgx/v5 v5.10.0` for its own PostgreSQL dialect, so a consumer already on `dbkit`+PostgreSQL (the common case for anyone who would want this seam at all) resolves the same module version Go's MVS already settled on, downloading nothing new.
- `eventbus/postgres`'s own measured cost: a throwaway module requiring only `github.com/jackc/pgx/v5` and its `pgxpool` subpackage and run through `go mod tidy` under `GOWORK=off` picks up 5 `// indirect` entries (`jackc/pgpassfile`, `jackc/pgservicefile`, `jackc/puddle/v2`, `golang.org/x/sync`, `golang.org/x/text`) -- one of which, `golang.org/x/text`, this module's own `go.mod` already requires directly for `pkgcore/i18n`, so the genuinely new cost for a consumer who imports only this subpackage is 4 modules, not 5. This is the same measurement method issue #1 and the rule above require, and the same conclusion the task that added this subpackage predicted: for an application that already depends on `go/dbkit`'s PostgreSQL dialect (`go/dbkit/dialect/postgres`, which requires the same pinned `github.com/jackc/pgx/v5 v5.10.0` this subpackage pins), the pgx/pgxpool dependency closure is ALREADY present in that application's build -- `eventbus/postgres` adds no NEW third-party dependency at all for that consumer, only a new subpackage import inside a module it already carries, a real advantage over `eventbus/redis` (which requires go-redis regardless of what else the application already depends on) for a PostgreSQL-only deployment that has no other reason to run Redis.
- `kv/nats`'s own measured cost: a throwaway module requiring only `github.com/nats-io/nats.go` and run through `go mod tidy` under `GOWORK=off` picks up 5 `// indirect` entries (`klauspost/compress`, `nats-io/nkeys`, `nats-io/nuid`, `golang.org/x/crypto`, `golang.org/x/sys`). Unlike `kv/postgres` and `eventbus/postgres` above, this is not a first-ever cost measurement: `eventbus/nats` landed first and already pins the identical `github.com/nats-io/nats.go v1.53.1`, already carrying this exact 5-entry closure as a **direct** require in this module's own root `go.mod`. So the isolated throwaway-module number above measures "what nats.go alone costs" -- a useful figure on its own, and the same one `eventbus/nats`'s own measurement reports -- but it is not the marginal cost of adding `kv/nats` to this repository: that marginal cost is zero, since `kv/nats` reuses the closure `eventbus/nats` already put in `go/pkgcore/go.mod`, exactly as `eventbus/postgres` reuses `go/dbkit`'s already-present pgx closure for a consumer already on that module. A consumer who imports neither `eventbus/nats` nor `kv/nats` still pays nothing, per the packaging rule below.

**Interfaces, deployment modes and implementation composition**

- Do not expose a capability on an infrastructure interface that only one implementation can satisfy. Design against the weakest of that seam's registered implementations -- an anchor that moves as implementations are added, not a fixed "the standalone one": no server-side scripting, no pub/sub, no pipelines on `KVStore`.
- Do not branch on `DeploymentMode` outside kernel wiring. Business logic must not contain `if mode == DeploymentModeStandalone`; the retrofit that added `Capability`/`Preset`/`SeamRegistry` made this structurally easier to hold, since business code has no global mode value to branch on at all -- it only ever sees the `Registry`'s already-resolved `EventBus`/`KVStore`/`Mailer`/`ObjectStore`.
- Do not write a mock for `KVStore`, `EventBus`, `Mailer` or `ObjectStore`. `NewMemoryKVStore`, `NewMemoryEventBus`, `NewConsoleMailer` and `NewLocalObjectStore` are the test doubles, and are also what `"kv.memory"`/`"eventbus.memory"`/`"mailer.console"`/`"objectstore.local"` adapt onto in `builtin_implementations.go`.
- Do not add a new in-process or stdlib-backed built-in's seam registration anywhere but `builtin_implementations.go`; it is the one centralized place those `Registration`s live, mirroring the "single home" instinct the rest of the codebase already applies elsewhere (e.g. `@speed/api-client`'s HTTP seam) -- not five scattered `init()`s. A built-in that pulls in a third-party dependency (a database/sql-driver-style implementation such as `eventbus/redis`, `kv/redis` or `objectstore/s3`) registers itself instead, from its own subpackage's own `init()`, precisely so that registering it does not require the dependency to live in this package -- see the "third-party dependency" rule above and each subpackage's own doc comment. Do not move such a registration into `builtin_implementations.go` "to keep them together": that would undo the dependency-isolation split.
- Do not declare a `Capability` an implementation does not actually have, and do not add a new `Capability` bit without updating `String()`. `Kernel.Bootstrap`'s validation trusts the declaration, not the value: `WithEventBus(bus, pkgcore.MultiReplicaSafe)` on a bus that is not multi-replica-safe passes assembly and fails silently later, in production, under real replica count -- the one thing this whole mechanism exists to catch.
- Do not expect `Kernel.Bootstrap` to fail an assembly for lacking `SurvivesRestart`. It logs a startup warning (via `log/slog`, since pkgcore cannot import `go/observability` -- see the dependency-direction rule below) and proceeds; losing state across a restart is a legitimate, deliberate choice for a throwaway or development composition, never a hard error. A `Stateless` implementation is exempt from even that warning: it holds nothing for a restart to drop, so a banner over it would name no loss (see `warnIfNotDurable`).
- Do not silently change an interface's semantics when adding an implementation. `kv/redis.NewKVStore` preserves the in-memory store's observable behaviour; where a Redis-backed bus cannot (asynchronous cross-process delivery, JSON payload shape, failures of remote handlers unobservable, no catch-up), the difference is documented on the constructor and spelled out to consumers before they choose it.
- Do not add a new implementation of `KVStore`, `EventBus`, `Mailer` or `ObjectStore` -- built-in or host-supplied -- without running that seam's `AssertConforms` against it. This is the mandatory conformance check the "Contract tests" section above documents; skipping it is how a new implementation quietly diverges from the contract the others honour.
- Do not build a read-modify-write cycle out of `Get` + `Set`. Use `IncrByFloat`, `IncrByFloatWithTTL` or `CompareAndSwap`; they are the only operations every backend can make atomic. A caller-side `IncrByFloat` followed by a conditional `Set` to attach a ttl on the key's creation is exactly the race `IncrByFloatWithTTL` exists to close — prefer it outright for that case rather than hand-rolling the two-call sequence `go/ratelimit`'s sliding-window counter used to (see that primitive's own doc comment).
- Do not retain or hand out a caller's byte slice in a `KVStore` implementation, and do not perform an operation on a cancelled context — return the context error instead.

**Tenancy**

- Do not treat a missing tenant as "all tenants". `MustTenantFromContext` returns `ErrNoTenant` so callers fail closed; propagate that error rather than defaulting.
- Do not pass a tenant through a bare string context key. Use `WithTenant`.
- Do not invent a system purpose at the call site. Declare it with `RegisterSystemPurpose` from the module's own registration; an undeclared purpose is refused.
- Do not call `WithSystemContext` without an `Actor`, and record a `Ticket` whenever one exists. Every bypass must be attributable.
- Do not treat a system context as an authorization bypass. It suppresses tenant filtering only.

**Module contract**

- Do not add a method to `Module`. Under lockstep versioning that breaks all modules at once — add a field to `Registry` instead.
- Do not perform I/O in `Register`. It declares; the kernel decides when anything runs.
- Do not depend on module registration order. Declare the dependency in `DependsOn`; `Bootstrap` sorts, and reports a cycle or a missing dependency rather than guessing.
- Do not swallow a registrar error. A duplicate key is a bug across modules, not a merge, and nothing is registered when the call returns an error.
- Do not publish a domain event the module never declared with `Events.Publishes`. The declarations are the catalog `integration` maps onto the versioned public event schema.
- Do not decorate a shared `apperr` value expecting the receiver to change. `WithParam` and `WithCause` derive a new error.

**Errors and configuration**

- Do not put human-readable text in an `apperr` code. The code is machine-readable and stable; the client resolves it through its own i18n catalog.
- Do not change or reuse a released `apperr` code. It is part of the public API contract.
- Do not surface a wrapped cause in an API response. `WithCause` is for logs and `errors.Is`.
- Do not resolve runtime or tenant-overridable settings through `config.Loader`. It handles bootstrap values only: how to reach infrastructure, and which deployment mode is running.
- Do not hand-write the configuration reference. It is generated from the `ConfigItem` declarations.

**Internationalization**

- Do not translate API responses with `i18n`. Handlers return codes; the catalog renders backend-generated content only, in the recipient's locale — never the operator's.
- Do not add a language by editing `pkgcore/i18n`. The catalog's languages are its modules' files: a new language is one new `<language>.toml` file (its name a canonical BCP 47 tag) in every module that ships messages, and nothing else. `docs/internal/11-cross-cutting.md` scopes v1.0's full-coverage guarantee to zh-CN/en-US; the mechanism it requires is deliberately not frozen to them.
- Do not ship a grouping section (`[errors]`) or an unquoted dotted header in a locale file. go-i18n folds the section name into the id; the contract is one flat top-level entry per message, id quoted and prefixed with the module's `Name` plus a dot.
- Do not let one locale drift from another. Every language a module ships must carry the same id set; `Builder.AddModule` fails with `ErrParityMismatch`, and `tools/check_i18n_keys.py` checks the same zh-CN/en-US parity over the raw files -- the docs-check pipeline runs it on doc/i18n-touching PRs (.github/workflows/docs-check.yml).
- Do not render a missing message in a fallback language. An unknown locale or code must surface as an error; the catalog never falls back silently.
- Do not add a third-party dependency to the root package for i18n. The i18n round added two direct dependencies and promoted a third, all in the `i18n` subpackage: nicksnyder/go-i18n/v2 (the catalog machinery, adopted by `docs/internal/11-cross-cutting.md` before it entered the code), BurntSushi/toml v1.6.0 (the locale-file parser -- go-i18n ships no TOML decoder of its own, JSON only, and the flat shape is validated over BurntSushi's decode before go-i18n sees the messages, which is what rejects the [errors]-section id-folding a straight decode would produce), and golang.org/x/text, already in the module graph as go-i18n's dependency and promoted because the catalog code itself imports its `language` package.

**Documentation**

- Do not add an exported identifier without a doc comment, an `Example` in the matching `example_test.go`, and an entry in the tables above, in the same pull request.

## Error index

| Sentinel | Triggered by | Handling |
|---|---|---|
| `ErrInvalidDeploymentMode` | `ParseDeploymentMode` on anything but standalone/distributed | Abort startup; the deployment mode is misconfigured |
| `ErrNoTenant` | `MustTenantFromContext` on an unscoped context | Fail closed. In a worker, rebuild the context with `WithTenant` |
| `ErrSystemActorRequired` | `WithSystemContext` with an empty `Actor` | Name the actor; the bypass is audited |
| `ErrSystemPurposeNotRegistered` | `WithSystemContext` with an undeclared purpose | Declare it with `RegisterSystemPurpose` |
| `ErrNotNumeric` | `IncrByFloat` on a key holding a non-number | The key is not a counter; the stored value is left untouched |
| `ErrInvalidMail` | `Mailer.Send` on a message with an empty From, no recipients, an empty recipient, a line break in a header, or no body | Validate the message; nothing reached the wire |
| `ErrInvalidObjectKey` | Any `ObjectStore` operation with a key that breaks the shared grammar (empty, overlong, an empty or `.`/`..` segment, NUL or backslash) | Validate the key before the call; nothing reached the backend. The error names the broken rule, never the key |
| `ErrObjectNotFound` | `ObjectStore.GetObject` on a key no object is stored under, every backend reporting the same sentinel | Handle absence as a normal outcome. `DeleteObject` never returns it: deleting a missing key is a success |
| `ErrDuplicateModuleName` | Two modules reporting the same `Name()` | Rename one; nothing was registered |
| `ErrDependencyCycle` | `DependsOn` forming a cycle | The error names the cycle; break it |
| `ErrMissingDependency` | Depending on a module absent from the bootstrap set | Add the module, or drop the dependency |
| `ErrInvalidConfigItem` | An item whose fields contradict one another: an unknown `Type`, a `Default`/`Min`/`Max` of the wrong Go type, `Min`/`Max` on a `string`/`bool` item, `Min` above `Max`, a `Default` outside its declared range, or `Sensitive` with `Public` | Fix the declaration; nothing was registered (the message never prints a sensitive item's value) |
| `ErrDuplicateConfigKey` / `ErrDuplicateFeatureFlag` / `ErrDuplicatePermission` / `ErrDuplicateJobType` / `ErrDuplicateNotificationType` / `ErrDuplicateEventType` / `ErrDuplicateAuditAction` | The same key registered twice | Two modules own one key; decide which does |
| `ErrUnresolvedFeatureDependency` | A flag depending on a flag nobody registered | Register the flag, or drop the dependency |
| `ErrCapabilityUnsatisfied` | `Bootstrap` resolving a seam (preset or injected) whose declared `Capability` does not satisfy `DeploymentMode.RequiredCapabilities()` | The error names the seam, the implementation and the missing capability; wire a qualifying implementation with `WithEventBus`/`WithKVStore`/`WithMailer`/`WithObjectStore`, or `WithPreset` a composition that already qualifies. Replaces the four `ErrMissingDistributed*` sentinels a fixed mode-keyed switch used to return before this retrofit |
| `ErrUnknownImplementation` | `SeamRegistry.Build`, or `Bootstrap` resolving a `Preset` entry, naming an implementation nothing registered | Register it first, or fix the `Preset`/`Config` typo |
| `ErrDuplicateImplementation` | `SeamRegistry.Register` with a `Registration.Name` already registered on that registry | Pick a different name; the original registration is untouched |
| `ErrMissingSeamConfig` | A built-in `mailer.smtp` or `objectstore.s3` `Registration.New` called with a `Config` missing a field that has no safe default (SMTP host; S3 endpoint, bucket or credentials) | Supply the field in `Config`, or bypass the preset layer with `WithMailer`/`WithObjectStore` and a hand-built `SMTPConfig`/`s3.Config` |
| `eventbus/redis.ErrEventBusClosed` | `Publish` on an `eventbus/redis.EventBus` after `Close` | Wiring error: a closed bus is out of the deployment; build a fresh one. Lives in the `eventbus/redis` subpackage, not here -- nothing outside the Redis implementation ever referenced it as `pkgcore.ErrEventBusClosed`, so it moved with the implementation rather than staying a root-package sentinel one subpackage's type returns |
| `eventbus/postgres.ErrEventBusClosed` | `Publish` on an `eventbus/postgres.EventBus` after `Close` | Identical wiring-error treatment, mirroring `eventbus/redis.ErrEventBusClosed` exactly; lives in the `eventbus/postgres` subpackage for the same reason |
| `config.ErrMissingValue` | A `config:"required"` field left zero | The error names the key and every source consulted |
| `config.ErrInvalidValue` | A supplied value not applicable to its field | The error names the offending key and its source |
| `config.ErrSourceUnreadable` | An unparseable config file or malformed flag | Fix the source; startup aborts |
| `config.ErrInvalidTarget` | `Load` given a non-struct-pointer or a bad `config` tag | Programming error; fix the target type |
| `i18n.ErrEmptyModuleName` | `Builder.AddModule` with an empty module name | Programming error; every module has a `Name()` |
| `i18n.ErrInvalidModuleName` | `Builder.AddModule` with a module name containing a dot | Programming error; the name is the `<module>.` prefix of every message id the module ships, and a dotted name would let two modules' id prefixes nest |
| `i18n.ErrDuplicateModule` | `Builder.AddModule` with a module already added | Register each module's locales exactly once |
| `i18n.ErrMissingLocaleFile` | A module shipping locale files but not one for every language of the catalog | Add the missing file; a module contributes every catalog language or none |
| `i18n.ErrUnsupportedLocale` | A locale file that is not a canonical language tag, or a file for a language the catalog does not serve | Fix the file name, or add the language to every message-shipping module |
| `i18n.ErrUnsupportedShape` | A file violating the flat contract: unquoted or dotted headers, a grouping section such as `[errors]`, reserved-key misuse, a table carrying both `translation` and a plural category, or a plural table with no translation | The error names the file and the entry; fix the TOML shape |
| `i18n.ErrParityMismatch` | The id sets of one module's locale files differing | The error names the languages and the missing ids; `tools/check_i18n_keys.py` checks the same zh-CN/en-US parity over the raw files -- the docs-check pipeline runs it on doc/i18n-touching PRs (.github/workflows/docs-check.yml) |
| `i18n.ErrUnknownLocale` | `Lookup`/`LookupPlural` for a locale no module ships | Programming error; the catalog never falls back to a default language |
| `i18n.ErrUnknownCode` | `Lookup`/`LookupPlural` for a code no module contributed | Programming error; the catalog never falls back to a default language |
