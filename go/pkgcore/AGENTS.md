# pkgcore

The dependency floor of the monorepo. Every other Go module imports it; it imports no other speed module.

It owns eight things and nothing else:

| Concern | Where |
|---|---|
| The module contract and the component assembly: the descriptor, the registry and its seats, and the component configuration contract (the `config` tag vocabulary, the key-path namespace, the `ComponentConfigResolver` seam and the describable documentation surface) | `component.go`, `component_registry.go`, `component_assembly.go`, `component_global.go`, `config_schema.go`, `config_resolver.go` |
| Tenant context, and the raw system-context marker (`WithSystemContext`/`SystemReasonFromContext`; the audited wrapper around it lives in `go/tenancy`) | `tenant.go` |
| Infrastructure module interfaces (`KVStore`, `EventBus`, `Mailer`, `ObjectStore`) plus each one's in-process implementation and its SMTP-backed one (stdlib `net/smtp`, so it earns no dependency-isolation benefit from a subpackage), and the permanent-transport-failure sentinel the `Mailer` and `SMSSender` contracts share (declared here because the transports that must produce it -- this package's SMTP mailer, the aliyun and tencent SMS adapters -- sit below every consumer in the module graph) | `kv.go`, `kv_memory.go`, `eventbus.go`, `eventbus_memory.go`, `mailer.go`, `mailer_console.go`, `mailer_validation.go`, `objectstore.go`, `objectstore_local.go`, `mailer_smtp.go`, `transport.go` |
| The shared outbound-SMS contract (`SMS`, `SMSSender`) plus its console implementation and its operator-gateway one (both stdlib-only, so neither earns a dependency-isolation benefit from a subpackage) -- an infrastructure module like `Mailer`, registered the same component way: `sms.console` and `sms.http` are its two built-in descriptors, carrying the capability declarations the roster below lists, and a composition that selects one resolves the sender through the registry (see `sms.go`'s own doc comment) -- what the module lacks is the surface the other four carry, not resolution: no `ComponentRegistry` accessor returns it, so a module built outside the assembly still takes the sender through its own wiring option. `SMS` carries a message in two renderings of one fact: the fully rendered `Text` a free-text transport delivers, and the template identity (`MessageID`, `Locale`, `Params`) a template-typed carrier adapter routes by -- the console and gateway implementations are free-text and ignore the identity fields | `sms.go`, `sms_console.go`, `sms_http.go` |
| The capability bits the assembly validates a composition against, the flat scalar `Config` the built-in construction paths take, and the five in-process/SMTP built-in component files (the distributed built-ins register themselves from their own subpackages -- see below) | `capability.go`, `flat_config.go`, `eventbus_memory.go`, `kv_memory.go`, `mailer_console.go`, `mailer_smtp.go`, `objectstore_local.go` |
| The merged backend message catalog, assembled by the assembly from every module's `Locales()` embed.FS | `i18n/` (+ `locales/`, pkgcore's own seed message files) |
| The `DeploymentMode` enumeration (a topology declaration only -- see "Deployment mode and implementation composition" below) | `deployment_mode.go` |
| The mandatory conformance suite for each module, and the two conformance runs of every in-process/SMTP built-in implementation | `eventbustest/`, `kvstoretest/`, `mailertest/`, `objectstoretest/` (suites); `*_conformance_test.go` (runs; the SMTP leg needs no Docker, see below) |

Three subpackages: `apperr` (the structured application error every module returns), `config` (the bootstrap configuration loader, run once at process startup) and `i18n` (the message catalog backend-generated content is rendered through, on nicksnyder/go-i18n). `locales/` carries pkgcore's own seed messages, which pkgcore's test suites feed through the catalog as its fixture and which serve as the canonical shape example -- no pkgcore component carries a `Locales` bundle, so nothing in a running application reads them (see the `pkgcore/locales` section).

A further subpackage, `probe`, serves a host's own process shell rather than a module and is stdlib-only: it issues one container self-probe, a GET request to the process's own HTTP server over loopback -- the HEALTHCHECK pattern a distroless-style image with no shell, no curl and no wget runs by re-invoking its own binary with a sentinel argument. Its loopback host is structural (`Check` dials 127.0.0.1 and nothing else, so the port and path its caller passes can only select which local listener is probed), while everything environment-shaped stays the host's own (which variable holds the port, what an empty port falls back to, which argument diverts the entry point): the package reads no environment variable and carries no port fallback.

Another subpackage, `spa`, serves a built single-page frontend from a directory on disk in front of a host's composed handler: GET/HEAD only, a caller-declared allowlist of server-owned paths (`WithServerPath` for exact paths, `WithServerPrefix` for whole-segment prefixes) that always pass through, the index.html fallback for unknown client routes with a real 404 for a miss under the content-addressed asset prefix, a cache policy keyed on that prefix (`WithAssetPrefix`, defaulting to vite's `assets`; the immutable/no-cache split its package doc comment explains), and a root pinned to an absolute path at construction whose request paths are root-pinned, cleaned and `filepath.IsLocal`-checked before any open. Its package doc comment carries the full contract, including the two file-system decisions that ship with it: a symlink inside the root pointing outside it is followed exactly as net/http's own file server follows one (the directory is the operator's own built output, and guarding symlinks in it would be defending the deployer against themselves), and a root that does not exist is not a construction error -- the handler degrades to 404s for its own surface while every declared server path keeps passing through, so a host can mount it before its dist exists.

Four more subpackages carry the Redis-, S3- and PostgreSQL-backed built-in implementations -- `eventbus/redis` (`EventBus`'s distributed-mode implementation on Redis Streams, registering `"eventbus.redis"`), `eventbus/postgres` (`EventBus`'s OTHER distributed-mode implementation, on PostgreSQL `LISTEN`/`NOTIFY` backed by a durable outbox table, registering `"eventbus.postgres"` -- the genuinely zero-extra-infrastructure option for a deployment that already runs PostgreSQL and does not want to stand up Redis purely for this one module; see its own package doc comment and `EventBus`'s delivery-semantics note for the full contract, and this file's Public API table below), `kv/redis` (`KVStore`'s, registering `"kv.redis"`), and `objectstore/s3` (`ObjectStore`'s, on any S3-compatible service, registering `"objectstore.s3"`) -- each in its own subpackage because Go resolves dependencies per package: a consumer of this root package must not inherit go-redis, jackc/pgx or minio-go merely by importing `pkgcore` (see this file's own Rules section). Each subpackage self-registers its component descriptor through its own `init()` (the `database/sql` driver pattern `component.go` follows); a host that wants a built-in Redis, PostgreSQL or S3 implementation must import the matching subpackage (a blank import is enough) and name the component in its composition configuration -- the built-in composition still points the `"eventbus"` module at `"eventbus.redis"`, unchanged by this addition -- or selection fails at `Prepare` time with an error naming the unknown component. Calling a subpackage's own constructor directly and putting the value into the by-type context needs no import-for-side-effect at all, since that path never goes through component selection. Each subpackage carries its own unit tests, its own `example_test.go`, and its own `integration_test/` (Docker-backed, `-tags=integration`) -- physically separate per package, per this repository's testing-layout rule, not shared with this package's own (Docker-free) unit tier. `eventbus/postgres` additionally carries its own `migrations/postgres/` (a single versioned SQL file for its outbox and cursor tables, embedded and applied through its own `EnsureSchema` rather than `dbkit.MigrationRegistry` -- this package cannot import `go/dbkit`, which sits above it in the dependency graph, so it cannot use that machinery directly; see the migration file's own doc comment) and no `migrations/sqlite/` sibling at all, a deliberate, documented exception (see that file's own header) since the mechanism is inherently PostgreSQL-specific and the standalone deployment mode never runs it.

A fifth subpackage, `eventbus/nats`, is a third distributed-mode `EventBus` implementation, following the identical split and registering `"eventbus.nats"` the same way. It is not part of either built-in composition (the distributed component set's `"eventbus"` module still names `"eventbus.redis"`); a host that wants it selects the component in its own composition configuration or puts `NewEventBus`'s value into the by-type context directly. Delivery semantics are deliberately identical to `eventbus/redis`'s -- fan-out to every replica, never load-balanced to one -- reached through JetStream's durable pull consumers instead of Redis consumer groups: every bus instance creates its own uniquely-named consumer on each event type's stream, so JetStream's own load-balancing (which only applies between two readers of the *same* consumer name) never triggers between instances. See the package's own doc comment for the full contract and its `integration_test/`'s `TestEventBus_FanOutDeliversToEveryReplica` for the real-server proof.

`kv/postgres` is a sixth such subpackage, registering a *second* implementation of a module an earlier subpackage already covers — the `"kv"` module's second, after `kv/redis`: `KVStore` backed by a single PostgreSQL table (`pkgcore_kv_entries`) with a TTL column, registering the `"kv.postgres"` component beside the `"kv.redis"` one -- the genuinely zero-extra-infrastructure option for a deployment that already runs PostgreSQL and does not want to stand up Redis purely for this one module, mirroring `eventbus/postgres`'s identical rationale for the `EventBus` module. The built-in composition still points `"kv"` at `"kv.redis"`; a host wanting `"kv.postgres"` instead names that component in its own composition configuration -- the block carries the `dsn` and the component builds (and owns) its own pool -- or shares an existing pool by putting `kv/postgres.NewKVStore(pool)`'s value into the by-type context directly. `NewKVStore` takes a `*pgxpool.Pool` directly (never a `*gorm.DB`), so a host already running `dbkit.Open` for its business tables shares the exact same connection credentials at the cost of one small, dedicated second pool rather than reaching into `dbkit`'s own internals for one. Both `IncrByFloat` and `CompareAndSwap` are single, database-arbitrated SQL statements -- an `INSERT ... ON CONFLICT DO UPDATE` upsert for the former, a `WITH` CTE combining an `UPDATE` (the "key exists" path) and an `INSERT ... ON CONFLICT DO NOTHING` (the "key genuinely absent" path) for the latter -- never a Go-level read-modify-write, proved race-free under real concurrent callers by the package's own `TestKVStore_ConcurrentIncrementsLoseNoUpdates` and `TestKVStore_ConcurrentCompareAndSwapSetIfAbsent_ExactlyOneWinner` in its `integration_test/` tier, the same discipline `go/billing`'s `applyBalanceDelta` established for its own single-`UPDATE` arithmetic guard. Unlike `kv/redis` (Redis's native active expiry), PostgreSQL has no equivalent: every read and write treats an expired row as absent (a `WHERE expires_at IS NULL OR expires_at > now()` guard, the same read-side treatment `pkgcore.memoryKVStore` gives an expired entry) but does not physically remove it until something touches the key again or a host calls the package's own `Store.Sweep` -- a plain, one-shot `DELETE` a host runs on its own schedule (no owned goroutine, no automatic call from `NewKVStore`), which is why `NewKVStore` returns the concrete `*Store` rather than the bare `pkgcore.KVStore` interface: `Sweep` is a capability outside what `KVStore` itself has room for. The two stores' reclamation entries differ because their state's lifetime differs: rows in a table outlive the process and are shared across replicas, so the physical reclamation is a host-run, concurrency-safe `Sweep`; `memoryKVStore`'s map dies with the process, so it sweeps itself -- an amortized pass every 1024 write operations reclaims expired entries nothing ever touches again. `pkgcore_kv_entries`' migration (`migrations/postgres/0001_create_pkgcore_kv_entries.sql`) has no `sqlite/` counterpart -- following `eventbus/postgres`'s identical precedent -- since the standalone deployment mode never runs this implementation at all (`pkgcore.NewMemoryKVStore` covers it with no database of its own); `schema.go`'s `EnsureSchema` is this package's own self-contained migration applier (idempotent `CREATE TABLE/INDEX IF NOT EXISTS`, no `schema_migrations` ledger), built the same way `eventbus/postgres.EnsureSchema` is, for the identical reason: `go/pkgcore` cannot import `go/dbkit`, which sits above it.

A further subpackage, `kv/memcached`, is a third distributed-mode `KVStore` implementation, added the identical way -- a package of its own from day one, on `github.com/bradfitz/gomemcache` (a genuinely zero-third-party-dependency client: a throwaway module blank-importing it alone carries no `// indirect` entries at all under `GOWORK=off go mod tidy`, the lowest measured cost of any built-in implementation in this file). Read its package doc comment before choosing it over `kv/redis`: it is honestly declared `MultiReplicaSafe` only, never `SurvivesRestart` -- Memcached is a pure in-memory cache with no persistence mechanism of any kind, so a restart, a rolling upgrade or ordinary LRU eviction under memory pressure silently drops everything it holds. That honest declaration is also why no built-in composition names `"kv.memcached"` (the distributed composition's `"kv"` module still names `"kv.redis"`); a host that wants it selects the `"kv.memcached"` component in its own composition configuration or puts `NewKVStore`'s value into the by-type context directly. Memcached's own primitives are narrower than every other KVStore backend here -- native `incr`/`decr` are 64-bit unsigned integer only, with no float support at the protocol level, and no atomic whole-value compare exists at all -- so `IncrByFloat` and `CompareAndSwap` are both bounded compare-and-swap retry loops over Memcached's native `gets`/`cas`/`add`; and its native per-key expiry is granular only to the whole second, which the shared `kvstoretest.AssertConforms` suite's millisecond-scale TTLs would silently violate without this store's own client-side logical-expiry envelope layered on top of Memcached's coarser physical one (see the package doc comment for the full design and its inherent year-2038 boundary for an extremely long ttl). See the package's own doc comment for the full contract and its `integration_test/` for the real-server proof, including two adversarial concurrency tests (`IncrByFloat` losing no update under many racing goroutines; `CompareAndSwap`'s set-if-absent form letting exactly one racing goroutine win) that only a real server's compare-and-swap primitives can exercise honestly.

Another subpackage, `kv/nats`, carries a fourth distributed-mode `KVStore` implementation (alongside `kv/redis`, `kv/postgres` and `kv/memcached`), on a NATS JetStream KV bucket, registering a `"kv.nats"` component the identical database/sql-style way `kv/redis` registers `"kv.redis"` -- but, unlike the subpackages above, `"kv.nats"` is **not** named by the built-in distributed composition: the subpackage only makes the component selectable, it does not change what any existing composition picks by default. A host that wants NATS instead of Redis, PostgreSQL or Memcached for the `"kv"` module either names `"kv.nats"` in its own composition configuration (after blank-importing `kv/nats` so the component is registered) or calls `kv/nats.NewKVStore` directly and puts the value into the by-type context. JetStream KV gives only a per-subject last-sequence ("revision") compare, never a native atomic increment or a native compare-by-value, so this implementation's `CompareAndSwap` and `IncrByFloat` are both built on that one revision check (`Update(key, value, revision)` failing `ErrKeyRevisionMismatch`, or `Create` failing `ErrKeyExists`, both mapped to "the swap did not happen" rather than an error) -- `IncrByFloat` wraps the same check in a bounded (200-attempt), exponentially-backed-off retry loop, since no server-side atomic float op exists to lean on instead. Expiry is carried in an 8-byte big-endian Unix-nanosecond header this implementation prefixes onto every stored value itself, never in the bucket's own TTL (a whole-bucket setting that cannot express "an increment keeps a live key's existing expiry, but starts a fresh key with none"), and every opaque `pkgcore.KVStore` key is hex-encoded before it reaches JetStream, since that store's own key charset excludes characters (a colon, notably) this repository's own KVStore tests use freely. Unlike `kv/redis`'s `NewKVStore`, which dials nothing, provisioning a JetStream KV bucket is itself a round trip the server must answer, so `kv/nats.NewKVStore` takes a `context.Context` and can fail. `eventbus/nats` was this repository's first consumer of `nats.go`; this subpackage is the second, sharing the exact same `github.com/nats-io/nats.go v1.53.1` dependency closure `eventbus/nats` put on this module's root `go.mod`. `.golangci.yml`'s `nats-only-in-pkgcore` depguard rule exempts both subpackages under the one rule name rather than a per-subpackage key. Its own `integration_test/` (Docker-backed, JetStream-enabled) runs the shared `kvstoretest.AssertConforms` plus two adversarial concurrency proofs (many goroutines racing `IncrByFloat` on one key with no lost update; many goroutines racing `CompareAndSwap` set-if-absent on one key with exactly one winner) and a real server-restart reconnect proof.

Four more subpackages, `eventbustest`, `kvstoretest`, `mailertest` and `objectstoretest`, hold one `AssertConforms` contract-test suite per infrastructure module -- the mandatory conformance check every implementation of that module, built-in or host-supplied, must pass. They play the same role for these four modules that `go/tenancy/tenancytest.AssertIsolated` plays for `dbkit.Repository[T]`: with several registered implementations per module, drift between them is caught in one shared suite instead of pairwise. See "Contract tests" under Public API below.

Two more subpackages, `redistest` and `rustfstest`, hold the disposable-container fixtures the integration tiers of every module build against rather than any module: `redistest` provides a Redis container with a go-redis client, a two-independent-client pair standing in for two replicas sharing one server, a fixed-host-port snapshotting variant for a survives-restart proof, and the post-restart readiness probe; `rustfstest` provides the RustFS container this repository's S3-compatible tiers run against -- endpoint, minio client, bucket provisioning (a hosting operation the store itself never performs) and the /health plus read-readiness waits a restart proof needs. They live here, not in a new module, because pkgcore sits underneath every module: any module's `integration_test/` -- and a consuming application's tests -- can import them, while `go/dbkit/dbtest`'s fixtures could not serve pkgcore's own tiers at all (pkgcore cannot import a module that sits above it in the dependency graph). Neither constructor carries a skip-on-missing-Docker path: a tier that spins up real infrastructure fails loudly when Docker is absent, matching every other Docker-backed tier here; each package's own unit suite instead probes for a daemon and skips, so a plain `go test ./...` run stays green without one. Both are test-only surfaces -- no runtime code imports them, and the image and credential pins they carry are the single pins every tier runs against.

`testkit` holds the small primitives the suites share for observing asynchronous work and pinning the platform's wire and context conventions: `Eventually`/`EventuallyWithin` (the bounded convergence poll every assertion on asynchronously delivered effects waits through, with `DefaultConvergence` as the shared default budget), `WaitForRun` (the typed receive a test uses to await a handler run landing on its channel), `TenantCtx` (the background-plus-tenant context a tenant-scoped call runs under), `DecodeErrorBody` (the `{code, params}` envelope decoder, reading a response body back into the one wire shape every module's structured error converges on) and `EventRecorder` (a concurrency-safe recorder of the events a bus delivers, with the count, first-match, by-tenant and slice accessors the tiers assert through). It lives here for the same reachability reason `redistest` does -- pkgcore sits underneath every module, so any module's test tiers and a consuming application's tests can import it -- and like them it is a test-only surface: no runtime code imports it, and it deliberately holds nothing but plumbing, never assertions about the behavior under test.

**SMS carrier adapters (aliyun, tencent, twilio).** `sms/aliyun`, `sms/tencent` and `sms/twilio` are pkgcore's three real carrier adapters for the `SMSSender` module -- each a stdlib-only implementation of its vendor's official signing and request shape (Aliyun Dysmsapi RPC HMAC-SHA1, Tencent Cloud SendSms TC3-HMAC-SHA256, Twilio Messages REST with Basic auth), delivering the module's messages to the vendor's fixed gateway over the `pkgcore/safehttp` guarded default client. They live here so every module above the dependency floor can reach a real carrier: go/notification, sitting below go/authn in the module graph, could not import them from their former authn home, which is exactly the reachability gap that made the SMS module shared. Each adapter carries its own unit tests, its own `example_test.go`, and its own env-gated `integration_test/` live leg (no Docker: the legs need the operator's real carrier credentials, never a container). Their behavioural contracts beyond their own tests are pinned by the consumer suites -- go/authn's phone-login flow and go/notification's delivery pipeline -- since SMS has no `smstest.AssertConforms`: only `sms.console` and `sms.http` register as components, the three carrier adapters carry no descriptor and a host builds them through their own constructors, and no shared suite covers the module's implementations the way `mailertest` and its three siblings cover the other modules' built-ins.

The two Chinese-cloud carriers have no free-text send at all: every message instantiates an account-approved template, so `sms/aliyun` and `sms/tencent` are the module's two template-typed adapters -- each `Config` carries a `Templates` map keyed `"<locale>/<message-id>"`, each entry naming one approved template and the variables it declares, and `Send` selects the mapped template, forwards exactly the declared variables from `SMS.Params`, and fails (before any request) when the map has no entry for the message, when `MessageID`/`Locale` is empty, or when a declared variable has no value. The account data -- which template codes exist, which variables each declares -- cannot be known by this codebase, so the map is the operator's declaration and an unmapped message is refused, never sent through another template or as free text. Twilio, the console sender and the HTTP gateway are free-text transports and keep delivering `SMS.Text`.

`safehttp` is the outbound-request guard those adapters (and go/authn's own federation client) dial through: it refuses any destination that is not public unicast at the moment of connection, so a DNS-rebinding answer cannot slip past. It moved from go/authn's `internal/` when the SMS transports made it shared -- its package doc records the destinations it fronts and the move.

`httpapi` is the shared HTTP surface convention every module's request handlers write responses and read requests through: `WriteJSON` writes a success body (the shared JSON content type, the caller's status and the encoded value), `WriteError` builds the coded error envelope (the `{"code", "params"}` body under the error's own suggested status, with a caller-supplied fallback for an error something below the handler did not classify), and `DecodeJSON` bounds and decodes a JSON request body, mapping every decode failure -- an oversized body included -- onto the calling module's coded invalid-request-body refusal. It is stdlib-and-`apperr`-only, carries its own unit tests and `example_test.go`, and is described under its own section in Public API below.

**Out of scope.** Database access (`dbkit`), tenant enforcement in SQL (`tenancy`), logging and tracing (`observability`), runtime and tenant-overridable configuration (the `config` *module*, not this `config` package), job execution (`jobs`). pkgcore declares contracts; it does not implement business behaviour.

## Public API

### `pkgcore`

**Wiring**

Everything assembles through the component registry: the host registers the components it wants (the descriptors of every module and assembly-time step self-register globally, so a fresh registry seeds itself from that registration), puts the values the composition needs into the by-type context, and drives the seven stages.

| Signature | Purpose |
|---|---|
| `type Component struct { Name; Module; New; Init; Start; Stop; Close; Requires; Provides; Capabilities; ConfigSchema; ConfigNamespace; BootstrapKeys; SystemPurposes; Migrations; Locales; OpenAPISpec }` | One selectable unit of the application: what it needs (`Requires` contract tokens, `ConfigSchema` under the `ConfigNamespace` prefix), what it offers (`Provides`), what it declares about itself (`Capabilities`), and the lifecycle callbacks the assembly drives. `New` is the one required callback; every other field is optional |
| `type ComponentConfig` | The composition configuration a registry plans from: a `components` block naming the selected components (each with its own configuration block) plus `strict`, which turns off auto-pull of components a selection did not name. Settings read like a file or environment (`With`, `Decode`) |
| `func NewComponentRegistry() *ComponentRegistry` | The assembly. Seeded from the global component registration; a host registers its own components with `Register` before driving any stage |
| `func (*ComponentRegistry) Register(c Component) error` | Add a descriptor. Names are unique; a duplicate is an error |
| `func (*ComponentRegistry) Put(v any)` | Publish a value into the by-type context: a host-supplied module value before `Prepare`, a runtime service during `Init`. Append-only -- `Get` reports ambiguity rather than picking one |
| `func Get[T any](r *ComponentRegistry) (T, error)` | The value T addresses: exactly one put value assignable to T, `ErrMissingRequirement`/`ErrAmbiguousProvider` otherwise |
| `func GetOptional[T any](r *ComponentRegistry) (T, bool, error)` | The optional-dependency reading of the by-type context: `(zero, false, nil)` for an absent value, the value with `true` for exactly one match, and any other error as-is (`ErrAmbiguousProvider`, the single-match conversion failure). The caller applies the absent case's documented default and lets a true error follow its own contract; `Get` stays the reading for a required dependency |
| `func (*ComponentRegistry) Prepare/Construct/Verify/Init/Start/Stop/Close(ctx) error` | The seven stages, each run once, in order: plan and capability-validate (`Prepare`), build instances in dependency order (`Construct`), closing validation (`Verify`), open the seats and run declarations plus `Init` callbacks (`Init`), then `Start`/`Stop`/`Close` in dependency and reverse order |
| `func (*ComponentRegistry) EventBus()/KVStore()/Mailer()/ObjectStore()/Locales() *i18n.Catalog` | The resolved module values and merged message catalog, read from the by-type context. Host-side reads; the module-facing equivalents are the seat accessors below |
| Seat accessors: `RoutesSeat()`/`ConfigSeat()`/`FeaturesSeat()`/`PermissionsSeat()`/`JobsSeat()`/`NotificationsSeat()`/`EventsSeat()`/`AuditActionsSeat()`/`RetentionSeat()`/`SchedulesSeat()` | The ten declaration seats plus their read forms (`reg.Permissions.Permissions()`, `reg.Routes.Routes()`, ...). Writes are accepted only while the `Init` stage runs; a write outside it fails (or panics on the void writers) with `ErrStageViolation` naming the seat and the current stage |
| `func MustRegister(c Component)`, `func RegisterComponent(c Component) error` | Global component registration, the `database/sql` driver pattern: every module's and step's package registers its descriptor from `init`, and a `ComponentRegistry` seeds itself from that registration. Duplicate names fail at startup with a message naming the keep/conflict |
| `func Assets(reg *ComponentRegistry) []Component`, `func RegisteredComponents(reg *ComponentRegistry) []Component` | Read-only enumerations of the selected components and the global registration, the surfaces golden component rosters and catalog merges read |
| `func ValidateFeatureGraph(reg *ComponentRegistry) error` | Reports feature flags depending on flags nobody registered. Runs as part of `Init`'s closing validation |

**Capability declarations and the implementation registry** -- the machinery a component's capability declaration and a module-internal implementation directory are built on; see "Deployment mode and implementation composition" below for the design this implements.

| Signature | Purpose |
|---|---|
| `type Capability uint8`, consts `MultiReplicaSafe` / `SurvivesRestart` / `Stateless` | What a component's descriptor declares about the implementation it provides. `func (Capability) Has(want Capability) bool`; `func (Capability) String() string` renders the set bits pipe-joined (`"MultiReplicaSafe\|SurvivesRestart"`), `"none"` for zero. The assembly's `Prepare` compares every selected component's declaration against what the configured deployment mode requires and fails with `ErrCapabilityUnsatisfied`, naming the component, the missing bit and the mode; `Stateless` suppresses the not-survives-restart startup banner (`mailer.console` is the built-in example) |
| `type Config map[string]string` | The flat scalar form a built-in implementation package's shared constructor takes: what a configuration file or environment can naturally provide, keyed by whatever name the implementation documents. A component descriptor's `New` callback receives the structured `ComponentConfig` and bridges its fields onto this flat map when it funnels through the package's one construction path; pkgcore itself never reads environment or files |

Built-in implementation names: `eventbus.memory`, `eventbus.redis`, `eventbus.postgres`, `eventbus.nats`, `kv.memory`, `kv.redis`, `kv.postgres`, `kv.nats`, `kv.memcached`, `mailer.console`, `mailer.smtp`, `objectstore.local`, `objectstore.s3` -- each a component descriptor (`component.go` in its own package) whose `New` funnels through an unchanged typed constructor (`NewMemoryEventBus`, `NewKVStore`, ...). The five in-process/SMTP built-ins register from this root package's component files (`eventbus_memory.go`, `kv_memory.go`, `mailer_console.go`, `mailer_smtp.go`, `objectstore_local.go`); the Redis-, PostgreSQL-, NATS-, Memcached- and S3-backed ones register themselves from their own subpackages' `init()`, so they are selectable by a composition only once the host has imported the matching subpackage. The Redis-backed components fall back to `"localhost:6379"` when the `addr` setting is unset; the SMTP, S3 and PostgreSQL ones have no safe default credentials and fail construction with a config error (`ErrMissingSeamConfig` for SMTP/S3; a plain error naming the missing `dsn`/`replica_id` for `eventbus.postgres`) instead of calling their panicking constructor with an empty field. A host that wants a typed configuration the flat settings cannot express (TLS material, a credential chain, one client shared across components) builds the object itself through the package's own constructor and puts the value into the by-type context, or writes its own component descriptor around it.

**Component registration** -- the second registration channel beside the implementation registries, for the config-driven component assembly. Every module implementation and assembly-time step registers a `Component` descriptor from its package's `init` through `MustRegister` (a host may add its own with `Register` before creating a registry), and a `ComponentRegistry` instance seeds itself from that global registration, parses the composition configuration the host puts, and drives the seven-stage lifecycle (`Prepare` / `Construct` / `Verify` / `Init` / `Start` / `Stop` / `Close`). The descriptor -- name, lifecycle callbacks, `Requires`/`Provides` contract tokens, `Capabilities`, `ConfigSchema`, `Migrations`/`Locales`/`OpenAPISpec`, `Module` -- and the registry are documented in full on their own godoc (`component.go`, `component_registry.go`, `config.go`; runnable walkthroughs in `component_example_test.go`). An empty configuration block (`{}` or `nil`) selects a component with its defaults; a `false` value deselects it; any key a component does not declare fails the Prepare stage with the accepted-key list. **The component configuration contract** (`config_schema.go`, `config_resolver.go`). A `ConfigSchema` field's `config` struct tag declares how the field resolves: a plain field is supplied by the component's configuration block alone; `expose` widens it to flag/environment resolution; `derive` marks a `[]byte` field as one unit of 32-byte key material and implies `expose`; `required` fails the Prepare stage when no source supplied a value (`ErrMissingConfigValue`); `sensitive` demands a `ConfigDocs()` entry with a non-empty description, or the assembly fails (`ErrInvalidComponent`); `env=NAME` pins the exact environment variable name; `group=NAME` declares a documentation group; `-` removes the field from every source. A field's key path is the address its configuration-block key already has -- its json tag name, or its lowercased Go name -- nested structs joining with dots, under the component's namespace: `components.<Name>.` by default, replaced wholesale by `Component.ConfigNamespace` (normalized to end with a dot) or dropped entirely by `pkgcore.NoConfigNamespace` (`"-"`). The Prepare stage refuses a selection in which two sources -- two selected components' fields, or a field and a `BootstrapKeys` declaration -- produce one final key path (`ErrConfigKeyConflict`, naming the key path and both sources): a single address two declarations share would silently resolve one of them from the other's value.

A schema target may implement `Documented` (`ConfigDocs() map[string]FieldDoc`, keyed by the field's local key path, matched case-insensitively) to document its fields with prose -- `Description`/`Default`/`Example`, operator-facing statements rather than runnable Go values. `pkgcore.DescribeComponentSchema(name, schema)` expands a declaration into `[]FieldDescriptor` (final key path, type, resolution flags, pinned env name, group, doc), following the registered component's own `ConfigNamespace`; it is the one collection the `--help` rendering and the configuration reference generator share, a read-only projection that never validates anything into an assembly. The five-source merge itself is deliberately not this package's: `ComponentConfigResolver` is the zero-dependency seam an engine implements and `Put`s into the registry before `Prepare`, and every selected component declaring a schema has its block replaced by the resolver's merged result -- the returned tree is what the assembly decodes strictly and what `New` receives, so it must carry the resolved value (derived key material included) of every field a source supplied. Without a resolver in the registry the blocks stand exactly as the composition carried them, the file-only behaviour a bare registry keeps, and a component declaring no schema is never passed to the resolver.

`PeriodicTask` (the `Registry.Schedules` seat) declares one periodic task a module owns — the job type, the window size `Every`, which tenants it runs for, and the two strings an enqueue needs (`KeyPrefix`, the module's own established idempotency-key prefix; `PlatformTenant`, the sentinel tenant a platform-scope task is enqueued under). **Declaring means scheduled**: a host that runs a `jobs.Scheduler` over the finished registry's declarations enqueues every declaration on that declaration's own cadence, and the host's single switch is whether it starts a scheduler at all — there is no per-declaration approval step. A module therefore declares a task exactly where it also registers that task's handler, so every declaration has an executor in the composition that made it, and the scheduler-side key derivation (`jobs.ScheduleWindowStart` + `jobs.ScheduleIdempotencyKey`, the "prefix + tenant segment + window start" shape) resolves the same key the module's own `Enqueue*` path resolves for the same window — a tick and a manual enqueue landing in one window dedupe onto one job. `Add` validates every declaration (a non-empty `Type` and `KeyPrefix`, a positive `Every`, a known `Scope`, and `PlatformTenant` set exactly for `PeriodicScopePlatform`) with `ErrInvalidPeriodicTask`, and rejects a repeated `Type` with `ErrDuplicatePeriodicTask`; nothing is registered when the call returns an error.

`pkgcore.MountRoutes(mux, routes...)` is the one implementation of the mounting rule every module route follows — each route's `Handler` registered at its own `Path` and, unless the path already ends in `/`, at `Path+"/"` as well, so the handler is reachable at the exact path AND below it without ServeMux's redirect-on-missing-slash behavior (a redirect does not preserve a POST's method or body). See its doc comment for the full reasoning; `examples/reference-app` and `go/saasctl`'s generated project are its two consumers, and `ExampleMountRoutes` is the runnable demonstration.

`MountedRoute.Access` (`pkgcore.RouteAccess`) carries a route's authorization decision: `Public` declares it deliberately reachable without a permission check, and `Permission` (a `pkgcore.RoutePermission`, `func(*http.Request) string`) selects the permission each request must hold -- a function because the required permission routinely varies by the request's route (read on GET/HEAD, write otherwise). The zero value declares NOTHING: a module's own `Mount` records none, and the platform's route table (`rbac.GuardRoutes`, which a host wires over `reg.Routes.Routes()`) refuses to serve a mounted route whose decision the host's table does not state, marking public routes with the positive `Public` declaration rather than by omission. `rbac.SplitPermission` reads a three-segment `"<module>:<entity>:<verb>"` permission at its last separator, so the selector may return those as well as two-segment names. `ExampleMountedRoute_access` is the runnable demonstration.

`ConfigItem` declarations are validated when registered: `Type` must be one of `string` / `int` / `bool` / `duration`; a non-nil `Default` must be a Go value of that kind (`string`, `int` or `int64`, `bool`, `time.Duration`; nil is legal and means "no value until one is set"); `Min`/`Max` are declarative ranges defined for `int` and `duration` items only, must satisfy `Min <= Max`, and a non-nil `Default` must fall inside them; `Sensitive` and `Public` are mutually exclusive. A contradictory declaration fails the whole `Add` call with an error wrapping `ErrInvalidConfigItem` -- see the error index below.

The process-start input a module consumes is declared one of two ways, and both are the module's contract: as a `ConfigSchema` `derive` field (the shape every in-repo platform key takes -- each resolves at the final key path the component's namespace declares, so its address, environment spelling and derivation identity are the schema's own), or as a `BootstrapKey` declaration on the component descriptor's `BootstrapKeys` seat (for a key no component's construction owns; the seat currently has no in-repo member). Either way the declaring module never reads the value: the host resolves it once, before the process is wired, from command-line flags, the environment, an optional config file, the root-key derivation and the declared defaults (`go/pkgcore/config`), and injects the result. A `BootstrapKey`'s `Format` is one of `string` / `int` / `bool` / `hexkey` (a 32-byte key's hexadecimal text); `Default` is an operator-facing statement of the fallback behaviour, never a second runnable default -- the authoritative default is whatever stands at the end of the resolution chain the key resolves on: the host's loader target struct for a key a host spells out itself, or the declaring party's defaults table (`pkgcore/config`'s `WithDevDefaults`) for a key with no host-owned struct field, which is the shape a component's declaration takes when the declaring component is the key's only owner; a `Sensitive` declaration must carry a `Description`. A component's statically declared `BootstrapKeys` are validated where the engine reads them (format closed set, the Sensitive/Description pairing, one declaration per key path across components), and the engine's loader folds both declaration faces into one key-material resolution. By convention `Key`'s first segment is the owning module's name, so the generated reference can group declarations per module.

The seat's key-material derivation convention is one exported function: `func BootstrapKeyPurpose(keyPath string) (string, error)` returns the derivation purpose string of one declared key path -- the literal `"speed." + keyPath + ".v1"`, never a string-surgery transform -- which a host composes with `dbkit.DeriveKey(rootKey, purpose)` to get that key's 32-byte material from one root secret. A path that is empty or carries an empty segment (a leading, trailing or doubled dot) fails with `ErrInvalidBootstrapKeyPath`, a plain sentinel matched with `errors.Is`: derivation runs at boot, before any HTTP surface exists, so it is deliberately not an `apperr` code. The purpose embeds the declared key path verbatim and `dbkit.DeriveKey` is deterministic, so renaming a declared key path is a rotation of that key's material and must ship as one. The six key paths this repository's modules declare today -- each as a component `ConfigSchema` derive field -- and the purpose each freezes: `authn.blind_index_key` → `speed.authn.blind_index_key.v1`, `authn.pii_cipher_key` → `speed.authn.pii_cipher_key.v1`, `config.cipher_key` → `speed.config.cipher_key.v1`, `notification.contact_index_key` → `speed.notification.contact_index_key.v1`, `org.invitation_email_index_key` → `speed.org.invitation_email_index_key.v1`, `pki.local_key_cipher_key` → `speed.pki.local_key_cipher_key.v1`. Whether a path is a declared key at all, and the precedence between a derived material and an explicitly configured one, are the host's own checks and policy, never this function's.

**One key belongs to one layer.** Key material -- a component's `BootstrapKeys` declaration or the `derive` fields of its `ConfigSchema` -- that also appears on the runtime configuration seat (`reg.Config`) is refused by the assembly at Init's closing validation (`validateOneLayerPerKey`), naming the key and both layers: the two seats are invisible to each other while modules register, and key material has no fallback semantics to chain across the layers. An ORDINARY schema field is deliberately outside this rule: it may share a path with a runtime item of the same name, which is the construction-time-fallback shape a module uses when its runtime reads fall back to the value the assembly resolved (`authn.session_ttl`'s schema field and runtime item are the in-repo instance). Sharing a module prefix is never a conflict -- `authn.password_min_length` (runtime) and `authn.pii_cipher_key` (key material) coexist.

Declaring zero keys is an honest state, not a gap: a module that consumes no process-start input declares none, and nothing asks for a placeholder. The current census: the six platform key paths -- `authn.pii_cipher_key`, `authn.blind_index_key`, `org.invitation_email_index_key`, `notification.contact_index_key`, `pki.local_key_cipher_key` and `config.cipher_key` -- are each declared as a component `ConfigSchema` derive field, so the `BootstrapKeys` seat itself has no in-repo member; every other platform module declares no process-start input at all.

`NotificationType`'s own annotation: `RecipientVisibleParams` names the parameters a dispatch of the type may carry to its recipient -- the keys of the interpolation values the type's templates reference (see `go/notification`'s `Dispatch.Params`). Anything NOT named is delivery-internal context that must never reach the recipient, and `go/notification` enforces the declaration on the two boundaries it owns: `DeliveryService.Dispatch` refuses a dispatch carrying any parameter outside the list before anything is enqueued (`ErrDispatchParamsNotAllowed`, naming the type and the offending keys), and the delivery path narrows a payload that nevertheless reaches it -- a job enqueued before the declaration restricted its params -- down to the list before anything renders, derives into the delivery key or persists into the row. An EMPTY list is a real declaration: the type's copy is not parameterized, so its dispatches may carry no parameters at all. Nil means "no restriction declared": a type that does not declare the list keeps accepting any parameters, so no existing declaration's behaviour changes. pkgcore itself only carries the field -- the enforcement lives in `go/notification` (that module's `AGENTS.md` has the delivery-side detail); its first real declaration is `go/admin`'s `admin.impersonation_started`, which declares the empty list (that module's documentation records the leak the empty list closes).


**Deployment mode and implementation composition**

These are two orthogonal axes: deployment mode declares topology -- how many replicas may run at once -- and therefore which capabilities every selected component must declare; it never selects a component. The assembly's Prepare stage is the one place that compares the two, per component, against each descriptor's declared capability bits.

### Module lifecycle, one-clock TTLs and panicking remote handlers

- `func Shutdown(ctx context.Context, reg *pkgcore.ComponentRegistry) error` (go/app) closes every component the assembly constructed whose instance implements `Close() error` — the resource-ownership contract the registry's Close stage runs: a descriptor's declared Close callback when it has one, otherwise the constructed product's own `Close() error` (a declared callback supersedes that fallback and owns the release entirely, which is the shape a release needing the context, the registry or a custom teardown takes). An implementation whose `New` builds resources it owns (a dialed NATS connection, a Redis client or pgx pool built from cfg, a throwaway temp directory) declares the ownership by implementing `Close() error` on the value it returns; the registry's Close stage records it and releases it exactly once — at `Shutdown` on success, or on the drive's own failure path, immediately, so a misconfigured composition never leaks what it already dialed. An injected module value (`Put`) is the host's to close and is never touched. The built-in components in `eventbus/redis`, `eventbus/nats`, `eventbus/postgres`, `kv/redis`, `kv/postgres`, `kv/nats`, `kv/memcached` and the `objectstore.local` one each return such a closeable value over the client/pool/connection/directory their `New` itself built (`kv/memcached`'s closer releases the pooled connections `gomemcache`'s `Client.Close` closes); `mailer.smtp` and `objectstore.s3` own no closable resource (the minio-go client exposes no close).
- Expiry arithmetic on the PostgreSQL-backed store (`kv/postgres`) and outbox (`eventbus/postgres`) runs entirely on the database clock: `Set`/`IncrByFloatWithTTL` store `now() + <interval>` computed inside the statement, reads judge against `now()`, outbox `created_at` is stamped by `now()` at insert, and `PurgeOutboxBefore` cuts off at `now() - <interval>` — no application clock is consulted anywhere, so replica/database clock skew cannot shorten or stretch a TTL (a security control must not be judged early by a clock disagreement). `kv/postgres`'s `WithClock` option is the explicit regression hook for that property (the store never calls it). `kv/nats` and `kv/memcached` carry expiry inside the value envelope and judge it on the reading replica's clock — documented per-backend; adopting NATS's server-side per-key TTL is not viable on the pinned nats.go v1.53.1 / nats-server pair because any header-less Put/Update (the only kind the KeyValue API can issue) clears the per-key TTL, which cannot express "increment preserves a live key's expiry" (see `kv/nats`'s package doc comment).
- `kv/nats.NewKVStore` probes first and adopts an existing bucket only when the adopted configuration can satisfy what the `"kv.nats"` component declares and relies on, refusing a non-compliant one with the exported `ErrUnadoptableBucket` (which the component's `New` propagates out of the Construct stage unchanged, so startup fails naming the bucket and the offending configuration instead of silently bypassing the capability checks): memory storage is refused because it cannot satisfy the registered `SurvivesRestart`, a whole-bucket TTL is refused because the server would silently expire `ttl<=0` stores-forever keys, and every other field an operator provisioned (history depth, description, replication, placement) is preserved untouched and never a refusal reason. It creates (never update-overwrites) an absent one — file storage, no TTL, exactly the configuration the adoption checks accept — and resolves a create race by re-probing and verifying the winner through the same check. `kv/memcached` never deletes a logically expired row on the read path — a stale read's unguarded `Delete` used to be able to destroy a concurrent writer's fresh value — and revives an expired-but-physically-present key through the server's compare-and-swap at the token the read returned, exactly like `kv/nats`'s revision-guarded revive.
- A remote event-bus handler that panics is recovered (so one buggy handler cannot take down a replica) and logged, never silently swallowed; the entry is not acked-as-delivered and its redelivery is bounded by each backend's own mechanism: `eventbus/redis` leaves it pending in the consumer group (never refetched — the reader consumes new entries only — so no stall and no sibling re-run), `eventbus/nats` negatively acknowledges it and JetStream redelivers it at `panicRedeliveryDelay` intervals up to the consumer's `MaxDeliver` (`eventMaxDeliver`) budget, each redelivery re-invoking only the panicked handler values — never the message's whole fan-out, so healthy siblings run exactly once — and settling with a terminal log line when the budget is exhausted (see `eventbus/nats`'s `deliverRemote`), and `eventbus/postgres` advances its cursor past the row like a clean delivery — so later same-type rows keep flowing and healthy sibling handlers never re-run — while retrying the still-panicking handler values in-process on a bounded attempt budget, settling with a terminal log line when the budget is exhausted (see `eventbus/postgres`'s `retryPanickedRows`). The in-memory bus — the standalone mode's whole delivery machinery, with no reader goroutine of its own to absorb a panic — contains a subscriber panic inside `Publish` itself, recovered and logged, with the handlers registered after the panicking one still run (see its `Publish`). The broker-backed buses' own same-instance local fan-outs contain panics the same way: `Publish` runs each locally-subscribed handler through the package's own recover (`runLocalHandler` in each of `eventbus/redis`, `eventbus/nats` and `eventbus/postgres`), which logs the panic, drops it (never an error a caller could act on), lets the handler's siblings still run, and keeps the publish a success — the in-memory shape, applied because the local fan-out runs on the CALLER's goroutine (frequently a background goroutine with no recover of its own, the exact caller `runMemoryBusHandler`'s doc comment names), not on a reader goroutine the remote-delivery machinery protects. Each bus's integration tier pins the containment against a real broker (its `panicked_local_handler_contained_test.go`), and `eventbus/postgres`'s version additionally pins that the row whose local handlers ran is still marked delivered, while the poller path's bounded retry of still-panicking handler VALUES keeps covering deliveries that run outside any publisher's stack.

### `pkgcore/apperr`

`type Error struct { Code string; Params map[string]any; Status int }` with `Error()`, `Unwrap()`, `WithParam(key, value) *Error`, `WithSensitiveParam(key, value) *Error`, `SensitiveParams() map[string]any`, `WithCause(error) *Error`.

Constructors and the status each suggests: `Invalid` 400, `Unauthorized` 401, `Forbidden` 403, `NotFound` 404, `Conflict` 409, `Internal` 500. `func As(error) (*Error, bool)` recovers one from a wrapped chain, and `func HasCode(error, string) bool` is its predicate form: it reports whether the chain's outermost `*Error` carries exactly that code -- the way to classify a decorated error, since `WithParam`/`WithCause` never hand back the sentinel a caller might compare against with `==` or `errors.Is`.

`WithParam`, `WithSensitiveParam` and `WithCause` return a *derived* `*Error` and leave the receiver untouched, so a package-level error value can be shared and decorated per request.

The contract on `WithParam`'s write side (its doc comment states it in full, and it must survive into consuming modules): a parameter recorded there is serialized VERBATIM into the HTTP response body and handed to an untrusted caller -- no transport filters or redacts this map, so two prohibitions rest on the caller. Content: never keys, secrets, tokens, personal data, internal hostnames or resolved addresses. Shape: `Params` is `map[string]any` and `WithParam` accepts `any`, so never pass a struct, slice or map whose fields would serialize wholesale -- a field safe today silently rides into every response carrying the error tomorrow. Keep to known-safe scalars. `WithSensitiveParam` is the declared alternative for everything a client must not see or that needs more than a scalar: its value lives in a separate map (`SensitiveParams()`, the only reader) that no transport serializes and that `Error()` never renders; it is for server-side diagnostics only, never a response field. The caller declares; the library never guesses.

### `pkgcore/httpapi`

`func WriteJSON(w http.ResponseWriter, status int, v any)`, `func WriteError(w http.ResponseWriter, err error, fallback *apperr.Error)` and `func DecodeJSON(w http.ResponseWriter, r *http.Request, maxBytes int64, dst any, invalid *apperr.Error) bool`; the const `JSONContentType` (`"application/json; charset=utf-8"`) is the media type of every JSON response the shared surface writes.

`WriteJSON` writes the shared JSON success response: the status the caller gave, the shared content type (set unconditionally -- a response whose contract pins a different media type writes that body itself), and the JSON encoding of the value, which the encoder terminates with a newline. An encode failure after the status line went out is a broken client connection, not a response defect, and is dropped.

`WriteError` writes the coded error envelope every HTTP refusal is: the body `{"code": ..., "params": ...}` under the HTTP status the error's `apperr` constructor suggested, with `Content-Type: application/json; charset=utf-8` unless the caller set its own first (an endpoint whose contract pins a different content type sets it before the call). An err that is not, and does not wrap, an `*apperr.Error` is written as `fallback` instead, so raw Go error text never reaches a caller either way; the cause never crosses the wire, and a parameter-less error omits the `params` key rather than emitting `null`.

`DecodeJSON` decodes r's JSON body into dst, reporting whether it did. A positive `maxBytes` bounds the body BEFORE decoding, so an over-limit body fails as soon as the read passes the limit rather than after it has been buffered in full (passing w lets net/http ask the server to close the connection after the oversized request); a non-positive `maxBytes` decodes without a bound, for the endpoints that set no body limit. On any decode failure -- malformed JSON, a value of the wrong shape, or a body past the bound -- it writes `invalid`, carrying the decode error as its cause, through `WriteError` and reports false: the oversize answer is the same coded refusal as malformed JSON.

### `pkgcore/config`

`func New(opts ...Option) *Loader` with `WithConfigFile(path)`, `WithArgs([]string)`, `WithEnviron([]string)`, `WithRootKey([]byte)`, `WithRootKeyEnv(name)`, `WithKeyDerivation(fn)`; `func (*Loader) Load(target any) error`.

Priority, highest first: command-line flags, environment variables, config file, the root-key derivation (derive-tagged key-material fields only), the defaults already on the target struct. `Database.DSN` maps to key `database.dsn` (segments joined by `KeyDelimiter`), flag `--database.dsn`, variable `SPEED_DATABASE__DSN` (`EnvPrefix` + `EnvSeparator`). Per-field options come from the `TagName` struct tag: `config:"required"`, `config:"-"`, `config:"env=NAME"` and the bare `config:"derive"`.

A `derive` field is one 32-byte unit of key material and must be typed exactly `[]byte` (anything else fails the target description with `ErrInvalidTarget`, as does a repeated token). It resolves through the same chain with the derivation standing where the struct default would: an explicit value from any text source must be 64 hex characters and is decoded to the field's 32 bytes (a non-text value, notably a config-file scalar the parser read as a number, is refused naming the key and its source); an emptied variable or empty file entry reads as unset, exactly as `""` does for a string field; a configured root key derives the field -- the loader calls the `WithKeyDerivation` function with the root key and the field's dotted key path, which is the same identifier flags and config files use and the derivation's identity, so renaming a field rotates its material -- and with no root key configured the struct default stands. The root key comes from exactly one option: `WithRootKey` (the 32 bytes) or `WithRootKeyEnv` (the name of the variable holding the key's 64-hex text, read inside the same `Load`, which is what lets a host forbidden from reading the environment itself still wire derivation). A second root-key option in any combination, and an empty variable name, panic. A configured root key that is not a 32-byte key fails `Load` with `ErrInvalidRootKey`, naming the source; derive fields plus a configured root key but no installed deriver fail `Load` with `ErrInvalidTarget`; and a deriver's result that is not 32 bytes is refused like any other unfitting value. Derive-tagged keys never enter the text decode, and every stored value is a freshly allocated slice -- a host's package-level development default pre-filled onto such a field is never written through. The platform composition a host wires is `pkgcore.BootstrapKeyPurpose` (the seat's purpose per declared key path) plus `dbkit.DeriveKey`, in one call: `dbkit.DeriveBootstrapKey`.

`func EnvName(prefix, key string) string` is that variable spelling as an exported pure function -- the prefix, then the key uppercased with each level of nesting marked by `EnvSeparator` -- and the loader reads through it (`derivedEnvName` applies it to the loader's own prefix), so a document or tool that prints a variable name for a key cannot drift from the name the loader actually reads. A field pinned with `config:"env=NAME"` is read from that name whatever `EnvName` derives. The prefix must be a form `WithEnvPrefix` accepts (non-empty, ending in `_`); `EnvName` does not validate it.

### `pkgcore/i18n`

The merged message catalog. `func NewBuilder() *Builder`; `func (*Builder) AddModule(module string, fsys fs.FS) error`; `func (*Builder) Build() *Catalog`. `func (*Catalog) Lookup(locale, code string, params map[string]any) (string, error)`; `func (*Catalog) LookupPlural(locale, code string, count int64, params map[string]any) (string, error)`; `func (*Catalog) Locales() []string`; plus the request-header negotiation primitive `func Negotiate(header string, supported []string) (string, bool)`. Locale constants `LocaleZHCN` / `LocaleENUS` (en-US being the platform default of the negotiation chains); sentinel errors `ErrEmptyModuleName`, `ErrInvalidModuleName`, `ErrDuplicateModule`, `ErrMissingLocaleFile`, `ErrUnsupportedLocale`, `ErrUnsupportedShape`, `ErrParityMismatch`, `ErrUnknownLocale`, `ErrUnknownCode`.

What it is for, and the file contract, live in the package doc; the summary that must survive into consuming modules: API responses are never translated on the backend — handlers return an `apperr` code plus params, the client resolves them — and the catalog renders the content the backend generates itself (emails, invoices, webhook text, audit descriptions), in the *recipient's* locale. `the assembly` feeds every selected component's `Locales` embed.FS to one `Builder` per bootstrap (mirroring dbkit's `MigrationRegistry` aggregation) and puts the frozen `Catalog` into the by-type context; a component reaches it through the registry's `Locales()` accessor, nil when the assembly carries none. A built `Catalog` is read-only and safe for concurrent use. Rendering fails loudly: unknown locale or code is an error, never a silent English fallback; template syntax errors surface at render time. Plural categories follow CLDR (zh-CN has only `other`; en-US has `one`/`other`); `count` selects the category while the template reads it from `params`.

`Negotiate` is the shared negotiation primitive for the tiers that read a request's `Accept-Language` header (a request header is a transport channel — the frontend's own language chain, resolved client-side, is what the header carries): RFC 4647 lookup semantics — exact and language-prefix matching, case-insensitive, `q=0` parts dropped, the rest answered by descending q weight with equal weights keeping the header's written order — answering the supported locale's own canonical spelling. A miss is `("", false)`: `Negotiate` holds no default, and every caller applies its own chain's next tier (the platform default en-US, a stored profile value), so no chain can accidentally inherit another's fallback.

### `pkgcore/locales`

pkgcore's own seed message bundle (`zh-CN.toml` + `en-US.toml`, embedded as `locales.FS`): one message per catalog shape (plain, parameterized, plural), phrased as real sentences about pkgcore. Nothing in a running application reads it — `the assembly` feeds only the selected components' `Locales` bundles, and no pkgcore component carries one — so its honest roles are pkgcore's own test fixture (its suites feed it through `AddModule("pkgcore", locales.FS)` and the assembly's component loop) and the canonical shape example; it never joins any bootstrapped catalog. pkgcore renders no user-facing content of its own; a real rendered message belongs in the bundle of the module that renders it, and the seed entries exist only for as long as they earn their keep as fixtures.

### `pkgcore/probe`

| Signature | Purpose |
|---|---|
| `func Check(ctx context.Context, port, path string, opts ...Option) error` | One GET request to `path` at `127.0.0.1:port`; nil exactly when the response carries the expected status (200 unless `WithWantStatus`). The loopback host is a package constant, never a parameter -- `port` and `path` come from the host's own configuration and can only select which local listener is probed. A response with any other status (or a request that never completes) is an error, classified as `ErrUnexpectedStatus` for the status case |
| `func WithTimeout(timeout time.Duration) Option` | Bounds the whole probe attempt independently of `ctx` (zero or negative adds no bound), so a wedged server is reported unhealthy rather than waited on by a caller whose context has no deadline of its own |
| `func WithWantStatus(status int) Option` | Declares the status a healthy answer carries; an exact comparison, never a 2xx range, so a degraded answer cannot pass as healthy |
| `var ErrUnexpectedStatus` | The classification `Check` wraps when the request completed but the response carried a different status |

### `pkgcore/spa`

`func New(dir string, next http.Handler, opts ...Option) *Handler` builds the frontend handler: `dir` is the built frontend's root (resolved to an absolute path once, at construction, so a later chdir cannot retarget what it serves), `next` the wrapped composed handler that receives every request the frontend does not answer (a nil `next` panics -- a wiring mistake, never a choice). Whether to build a `Handler` at all is the caller's own decision, and a root that does not exist is not a construction error: the handler degrades to 404s for its own surface while every declared server path keeps passing through, so a host can mount it before its dist exists.

| Option | What it declares |
|---|---|
| `WithServerPath(p string)` | One exact path the wrapped handler owns (a host's liveness or metrics endpoint). Requests for it always pass through to `next`, never served from the directory |
| `WithServerPrefix(prefix string)` | A whole-segment path prefix the wrapped handler owns: the prefix itself and everything nested below it pass through, while a path merely sharing the leading characters does not. Declaring `/api` covers `/api` and `/api/v1/orders`, never `/apifoo`. The caller must declare every path its composed server owns outside the declared prefixes, or such a path would be answered from the directory instead of reaching its handler |
| `WithAssetPrefix(name string)` | The content-addressed asset directory's name, defaulting to `assets` (the directory a default vite build emits), where files carry the immutable cache policy and a miss answers a real 404 instead of the index fallback. The empty name disables the asset policy entirely, for a build whose output carries no content-addressed directory |

The `http.Handler` these options configure serves GET and HEAD from the directory and passes every other method through unchanged; the package doc comment carries the full interception, cache-policy, confinement and symlink contract.

Each `AssertConforms` calls `t.Run` once per property it checks and calls `factory` once per subtest, and a failure's subtest name says which property broke. The `eventbustest` and `kvstoretest` suites are capability-gated: their `caps` argument carries the capability bits the implementation under test declares (the same bits its component descriptor declares and its `component_test.go` pins to the package's exported `Capabilities` constant), and the cross-instance checks run only when `caps` declares `MultiReplicaSafe` -- a declaration is a promise the gated contract verifies, and an implementation declaring no bit runs the single-instance checks only, so declared-but-unverified cannot exist. The `eventbustest` and `kvstoretest` factory returns a PAIR of instances -- the shape of a deployment, not of a single store. A single-process implementation (the in-memory bus or store) returns the same instance twice: a one-replica deployment's "second instance" is its own one instance (the single-instance checks run against the pair's first instance; the cross-instance ones, for a `MultiReplicaSafe`-declaring implementation, against both). A shared-backend implementation (Redis, PostgreSQL, NATS, Memcached) returns two genuinely independent connections, and the cross-instance assertions become the checks that make the suite able to see what such an implementation exists for: a write or publish made through one connection visible through another. That makes the two-instance shape the contract-suite form of verifying the `MultiReplicaSafe` capability bit -- the bit claims exactly that a second instance of the same deployment observes what the first one wrote or published, and these assertions check that claim against the pair the factory builds, so an implementation that cannot satisfy the claim fails here the same way `the assembly` fails an assembly whose resolved implementation cannot satisfy the deployment mode's requirements (`ErrCapabilityUnsatisfied`), but at the level of behaviour rather than declaration. Each integration leg passes the declared bits, so which assertion runs follows from the declaration alone: the memory unit legs pass the zero capability, the redis/postgres/nats eventbus legs and the redis/postgres/nats kv legs pass `MultiReplicaSafe\|SurvivesRestart`, and the memcached kv leg passes `MultiReplicaSafe` alone. A `mailertest` or `objectstoretest` factory, whose suite keeps the single-instance shape, may hand in a backend that is not reusable across calls (a fake relay wired to expect one connection, say). `factory` is not required to return an empty-state instance -- every subtest derives its own key/event-type/message from the subtest name (or, for `mailertest`, uses fixed-shape messages that never collide), so several subtests can safely share one long-lived backend (a single Redis container, a single S3 bucket) without colliding, which is exactly what the Redis/RustFS integration legs below do.

The two restart protocols above verify the other KVStore capability bit, `SurvivesRestart`, which no per-subtest factory pair can express because it needs a genuine restart of the service that holds the data between the write and the read. Each KV integration leg runs the protocol matching its implementation's declaration — and its protocol call carries that same declaration as its `caps` argument, so a protocol run whose caps contradict the declaration is refused outright rather than silently verifying nothing: `kv/redis`, `kv/postgres` and `kv/nats` run `AssertSurvivesRestart(t, MultiReplicaSafe\|SurvivesRestart, ...)`, driving the restart against the real container — the state-holding-service restart `pkgcore.Capability`'s own `SurvivesRestart` doc comment names (the redis leg lets a forced one-second RDB snapshot fire before the stop, so the proof rests on a snapshot that demonstrably landed; the nats leg's store runs over the FileStorage bucket `NewKVStore` itself provisions, which survives the container's stop/start — the restart that would expose a MemoryStorage-adopted bucket, which `NewKVStore`'s own refusal makes unreachable through this store), and `kv/memcached` runs `AssertDoesNotSurviveRestart(t, MultiReplicaSafe, ...)`, pinning the factual basis of its honest non-declaration. The unit tier exercises the protocol machinery without Docker: `kvstoretest`'s own tests prove the positive protocol rejects a store whose data dies with its service's restart (the MemoryStorage shape on a unit scale) and accepts one whose data outlives the restart, prove the negative protocol accepts the loss, and pin each caps refusal.

The `SurvivesRestart` declarations of the non-KV modules are verified the same way, at the same service-restart level: `objectstoretest.AssertSurvivesRestart` (above) is the ObjectStore twin of the KV protocol, and `objectstore/s3`'s integration leg runs it against a genuine restart of its real RustFS container — an object stored before the stop/start must read back intact through a fresh store afterwards, and the restarted service must take new writes. The EventBus module's declarations get per-backend evidence instead of one shared protocol, because an EventBus is the transport, not the record — nothing the shared suite could read back through the bus API would outlive or fail to outlive a restart, so the state that matters (committed entries, cursors) is verified at the state level against each backend's own real container, and the two restart shapes are recorded separately rather than conflated: closing and reopening the bus (eventbus/postgres's catch-up proofs under the same `replicaID`) proves the durable-cursor-across-consumer-restart property and nothing about the server behind the bus, per `pkgcore.Capability`'s own definition, while each declaring eventbus leg's `declared_survives_restart_test.go` drives a genuine restart of its state-holding container — the PostgreSQL container between downtime publishes and the reconnecting replica's catch-up (eventbus/postgres), the Redis container between a committed publish and the read-back of the committed stream entries and group cursor (eventbus/redis, over a fixture that forces the one-second RDB snapshot the operator-configured persistence premise names), and the NATS container between a committed publish and the read-back of the committed JetStream stream state (eventbus/nats, over the file storage that is the zero value of `StreamConfig.Storage` and that this package never overrides). Each backend's package doc comment records what its declaration promises, the operator-provided configuration premise it stands on, and what it does not promise; see those records for the redis and nats persistence-premise details.

Every in-process or SMTP built-in implementation runs its matching suite from this module's `unittest/` directory, the unit-tier home the testing-layout rule assigns to module-contract drivers of the module root's own built-ins (unit-tier checks with no single source-file target): `unittest/eventbus_conformance_test.go`, `unittest/kv_conformance_test.go`, `unittest/mailer_conformance_test.go` and `unittest/objectstore_conformance_test.go` (package `unittest`, black-box against package `pkgcore` -- each must be an external test package, because each imports the module's `*test` package, which itself imports `pkgcore`, and an internal `package pkgcore` test file importing that back would be an import cycle) run `NewMemoryEventBus`/`NewMemoryKVStore`/`NewConsoleMailer`+`NewSMTPMailer`/`NewLocalObjectStore` through `AssertConforms`; the mailer driver additionally runs `TestSMTPMailer_PermanentRefusalCarriesTheSentinel` -- the sentinel clause, driven from a rejecting fake relay -- beside the conformance run. The SMTP leg needs no Docker: it scripts an in-process fake relay (`internal/testutil/fake_smtp_server.go`), so it lives in the plain unit tier alongside the other three memory/console/local legs. The eight Redis-, PostgreSQL-, NATS-, Memcached- and S3-backed implementations run the identical call against a real Redis/PostgreSQL/NATS/Memcached/RustFS container from their own subpackage's own `integration_test/` (`-tags=integration`, Docker required) -- `eventbus/redis/integration_test/`, `eventbus/postgres/integration_test/`, `eventbus/nats/integration_test/`, `kv/redis/integration_test/`, `kv/postgres/integration_test/`, `kv/nats/integration_test/`, `kv/memcached/integration_test/` and `objectstore/s3/integration_test/` -- rather than a shared one here: a package's integration tests live in its own `integration_test/` directory. `eventbus/postgres/integration_test/` additionally carries the real-server proofs beyond `AssertConforms` that no other module's tier needs: an explicit fan-out proof (two bus instances, distinct `replicaID`s, sharing one pool, both Subscribed -- both receive one Publish); an explicit catch-up proof in both of its consumer-restart shapes -- a full restart under the same `replicaID`, and a live listener connection severed and reconnected mid-test (`pg_terminate_backend` against the container) -- since the persisted per-replicaID cursor, durable across the CONSUMER's own restarts, is this implementation's whole reason to exist over `eventbus/redis`'s fresh-instance-at-live-end shape (a claim about the bus's own design, distinct from the `SurvivesRestart` bit both declare, which names the server's durability and which this tier additionally verifies for PostgreSQL by its own `TestEventBus_DeclaredSurvivesRestart_DurableCursorAcrossServerRestart` -- the same catch-up protocol with a genuine stop/start of the PostgreSQL container between the downtime publishes and the reconnecting replica); a re-entrant-publish pair proving a handler may `Publish` on the bus that invoked it without deadlocking on either delivery arm; a cursor-advance-retry proof that a connection loss between a row's delivery and its cursor advance never duplicates the row; and the two no-loss regressions pinning the healthy-path exactly-once guarantee -- same-type publishes serialized into id order by a per-type advisory transaction lock inside every publish transaction, and a local publish never advancing the persisted cursor past same-type rows this replica's own lagging listener has not delivered yet (`TestEventBus_LaggingPoller_LocalPublishMustNotSkipUnseenRemoteRows` and `TestEventBus_ConcurrentMultiReplicaPublish_NoEventLostNoDuplicate`; see the package doc comment's delivery-semantics note for why the crash windows that degrade this to at-least-once are accepted and documented rather than papered over). `eventbus/nats/integration_test/` carries the analogous fan-out proof for its own implementation, `TestEventBus_FanOutDeliversToEveryReplica` (two independent `*nats.Conn`s, one Publish, both replicas' handlers fire), the same property `eventbus/redis` and `eventbus/postgres` are each documented and tested to have. `kv/postgres/integration_test/` runs the same call against a real PostgreSQL container, alongside the two adversarial concurrency proofs `TestKVStore_ConcurrentIncrementsLoseNoUpdates` and `TestKVStore_ConcurrentCompareAndSwapSetIfAbsent_ExactlyOneWinner` that `AssertConforms` alone (effectively single-threaded) cannot exercise. A host that writes a new component descriptor for one of these modules, or puts a hand-built value into the by-type context, is expected to run the matching `AssertConforms` against it the same way, per this file's own Rules section.

`internal/testutil` holds `FakeSMTPServer`, the scripted SMTP relay `mailer_smtp_test.go`'s own wire-level tests and `unittest/mailer_conformance_test.go`'s SMTP leg both drive -- a single home for a helper a second consumer also needed, rather than a second, drifting copy of the same fake. It deliberately does not import `pkgcore` itself (only `package pkgcore`'s own unexported-symbol tests and the `unittest` driver, each outside `testutil`, need `SMTPConfig`/`NewSMTPMailer` to build a `pkgcore.Mailer` around a `FakeSMTPServer`, and `testutil` importing `pkgcore` back would make the `package pkgcore` internal tests an import cycle); each caller therefore builds its own few-line `pkgcore.Mailer` wrapper around `FakeSMTPServer.Addr()`.

## Typical integration

Implementing a module:

```go
func (m *Module) Register(reg *pkgcore.ComponentRegistry) error {
	reg.RoutesSeat().Mount("/api/v1/billing", m.router())

	if err := reg.ConfigSeat().Add(pkgcore.ConfigItem{
		Key: "billing.invoice_retry_limit", Type: "int", Default: 3,
		Description: "How many times a failed invoice charge is retried.",
	}); err != nil {
		return err
	}
	if err := reg.PermissionsSeat().Add("billing:read", "billing:write"); err != nil {
		return err
	}
	if err := reg.EventsSeat().Publishes(pkgcore.EventDecl{
		Type: "billing.invoice.paid", PayloadType: "billing.InvoicePaid",
		Description: "An invoice was paid in full.",
	}); err != nil {
		return err
	}
	reg.EventsSeat().Subscribe("authn.user_created", m.openCreditLedger)
	return nil
}
```

Booting a host:

```go
// The host's bootstrap target: go/pkgcore/config's loader fills it from
// flags, the environment, an optional config file and the struct's own
// defaults (a field may pin its exact variable name with config:"env=...").
var boot struct {
	DeploymentMode string
}
if err := config.New().Load(&boot); err != nil {
	return err
}
mode, err := pkgcore.ParseDeploymentMode(boot.DeploymentMode)
if err != nil {
	return err
}

// The assembly is the host's own: it selects the components the composition
// configuration names. A bare selection is the standalone composition (the
// in-process module components); a distributed host names the distributed ones
// instead (eventbus.redis, kv.redis, mailer.smtp, objectstore.s3), each
// declaring MultiReplicaSafe and SurvivesRestart, so a distributed-mode
// composition passes the capability validation Prepare runs. The deployment
// mode never selects an implementation -- it only states which capabilities
// the selected components must declare.
reg := pkgcore.NewComponentRegistry()
if err := app.Assemble(ctx, reg, spec); err != nil {
	return err
}
_ = mode
```

A host that wants pkgcore's own Redis/SMTP/S3 implementations instead of
building its own imports their subpackages (a blank import is enough) and
names the components in its composition configuration (`eventbus.redis`,
`kv.redis`, `mailer.smtp`, `objectstore.s3`) in place of the four hand-built
module values calls above -- each component's own doc comment records what it
does and does not source configuration for.

Returning an error:

```go
return apperr.NotFound("billing.subscription_not_found").WithParam("id", id)
```

Full runnable versions of all of the above live in `example_test.go` (the shared wiring and standalone-mode examples, the local object store's constructor, and the SMTP mailer's construction), `component_example_test.go` (the component-assembly walkthrough, run through the seven-stage drive), and each split-out subpackage's own `example_test.go` (`eventbus/redis`'s and `kv/redis`'s each demonstrate their constructor and the package's self-registration, aliasing their own import as `eventbusredis`/`kvredis` against go-redis's same `redis` package name; `objectstore/s3`'s needs no such alias; `eventbus/postgres`'s aliases as `eventbuspostgres`, mirroring the same convention for the same reason: its package name, `postgres`, is common enough (`gorm.io/driver/postgres`, `go/dbkit/dialect/postgres`) that an unaliased import would read ambiguously in a host file wiring more than one), plus `apperr/example_test.go`, `config/example_test.go` and `i18n/example_test.go`, and are executed by CI. `eventbus/postgres` is not named by the built-in composition (see this file's own file-location section above) -- its self-registration is instead demonstrated by its own `example_test.go`'s `Example` function, mirroring `eventbus/redis`'s identical one. `kv/nats`'s own `example_test.go` aliases its import as `kvnats`, the same reason `eventbus/postgres` aliases as `eventbuspostgres`: its package name, `nats`, collides with `github.com/nats-io/nats.go`'s own package name, which the same file also imports unaliased for the `*nats.Conn` type. Unlike `kv/redis`'s example (which dials nothing and runs for real, carrying an `Output:` comment), `kv/nats`'s `ExampleNewKVStore` is compiled but never executed, since provisioning a JetStream bucket is a real round trip no example can perform without a live server -- `kv/nats` is like `eventbus/postgres` in this respect too: the built-in composition does not name it. `objectstore/s3`'s example file additionally carries `ExampleFromConfig`, its one-step constructor's runnable documentation, which runs for real like its `NewObjectStore` sibling since it dials nothing.

## Rules

**Dependencies**

- Do not import any other speed module here, `dbkit` included -- `go/observability` too, even though it seems tempting for structured logging. pkgcore is the floor; an import from above is a cycle. That is why the `Component` descriptor's `Migrations` field is a plain `embed.FS` rather than a `dbkit` type, and why the package's own log calls reach for the standard library's `log/slog` directly instead of `obs.FromContext` -- `warnIfNotDurable`'s `SurvivesRestart` startup warning, the component drive's one module-composition Info line, and the memory bus's contained-panic Error line. The last can fire on any publish path; the floor cannot do better without importing `go/observability`, which would be a cycle (the same accepted trade each `eventbus/*` subpackage records on its own recover sites).
- Do not add a third-party dependency to the root package without arguing for it in the pull request: it lands in every consumer's `go.sum`. **The root package carries no third-party dependencies of its own**: the ones its subpackages need (go-redis, minio-go, jackc/pgx, nats.go, gomemcache) live behind each subpackage's own constructor, and no SDK type crosses a module -- only a consumer that imports the subpackage itself pays for its dependencies, exactly as the packaging rule below intends. Go resolves dependencies per package, so a consumer of the root package alone inherits none of them; the claim is measurable at any time with a throwaway module that blank-imports only `github.com/vislake/speed/go/pkgcore` and runs `go mod tidy` under `GOWORK=off`. minio-go was chosen over the AWS SDK for the leaner dependency graph and for covering MinIO, Aliyun OSS and AWS S3 with one client.
- `kv/postgres`'s third-party cost is confined to its own subpackage: a consumer who never imports it inherits none of pgx's closure, and a consumer already on `go/dbkit`'s PostgreSQL dialect resolves the identical pgx version Go's minimal version selection already settled on, downloading nothing new. `kv.go` itself imports no `gorm` and no `go/dbkit`, which this package cannot depend on regardless (see the dependency-direction rule below).
- `eventbus/postgres`'s third-party cost follows the same confinement: its pgx/pgxpool closure is already present in any application that depends on `go/dbkit`'s PostgreSQL dialect, so for that consumer -- the ordinary one for a deployment that already runs PostgreSQL -- the subpackage adds no new third-party dependency at all, only a new import inside a module it already carries. That is a real advantage over `eventbus/redis` (which requires go-redis regardless of what else the application depends on) for a PostgreSQL-only deployment that has no other reason to run Redis.
- `kv/nats`'s third-party cost is the nats.go closure it shares with `eventbus/nats` -- the same pinned version, carried once in this module's root `go.mod` -- so the marginal cost of the second NATS subpackage is zero, and a consumer who imports neither pays nothing, per the packaging rule below.

**Interfaces, deployment modes and implementation composition**

- Do not expose a capability on an infrastructure interface that only one implementation can satisfy. Design against the weakest of that module's registered implementations -- an anchor that moves as implementations are added, not a fixed "the standalone one": no server-side scripting, no pub/sub, no pipelines on `KVStore`.
- Do not branch on `DeploymentMode` outside assembly wiring. Business logic must not contain `if mode == DeploymentModeStandalone`: business code has no global mode value to branch on at all -- it only ever sees the by-type values the `ComponentRegistry` carries (`EventBus`/`KVStore`/`Mailer`/`ObjectStore`).
- Do not write a mock for `KVStore`, `EventBus`, `Mailer`, `ObjectStore` or `SMSSender`. `NewMemoryKVStore`, `NewMemoryEventBus`, `NewConsoleMailer`, `NewLocalObjectStore` and `NewConsoleSMSSender` are the test doubles; the four in-process ones are the very implementations the `"kv.memory"`/`"eventbus.memory"`/`"mailer.console"`/`"objectstore.local"` components provide (`kv_memory.go`, `eventbus_memory.go`, `mailer_console.go`, `objectstore_local.go`; `NewConsoleSMSSender` is likewise what the `"sms.console"` component provides, in `sms_console.go`).
- Do not add a new in-process or stdlib-backed built-in's component descriptor anywhere but the module's own component file (`eventbus_memory.go` for an eventbus built-in, `kv_memory.go` for a kv one, `mailer_console.go`/`mailer_smtp.go` for a mailer one, `objectstore_local.go` for an objectstore one); that file is the one centralized place its module's built-in components live, mirroring the "single home" instinct the rest of the codebase already applies elsewhere (e.g. `@speed/api-client`'s HTTP module) -- not a scattered `init()` per built-in. A built-in that pulls in a third-party dependency (a database/sql-driver-style implementation such as `eventbus/redis`, `kv/redis` or `objectstore/s3`) registers itself instead, from its own subpackage's own `init()`, precisely so that registering it does not require the dependency to live in this package -- see the "third-party dependency" rule above and each subpackage's own doc comment. Do not move such a registration into the module's built-in component files "to keep them together": that would undo the dependency-isolation split.
- Do not declare a `Capability` an implementation does not actually have, and do not add a new `Capability` bit without updating `String()`. `the assembly`'s validation trusts the declaration, not the value: a descriptor declaring `MultiReplicaSafe` over a bus that is not multi-replica-safe passes assembly and fails silently later, in production, under real replica count -- the one thing this whole mechanism exists to catch.
- Do not hand-roll a component descriptor for an implementation a package already ships. Every distributed implementation package registers its own component (`component.go`, from `init`) whose `New` funnels through the package's own constructor and whose `Capabilities` field carries the exported `Capabilities` constant its `component_test.go` pins; a hand-rolled descriptor can drift from both. Write your own descriptor only for an implementation no package owns.
- Do not expect `the assembly` to fail an assembly for lacking `SurvivesRestart`. It logs a startup warning (via `log/slog`, since pkgcore cannot import `go/observability` -- see the dependency-direction rule below) and proceeds; losing state across a restart is a legitimate, deliberate choice for a throwaway or development composition, never a hard error. A `Stateless` implementation is exempt from even that warning: it holds nothing for a restart to drop, so a banner over it would name no loss (see `warnIfNotDurable`). Every boot also logs one Info line naming what the four modules resolved to -- the durability warnings are not the composition answer; the Info line is, and it must not be removed for the sake of quieting the warnings (a `Stateless` module like `mailer.console` would otherwise boot in silence, hiding a forgotten `Put(NewSMTPMailer(...))` that prints verification codes to stdout and reports success).
- Do not silently change an interface's semantics when adding an implementation. `kv/redis.NewKVStore` preserves the in-memory store's observable behaviour; where a Redis-backed bus cannot (asynchronous cross-process delivery, JSON payload shape, failures of remote handlers unobservable, no catch-up), the difference is documented on the constructor and spelled out to consumers before they choose it.
- Do not add a new implementation of `KVStore`, `EventBus`, `Mailer` or `ObjectStore` -- built-in or host-supplied -- without running that module's capability-gated `AssertConforms` against it, passing the same capability bits the implementation declares (its component descriptor's `Capabilities` field carries them and its `component_test.go` pins them to the exported `Capabilities` constant; a host-supplied component declares them on its own descriptor the same way). This is the mandatory conformance check the "Contract tests" section above documents; skipping it is how a new implementation quietly diverges from the contract the others honour -- and the gated form is what keeps a declaration a promise the suite verifies: an implementation declaring `MultiReplicaSafe` must run the cross-instance assertions (its pair is the verification), and one declaring no bit runs the single-instance checks only. A `KVStore` implementation that declares `SurvivesRestart` must additionally pass `kvstoretest.AssertSurvivesRestart`, called with those same declared bits, against a genuine restart of the service that holds the state -- its `caps` argument refuses a call that does not declare the bit, so the protocol run and the declaration cannot come apart -- and one that honestly does not declare the bit runs `AssertDoesNotSurviveRestart` (whose `caps` argument refuses the opposite mismatch) instead, pinning the factual basis of the non-declaration.
- Do not build a read-modify-write cycle out of `Get` + `Set`. Use `IncrByFloat`, `IncrByFloatWithTTL` or `CompareAndSwap`; they are the only operations every backend can make atomic. A caller-side `IncrByFloat` followed by a conditional `Set` to attach a ttl on the key's creation is exactly the race `IncrByFloatWithTTL` exists to close — prefer it outright for that case rather than hand-rolling a two-call sequence (see `IncrByFloatWithTTL`'s own doc comment).
- Do not retain or hand out a caller's byte slice in a `KVStore` implementation, and do not perform an operation on a cancelled context — return the context error instead.

**Tenancy**

- Do not treat a missing tenant as "all tenants". `MustTenantFromContext` returns `ErrNoTenant` so callers fail closed; propagate that error rather than defaulting.
- Do not pass a tenant through a bare string context key. Use `WithTenant`.
- Do not invent a system purpose at the call site. Declare it with `RegisterSystemPurpose` from the module's own registration; an undeclared purpose is refused.
- Do not call `WithSystemContext` without an `Actor`, and record a `Ticket` whenever one exists. Every bypass must be attributable.
- Do not treat a system context as an authorization bypass, and do not assume it bypasses tenant filtering either: this package's marker suppresses nothing by itself. The layers that own tenant filtering and data access decide what a system reason changes -- and several of them (dbkit's `Repository[T]` among them) never widen anything on its presence.

**Module contract**

- Do not widen the module contract (`Register`'s signature or the descriptive surface beside it). Under lockstep versioning that breaks all modules at once — add a seat to the `ComponentRegistry` instead.
- Do not perform I/O in `Register`. It declares; the assembly decides when anything runs.
- Do not depend on module registration order. Declare the dependency in `DependsOn`; the assembly sorts, and reports a cycle or a missing dependency rather than guessing.
- Do not call a module's attach step before the assembly returns: `config`, `rbac` and `integration` each expose `Attach(reg *pkgcore.ComponentRegistry) (*<module>.Service, error)` and `admin` exposes `AttachRBAC(*rbac.Service)` — each exactly once, before the first host step that consumes the returned Service. No shared helper batches them: every `Attach` returns its own module's Service type, so no one interface is satisfied by all of them, and each host wires its own sequence (`the assembly`'s "Post-assembly module steps" section is the contract, including what an un-attached Service does when something reaches it).
- Do not swallow a registrar error. A duplicate key is a bug across modules, not a merge, and nothing is registered when the call returns an error.
- Do not publish a domain event the module never declared with `Events.Publishes`. The declarations are the catalog `integration` maps onto the versioned public event schema.
- Do not decorate a shared `apperr` value expecting the receiver to change. `WithParam` and `WithCause` derive a new error.

**Errors and configuration**

- Do not put human-readable text in an `apperr` code. The code is machine-readable and stable; the client resolves it through its own i18n catalog.
- Do not change or reuse a released `apperr` code. It is part of the public API contract.
- Do not surface a wrapped cause in an API response. `WithCause` is for logs and `errors.Is`.
- Do not put a value a client must not see into `WithParam`, and do not pass a struct, slice or map as a parameter: `Params` is serialized verbatim into the response body, unfiltered. Record server-side-only diagnostics with `WithSensitiveParam` (read back through `SensitiveParams()`), never in `Params`.
- Do not resolve runtime or tenant-overridable settings through `config.Loader`. It handles bootstrap values only: how to reach infrastructure, and which deployment mode is running.
- Do not read flags, environment variables or config files inside a component to configure it. The component declares how each `ConfigSchema` field resolves (the `config` tag) and receives the finished value as its `New` cfg; the five-source merge belongs to the assembling engine's `ComponentConfigResolver`, and a component reading a source itself bypasses the declaration the assembly validated and the strict decode it enforced.
- Do not hand-write the configuration reference. It is generated from the `ConfigItem` declarations.

**Internationalization**

- Do not translate API responses with `i18n`. Handlers return codes; the catalog renders backend-generated content only, in the recipient's locale — never the operator's.
- Do not add a language by editing `pkgcore/i18n`. The catalog's languages are its modules' files: a new language is one new `<language>.toml` file (its name a canonical BCP 47 tag) in every module that ships messages, and nothing else. The catalog's full-coverage guarantee is scoped to zh-CN/en-US; the mechanism itself is deliberately not frozen to those two languages.
- Do not ship a grouping section (`[errors]`) or an unquoted dotted header in a locale file. go-i18n folds the section name into the id; the contract is one flat top-level entry per message, id quoted and prefixed with the module's `Name` plus a dot.
- Do not let one locale drift from another. Every language a module ships must carry the same id set; `Builder.AddModule` fails with `ErrParityMismatch`, and `tools/check_i18n_keys.py` checks the same zh-CN/en-US parity over the raw files -- the docs-check pipeline runs it on doc/i18n-touching PRs (.github/workflows/docs-check.yml).
- Do not render a missing message in a fallback language. An unknown locale or code must surface as an error; the catalog never falls back silently.
- Do not add a third-party dependency to the root package for i18n. All i18n third-party dependencies live in the `i18n` subpackage: nicksnyder/go-i18n/v2 (the catalog machinery), BurntSushi/toml (the locale-file parser -- go-i18n ships no TOML decoder of its own, JSON only, and the flat shape is validated over BurntSushi's decode before go-i18n sees the messages, which is what rejects the [errors]-section id-folding a straight decode would produce), and golang.org/x/text, which the catalog code itself imports for its `language` package.

**Documentation**

- Do not add an exported identifier without a doc comment, an `Example` in the matching `example_test.go`, and an entry in the tables above, in the same pull request.

## Error index

| Sentinel | Triggered by | Handling |
|---|---|---|
| `ErrInvalidDeploymentMode` | `ParseDeploymentMode` on anything but standalone/distributed | Abort startup; the deployment mode is misconfigured |
| `ErrNoTenant` | `MustTenantFromContext` on an unscoped context | Fail closed. In a worker, rebuild the context with `WithTenant` |
| `ErrSystemActorRequired` | `WithSystemContext` with an empty `Actor` | Name the actor; the bypass is audited |
| `ErrSystemPurposeNotRegistered` | `WithSystemContext` with an undeclared purpose | Declare it with `RegisterSystemPurpose` |
| `ErrNotNumeric` | `IncrByFloat` on a key holding a non-number | The key is not a counter; the stored value is left untouched |
| `ErrInvalidMail` | `Mailer.Send` on a message with an empty From, no recipients, an empty recipient, an address field that does not parse as one address, a line break in a header, or no body | Validate the message; nothing reached the wire |
| `ErrTransportPermanent` | Not returned by any pkgcore call directly: the sentinel a transport implementation wraps around the destination's own permanent refusal -- the SMTP mailer's 5xx answer to RCPT, the aliyun and tencent SMS adapters' invalid-number and blacklist codes | Match with `errors.Is`. A wrapped failure is terminal for that destination (go/notification stops retrying and marks its external contact bounced); an implementation must never wrap a connection, credential, configuration or transient failure -- the sentinel's own doc comment draws the boundary |
| `ErrInvalidObjectKey` | Any `ObjectStore` operation with a key that breaks the shared grammar (empty, overlong, an empty or `.`/`..` segment, NUL or backslash) | Validate the key before the call; nothing reached the backend. The error names the broken rule, never the key |
| `ErrObjectNotFound` | `ObjectStore.GetObject` on a key no object is stored under, every backend reporting the same sentinel | Handle absence as a normal outcome. `DeleteObject` never returns it: deleting a missing key is a success |
| `ErrDependencyCycle` | `DependsOn` forming a cycle | The error names the cycle; break it |
| `ErrInvalidConfigItem` | An item whose fields contradict one another: an unknown `Type`, a `Default`/`Min`/`Max` of the wrong Go type, `Min`/`Max` on a `string`/`bool` item, `Min` above `Max`, a `Default` outside its declared range, or `Sensitive` with `Public` | Fix the declaration; nothing was registered (the message never prints a sensitive item's value) |
| `ErrInvalidBootstrapKeyPath` | `BootstrapKeyPurpose` on a path that is empty or carries an empty segment (a leading, trailing or doubled dot) | Fix the declaration's key path; nothing is derived under it. The error names the offending path -- declaration text, never secret material |
| `ErrDuplicateConfigKey` / `ErrDuplicateFeatureFlag` / `ErrDuplicatePermission` / `ErrDuplicateJobType` / `ErrDuplicateNotificationType` / `ErrDuplicateEventType` / `ErrDuplicateAuditAction` / `ErrDuplicatePeriodicTask` | The same key registered twice | Two modules own one key; decide which does |
| `ErrInvalidPeriodicTask` | A periodic-task declaration whose fields contradict one another: an empty `Type` or `KeyPrefix`, a non-positive `Every`, an unknown `Scope`, a platform-scope declaration without its `PlatformTenant`, or a per-tenant declaration carrying one | Fix the declaration; nothing was registered |
| `ErrUnresolvedFeatureDependency` | A flag depending on a flag nobody registered | Register the flag, or drop the dependency |
| `ErrCapabilityUnsatisfied` | The assembly's `Prepare` validating a selected component whose declared `Capability` does not satisfy `DeploymentMode.RequiredCapabilities()` | The error names the component, the missing capability and the mode; select or configure a component that qualifies, or put a qualifying value into the by-type context. There is no per-mode sentinel family: one error carries the whole refusal |
| `ErrMissingSeamConfig` | A built-in `mailer.smtp` or `objectstore.s3` construction with a configuration missing a field that has no safe default (SMTP host; S3 endpoint, bucket or credentials) | Supply the field in the component's configuration block, or put a hand-built value (`SMTPConfig`/`s3.Config`) into the by-type context |
| `ErrMissingConfigValue` | The Prepare stage resolving a selected component's configuration block: a field the schema declares `config:"required"` for which no source supplied a value | The error names the component and the key path; supply the value in the component's configuration block (or let a source the resolver consults supply it), or drop the declaration. `config.ErrMissingValue` is the loader's separate zero-value check on a host's own loader target |
| `ErrConfigKeyConflict` | The Prepare stage's one-key-path-per-source check: two selected components' `ConfigSchema` fields, or a field and a `BootstrapKeys` declaration, producing one final key path under the namespaces the descriptors declare | The error names the key path and both sources; give one of them a distinct key path or namespace. Distinct from `ErrDuplicateConfigKey`, which is the runtime Config seat's duplicate-item refusal |
| `eventbus/redis.ErrEventBusClosed` | `Publish` on an `eventbus/redis.EventBus` after `Close` | Wiring error: a closed bus is out of the deployment; build a fresh one. Lives in the `eventbus/redis` subpackage, not here -- nothing outside the Redis implementation ever referenced it as `pkgcore.ErrEventBusClosed`, so it moved with the implementation rather than staying a root-package sentinel one subpackage's type returns |
| `eventbus/postgres.ErrEventBusClosed` | `Publish` on an `eventbus/postgres.EventBus` after `Close` | Identical wiring-error treatment, mirroring `eventbus/redis.ErrEventBusClosed` exactly; lives in the `eventbus/postgres` subpackage for the same reason |
| `probe.ErrUnexpectedStatus` | `probe.Check` against a server answering a status other than the declared one | The error names the probed URL, the answered status and the expected one; report the container unhealthy. Request failures and an elapsed bound are plain wrapped errors (a `url.Error`/context error), not this sentinel -- only a completed request with the wrong status carries it |
| `config.ErrMissingValue` | A `config:"required"` field left zero | The error names the key and every source consulted |
| `config.ErrInvalidValue` | A supplied value not applicable to its field | The error names the offending key and its source |
| `config.ErrSourceUnreadable` | An unparseable config file or malformed flag | Fix the source; startup aborts |
| `config.ErrInvalidTarget` | `Load` given a non-struct-pointer or a bad `config` tag, or a target with derive fields and a configured root key but no installed deriver | Programming error; fix the target type or the wiring |
| `config.ErrInvalidRootKey` | The configured root key is not a 32-byte key: `WithRootKey` a non-empty key of another length, or `WithRootKeyEnv`'s variable set to a non-empty value that is not 64 hex characters | The error names the source (the option or the variable); an unset or emptied variable is an unconfigured root key, not an error |
| `i18n.ErrEmptyModuleName` | `Builder.AddModule` with an empty module name | Programming error; every module has a `Name()` |
| `i18n.ErrInvalidModuleName` | `Builder.AddModule` with a module name containing a dot | Programming error; the name is the `<module>.` prefix of every message id the module ships, and a dotted name would let two modules' id prefixes nest |
| `i18n.ErrDuplicateModule` | `Builder.AddModule` with a module already added | Register each module's locales exactly once |
| `i18n.ErrMissingLocaleFile` | A module shipping locale files but not one for every language of the catalog | Add the missing file; a module contributes every catalog language or none |
| `i18n.ErrUnsupportedLocale` | A locale file that is not a canonical language tag, or a file for a language the catalog does not serve | Fix the file name, or add the language to every message-shipping module |
| `i18n.ErrUnsupportedShape` | A file violating the flat contract: unquoted or dotted headers, a grouping section such as `[errors]`, reserved-key misuse, a table carrying both `translation` and a plural category, or a plural table with no translation | The error names the file and the entry; fix the TOML shape |
| `i18n.ErrParityMismatch` | The id sets of one module's locale files differing | The error names the languages and the missing ids; `tools/check_i18n_keys.py` checks the same zh-CN/en-US parity over the raw files -- the docs-check pipeline runs it on doc/i18n-touching PRs (.github/workflows/docs-check.yml) |
| `i18n.ErrUnknownLocale` | `Lookup`/`LookupPlural` for a locale no module ships | Programming error; the catalog never falls back to a default language |
| `i18n.ErrUnknownCode` | `Lookup`/`LookupPlural` for a code no module contributed | Programming error; the catalog never falls back to a default language |
