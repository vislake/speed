# metering

go/metering is speed's usage-metering module: a single `Recorder` interface (plus a billing-grade `Enqueue` helper) business modules call to report usage, decoupled entirely from which backend stores and aggregates it. This file is the module-level discipline that ships with `go/metering` to consuming projects; the design rationale is `docs/internal/06-billing-and-metering.md`, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: round 1, a deliberately bounded foundation round.** This round ships the `Recorder`/`Enqueue` pipeline end to end (both reliability tiers), the in-process aggregation backend only (real-time `sync.Map` counters plus SQLite/PostgreSQL usage-summary tables), and an overage-threshold-crossing event published on `pkgcore.EventBus`. It does NOT ship the Plan/Feature/Entitlement domain model, credits, actual quota enforcement, or a distributed aggregation backend. Judge what exists by the code, not by this sentence.

## Scope

**In scope this round.** `UsageEvent` and the `Recorder` interface (`recorder.go`). `AnalyticsRecorder`, the analytics-grade (fail-open) tier: an in-process bounded channel plus a background flush goroutine (`analytics.go`). `Enqueue` and `Dispatcher`, the billing-grade (must-not-silently-drop) tier's write and delivery halves: a caller-transaction outbox write plus a background poller retrying indefinitely and escalating a permanently failing row to an Error-level alert once its failed attempts pass the stated horizon (`outbox.go`, `dispatcher.go`, `repository.go`'s outbox functions; see the "Escalation round" section below). `Aggregator`, the in-process aggregation backend both tiers feed: real-time counters, database-backed summary rows, and overage-threshold detection (`aggregator.go`, `overage.go`); its billing-grade entry point, `IngestBillingGrade`, additionally records a durable idempotency receipt in the same database transaction as the summary write, so `Dispatcher` redelivering a row after an interrupted first attempt cannot double-count it (`ingest_receipt.go`). Three tables with dual-dialect versioned SQL migrations (`metering_usage_summaries`, `metering_outbox_records`, `metering_ingest_receipts`). `pkgcore.Module` wiring: configuration items for the period-bucket size and a default overage threshold, and the one published domain event.

**Deliberately not in scope this round:**

| Not here | Where it belongs | Why |
|---|---|---|
| Plan/Feature/Entitlement domain model, `Entitlements.Check` | `go/billing` (unstarted) | docs/internal/06-billing-and-metering.md's own domain-model section places this there; metering measures and signals, it does not decide |
| Credits (`credit_balance`/`credit_transaction`, reserve/confirm/refund) | `go/billing` (unstarted) | The design doc is explicit credits are a separate, synchronous path, not the metering pipeline |
| Actual blocking of over-quota calls | `go/billing` (unstarted) | `OverageThresholdCrossedEvent` is a signal; `Plan.Grants.OverageMode`'s Block/AllowAndBill/Notify decision needs the domain model above to exist first |
| Redis Streams / PostgreSQL atomic-increment aggregation backend, TimescaleDB raw-detail storage | A later round | This round ships the in-process backend only, per the design doc's own "MVP now, split into its own container once volume grows" framing |
| A `jobs`-queue-driven `Dispatcher` | A later round's hardening | This round's Dispatcher is an in-process goroutine; the task's own scope explicitly allows this as later-round work |
| An HTTP surface / OpenAPI fragment | A later round | metering is a Go-level API business modules call in-process, not a service reached over HTTP, this round |
| `metering:*` permissions, an audit action | A later round | No HTTP surface to gate, and no operation privileged enough to warrant an audit trail entry this round; inventing either speculatively is exactly what the round-boundary discipline forbids |

## Data model

Three tables, deliberately spanning **two** data domains (`docs/internal/04-data-and-tenancy.md`):

| Table | Domain | Repository shape | Isolation proof |
|---|---|---|---|
| `metering_usage_summaries` | Tenant | `SummaryRepository`, embeds `dbkit.Repository[UsageSummary]` | `tenancytest.AssertIsolated` |
| `metering_ingest_receipts` | Tenant | `IngestReceiptRepository`, embeds `dbkit.Repository[IngestReceipt]` | `tenancytest.AssertIsolated` |
| `metering_outbox_records` | Platform | plain `*gorm.DB` functions (`repository.go`) | `tenancytest.AssertNotTenantScoped` |

### Outbox table: platform data, not tenant-scoped

This is the module's one deliberate departure from a literal "every table this round writes must be tenant-scoped" reading, and it is worth stating plainly since it looks, at first glance, like it should be tenant data (every row genuinely belongs to one tenant).

`OutboxRecord` does **not** implement `dbkit.TenantScoped`. The reason is `Dispatcher`: outbox delivery is a background process that must find every tenant's pending rows to retry them. `dbkit.Repository[T]` has no cross-tenant read path -- `tenancy.WithSystemContext` elevates *who may ask* for the escape hatch, not *what `dbkit.Repository[T]` itself can see* (see that function's own doc comment: "granting a system context does not widen what `dbkit.Repository[T]` ... can see or touch"). A genuinely tenant-scoped `OutboxRecord` would leave `Dispatcher` with no sanctioned way to scan pending rows across tenants at all.

This is not a novel problem or a novel answer: it is the exact shape `go/jobs`' own `jobRecord` already solves the identical way, and root `CLAUDE.md`'s Repository Status census names two more precedents doing the same thing (`go/dbkit`'s `AuditEvent`, `go/config`'s `row`) -- "platform data with a real, non-enforced `tenant_id` column ... never `dbkit.TenantScoped`". `tenant_id` on `metering_outbox_records` is real and populated; it is simply not the database-enforced kind, and `tenancytest.AssertNotTenantScoped` (not `AssertIsolated`) is the correct suite for it, run in `repository_test.go`.

`UsageSummary`, by contrast, has no such cross-tenant reader: every caller who ever needs a summary row already knows which tenant it is asking about (an event's own `TenantID`, or a tenant's own dashboard request), so it stays genuinely tenant-scoped through `SummaryRepository`.

### `UsageSummary.ID` is deterministic

`ID` is `summaryID(Feature, PeriodStart)` -- not a random ULID/UUID -- so `Aggregator.upsertSummary` can reach the one row for a given `(tenant, feature, period)` through `dbkit.Repository[T].FindByID` rather than a hand-written query, which this codebase's raw-GORM-bypass discipline forbids outside `dbkit`'s own internals. Because `ID` is derived from `Feature` and `PeriodStart` alone, it is **not** globally unique across tenants -- two different tenants both measuring `"ai.generation"` in the same calendar month get the same `ID` string -- so `UsageSummary` declares `TenantID` as a second `primaryKey` column directly (a true composite key `(id, tenant_id)`, the same shape `go/config`'s `row` uses for its own non-globally-unique key), rather than embedding `dbkit.TenantModel` the way a globally-unique-ID model (`go/pki`'s `Certificate`, say) safely can.

### `metering_ingest_receipts`: the billing-grade idempotency ledger

`Dispatcher`'s billing-grade delivery is two separate database writes: `Aggregator.IngestBillingGrade` folding the event into the aggregation pipeline, and (a separate call, against Dispatcher's own connection) `markOutboxDelivered` flipping the outbox row's status. A process crash, or merely a transient failure of the second write, landing between the two leaves the outbox row `pending`, so the next `Dispatcher.RunOnce` cycle reclaims and redelivers it -- calling the ingest path a second time for an event that was already durably applied.

`IngestReceipt` closes that window: `IngestBillingGrade` inserts one receipt row keyed by `(TenantID, IdempotencyKey)` in the SAME database transaction as the `UsageSummary` upsert -- `Aggregator.foldIntoSummaryOnce`'s own one `dbkit.WithTenantSession` call, both writes composed as raw GORM calls against the tx it hands its callback (see `upsertSummaryTx`'s doc comment for why routing either write back through `dbkit.Repository[T]` would nest a second, refused transaction; both run against `SummaryRepository`'s own connection, never `Dispatcher`'s -- see `ingest_receipt.go`'s doc comment for why that connection independence, exercised by `dispatcher_test.go`'s delivery-failure and crash-recovery tests, rules out merging this with `markOutboxDelivered`'s own write instead). Either both commit, or neither does.

The receipt insert runs as `ON CONFLICT DO NOTHING`, not as a plain insert whose `gorm.ErrDuplicatedKey` violation would be caught: on PostgreSQL a statement error leaves the whole transaction aborted, so catching the violation and committing anyway would commit a poisoned transaction (the driver reports the server's COMMIT-became-ROLLBACK as an error) -- an SQLite-only suite, where a failed statement is harmless, cannot see that failure, which is exactly why it was shipped that way originally and why the fix and its regressions live in the module's PostgreSQL integration tier (see the Testing section). The `RowsAffected == 0` answer to a redelivered event is thus a safe no-op on a transaction that stays healthy -- applying nothing to the real-time counter, the summary row, or the overage-crossing publish -- rather than a second application or an error. `AnalyticsRecorder` keeps calling the plain, non-deduped `Ingest`. The table's growth is bounded, not open-ended: `Dispatcher`'s retention sweep retires a receipt together with its delivered outbox row once the row has stayed delivered past the retention window (see "Retention" in the rescan-round section below), so a receipt lives exactly as long as the dedup answer it guards is still answerable.

## Reliability tiers

Both tiers are documented in full on their own types (`Recorder`, `AnalyticsRecorder`, `Enqueue`, `Dispatcher`); this section is the map between them and `docs/internal/06-billing-and-metering.md`'s "reliability tiers" split:

- **Analytics-grade** (`AnalyticsRecorder.Record`): fail-open. A full channel drops the event, increments a counter (`Dropped()`), and logs a warning -- and, since the rescan round (P2-metering-11), so does a buffered event whose delivery into the aggregator failed: `deliver` counts that loss into the same `Dropped()` counter, so the metric tells the whole truth about the tier. No idempotency dedup this round -- see Known limitations.
- **Billing-grade** (`Enqueue` + `Dispatcher`): must not silently drop, and must not silently double-count either. `Enqueue` writes a row in the caller's own transaction (never inside the caller's transaction does the row commit without the caller's own write, or vice versa -- proved by `TestEnqueue_SharesTheCallerTransaction_CommitLandsTheRow`/`_RollbackDiscardsTheRow`), deduped at the database level by a unique index on `(tenant_id, idempotency_key)`: a retried `Enqueue` -- even a retry inside a NEW caller transaction, the shape the PostgreSQL tier's `TestPostgres_Enqueue_IdempotentRetry_InsideOneCallerTransaction` proves -- returns the existing row with the transaction left healthy. `Dispatcher.RunOnce` claims pending rows and delivers each into `Aggregator.IngestBillingGrade`, leaving a failed row pending (with `Attempts`/`LastError` recorded) for the next cycle rather than dropping or dead-lettering it -- and escalating a row whose failed attempts reach the stated escalation horizon to an Error-level alert on every subsequent failure, the alert half of the tier's documented "retries indefinitely, plus an alert" contract (see `Dispatcher`'s "Escalation" doc section; `defaultDispatchEscalationAttempts`, host-tunable via `WithDispatchEscalationAttempts`) -- proved recoverable-after-crash by `TestDispatcher_CrashMidDelivery_RowIsRecoveredOnTheNextRun` -- and, when a row is instead redelivered AFTER its own aggregation already committed (the "Ingest succeeded, `markOutboxDelivered` did not" crash window -- see `metering_ingest_receipts` above), proved to apply the event exactly once by `TestDispatcher_RunOnce_RedeliveredRow_DoesNotDoubleCount` and `TestAggregator_IngestBillingGrade_RedeliveredEvent_DoesNotDoubleCount` on SQLite, and re-proved on real PostgreSQL -- where the redelivery must retire the row on its first cycle rather than fail on a poisoned transaction -- by the integration tier's `TestPostgres_Dispatcher_RedeliveredRow_RetiresInsteadOfErroring` and `TestPostgres_IngestBillingGrade_Redelivery_IsANoOpNotAnError`.

Both tiers converge on `Aggregator`'s in-process counters and `UsageSummary` rows -- the "same pipeline, swappable backend" property `doc.go` describes -- through two different entry points: the plain `Ingest` for analytics-grade, and the idempotency-checked `IngestBillingGrade` for billing-grade.

## Overage thresholds: declared config schema, Go-level values

`Module.Register` declares `ConfigPeriodBucketSize` and `ConfigDefaultOverageThreshold` on `reg.Config` -- schema only. Nothing in this round's code paths reads either through a live `config.Service` call: `Aggregator`'s actual period bucket and thresholds come from `Module`'s own `WithPeriodBucket`/`WithOverageThresholds` Go-level options, defaulted at construction.

This mirrors `go/pki`'s identical, already-accepted simplification for its own CA/certificate validity periods (`go/pki/AGENTS.md`: "Register only declares the schema ... wiring these declared config keys into that decision is left to the host, or to a later round"). The reason it is the right simplification here too, not a shortcut: reading a *live, per-tenant* config value would require metering to depend on `go/config` (a real module-to-module import this codebase's established convention avoids in favor of a structurally-typed, no-import seam -- see `org`'s `FeatureGate`/`Scope` for the pattern) purely to serve a round whose thresholds are themselves a stand-in for `go/billing`'s eventual real, per-plan entitlement values. Building that seam now, before `go/billing` exists to give it a real caller, would be exactly the kind of "prepare for later" this codebase's round-boundary discipline forbids.

## Known limitations

- **Summary writes are serialized by a single process-wide mutex** (`Aggregator.mu`), not a real atomic database upsert. `dbkit.Repository[T]`'s `Create`/`FindByID`/`Update` each open their own transaction, so a naive read-modify-write sequence is a lost-update race under concurrent `Ingest` calls for the same `(tenant, feature, period)` key without external coordination; the mutex closes that race for exactly one process, which is this round's whole story (the in-process aggregation backend). A distributed backend (Redis `INCRBYFLOAT`, or a PostgreSQL `INSERT ... ON CONFLICT`) would replace the mutex with a real cross-process atomic upsert; it does not need to reuse this one. Proved race-free within one process by `TestAggregator_Ingest_ConcurrentSameKey_NoLostUpdates` under `-race`.
- **`AnalyticsRecorder` does not deduplicate a retried `Record` call against `IdempotencyKey`.** Doing so would require persisting every seen key somewhere durable, which contradicts this tier's whole cheap, in-memory, best-effort positioning. The billing-grade `Enqueue` path does dedupe (database-level unique index), because that path already pays for durable storage on every call.
- **`Dispatcher` assumes exactly one process runs against a database at a time.** `claimPendingOutboxRecords` is a read, not an atomic claim-and-lock -- it never marks a row "in flight" before attempting delivery, so two concurrent `Dispatcher` processes could both claim and attempt to deliver the same pending row. `metering_ingest_receipts`'s unique `(id, tenant_id)` primary key (see "`metering_ingest_receipts`: the billing-grade idempotency ledger" above) already keeps this from double-counting the aggregation itself -- whichever process's `IngestBillingGrade` transaction commits first wins the receipt row, and the loser's own transaction applies nothing (its `ON CONFLICT DO NOTHING` receipt insert reports `RowsAffected == 0` and the transaction commits cleanly, a no-op that stays healthy on PostgreSQL rather than aborting), a real database-level guarantee independent of `Aggregator.mu`, which only serializes callers within one process. What concurrent `Dispatcher`s still are NOT safe against is wasted, duplicate work and log noise -- both processes race `markOutboxDelivered` for the same row, retry the same failure independently, and increment `Attempts` twice for one real attempt -- and, more subtly, a genuine race between the loser's skipped receipt insert and a legitimate SECOND, later delivery of the SAME `IdempotencyKey` is not this table's problem to solve (`IdempotencyKey` reuse across genuinely different events is a caller-discipline requirement `UsageEvent.IdempotencyKey`'s own doc comment already states). A `jobs`-queue-driven poller (explicitly allowed as later-round hardening) would still want a real claim step -- an atomic `status: pending -> processing` transition with a visibility timeout, the same shape `go/jobs`' own `claimOne` already implements for `jobRecord` -- to avoid that wasted work, before running more than one worker.
- **Fixed re-claim delay; no backoff curve.** A failing outbox row is retried at most once per `retryDelay` (default: one poll interval), measured from the failure itself: `markOutboxAttemptFailed` moves the row's `retry_after` to the failure time plus the dispatcher's delay (migration 0005's column), and `claimPendingOutboxRecords` refuses the row until that moment -- the `go/jobs` `scheduled_at` shape this module's own earlier docs cited as the model for honest retry spacing, now real with a fixed rather than curving delay. The curve itself (the delay growing per attempt) remains future hardening. This replaced the attempts-class ordering the round before shipped (`attempts ASC, created_at ASC`, migration 0004): ranking never-failed rows ahead of every already-failed row kept a failing pile from occupying batch after batch, but it also meant a row that failed ONCE was never claimed again while a sustained enqueue rate kept every batch full of never-failed rows -- permanent starvation of exactly the rows retry exists to reach (reviewer finding P1-metering-10). A row that failed is now out of the candidate set for the whole delay, which delivers both fairness directions at once: rows enqueued while a failing pile waits its window out go first (the pile cannot occupy batch after batch), and the failed row itself is reached the moment its window opens, whatever the arrival rate (no sustained flood can push its schedule slot later than the delay). `attempts` remains on the row as recorded history; it no longer orders claims.
- **PostgreSQL integration tier ships this round's `integration_test/` package**, after three real defects proved the SQLite-assumption class the tier exists to rule out: (1) `Enqueue`'s idempotent-retry recovery read the duplicate row back on the same transaction that the unique-violation error had just aborted on PostgreSQL (SQLSTATE 25P02), collapsing the retry contract and dragging the caller's own business transaction down; (2) `foldIntoSummaryOnce` swallowed the receipt-insert conflict and committed an aborted transaction, which the pgx driver surfaces as an error, so a redelivered outbox row failed forever instead of retiring; (3) `UsageEvent.validate` bounded only `Metadata`, so over-long `TenantID`/`Feature`/`IdempotencyKey` values wrote silently on SQLite (VARCHAR length is not enforced there) and failed with SQLSTATE 22001 inside the caller's transaction on PostgreSQL. Each is fixed by code that never lets a conflict or an over-long write reach a live transaction -- `ON CONFLICT DO NOTHING` inserts reporting `RowsAffected == 0` in `Enqueue` and `foldIntoSummaryOnce`, and byte bounds enforced by `validate` before any write -- and each fix ships a regression proven to fail on real PostgreSQL before the fix and pass after (see the Testing section). The raw-repository duplicate answer (`gorm.ErrDuplicatedKey`, dbkit's portable translation of each driver's own error) remains the documented behavior for callers that use `IngestReceiptRepository` directly and is re-proven on the real server by the tier. Honest residuals the tier does not cover: `AssertNotTenantScoped` is not re-run for the outbox table (the suite exercises the same GORM tenant plugin on both dialects, and its fixtures need package-internal helpers, so the SQLite proof stands); no two concurrent `Dispatcher` processes are simulated (the single-process limitation above is a deployment shape, not a dialect behavior); the analytics-grade fail-open path is exercised only indirectly, since `AnalyticsRecorder` itself performs no database writes; and the `LastError` truncation is pinned on SQLite at the stored-value level, not re-proven on the real server -- the rune-boundary tests and the short-invalid-UTF-8 sanitization tests added by the rescan round (P3-metering-15) both assert on the exact stored bytes, and the byte-level defect is dialect-independent: those are the exact bytes PostgreSQL would refuse with 22021 (invalid byte sequence) on the failure-record write itself.
- **No reference-app consumer.** Per this round's own stated scope: a real consumer (`go/billing` driving reference-app's AI-generation credit flow, or similar) is later-round work, since `go/billing` -- the module that would actually call this one for something reference-app does -- does not exist yet.
- **No `jobs` dependency.** `go.mod` requires `pkgcore`, `dbkit`, `observability` and `tenancy` (test-only, for `tenancytest`) and nothing above them. A `jobs`-queue-driven `Dispatcher` (the explicitly allowed later hardening) will need `go/jobs` as a new dependency then.

## Testing

- **Unit tests**: SQLite only, no Docker required. `go/metering/internal/testutil` provides `NewSQLite`/`NewPostgres`/`Migrate`, mirroring `go/pki/internal/testutil`'s exact shape, so every test in this module applies the real, versioned migration files from zero rather than an `AutoMigrate`.
- `repository_test.go` covers `SummaryRepository`'s CRUD paths and `tenancytest.AssertIsolated`, plus every outbox plain-function (`insertOutboxRecord`, `findOutboxByIdempotencyKey`, `claimPendingOutboxRecords`, `markOutboxDelivered`, `markOutboxAttemptFailed`, `retireDeliveredOutboxRecords`' own regression living in `dispatcher_test.go`) and `tenancytest.AssertNotTenantScoped`. Its `TestClaimPendingOutboxRecords_OrderedByRetrySchedule` pins the claim query's schedule semantics (only rows whose `retry_after` has arrived are claimable, oldest-scheduled first, a row inside its window never claimable), replacing the pre-rescan `TestClaimPendingOutboxRecords_LeastFailedFirst` pin of the attempts-class ordering; `TestMarkOutboxAttemptFailed` additionally pins the failed row's `retry_after` scheduling and the claim query's refusal of an in-window row. `TestTruncateError_DoesNotSplitAMultiByteRune` / `TestMarkOutboxAttemptFailed_LongMultiByteCause_StoredValueStaysValidUTF8` pin `truncateError`'s rune-boundary truncation, and `TestTruncateError_ShortInvalidUTF8_IsSanitized` / `TestMarkOutboxAttemptFailed_ShortInvalidUTF8Cause_StoredValueIsSanitized` pin the sanitize-at-any-length half -- both at the stored-value level, since the byte-level defect is dialect-independent: the stored-value assertion checks the exact bytes PostgreSQL would refuse with 22021.
- `outbox_test.go` covers `Enqueue`'s validation, its idempotent-retry guarantee, its transactional atomicity in both directions (commit lands the row, rollback discards it), and metadata encode/decode round-tripping.
- `repository_test.go` additionally pins the dialect-independent half of the duplicate-handling fix: `TestInsertOutboxRecord_DuplicateKey_IsANoOpNotAnError` proves a second insert for the same `(tenant_id, idempotency_key)` reports `inserted == false` with no error -- the `ON CONFLICT DO NOTHING` insert never aborts the transaction the way a caught unique-violation error would on PostgreSQL.
- `recorder_test.go`'s `TestUsageEvent_Validate` table gained exact-bound/over-long rows for all three fixed-width fields (`tenant_id` 64, `feature` 128, `idempotency_key` 200 bytes), each over-long row expecting the coded `metering.field_too_long` error -- the rows fail against a `validate` without the bounds, which is the SQLite-side half of the PostgreSQL 22001 defect.
- `ingest_receipt_test.go` covers `IngestReceiptRepository`'s `tenancytest.AssertIsolated` suite, that a duplicate `Create` for the same `(tenant, id)` surfaces as the portable `gorm.ErrDuplicatedKey` through dbkit's error translation (the raw-repository answer; the idempotent fold path itself avoids the error via `ON CONFLICT DO NOTHING`, per `foldIntoSummaryOnce`'s doc comment), and that two different tenants may reuse the same `IdempotencyKey` value without colliding.
- `aggregator_test.go` covers real-time counter increments, period isolation, summary-row upserts, the overage-threshold edge-triggered publish (exactly one event per crossing, never one per subsequent event), the best-effort publish-failure contract, a `-race` concurrency proof against the single-mutex serialization the Known limitations section documents, and `IngestBillingGrade`'s own happy path plus its idempotency guarantee: `TestAggregator_IngestBillingGrade_RedeliveredEvent_DoesNotDoubleCount` and `_DoesNotRepublishOverage` redeliver the identical event and prove the real-time counter, the summary row and the overage publish each apply exactly once, while `_DifferentEvents_BothApply` proves the check is keyed by `IdempotencyKey`, not merely tenant+feature. The rescan round's reconstruction and eviction regressions live here too: `TestAggregator_RealtimeCount_AfterRestart_ReflectsSummaryHistory`, `TestAggregator_IngestBillingGrade_AfterRestart_RedeliveryAndNewEvents`, `TestAggregator_Restart_ReconstructsOverageLatch_NoDoubleFire` and `TestAggregator_Ingest_ExpiredPeriodEntriesAreEvicted`.
- `dispatcher_test.go` covers the delivery happy path, batch-size limiting, a per-cycle delivery-failure proof (row stays pending with `Attempts` recorded, `RetryAfter` scheduled a retry delay out), the round's mandated crash-recovery proof (`TestDispatcher_CrashMidDelivery_RowIsRecoveredOnTheNextRun`): a "crashed" aggregator (a closed database connection standing in for a mid-`Ingest` process death) leaves the enqueued row recoverable and pending, never lost, and a fresh healthy `Dispatcher` completes delivery on its next run once the row's re-claim window has opened (the test moves `retry_after` into the past deterministically, in place of waiting out the delay) -- and the crash-recovery double-count regression, `TestDispatcher_RunOnce_RedeliveredRow_DoesNotDoubleCount`: it calls `IngestBillingGrade` directly to simulate a first delivery attempt whose aggregation already committed but whose `markOutboxDelivered` write never ran, leaving the row genuinely still `pending`, then drives `RunOnce` for real and proves the interrupted row completes delivery with the event applied exactly once, not twice. It also carries the rescan round's fairness regressions `TestDispatcher_RunOnce_FailedRowsAtTheHead_DoNotStarveNewerRows` (fifty permanently failing head rows must not keep a healthy row enqueued behind them from being claimed and delivered on the next cycle -- and must not be retried before their re-claim windows either) and `TestDispatcher_RunOnce_OnceFailedRow_IsStillRetriedUnderSteadyArrivals` (a row that failed once is retried and delivered even while every batch could fill with never-failed arrivals), the retention regression `TestDispatcher_RetentionSweep_RetiresDeliveredRowsOlderThanRetention` (delivered rows and their receipts are retired once past the window; the receipts are asserted present before and gone after), the cancel-restart regression `TestDispatcher_CancelThenStart_RestartsThePollLoop`, and the lifecycle regressions `TestDispatcher_Stop_BeforeStart_DoesNotPreventStoppingALaterLoop` and `TestDispatcher_ConcurrentStartAndStop_NoDataRace` (an early Stop must not consume the ability to stop a later Start's loop; Start and Stop must be race-free under any interleaving). The escalation round's two regressions live here too: `TestDispatcher_RunOnce_PermanentlyFailingRow_EscalatesToErrorPastTheStatedHorizon` (a permanently failing row stays pending and keeps being retried, is Warn-only below the stated horizon -- one `metering.outbox_delivery_failed` per attempt -- and produces an Error-level `metering.outbox_delivery_escalated` line naming the row on the horizon attempt and on every later failed attempt; pre-fix the horizon attempt logged only the Warn, so the escalation assertions failed) and `TestDispatcher_RunOnce_RowRecoveredBelowTheHorizon_NeverEscalates` (a row that fails once below the horizon and then delivers never escalates -- healthy rows and transient failures stay on the ordinary Warn cadence). Both drive the delivery loop against a genuinely closed aggregator database connection and capture real log output through `slog.SetDefault`.
- `analytics_test.go` covers the fail-open drop contract (a full buffer never blocks `Record`) and the background flush loop reaching `Aggregator.Ingest`, plus the shutdown and lifecycle regressions: `TestAnalyticsRecorder_Stop_DeliversEventsBufferedAtStopTime` and `TestAnalyticsRecorder_Record_AfterStop_DropsAndCounts` pin the drain-on-Stop contract (events buffered at Stop are delivered before it returns; events Recorded after it latches closed are counted drops, never silent buffer enqueues), `TestAnalyticsRecorder_IngestFailure_CountsIntoDropped` pins the rescan round's widened drop accounting (a delivery failure is a counted drop), `TestAnalyticsRecorder_CancelThenStart_RestartsTheLoopAndDeliversBuffered` pins the cancel-restart contract (a canceled ctx leaves `Start` restartable and events recorded during the dead gap buffered, delivered by the fresh loop), and `TestAnalyticsRecorder_Stop_BeforeStart_DoesNotPreventStoppingALaterLoop` / `TestAnalyticsRecorder_ConcurrentStartAndStop_NoDataRace` pin the same either-order, race-free lifecycle the Dispatcher tests above cover.
- `module_test.go` covers `pkgcore.Module` identity, the dual-dialect migration layout, locale-file parity, `Register`'s full declared surface (bootstrapped through a real `pkgcore.Kernel`, which also proves the locale bundle survives `i18n.Builder.AddModule`'s parity check), coexistence with another module, and the no-I/O contract of `Register`.
- **PostgreSQL integration tier** (`integration_test/`, run as `go test -tags=integration ./...` from the module directory, `-race` in CI): real testcontainers PostgreSQL 16, one disposable container per test via `internal/testutil.NewPostgres` (skipping when no Docker daemon is reachable), the module's `postgres/*.sql` migrations applied from zero on every test -- the same zero-to-head proof the unit tier's `NewSQLite` runs on the SQLite set, now on the second dialect. ## Rescan round: the seven reviewer findings

A review rescan of this module closed seven findings, each with a regression that fails before and passes after (real runs recorded in the round report). What a reader of this file needs to know beyond the per-file doc comments:

- **P1-metering-10 -- the claim query could starve a row that failed once.** See the "Fixed re-claim delay; no backoff curve" Known limitation above: the attempts-class ordering was replaced by a per-row retry schedule (`retry_after`, migration 0005, claim query + `markOutboxAttemptFailed` scheduling + `Dispatcher.retryDelay`, `Module.WithDispatchRetryDelay`). Regressions: `TestClaimPendingOutboxRecords_OrderedByRetrySchedule`, `TestDispatcher_RunOnce_OnceFailedRow_IsStillRetriedUnderSteadyArrivals` (a failed row raced against a steady flood is reached and delivered), plus the reworked `TestDispatcher_RunOnce_FailedRowsAtTheHead_DoNotStarveNewerRows` (the pile half still holds: a fresh row behind a failing pile is claimed next cycle while the pile waits out its window, pinned to Attempts = 1 through that cycle).
- **P2-metering-11 -- an Ingest failure in `deliver` was not counted.** `AnalyticsRecorder.deliver` now counts a failed delivery into `Dropped()`: a buffered event whose Ingest fails is a lost event exactly like a full-buffer drop, and the fail-open tier's accounting must say so. Regression: `TestAnalyticsRecorder_IngestFailure_CountsIntoDropped`.
- **P2-metering-12 -- real-time counters and the overage latch were not reconstructible across a restart.** `Aggregator` now reconstructs each counter entry from its bucket's `UsageSummary` row on the key's first touch in the process (`ensureSeeded`, run by `Ingest`, `IngestBillingGrade` and `RealtimeCount`): quantity starts at the summary's, and the overage latch is set when that quantity already meets the threshold, so a mid-period restart neither under-reports the period history nor fires `EventOverageThresholdCrossed` a second time for one period. The `alreadyIngested` redelivery path deliberately does NOT add its delta on top: the seed read happens after the earlier delivery's fold committed, so the entry already holds the event -- adding again would double-count, which is why the existing redelivery tests (`TestAggregator_IngestBillingGrade_RedeliveredEvent_DoesNotDoubleCount`) still pass. The per-key lazy reconstruction is the documented equivalent of a startup backfill, which tenant-scoped summary rows make impossible without the cross-tenant system-context path metering is not sanctioned to use. Regressions: `TestAggregator_RealtimeCount_AfterRestart_ReflectsSummaryHistory`, `TestAggregator_IngestBillingGrade_AfterRestart_RedeliveryAndNewEvents`, `TestAggregator_Restart_ReconstructsOverageLatch_NoDoubleFire`.
- **P2-metering-13 -- counters never evicted expired periods.** `Ingest`/`IngestBillingGrade` now sweep, under `mu` and at most once per period boundary crossed (`sweptThrough`), every resident entry whose period predates the event's own. Eviction loses nothing: an add for a swept key always follows its own committed summary upsert, and a later touch of the expired period re-seeds from that row. Regression: `TestAggregator_Ingest_ExpiredPeriodEntriesAreEvicted`. Residual, recorded on the code: entries are recreated by a later touch of their period (a query for an old period, a backdated event) and retired at the next crossed boundary -- residency is bounded by traffic, not by the calendar, and there is deliberately no wall-clock janitor this round.
- **P3-metering-14 -- a ctx-cancel stop left Start a permanent no-op and Record stuffing an unconsumed buffer.** The flush loop (and, symmetrically, the poll loop) now clears its own `started` flag on exit when the exit came from a canceled ctx rather than from `Stop`: a later `Start` runs a fresh loop, and the `stopped` latch is deliberately NOT set by the cancel, so events recorded during the dead gap are buffered honestly and delivered by the fresh loop (or drained by a later `Stop`). Regressions: `TestAnalyticsRecorder_CancelThenStart_RestartsTheLoopAndDeliversBuffered`, `TestDispatcher_CancelThenStart_RestartsThePollLoop`.
- **P3-metering-15 -- `truncateError` passed short invalid UTF-8 through raw.** The short-value fast path returned any in-bounds `cause` untouched, so a short error string carrying an invalid byte sequence was stored raw -- refused by PostgreSQL on the failure-record write itself (SQLSTATE 22021). `truncateError` now sanitizes at ANY length (invalid bytes rendered as the Unicode replacement character via `strings.ToValidUTF8`, then the byte bound enforced on a rune boundary) -- the third instance of the rune-safe helper shape `go/sharing`'s `truncateAccessLogValue` and `go/authn`'s `truncateClientField` establish. Regressions: `TestTruncateError_ShortInvalidUTF8_IsSanitized`, `TestMarkOutboxAttemptFailed_ShortInvalidUTF8Cause_StoredValueIsSanitized`. PG-shaped by origin (the 22021 refusal), pinned at the stored-value level on SQLite exactly as the existing long-cause tests are, per the integration-tier residual recorded below.
- **P3-metering-16 -- delivered outbox rows and ingest receipts had no retention.** `Dispatcher`'s poll loop now runs a bounded retention pass each cycle (`retireDeliveredOutboxRecords`): a delivered row that has stayed delivered past `Module.WithOutboxRetention`'s window (default: 7 days) and its receipt are deleted together in one transaction under the row's own tenant. What the sweep safely deletes, and only that: delivered rows (never pending ones -- a pending row is the retry queue, and its receipt is what makes its redelivery idempotent), one bounded batch per cycle, oldest first, an interruption convergent rather than duplicated. The window is the Enqueue-idempotency horizon: a caller retrying an `Enqueue` whose answer it never saw resolves against the existing row while it lives; a key re-enqueued after its row was retired is a genuinely new event -- the standard horizon every outbox retention policy assumes. Regression: `TestDispatcher_RetentionSweep_RetiresDeliveredRowsOlderThanRetention`.

## Escalation round: billing/metering P2-3

A review finding (P2-3, the observability twin of the P1-4 overage-latch round) closed the gap between the billing-grade contract's promise and its delivery: `docs/internal/06-billing-and-metering.md`'s reliability-tier table and `Dispatcher`'s own doc comment promised a delivery failure that "retries indefinitely, plus an alert", but the delivery loop retried a permanently failing row forever with only a per-attempt Warn -- no cap, no escalation, no alert -- so no operations person could discover the stuck row. The chosen shape is the promised alert, not a cap: retry remains indefinite and no row converges to a terminal state (billing-grade data is never dropped), and the alert is `Dispatcher`'s escalation horizon (`escalationAttempts`, default `defaultDispatchEscalationAttempts` = 60, host-tunable via the new `Module.WithDispatchEscalationAttempts`): once a row's failed attempts -- its durable, persisted `Attempts` -- reach the horizon, its failure cadence switches from the per-attempt Warn `metering.outbox_delivery_failed` to the Error-level `metering.outbox_delivery_escalated` naming the row (`outbox_id`, `tenant_id`, `feature`, `attempts`, `escalation_threshold`), repeated on every subsequent failed attempt until the row is fixed. Operations discovers a stuck row through log-based alerting on that Error key, within roughly the horizon times the retry delay of the row's first failure (about two minutes at the module's default pacing). Regressions (real fail-before/pass-after runs, `-count=1`, logged output captured through `slog.SetDefault`): the two tests the Testing section describes above; pre-fix, the permanently-failing-row test failed its three escalation assertions (no escalation line at the stated horizon, no Error level, no escalation after further attempts) while the row kept retrying exactly as the contract's retry half requires.

## Adjudications a reviewer should not "correct"

**`metering_outbox_records` is platform data, not tenant-scoped**, even though every row genuinely belongs to one tenant. See "Outbox table: platform data, not tenant-scoped" above -- this is a deliberate, precedented choice (matching `go/jobs`' `jobRecord`, `go/config`'s `row`, `go/dbkit`'s `AuditEvent`), not an isolation gap. A reviewer expecting `dbkit.Repository[OutboxRecord]` here should read that section before flagging it.

**`Enqueue` is not behind the `Recorder` interface.** `Recorder.Record(ctx, event)`'s signature has no room for the caller's transaction handle `Enqueue(ctx, tx, event)` requires, and forcing billing-grade delivery through a shape designed for fire-and-forget analytics would be the wrong abstraction, not a missing one. Billing-grade callers use the package-level `Enqueue` function directly.

**`ConfigDefaultOverageThreshold`'s `Type` is `"int"`, not a float type.** `pkgcore.ConfigItem.Type`'s vocabulary is closed to `"string"`, `"int"`, `"bool"` and `"duration"` -- there is no float type to declare. This is consistent with `UsageEvent.Quantity`/`OverageThresholds` staying `float64` at the Go level (a caller may well meter fractional units); the config item is a coarse, integer-only stand-in exactly because it is not live-read this round anyway (see "Overage thresholds" above).

**Serial numbers of outbox rows are UUIDs (`github.com/google/uuid`), and `metering.mod`'s one third-party dependency is deliberately this narrow.** `go.mod` requires only `google/uuid` beyond this codebase's own modules -- no float/decimal library, no cron/scheduling library for `Dispatcher`'s poll loop (`time.Ticker` is enough), no JSON library beyond the standard library's `encoding/json` for `OutboxRecord.Metadata`. Consumers of this module pay for exactly one small, dependency-free third-party package.
