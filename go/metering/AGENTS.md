# metering

go/metering is speed's usage-metering module: a single `Recorder` interface (plus a billing-grade `Enqueue` helper) business modules call to report usage, decoupled entirely from which backend stores and aggregates it. This file is the module-level discipline that ships with `go/metering` to consuming projects; the design rationale lives in `docs/internal/06-billing-and-metering.md`, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: a deliberately bounded foundation.** The module ships the `Recorder`/`Enqueue` pipeline end to end (both reliability tiers), the in-process aggregation backend only (real-time `sync.Map` counters plus SQLite/PostgreSQL usage-summary tables), and an overage-threshold-crossing event published on `pkgcore.EventBus`. It does NOT ship the Plan/Feature/Entitlement domain model, credits, actual quota enforcement, or a distributed aggregation backend; those live in `go/billing` or in the Known limitations list below. Judge what exists by the code, not by this sentence.

**Metrics instrumentation.** The 09-table "metering pipeline" row is instrumented at the sites this module genuinely has (`metrics.go`, unit-tested through a ManualReader in `metrics_test.go`): `metering.events.ingested` and `metering.events.dropped` on `AnalyticsRecorder`'s Record/drop paths (the analytics tier's ingest and counted-loss rates), `metering.outbox.delivery` outcome-labeled on `Dispatcher`'s delivery attempts, and `metering.aggregation.duration` channel-labeled analytics/outbox on the two `Aggregator` ingest entry points. The row's "outbox backlog depth" half is deliberately derived rather than gauged -- an honest depth gauge would need a COUNT over the whole outbox table every poll cycle, a scan the batch-bounded claim query never pays -- with the derivation recorded in `metrics.go`'s own doc comment, not silently substituted.

## Scope

**In scope.** `UsageEvent` and the `Recorder` interface (`recorder.go`). `AnalyticsRecorder`, the analytics-grade (fail-open) tier: an in-process bounded channel plus a background flush goroutine (`recorder_analytics.go`). `Enqueue` and `Dispatcher`, the billing-grade (must-not-silently-drop) tier's write and delivery halves: a caller-transaction outbox write plus a background poller retrying indefinitely and escalating a permanently failing row to an Error-level alert once its failed attempts pass the stated horizon (`outbox.go`, `dispatcher.go`, `repository.go`'s outbox functions; the escalation is documented on `Dispatcher`'s own doc comment). `Aggregator`, the in-process aggregation backend both tiers feed: real-time counters, database-backed summary rows, and overage-threshold detection (`aggregator.go`, `overage.go`); its billing-grade entry point, `IngestBillingGrade`, additionally records a durable idempotency receipt in the same database transaction as the summary write, so `Dispatcher` redelivering a row after an interrupted first attempt cannot double-count it (`ingest_receipt.go`). Three tables with dual-dialect versioned SQL migrations (`metering_usage_summaries`, `metering_outbox_records`, `metering_ingest_receipts`). `pkgcore.Module` wiring: configuration items for the period-bucket size and a default overage threshold, and the one published domain event.

**Deliberately not in scope:**

| Not here | Where it lives | Why |
|---|---|---|
| Plan/Feature/Entitlement domain model, `Entitlements.Check` | `go/billing` | metering measures and signals, go/billing decides: billing's `Feature`/`Plan`/`Grant`/`Entitlements` ship the domain model (see "billing is metering's first consumer" below) |
| Credits (reserve/confirm/refund ledger) | `go/billing` | Credits are a separate, synchronous path, not the metering pipeline; go/billing ships its own credits ledger |
| Actual blocking/allowance decisions for over-quota calls | `go/billing` | `OverageThresholdCrossedEvent` is a signal; the decision is `EntitlementsService.Check`'s, from `Grant.OverageMode` |
| Distributed aggregation backend (Redis Streams / PostgreSQL atomic increments / TimescaleDB raw-detail storage) | not implemented | The in-process backend is the shipped one; see the mutex Known limitation below |
| A `jobs`-queue-driven `Dispatcher` | not implemented | `Dispatcher` is an in-process goroutine poller; a jobs-driven poller would add `go/jobs` as a dependency and needs a real claim step (see Known limitations) |
| An HTTP surface / OpenAPI fragment | not implemented | metering is a Go-level API business modules call in-process, not a service reached over HTTP |
| `metering:*` permissions, an audit action | not implemented | No HTTP surface to gate, and no operation privileged enough to warrant an audit trail entry |
| Live reading of `ConfigDefaultOverageThreshold`/`ConfigPeriodBucketSize` through `config.Service` | not implemented | See "Overage thresholds" below |

## Data model

Three tables, deliberately spanning **two** data domains:

| Table | Domain | Repository shape | Isolation proof |
|---|---|---|---|
| `metering_usage_summaries` | Tenant | `SummaryRepository`, embeds `dbkit.Repository[UsageSummary]` | `tenancytest.AssertIsolated` |
| `metering_ingest_receipts` | Tenant | `IngestReceiptRepository`, embeds `dbkit.Repository[IngestReceipt]` | `tenancytest.AssertIsolated` |
| `metering_outbox_records` | Platform | plain `*gorm.DB` functions (`repository.go`) | `tenancytest.AssertNotTenantScoped` |

### Outbox table: platform data, not tenant-scoped

This is the module's one deliberate departure from a literal "every table written must be tenant-scoped" reading, and it is worth stating plainly since it looks, at first glance, like it should be tenant data (every row genuinely belongs to one tenant).

`OutboxRecord` does **not** implement `dbkit.TenantScoped`. The reason is `Dispatcher`: outbox delivery is a background process that must find every tenant's pending rows to retry them. `dbkit.Repository[T]` has no cross-tenant read path -- `tenancy.WithSystemContext` elevates *who may ask* for the escape hatch, not *what `dbkit.Repository[T]` itself can see* (see that function's own doc comment: "granting a system context does not widen what `dbkit.Repository[T]` ... can see or touch"). A genuinely tenant-scoped `OutboxRecord` would leave `Dispatcher` with no sanctioned way to scan pending rows across tenants at all.

This is not a novel problem or a novel answer: it is the exact shape `go/jobs`' own `jobRecord` already solves the identical way, and `go/dbkit`'s `AuditEvent` and `go/config`'s `row` are the same "platform data with a real, non-enforced `tenant_id` column ... never `dbkit.TenantScoped`" shape. `tenant_id` on `metering_outbox_records` is real and populated; it is simply not the database-enforced kind, and `tenancytest.AssertNotTenantScoped` (not `AssertIsolated`) is the correct suite for it, run in `repository_test.go`.

`UsageSummary`, by contrast, has no such cross-tenant reader: every caller who ever needs a summary row already knows which tenant it is asking about (an event's own `TenantID`, or a tenant's own dashboard request), so it stays genuinely tenant-scoped through `SummaryRepository`.

### `UsageSummary.ID` is deterministic

`ID` is `summaryID(Feature, PeriodStart)` -- not a random ULID/UUID -- so `Aggregator.upsertSummary` can reach the one row for a given `(tenant, feature, period)` through `dbkit.Repository[T].FindByID` rather than a hand-written query, which this codebase's raw-GORM-bypass discipline forbids outside `dbkit`'s own internals. Because `ID` is derived from `Feature` and `PeriodStart` alone, it is **not** globally unique across tenants -- two different tenants both measuring `"ai.generation"` in the same calendar month get the same `ID` string -- so `UsageSummary` declares `TenantID` as a second `primaryKey` column directly (a true composite key `(id, tenant_id)`), rather than embedding `dbkit.TenantModel` the way a globally-unique-ID model (`go/pki`'s `Certificate`, say) safely can.

### `metering_ingest_receipts`: the billing-grade idempotency ledger

`Dispatcher`'s billing-grade delivery is two separate database writes: `Aggregator.IngestBillingGrade` folding the event into the aggregation pipeline, and (a separate call, against Dispatcher's own connection) `markOutboxDelivered` flipping the outbox row's status. A process crash, or merely a transient failure of the second write, landing between the two leaves the outbox row `pending`, so the next `Dispatcher.RunOnce` cycle reclaims and redelivers it -- calling the ingest path a second time for an event that was already durably applied.

`IngestReceipt` closes that window: `IngestBillingGrade` inserts one receipt row keyed by `(TenantID, IdempotencyKey)` in the SAME database transaction as the `UsageSummary` upsert -- `Aggregator.foldIntoSummaryOnce`'s own one `dbkit.WithTenantSession` call, both writes composed as raw GORM calls against the tx it hands its callback (see `upsertSummaryTx`'s doc comment for why routing either write back through `dbkit.Repository[T]` would nest a second, refused transaction; both run against `SummaryRepository`'s own connection, never `Dispatcher`'s -- see `ingest_receipt.go`'s doc comment for why that connection independence rules out merging this with `markOutboxDelivered`'s own write). Either both commit, or neither does.

The receipt insert runs as `ON CONFLICT DO NOTHING`, not as a plain insert whose `gorm.ErrDuplicatedKey` violation would be caught: on PostgreSQL a statement error leaves the whole transaction aborted, so catching the violation and committing anyway would commit a poisoned transaction (the driver reports the server's COMMIT-became-ROLLBACK as an error) -- an SQLite-only suite, where a failed statement is harmless, cannot see that failure, which is why the PostgreSQL integration tier (see the Testing section) is where this behavior is proven. The `RowsAffected == 0` answer to a redelivered event is thus a safe no-op on a transaction that stays healthy -- applying nothing to the real-time counter, the summary row, or the overage-crossing publish -- rather than a second application or an error. `AnalyticsRecorder` keeps calling the plain, non-deduped `Ingest`. The table's growth is bounded, not open-ended: `Dispatcher`'s retention sweep retires a receipt together with its delivered outbox row once the row has stayed delivered past the retention window (see the retention Known limitation below), so a receipt lives exactly as long as the dedup answer it guards is still answerable.

## Reliability tiers

Both tiers are documented in full on their own types (`Recorder`, `AnalyticsRecorder`, `Enqueue`, `Dispatcher`); this section maps them onto the design's reliability-tiers split:

- **Analytics-grade** (`AnalyticsRecorder.Record`): fail-open. A full channel drops the event, increments a counter (`Dropped()`), and logs a warning -- and so does a buffered event whose delivery into the aggregator failed: `deliver` counts that loss into the same `Dropped()` counter, so the metric tells the whole truth about the tier. No idempotency dedup -- see Known limitations.
- **Billing-grade** (`Enqueue` + `Dispatcher`): must not silently drop, and must not silently double-count either. `Enqueue` writes a row in the caller's own transaction (never inside the caller's transaction does the row commit without the caller's own write, or vice versa -- proved by `TestEnqueue_SharesTheCallerTransaction_CommitLandsTheRow`/`_RollbackDiscardsTheRow`), deduped at the database level by a unique index on `(tenant_id, idempotency_key)`: a retried `Enqueue` -- even a retry inside a NEW caller transaction, the shape the PostgreSQL tier's `TestPostgres_Enqueue_IdempotentRetry_InsideOneCallerTransaction` proves -- returns the existing row with the transaction left healthy. `Dispatcher.RunOnce` claims pending rows and delivers each into `Aggregator.IngestBillingGrade`, leaving a failed row pending (with `Attempts`/`LastError` recorded) for the next cycle rather than dropping or dead-lettering it -- and escalating a row whose failed attempts reach the stated escalation horizon to an Error-level alert on every subsequent failure, the alert half of the tier's "retries indefinitely, plus an alert" contract (see `Dispatcher`'s "Escalation" doc section; `defaultDispatchEscalationAttempts`, host-tunable via `WithDispatchEscalationAttempts`; a permanently failing row never converges to a terminal state, and a row that recovers below the horizon never escalates) -- recoverable after a crash (a delivery interrupted between the ingest commit and the delivered-mark is redelivered idempotently: `TestDispatcher_CrashMidDelivery_RowIsRecoveredOnTheNextRun`, `TestDispatcher_RunOnce_RedeliveredRow_DoesNotDoubleCount`, `TestAggregator_IngestBillingGrade_RedeliveredEvent_DoesNotDoubleCount` on SQLite, and on real PostgreSQL -- where the redelivery must retire the row on its first cycle rather than fail on a poisoned transaction -- `TestPostgres_Dispatcher_RedeliveredRow_RetiresInsteadOfErroring` and `TestPostgres_IngestBillingGrade_Redelivery_IsANoOpNotAnError`).

Both tiers converge on `Aggregator`'s in-process counters and `UsageSummary` rows -- the "same pipeline, swappable backend" property `doc.go` describes -- through two different entry points: the plain `Ingest` for analytics-grade, and the idempotency-checked `IngestBillingGrade` for billing-grade.

**One feature belongs to exactly one reliability tier.** The convergence above is also a prohibition, not a style suggestion: a caller must never record the same `Feature` through both `AnalyticsRecorder.Record` and the billing-grade `Enqueue` path. Both tiers fold into the same per-tenant, per-feature, per-period `counterEntry` and `UsageSummary` row, and neither carries a tier marker, so a feature measured through both tiers is a blend no reader can attribute -- and the mixing cost is concrete: the row's quantity then mixes data that may be dropped by design (the fail-open analytics tier, whose retried `Record` is not deduplicated either -- see the "AnalyticsRecorder does not deduplicate" Known limitation -- so a retry can fold a second time into the same row) with data that must neither drop nor double-count (the billing-grade tier), and a billing figure read from that row silently contains quantities it was allowed to lose. Billing-grade delivery already feeds the same real-time counters and summary rows the analytics tier feeds, so a feature whose records must not be lost is recorded through `Enqueue` alone; the analytics tier is for features that carry no billing weight. The prohibition is caller discipline, carried by review -- nothing in `Aggregator` distinguishes the tiers structurally, and no tier marker is stored on the row. The same rule is stated at the two places a recorder-call author reads: `UsageEvent.Feature`'s doc comment and `doc.go`'s "One feature belongs to exactly one reliability tier" section.

## Overage thresholds: declared config schema, Go-level values

`Module.Register` declares `ConfigPeriodBucketSize` and `ConfigDefaultOverageThreshold` on `reg.ConfigSeat()` -- schema only. Nothing reads either through a live `config.Service` call: `Aggregator`'s actual period bucket and thresholds come from `Module`'s own `WithPeriodBucket`/`WithOverageThresholds` Go-level options, defaulted at construction.

Why the schema-only declaration is right, not a shortcut: reading a live, *per-tenant* config value would require metering to depend on `go/config` (a real module-to-module import this codebase's established convention avoids in favor of a structurally-typed, no-import seam -- see `org`'s `FeatureGate`/`Scope` for the pattern) purely to serve thresholds that are still a stand-in: billing's quota limits live in its own per-plan `Grant` values and nothing wires them into metering's Go-level thresholds (or into the `metering.default_overage_threshold` config item), so a live-read seam would still have no real consumer. The same schema-only simplification `go/pki` documents for its own validity periods.

## billing is metering's first consumer

`go/billing` is a real, landed consumer of this module. The actual use sites, all in go/billing:

- `billing/go.mod` requires (and, for local development, replaces) `go/metering` -- an import billing can make, since metering sits below it in the module dependency graph.
- `billing/module.go` carries the compile-time assertion `var _ UsageReader = (*metering.Aggregator)(nil)`: billing's `UsageReader` interface (declared in billing/entitlements.go as a small structural seam, so billing's unit tests need no real Aggregator wiring) is satisfied by metering's concrete type with no adapter to write.
- `billing/entitlements.go`'s `checkQuota` reads `s.usage.RealtimeCount(...)` for every Quota-feature decision, rounding the used count up against the grant's integer limit; a host wires the reader into `billing.NewModule(db, usage, ...)`/`NewEntitlementsService`, and a nil one answers the coded `ErrUsageReaderUnconfigured` rather than guessing an allowance ("zero usage would fail OPEN for an over-quota tenant").
- The overage EVENT's relationship is comment-only so far: `billing/model.go`'s `OverageModeNotify` and `billing/entitlements.go` name `EventOverageThresholdCrossed` as the signal those modes rely on, but no code in either module subscribes to it (see overage.go's own doc comment).

What still does not exist: a production host wiring a real `*metering.Aggregator` into billing, and any code anywhere driving a Quota-kind judgment through a wired reader. The one composed in-repo wiring is go/admin's own test host -- `go/admin/module_test.go`'s `buildTestAdminModule` constructs `billing.NewModule(db, meteringModule.Aggregator())` -- usage genuinely lands in that aggregator in the module's own surface suite (`usage_test.go` drives real `Ingest` calls into it and reads the summaries back) -- but no code calls `Entitlements().Check` on a Quota-kind feature through the wiring, so the seam's judgment path stays unexercised everywhere: billing's own compiled example uses a fixed-zero stub reader, the reference app passes billing a nil `UsageReader` with Boolean-only demo grants (see the Known limitation below), and any wiring of billing's per-plan grant limits into metering's Go-level thresholds also still does not exist (see "Overage thresholds" above).

## Known limitations

- **Summary writes are serialized by a single process-wide mutex** (`Aggregator.mu`), not a real atomic database upsert. `dbkit.Repository[T]`'s `Create`/`FindByID`/`Update` each open their own transaction, so a naive read-modify-write sequence is a lost-update race under concurrent `Ingest` calls for the same `(tenant, feature, period)` key without external coordination; the summary fold therefore runs as ONE database-arbitrated statement (`upsertSummaryTx`, an `INSERT ... ON CONFLICT DO UPDATE` doing the arithmetic server-side), which closes that race across processes too -- the mutex's remaining job is in-process ordering (each event's seed read before its own fold, and the expired-period sweep against in-flight folds). Real-time counters stay per-process state: a second replica's folds land in the shared summary through the same atomic statement, and its counters reconstruct from that summary on first touch. A distributed aggregation backend (Redis `INCRBYFLOAT`, a PostgreSQL atomic-increment backend, TimescaleDB raw-detail storage) that replaces the in-process counters too is not implemented. Proved race-free within one process by `TestAggregator_Ingest_ConcurrentSameKey_NoLostUpdates` under `-race`.
- **`AnalyticsRecorder` does not deduplicate a retried `Record` call against `IdempotencyKey`.** Doing so would require persisting every seen key somewhere durable, which contradicts this tier's whole cheap, in-memory, best-effort positioning. The billing-grade `Enqueue` path does dedupe (database-level unique index), because that path already pays for durable storage on every call.
- **`Dispatcher` assumes exactly one process runs against a database at a time.** `claimPendingOutboxRecords` is a read, not an atomic claim-and-lock -- it never marks a row "in flight" before attempting delivery, so two concurrent `Dispatcher` processes could both claim and attempt to deliver the same pending row. `metering_ingest_receipts`'s unique `(id, tenant_id)` primary key (see "`metering_ingest_receipts`: the billing-grade idempotency ledger" above) already keeps this from double-counting the aggregation itself -- whichever process's `IngestBillingGrade` transaction commits first wins the receipt row, and the loser's own transaction applies nothing (its `ON CONFLICT DO NOTHING` receipt insert reports `RowsAffected == 0` and the transaction commits cleanly, a no-op that stays healthy on PostgreSQL rather than aborting), a real database-level guarantee independent of `Aggregator.mu`, which only serializes callers within one process. What concurrent `Dispatcher`s still are NOT safe against is wasted, duplicate work and log noise -- both processes race `markOutboxDelivered` for the same row, retry the same failure independently, and increment `Attempts` twice for one real attempt -- and, more subtly, a genuine race between the loser's skipped receipt insert and a legitimate SECOND, later delivery of the SAME `IdempotencyKey` is not this table's problem to solve (`IdempotencyKey` reuse across genuinely different events is a caller-discipline requirement `UsageEvent.IdempotencyKey`'s own doc comment already states). A `jobs`-queue-driven poller would need a real claim step -- an atomic `status: pending -> processing` transition with a visibility timeout, the same shape `go/jobs`' own `claimOne` already implements for `jobRecord` -- to avoid that wasted work, before running more than one worker.
- **Retries are spaced by a fixed delay; there is no backoff curve.** A failing outbox row is retried at most once per `retryDelay` (default: one poll interval), measured from the failure itself: `markOutboxAttemptFailed` moves the row's `retry_after` to the failure time plus the dispatcher's delay (migration 0005's column), and `claimPendingOutboxRecords` refuses the row until that moment -- the `go/jobs` `scheduled_at` shape. The delay does not grow per attempt (the curve is not implemented). The claim order is the retry schedule alone, never an attempts class: ranking never-failed rows ahead of every already-failed row would let a sustained enqueue rate keep a once-failed row unclaimed forever -- permanent starvation of exactly the rows retry exists to reach. Ordering by the schedule delivers both fairness directions at once: rows enqueued while a failing pile waits its window out go first, and the failed row itself is reached the moment its window opens, whatever the arrival rate. The claim query orders by the bare column (`retry_after ASC, created_at ASC`) and the schema makes `retry_after` NOT NULL (migration 0007), so NULL is structurally impossible and can never sort differently on the two dialects (SQLite places NULLs first in ASC, PostgreSQL's ASC default is NULLS LAST); `attempts` stays on the row as recorded failure history and as the escalation count, and orders nothing.
- **Real-time counter entries are reconstructed, not restored.** Counters are in-process state and die with the process; on a key's first touch in a new process, `Aggregator` seeds the entry from its bucket's `UsageSummary` row (`ensureSeeded`, run by both ingest paths before the event's own write and by `RealtimeCount` on a map miss): quantity starts at the summary's, and the overage latch is set only when the row attests that the CURRENT threshold was in force at its last fold (`UsageSummary.OverageThreshold` == the current effective value, migration 0006) -- an unattested row (folded under a different threshold, under none at all, or before the column existed) leaves the latch open, so the first post-restart fold that reaches the threshold is the crossing event under the current configuration, and a pure read never latches or publishes anything. A duplicate redelivery (`alreadyIngested`) adds no delta on top: its seed read happened after the earlier fold committed, so the counter already holds the event. The per-key lazy reconstruction is the equivalent of a startup backfill, which tenant-scoped summary rows make impossible without the cross-tenant system-context path metering is not sanctioned to use. Resident entries whose period has passed are evicted on the next ingest, at most once per crossed period boundary (`sweptThrough`); an add for a swept key always follows its own committed summary upsert, and a later touch of the expired period re-seeds from that row, so eviction loses nothing -- residency is bounded by traffic, not by the calendar (there is no wall-clock janitor). See the 0006 migration's header comment for the bounded duplicate-fire residual the unattested state leaves on the one period straddling an upgrade.
- **Outbox error text is truncated and sanitized at the write site.** `markOutboxAttemptFailed` stores `truncateError(cause)`: never more bytes than the `LastError` column holds, always valid UTF-8 (short invalid sequences are rendered as the Unicode replacement character via `strings.ToValidUTF8` before the byte bound applies, enforced on a rune boundary) -- PostgreSQL refuses raw invalid bytes on the failure-record write itself (SQLSTATE 22021), so the stored value must be valid on both dialects.
- **Start/Stop lifecycle of the poll and flush loops.** A `Stop` ends the loop and drains what is buffered; a canceled context also ends the loop but leaves it restartable (`started` is cleared on exit unless a newer `Start` has replaced the channels), and events recorded during the dead gap are buffered honestly and delivered by the fresh loop or drained by a later `Stop` -- see `Start`/`run`/`Stop` doc comments on both `Dispatcher` and `AnalyticsRecorder`, pinned by the cancel-restart and either-order lifecycle tests in the Testing section.
- **PostgreSQL integration tier** ships in this module's `integration_test/` package, after three real defects proved the SQLite-assumption class the tier exists to rule out: (1) `Enqueue`'s idempotent-retry recovery read the duplicate row back on the same transaction that the unique-violation error had just aborted on PostgreSQL (SQLSTATE 25P02), collapsing the retry contract and dragging the caller's own business transaction down; (2) `foldIntoSummaryOnce` swallowed the receipt-insert conflict and committed an aborted transaction, which the pgx driver surfaces as an error, so a redelivered outbox row failed forever instead of retiring; (3) `UsageEvent.validate` bounded only `Metadata`, so over-long `TenantID`/`Feature`/`IdempotencyKey` values wrote silently on SQLite (VARCHAR length is not enforced there) and failed with SQLSTATE 22001 inside the caller's transaction on PostgreSQL. Each is closed by code that never lets a conflict or an over-long write reach a live transaction -- `ON CONFLICT DO NOTHING` inserts reporting `RowsAffected == 0` in `Enqueue` and `foldIntoSummaryOnce`, and byte bounds enforced by `validate` before any write -- and each fix ships a regression proven to fail on real PostgreSQL before the fix and pass after (see the Testing section). The raw-repository duplicate answer (`gorm.ErrDuplicatedKey`, dbkit's portable translation of each driver's own error) remains the documented behavior for callers that use `IngestReceiptRepository` directly and is re-proven on the real server by the tier. Honest residuals the tier does not cover: `AssertNotTenantScoped` is not re-run for the outbox table (the suite exercises the same GORM tenant plugin on both dialects, and its fixtures need package-internal helpers, so the SQLite proof stands); no two concurrent `Dispatcher` processes are simulated (the single-process limitation above is a deployment shape, not a dialect behavior); the analytics-grade fail-open path is exercised only indirectly, since `AnalyticsRecorder` itself performs no database writes; and the `LastError` truncation is pinned on SQLite at the stored-value level, not re-proven on the real server -- the rune-boundary tests and the short-invalid-UTF-8 sanitization tests both assert on the exact stored bytes, and the byte-level defect is dialect-independent: those are the exact bytes PostgreSQL would refuse with 22021 (invalid byte sequence) on the failure-record write itself.
- **No billing-grade `Enqueue` consumer anywhere, and billing's `UsageReader` seam is wired to a real `*metering.Aggregator` only inside go/admin's own test host -- never a production host, never exercised for a Quota-kind judgment** (see "What still does not exist" above for the admin wiring and the empty-judgment gap). The reference app wires metering itself: `internal/app/server.go` constructs `metering.NewModule(db)` (module in the `Bootstrap` set; `Start` after `Bootstrap` returns, `Stop` on the app's cleanup path), passes the module to `admin.WithMetering` so `GET /api/v1/admin/usage-summary` reads `Module.Summaries().List` per tenant, and wires `go/ai-gateway`'s `WithUsageRecorder` seam to the module's `Recorder()` -- the analytics-grade (fail-open) tier, the only one a recorder callback's `Record(ctx, event)` shape can carry -- so the gateway records usage automatically on every successful AI call: consult's Chat under `ai.chat_tokens`, a completed smilesim image job under `ai.image_count` and `ai.image_steps`. Each event folds through that tier alone into the `metering_usage_summaries` rows admin's usage-summary endpoint reads back -- never also through `Enqueue`, per the one-feature-one-tier rule -- and `flowtests/usage_summary_flow_test.go` drives the whole round trip for real over `ai.chat_tokens`. The billing-grade `Enqueue` path, which demands the caller's own transaction handle, still has no caller anywhere, and the reference app passes billing a nil `UsageReader`, so quota judging against live usage counts does not run end to end.
- **No `jobs` dependency.** `go.mod` requires `pkgcore`, `dbkit`, `observability` and `tenancy` (test-only, for `tenancytest`) and nothing above them; a `jobs`-queue-driven `Dispatcher` would add `go/jobs` as a new dependency.
## Testing

- **Unit tests**: SQLite only, no Docker required. `go/metering/internal/testutil` provides `NewSQLite`/`NewPostgres`/`Migrate`, mirroring `go/pki/internal/testutil`'s exact shape, so every test in this module applies the real, versioned migration files from zero rather than an `AutoMigrate`.
- `repository_test.go` covers `SummaryRepository`'s CRUD paths and `tenancytest.AssertIsolated`, plus every outbox plain-function (`insertOutboxRecord`, `findOutboxByIdempotencyKey`, `claimPendingOutboxRecords`, `markOutboxDelivered`, `markOutboxAttemptFailed`, `retireDeliveredOutboxRecords`' own regression living in `dispatcher_test.go`) and `tenancytest.AssertNotTenantScoped`. Its `TestClaimPendingOutboxRecords_OrderedByRetrySchedule` pins the claim query's schedule semantics (only rows whose `retry_after` has arrived are claimable, oldest-scheduled first, a row inside its window never claimable); `TestMarkOutboxAttemptFailed` additionally pins the failed row's `retry_after` scheduling and the claim query's refusal of an in-window row. `TestTruncateError_DoesNotSplitAMultiByteRune` / `TestMarkOutboxAttemptFailed_LongMultiByteCause_StoredValueStaysValidUTF8` pin `truncateError`'s rune-boundary truncation, and `TestTruncateError_ShortInvalidUTF8_IsSanitized` / `TestMarkOutboxAttemptFailed_ShortInvalidUTF8Cause_StoredValueIsSanitized` pin the sanitize-at-any-length half -- both at the stored-value level, since the byte-level defect is dialect-independent: the stored-value assertion checks the exact bytes PostgreSQL would refuse with 22021.
- `outbox_test.go` covers `Enqueue`'s validation, its idempotent-retry guarantee, its transactional atomicity in both directions (commit lands the row, rollback discards it), and metadata encode/decode round-tripping.

- `recorder_test.go`'s `TestUsageEvent_Validate` table carries exact-bound/over-long rows for all three fixed-width fields (`tenant_id` 64, `feature` 128, `idempotency_key` 200 bytes), each over-long row expecting the coded `metering.field_too_long` error.
- `ingest_receipt_test.go` covers `IngestReceiptRepository`'s `tenancytest.AssertIsolated` suite, that a duplicate `Create` for the same `(tenant, id)` surfaces as the portable `gorm.ErrDuplicatedKey` through dbkit's error translation (the raw-repository answer; the idempotent fold path itself avoids the error via `ON CONFLICT DO NOTHING`, per `foldIntoSummaryOnce`'s doc comment), and that two different tenants may reuse the same `IdempotencyKey` value without colliding.

- `dispatcher_test.go` covers the delivery happy path, batch-size limiting, a per-cycle delivery-failure proof (row stays pending with `Attempts` recorded, `RetryAfter` scheduled a retry delay out), the crash-recovery proof (`TestDispatcher_CrashMidDelivery_RowIsRecoveredOnTheNextRun`): a "crashed" aggregator (a closed database connection standing in for a mid-`Ingest` process death) leaves the enqueued row recoverable and pending, never lost, and a fresh healthy `Dispatcher` completes delivery on its next run once the row's re-claim window has opened (the test moves `retry_after` into the past deterministically, in place of waiting out the delay) -- and the crash-recovery double-count regression, `TestDispatcher_RunOnce_RedeliveredRow_DoesNotDoubleCount`: it calls `IngestBillingGrade` directly to simulate a first delivery attempt whose aggregation already committed but whose `markOutboxDelivered` write never ran, leaving the row genuinely still `pending`, then drives `RunOnce` for real and proves the interrupted row completes delivery with the event applied exactly once, not twice. The tier's `postgres_isolation_test.go` re-runs both tenant-scoped repositories' `AssertIsolated` suites against the real server (the re-run every tenant-scoped module's tier makes); `postgres_ingest_receipts_test.go` re-proves the raw duplicate-`Create` `gorm.ErrDuplicatedKey` classification on PostgreSQL and carries the two billing-grade redelivery regressions (`TestPostgres_IngestBillingGrade_Redelivery_IsANoOpNotAnError`, `TestPostgres_Dispatcher_RedeliveredRow_RetiresInsteadOfErroring`); `postgres_outbox_test.go` carries the idempotent-retry-inside-a-caller-transaction regression (`TestPostgres_Enqueue_IdempotentRetry_InsideOneCallerTransaction`); `postgres_validation_test.go` carries the over-long-field regression (`TestPostgres_Enqueue_OverlongField_RefusedBeforeAnyWrite`). The tier exists because the defects it regresses are visible only on real PostgreSQL: a raw 23505-then-25P02 collapse for the outbox retry, a COMMIT-became-ROLLBACK error leaving the outbox row `pending` forever for the redelivery, and raw 22001 errors poisoning the caller's transaction for over-long fields. Wired into CI as a `go/metering` row of `full-check.yml`'s integration-tiers matrix.

## Deliberate shapes worth stating

**`metering_outbox_records` is platform data, not tenant-scoped**, even though every row genuinely belongs to one tenant. See "Outbox table: platform data, not tenant-scoped" above -- this is a deliberate, precedented choice (matching `go/jobs`' `jobRecord`, `go/config`'s `row`, `go/dbkit`'s `AuditEvent`), not an isolation gap.

**`Enqueue` is not behind the `Recorder` interface.** `Recorder.Record(ctx, event)`'s signature has no room for the caller's transaction handle `Enqueue(ctx, tx, event)` requires, and forcing billing-grade delivery through a shape designed for fire-and-forget analytics would be the wrong abstraction, not a missing one. Billing-grade callers use the package-level `Enqueue` function directly.

**`ConfigDefaultOverageThreshold`'s `Type` is `"int"`, not a float type.** `pkgcore.ConfigItem.Type`'s vocabulary is closed to `"string"`, `"int"`, `"bool"` and `"duration"` -- there is no float type to declare. This is consistent with `UsageEvent.Quantity`/`OverageThresholds` staying `float64` at the Go level (a caller may well meter fractional units); the config item is a coarse, integer-only stand-in exactly because it is not live-read anyway (see "Overage thresholds" above).

**Serial numbers of outbox rows are UUIDs (`github.com/google/uuid`), and the module's third-party footprint is deliberately this narrow.** `go.mod` requires only `google/uuid` beyond this codebase's own modules -- no float/decimal library, no cron/scheduling library for `Dispatcher`'s poll loop (`time.Ticker` is enough), no JSON library beyond the standard library's `encoding/json` for `OutboxRecord.Metadata`. Consumers of this module pay for a single small, dependency-free third-party package.
