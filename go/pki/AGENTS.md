# pki

go/pki owns key material that needs a lifecycle: signing keys and X.509 certificates, from generation through rotation to revocation. This file is the module-level discipline that ships with `go/pki` to consuming projects; the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: implemented and tested.** The key-lifecycle layer (`Service`, the `Signer` seam, `LocalSigner`, the `pki_signing_keys` and `pki_local_keys` tables) is what `authn` consumes through its own `KeySource` interface; the X.509 layer (`CAService`, `pki_authorities`, `pki_certificates`) issues an internal CA chain; revocation exists on both layers; CRL generation, two JWKS exports and an HTTP surface under `/api/v1/pki` complete the module; `SignerRegistry` (a `pkgcore.SeamRegistry[Signer]`) carries `LocalSigner` plus the `go/pki/signer/vault` and `go/pki/signer/kmsaws` provider implementations. Judge what exists by the code, not by this sentence.

## Scope

**In scope.** Five tables (`pki_signing_keys`, `pki_authorities`, `pki_certificates`, `pki_local_keys`, `pki_certificate_revocations`) with dual-dialect versioned SQL migrations, registered through `dbkit.MigrationRegistry` the same way every other module does. The `Signer` interface and `LocalSigner`, the local, zero-external-dependency implementation `task dev` runs and every unit test in this module (and its consumers) can use as a test double. Internal CA issuance: `CAService.CreateRootCA`, `CreateIntermediateCA` and `IssueCertificate`, all through `crypto/x509`, with 16-byte `crypto/rand` serial numbers -- never a timestamp. `Service`, the key-lifecycle layer's public entry point, whose method signatures match the shape `authn`'s `KeySource` interface requires, structurally, with no import edge in either direction. `pkgcore.Module` wiring: permissions (`pki:read`, `pki:issue`, `pki:revoke_signing_key`, `pki:revoke_certificate`, `pki:rotate`), audit actions (`pki.authority.create`, `pki.certificate.issue`, `pki.key.revoke`, `pki.certificate.revoke`), configuration items for CA/certificate/CRL validity periods and the CRL distribution point default, the signing-key/certificate lifecycle events, and the bilingual locale bundle for every declared error code.

`SignerRegistry` (`signer_registry.go`) is a package-level `pkgcore.SeamRegistry[Signer]` carrying `LocalSigner` under the name `"signer.local"`; `go/pki/signer/vault` (HashiCorp Vault Transit, registering `"signer.vault"`/`"signer.vault-direct"`) and `go/pki/signer/kmsaws` (AWS KMS, registering `"signer.aws-kms"`/`"signer.aws-kms-direct"`) each register both an envelope-mode and a direct-sign-mode name -- see "Signer providers: `vault` and `kmsaws`" below for why two names per provider.

**Still not in scope, by design**: TLS certificates for transport, ACME, an OCSP responder (CRL only), Certificate Transparency logs, cross-deployment CA federation, a generic "private-key export" API, SM2. `pki.authority.expiring`/`pki.certificate.expiring`/`.issued`/`.renewed` events and `pki.key.rotate`/`pki.private_key.deliver` audit actions are not declared -- see events.go's and module.go's own doc comments for exactly why each one has no genuine emitter.

## Signer providers: `vault` and `kmsaws`

`go/pki/signer/vault` and `go/pki/signer/kmsaws` are the two provider subpackages. Both follow the identical shape `go/pkgcore/eventbus/redis`, `go/pkgcore/kv/redis` and `go/pkgcore/objectstore/s3` establish: importing either package for side effect (`import _ ".../pki/signer/vault"`) registers its implementations onto the package-level `SignerRegistry` (`signer_registry.go`); a host that never imports a provider subpackage never resolves its names.

**Two names per provider, not one.** Each package supports both `Config.Mode` values -- `ModeEnvelope` (the real private key, encrypted externally, decrypted locally to sign) and `ModeDirectSign` (the key generated inside, and never exported by, the external service). `pkgcore.SeamRegistry[T]`'s own contract pairs one *fixed* `Capability` value with one registered name -- `Build` returns whatever `Capability` was recorded on the `Registration` at `init()` time, never something read back off the constructed value -- so a capability that depends on a runtime `Mode` cannot correctly live on a single name. Each package therefore registers two names: `"signer.vault"` / `"signer.aws-kms"` (envelope, `Capabilities: 0`) and `"signer.vault-direct"` / `"signer.aws-kms-direct"` (direct-sign, `Capabilities: pkgcore.KeyNeverLeavesBoundary`) -- mirroring how `pkgcore`'s own `MailerRegistry` carries `"mailer.console"` (`Stateless`) and `"mailer.smtp"` (`MultiReplicaSafe|SurvivesRestart`) as two names rather than one whose capability depends on configuration.

**Both packages hide their private key material behind a self-describing `keyRef` in envelope mode.** Neither package has its own persistent storage: `GenerateKey` under `ModeEnvelope` generates a real `ed25519` key pair in-process, PKCS8-marshals the private half, and immediately wraps it with the external service's own encrypt operation (Vault Transit's `encrypt`, KMS's `Encrypt` against a caller-provisioned symmetric wrapping key); the resulting ciphertext itself -- not a name pointing at storage this package keeps -- IS the `keyRef` `pki.Signer.GenerateKey` returns. `Sign`/`Public` decrypt it back into memory for the call's duration only, the same cost `LocalSigner.Sign` pays for its own `dbkit`-encrypted column. `Destroy` under `ModeEnvelope` validates the `keyRef` still decrypts (reporting `pki.ErrKeyNotFound` if not) and otherwise no-ops -- there is nothing named by `keyRef` for the external service to delete; the caller dropping its own row (e.g. `pki_signing_keys.key_ref`) is what actually destroys the key. Under `ModeDirectSign`, `keyRef` is the provider's own key name/ID (a Vault Transit key name; an AWS KMS `KeyId`), and `Destroy` really does ask the provider to remove it -- immediately for Vault (`DELETE transit/keys/<name>`, after `GenerateKey` flips `deletion_allowed` so the delete can succeed at all), only *scheduled* for AWS KMS (`ScheduleKeyDeletion` with the minimum 7-day `PendingWindowInDays` -- KMS has no "delete now" for a protected key, an honest limitation `kmsaws/signer.go`'s `Destroy` doc comment records, not a bug).

**The two implementations agree on FAILURE semantics, not just success ones, and both fail closed on an empty signing answer.** A host that swaps one registered implementation for the other (a registration-name change, zero code change) observes the same failure vocabulary: an unrecognized `keyRef` is `pki.ErrKeyNotFound` from both `signDirect` paths -- `vault` answers it for a nil secret, `kmsaws` for a nil `SignOutput` -- and a signing backend that answers with no signature bytes at all is a coded failure, never a `(nil, nil)` empty-signature success: `kmsaws` answers `pki.ErrSignerUnavailable` for a `Signature`-less `SignOutput`, `vault`'s `decodeVaultSignature` refuses an empty decoded signature, and `vault` also parses and validates the `v<N>` version its envelope carries (refusing a malformed one) rather than dropping it unread. The contract sentence lives in `go/pki/signer.go`'s `Sign` doc comment; `TestSigner_DirectMode_Sign_NilResponse_FailsClosed`/`TestSigner_DirectMode_Sign_EmptySignature_FailsClosed` (`kmsaws/signer_test.go`) and `TestDecodeVaultSignature_RejectsMalformedVersion`/`TestDecodeVaultSignature_RejectsEmptySignature` (`vault/signer_test.go`) pin it.

**Standing warning on `signer.vault-direct`: Vault-side rotation of a Transit key is NOT governed by this module's lifecycle state machine.** The module rotates by creating NEW Transit key names (`pending` -> `active` -> `retiring` -> `retired` across fresh `pki-<uuid>` keys); it never rotates a Transit key in place. If an operator rotates one in place through Vault's own `rotate` endpoint instead, nothing in this module notices: `signDirect` pins no `key_version`, Vault signs with the new latest version, and the public-key read / JWKS export serve the latest too -- signatures and the advertised key diverge across time with no pending/retiring overlap window and no error. The gap is recorded, not silently accepted: the warning is carried on the registration in `vault/register.go`, spelled out in `vault/doc.go`'s "in-place Transit key rotation" section, and accounted for on `decodeVaultSignature` (`vault/signer.go`), which validates the version even though nothing can act on it yet, so the field never reads like a decided irrelevance. What does not ship is the fix that would close the gap: pinning `key_version` on the sign request to the version the module issued and exported with, and reconciling it with the lifecycle state.

**`kmsaws`'s direct-sign mode uses `ED25519_SHA_512` with `MessageType: RAW`, never `ED25519_PH_SHA_512`/`DIGEST`.** The two combinations are NOT interchangeable, and a signature made under the wrong one signs successfully but fails only at verification time, against a signature already delivered. `TestSignDirect_ProducesAPureEdDSASignature` (`kmsaws/signer_test.go`) pins a real `crypto/ed25519.Verify` call against a signature produced through this package's own request-building and response-decoding path, so an edit that swaps either constant fails a test rather than silently shipping an unverifiable signature.

**No offline-runnable Example against a live backend, for either package, and no integration tier.** Both packages' `example_test.go` demonstrate construction and `pki.SignerRegistry` self-registration only, never an actual network round trip: neither Vault dev-mode (Docker-backed, via testcontainers) nor a real AWS account is reachable from the plain unit-test tier godoc `Example`s run under. `signer_test.go` in each package instead stubs the third-party client's own interface (`transitClient` for Vault's `*vaultapi.Logical`; `kmsClient` for AWS's `*kms.Client`) and exercises every request/response shape this package builds and parses against those stubs. **AWS KMS gets no integration leg at all, by design, not by gap**: LocalStack's KMS implementation is known to diverge from the real service, so a testcontainers-backed proof there would prove conformance against LocalStack, not against AWS KMS, which is worse than no such proof since it would look like coverage without being coverage. Real verification against a live AWS account is manual, and has not been performed. Vault's eventual target design includes a Docker-backed `integration_test/` starting a real Vault dev-mode server; no such package exists yet, so `go/pki/signer/vault` carries the identical "stubbed unit tests only" status as `kmsaws`, without sharing `kmsaws`'s "never gets one, by design" reasoning.

## Data model

Five tables spanning three of the four data domains. **One table never mixes two data domains**:

| Table | Domain | Repository shape | Isolation proof |
|---|---|---|---|
| `pki_signing_keys` | Platform | `SigningKeyRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |
| `pki_authorities` | Platform | `AuthorityRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |
| `pki_certificates` | **Tenant** | `CertificateRepository`, embeds `dbkit.Repository[Certificate]` | `tenancytest.AssertIsolated` |
| `pki_local_keys` | Platform | `LocalKeyRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |
| `pki_certificate_revocations` | Platform | `CertificateRevocationRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |

**`pki_certificate_revocations` is a denormalized, append-only revocation ledger**, and the reason it exists at all is a cross-domain problem: `pki_certificates` is tenant data, so a tenant-scoped `dbkit.Repository[Certificate]` read can never enumerate every certificate one authority (platform data) has ever revoked across every tenant. This table carries a real, deliberately UNENFORCED `tenant_id` column -- the same accommodation `go/notification`'s `send_records`/`platform_blacklist` and `go/dbkit/audit`'s `AuditEvent` make for the identical shape of problem -- and is written as a SECOND statement after `CAService.RevokeCertificate`'s `pki_certificates` update; see `model.go`'s `CertificateRevocation` doc comment for the full "why this is safe" argument (bounded staleness on a crash between the two writes, never an incorrect "not revoked" answer).

**No business table ever holds a private key, and this is a schema fact, not a documentation promise.** `pki_signing_keys`, `pki_authorities` and `pki_certificates` carry only `signer_name` + `key_ref` -- an opaque pointer to whichever `Signer` implementation actually owns the key. `pki_local_keys` is `LocalSigner`'s own, separate store, read and written by no other code in this module.

**`pki_signing_keys.status` carries the full five-value lifecycle vocabulary** (`pending`/`active`/`retiring`/`retired`/`revoked`), driven by lifecycle.go's transitions (`StageDueRotations`/`PromoteDuePending`/`RetireDueRetiring`), the `jobs`-driven expiry scan (job.go) and the revocation paths (revocation.go).

**`pki_signing_keys` enforces "at most one active key per purpose" at the database, not just in application code**: `uq_pki_signing_keys_active_purpose` is a partial unique index (`WHERE status = 'active'`). `TestSigningKeyRepository_ActivePurposeUniqueness_IsEnforcedByTheDatabase` proves a second `Create` for an already-active purpose is refused by SQLite; this is standard SQL (no PostgreSQL-only feature), so the same index works unmodified on both dialects.

**`pki_local_keys.not_after` is nullable and unpopulated.** `LocalSigner.GenerateKey` takes no expiry parameter -- the `Signer` interface's frozen shape has no room for one, and the key-lifecycle layer that knows a key's intended lifetime records it on the *owning* row (`pki_signing_keys`), never on `pki_local_keys`. Populating the column would make `Service` acquire signer-implementation-specific knowledge of which implementation "local" is; see `model.go`'s `LocalKey.NotAfter` doc comment.

**`pki_authorities.parent_id` is a genuine nullable column, not an empty-string sentinel.** No unique index is keyed on it (an authority may issue any number of intermediates), so there is no NULL-vs-empty-string collision to design around, and a real `NULL` for a root authority is the honest representation.

**`pki_authorities` carries CRL state**: `crl_distribution_point` (the URL this authority's own CRL is served at -- empty omits the extension from every certificate this authority signs, never a broken placeholder, matching every other unset-value field in this module), `crl_number` (RFC 5280 §5.2.3, monotonically increasing on every `GenerateCRL` call, `0` meaning no CRL has ever been generated), and `crl_pem`/`crl_issued_at`/`crl_next_update` (the most recently generated document itself, stored rather than recomputed on every fetch -- see `crl.go`'s `GenerateCRL`).

## Signer seam

The single most important interface-shape decision in this module: `Signer` exposes signing *operations* (`GenerateKey`/`Sign`/`Public`/`Destroy`), never a way to read a private key back out. A `Protect(key)`/`Unprotect(ref)` shape was considered and rejected -- its semantics require the private key to exist in plaintext inside this process's memory at some point, which defeats the entire point of a KMS-backed implementation. See `signer.go`'s doc comment for the full argument, including why `Sign` does not reuse the standard library's `crypto.Signer` (no `context.Context` parameter, which a KMS-backed direct-sign implementation genuinely needs for timeout/cancellation/trace propagation on a path a login walks through).

`input`'s meaning in `Sign` is algorithm-dependent and is never normalized to "always a digest": for `AlgorithmEd25519` (the only algorithm shipped), `input` is the *complete message* -- PureEdDSA hashes internally, and this is also exactly RFC 8037's JWT `EdDSA`. Getting this wrong for a KMS-backed implementation is not cosmetic (AWS KMS's `MessageType: RAW` vs. `DIGEST` select genuinely different signature algorithms), which is why the doc comment spells this out.

`LocalSigner` does **not** have the `KeyNeverLeavesBoundary` capability: a `Sign` call decrypts the private key into this process's memory for the duration of the `crypto/ed25519` call. That is the deliberate, documented cost of a zero-dependency signer.

## `Service`: the key-lifecycle layer's public shape

`Service.EnsurePurpose`/`ActiveSigner`/`VerificationKeys` are declared using **only standard-library types** in every signature, including an anonymous struct as `VerificationKeys`'s return-slice element type. This is not a style choice: structural interface satisfaction across two packages' own named types requires exact, literal signature equality, since two packages' named structs are never the same type. `authn`'s `KeySource` interface is declared independently, in `go/authn`, with **zero import of `go/pki`** -- and `*Service` satisfies it structurally. `service.go`'s `keySourceShape` is the compile-time proof of that conformance, kept in this module (not in a test file) specifically so it fails to compile the moment an edit accidentally breaks the shape.

`Service.EnsurePurpose` is the **bootstrap path, not rotation**: it creates a key and marks it `active` in the same call, synchronously, with no propagation window -- safe because a purpose with no active key has never signed anything, so no multi-replica cache-propagation race exists to protect against. When the purpose's active key has fallen out of its validity window and no usable pending successor is in flight, `EnsurePurpose` heals the purpose itself -- revoking the expired key (and any out-of-validity staged pending) through the ordinary guarded revoke transition and creating an in-validity replacement in the same call. Rotating an EXISTING in-validity active key goes through the pending/propagation-window path instead (lifecycle.go), driven by the expiry scan a host schedules through `Service.EnqueueExpiryScan`. `EnsurePurpose` does not verify that an already-active key's `Algorithm` matches the requested one on a repeated call -- a second call with a different algorithm for the same purpose silently keeps the first key; that is a known limitation of the call, not an error or a rotation trigger.

`Service.PromoteNow` is a manual, propagation-window-honoring promotion trigger, a companion to `RevokeSigningKey`: revoking a purpose's active key in an emergency leaves that purpose with no active signer until a replacement is promoted, and getting a working signer back online is a host's explicit decision. It is not itself revocation, and nothing in the module calls it automatically. `Service.ReclaimRetired` is the host-invoked retirement-and-reclaim point -- see "Known limitations" below.

**Validity is enforced at key-take time, never expressed through status.** A signing key's `NotBefore`/`NotAfter` are enforced on EVERY read path at the moment the key is taken -- `ActiveSigner` refuses an out-of-validity active key with `ErrNoActiveKey`, `VerificationKeys` offers only in-validity keys, `ExportJWKS` publishes only in-validity keys, and `EnsurePurpose` treats an out-of-validity active key as no key at all. Status and validity are two independent axes: the state machine's statuses say how far rotation has progressed, while the validity window says whether the key may be USED at this instant, and the two can disagree (an "active" key whose NotAfter passed because the expiry scan has not run yet). The boundary direction: both ends of the window are INCLUSIVE (a key is valid at its NotAfter and refused a moment later), the identical boundary crypto/x509 applies to a certificate's validity window. For the verify path the choice is strict now-filtering, NOT judgment by a token's issue time -- pki never parses the credentials it enables (VerificationKeys returns public keys and metadata only, per the KeySource shape), so the token issue time is not available where the key is chosen. The availability cost of strict now-filtering is bounded by the rotation design itself: the expiry scan demotes an active key to retiring when its replacement activates, which the rotation lead time schedules a default of thirty days before NotAfter -- so tokens signed by an in-validity key normally outlive their key's NotAfter only when a host declares a maxCredentialLifetime close to or beyond its renewal lead time, which such a host must size itself (`WithRenewalLeadTime`).

## X.509 layer: real consumer, precise residuals

The reference app's AI-output attestation layer -- `examples/reference-app/internal/attestation`, its package doc carries the product narrative -- is the X.509 layer's real consumer, the discharge of the repository's mandatory-first-consumer rule (docs/internal/22-pki.md's "the X.509 layer has a real consumer" section records the closure). It drives every main path this layer exists for: boot-time CA creation (`CreateRootCA` + `CreateIntermediateCA`, once per database, re-found idempotently by fixed subject names), per-tenant certificate issuance (`IssueCertificate`, purpose `simulation.attestation`, 365-day validity), signing with an issued certificate's key (`SignCertificate`, the one capability the integration found the layer lacked, added to `CAService` as a purely additive method), and chain-verified gating of public shares of AI outputs (`VerifyCertificate`). `examples/reference-app/cmd/server/attestation_flow_test.go` drives the full journey over the composed HTTP stack -- issuance, signing, verification, revocation and CRL publication -- including pki's certificate-revoke and CRL-fetch HTTP operations over the wire.

The no-consumer exception's three compensating obligations resolve as follows:

1. **The godoc `Example` obligation is retained with a narrowed narrative** -- a compiled-and-run example set remains the module's cheapest always-true consumer proof; `example_test.go` carries `ExampleCAService_SignCertificate` (issue -> sign -> verify against the leaf's own public key -> signing refused with `ErrCertificateRevoked` after revocation) alongside the rest of the set.
2. **The "unverified by any real consumer" obligation is closed.** The app issues, signs with, verifies, revokes and CRL-publishes real certificates over the composed HTTP stack.
3. **The "API may be broken by the first consumer" exemption is narrowed to the residual unconsumed surface below.** The integration changed this layer by exactly one additive method; the API-stability sentence covers only what remains unconsumed.

**The precisely residual unconsumed surface** (each item is what may still change freely, and the reason it stays out):

- **The two JWKS exports** (`CAService.ExportAuthorityChainJWKS` and the HTTP `pki_getAuthorityJwks`/`pki_getKeyJwks` reads) have no caller: the app's external verifier needs no JWKS because the AI-output gate and the CRL verifier both use the raw certificates and documents directly.
- **The CRLDP extension path**: the app's authorities carry no `CRLDistributionPoint` (the app has no stable public origin URL to declare), so `RootCAParams`/`IntermediateCAParams.CRLDistributionPoint`'s embedding machinery stays unexercised by a real certificate.
- **`EnqueueCRLRegenerate`/periodic CRL regeneration stays unscheduled**: the app's verifier path is row-state + chain verification and the attestation flow generates CRLs on demand through the Go API, so a periodic refresh has no reader waiting on it.
- **Expiry-driven lifecycle for `pki_authorities`/`pki_certificates` stays unbuilt**: the attestation certificates carry a real 365-day validity and an expired certificate stops its outputs from being shareable, so an expiry-warning/renewal mechanism has a concrete waiting object; it does not exist.
- **Authority revocation** (`AuthorityStatusRevoked`) has no writing method; the app's chain-verification refusals around it are exercised through the module's own directly-seeded tests.


**The key-lifecycle layer (`Service`, `Signer`, `LocalSigner`) does NOT get this exception.** It has a real, if indirect, consumer: `authn` consumes it through `KeySource`, and reference-app assembles `authn`. Its public API is held to the ordinary frozen-API standard -- including `Service.RevokeSigningKey`, `PromoteNow`, `ReclaimRetired` and `ExportJWKS`, even though none of them has a real caller yet either: they extend an already-frozen type (`Service`), not a still-exempt one (`CAService`), so the same discipline that governs `EnsurePurpose`/`ActiveSigner`/`VerificationKeys` governs these too.

## HTTP surface

`go/pki/api/openapi.yaml` is this module's OpenAPI fragment, covering five operations under `/api/v1/pki`: `pki_revokeSigningKey`, `pki_revokeCertificate`, `pki_getKeyJwks`, `pki_getAuthorityJwks`, `pki_getAuthorityCrl`. The CA/certificate issuance surface and the key-lifecycle's synchronous surface (`EnsurePurpose`/`ActiveSigner`/`VerificationKeys`) stay Go-only; nothing in the fragment re-exposes them, and there is no plan to. Generated by the pinned oapi-codegen into a committed `pki-server.gen.go`; `Handler` (`handler.go`) implements the generated `api.ServerInterface` behind a `var _ api.ServerInterface = (*Handler)(nil)` compile-time assertion, and `Module.OpenAPISpec()`/`Register`'s `reg.Routes.Mount(apiPath, m.handler)` are wired for real. The fragment is in `api-contract.yml`'s regeneration-and-porcelain-gate steps, so the committed `pki-server.gen.go` cannot drift from the spec.

**Tenant context is read only where the underlying table needs it.** Unlike every other module's HTTP surface, this one spans two data domains: only `PkiRevokeCertificate` reads the caller's tenant from the request context (`pkgcore.MustTenantFromContext`, never a request parameter/header/body) because `pki_certificates` is the one tenant-scoped table this module has. The other four operations (signing-key revoke, both JWKS exports, the CRL fetch) touch only platform data (`pki_signing_keys`, `pki_authorities`) and never resolve a tenant at all -- a request to one of them succeeds under any tenant, or none, exactly as the underlying repository call would.

**Each operation's permission gate and its evaluation domain are fixed -- a host gate must not improvise either.** This Handler performs no permission check of its own (enforcement belongs to the host's rbac gate, the same division every other module documents), but which permission gates which operation, and in which domain, is part of the module's contract: `PkiRevokeSigningKey` is gated on `pki:revoke_signing_key` evaluated under the PLATFORM domain (`rbac.SystemDomain`), NEVER in the request tenant's domain -- the tenant is absent from the operation's DATA access (the row has no tenant column) and yet its permission must still be evaluated in the platform domain, or a single tenant's grant reaches every tenant's tokens; `PkiRevokeCertificate` is gated on `pki:revoke_certificate` evaluated in the request's own tenant domain; the three reads (both JWKS exports and the CRL fetch) serve platform public-key material and are gated on `pki:read`. `examples/reference-app`'s gate implements exactly this shape (`guardPkiRoute`/`pkiSubjectResolverFor`, demo_subject.go -- the subject resolver pins the signing-key revoke's tenant to `rbac.SystemDomain`), and `TestBuildServer_PkiSigningKeyRevoke_RequiresThePlatformDomainPermission` pins the boundary through the composed HTTP stack: a tenant-domain holder of the permission is refused 403 while platform staff under SystemDomain succeeds. See module.go's permission const block and handler.go's `Handler` doc comment for the same table in code form.

**Audit recording happens at the HTTP boundary, not inside the Go API.** `Handler.recordAudit` calls `audit.Emit` after `Service.RevokeSigningKey`/`CAService.RevokeCertificate` has already committed -- the identical placement and identical reasoning `examples/reference-app/internal/notes/handler.go`'s `recordNoteCreatedAudit` documents (a same-SQLite-connection deadlock hazard if the write-capture plugin instead shared the business write's own transaction). This keeps `revocation.go` itself free of an `audit.Emit`/`go/dbkit/audit` dependency it does not otherwise need: a caller of the Go API directly (bypassing HTTP) gets the state transition, the cache invalidation and the published event, but not an audit row, unless it records one itself.

**No reference-app consumer, and no `api-contract.yml` regeneration-and-diff gate, this round.** Per the round's own scope note (task item 5), wiring `examples/reference-app` as a live consumer of this surface was judged out of scope rather than "genuinely small and clean" -- the app is a dental SaaS with no certificate-issuing feature to hang a revoke/JWKS/CRL UI off of, the same reasoning that has kept the whole X.509 layer unconsumed since round 1. `Taskfile.yml`'s `api:gen` task DOES run oapi-codegen over this fragment now (added alongside the other six in this round), so `task api:gen` regenerates `pki-server.gen.go` correctly -- but `.github/workflows/api-contract.yml`'s own regenerate-then-porcelain-gate enforcement was NOT extended to include this fragment in this round, a known gap rather than an oversight. The gap is closed as of the `28a7332` CI round: pki's directory is in that workflow's regeneration steps, so the committed `pki-server.gen.go` is regenerated and porcelain-gated (`git status --porcelain --untracked-files=all`) exactly like every other fragment's -- and the fragment universe has since been single-sourced in `tools/api_fragments.json` (drift-gated by `tools/check_api_fragments.py`), where pki is a registered member -- while CI still builds and tests this module on every PR (`fast-check.yml`'s standard per-module matrix, which compiles `handler.go` against the committed `pki-server.gen.go` and would fail if they drifted structurally). **The "no reference-app consumer" half of that judgment closed with the X.509-consumer round (2026-09-08): the app now drives `pki_revokeCertificate` and `pki_getAuthorityCrl` over the wire in `attestation_flow_test.go` (signing-key revoke was already driven by `pki_revoke_gate_flow_test.go`); the two JWKS read operations remain the only HTTP operations no caller exercises.**

## Known limitations

- **`SignerRegistry` and `pkgcore.KeyNeverLeavesBoundary` are both landed (round 4).** `SignerRegistry` (`signer_registry.go`) is a package-level `pkgcore.SeamRegistry[Signer]` carrying `"signer.local"` (`LocalSigner`, `Capabilities: 0`) from this package's own `init()`, plus whatever names a host has blank-imported (`go/pki/signer/vault`'s `"signer.vault"`/`"signer.vault-direct"`, `go/pki/signer/kmsaws`'s `"signer.aws-kms"`/`"signer.aws-kms-direct"`). `Module.WithSigner(name string, signer Signer)` is kept alongside it, unchanged, as the escape hatch for a caller that already holds a concrete `Signer` value -- both exist simultaneously by design, the identical shape `pkgcore` itself keeps `WithEventBus`/`WithKVStore`/etc. alongside their own registries; see "Signer providers: `vault` and `kmsaws`" above for the full rationale, including why `"signer.local"`'s own registry entry opens an independent database connection from `pkgcore.Config` rather than sharing a `Module`'s `db` (`signer_registry.go`'s `localSignerFromConfig` doc comment). `KeyNeverLeavesBoundary` is declared in `go/pkgcore/capability.go`, following the exact pattern of `MultiReplicaSafe`/`SurvivesRestart`/`Stateless`; `LocalSigner` does not have it (unchanged), and `vault`/`kmsaws` have it only in `ModeDirectSign`.
- **`KeyNeverLeavesBoundary` is enforced at the pki tier's registry-resolution point (`BuildSignerRequiring`), and only there.** `pkgcore.Kernel.Bootstrap` (`go/pkgcore/registry.go`) still resolves and validates capabilities only for the four fixed built-in seams (`EventBus`, `KVStore`, `Mailer`, `ObjectStore`) via `resolveKernelSeam`/`validateSeamCapability`; it has no knowledge of `pki.SignerRegistry` or `pki.Signer`, and that half of the earlier "declared but not enforced anywhere" record is unchanged. What the enforcement round added is the record's own sanctioned `pki`-local check (`signer_registry.go`'s `BuildSignerRequiring`, the shape the earlier record named -- "`Module` or `SignerRegistry.Build` taking a required `Capability` and refusing a resolved `Signer` that lacks it"): a host that intends to require a capability of the signer it wires resolves it through `BuildSignerRequiring(name, cfg, required)` instead of `SignerRegistry.Build`, and a resolution whose registration lacks a required bit is refused with an error wrapping `pkgcore.ErrCapabilityUnsatisfied`, naming the signer and the missing capability -- so the wiring mistake the record described (a host resolving `vault`/`kmsaws` in envelope mode where it intended direct-sign, or `signer.local` where it intended a boundary-keeping provider) now fails at the resolution point when the host declares the requirement. Two residuals are recorded rather than hidden: `Module.WithSigner` still takes no requirement parameter, because a directly injected `Signer` value carries no capability declaration for anything to compare -- a host that requires the boundary of an injected signer must have obtained that signer through `BuildSignerRequiring` -- and a host that never declares a requirement gets no check, exactly as with the four built-in seams' deployment-mode declarations. `go/pkgcore/capability.go`'s doc comment predates this round and still describes the Kernel-only picture; the pkgcore-generalization alternative the record named remains unbuilt, by design, since the pki-local check covers the one comparison point where a capability declaration exists.
- **The X.509 layer has a real consumer as of 2026-09-08, and only the precisely residual surface above is not frozen.** See "X.509 layer: real consumer, precise residuals" above and the "Real consumer: AI-output attestation" round entry below for what the reference app's attestation layer exercises and the exact list of what it does not (the JWKS exports, the CRLDP embedding path, CRL-regeneration scheduling, expiry-driven authority/certificate lifecycle). `CAService`'s current shape is a real consumer's shape; the residual items listed there are the ones a future integration may still change freely.
- **The PostgreSQL integration tier is in the CI matrix as of the pki-dbkit deferral-batch round; it remains narrower than the module's eventual tier.** The migration-dedupe round shipped this module's first `integration_test/` package (`go/pki/integration_test/postgres_migration_dedupe_test.go`, run as `go test -race -tags=integration ./...` from the module directory against a real PostgreSQL server started with testcontainers -- `go/pki/internal/testutil.NewPostgres`), proving migration 0008's duplicate-ledger upgrade on the second dialect. The CI round wired it into `full-check.yml`'s integration-tiers matrix (the same `go test -race -tags=integration ./...` leg every other module's row runs), so full-check now runs it on `full-ci`-labeled PRs and every push to main. `docs/internal/22-pki.md`'s testing strategy names the module's eventual PostgreSQL leg as broader than this one regression (dual-dialect migrations from zero, `pki_certificates`'s `AssertIsolated` and the other five tables' `AssertNotTenantScoped`, all against a real server) -- that remains future rounds' work, as do the SQLite-only proofs every round since has added for its own migrations.
- **`api-contract.yml` gates this fragment as of the `28a7332` CI round.** See "HTTP surface (round 3)" above -- `task api:gen` regenerates `pki-server.gen.go` correctly, and the CI workflow's own regeneration then runs its porcelain consistency gate over the committed artifact, the enforcement the round-3 record above marked as the future round's job.
- **`ErrSignerUnavailable`'s first trigger was CRL signing; a provider now returns it directly too.** Round 1/2's AGENTS.md parenthetically associated this code with "a KMS-backed signer" (round 4's `vault`/`kmsaws`); `crl.go`'s `GenerateCRL` gives it its first trigger, wrapping ANY non-`*apperr.Error` failure from `x509.CreateRevocationList` this way, including the library's own template-validation errors -- an imprecision accepted because this module's own callers never produce an invalid template. The P2-3 closing round (2026-09-08) made the round-4-provider adoption real: `kmsaws`'s `signDirect` answers a KMS Sign whose response carries no `Signature` field with `ErrSignerUnavailable` (a signing backend that did not actually sign -- the fail-closed twin semantics bullet in "Signer providers" above and the seam contract sentence in `go/pki/signer.go`). `vault`'s own missing-`signature`-field answer remains an unwrapped `fmt.Errorf`, exactly as the original accounting recorded for both providers; what changed is that `kmsaws` now has a coded reason to return this code, not just `GenerateCRL`'s wrapping. See errors.go's own doc comment for the full accounting.
- **`Service.PromoteNow` is a round-3 addition that is NOT itself revocation.** It exists as a companion to `RevokeSigningKey` (an emergency revocation leaves a purpose with no active key until something is promoted) but performs no revocation of its own, and nothing in this module ever calls it automatically -- a host must call it explicitly. See `lifecycle.go`'s own doc comment for why it lives next to `PromoteDuePending` rather than in `revocation.go`, and for why it honors, rather than bypasses, the propagation window.
- **`Service.ReclaimRetired` (the retirement-and-reclaim round) is host-invoked and never automatic, and its report must be read through each signer's own `Destroy` semantics.** It is deliberately NOT wired into `ScanExpiry` or the expiry-scan job -- for the `vault`/`kmsaws` direct-sign modes `Destroy` is real provider-side deletion, and the scan's "never pushes to any external system" boundary (lifecycle.go) holds for deletion too. A host "enables reclamation" by calling the method on its own schedule; its schedule IS its retention declaration. The report's `Destroyed` list means "`Destroy` answered nil" -- which for `LocalSigner` is a physically deleted `pki_local_keys` row, for direct-sign modes a scheduled/performed provider deletion, and for envelope modes a validation no-op that reclaims nothing (the ciphertext in the row IS the material; dropping the row is a host history decision per the module's own recorded boundary). `ErrKeyNotFound` counts as already-reclaimed (`Destroyed`, quiet convergence); `revoked` keys are deliberately never reclaimed (the emergency path must not silently bundle deletion); a host wanting a revoked key's material gone calls its signer's `Destroy` directly. Full argument in `reclaim.go`'s doc comment and the round entry below.
- **`Service.EnqueueExpiryScan` carries a window-scoped idempotency key, sized against the host scheduler's interval.** Each enqueue names the `DefaultExpiryScanWindow` window (one hour; `expiryScanWindowStart`) its clock read falls in, so a multi-replica scheduler's same-window enqueues collapse into one job and a later window's enqueue runs the scan again. The window is the module's answer to the two wrong extremes the reviewer round found in this task's keyless history: no key at all (each tick its own independent job -- the pre-reviewer shape this file's older entries record -- so N replicas at a 1-minute cadence fire N redundant scans a minute) and a window-less constant key (exactly one scan per database file, since jobs' idempotency resolves one key forever on StandaloneQueue). A window of one hour against the reference host's one-minute tick is a 60:1 ratio; a host whose scheduler interval approaches the window must widen it through `WithExpiryScanWindow` (`DefaultExpiryScanWindow`'s doc comment and the module option say so), or every tick lands in a fresh window and the dedup is void. See `job.go`'s own doc comment for the full argument, and `enqueue_window_test.go` for the collapse/later-window/boundary proofs against a real `StandaloneQueue`.
- **`platformScanTenantID` is a deliberate accommodation, not a design pki would have chosen.** `jobs.Task.Validate` requires a non-empty `TenantID` unconditionally, but `pki_signing_keys` is platform data with no tenant to put there -- every other module's periodic task (`storage.taskTypeExpirySweep`) has a real one because its scanned data is tenant data. A fixed sentinel value exists purely to satisfy `jobs`' own validation; `expiryScanHandler.Handle` never reads it, since `SigningKeyRepository` is a plain `*gorm.DB` with no tenant-filtering plugin engaged. See `job.go`'s own doc comment.

- **Vault direct-sign rotation is not pinned to a key version.** See "Signer providers: `vault` and `kmsaws`" above for the standing warning and the unshipped fix.
- **No delivery path exists for a private key out of the module**, and `pki.key.rotate`/`pki.private_key.deliver` audit actions are deliberately undeclared (no human actor and no event exist to record); `pki_certificates.key_delivered` records the fact if a host ever delivers one itself.

## Adjudications a reviewer should not "correct"

**pki is not part of `saasctl new`'s `--with` selection set.** `pki` follows `authn` rather than being independently selectable. This module does not implement that wiring (it is `authn`'s `KeySource` change plus a `saasctl` template update), but a reviewer should not expect a `pki` entry in `go/saasctl`'s `--with` universe to appear, or to ever appear as an independent selection.

**`pki_authorities`/`pki_certificates` are not linked by a foreign key**, even though `Certificate.AuthorityID` names an `Authority` row. Cross-module foreign keys are forbidden in this codebase; here the two tables additionally sit in different data domains (platform vs. tenant), so a single FK constraint could not express the boundary correctly even if the module-boundary rule did not already forbid it.

**Serial numbers are 16 bytes of `crypto/rand`, not validated for global uniqueness across independent CAs.** A collision is cryptographically negligible (2^128 space) and is not the failure mode a timestamp-based serial would have -- millisecond timestamps collide constantly under concurrent issuance from a single CA. No uniqueness constraint sits on `serial`: `CertificateRevocationRepository.ListByAuthority`'s query shape keys on `authority_id`, not `serial`, so the constraint is not needed. A reviewer should not treat its absence as an oversight.

**`pki:rotate` is declared with no HTTP operation gating it, and that is deliberate, not an omission.** The capability `pki:rotate` names is real and already running (the expiry scan, and `Service.PromoteNow`), just not exposed as a permission-gated manual HTTP trigger -- see module.go's own doc comment on `PermissionRotate` for why declaring it now is not the same "prepare for later" a genuinely nonexistent capability would be.

**`ErrSignerUnavailable`'s real triggers are `GenerateCRL`'s wrap of ANY non-coded `Signer.Sign` failure and `kmsaws`'s empty-answer refusal, not specifically a KMS-backed provider's network fault.** This is recorded, not hidden, in errors.go's own doc comment and in "Known limitations" above -- a reviewer should not "fix" this by narrowing the wrap to a specific error type without first checking whether the narrower shape genuinely fits every `Signer` implementation's failure modes, `LocalSigner`'s included.

**Certificate revocation is database-arbitrated, and the arbitration lives in two guarded writes.** The certificate-row transition is one conditional `UPDATE` matching only a row still active (`CertificateRepository.RevokeIfActive`), and the ledger insert is `INSERT ... ON CONFLICT (certificate_id) DO NOTHING` (`CertificateRevocationRepository.InsertIfAbsent`) -- between them, exactly one racing call wins, a loser can never write its own reason and timestamp over the winner's committed row, and the ledger and the certificate row can never disagree about when or why the revocation happened. Every ledger row is built from values the certificate row already held committed, so a retry with a different reason never rewrites the original revocation's facts. A failed ledger insert is a returned error, never log-and-forget, and a crash between the two statements leaves bounded staleness (a CRL omits one serial until a repair call runs), never an incorrect "not revoked" answer. A reviewer should not "simplify" either write back into a check-then-act.
