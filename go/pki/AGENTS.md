# pki

go/pki owns key material that needs a lifecycle: signing keys and X.509 certificates, from generation through rotation to revocation. This file is the module-level discipline that ships with `go/pki` to consuming projects; the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`. Judge what exists by the code, not by this file's claims: every mechanism below is real, tested code, and the claims are backed by the test names this file cites.

## Scope

**In scope.** Four tables (`pki_signing_keys`, `pki_authorities`, `pki_certificates`, `pki_local_keys`) plus the `pki_certificate_revocations` revocation ledger, with dual-dialect versioned SQL migrations, registered through `dbkit.MigrationRegistry` the same way every other module does. The `Signer` interface and `LocalSigner`, the local, zero-external-dependency implementation `task dev` runs and every unit test in this module (and its consumers) can use as a test double. Internal CA issuance: `CAService.CreateRootCA`, `CreateIntermediateCA` and `IssueCertificate`, all through `crypto/x509`, with 16-byte `crypto/rand` serial numbers -- never a timestamp. `Service`, the key-lifecycle layer's public entry point, whose method signatures match the shape `authn`'s `KeySource` interface requires, structurally, with no import edge in either direction. module-contract wiring: permissions (`pki:read`, `pki:issue`, `pki:rotate`, `pki:revoke_signing_key`, `pki:revoke_certificate` -- the revoke pair is split by data domain, since one `pki:revoke` could not span the platform-domain `pki_signing_keys` and the tenant-domain `pki_certificates`; see "HTTP surface" below for the split's evaluation domains), audit actions (`pki.authority.create`, `pki.certificate.issue`, `pki.key.revoke`, `pki.certificate.revoke`), configuration items for CA/certificate/CRL validity periods and the CRL distribution point default, plus the lifecycle settings `pki.propagation_window` and `pki.renewal_lead_time` -- every one of them read at runtime through the module's settings seam (`settings.go`'s `SettingsReader`/`WithSettingsReader`, which the component descriptor wires automatically from the config module's handle when a config component is assembled): an explicit config row wins, and an unset row, an unwired reader or a failed read falls back to the construction-time or package value; the CA/certificate pairs additionally default a zero `NotAfter` to the declared default and clamp a request beyond the declared max to it (`boundedNotAfter`), and the CRL distribution point default applies to NEWLY created authorities only, never rewriting existing rows. These are genuinely pki's own settings, unlike the retiring overlap period, which routes through `EnsurePurpose`'s `maxCredentialLifetime` parameter rather than a config item (see "retiring overlap" in the `Service` section below for why the two are not the same concept) -- and the bilingual locale bundle for every declared error code.

The key-lifecycle layer: `Service.EnsurePurpose`/`ActiveSigner`/`VerificationKeys` are the public entry points. The lifecycle state machine lives in `lifecycle.go` -- `ScanExpiry` drives `PromoteDuePending`/`RetireDueRetiring`/`StageDueRotations` over the `pending -> active -> retiring -> retired` (plus `revoked`) vocabulary -- and is driven by a `go/jobs` task (`job.go`'s expiry-scan task, claimed on `reg.JobsSeat()` only when a host wires a queue via `WithQueue`), whose periodic schedule the module declares on the `pkgcore.ComponentRegistry.Schedules` seat alongside that handler (a platform-scope task at `Service.expiryScanSchedule`'s configured window). A host runs it either by starting a `jobs.Scheduler` over the finished registry or by calling `Service.EnqueueExpiryScan` on its own cadence; go/pki itself never enqueues anything. The transitions honor a propagation window and a retiring overlap period (see `lifecycle.go`'s own doc comments for the semantics; the overlap is sized against `EnsurePurpose`'s `maxCredentialLifetime`). Four lifecycle events -- `pki.signing_key.staged`/`.activated`/`.retired`/`.revoked` -- are declared and published from the transitions that actually fire them, and a process-local, event-invalidated key-set cache (`cache.go`) sits behind the `Service.ActiveSigner`/`VerificationKeys` hot path -- the same pattern `go/rbac`'s decision cache uses -- so a rotation or revoke on one replica converges the others through the bus rather than through the TTL. `SignerRegistry` (`signer_registry.go`) is a package-level `pkgcore.SeamRegistry[Signer]` carrying `LocalSigner` under the name `"signer.local"`; `pkgcore.KeyNeverLeavesBoundary` (`go/pkgcore/capability.go`) is the capability the direct-sign provider modes declare; and two provider subpackages implement the module against external key services -- `go/pki/signer/vault` (HashiCorp Vault Transit, registering `"signer.vault"`/`"signer.vault-direct"`) and `go/pki/signer/kmsaws` (AWS KMS, registering `"signer.aws-kms"`/`"signer.aws-kms-direct"`) -- each supporting both envelope and direct-sign modes; see "Signer providers: `vault` and `kmsaws`" below for the full shape and the two-names-per-provider rationale.

Revocation for both layers: `Service.RevokeSigningKey` (any prior status, immediately excluded from `ActiveSigner`/`VerificationKeys` through the event-invalidated cache -- never a second cache-clearing path) and `CAService.RevokeCertificate` (marks the tenant certificate revoked and writes a `pki_certificate_revocations` ledger row), both idempotent no-ops on a repeated call (a repeated revoke of an already-revoked certificate reconciles rather than just returning -- see "Certificate revocation is ledger-arbitrated" below); `CAService.VerifyCertificate`, a real `crypto/x509` chain verification that refuses a revoked certificate OR a revoked authority anywhere in its chain up to the root; CRL generation (`CAService.GenerateCRL`, `crypto/x509.CreateRevocationList`, RFC 5280 CRL numbering) plus a periodic `go/jobs` task (`crl.go`'s CRL-regeneration task, scheduled through `CAService.EnqueueCRLRegenerate` exactly like `Service.EnqueueExpiryScan`'s pattern); a `CRLDistributionPoints` extension embedded into every certificate a CA with a declared `CRLDistributionPoint` signs (`CAParams.CRLDistributionPoint`); two distinct JWKS exports -- `Service.ExportJWKS` (active+retiring public keys of one purpose) and `CAService.ExportAuthorityChainJWKS` (one authority's own chain up to the root), both over `github.com/go-jose/go-jose/v4`, both public-keys-only; `Service.PromoteNow` (`lifecycle.go`), a manual, propagation-window-honoring promotion trigger meant as a revocation companion (see its own doc comment for why it is not itself part of revocation); `Service.ReclaimRetired`, the host-invoked reclamation of retired keys' underlying material (see "Reclaiming retired keys' material" below); and the module's HTTP surface under `/api/v1/pki` (`go/pki/api/openapi.yaml`, `handler.go`, `Module.OpenAPISpec()`/`reg.RoutesSeat().Mount` wired for real) -- see "HTTP surface" below.

**Still not in scope, by design:** TLS certificates for transport, ACME, an OCSP responder (CRL only), Certificate Transparency logs, cross-deployment CA federation, a generic "export private key" API, and SM2. `pki.authority.expiring`/`pki.certificate.expiring`/`.issued`/`.renewed` events and `pki.key.rotate`/`pki.private_key.deliver` audit actions are likewise undeclared -- see events.go's and module.go's own doc comments for exactly why each one has no genuine emitter.

## The bootstrap key it declares

`Register` declares one process-start key on the component descriptor's `BootstrapKeys`: `pki.local_key_cipher_key`, the AES key that seals `LocalSigner`'s `pki_local_keys` private-key column (`RegisterLocalKeySerializer`). It is `hexkey` and Sensitive, its documented fallback is a non-secret development default (which a real deployment must override, or its signing keys are sealed under material committed to this repository's source), and it is separate from every other module's key material -- the keys it seals are the ones `authn`'s access tokens are ultimately signed with, and dbkit's key-separation rule spans modules. The declaration states the contract; the host resolves the value and injects the cipher. pki never reads the environment. The `vault`/`kmsaws` provider modes have no equivalent key here: their material lives in the external service.

## Signer module

The single most important interface-shape decision in this module: `Signer` exposes signing *operations* (`GenerateKey`/`Sign`/`Public`/`Destroy`), never a way to read a private key back out. A `Protect(key)`/`Unprotect(ref)` shape would require the private key to exist in plaintext inside this process's memory at some point, which defeats the entire point of a KMS-backed implementation. See `signer.go`'s doc comment for the full argument, including why `Sign` does not reuse the standard library's `crypto.Signer` (no `context.Context` parameter, which a KMS-backed direct-sign implementation genuinely needs for timeout/cancellation/trace propagation on a path a login walks through).

`input`'s meaning in `Sign` is algorithm-dependent and is never normalized to "always a digest": for `AlgorithmEd25519` (the only algorithm supported), `input` is the *complete message* -- PureEdDSA hashes internally, and this is also exactly RFC 8037's JWT `EdDSA`. Getting this wrong for a KMS-backed implementation is not cosmetic (AWS KMS's `MessageType: RAW` vs. `DIGEST` select genuinely different signature algorithms), which is why the doc comment spells this out even though `LocalSigner` has no `MessageType` parameter to get wrong.

`LocalSigner` does **not** have the `KeyNeverLeavesBoundary` capability the `vault`/`kmsaws` implementations declare in direct-sign mode: a `Sign` call decrypts the private key into this process's memory for the duration of the `crypto/ed25519` call. That is the deliberate, documented cost of a zero-dependency signer.

**`LocalSigner` is also the `signer.local` component** (`component.go`, self-registered from `init` beside the `SignerRegistry` name-based path). A composition configuration selects `signer.local` as the `signer` module's implementation — a binding module, so exactly one signer is selected per assembly. The component `Requires` the database (`*gorm.DB`) and builds the signer over that shared connection, never the second connection the registry entry's own constructor must open for itself because a flat `pkgcore.Config` cannot carry a `*gorm.DB`; it `Provides` `(*Signer)(nil)` for consumers' tokens and declares the same 0 capabilities the registry entry declares. Like every `LocalSigner` caller, it expects `LocalKeySerializerName` to be registered (once, at bootstrap) against the host's cipher — the pki module's own `Prepare` step is where that registration goes. The component face covers every built-in signer name, beside the registry path (`signer_registry.go`) a caller holding a flat `pkgcore.Config` keeps: `go/pki/signer/vault`'s own `component.go` registers `signer.vault` and `signer.vault-direct`, `go/pki/signer/kmsaws`'s registers `signer.aws-kms` and `signer.aws-kms-direct`, each implementing the `signer` module, `Providing` `(*Signer)(nil)`, spelling the same two-name mode split its registration declares (the `-direct` components carry `pkgcore.KeyNeverLeavesBoundary`; the envelope modes and `signer.local` declare 0 capabilities), and taking the identical key set the flat registration documents — both faces funnel through the same per-name adapters, so they cannot diverge.

Failure semantics are as much the module's contract as success shapes: the contract sentence in `go/pki/signer.go`'s `Sign` doc comment states that an unrecognized `keyRef` is `pki.ErrKeyNotFound` from every implementation, that an empty signing answer is a coded failure (never a `(nil, nil)` empty-signature success, never a panic on a malformed answer), and records each provider's concrete behavior. The empty-signature failure cannot reach a security bypass: an empty signature through authn's `Signer.Issue` produces a token Ed25519 verification always rejects -- a loud availability failure, not a silent one.

## Signer providers: `vault` and `kmsaws`

`go/pki/signer/vault` and `go/pki/signer/kmsaws` are the two provider subpackages. Both follow the identical shape `go/pkgcore/eventbus/redis`, `go/pkgcore/kv/redis` and `go/pkgcore/objectstore/s3` established: importing either package for side effect (`import _ ".../pki/signer/vault"`) registers its implementations onto the package-level `SignerRegistry` (`signer_registry.go`); a host that never imports a provider subpackage never resolves its names.

**Two names per provider, not one.** Each package supports both `Config.Mode` values -- `ModeEnvelope` (the real private key, encrypted externally, decrypted locally to sign) and `ModeDirectSign` (the key generated inside, and never exported by, the external service). `pkgcore.SeamRegistry[T]`'s own contract pairs one *fixed* `Capability` value with one registered name -- `Build` returns whatever `Capability` was recorded on the `Registration` at `init()` time, never something read back off the constructed value -- so a capability that depends on a runtime `Mode` cannot correctly live on a single name. Each package therefore registers two names: `"signer.vault"` / `"signer.aws-kms"` (envelope, `Capabilities: 0`) and `"signer.vault-direct"` / `"signer.aws-kms-direct"` (direct-sign, `Capabilities: pkgcore.KeyNeverLeavesBoundary`) -- mirroring how `pkgcore`'s own mailer registers `"mailer.console"` (`Stateless`) and `"mailer.smtp"` (`MultiReplicaSafe|Stateless`) as two components rather than one whose capability depends on configuration.

**Both packages hide their private key material behind a self-describing `keyRef` in envelope mode.** Neither package has its own persistent storage: `GenerateKey` under `ModeEnvelope` generates a real `ed25519` key pair in-process, PKCS8-marshals the private half, and immediately wraps it with the external service's own encrypt operation (Vault Transit's `encrypt`, KMS's `Encrypt` against a caller-provisioned symmetric wrapping key); the resulting ciphertext itself -- not a name pointing at storage this package keeps -- IS the `keyRef` `pki.Signer.GenerateKey` returns. `Sign`/`Public` decrypt it back into memory for the call's duration only, the same cost `LocalSigner.Sign` pays for its own `dbkit`-encrypted column. `Destroy` under `ModeEnvelope` validates the `keyRef` still decrypts (reporting `pki.ErrKeyNotFound` if not) and otherwise no-ops -- there is nothing named by `keyRef` for the external service to delete; the caller dropping its own row (e.g. `pki_signing_keys.key_ref`) is what actually destroys the key. Under `ModeDirectSign`, `keyRef` is the provider's own key name/ID (a Vault Transit key name; an AWS KMS `KeyId`), and `Destroy` really does ask the provider to remove it -- immediately for Vault (`DELETE transit/keys/<name>`, after `GenerateKey` flips `deletion_allowed` so the delete can succeed at all), only *scheduled* for AWS KMS (`ScheduleKeyDeletion` with the minimum 7-day `PendingWindowInDays` -- KMS has no "delete now" for a protected key, an honest limitation `kmsaws/signer.go`'s `Destroy` doc comment records, not a bug).

**The two implementations agree on FAILURE semantics, not just success ones, and both fail closed on an empty signing answer.** A host that swaps one registered implementation for the other (a registration-name change, zero code change) observes the same failure vocabulary: an unrecognized `keyRef` is `pki.ErrKeyNotFound` from both `signDirect` paths -- `vault` answers it for a nil secret, `kmsaws` for a nil `SignOutput` -- and a signing backend that answers with no signature bytes at all is a coded failure, never a `(nil, nil)` empty-signature success: `kmsaws` answers `pki.ErrSignerUnavailable` for a `Signature`-less `SignOutput`, `vault`'s `parseVaultSignatureEnvelope` refuses an empty decoded signature, and `signDirect` compares the parsed `v<N>` version against the signer's pin -- a signature whose envelope names any version other than `directSignPinnedKeyVersion` is refused, so a rotation that actually changed which version signed (or a Vault that ignored the request's `key_version` parameter) surfaces as a loud error rather than a signature no exported key verifies. `TestSigner_DirectMode_Sign_NilResponse_FailsClosed`/`TestSigner_DirectMode_Sign_EmptySignature_FailsClosed` (`kmsaws/signer_test.go`) and `TestParseVaultSignatureEnvelope_RejectsMalformedVersion`/`TestParseVaultSignatureEnvelope_RejectsEmptySignature` (`vault/signer_test.go`) pin all four shapes. The version field is Vault's own `v1`/`v2` spelling, `v` prefix included; the envelope round-trip test `TestSigner_DirectMode_Sign_DecodesVaultSignatureEnvelope` exercises the parse against that spelling.

**`signer.vault-direct` pins the Transit key version.** The module rotates by creating NEW Transit key names (`pending` -> `active` -> `retiring` -> `retired` across fresh `pki-<uuid>` keys); it never rotates a Transit key in place, and Vault's own `rotate` endpoint is the one way a managed name can acquire a version other than the one this package created it at. `signDirect` pins every direct-sign request to the key's created version (`directSignPinnedKeyVersion`, `vault/signer.go` -- the version every `keyRef` this package issues was created at, the version the module issued and exported with); `readPublicKey` serves that same version's key rather than the key's `latest_version`; and a sign answer whose `vault:v<N>:` envelope names any other version is refused -- an in-place rotation therefore leaves signatures and the advertised key on the created version, forever consistent with each other, and cannot make the rotated version usable either: it stays inert until the host rotates through the module's own lifecycle (a new name per stage). Two boundaries are recorded rather than hidden: the pin's behavior is proven against stubbed clients only -- this package has no real-Vault integration leg, so a real Vault's rotation-policy interactions (`min_decryption_version` above all, which can make a pinned sign request itself be refused) remain for a future integration tier to verify -- and the pin never adopts the rotated version. The full mechanics live in `vault/doc.go`'s "in-place Transit key rotation" section and the registration note in `vault/register.go`.

The pin is literal and enforced on both halves: `signDirect` sends `key_version` on every direct-sign request (the pinned value is the constant 1, the version a freshly created Transit key starts at), and `readPublicKey` answers from the pinned version's entry in the key read response's `keys` map -- Vault keeps every version's public-key entry for as long as the key exists -- never from the response's own `latest_version`, so the exported key cannot shift off the version the signatures verify against. `TestSigner_DirectMode_Sign_EnvelopeVersionBeyondThePin_IsRefused` and `TestSigner_DirectMode_Public_ServesThePinnedVersionNotTheLatest` (`vault/signer_test.go`) pin both halves, and the sign request's pinned `key_version` is additionally asserted by `TestSigner_DirectMode_Sign_DecodesVaultSignatureEnvelope`'s request-shape check.


**`kmsaws`'s direct-sign mode uses `ED25519_SHA_512` with `MessageType: RAW`, never `ED25519_PH_SHA_512`/`DIGEST`.** The two combinations are NOT interchangeable, and a signature made under the wrong one signs successfully but fails only at verification time, against a signature already delivered. `TestSignDirect_ProducesAPureEdDSASignature` (`kmsaws/signer_test.go`) pins a real `crypto/ed25519.Verify` call against a signature produced through this package's own request-building and response-decoding path, so a future edit that swaps either constant fails a test rather than silently shipping an unverifiable signature.

`kmsaws`'s 3 is deliberately not the AWS SDK's usual, much larger footprint: `Config` takes only static credentials (`AccessKeyID`/`SecretAccessKey`/`SessionToken`), never `github.com/aws/aws-sdk-go-v2/config`'s default-credential-chain resolver, which pulls in STS, SSO and SSO-OIDC (measured with the identical throwaway-module method: `service/kms` plus `config` together tidy to 13 indirect entries, more than four times this package's actual 3) for a resolution mechanism this package's constructor-supplied-credentials contract never needs. Neither package's own root-package imports leak beyond its subpackage: `hashicorp-vault-only-in-pki-signer-vault` and `aws-sdk-only-in-pki-signer-kmsaws` (`.golangci.yml`) deny the respective client import from every other file under `go/`, mirroring `go/pkgcore`'s own `redis-only-in-pkgcore-and-jobs`/`minio-only-in-pkgcore` rules -- narrowed to the implementation package itself (not the whole module), the same shape `go/observability`'s exporter-split rules use, since `go/pki`'s own root package (where `Signer` and `LocalSigner` live) must not import either SDK either.

**No offline-runnable Example against a live backend, for either package.** Both packages' `example_test.go` demonstrate construction and `pki.SignerRegistry` self-registration only, never an actual network round trip: neither a Vault dev-mode server (Docker-backed, via testcontainers) nor a real AWS account is reachable from the plain unit-test tier godoc `Example`s run under. `signer_test.go` in each package instead stubs the third-party client's own interface (`transitClient` for Vault's `*vaultapi.Logical`; `kmsClient` for AWS's `*kms.Client`) and exercises every request/response shape this package builds and parses against those stubs -- proving the code compiles and shapes requests correctly from an external caller's perspective, the strongest guarantee available without a real backend. **AWS KMS gets no integration leg at all, by design, not by gap**: LocalStack's KMS implementation is known to diverge from the real service, so a testcontainers-backed proof there would prove conformance against LocalStack, not against AWS KMS, which is worse than no such proof since it would look like coverage without being coverage. Real verification against a live AWS account is manual, and has not been performed -- stated plainly rather than left implicit. Vault, by contrast, has no such leg either: no `go/pki/signer/vault/integration_test/` package exists, so `go/pki/signer/vault` carries the identical "stubbed unit tests only" status as `kmsaws`, without sharing `kmsaws`'s "never gets one, by design" reasoning (a Docker-backed Vault dev-mode leg, exercising both envelope and direct-sign modes, is the shape such a package would take).

## Data model

Five tables spanning three of the four data domains. **One table never mixes two data domains** -- the central schema decision of this module, answering the diagnosed system's central defect (a platform CA and per-tenant certificates sharing one table under one weak key):

| Table | Domain | Repository shape | Isolation proof |
|---|---|---|---|
| `pki_signing_keys` | Platform | `SigningKeyRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |
| `pki_authorities` | Platform | `AuthorityRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |
| `pki_certificates` | **Tenant** | `CertificateRepository`, embeds `dbkit.Repository[Certificate]` | `tenancytest.AssertIsolated` |
| `pki_local_keys` | Platform | `LocalKeyRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |
| `pki_certificate_revocations` | Platform | `CertificateRevocationRepository`, plain `*gorm.DB` | `tenancytest.AssertNotTenantScoped` |

**`pki_certificate_revocations` is a denormalized, append-only revocation ledger**, and the reason it exists at all is a cross-domain problem: `pki_certificates` is tenant data, so a tenant-scoped `dbkit.Repository[Certificate]` read can never enumerate every certificate one authority (platform data) has ever revoked across every tenant. This table carries a real, deliberately UNENFORCED `tenant_id` column -- the same accommodation `go/notification`'s `send_records`/`platform_blacklist` and `go/dbkit/audit`'s `AuditEvent` already make for the identical shape of problem. The ledger row is written as a separate statement from `CAService.RevokeCertificate`'s `pki_certificates` update, and both writes are database-arbitrated single-winner statements that can never disagree about when or why the revocation happened -- see "Certificate revocation is ledger-arbitrated" below; `model.go`'s `CertificateRevocation` doc comment carries the full "why this is safe" argument (bounded staleness on a crash between the two writes, never an incorrect "not revoked" answer).

**No business table ever holds a private key, and this is a schema fact, not a documentation promise.** `pki_signing_keys`, `pki_authorities` and `pki_certificates` carry only `signer_name` + `key_ref` -- an opaque pointer to whichever `Signer` implementation actually owns the key. `pki_local_keys` is `LocalSigner`'s own, separate store, read and written by no other code in this module.

**`pki_signing_keys.status` carries the full five-value lifecycle vocabulary** (`pending`/`active`/`retiring`/`retired`/`revoked`, the values of the `SigningKeyStatus*` constants in model.go). The transitions that write each value live in `lifecycle.go` (see "Validity at key-take time, domain-split revoke permissions, and windowed periodic-task keys" below and the `Service` section above), and `Service.RevokeSigningKey` writes `SigningKeyStatusRevoked` from any prior status.

**`pki_signing_keys` enforces "at most one active key per purpose" at the database, not just in application code**: `uq_pki_signing_keys_active_purpose` is a partial unique index (`WHERE status = 'active'`), the same partial-index technique the codebase's soft-delete mechanism uses for "a value can repeat across states but not within one". `TestSigningKeyRepository_ActivePurposeUniqueness_IsEnforcedByTheDatabase` proves a second `Create` for an already-active purpose is refused by SQLite; this is standard SQL (no PostgreSQL-only feature), so the same index works unmodified on both dialects. Revoking an active key is what frees the active slot for a replacement.

**`pki_local_keys.not_after` is nullable and unpopulated by any code path.** `LocalSigner.GenerateKey` takes no expiry parameter -- the `Signer` interface's frozen shape has no room for one, and the key-lifecycle layer that does know a key's intended lifetime records it on the *owning* row (`pki_signing_keys`/`pki_authorities`/`pki_certificates`), not on `pki_local_keys`. The column and its index exist ahead of any writer so the expiry scan can scan `pki_local_keys` directly -- across whichever table actually owns a given `key_ref` -- without a three-way join; populating it would require `Service` to acquire signer-implementation-specific knowledge of `LocalSigner`, which the `Signer` module's abstraction is built to prevent (see also `model.go`'s `LocalKey.NotAfter` doc comment).

**`pki_authorities.parent_id` is a genuine nullable column, not an empty-string sentinel.** Unlike `org_nodes.parent_id` or `configs.tenant_id`, no unique index is keyed on it (an authority may issue any number of intermediates), so there is no NULL-vs-empty-string collision to design around, and a real `NULL` for a root authority is the honest representation.

**`pki_authorities` carries five CRL columns** (migration `0006`): `crl_distribution_point` (the URL this authority's own CRL is served at -- empty omits the extension from every certificate this authority signs, never a broken placeholder, matching every other unset-value field in this module), `crl_number` (RFC 5280 §5.2.3, monotonically increasing on every `GenerateCRL` call, `0` meaning no CRL has ever been generated), and `crl_pem`/`crl_issued_at`/`crl_next_update` (the most recently generated document itself, stored rather than recomputed on every fetch -- see `crl.go`'s `GenerateCRL`).

**Every `key_ref` column is `VARCHAR(4096)`, not the 255 characters a `VARCHAR(255)` would allow.** The width matters for `kmsaws`'s envelope mode, where the `keyRef` is the base64 of the whole KMS `CiphertextBlob`: base64 of any blob of 192 bytes or more exceeds 255 characters, and a real KMS symmetric ciphertext blob for an ~80-byte PKCS8 ed25519 key is empirically 0.5-2KB raw (up to ~2732 base64 characters). PostgreSQL, which enforces `VARCHAR(255)` where SQLite does not, would refuse the write at insert time under the narrower declaration. Migration `0009` widens the three columns (`pki_signing_keys`, `pki_authorities`, `pki_certificates`) to `VARCHAR(4096)` -- the next power-of-two bound above that window, admitting any raw blob up to 3072 bytes and kept finite on purpose so an opaque handle cannot silently grow into a document store; the full rationale is in the migration's own header, with the GORM model size tags (model.go, the Atlas-style source of the schema) widened in lockstep. PostgreSQL's half of 0009 is a plain `ALTER COLUMN TYPE`; the SQLite half rebuilds each table (SQLite cannot ALTER a column type) via rename/create-widened/copy-by-explicit-column-list/drop, re-creating every index under its original name -- safe under dbkit's `MigrationRegistry`, which applies one module's files inside a single transaction. No host-owned storage indirection exists behind envelope `keyRef`s: a design making the envelope `keyRef` a short name resolved through host-owned storage would reverse the deliberate "the ciphertext itself IS the keyRef, the package keeps no storage" posture. Verification limits, stated honestly: the module's PostgreSQL half of 0009 has been reviewed for dialect correctness but never executed against a real server (the integration tier covers one regression only -- see the Testing section), and the over-length-refusal itself is not exercisable in this repository at all. The unit gates are (a) the migration set applies from zero on SQLite through the MigrationRegistry path every test DB boots with, (b) `key_ref_widening_test.go` round-trips a 2732-character envelope-length keyRef through all three repositories against the migrated schema and pins the declared `VARCHAR(4096)` type SQLite reports -- the pre-0009 schema fails that PRAGMA pin, since it declares `VARCHAR(255)` -- and (c) `model_test.go` pins the three `size:4096` model tags.

## `Service`: the key-lifecycle layer's public shape

`Service.EnsurePurpose`/`ActiveSigner`/`VerificationKeys` are declared using **only standard-library types** in every signature, including an anonymous struct as `VerificationKeys`'s return-slice element type. This is not a style choice: structural interface satisfaction across two packages' own named types requires exact, literal signature equality, since two packages' named structs are never the same type. `authn`'s `KeySource` interface is declared independently, in `go/authn`, with **zero import of `go/pki`** -- and `*Service` satisfies it structurally. `service.go`'s `keySourceShape` is the compile-time proof of that conformance, kept in this module (not in a test file) specifically so it fails to compile the moment an edit accidentally breaks the shape. authn signs through this layer: `KeySet`/`TokenKey`/`GenerateTokenKey`/`NewKeySet` do not exist on the signing path -- the injection point is `WithKeySource`, with no static-key alternative -- and `authn.Signer`/`authn.Verifier` resolve keys from a `KeySource` on every call, an algorithm-consistency check runs on token verification, and `go/saasctl`'s `authn`-containing templates plus `examples/reference-app` wire a real `*pki.Service`-backed `KeySource`.

**`EnsurePurpose` is the BOOTSTRAP path, not rotation.** It declares that `purpose` needs a signing key of `algorithm`, with a retiring overlap period that must eventually cover `maxCredentialLifetime`. Idempotent in the sense a caller needs at bootstrap: if the purpose already has an active key WITHIN its validity window, `EnsurePurpose` returns nil without creating a second one. It does not verify that the existing key's `Algorithm` matches the `algorithm` argument: a repeated call with a different algorithm for the same purpose silently keeps the first key -- a known limitation of this call, safe today because no code path does it. When the purpose's active key is out of validity (the expiry scan never ran, or ran too late) AND no pending successor is in flight (the scan staged one but stopped before promoting it -- in which case the scan, or a host's `PromoteNow`, owns the rotation and bootstrap must not churn the purpose with a second candidate), `EnsurePurpose` self-heals: it revokes the expired key through the same guarded transition and event `Service.RevokeSigningKey` uses -- revoking is what frees the active slot for a replacement, since the partial unique index allows one active row per purpose, and what tells every replica's cache the key is gone -- and falls through to create an in-validity replacement in the same call. Revoking rather than silently overwriting keeps the expired key's fate on the record: its row carries the `RevocationReason` and the `EventSigningKeyRevoked` event reaches the same subscribers an operator-initiated revoke reaches. When the purpose has NO active key at all, `EnsurePurpose` creates a key and marks it `SigningKeyStatusActive` in the same call, synchronously, with no propagation window -- safe specifically because a purpose with no active key has never signed anything, so there is no multi-replica cache-propagation race to protect against on a kid nothing has verified yet. (The self-heal's revoke-then-create has the same bounded staleness profile as any revocation -- a replica whose cache still holds the revoked kid can keep using it for at most the cache TTL.) `defaultKeyValidity` (`service.go`) is the un-configurable default standing in for a host's real rotation policy where a host does not declare one.

## X.509 layer: real consumer, precise residuals

The X.509 layer's mandatory-first-consumer exception is closed by a genuine
consumer: `examples/reference-app/internal/attestation`, the reference app's
AI-output authenticity attestation layer (its package doc carries the product
narrative; docs/internal/22-pki.md's "X.509 layer has a real consumer"
section records the closure). A dental AI SaaS shares AI-generated
simulation outputs (patient media) through public share links; the platform
is the only legitimate holder of the keys it issues (pki never delivers
them), so the app vouches for its own outputs. The consumer drives every
main path this layer exists for:

- **Boot-time CA creation.** At boot (`internal/app/server.go`, after
  the assembly) the attestation service's `EnsureAuthorityChain`
  calls `CAService.CreateRootCA` + `CreateIntermediateCA` once per
  database; later boots find the chain again by fixed subject names, so a
  restart never mints a second chain (proven by
  `TestX509Attestation_ChainAndAttestationsSurviveARestart`, which boots,
  shares, tears down and reboots over one database and object store and
  finds exactly one root and one intermediate).
- **Per-tenant issuance and signing.** Every surface that makes a
  succeeded simulation output visible to its own tenant -- the job-status
  poll, the per-photo enumeration and the simulation-content read, all in
  `internal/app/smilesim.go` -- calls `EnsureAttested`, which opens the
  output's bytes under the ctx tenant, signs a canonical message (object
  id, content SHA-256, tenant) with the tenant's `simulation.attestation`
  certificate through `CAService.SignCertificate` -- reusing the tenant's
  current certificate while active, issuing a fresh one through
  `CAService.IssueCertificate` otherwise (365-day validity under the app's
  intermediate authority) -- and upserts one attestation row per object
  (`smilesim_attestations`, tenant-scoped).
- **Chain-verified share gating.** The sharing resolver's gate
  (`internal/app/sharing_resolver.go`) runs `CheckContent` before serving
  any share: an attested object is served only when
  `CAService.VerifyCertificate` vouches for its certificate (revoked row,
  revoked chain member or expiry all refuse), the Ed25519 signature over
  the stored message verifies with the leaf's public key, the message
  names this object and tenant, and the live content digest matches the
  attested digest; un-attested objects (patient photos) pass untouched. A
  refusal surfaces as the resolver error sharing answers with
  `sharing.resource_unavailable` (502).
- **Revocation and CRL publication over the wire.**
  `TestX509Attestation_SimulationOutputSharedThroughTheChainVerifiedGate`
  drives the full drill: revoke via the `pki_revokeCertificate` HTTP
  operation, share refused, the output re-attested under a fresh
  certificate on the next poll, share served again; CRL generation stays a
  Go-API operation executed on demand (the flow generates through a CA
  service over a second connection to the app's database), while the CRL
  fetch leg is genuinely HTTP (`pki_getAuthorityCrl`), parsed and
  signature-checked with the standard library the way an external verifier
  would. The tamper leg corrupts the output's stored bytes on disk (the
  object store's own file, reached through `cfg.ObjectStoreRoot` +
  `storage.ObjectKey`'s layout) rather than touching any row: the gate's
  live-digest comparison is what refuses, proving the check runs over the
  bytes being served. A failed attestation is logged and swallowed at the
  observation site; the output then refuses at the sharing gate until a
  later observation retries, so nothing silently bypasses. The demo
  journey needs no new permission or role: the pki HTTP operations sit
  behind the pki entry of the reference app's route table (`DemoRouteRules`,
  `pkiPermissionFor` with `pkiSubjectResolverFor`), gated on
  `pki:read` and `pki:revoke_certificate` in the tenant domain, which the
  demo owner role holds.

**The one API addition the integration needed.** Nothing could sign with
an issued certificate's key. `CAService.SignCertificate` (sign.go) fills
that: tenant context required, a revoked row and a revoked chain member
refused with the coded `ErrCertificateRevoked` through the SAME shared
`walkAuthorityChain` verification uses (no second hand-copy of the refusal
loop), a certificate outside its validity window refused at the service
clock with an uncoded error (the module's expiry-not-encoded convention),
and a non-coded `Signer.Sign` failure wrapped as `ErrSignerUnavailable`
exactly as `GenerateCRL` wraps one. No other public API changed. The
integration changed this layer by exactly that one additive method, so the
no-consumer exemption's three compensating obligations resolve as follows:

1. **The godoc `Example` obligation is retained with a narrowed
   narrative** -- a compiled-and-run example set remains the module's
   cheapest always-true consumer proof, and `example_test.go` carries
   `ExampleCAService_SignCertificate` (issue -> sign -> verify against the
   leaf's own public key -> signing refused with `ErrCertificateRevoked`
   after revocation) alongside the examples that cover the layer's other
   main paths (`Example`'s root -> intermediate -> end-entity chain,
   `ExampleCAService_GenerateCRL`'s revocation path,
   `ExampleCAService_ExportAuthorityChainJWKS`, and the key-lifecycle and
   `SignerRegistry` examples).
2. **The "unverified by any real consumer" obligation is closed.** The app
   issues, signs with, verifies, revokes and CRL-publishes real
   certificates over the composed stack; only the residual list below
   remains exercised by the module's own tests alone. Module side,
   `sign_test.go` pins `SignCertificate`'s contract (sign-and-verify
   against the leaf key, tenant required, not found, revoked row, revoked
   chain member, outside-window refusals at both ends with the clock hook,
   message-exactness); app side, `internal/attestation`'s unit suite
   (`store_test.go` tenant isolation and upsert arbitration,
   `message_test.go` canonical message + gate-stage refusals) and the two
   composed flow tests above run over the real composed stack.
3. **The "API may be broken by the first consumer" exemption is narrowed
   to the residual surface below.** What remains unconsumed is listed
   precisely there; the API-stability sentence covers only that surface,
   and the layer's public API is not yet held to the key-lifecycle
   layer's frozen standard.

**The precisely residual unconsumed surface** (each item is what a future
integration may still change freely, and the reason it stays out):

- **The two JWKS exports** (`CAService.ExportAuthorityChainJWKS` and the
  HTTP `pki_getAuthorityJwks`/`pki_getKeyJwks` reads) have no caller: the
  app's external verifier needs no JWKS because the AI-output gate and the
  CRL verifier both use the raw certificates and documents directly.
- **The CRLDP extension path**: the app's authorities carry no
  `CRLDistributionPoint` (the app has no stable public origin URL to
  declare), so `CAParams.CRLDistributionPoint`'s
  embedding machinery stays unexercised by a real certificate.
- **`EnqueueCRLRegenerate` has no reader in this app's verifier path**:
  the app's verifier path is row-state + chain verification and the flow
  generates CRLs on demand through the Go API and fetches them over the
  HTTP read operation. The module still declares the CRL-regeneration
  schedule on the registry alongside its handler (both pki tasks are
  platform-scope declarations), so a host running a `jobs.Scheduler` --
  this app's host scheduler included -- regenerates every authority's CRL
  at the declared window; a host that must not is a host that starts no
  scheduler.
- **Expiry-driven lifecycle for `pki_authorities`/`pki_certificates`
  stays unbuilt**: the attestation certificates carry a real 365-day
  validity and an expired certificate's outputs stop being shareable, so
  a renewal or expiry-warning mechanism would serve a concrete waiting
  object; it does not exist.
- **Authority revocation** (`AuthorityStatusRevoked`) has no writing
  method; the app's chain-verification refusals around it are exercised
  through the module's own directly-seeded tests.

**The key-lifecycle layer (`Service`, `Signer`, `LocalSigner`) never had
this exception.** It has a real, if indirect, consumer: `authn` consumes
it through `KeySource`, and the reference app assembles `authn`. Its public
API is held to the ordinary frozen-API standard -- including
`PromoteNow`, `ReclaimRetired` and `ExportJWKS`, even though none of
the three has a real caller yet (RevokeSigningKey does: the HTTP
`PkiRevokeSigningKey` handler calls it, driven over the wire by
`examples/reference-app/flowtests/pki_revoke_gate_flow_test.go`): they
extend an already-frozen type (`Service`), not a still-exempt one
(`CAService`), so the same discipline that governs
`EnsurePurpose`/`ActiveSigner`/`VerificationKeys` governs these too.

## HTTP surface

`go/pki/api/openapi.yaml` is this module's OpenAPI fragment, covering exactly the five operations under `/api/v1/pki`: `pki_revokeSigningKey`, `pki_revokeCertificate`, `pki_getKeyJwks`, `pki_getAuthorityJwks`, `pki_getAuthorityCrl`. The module's Go-only surface (CA/certificate issuance, `EnsurePurpose`/`ActiveSigner`/`VerificationKeys`) stays Go-only; nothing in this fragment re-exposes it. Generated by the same pinned oapi-codegen v2.8.0 the other fragments use, into a committed `pki-server.gen.go`; regeneration is deterministic (a second `-config oapi-codegen.yaml openapi.yaml` run diffs empty against the committed file). `Handler` (`handler.go`) implements the generated `api.ServerInterface` behind a `var _ api.ServerInterface = (*Handler)(nil)` compile-time assertion, and `Module.OpenAPISpec()`/`Register`'s `reg.RoutesSeat().Mount(apiPath, m.handler)` mount exactly one route at `apiPath`.

**Tenant context is read only where the underlying table needs it.** Unlike every other module's HTTP surface, this one spans two data domains: only `PkiRevokeCertificate` reads the caller's tenant from the request context (`pkgcore.MustTenantFromContext`, never a request parameter/header/body) because `pki_certificates` is the one tenant-scoped table this module has. The other four operations (signing-key revoke, both JWKS exports, the CRL fetch) touch only platform data (`pki_signing_keys`, `pki_authorities`) and never resolve a tenant at all -- a request to one of them succeeds under any tenant, or none, exactly as the underlying repository call would.

**Each operation's permission gate and its evaluation domain are fixed -- a host gate must not improvise either.** This Handler performs no permission check of its own (enforcement belongs to the host's rbac gate, the same division every other module documents), but which permission gates which operation, and in which domain, is part of the module's contract: `PkiRevokeSigningKey` is gated on `pki:revoke_signing_key` evaluated under the PLATFORM domain (`rbac.SystemDomain`), NEVER in the request tenant's domain -- the tenant is absent from the operation's DATA access (the row has no tenant column) and yet its permission must still be evaluated in the platform domain, or a single tenant's grant reaches every tenant's tokens; `PkiRevokeCertificate` is gated on `pki:revoke_certificate` evaluated in the request's own tenant domain; the three reads (both JWKS exports and the CRL fetch) serve platform public-key material and are gated on `pki:read`. `examples/reference-app`'s gate implements exactly this shape (the pki entry of `DemoRouteRules`: `pkiPermissionFor`/`pkiSubjectResolverFor`, internal/app/demo/demo_subject.go -- the subject resolver pins the signing-key revoke's tenant to `rbac.SystemDomain`, the same domain shift `go/admin`'s `adminSubjectResolver` makes for every `admin:*` permission), and `TestBuildServer_PkiSigningKeyRevoke_RequiresThePlatformDomainPermission` pins the boundary through the composed HTTP stack: a tenant-domain holder of the permission (the demo owner role in tenant-acme) is refused 403 while platform staff under SystemDomain succeeds. See module.go's permission const block and handler.go's `Handler` doc comment for the same table in code form.

**Audit recording happens at the HTTP boundary, not inside the Go API.** `Handler.recordAudit` calls `audit.Emit` after `Service.RevokeSigningKey`/`CAService.RevokeCertificate` has already committed -- the identical placement and identical reasoning `examples/reference-app/internal/notes/handler.go`'s `recordNoteCreatedAudit` documents (a same-SQLite-connection deadlock hazard if the write-capture plugin instead shared the business write's own transaction). This keeps `revocation.go` itself free of an `audit.Emit`/`go/dbkit/audit` dependency it does not otherwise need: a caller of the Go API directly (bypassing HTTP) gets the state transition, the cache invalidation and the published event, but not an audit row, unless it records one itself.

**The reference app consumes this surface's tenant-domain operations; the three platform-domain reads have no caller.** The X.509 layer's real consumer (the section above) drives `pki_revokeCertificate` and `pki_getAuthorityCrl` over the wire in `flowtests/attestation_flow_test.go` (the signing-key revoke operation is driven by `flowtests/pki_revoke_gate_flow_test.go`); the two JWKS read operations remain the only HTTP operations no caller exercises. The fragment IS in the API-contract pipeline's regeneration steps: `Taskfile.yml`'s `api:gen` task runs oapi-codegen over it, `.github/workflows/api-contract.yml` regenerates and porcelain-gates the committed `pki-server.gen.go` (`git status --porcelain --untracked-files=all`) exactly like every other fragment's, and the fragment universe is single-sourced in `tools/api_fragments.json` (drift-gated by `tools/check_api_fragments.py`), where pki is a registered member. CI builds and tests this module on every PR (`fast-check.yml`'s standard per-module matrix, which compiles `handler.go` against the committed `pki-server.gen.go` and would fail if they drifted structurally).

## Known limitations

- **`SignerRegistry` and `pkgcore.KeyNeverLeavesBoundary`.** `SignerRegistry` (`signer_registry.go`) is a package-level `pkgcore.SeamRegistry[Signer]` carrying `"signer.local"` (`LocalSigner`, `Capabilities: 0`) from this package's own `init()`, plus whatever names a host has blank-imported (`go/pki/signer/vault`'s `"signer.vault"`/`"signer.vault-direct"`, `go/pki/signer/kmsaws`'s `"signer.aws-kms"`/`"signer.aws-kms-direct"`) — every one of those names is also a `pkgcore.Component` (see the component section above), so a composition configuration selects the same names the registry resolves, with the same capability declarations. `Module.WithSigner(name string, signer Signer)` is kept alongside it as the escape hatch for a caller that already holds a concrete `Signer` value -- both exist simultaneously by design, the identical shape `pkgcore` itself keeps direct injection (`Put` into the by-type context) alongside the name-based registries; see "Signer providers: `vault` and `kmsaws`" above for the full rationale, including why `"signer.local"`'s own registry entry opens an independent database connection from `pkgcore.Config` rather than sharing a `Module`'s `db` (`signer_registry.go`'s `localSignerFromConfig` doc comment). `KeyNeverLeavesBoundary` is declared in `go/pkgcore/capability.go`, following the exact pattern of `MultiReplicaSafe`/`SurvivesRestart`/`Stateless`; `LocalSigner` does not have it, and `vault`/`kmsaws` have it only in `ModeDirectSign`.
- **`KeyNeverLeavesBoundary` is enforced at the registry-resolution point (`BuildSignerRequiring`), and only there.** The assembly resolves and validates capabilities for every selected component at construction time (`validateComponentCapabilities`, `go/pkgcore/component_assembly.go`); it has no knowledge of `pki.SignerRegistry` or `pki.Signer`. The `pki`-local check is `signer_registry.go`'s `BuildSignerRequiring(name, cfg, required)`: a host that intends to require a capability of the signer it wires resolves through it instead of `SignerRegistry.Build`, and a resolution whose registration lacks a required bit is refused with an error wrapping `pkgcore.ErrCapabilityUnsatisfied`, naming the signer and the missing capability -- the wiring mistake of resolving `vault`/`kmsaws` in envelope mode where direct-sign was meant, or `signer.local` where a boundary-keeping provider was meant, now fails at the resolution point when the host declares the requirement. Two residuals are recorded rather than hidden: `Module.WithSigner` takes no requirement parameter, because a directly injected `Signer` value carries no capability declaration for anything to compare -- a host that requires the boundary of an injected signer must have obtained it through `BuildSignerRequiring` -- and a host that never declares a requirement gets no check, exactly as with the four built-in modules' deployment-mode declarations.
- **The X.509 layer has a real consumer, and only the precisely residual surface above is not frozen.** See "X.509 layer: real consumer, precise residuals" above for what the reference app's attestation layer exercises and the exact list of what it does not (the JWKS exports, the CRLDP embedding path, CRL-regeneration scheduling, expiry-driven authority/certificate lifecycle). `CAService`'s current shape is a real consumer's shape; the residual items listed there are the ones a future integration may still change freely.
- **The PostgreSQL integration tier covers the migration-dedupe regression, and everything else is proven against SQLite only.** The tier is `go/pki/integration_test/postgres_migration_dedupe_test.go` (run as `go test -tags=integration ./integration_test/...` from the module directory against a real PostgreSQL 16 server started with testcontainers -- `go/pki/internal/testutil.NewPostgres`), proving migration 0008's duplicate-ledger upgrade on the second dialect (see "Migration 0008's in-place duplicate-ledger dedupe" below); it runs in `full-check.yml`'s integration-tiers matrix. The tier covers that one regression; everything else -- migration 0006's five CRL columns on `pki_authorities`, the `pki_certificate_revocations` table (migration 0007), migration 0009's `VARCHAR(4096)` widening, and the CRL-signature round trip (`crl_test.go`'s `x509.RevocationList.CheckSignatureFrom` proof) among them -- is proven against SQLite only, and dual-dialect migrations-from-zero plus the isolation suites are not re-run against the real server.
- **`ErrSignerUnavailable`'s triggers are CRL signing and the `kmsaws` direct-sign path.** `crl.go`'s `GenerateCRL` raises it by wrapping ANY non-`*apperr.Error` failure from `x509.CreateRevocationList` this way, including the library's own template-validation errors -- an imprecision accepted because this module's own callers never produce an invalid template. `kmsaws`'s `signDirect` also answers it for a KMS `Sign` response carrying no `Signature` field -- a signing backend that did not actually sign (the fail-closed semantics bullet in "Signer providers" above and the module contract sentence in `go/pki/signer.go`). `vault`'s own missing-`signature`-field answer remains an unwrapped `fmt.Errorf`. See errors.go's own doc comment for the full accounting.
- **`Service.PromoteNow` is not itself revocation.** It exists as a companion to `RevokeSigningKey` (an emergency revocation leaves a purpose with no active key until something is promoted) but performs no revocation of its own, and nothing in this module ever calls it automatically -- a host must call it explicitly. See `lifecycle.go`'s own doc comment for why it lives next to `PromoteDuePending` rather than in `revocation.go`, and for why it honors, rather than bypasses, the propagation window.
- **`Service.ReclaimRetired` is host-invoked and never automatic, and its report must be read through each signer's own `Destroy` semantics.** It is deliberately NOT wired into `ScanExpiry` or the expiry-scan job -- for the `vault`/`kmsaws` direct-sign modes `Destroy` is real provider-side deletion, and the scan's "never pushes to any external system" boundary (lifecycle.go) holds for deletion too. A host "enables reclamation" by calling the method on its own schedule; its schedule IS its retention declaration. The report's `Destroyed` list means "`Destroy` answered nil" -- which for `LocalSigner` is a physically deleted `pki_local_keys` row, for direct-sign modes a scheduled/performed provider deletion, and for envelope modes a validation no-op that reclaims nothing (the ciphertext in the row IS the material; dropping the row is a host history decision per the module's own recorded boundary). `ErrKeyNotFound` counts as already-reclaimed (`Destroyed`, quiet convergence); `revoked` keys are deliberately never reclaimed (the emergency path must not silently bundle deletion); a host wanting a revoked key's material gone calls its signer's `Destroy` directly. Full argument in `reclaim.go`'s doc comment and in "Reclaiming retired keys' material" below.
- **`Service.EnqueueExpiryScan` carries a window-scoped idempotency key, sized against the host scheduler's interval.** Each enqueue names the `DefaultExpiryScanWindow` window (one hour; `jobs.ScheduleWindowStart`) its clock read falls in, so a multi-replica scheduler's same-window enqueues collapse into one job and a later window's enqueue runs the scan again. The window is the module's answer to the two wrong extremes: no key at all (each tick its own independent job, so N replicas at a 1-minute cadence fire N redundant scans a minute) and a window-less constant key (exactly one scan per database file, since jobs' idempotency resolves one key forever on StandaloneQueue). A window of one hour against the reference host's one-minute tick is a 60:1 ratio; a host whose scheduler interval approaches the window must widen it through `WithExpiryScanWindow` (`DefaultExpiryScanWindow`'s doc comment and the module option say so), or every tick lands in a fresh window and the dedup is void. See `job.go`'s own doc comment for the full argument, and `enqueue_window_test.go` for the collapse/later-window/boundary proofs against a real `StandaloneQueue`.
- **`platformScanTenantID` is a deliberate accommodation, not a design pki would have chosen.** `jobs.Task.Validate` requires a non-empty `TenantID` unconditionally, but `pki_signing_keys` is platform data with no tenant to put there -- every other module's periodic task (e.g. `go/storage`'s `storage.taskTypeExpirySweep`) has a real one because its scanned data is tenant data. A fixed sentinel value exists purely to satisfy `jobs`' own validation; the registered scan handler never reads it, since `SigningKeyRepository` is a plain `*gorm.DB` with no tenant-filtering plugin engaged. See `job.go`'s own doc comment.
- **The real host scheduling the expiry scan is `examples/reference-app`.** The app's host-side scheduler (`examples/reference-app/internal/app/server.go`'s `BuildServer`, over `reg.Schedules` with the host's configured-tenants-∪-D3-ledger universe as the lister) runs every declared schedule on the cadence `cfg.PeriodicTaskInterval` (one minute by default, `jobs.DefaultScheduleInterval`), started and stopped with the queue worker (the same `cfg.DisableQueueWorker` gate). The declared enqueues are window-scoped (the bullet above), so on this app's StandaloneQueue the scan runs at most once per `DefaultExpiryScanWindow` window -- per-minute ticks collapse into the hour's one job -- which is all the day-scale rotation cadence needs (the 30-day `DefaultRenewalLeadTime` against a one-year default validity leaves an hour of scan latency invisible). The rotation flow test compresses the window below its own one-second tick cadence (`cfg.PKIExpiryScanWindow`) precisely so each test tick lands in a fresh window and the proof can observe a stage and a promotion on consecutive ticks; the window semantics themselves are proven in the module (`enqueue_window_test.go`), not re-proven here. The reference app is what makes the scan genuinely scheduled in a real host: without these enqueues, the boot key authn's `KeySource` consumption signs with would age out of its rotation policy with nobody ever staging its replacement. The end-to-end proof is `TestBuildServer_PeriodicScheduler_PKIExpiryScan_RotatesBootKey` (`examples/reference-app/flowtests/periodic_pki_scan_flow_test.go`): through real ticks, a real `StandaloneQueue` drain and the real registered scan handler, the purpose's boot key (created lazily by authn's first token issue through `KeySource`) is staged over by a pending successor and promoted away to `retiring`, observed through a second connection to the app's SQLite file, with the rotated purpose still signing and verifying real tokens over the wire afterward.
- **The same host also runs pki's CRL-regeneration schedule, even though its verifier path never reads a CRL.** `pki.Module.Register` declares both tasks on the `pkgcore.ComponentRegistry.Schedules` seat alongside their handlers whenever the module is wired with a queue, and this host wires `pki.WithQueue` and starts a scheduler -- declaring means scheduled, so the registered CRL-regeneration handler really receives a task every declared window (one `DefaultCRLRegenerateWindow`), regenerating every authority's CRL. The app's AI-output gate and its CRL verifier read ROW STATE plus the certificate chain (`VerifyCertificate` refuses a revoked row directly) and the attestation flow generates CRLs on demand through the Go API, so the periodic regeneration's output has no reader in this app; it is a cost of the module owning its default schedule, and the host's lever is whether it starts a scheduler at all. A host with an external CRL reader (one that declared a `CRLDistributionPoint` on the certificates it issues, which the reference app also does not) gets the same schedule with no wiring of its own.
- **No `Algorithm`-mismatch detection on rotation.** `Service.EnsurePurpose` does not verify that an already-active key's `Algorithm` matches the requested one on a repeated call -- a repeated call with a different algorithm for the same purpose silently keeps the first key (see "`Service`: the key-lifecycle layer's public shape" above). It is safe today only because no code path does it; the call's own doc comment records the open question of what a mismatch should mean. The module's own rotation cannot create the mismatch: `lifecycle.go`'s staging derives the successor's `Algorithm` from the row it replaces (`active.Algorithm`), so only a caller changing its argument between calls can reach the silent-keep path.

## Adjudications a reviewer should not "correct"

**pki is not part of `saasctl new`'s `--with` selection set, and never appears as an independent selection.** `pki` follows `authn` rather than being independently selectable: every `authn`-containing selection's go.mod requires pki, since the generated server wires pki's `Service` as authn's `KeySource`. That wiring lives in `go/saasctl`'s templates and in authn's own module wiring, not in this module -- but a reviewer should not expect a `pki` entry in `go/saasctl`'s `--with` universe.

**`pki_authorities`/`pki_certificates` are not linked by a foreign key**, even though `Certificate.AuthorityID` names an `Authority` row. Cross-module foreign keys are forbidden in this codebase; here the two tables additionally sit in different data domains (platform vs. tenant), so a single FK constraint could not express the boundary correctly even if the module-boundary rule did not already forbid it.

**Serial numbers are 16 bytes of `crypto/rand`, not validated for global uniqueness across independent CAs.** A collision is cryptographically negligible (2^128 space) and is not the failure mode the diagnosed system actually had -- that system used millisecond timestamps, which collide constantly under concurrent issuance from a single CA. No uniqueness constraint exists on `serial`: `CertificateRevocationRepository.ListByAuthority`'s query shape keys on `authority_id`, not `serial`, so the constraint is not needed -- a reviewer should not treat its absence as an oversight.

**`pki:rotate` is declared with no HTTP operation gating it yet, and that is deliberate, not an omission.** The capability `pki:rotate` names is real and already running (the expiry scan, and `Service.PromoteNow`), just not exposed as a permission-gated manual trigger -- see module.go's own doc comment on `PermissionRotate` for why declaring it is not the "prepare for later" that would be refused for a genuinely nonexistent capability. The unsplit `pki:revoke` name is declared by no one; rbac's attach-time catalog freeze refuses a grant of it.

**`ErrSignerUnavailable`'s real triggers are `GenerateCRL` wrapping ANY non-coded `Signer.Sign` failure and the `kmsaws` direct-sign missing-`Signature` answer, not specifically a KMS-backed provider's network fault.** This is recorded, not hidden, in errors.go's own doc comment and in "Known limitations" above -- a reviewer should not "fix" this by narrowing the wrap to a specific error type without first checking whether the narrower shape genuinely fits every `Signer` implementation's failure modes, `LocalSigner`'s included.

## Certificate revocation is ledger-arbitrated

A revocation of one certificate is two database writes that must agree about when and why it happened: the `pki_certificates` row's transition to revoked and the `pki_certificate_revocations` ledger row. Both writes are guarded, database-arbitrated single-winner statements, so exactly one winning call among any number of concurrent revokes of the same certificate commits each of them, and a loser can never write its own reason and timestamp over the winner's committed row:

- **The certificate-row transition is a guarded conditional UPDATE.** `CertificateRepository.RevokeIfActive` (repository.go) -- a method on the module's dual-hold repository shape (`*dbkit.Repository[T]` plus the same-connection `*gorm.DB`, the shape `go/notification`'s `VerifiedContactRepository` documents for its own conditional updates) -- is one conditional `UPDATE` matching only a row still active, returning `RowsAffected`: exactly one racing call's statement matches and commits, and a loser's matches zero rows. `RowsAffected == 0` does not distinguish missing from already-revoked -- `FindByID` answers the former; the tenant filter is the dbkit isolation plugin's injection, never hand-written (`RevokeIfActive`'s own doc comment records the full contract).
- **The ledger insert arbitrates too.** `CertificateRevocationRepository.InsertIfAbsent` (repository.go) is an `INSERT ... ON CONFLICT (certificate_id) DO NOTHING` whose `RowsAffected` verdict names exactly one winning call among any number of concurrent revokes of the same certificate. Only the winner publishes `EventCertificateRevoked` (row-then-event), and the returned bool of `RevokeCertificate` reports whether THIS call won that arbitration -- exactly one concurrent call reports `true` under every interleaving. `Create` is retained alongside `InsertIfAbsent` for callers that want a duplicate to fail; nothing in the revocation path calls it.
- **The uniqueness constraint is real DDL.** Migration `0008` (both dialect directories, same name and order) creates `uq_pki_certificate_revocations_certificate` and drops the non-unique `idx_pki_certificate_revocations_certificate_id`, which no query references (CRL generation reads by `authority_id`). Migration 0008's in-place dedupe for databases that predate the constraint is described in "Migration 0008's in-place duplicate-ledger dedupe" below.
- **Between the two guarded writes the certificate row and its ledger row can never disagree**: every ledger payload is built from values the certificate row already held committed -- the transition winner's own write, or the re-read every other path takes.
- **A failed ledger insert is an error, never log-and-forget.** The error is returned wrapped with the facts a retrying caller needs: the certificate is already revoked, its ledger row is missing, and retrying `RevokeCertificate` reconstructs the row. The handler layer maps it to `pki.internal_error` (500) like any other uncoded failure.
- **Retry completes the revocation.** Revoking an already-revoked certificate is not a bare early-return no-op: the reconciliation path still attempts the idempotent insert, repairs a genuinely missing row, publishes the one event the failed call could not, and reports `true`. An existing row no-ops the insert and reports `(false, nil)`. A call whose UPDATE matched zero rows re-reads the committed row and falls through to the same reconciliation path: it only supplements the ledger write, from the committed row's own `RevokedAt`/`RevocationReason`, never from the retry's reason argument, so history is never rewritten. The one unrepaired window left is a crash between the two statements: bounded staleness (a CRL omits one serial until the next revoke repairs the row), never an incorrect "not revoked".

`revocation.go`'s `RevokeCertificate` doc comment and `model.go`'s `CertificateRevocation` doc comment describe the arbitrated transition, the retry/reconciliation contract and the error contract.

Tests: a concurrent double-revoke test (goroutines released through a channel barrier, no sleeps) asserts exactly one ledger row, one event, one `true` winner and revoked status across 25 trials; a ledger-write-failure test (failure injected by a SQLite trigger on the test's own handle) asserts a returned error, zero events, and a retry that converges to exactly one row, one event and `(true, nil)`; a sequential idempotent re-revoke pin; and a repository-level proof that the unique constraint is database-enforced. A reason-identical double-revoke race cannot see a loser's blind overwrite (a loser carrying the same reason writes an indistinguishable row), which is why the different-reasons variant exists: `TestCAService_RevokeCertificate_ConcurrentDifferentReasons_CertificateAndLedgerNeverDisagree` (revocation_test.go) releases eight goroutines, each carrying its own reason, through the same channel-barrier harness across 25 trials, and asserts the certificate row and the ledger row agree with each other and with the single event.

## Issuance and CRL-persistence guards

**Issuance never signs under a revoked authority.** `CreateIntermediateCA`/`IssueCertificate` check the signing authority's revocation state -- the same `Authority`-row `Status` column the verification path trusts as its source of truth -- after the `FindByID` load and before any key is generated, and refuse with the coded error `ErrAuthorityRevoked` (`pki.authority_revoked`, `Conflict`, localized in both bundles) when the authority is revoked. The check covers the whole chain, not just the direct authority (see "Issuance refusal walks the whole chain" below): a revoked issuer (a compromised key) must not keep minting certificates every downstream verifier rejects.

**CRL persistence is CAS-arbitrated.** `GenerateCRL` persists through `AuthorityRepository.UpdateCRLIfCurrent`, ONE guarded conditional UPDATE matching only a row whose `CRLNumber` still equals the number the call read and writing only the four CRL columns -- a blind full-row save of a read-modify-write cycle would let two overlapping calls both read `CRLNumber` N, both sign a document numbered N+1, and the loser's save silently overwrite the winner's committed row. A call that loses the CAS re-reads and regenerates at the winner's number (loop bounded by `maxGenerateCRLAttempts`, 16). Every successful call advances the register by exactly one however many calls overlap, and the guarded write can never resurrect stale non-CRL columns over a concurrent writer's committed row. The concurrent eight-goroutine proof across 25 trials asserts final `CRLNumber` exactly initial+8, no errors, and the stored document's embedded `Number` agreeing with the column; `TestAuthorityRepository_UpdateCRLIfCurrent_GuardedTransition` pins the guard's semantics (a stale expected number lands nothing and leaves the winner's row untouched).

Two adjacent decisions are recorded elsewhere in this file: migration 0009's widening of the three `key_ref` columns to `VARCHAR(4096)` (see "Data model"), and the host-invoked shape of key-material destruction (`Service.ReclaimRetired`, below) as the answer to the fact that an expiry scan stopping at `retired` would otherwise leave underlying key material -- `LocalSigner`'s encrypted `pki_local_keys` rows in particular -- accumulating forever. Auto-destroy wired into the `retiring -> retired` transition is a lifecycle-policy decision, not a wiring detail: for the `vault`/`kmsaws` direct-sign providers `Destroy` triggers REAL provider-side deletion (KMS's seven-day minimum pending window among them), and the module's lifecycle vocabulary has no post-retired state an auto-destroy could consult before acting across every `Signer` implementation, future ones included. Nothing in this module leaks private key material meanwhile: the rows stay encrypted at rest.

## Reclaiming retired keys' material

**The decision: host-facing reclaim -- never automatic.** `Service.ReclaimRetired(ctx)` walks every `SigningKeyStatusRetired` row whose `SignerName` equals this Service's own and calls the signer's `Destroy` on its `KeyRef`, returning a `ReclaimReport` (`Destroyed` / `NotOwned` / `Failed`, nil-when-empty like `ScanReport`). It is deliberately NOT wired into `ScanExpiry` or the expiry-scan job, for the three reasons `reclaim.go`'s own doc comment develops in full:

1. **Destroy under direct-sign modes is real provider-side deletion** -- the module's "advances the state machine, never pushes to any external system" boundary (lifecycle.go's `ScanExpiry` doc) applies to deletion as much as to activation, so destruction must be an explicit host act, the same "module manages the state machine, host owns every push" division the rotation design draws.
2. **Auto-destroy and retention are per-deployment policy.** A host "enables reclamation" by calling the method on its own schedule (after each expiry-scan drain for a `LocalSigner` deployment; rarely and deliberately for a direct-sign one), and its schedule IS the retention declaration -- the module adds no configuration schema, the same reason `DefaultCacheTTL` is a named constant.
3. **The consultable boundary already exists.** The host consults the state machine itself (`retired` means the overlap elapsed and nothing under the key is still offered for verification), decides, and calls. No new state is needed for deliberate reclamation; a tombstone/pending-destruction state with a grace period does not exist -- it would be surface area with no in-repo consumer, and the module cannot in principle certify per-mode destruction at the `Signer` interface level (an envelope-mode `Destroy` returns nil after validating and reclaims nothing; the ciphertext row IS the material), so a module-owned "destroyed" marker would record the signer's answer, not the truth.

**The signer-name guard is load-bearing, not cosmetic.** Only rows whose `SignerName` is this Service's own are ever handed to `Destroy`; foreign rows land in `NotOwned`. `ErrKeyNotFound`-as-already-reclaimed would silently swallow a cross-owner miss (a second Service instance sharing `pki_signing_keys`), so a guard-less implementation both deletes material it does not own and reports foreign rows as converged. `TestService_ReclaimRetired_DoesNotTouchKeysOwnedByAnotherSigner` plants a retired row wearing `SignerName: "vault"` whose `KeyRef` points at a real local key, and pins that the material survives: the guard moves the row to `NotOwned` rather than destroying it.

**Convergence and isolation.** `ErrKeyNotFound` from `Destroy` counts as already reclaimed (`Destroyed`, distinct log line), so repeated calls converge quietly for implementations that answer that way; any other error is logged with the kid and lands in `Failed` without aborting the walk, and the next call re-attempts the failed key (still `retired`, material still in place).

**Deliberately not built**, each with its trigger condition:

- **`revoked` keys are not reclaimed.** Revocation is the emergency path; incident response may need the material of the very key just stopped, and an emergency action should never silently bundle deletion. A host that wants a revoked key's material gone calls its signer's `Destroy` directly.
- **No automatic destruction and no new state.** If a real consumer -- most plausibly a `vault`/`kmsaws` direct-sign deployment that wants destruction on the scan's own cadence, or one that needs repeat runs silent for providers answering an already-destroyed key with a raw error -- needs the automatic shape, it would be a per-implementation destroy capability declaration and/or a module-owned `destroyed` marker with a guarded transition, whose tests must pin the marker's semantics per mode (the module cannot certify an envelope-mode `Destroy` actually reclaimed anything -- see above) and the cache/event non-effects this module proves for the host-invoked shape.
- **No reference-app wiring.** `examples/reference-app`'s host-side periodic scheduler (which genuinely drives the expiry scan) is the natural first caller of `ReclaimRetired` for its local-signer deployment, but host-side wiring decisions live in the host: only the mechanisms the app actually consumes are scheduled (see "Known limitations" above).
- **No HTTP/audit surface.** Reclamation is a background lifecycle act like the expiry scan itself: no HTTP operation, no audit action (there is no human operator "who did it" to record -- the same reasoning `pki.key.rotate` is deliberately never declared), and no event (it changes no row; retired keys are already outside every replica's verifiable set and active pointer, so no replica cache needs to converge).

## Issuance refusal walks the whole chain

The `ErrAuthorityRevoked` check applies to the whole chain, not just the direct authority: with root R revoked but its intermediate I still `AuthorityStatusActive`, both `CreateIntermediateCA` and `IssueCertificate` under I would mint certificates that the module's own `VerifyCertificate` refuses -- the asymmetric hole of a direct-issuer-only check still open one hop up the chain. Both issuance paths apply the same status check `VerifyCertificate` applies to its whole chain, through one shared walk, `CAService.checkNoRevokedAuthorityInChain` (ca.go): starting from the direct authority the caller already loaded and following `ParentID` upward, cycle-guarded exactly like `VerifyCertificate`'s own walk (revocation.go), it refuses with `ErrAuthorityRevoked` when any chain member -- the direct authority first, then each ancestor up to the root -- is `AuthorityStatusRevoked`, so a direct-authority-only check is subsumed as the walk's first step. The returned error's `authority_id` param names the revoked row the walk actually met. Cost: one `FindByID` per ancestor per issuance, acceptable for a path that is never hot. Latent in practice (no production path sets `AuthorityStatusRevoked`; tests seed it directly), real the moment authority-revocation wiring exists. The doc comments and the error-index row state the whole-chain semantics.

**Regression tests.** `ca_test.go`'s `TestCAService_CreateIntermediateCA_RevokedRootAncestor_Refused` and `TestCAService_IssueCertificate_RevokedRootAncestor_Refused` build a root -> intermediate chain, seed the ROOT revoked through the same direct `AuthorityRepository.Update` the single-hop pair uses, and assert both issuance paths under the ACTIVE intermediate are refused with `ErrAuthorityRevoked` naming the root. The existing single-hop pair (`*_RevokedParent_Refused` / `*_RevokedAuthority_Refused`) stays green: the direct authority is the walk's first member, so those refusals are unchanged.

## Migration 0008's in-place duplicate-ledger dedupe

Migration `0008_enforce_one_ledger_row_per_certificate.sql` (both dialect copies) creates the ledger's `uq_pki_certificate_revocations_certificate` unique index. The index is only creatable when the ledger already holds one row per `certificate_id`, and a ledger written before the constraint existed can hold TWO rows for one certificate: the pre-arbitration revoke path wrote its ledger row through a check-then-act insert, so two concurrent revokes could both pass the check and both land a row. A deployment carrying such duplicates hits the upgrade failure: the `CREATE UNIQUE INDEX` fails, and because `dbkit.MigrationRegistry` applies one module's files in a single transaction, 0008 and 0009 roll back together, stranding the deployment at startup with 0008 unrecorded and no remediation path.

**The registry semantics the fix shape rests on** (read-only evidence in `go/dbkit/migrations.go`): `schema_migrations` records applied files by `(module, filename)` alone (`isApplied`/`recordApplied`) -- no content hash is stored and a recorded file is never re-executed or re-compared, so a file whose content changed after it was recorded never runs again, while a file whose module transaction failed has NO record and re-runs in full on the next boot. The 0008 file itself carries a dedupe statement before the `CREATE UNIQUE INDEX`, keeping the earliest row per `certificate_id` (by `created_at`, `id` as the deterministic tiebreak) -- the row the database-arbitrated arbitration the index provides would itself have let win. One file therefore serves BOTH deployment classes: the deployment stranded at 0008 (its rolled-back transaction left no record, so the next boot executes the dedupe, then the index, then 0009) and the deployment already past 0008 (its record makes the edited file a strict no-op). A new 0009-and-later migration cannot help the stranded class at all, since that deployment can never get past the failing 0008 to reach it. The dedupe is a no-op on a duplicate-free ledger, and `ROW_NUMBER OVER` is standard SQL both dialects support (SQLite since 3.25), so the statement is byte-identical across the two copies like the rest of the file. No change to `go/dbkit`: its semantics are the reason the fix works, not a defect.

**Regression tests**: the SQLite unit legs and the real-PostgreSQL leg (this module's `integration_test/` package, run with `-tags=integration` against a real postgres:16-alpine via testcontainers) share the scenario helpers in `go/pki/internal/testutil/migration_dedupe.go` -- see the Testing section above for what each leg seeds and asserts. An undeduped 0008 fails both legs (`duplicated key not allowed` on SQLite; `ERROR: could not create unique index ... (SQLSTATE 23505)` on PostgreSQL); the deduped file passes both, and regression (b)'s re-apply no-op passes on both sides.

## Validity at key-take time, domain-split revoke permissions, and windowed periodic-task keys

Three corrections to "the state machine's statuses alone decide a key's fate" thinking:

**Validity is enforced at key-take time, on every read path.** A signing key's `NotBefore`/`NotAfter` are enforced on every read path by one predicate, `keyInValidity` (service.go; `[NotBefore, NotAfter]`, both ends inclusive, the same boundary `crypto/x509` applies), checked at the moment each key is taken: `ActiveSigner` answers `ErrNoActiveKey` for an out-of-validity active key, `VerificationKeys` offers only in-validity keys, `ExportJWKS` publishes only in-validity keys, and `EnsurePurpose` treats an out-of-validity active key as no key at all -- revoking it (and any out-of-validity staged pending) through the ordinary guarded revoke transition and creating an in-validity replacement in the same call, so a purpose never stays dead waiting for a scan tick that may not be wired. The verify path's boundary choice is strict now-filtering, not judgment by a token's issue time -- pki never parses credentials, so the issue time is unavailable where the key is chosen; the availability cost is bounded by the rotation design (signing stops at demotion, scheduled a default 30 days before `NotAfter`), and a host whose declared `maxCredentialLifetime` approaches its renewal lead time must size the lead itself (`WithRenewalLeadTime`).

**The state-machine transitions behind the scan are single-statement database-arbitrated.** Each status mutation the scan performs is a guarded single-statement write whose WHERE clause carries the status the caller read: `PromoteToActive` demotes `previousActiveID` with `WHERE status = active` and promotes `pendingID` with `WHERE status = pending` (both inside one transaction, RowsAffected-refused), `RetireRetiring` matches `WHERE status = retiring`, `Revoke` matches `status != revoked`. There is no Go-level read-modify-write of a transitioned row that a caller blindly saves -- a concurrent loser's guarded write matches zero rows and loses cleanly -- so SQLite serialization hides nothing that PostgreSQL would expose: the arbiter is the status predicate in the statement, identical on both dialects. Pinned by `TestSigningKeyRepository_PromoteToActive_ConcurrentCalls_ExactlyOneWinner` (8 goroutines x 25 trials, exactly one winner per trial) and by `TestService_EnsurePurpose_ConcurrentHeals_OneReplacementBothSucceed`. The scan's one check-then-act that is NOT index-arbitrated is `StageDueRotations`'s exists-then-insert of a pending row (no partial unique index exists on `status = pending`), whose failure mode is a duplicated pending key under two genuinely concurrent staging passes -- an extra rotation cycle, converged by the guarded single-winner `PromoteToActive`, never a second active key or an expired key kept usable.

**The two periodic tasks carry windowed idempotency keys.** Both tasks enqueue under the key of the window their clock read falls in -- `pki.expiry_scan:<RFC3339 window start>` (job.go, through `jobs.SchedulePlatformIdempotencyKey`, `DefaultExpiryScanWindow`) and `pki.crl_regenerate:<RFC3339 window start>` (crl.go, through the same derivation, `DefaultCRLRegenerateWindow`) -- absolute-clock hour boundaries (`jobs.ScheduleWindowStart`), the exact windowed shape `go/storage`, `go/compliance` and `go/sharing` converged on for their sweeps: same-window enqueues collapse into one job, later windows run again, a dead-lettered job poisons only its own window, and the reference host's 1-minute tick against the 1-hour default window is a 60:1 ratio (a window approaching the host interval would void the dedup, which is why `WithExpiryScanWindow` exists for hosts whose cadence is wider and for the rotation flow test, which compresses the window below its own tick cadence). Keylessness would mean NO dedup at all: with N replicas at a 1-minute cadence, N concurrent expiry scans and N concurrent CRL regenerations would fire every minute -- overlapping expiry scans losing guarded transitions surface as scan errors, and each CRL regeneration would produce its own full document and advance the authority's `crl_number` register, pure wasted work and write churn. Two scans of DIFFERENT windows can still overlap in execution; the arbitration paragraph above is what makes that safe. `enqueue_window_test.go` pins all three window properties (same-window collapse, later-window re-run, boundary) for both tasks against a real `StandaloneQueue`.

**Revoke permissions are split by data domain, and the signing-key half must be evaluated in the platform domain.** No single permission can span `pki_signing_keys` (platform data) and `pki_certificates` (tenant data), because rbac evaluates every permission inside SOME tenant's scope and one name spanning the two domains is wrong in whichever single domain it is evaluated in -- a tenant-domain holder of the platform half could stop the whole deployment's token issuance. The split: `pki:revoke_signing_key` (evaluated under `rbac.SystemDomain`, NEVER the request tenant's domain -- the same domain shift `go/admin`'s `admin:*` permissions use) and `pki:revoke_certificate` (evaluated in the request tenant's own domain); the unsplit `pki:revoke` name is declared by no one, so rbac's attach-time catalog freeze refuses a grant of it. The module itself still performs no permission check (host's router gate, per module.go), but the per-operation gate table is fixed and documented in handler.go's `Handler` doc comment, in module.go's const docs and in "HTTP surface" above; `examples/reference-app`'s gate implements it for real (the pki entry of `DemoRouteRules`, internal/app/demo/demo_subject.go). An HTTP issuance surface, if one is added, must split `pki:issue` the same way before it lands.

## The authority-chain JWKS refuses revoked chains and prunes out-of-validity members

`VerifyCertificate` (revocation.go) and `ExportAuthorityChainJWKS` (jwks.go) each walk the authority chain, and the two walks must stay consistent on the properties the verification path enforces: the cycle guard and, above it, the revocation refusal. The export walks the same chain `VerifyCertificate` verifies, and for a data-plane cluster that kid-matches public keys "without a full X.509 path-validation library of its own" (the export's own documented consumer model), the export is the ONLY possible enforcement point for revocation: revoke an intermediate CA whose key leaked, and every refreshed authority-chain JWKS (GET `/api/v1/pki/authorities/{id}/jwks`, handler.go) must drop the leaked key, or data planes that had already pulled the document keep accepting signatures made with it. Validity has the same shape at lower weight (an authority past `NotAfter` must not export forever, since no expiry-driven lifecycle ever reaps the row).

**The shared walk.** The export's chain walk is not a third hand-copy: `VerifyCertificate` and `ExportAuthorityChainJWKS` share one walk, `CAService.walkAuthorityChain` (revocation.go), which loads each member, refuses an `AuthorityStatusRevoked` member with `ErrCertificateRevoked` (the same coded refusal, same `authority_id` param, before any per-caller work runs) and hands every surviving member to a per-caller `visit`. The revocation refusal lives inside the walk precisely so no future rewrite of either caller can drop it -- the walk's doc comment carries the PROTECTED-CONTRACT sentence (per the `go/integration` errors.go precedent) stating which properties the two chain walks must keep consistent, and recording the failure mode it exists to prevent. Out-of-validity members (past `NotAfter` at the service clock, judged from the parsed certificate through the shared `validityWindowCovers` boundary -- `keyInValidity` (service.go) delegates to the same predicate, so the `[NotBefore, NotAfter]` boundary is defined in exactly one place) are pruned from the export per member exactly as the key-lifecycle `ExportJWKS` excludes an expired key, while the verifier keeps refusing such chains wholesale through x509's own path validation -- the granularity difference is deliberate and stated in the protected contract, and neither path ever vouches for the out-of-validity member itself. Healthy chains export byte-unchanged. `ca.go`'s `checkNoRevokedAuthorityInChain` is deliberately still its own walk: it answers "may nothing NEW be signed under this chain" with `ErrAuthorityRevoked`, never `ErrCertificateRevoked`, and the shared walk's doc says so, so a reader sees the full map of chain walks in one place.

**Consumption note for `SigningKeyRepository.ListByPurposeAndStatuses`**: the method is CONSUMED, by three call sites matching its doc comment: `Service.ExportJWKS` (jwks.go, active+retiring), the staging step of `Service`'s rotation self-heal (service.go, pending), and the expiry scan's staging step (lifecycle.go, pending). Its comment is a complete sentence, not a fragment; the read paths it serves are the three call sites above, so no special handling is warranted.

**Regression tests**, named and pinned: `TestCAService_ExportAuthorityChainJWKS_RevokedAuthorityInChain_Refused` and `TestCAService_ExportAuthorityChainJWKS_RevokedRootAncestor_Refused` (a revoked member -- the requested authority or its root ancestor -- refuses the whole export with `ErrCertificateRevoked` naming it, the verify-side answer), `TestCAService_ExportAuthorityChainJWKS_ExcludesAuthoritiesOutsideTheirValidityWindow` (an out-of-validity member is excluded from the document at the service clock, the twin of the signing-key export's exclusion test), and `TestHandler_PkiGetAuthorityJwks_RevokedAuthorityInChain_Refused` (the HTTP fetch answers 409 `pki.certificate_revoked`). The verification-side chain tests (`VerifyCertificate`'s valid-chain, revoked-certificate and revoked-authority refusals) pass unchanged on the refactor onto the shared walk.
