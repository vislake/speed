# jobs

jobs is speed's asynchronous task queue: the `Queue`/`Task`/`Job`/`Handler` contract every deployment mode implements, `StandaloneQueue` (the standalone deployment mode's implementation — an in-process worker pool backed by a SQLite-persisted task table), and `AsynqQueue` (the distributed deployment mode's implementation — Redis via `github.com/hibiken/asynq`). It sits above `tenancy` and `observability` in the module dependency graph (`pkgcore -> dbkit / observability -> tenancy -> config / jobs -> ...`) and is itself a dependency of every module that needs to run something asynchronously: `storage` (derivative generation), `notification` (delivery + retry), `billing` (invoice generation), `ai-gateway` (generation jobs), `integration` (webhook delivery), `compliance` (retention/export jobs). See `docs/internal/07-platform-services.md`'s jobs section for the full design intent this module implements.

**Three dependencies, used for different reasons.** `observability` is used throughout (`obs.FromContext` for every log line this package emits, `otel.Meter` for the queue-depth gauge) — see `worker.go`, `standalone_queue.go`, `asynq_worker.go` and `asynq_queue.go`. `dbkit` is used only through the `*gorm.DB` a caller passes into `NewStandaloneQueue`: this package never calls `dbkit.Open` itself, and never imports `dbkit.Repository[T]` at all — see "The persistence model is platform data, not tenant data" below for why. This has no analog in `AsynqQueue` at all: it holds no `*gorm.DB` and creates no schema — its entire persistence is Redis, reached exclusively through `asynq`'s own client/server/inspector types plus this package's own thin `redis.UniversalClient`-backed cancellation-marker bookkeeping (`asynq_queue.go`). `tenancy` is a dependency only because this package's own tests use `tenancy/tenancytest.AssertNotTenantScoped`; no non-test `.go` file in this package imports it.

**`hibiken/asynq` and `redis/go-redis/v9` are direct dependencies of this module**, added specifically for `AsynqQueue` — per the design doc (`docs/internal/07-platform-services.md`: "the distributed deployment mode = Redis (`hibiken/asynq`, mature and ships its own retry/delay/scheduling/Web UI, not worth reimplementing ourselves)") and per root `CLAUDE.md`'s dependency-justification rule. An earlier revision of this file documented `go.mod` as *deliberately* carrying no `asynq` dependency "until that implementation lands" — this is that implementation landing, and this is the one dependency addition that sentence was always describing, not a violation of it. `testcontainers-go/modules/redis` is an additional dependency used **only** by `integration_test/`, gated behind the `integration` build tag — it never appears in any non-test import, and a plain `go build`/`go vet`/`go test ./...` never needs Docker or Redis. See "Testing" below for the two-tier layout this makes possible.

## Public API

### `job.go`

| Signature | Purpose |
|---|---|
| `type JobID string` | A `Job`'s identity. Generated by `Enqueue`, never caller-supplied |
| `type Status string` + `StatusPending/Running/Retrying/Succeeded/DeadLetter/Cancelled` | A `Job`'s lifecycle state. See "State transitions" below for the full diagram |
| `func (Status) Terminal() bool` | Reports `Succeeded`, `DeadLetter` or `Cancelled` — states no worker ever transitions out of |
| `type Priority int` + `PriorityLow=0/Normal=5/High=10` | Dispatch priority. Higher runs first; ties broken by `ScheduledAt` ascending in `StandaloneQueue`; mapped onto three fixed asynq queues in `AsynqQueue` (see "Distributed: AsynqQueue" below) |
| `type Result struct { Data []byte }` | A succeeded `Job`'s opaque output — a contract between the `Task`'s producer and its `Handler`, never interpreted by the queue itself |
| `type Job struct { ID, Type, TenantID, Payload, IdempotencyKey, Status, Priority, ProgressPct, ProgressMsg, Result *Result, Error, Attempts, MaxRetries, ScheduledAt, CreatedAt, UpdatedAt, StartedAt *time.Time, CompletedAt *time.Time }` | The pinned record every `Queue` implementation reports through `Get`. `Error` is cleared once `Status` becomes `Succeeded`, but is **not** cleared by `Cancel` — a `Job` cancelled after a failed attempt keeps that attempt's message for diagnostic visibility |
| `var ErrJobNotFound = apperr.NotFound("jobs.job_not_found")` | Returned by `Get`/`Cancel` for an id that does not exist, or exists under a tenant the caller cannot access — the two cases are indistinguishable on purpose (mirrors `dbkit.Repository[T].FindByID`) |

### `task.go`

| Signature | Purpose |
|---|---|
| `type Task struct { Type, TenantID pkgcore.TenantID, Payload []byte, IdempotencyKey string }` | What a caller hands `Enqueue`. `TenantID` is a field on `Task`, not resolved from `Enqueue`'s `ctx` — see "Why Task carries its own TenantID" below |
| `var ErrInvalidTask = apperr.Invalid("jobs.invalid_task")` | Returned by `Enqueue` for an empty `Type` or `TenantID`, before anything is persisted |

### `handler.go`

| Signature | Purpose |
|---|---|
| `type ProgressFn func(pct int, msg string)` | The progress-reporting callback `Handle` receives |
| `type Handler interface { Type() string; Handle(ctx, job *Job, progress ProgressFn) (Result, error) }` | Processes every `Job` of one `Task.Type`. `ctx` already carries `job.TenantID` — see "The tenant context trap" |
| `func NewHandlerFunc(jobType string, fn func(...) (Result, error)) Handler` | Adapts a plain function into a `Handler`, mirroring `http.HandlerFunc` |
| `type FailureHook interface { OnFailure(ctx, job *Job, cause error) }` | A `Handler` optionally implements this too, to run compensation once a `Job` dead-letters — see "Failure compensation stays out of this layer" |

### `queue.go`

| Signature | Purpose |
|---|---|
| `type Queue interface { Enqueue(ctx, Task, ...EnqueueOption) (JobID, error); Get(ctx, JobID) (*Job, error); Cancel(ctx, JobID) error }` | The portable, deployment-mode-independent contract. Both `StandaloneQueue` and `AsynqQueue` implement it identically — see either type's own section for why its extra methods (`RegisterHandler`, `Start`, `Close`) live outside this interface |
| `const DefaultMaxRetries = 3` / `const DefaultTimeout = 5 * time.Minute` | Applied when the matching `EnqueueOption` is omitted, by both implementations |
| `type EnqueueOption func(*enqueueOptions)` + `WithPriority` / `WithDelay` / `WithScheduledAt` / `WithMaxRetries` / `WithTimeout` | Per-`Enqueue`-call configuration, shared verbatim by both implementations (`resolveEnqueueOptions` is called by both `StandaloneQueue.Enqueue` and `AsynqQueue.Enqueue`). `WithDelay`/`WithScheduledAt` are mutually exclusive — whichever is passed last to `Enqueue` wins. A negative `WithMaxRetries` clamps to 0; a non-positive `WithTimeout` is ignored (falls back to the configured default) rather than honored literally |

## The tenant context trap

**This is the single most important thing to get right in this package**, per root `CLAUDE.md`'s "Traps Specific to This Codebase" and the backend coding standard §7, and it applies **identically to both implementations** — a Redis-backed worker consuming a task minutes or hours after `Enqueue` ran has exactly the same "the original context is long gone" problem an in-process one does, just with a different persistence layer underneath.

**StandaloneQueue.** A `Task`'s `Enqueue` call and the eventual `Handle` call that processes it run on **completely different contexts, potentially minutes or hours apart**: the `context.Context` active when `Enqueue` was called is long gone by the time a worker goroutine reads the row back out of SQLite — it was never persisted, because a `context.Context` cannot be. If a worker naively called `handler.Handle(someAmbientCtx, job, progress)` with whatever context its own dispatch loop happens to be running on, `job.TenantID` and the tenant `Handle`'s own `ctx` carries would silently disagree — or, since the dispatcher's internal loops run on a bare `context.Background()`, there would be no tenant at all, and any `dbkit.Repository[T]` call inside `Handle` would fail closed with `pkgcore.ErrNoTenant`.

**This is closed by construction, not by convention.** `worker.go`'s `jobContext(tenant pkgcore.TenantID) context.Context` is the ONE place a tenant is attached for a `Handle`/`OnFailure` call: `execute` calls it with `rec.TenantID` — the tenant recorded on the `Job` itself when it was enqueued — every single time, before applying the per-attempt timeout and calling `Handle`. No code path in `StandaloneQueue` calls `Handle` any other way.

**AsynqQueue: the same trap, a different rebuild point.** `Task.TenantID` cannot ride inside asynq's own `Task.Payload` (that field must stay exactly the caller's own opaque bytes, per `Task.Payload`'s and `Job.Payload`'s doc comments) — it rides in asynq's `Task.Headers` instead (`asynq_store.go`'s `headerTenantID`, written by `buildTaskHeaders` at `Enqueue` time). `Headers` are part of asynq's own `base.TaskMessage` and survive retries and archiving unchanged (confirmed by reading asynq's `processor.go`: every retry/archive/error-handler path reconstructs the `Task` via `NewTaskWithHeaders(msg.Type, msg.Payload, msg.Headers)`). `asynq_worker.go`'s `processTask` is the ONE place a tenant is attached for `AsynqQueue`: `handleCtx := pkgcore.WithTenant(ctx, tenantID)`, with `tenantID` read from `t.Headers()[headerTenantID]` — never from anywhere else. If that header is ever empty (never expected for a `Task` this package's own `Enqueue` created — see `errAsynqTaskMissingTenant`'s own doc comment), the attempt fails closed rather than calling `Handle` with no tenant at all.

**Why `ctx`, not a fresh `context.Background()`, is `handleCtx`'s base for `AsynqQueue` — a deliberate difference from `StandaloneQueue`'s `jobContext`.** `StandaloneQueue.jobContext` is built over `context.Background()`, explicitly NOT derived from the dispatcher's own lifecycle, so that closing the queue never abruptly cancels a `Handle` call already in flight. `AsynqQueue.processTask` instead builds `handleCtx` on top of `ctx`, the per-task `context.Context` asynq's own processor constructs fresh for every attempt (`asynqcontext.New`, scoped to exactly this one dequeue, deadline-bounded by the Task's own `Timeout`/`Deadline` options). This is not a shortcut; it is what makes two things work correctly:

- **asynq's own per-attempt timeout enforcement becomes `Handle`'s own timeout enforcement**, instead of this package reimplementing `context.WithTimeout` on top of a fresh, uncoupled context — exactly the "prefer configuring/wrapping asynq's own primitives" instruction this implementation was built under. A `Handle` call built on a *disconnected* fresh context would keep running even after asynq's processor had already decided (via `ctx.Done()`) that the attempt timed out and requeued it for retry — burning CPU/IO on work asynq itself no longer considers current.
- **`Inspector.CancelProcessing` (used by `AsynqQueue.Cancel` for an already-`Active` Job) becomes able to interrupt a real, in-flight `Handle` call**, because asynq's cancellation pub/sub mechanism cancels exactly this `ctx` (via a `map[taskID]context.CancelFunc` internal to asynq's processor), which `handleCtx` is now downstream of. This is strictly *better* than `StandaloneQueue`'s own documented "does not preempt" limitation, not a violation of it — `Queue.Cancel`'s doc comment only ever promises a running Job "is allowed to" keep executing, never that it is guaranteed to.
- Closing the *queue* (`AsynqQueue.Close`) still does not abruptly cancel an in-flight `Handle` call either way: `asynq.Server.Shutdown()` does not cancel a running attempt's `ctx` on its own — it stops pulling new tasks and, after `Config.ShutdownTimeout` elapses, requeues whatever is still active back to Redis while the orphaned goroutine keeps running to its own natural completion or per-attempt deadline. See "Close vs Shutdown" below.

**Proof, not just a promise:**
- `worker_test.go`'s `TestJobContext_*` trio proves `StandaloneQueue`'s mechanism at the unit level (see their own doc comments).
- `standalone_queue_test.go`'s `TestStandaloneQueue_RebuildsTenantContext_HandlerUsesOnlyJobTenant` proves the same guarantee end to end for `StandaloneQueue`, through a real `dbkit.Repository[T]` call.
- `integration_test/tenant_context_test.go`'s `TestRedisQueue_RebuildsTenantContext` proves the identical guarantee end to end for `AsynqQueue`, against a **real asynq.Server dequeuing from a real Redis** (via testcontainers-go) — the same real `dbkit.Repository[T]`-based technique, so both deployment modes are held to the exact same, non-tautological standard: the `Task` is enqueued from a context carrying no tenant at all, so a passing test can only be explained by the worker's own rebuild, never by anything leaking through from the call site.

**Why `Task` carries its own `TenantID` instead of `Enqueue` resolving it from `ctx`.** Unlike an HTTP request handler, `Enqueue` is legitimately called from places with no single ambient tenant — a platform-level scheduler enqueuing one cleanup `Task` per tenant in a loop, for example (`docs/internal/07-platform-services.md`'s sharing-link expiry case). This mirrors `pkgcore.Event.TenantID`'s identical design for the same reason, and is exactly as true for `AsynqQueue.Enqueue` as it is for `StandaloneQueue.Enqueue`. `Task.TenantID` is required non-empty (`ErrInvalidTask`) — every `Job` must be attributable to a tenant, unlike `Event`, which supports a zero-value tenant for genuinely system-wide facts.

## Failure compensation stays out of this layer

Per root `CLAUDE.md`'s "Asynchronous work" discipline: *"the queue offers an `OnFailure` hook; refunding credits and similar compensation belongs to the business module."* `FailureHook` (`handler.go`) is that hook, and the **entire** extent of this package's involvement in failure compensation, for **both** implementations: a `Handler` that needs to run business-specific logic once a `Job` exhausts its retries — refunding a pay-per-use credit reservation, for example — implements `OnFailure` alongside `Handle`. Neither `StandaloneQueue` nor `AsynqQueue` special-cases a `Task.Type`, knows what "refund credits" means, or contains any compensation logic of its own — that boundary is enforced by `FailureHook` simply having no more surface than `OnFailure(ctx, job, cause)`.

`StandaloneQueue.execute` calls it directly, once `completeDeadLetter` has persisted `StatusDeadLetter`. `AsynqQueue` cannot do the equivalent directly — asynq's `Handler.ProcessTask` (what `processTask` implements) has already returned by the time asynq itself decides whether an attempt's failure retries or archives — so `AsynqQueue` wires `asynq.Config.ErrorHandler` (`asynq_worker.go`'s `handleError`/`handleErrorAttempt`) instead, the only hook point asynq offers for "a Handler failed." `handleErrorAttempt` replicates asynq's own archive-vs-retry boundary (`retried >= maxRetry`, read via the same `asynq.GetRetryCount`/`GetMaxRetry` a `Handler` could call itself) purely to decide whether *this* is the terminal attempt — it schedules or persists nothing, so this is reading asynq's own documented `MaxRetry` contract, not reimplementing its retry machinery. See "Distributed: AsynqQueue" → "Dead-letter mapping" for the full reasoning and its one documented edge case.

## Observability

Every log line this package emits goes through `obs.FromContext(ctx)` (never a package-level or hand-built logger), with a constant message and `snake_case` key-value attributes — `job_id`, `job_type`, `tenant_id` (via `ctx`'s own tenant, attached automatically by `obs.FromContext` per `observability.AGENTS.md`), `attempts`, `duration_ms`, `retry_in_ms`, `error`. See `worker.go`'s `execute`, `standalone_queue.go`'s `Enqueue`, and `asynq_worker.go`'s `processTaskUncancelled`/`handleErrorAttempt`.

**`jobs.queue.depth`** is the queue-backlog gauge `docs/internal/09-observability.md`'s must-instrument table names for this module, wired by both `StandaloneQueue.Start` and `AsynqQueue.Start` via the shared `instrumentationName` constant (`standalone_queue.go`) — but with **different label sets**, and deliberately so. `StandaloneQueue.registerQueueDepthGauge` groups its SQL query by `(job_type, status)`, since a SQL `GROUP BY` can do that cheaply. `AsynqQueue.registerQueueDepthGauge` instead reports `(queue, status)`, where `queue` is one of the three fixed priority tiers (`critical`/`default`/`low`): asynq's own `Inspector.GetQueueInfo` aggregates backlog **per queue**, not per job type, and listing every pending/retry task just to count them by type on every metrics-collector scrape would be disproportionate. Both label sets are low-cardinality and neither ever includes `tenant_id`, per root `CLAUDE.md`'s Prometheus-cardinality rule — a specific tenant's backlog is still a job for structured logs and trace attributes, on both deployment modes.

**`jobs.job.duration` / `jobs.job.attempts` / `jobs.job.dead_letter`** cover the must-instrument table's remaining task-queue rows beyond backlog depth — execution duration percentiles, failure rate, retry count and dead-letter count — on `StandaloneQueue` today: `standalone_queue.go`'s `registerJobMetrics` wires a `Float64Histogram` and two `Int64Counter`s (mirroring `observability.Middleware`'s own Counter/Histogram pattern for the HTTP row of the same table), recorded by `worker.go`'s `recordJobMetrics`/`recordDeadLetter` at the exact three points `execute` already logs "job succeeded" / "job attempt failed, scheduling retry" / "job exhausted retries, moving to dead letter". All three are labeled `(job_type, status)` (`jobs.job.dead_letter` by `job_type` alone), `status` being one of `StatusSucceeded`/`StatusRetrying`/`StatusDeadLetter` — never `tenant_id`, for the identical cardinality reason `jobs.queue.depth` gives above. Failure rate and retry count are both derived from `jobs.job.attempts` by slicing on `status` rather than each getting a dedicated instrument. **`AsynqQueue` does not yet wire these three** — see Known limitations.

## The persistence model is platform data, not tenant data

This section is `StandaloneQueue`-specific; `AsynqQueue` has no GORM model, no `dbkit.Repository[T]` question, and no `tenancytest.AssertNotTenantScoped` proof to run at all — its only persistence is Redis, reached exclusively through asynq's own client/server/inspector, plus this package's own cancellation-marker keys (`asynq_queue.go`'s `cancelMarkerKey`), which are plain `redis.UniversalClient` `GET`/`SET` calls carrying no tenant-scoping mechanism of their own (they are keyed by opaque `JobID`, and every caller-facing read of them — `Get`, `Cancel` — is already downstream of `callerMayAccess`'s own tenant check against the *task's* `tenant_id` header).

`jobRecord` (`store.go`) deliberately does **not** implement `dbkit.TenantScoped` — no `GetTenantID` method, no embedded `dbkit.TenantModel`. Per `docs/internal/04-data-and-tenancy.md`'s data-domain table and `dbkit/AGENTS.md`'s "Known limitations", this makes it platform data: the dispatcher's claim query scans eligible `Job`s **across every tenant at once**, in priority order, to decide what to run next and to enforce per-tenant concurrency limits — an access pattern `dbkit.Repository[T]` cannot serve, and whose generic constraint would not even compile against a model like this. `tenant_id` is still a real, indexed column — read explicitly by the per-tenant concurrency gate and by `Queue.Get`/`Cancel`'s own access check (`callerMayAccess`, shared verbatim by `AsynqQueue`) — it is simply never auto-injected as a query filter. `store_test.go`'s `TestJobRecord_NotTenantScoped` (`tenancytest.AssertNotTenantScoped`) is the standing, CI-enforced proof of this property.

The `jobs` table itself is created imperatively (`store.go`'s `createJobsTableSQL`) rather than through `dbkit.MigrationRegistry` — an implementation detail specific to the standalone deployment mode, with no other consumer, since `AsynqQueue` creates no schema at all (asynq manages its own Redis key layout internally). The SQL is still written to be portable across both dbkit dialects, even though only SQLite is exercised — see Known limitations.

## Distributed: AsynqQueue

This section is the mapping table root `CLAUDE.md`'s "prefer configuring/wrapping [a mature dependency] correctly over reimplementing logic it already has" instruction produced: for every concern this package's contract defines, what asynq already provides natively, what needed a thin layer on top, and why. `AsynqQueue` implements the **exact same** `Queue`/`Task`/`Job`/`Handler`/`EnqueueOption` shapes `StandaloneQueue` does — nothing in this section changes any of those types.

### Task / Job / EnqueueOption → asynq primitives

| This package | asynq primitive | Notes |
|---|---|---|
| `Task.Type` | `asynq.Task`'s `typename` | Exact match, no asynq `ServeMux` prefix-routing involved — see "Why no `asynq.ServeMux`" below |
| `Task.Payload` | `asynq.Task.Payload()` | Unchanged bytes, never re-encoded — `Task.Headers` carries this package's own metadata instead (below), so `Payload` stays exactly what the caller gave `Enqueue` |
| `Task.TenantID` | `asynq.Task.Headers()["tenant_id"]` | `asynq_store.go`'s `headerTenantID`. See "The tenant context trap" above |
| `Task.IdempotencyKey` | `asynq.TaskID(...)` (client Enqueue option) + `Headers()["idempotency_key"]` | See "Idempotency" below |
| `Job.CreatedAt` | `Headers()["created_at"]` (Unix nanoseconds) | asynq's own `TaskInfo` has **no** creation-time field at all — this package supplies one via `Headers`, the only durable, retry-surviving channel asynq offers for caller metadata |
| `EnqueueOption` `WithPriority` | `asynq.Queue(name)` (one of three fixed queues) + `Config.Queues` weights | See "Priority → queue mapping" below |
| `EnqueueOption` `WithMaxRetries` | `asynq.MaxRetry(n)` | Direct pass-through |
| `EnqueueOption` `WithTimeout` | `asynq.Timeout(d)` | Direct pass-through — this is also what bounds `handleCtx`, see "The tenant context trap" above |
| `EnqueueOption` `WithDelay` / `WithScheduledAt` | `asynq.ProcessAt(resolved.scheduledAt)` | `resolveEnqueueOptions` (shared with `StandaloneQueue`) already resolves both into one absolute time; asynq itself decides Pending-vs-Scheduled from whether that time is in the future |
| `Job.Status` | `asynq.TaskState` (+ this package's own cancellation-marker overlay) | See `asynq_store.go`'s `statusFromTaskState` and "Cancel" below |
| `Job.Attempts` | `asynq.TaskInfo.Retried` (+1 in some states) | See `asynq_store.go`'s `attemptsFromTaskInfo` — **not** simply `Retried+1` in every state; its own doc comment traces the exact asynq internals (`internal/rdb`'s `Retry`/`Archive` Lua scripts) this formula is pinned against, with a table test (`asynq_store_test.go`) covering every case |
| `Job.MaxRetries` | `asynq.TaskInfo.MaxRetry` | Direct pass-through |
| `Job.Error` | `asynq.TaskInfo.LastErr` | Direct pass-through, same caveat as `StandaloneQueue`'s: operator-visible text, not a structured error |
| `Job.Result` | `asynqResultEnvelope.Data`, read out of `TaskInfo.Result` | See "Progress reporting" below |

**Always-set `asynq.Retention` on every `Enqueue` call.** This is not optional tuning — it is required for `Get()` to work at all for a succeeded `Job`. Left unset, asynq deletes a completed task's entire record the instant it succeeds; `Get()` immediately after success would then report `ErrJobNotFound` instead of `StatusSucceeded`, silently breaking the single most basic use of this package. `DefaultAsynqCompletedRetention` (24h, overridable via `WithAsynqCompletedRetention`) is how long a succeeded `Job` stays visible to `Get()` — unlike `StandaloneQueue`'s SQLite row, which is never deleted. See Known limitations.

**Why no `asynq.ServeMux`.** asynq ships a `ServeMux` for longest-prefix routing of task types to handlers — a real feature, but one this package does not need: `Task.Type` is always matched **exactly** against a registered `Handler.Type()`, mirroring `StandaloneQueue`'s own `map[string]Handler` exactly. `AsynqQueue` registers a single `asynq.HandlerFunc` (`processTask`) directly with `asynq.Server.Start`, doing its own exact-match lookup via the same `handlers` map/mutex shape `StandaloneQueue` uses (duplicated, not shared — see `tryReserveTenantSlot`'s own doc comment for why touching `StandaloneQueue`'s fields was avoided). One concrete benefit: a claimed `Job` with no registered `Handler` reports the **exact same** `ErrHandlerNotRegistered` sentinel on both deployment modes, rather than `AsynqQueue` surfacing `ServeMux`'s own `asynq.ErrHandlerNotFound` text instead (which `ServeMux`'s fixed, non-overridable `NotFoundHandler()` would have forced).

### Priority → queue mapping

asynq's native priority mechanism is **named, weighted queues** (`Config.Queues map[string]int`, e.g. `{"critical":6,"default":3,"low":1}` — asynq's own documented example ratio, used verbatim as this package's default), processed proportionally to weight while all are non-empty. This package defines exactly three fixed queue names (`asynq_store.go`: `asynqQueueCritical`/`Default`/`Low`) and maps `Priority` onto them: `>= PriorityHigh` → `critical`, `<= PriorityLow` → `low`, everything else → `default`.

**This is coarser than `StandaloneQueue`'s fully continuous `Priority` ordering**, and deliberately so: asynq's model is a small number of named queues, not a per-job numeric sort key, and a queue-per-tenant or queue-per-arbitrary-priority scheme would make every dequeue poll (which iterates the configured queue list) scale with tenant count instead of staying O(1) — see "Per-tenant concurrency limiting" below for why a queue-per-tenant scheme was rejected on the same grounds. A caller enqueuing with `Priority(7)` gets `default`, and `Get()` reports it back as `PriorityNormal` (5), not 7 — `priorityForQueue` is a many-to-one collapse's approximate inverse, not a lossless round-trip. `WithAsynqQueueWeights` overrides the three weights; it cannot add a fourth queue.

### Idempotency

`Task.IdempotencyKey`, when non-empty, becomes part of a **deterministic asynq TaskID**: `"idem:" + tenantID + ":" + idempotencyKey` (`AsynqQueue.Enqueue`). asynq's own client already refuses to enqueue a second task under a `TaskID` that still exists in any state (`asynq.ErrTaskIDConflict`) — this package's idempotency contract ("a second `Enqueue` call for the same (`TenantID`, `IdempotencyKey`) pair returns the first call's `JobID`") maps onto that native mechanism directly: on conflict, `Enqueue` looks the existing task up (`findTaskInfo`) and returns *its* ID, exactly like `StandaloneQueue`'s own unique-index-based `insertRecord` does for SQLite. Proven under genuine Redis-level concurrency (ten simultaneous `Enqueue` calls for the same key racing against real asynq/Redis, not a mock) by `integration_test/enqueue_execute_test.go`'s `TestRedisQueue_Idempotency`.

**One real difference from `StandaloneQueue`, worth stating plainly: idempotency is not permanent in the distributed deployment mode.** `StandaloneQueue`'s SQLite unique index holds forever (the row is never deleted, "regardless of what that first Job's outcome was" — `Task.IdempotencyKey`'s own doc comment). asynq's `TaskID`-conflict check only holds for as long as asynq itself still has a live record under that ID: indefinitely while Pending/Scheduled/Retry/Active, until `completedRetention` elapses once succeeded, or until evicted from asynq's own bounded-size archive once dead-lettered. A duplicate `Enqueue` call arriving after either window closes creates a **new**, independent `Job` rather than returning the original's id. See Known limitations.

### Progress reporting

`ProgressFn` calls are persisted via `asynq.Task.ResultWriter()`, a mechanism asynq documents specifically for writing result/progress data from inside a running `Handler` — `Write` can be called any number of times, each call overwriting the prior one, and the latest write is immediately visible through `Inspector.GetTaskInfo` (i.e. through `Queue.Get`) regardless of whether the task is still `Active` or has already reached a terminal state. This is exactly "configuring asynq's own primitive correctly" rather than inventing a parallel Redis structure purely for progress.

The bytes written are `asynq_store.go`'s `asynqResultEnvelope{StartedAt, ProgressPct, ProgressMsg, Data}`, JSON-encoded — one struct doing double duty as both the progress channel and the final-success-result channel, because asynq's `ResultWriter`/`TaskInfo.Result` is a single `[]byte` slot, not two. `processTaskUncancelled` writes an envelope with `StartedAt` set (and progress at its zero value) **before** calling `Handle` — read back by `Get()` as `Job.StartedAt`, mirroring `StandaloneQueue`'s `claimOne` setting `started_at` at claim time — then again on every `progress()` call, then once more on success with `Data` set to the `Handler`'s returned `Result.Data`.

**One deliberate, low-stakes difference from `StandaloneQueue`: progress resets to zero at the start of every new attempt**, rather than carrying a failed attempt's last-reported percentage forward the way `StandaloneQueue` does (`StandaloneQueue` only "carries it forward" because nothing ever resets it — no test in this package asserts on that carry-over behavior specifically). Recovering the previous envelope to preserve it across a retry would cost an extra `Inspector.GetTaskInfo` round trip on every attempt start purely to avoid a momentary 0% display during a retry — not judged worth it.

### Per-tenant concurrency limiting

**What asynq offers natively, and why neither fits:**
- **Named, weighted queues (`Config.Queues`)** — already used for `Priority` (above). Using one queue per tenant instead would make asynq's own per-poll queue iteration scale with tenant count, and a real deployment can have far more tenants than a small, fixed queue list should ever hold — rejected for the same O(1)-queue-count reason "Priority → queue mapping" gives.
- **Task grouping / `GroupAggregator`** — this is asynq's *batch aggregation* feature (combine N tasks in the same group into one before it ever reaches a `Handler`, e.g. batching notification sends), a completely different problem from limiting how many tasks belonging to one key may run **concurrently**. It offers no concurrency-limiting semantic at all, checked and rejected explicitly rather than overlooked.
- **`Config.Concurrency`** — a single global cap across every tenant and queue, the direct analog of `StandaloneQueue`'s `WithWorkerCount`. Necessary, but says nothing about how that shared pool is *distributed* across tenants.

**Conclusion: asynq has no built-in equivalent to "cap how many Jobs any one arbitrary, runtime-supplied tenant ID may run concurrently, out of a shared worker pool" — this needed a layer on top.** That layer is `asynq_worker.go`'s `tryReserveTenantSlot`/`releaseTenantSlot`: the same `map[pkgcore.TenantID]int` + `sync.Mutex` shape `StandaloneQueue.dispatchOnce` uses, but applied at a different point in the pipeline, because asynq gives this package no way to peek at a task's tenant *before* dequeuing it off Redis the way `StandaloneQueue.dispatchOnce` can peek at a claim candidate before claiming it:

- `StandaloneQueue`: an over-limit candidate is **skipped without being claimed** — it stays `StatusPending`, `Attempts` untouched, and the dispatcher moves on to the next (possibly different-tenant) candidate in the same poll.
- `AsynqQueue`: by the time `processTask` runs, asynq has **already** dequeued the task and occupied one of `Config.Concurrency`'s global slots. Blocking inside `processTask` until a tenant slot frees up was considered and rejected: it would let one tenant's flood occupy every global concurrency slot with jobs that are all merely *waiting on each other*, which is precisely the starvation scenario per-tenant limiting exists to prevent. Instead, `processTask` bounces immediately — returns `errTenantAtCapacity` without ever calling `Handle` — freeing the global slot right away for the next dequeue, functionally equivalent to `StandaloneQueue`'s "skip and move on."

**The one piece that makes a fast bounce safe rather than merely fast: `asynq.Config.IsFailure`.** A naive bounce-and-retry would consume one of the Job's `MaxRetries` on every bounce, via asynq's own `internal/rdb` `Retry` Lua script (`if isFailure { Retried++ }`, confirmed by reading it directly) — a Job could then be dead-lettered purely from contention, having never actually run. `AsynqQueue`'s `Config.IsFailure` reports `false` specifically for `errTenantAtCapacity` (`asynq_worker.go`'s `isFailure`), which the same Lua script honors by **not** incrementing `Retried` at all — so a throttled Job can bounce any number of times without ever burning into `MaxRetries`. `Config.RetryDelayFunc` (`retryDelay`) also special-cases the same error with a short, fixed, jittered delay (`WithAsynqThrottleRetryDelay`, default 200ms) instead of asynq's own exponential business-failure backoff, so a throttled tenant's backlog drains quickly once a slot frees rather than waiting out a multi-second exponential delay meant for genuine failures.

**One narrow, explicitly accepted edge case:** asynq's own archive-vs-retry decision (`retried >= maxRetry`) is evaluated *before* `IsFailure` is ever consulted (confirmed by reading `processor.go`'s `handleFailedMessage`). A bounce that happens to land exactly on what would otherwise be a Job's final allowed attempt is therefore archived immediately, same as any other failure on that attempt, rather than bounced again — a real but very narrow race, and a strictly better outcome than the alternative (removing the `retried >= maxRetry` guard entirely would let a permanently-contended Job retry forever).

Proven against a real `asynq.Server`/Redis, not a mock, by `integration_test/tenant_concurrency_test.go`'s `TestRedisQueue_PerTenantConcurrencyLimiting` — the same scenario shape as `standalone_queue_test.go`'s `TestPerTenantConcurrencyLimiting`, with `Config.Concurrency` deliberately small relative to the flood size so more than one of a flooding tenant's Jobs is dequeuable at once, the exact condition that would starve another tenant if bouncing blocked instead of returning immediately.

### Dead-letter mapping

A `Job` that exhausts its retries maps onto asynq's own **archived** state (`asynq.TaskStateArchived`) — asynq's own documented dead-letter equivalent ("archived and stored for inspection purposes"), reached automatically once asynq's own `retried >= maxRetry` check fires; this package never calls `Inspector.ArchiveTask` itself, since asynq already decides and performs this transition on its own. `AsynqQueue.DeadLetterJobs` maps onto `Inspector.ListArchivedTasks`, called once per priority queue with internal pagination (asynq's own page size default is small; this package fully drains each queue's archive rather than truncating at one page) — the direct analog of `StandaloneQueue.DeadLetterJobs`'s SQL `WHERE status = 'dead_letter'`.

**`FailureHook.OnFailure` has no direct asynq equivalent to hook into** — asynq's `Handler.ProcessTask` (`processTask`) has already returned by the time asynq itself decides an attempt's failure means archiving rather than retrying, and asynq offers no separate "task was just archived" callback. `Config.ErrorHandler` (`handleError`/`handleErrorAttempt`) is the closest available hook: it runs on **every** failed attempt, before that decision, so `handleErrorAttempt` replicates the same `retried >= maxRetry` boundary asynq's own processor uses (via `asynq.GetRetryCount`/`GetMaxRetry`, the same accessors a `Handler` itself could call) purely to recognize "this is the terminal one," then invokes `OnFailure` on a **freshly built** context (`pkgcore.WithTenant(context.Background(), tenantID)` + `q.defaultTimeout`) — never the just-failed attempt's own `ctx`, which may already be at or past its deadline — exactly mirroring `StandaloneQueue.execute`'s identical choice for the identical reason. See `asynq_worker_test.go`'s `TestAsynqQueue_HandleErrorAttempt` for the unit-level proof (every case: retries remain, retries exhausted, no handler registered, handler without `FailureHook`, a throttle bounce is never treated as dead-letter-worthy) and `integration_test/retry_dead_letter_test.go`'s `TestRedisQueue_DeadLetterAndFailureHook` for the same guarantee against a real asynq/Redis pipeline.

**Approximation accepted:** `q.defaultTimeout` stands in for the Job's own exact per-attempt timeout, which asynq's context accessors do not expose (`TaskID`/`RetryCount`/`MaxRetry`/`QueueName` only) — recovering the exact value would cost an extra `Inspector` round trip solely for this bound. A cosmetic one too: a throttle bounce still overwrites `TaskInfo.LastErr` with its own message (asynq's retry Lua script always records `LastErr`, regardless of `IsFailure`), so a Job dead-lettered by the narrow race above may show a throttle message rather than its last genuine failure's.

### Cancel

`Cancel`'s only **permanent, authoritative** effect is the cancellation marker (`asynq_queue.go`'s `writeCancelMarker`/`readCancelMarker`: a plain `redis.UniversalClient` key, `asynqjobs:cancelled:<id>`, namespaced clearly apart from every key asynq itself owns). `Get()` reports `StatusCancelled` from this marker **unconditionally**, regardless of whatever asynq's own underlying state naturally becomes — exactly mirroring `StandaloneQueue`'s `markCancelled` + its completion functions' `WHERE status = 'running'` no-op guard, which makes a still-in-flight attempt's eventual outcome unable to resurrect a cancelled Job.

**`Cancel` does NOT call `Inspector.DeleteTask` for a not-yet-running Job — this was tried and is a documented dead end, not an oversight.** `DeleteTask` removes the task's entire `TaskInfo` record; a subsequent `Get()` would then find nothing to combine the cancellation marker with, and would report `ErrJobNotFound` for a Job the caller explicitly cancelled — indistinguishable from a Job that never existed. This was a genuine bug in an earlier version of this method, caught specifically by `integration_test/cancel_test.go`'s `TestRedisQueue_Cancel_PendingJobNeverRuns` running against a real Redis (a unit test built on a hand-constructed `*asynq.TaskInfo`, never having actually exercised a real delete, could not have caught it — the concrete reason this task's own instructions required real-backend testing here rather than mocks). Instead:

1. `Cancel` leaves the task's own asynq record alone, and just writes the marker (plus, for an already-`Active` Job, a best-effort `Inspector.CancelProcessing` signal — see "The tenant context trap" above for why that can actually interrupt a running `Handle` call for `AsynqQueue`, unlike `StandaloneQueue`).
2. `processTask` checks for exactly this same marker as the very **first** thing it does, before even the handler lookup — if found, it returns `nil` without ever calling `Handle`, which asynq records as an ordinary successful completion (retained for `completedRetention`, exactly like a real success) rather than a retry or an archive.
3. `Get()`'s marker-overlay (step 0 above) then reports `StatusCancelled` for that Job regardless, using the still-fully-intact `TaskInfo` for every other field (`Type`, `Payload`, `TenantID`, etc.).

This correctly satisfies "cancelling a `StatusPending`/`StatusRetrying` Job prevents it from ever being dispatched" (`Handle` never runs) without ever breaking `Get()`'s visibility contract. The accepted cost: every dispatched task now costs one extra Redis round trip (the marker check) even when never cancelled, and asynq's own internal processed/failed counters (visible via `Inspector.GetQueueInfo` or `asynqmon`) count a cancelled-before-dispatch Job as "processed" — asynq has no third bucket for "revoked."

Cancelling an `Active` Job is proven by `integration_test/cancel_test.go`'s `TestRedisQueue_Cancel_RunningJob`: `Get()` reports `StatusCancelled` **immediately**, without waiting for the in-flight (best-effort-interrupted) `Handle` call to actually return.

### Close vs Shutdown

`AsynqQueue.Close(ctx)` keeps the same signature shape as `StandaloneQueue.Close(ctx)` for bootstrap-code ergonomics, but wraps a genuinely different underlying primitive. `asynq.Server.Shutdown()` takes no arguments at all — it waits for in-flight attempts up to `Config.ShutdownTimeout` (a **construction-time** setting, default 8s, not a per-call parameter), and if that elapses first, requeues whatever is still active back to Redis rather than waiting indefinitely; the orphaned goroutine itself is not force-cancelled (Go cannot do that) and keeps running to its own natural completion or per-attempt deadline — the exact same *shape* of behavior `StandaloneQueue.Close` documents for itself ("does not itself cancel an in-flight Handle call... waits... up to ctx's deadline"), just bounded by a value fixed at construction instead of supplied per call. `AsynqQueue.Close`'s own `ctx` parameter bounds how long *this call* waits for `Shutdown()` to finish, layered on top, not fed into asynq's own timeout.

## Retry, backoff and dead-letter

**StandaloneQueue.** A `Job`'s `Attempts` is incremented at claim time (`pending`/`retrying` → `running`), before `Handle` runs. On failure, `execute` compares `Attempts` against `MaxRetries`: `Attempts <= MaxRetries` → `StatusRetrying`, `ScheduledAt` moved forward by `backoffDelay(Attempts)` (`backoffBase * 2^(Attempts-1)`, capped at `backoffMax`); `Attempts > MaxRetries` → `StatusDeadLetter` (total attempts made = `MaxRetries + 1`), and, if the registered `Handler` also implements `FailureHook`, its `OnFailure` runs once.

**AsynqQueue.** The identical `Attempts`/`MaxRetries` arithmetic holds (see the mapping table's `attemptsFromTaskInfo` entry above and its own doc comment for the exact per-state formula), but the retry/archive **decision and the backoff delay itself are asynq's own**, not this package's: `asynq.MaxRetry` (set from `resolved.maxRetries` on every `Enqueue`) is what asynq compares its own `Retried` counter against, and `Config.RetryDelayFunc` (defaulting to `asynq.DefaultRetryDelayFunc`, an exponential Sidekiq-style formula — overridable via `WithAsynqRetryDelayFunc`) computes the delay, for every failure that is not a tenant-concurrency bounce (see "Per-tenant concurrency limiting" above). This package's own `backoffDelay`/`WithBackoff` (`worker.go`/`standalone_queue.go`) have no `AsynqQueue` equivalent by design — asynq already has a configurable backoff formula, and `WithAsynqRetryDelayFunc` is that same tuning knob shifted to asynq's own extension point rather than reimplemented.

A claimed `Job` whose `Type` has no registered `Handler` (`ErrHandlerNotRegistered`, the exact same sentinel on both deployment modes) is treated exactly like any other `Handle` failure on both — retried, then dead-lettered — rather than dropped or looped forever, so a startup-ordering mistake can resolve itself, and a genuine mismatch surfaces in `DeadLetterJobs` instead of vanishing silently.

## Typical integration

```go
db, err := dbkit.Open(ctx, dbkit.Options{Dialect: dbkit.DialectSQLite, DSN: dsn})
// handle err

queue := jobs.NewStandaloneQueue(db, jobs.WithWorkerCount(8), jobs.WithTenantConcurrencyLimit(2))
if err := queue.RegisterHandler(&ImageGenHandler{svc: svc}); err != nil {
    // handle err
}
if err := queue.Start(ctx); err != nil {
    // handle err
}
defer queue.Close(shutdownCtx)

id, err := queue.Enqueue(ctx, jobs.Task{
    Type:           "ai.generate_smile",
    TenantID:       tenant,
    Payload:        payloadBytes,
    IdempotencyKey: "smile-gen:" + requestID, // derived from the business operation, never random
}, jobs.WithPriority(jobs.PriorityHigh), jobs.WithMaxRetries(2))
```

The distributed deployment mode's equivalent — same `Task`/`EnqueueOption`s, same `Handler`, different construction (per `SPEED_DEPLOYMENT_MODE`, wired once at kernel startup, never branched on in business code — root `CLAUDE.md`'s "Deployment modes" discipline):

```go
redisOpt := asynq.RedisClientOpt{Addr: cfg.RedisAddr, Password: cfg.RedisPassword}
queue := jobs.NewAsynqQueue(redisOpt, jobs.WithAsynqConcurrency(8), jobs.WithAsynqTenantConcurrencyLimit(2))
if err := queue.RegisterHandler(&ImageGenHandler{svc: svc}); err != nil {
    // handle err
}
if err := queue.Start(ctx); err != nil {
    // handle err
}
defer queue.Close(shutdownCtx)

id, err := queue.Enqueue(ctx, jobs.Task{ /* identical to above */ }, jobs.WithPriority(jobs.PriorityHigh), jobs.WithMaxRetries(2))
```

A `Handler` implementation is identical on both deployment modes — it never knows which one it is running under:

```go
func (h *ImageGenHandler) Type() string { return "ai.generate_smile" }

func (h *ImageGenHandler) Handle(ctx context.Context, job *jobs.Job, progress jobs.ProgressFn) (jobs.Result, error) {
    // ctx already carries job.TenantID -- a dbkit.Repository[T] call here
    // needs no extra tenant plumbing of its own, on either deployment mode.
    progress(10, "starting")
    out, err := h.svc.Generate(ctx, job.Payload)
    if err != nil {
        return jobs.Result{}, err // retried, then dead-lettered -- see below
    }
    progress(100, "done")
    return jobs.Result{Data: out}, nil
}

// OnFailure runs once, only after every retry is exhausted, on either deployment mode.
func (h *ImageGenHandler) OnFailure(ctx context.Context, job *jobs.Job, cause error) {
    h.credits.Refund(ctx, job.TenantID, job.IdempotencyKey) // business compensation lives here, not in jobs
}
```

See `example_test.go`'s `Example`/`ExampleNewHandlerFunc` (compiled and run, `StandaloneQueue`) and `ExampleNewAsynqQueue` (compiled only — no `// Output:` comment, since it needs a real Redis the default test tier must not require; see that function's own doc comment) for the same shape. `integration_test/enqueue_execute_test.go`'s `TestRedisQueue_EnqueueExecuteRoundTrip` is `ExampleNewAsynqQueue`'s shape actually run end to end against a real Redis.

`isJobNotFound` (`job_test.go`) matches `ErrJobNotFound` by `.Code` via `apperr.As`, not by identity — the same discipline `dbkit`'s own `isRecordNotFound` test helpers use. `integration_test/` defines its own small equivalents locally where needed (test helpers are never part of a package's importable surface regardless of which package they live in, so nothing here is "shared" across package boundaries in violation of the backend coding standard's test-helper rule — see `dbkit/integration_test/postgres_tenant_isolation_test.go`'s identical `ctxFor`/`isRecordNotFound` precedent).

**Verified unaffected by this implementation:** every pre-existing `Demo*`/non-`Asynq*`-prefixed test in this package's default tier passes unchanged, and `demo_queue.go`/`worker.go`/`store.go` were not modified at all while building `AsynqQueue` — see this module's own commit history / the pull request that introduced this section for the `go test ./... -race -v` transcript proving it. (`demo_queue.go` was later renamed to `standalone_queue.go`, and the `DemoQueue`/`NewDemoQueue` identifiers to `StandaloneQueue`/`NewStandaloneQueue`, in a subsequent revision — this note describes the names as they stood when `AsynqQueue` was first added; the `Demo*`-prefixed test names themselves were left unchanged by that later rename.)

## Rules

- **Never call a `Handler`'s `Handle` or `OnFailure` with any context other than one carrying exactly `job.TenantID` via `pkgcore.WithTenant`.** For `StandaloneQueue` this means `jobContext(job.TenantID)` (`worker.go`'s `execute`); for `AsynqQueue` this means `pkgcore.WithTenant(ctx, tenantID)` built from `t.Headers()[headerTenantID]` (`asynq_worker.go`'s `processTaskUncancelled`/`handleErrorAttempt`). Do not "simplify" either by threading some other ambient context through instead, and do not assume any context available at a call site already carries the right tenant.
- **Do not add business-specific logic to this package**, on either deployment mode. `FailureHook` is the queue's entire failure-compensation surface — see "Failure compensation stays out of this layer".
- **Do not give `jobRecord` a `GetTenantID` method or embed `dbkit.TenantModel` into it** (`StandaloneQueue` only — see "The persistence model is platform data, not tenant data").
- **Do not use `dbkit.Repository[T]` for `jobRecord`** (`StandaloneQueue` only, same reasoning).
- **Do not persist a `context.Context`, or store one in `StandaloneQueue`'s or `AsynqQueue`'s own fields.** Each `Handle`/`OnFailure` call's context is built fresh, independent of the queue's own `Start`/`Close` lifecycle either way — see "Close vs Shutdown" for `AsynqQueue`'s version of this, and `StandaloneQueue.Close`'s own doc comment for the original.
- **Do not add a new `EnqueueOption` or change `Queue`/`Handler`/`Job`/`Task`'s shape without weighing BOTH implementations.** These are the pinned contract both `StandaloneQueue` and `AsynqQueue` satisfy — a change here is now expensive on two implementations, not one, exactly root `CLAUDE.md`'s "treat public API as frozen" concern.
- **Do not skip `tenancytest.AssertNotTenantScoped` for `jobRecord`** (`StandaloneQueue` only) because it "obviously" is not tenant-scoped.
- **Do not assume `Cancel` interrupts an already-running `Handle` call on `StandaloneQueue`.** `AsynqQueue`'s `Cancel` does best-effort attempt to, via `Inspector.CancelProcessing` — see "The tenant context trap" and "Cancel" above for why that is possible there and not on `StandaloneQueue`, and why neither is a hard guarantee.
- **Do not call `Inspector.DeleteTask` from `AsynqQueue.Cancel`.** This looks like the obvious way to stop asynq from processing a not-yet-run Job, and is wrong — see "Cancel"'s own section above for the `Get()`-breaking bug this was and the marker-plus-`processTask`-early-exit design that replaced it.
- **Do not enqueue an asynq task without `asynq.Retention` set.** Omitting it deletes a succeeded task's record immediately, breaking `Get()` for the success path — see "Task / Job / EnqueueOption → asynq primitives" above.
- **Do not let a per-tenant-concurrency bounce (`errTenantAtCapacity`) increment asynq's own retry counter.** `Config.IsFailure` reporting `false` for it is what makes an unbounded number of bounces safe — see "Per-tenant concurrency limiting" above; removing or bypassing that would reintroduce the "dead-lettered purely from contention" bug it exists to prevent.
- **Do not use `asynq.ServeMux` for handler dispatch.** This package's own exact-match `map[string]Handler` (mirroring `StandaloneQueue`'s) is what keeps `ErrHandlerNotRegistered` identical across both deployment modes — see "Why no `asynq.ServeMux`" above.
- **Do not call `handler.Handle` or `hook.OnFailure` directly from `StandaloneQueue.execute`.** Always go through `worker.go`'s `invokeHandle`/`invokeOnFailure`, which recover a panic raised inside either call into an ordinary `Handle` failure instead of letting it crash the whole worker-pool process — every tenant's in-flight and queued Jobs, not just the one that panicked. `AsynqQueue` needs no equivalent: asynq's own `processor.perform` already recovers the same call for free.
- **Do not let `StandaloneQueue.execute` call `Handle` for a `jobRecord` whose `tenant_id` column is empty.** `execute`'s dispatch `switch` checks `rec.TenantID == ""` (`errStandaloneJobMissingTenant`) as its own case, before the `default` case that calls `invokeHandle` — mirror that same shape if this is ever refactored, the way it already mirrors `AsynqQueue.processTaskUncancelled`'s `errAsynqTaskMissingTenant` check.

## Known limitations

**Shared by both deployment modes:**
- **No queue-wide, cross-`Handler` observability of `DeadLetterJobs` beyond a plain list.** No requeue-from-dead-letter API on either deployment mode, and no *caller-facing* pagination (`AsynqQueue.DeadLetterJobs` paginates internally against asynq's own `Inspector`, but still returns one flat slice).
- **`Enqueue`'s idempotency is scoped per tenant, not globally**, on both deployment modes — deliberate, not a gap (idempotency keys are business-operation identifiers meaningful within one tenant's own operations).

**`StandaloneQueue`-specific** (unchanged by this implementation):
- **`Cancel` does not preempt an in-flight `Handle` call.** See "Rules" above for the contrast with `AsynqQueue`.
- **This module's own `StandaloneQueue` tests exercise SQLite only, never `dbkit/dbtest.NewPostgres`** — there is no distributed-deployment-mode dialect of `StandaloneQueue`'s schema to verify, since the distributed deployment mode's own Queue implementation (`AsynqQueue`) has no SQL schema at all.
- **The dispatcher is a single goroutine.**

**`AsynqQueue`-specific:**
- **Only `jobs.queue.depth` is wired; `jobs.job.duration`/`jobs.job.attempts`/`jobs.job.dead_letter` (see "Observability" above) are not.** `docs/internal/09-observability.md`'s must-instrument table requires execution-duration percentiles, failure rate, retry count and dead-letter count for the task-queue domain on every deployment mode, and today only `StandaloneQueue` produces them (`worker.go`'s `recordJobMetrics`/`recordDeadLetter`); `AsynqQueue`'s `asynq_worker.go` (`processTaskUncancelled`/`handleErrorAttempt`) only logs the equivalent events structurally. This is a real, tracked gap, not a deliberate design choice — the fix is the same Counter/Histogram pattern `StandaloneQueue` now uses, recorded at the same points asynq_worker.go already logs `attempts`/`duration_ms`/`error`, and is the intended fast-follow.
- **Idempotency is bounded by asynq's own retention windows, not permanent** — see "Idempotency" above for exactly which windows and why.
- **A succeeded Job's visibility to `Get()` is bounded by `completedRetention` (default 24h), and a cancelled Job's by `cancelledRetention` (default 30 days)** — unlike `StandaloneQueue`'s SQLite rows, which are kept forever. Both are configurable (`WithAsynqCompletedRetention`/`WithAsynqCancelledRetention`) but neither can be made literally infinite without unbounded Redis growth becoming the operator's problem instead.
- **`Priority` is collapsed onto three fixed queues, not a continuous ordering** — see "Priority → queue mapping" above. `WithAsynqQueueWeights` retunes the three; it cannot add a fourth.
- **A per-tenant-concurrency bounce landing on a Job's otherwise-final allowed attempt is archived immediately rather than bounced again** — the one narrow edge case "Per-tenant concurrency limiting" above documents and accepts.
- **`jobs.queue.depth` is labeled `(queue, status)` here, `(job_type, status)` on `StandaloneQueue`** — see "Observability" above for why asynq's own `Inspector.GetQueueInfo` cannot cheaply produce the finer label.
- **A cancelled-before-dispatch Job, and a per-tenant-concurrency bounce, both show up in asynq's own internal processed/failed counters (visible via `Inspector`/`asynqmon`) under "processed" or with a stale `LastErr`, not under any dedicated bucket of their own** — asynq has none; this package's own `Job.Status`/`Job.Error` remain correct regardless (see "Cancel" and "Dead-letter mapping" above), only asynq's own raw operational stats are approximate for these two cases.
- **This package does not stand up asynq's own Web UI (`asynqmon`)** — that is a separate, independently deployable process/Docker image pointed at the same Redis, an operational/deployment concern outside a Go library's own scope, not something `AsynqQueue` embeds or launches.

## Error index

| Sentinel | Triggered by | Handling |
|---|---|---|
| `ErrJobNotFound` (`jobs.job_not_found`) | `Queue.Get`/`Cancel` for an id that does not exist, or exists under a tenant `ctx` cannot access — both implementations | Match with `apperr.As(err).Code`, not identity — see `isJobNotFound` in `job_test.go`. Not a bug to handle specially: this is the deliberately-collapsed "not found or not yours" response |
| `ErrInvalidTask` (`jobs.invalid_task`) | `Enqueue`, for an empty `Task.Type` or `Task.TenantID` — both implementations | Fix the caller; nothing is persisted |
| `ErrDuplicateHandlerType` (`jobs.duplicate_handler_type`) | `RegisterHandler`, for a `Type` already registered on that instance — both implementations | Almost always a wiring bug |
| `ErrHandlerNotRegistered` (`jobs.handler_not_registered`) | A worker claims a `Job` whose `Type` has no registered `Handler` — both implementations, same sentinel | Treated as an ordinary `Handle` failure (retried, then dead-lettered) — check `DeadLetterJobs` and the structured "job exhausted retries"/"Retry exhausted" log line, then fix the missing `RegisterHandler` call |
| `errAsynqTaskMissingTenant` (`jobs.asynq_task_missing_tenant`, unexported) | `AsynqQueue` only: a dequeued task's `Headers` carry no `tenant_id` at all | Should never happen for a `Task` this package's own `Enqueue` created (`buildTaskHeaders` always sets it); realistically indicates a non-`jobs` producer writing directly into the same Redis instance/queues. Treated as an ordinary `Handle` failure like the others |
| `errStandaloneJobMissingTenant` (`jobs.standalone_job_missing_tenant`, unexported) | `StandaloneQueue` only: `execute` claims a `jobRecord` whose `tenant_id` column is empty — `worker.go`'s mirror of `errAsynqTaskMissingTenant` above | Should never happen for a `Job` this package's own `Enqueue` created (`Task.validate` rejects an empty `TenantID` first); realistically indicates a row that reached the `jobs` table by some path other than `Enqueue` (a migration bug, a manual SQL fixup). Checked before calling `Handle`, never after — treated as an ordinary `Handle` failure like the others |
| `errStandaloneHandlerPanicked` (`jobs.standalone_handler_panicked`, unexported) | `StandaloneQueue` only: a `Handler`'s `Handle` panicked instead of returning normally, recovered by `worker.go`'s `invokeHandle` | Not a data problem like the other rows — a `Handler` implementation bug. Treated as an ordinary `Handle` failure like the others (retried, then dead-lettered); the panic value becomes this error's cause, the full stack trace is logged (never persisted to `Job.Error`) |

Design rationale lives in `docs/internal/07-platform-services.md` (the jobs section) and `docs/internal/04-data-and-tenancy.md` (the data-domain table `jobRecord`'s platform-data classification follows). The tenant-context-rebuild discipline is also stated at the root: `CLAUDE.md`'s "Traps Specific to This Codebase" and the backend coding standard §7.
