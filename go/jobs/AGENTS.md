# jobs

jobs is speed's asynchronous task queue: the `Queue`/`Task`/`Job`/`Handler` contract every runtime profile implements, and `DemoQueue`, the demo profile's implementation — an in-process worker pool backed by a SQLite-persisted task table. It sits above `tenancy` and `observability` in the module dependency graph (`pkgcore -> dbkit / observability -> tenancy -> config / jobs -> ...`) and is itself a dependency of every module that needs to run something asynchronously: `storage` (derivative generation), `notification` (delivery + retry), `billing` (invoice generation), `ai-gateway` (generation jobs), `integration` (webhook delivery), `compliance` (retention/export jobs). See `docs/internal/07-platform-services.md`'s jobs section for the full design intent this module implements.

**Two dependencies, used for different reasons.** `observability` is used throughout (`obs.FromContext` for every log line this package emits, `otel.Meter` for the queue-depth gauge) — see `worker.go` and `demo_queue.go`. `dbkit` is used only through the `*gorm.DB` a caller passes into `NewDemoQueue`: this package never calls `dbkit.Open` itself (the caller does, exactly as `dbkit.NewRepository[T](db)` expects), and never imports `dbkit.Repository[T]` at all — see "The persistence model is platform data, not tenant data" below for why. `tenancy` is a dependency only because this package's own tests use `tenancy/tenancytest.AssertNotTenantScoped`; no non-test `.go` file in this package imports it.

**Production is a separate, later task.** Everything below (`DemoQueue`) is the demo-profile implementation. Production is Redis-backed (`hibiken/asynq`, per the design doc: mature, ships its own retry/delay/scheduling/Web UI, not worth reimplementing) and is not built in this package yet — `go.mod` deliberately does not carry an `asynq` dependency until that implementation lands, rather than an unused one sitting in `go.sum` unjustified (root `CLAUDE.md`: "every dependency added here lands in someone else's go.sum... adding one needs justification"). The `Queue`/`Task`/`Job`/`Handler`/`EnqueueOption` shapes documented here are the pinned contract that implementation must satisfy — see each type's own doc comment for the reasoning behind its exact shape, since changing it after a production implementation exists is expensive (root `CLAUDE.md`: "treat public API as frozen unless you are intentionally shipping a breaking change").

| Concern | Where |
|---|---|
| Portable types every profile shares: `JobID`, `Status`, `Priority`, `Result`, `Job` | `job.go` |
| `Task`, the Enqueue input shape | `task.go` |
| `Handler`, `ProgressFn`, `FailureHook`, the `NewHandlerFunc` adapter | `handler.go` |

## Public API

### `job.go`

| Signature | Purpose |
|---|---|
| `type JobID string` | A `Job`'s identity. Generated by `Enqueue`, never caller-supplied |
| `type Status string` + `StatusPending/Running/Retrying/Succeeded/DeadLetter/Cancelled` | A `Job`'s lifecycle state. See "State transitions" below for the full diagram |
| `func (Status) Terminal() bool` | Reports `Succeeded`, `DeadLetter` or `Cancelled` — states no worker ever transitions out of |
| `type Priority int` + `PriorityLow=0/Normal=5/High=10` | Dispatch priority. Higher runs first; ties broken by `ScheduledAt` ascending |
| `type Result struct { Data []byte }` | A succeeded `Job`'s opaque output — a contract between the `Task`'s producer and its `Handler`, never interpreted by the queue itself |
| `type Job struct { ID, Type, TenantID, Payload, IdempotencyKey, Status, Priority, ProgressPct, ProgressMsg, Result *Result, Error, Attempts, MaxRetries, ScheduledAt, CreatedAt, UpdatedAt, StartedAt *time.Time, CompletedAt *time.Time }` | The pinned record every `Queue` implementation reports through `Get`. `Error` is cleared once `Status` becomes `Succeeded`, but is **not** cleared by `Cancel` — a `Job` cancelled after a failed attempt keeps that attempt's message for diagnostic visibility |
| `var ErrJobNotFound = apperr.NotFound("jobs.job_not_found")` | Returned by `Get`/`Cancel` for an id that does not exist, or exists under a tenant the caller cannot access — the two cases are indistinguishable on purpose (mirrors `dbkit.Repository[T].FindByID`) |

### `task.go`

| Signature | Purpose |
|---|---|
| `type Task struct { Type, TenantID pkgcore.TenantID, Payload []byte, IdempotencyKey string }` | What a caller hands `Enqueue`. `TenantID` is a field on `Task`, not resolved from `Enqueue`'s `ctx` — see "Why Task carries its own TenantID" below |
| `var ErrInvalidTask = apperr.Invalid("jobs.invalid_task")` | Returned by `Enqueue` for an empty `Type` or `TenantID`, before anything is persisted |

### `handler.go`

| Signature | Purpose |
|---|---|
| `type ProgressFn func(pct int, msg string)` | The progress-reporting callback `Handle` receives |
| `type Handler interface { Type() string; Handle(ctx, job *Job, progress ProgressFn) (Result, error) }` | Processes every `Job` of one `Task.Type`. `ctx` already carries `job.TenantID` — see "The tenant context trap" |
| `func NewHandlerFunc(jobType string, fn func(...) (Result, error)) Handler` | Adapts a plain function into a `Handler`, mirroring `http.HandlerFunc` |
| `type FailureHook interface { OnFailure(ctx, job *Job, cause error) }` | A `Handler` optionally implements this too, to run compensation once a `Job` dead-letters — see "Failure compensation stays out of this layer" |

### `queue.go`

| Signature | Purpose |
|---|---|
| `type Queue interface { Enqueue(ctx, Task, ...EnqueueOption) (JobID, error); Get(ctx, JobID) (*Job, error); Cancel(ctx, JobID) error }` | The portable, profile-independent contract. See `DemoQueue` for why its extra methods (`RegisterHandler`, `Start`, `Close`) live outside this interface |
| `const DefaultMaxRetries = 3` / `const DefaultTimeout = 5 * time.Minute` | Applied when the matching `EnqueueOption` is omitted |
| `type EnqueueOption func(*enqueueOptions)` + `WithPriority` / `WithDelay` / `WithScheduledAt` / `WithMaxRetries` / `WithTimeout` | Per-`Enqueue`-call configuration. `WithDelay`/`WithScheduledAt` are mutually exclusive — whichever is passed last to `Enqueue` wins. A negative `WithMaxRetries` clamps to 0; a non-positive `WithTimeout` is ignored (falls back to the configured default) rather than honored literally, since a zero/negative `context.WithTimeout` deadline would expire before a `Handler` ever ran |

### `demo_queue.go`

| Signature | Purpose |
|---|---|
| `const DefaultWorkerCount=4` / `DefaultTenantConcurrencyLimit=2` / `DefaultPollInterval=200ms` / `DefaultBackoffBase=1s` / `DefaultBackoffMax=5m` | `DemoQueue`'s construction defaults |
| `var ErrDuplicateHandlerType = apperr.Invalid("jobs.duplicate_handler_type")` | Returned by `RegisterHandler` for a `Type` already registered on that `DemoQueue` |
| `type Option func(*DemoQueue)` + `WithWorkerCount` / `WithTenantConcurrencyLimit` / `WithPollInterval` / `WithJobTimeout` / `WithBackoff` | `NewDemoQueue`'s construction-time tuning. Unlike `dbkit.Options`' fixed connection-pool limits, these are exposed because worker-pool sizing and per-tenant concurrency really are deployment-dependent |
| `type DemoQueue struct { ... }` | The demo `Queue` implementation. Returned as its own concrete exported type, not the `Queue` interface (compare `pkgcore.NewMemoryKVStore`, which returns `KVStore`): a caller needs `RegisterHandler`/`Start`/`Close`, none of which belong on `Queue`'s portable surface |
| `func NewDemoQueue(db *gorm.DB, opts ...Option) *DemoQueue` | `db` must come from `dbkit.Open` (directly, or via `dbkit/dbtest`). Performs no I/O |
| `func (*DemoQueue) RegisterHandler(h Handler) error` | Register every `Handler` before calling `Start`; safe to call after too, but a `Job` already claimed will not retroactively use a late registration |
| `func (*DemoQueue) Start(ctx) error` | Creates the schema if absent, recovers any `StatusRunning` row left by an unclean exit back to `StatusPending`, wires the `jobs.queue.depth` metric, launches the dispatcher and `WorkerCount` worker goroutines. Safe to call more than once (a no-op after the first) |
| `func (*DemoQueue) Close(ctx) error` | Stops the dispatcher/workers and waits for in-flight `Job`s to reach their own natural completion or timeout, up to `ctx`'s deadline. Idempotent |
| `func (*DemoQueue) Enqueue/Get/Cancel` | Implements `Queue` — see `queue.go`'s and `job.go`'s own entries above |
| `func (*DemoQueue) DeadLetterJobs(ctx) ([]*Job, error)` | Every `StatusDeadLetter` `Job` `ctx` may access. Not part of `Queue`: an operational convenience specific to this implementation |

## The tenant context trap

**This is the single most important thing to get right in this package**, per root `CLAUDE.md`'s "Traps Specific to This Codebase" and the backend coding standard §7. A `Task`'s `Enqueue` call and the eventual `Handle` call that processes it run on **completely different contexts, potentially minutes or hours apart**: the `context.Context` active when `Enqueue` was called is long gone by the time a worker goroutine reads the row back out of SQLite — it was never persisted, because a `context.Context` cannot be. If a worker naively called `handler.Handle(someAmbientCtx, job, progress)` with whatever context its own dispatch loop happens to be running on, `job.TenantID` and the tenant `Handle`'s own `ctx` carries would silently disagree — or, since the dispatcher's internal loops run on a bare `context.Background()`, there would be no tenant at all, and any `dbkit.Repository[T]` call inside `Handle` would fail closed with `pkgcore.ErrNoTenant`.

**This is closed by construction, not by convention.** `worker.go`'s `jobContext(tenant pkgcore.TenantID) context.Context` is the ONE place a tenant is attached for a `Handle`/`OnFailure` call: `execute` calls it with `rec.TenantID` — the tenant recorded on the `Job` itself when it was enqueued — every single time, before applying the per-attempt timeout and calling `Handle`. No code path in this package calls `Handle` any other way.

**Proof, not just a promise:**
- `worker_test.go`'s `TestJobContext_ProducesTenantScopedContext` / `TestJobContext_IgnoresAmbientTenant` / `TestJobContext_ContrastWithoutRebuild_FailsClosedWithErrNoTenant` prove the mechanism at the unit level: a context from `jobContext` carries exactly the given tenant regardless of what (if anything) an ambient context carried, and — the negative control — a context that skips `jobContext` entirely (a bare `context.Background()`, exactly what a regressed worker would produce) fails `pkgcore.MustTenantFromContext` with `pkgcore.ErrNoTenant`. If a future change to `execute`/`runWorker` ever stops routing through `jobContext`, this is the test that must start failing, by this exact, well-labeled name.
- `demo_queue_test.go`'s `TestDemoQueue_RebuildsTenantContext_HandlerUsesOnlyJobTenant` proves the same guarantee end to end, through the real `DemoQueue`/dispatcher/worker pipeline: a `Handler` performs a genuine `dbkit.Repository[T]` call, and the `Task` is enqueued from a `context.Background()` carrying **no tenant at all** — so the eventual success can only be explained by the worker's own rebuild, never by anything leaking through from the call site.

**Why `Task` carries its own `TenantID` instead of `Enqueue` resolving it from `ctx`.** Unlike an HTTP request handler, `Enqueue` is legitimately called from places with no single ambient tenant — a platform-level scheduler enqueuing one cleanup `Task` per tenant in a loop, for example (`docs/internal/07-platform-services.md`'s sharing-link expiry case). This mirrors `pkgcore.Event.TenantID`'s identical design for the same reason. `Task.TenantID` is required non-empty (`ErrInvalidTask`) — every `Job` must be attributable to a tenant, unlike `Event`, which supports a zero-value tenant for genuinely system-wide facts.

## Failure compensation stays out of this layer

Per root `CLAUDE.md`'s "Asynchronous work" discipline: *"the queue offers an `OnFailure` hook; refunding credits and similar compensation belongs to the business module."* `FailureHook` (`handler.go`) is that hook, and the **entire** extent of this package's involvement in failure compensation: a `Handler` that needs to run business-specific logic once a `Job` exhausts its retries — refunding a pay-per-use credit reservation, for example — implements `OnFailure` alongside `Handle`. The queue calls it exactly once, after the `Job`'s `Status` is already persisted as `StatusDeadLetter`, and never inspects, retries, or otherwise reacts to what `OnFailure` does. `jobs` itself never special-cases a `Task.Type`, never knows what "refund credits" means, and contains no compensation logic of its own anywhere in this package — that boundary is enforced by `FailureHook` simply having no more surface than `OnFailure(ctx, job, cause)`.

## Observability

Every log line this package emits goes through `obs.FromContext(ctx)` (never a package-level or hand-built logger), with a constant message and `snake_case` key-value attributes — `job_id`, `job_type`, `tenant_id` (via `ctx`'s own tenant, attached automatically by `obs.FromContext` per `observability.AGENTS.md`), `attempts`, `duration_ms`, `retry_in_ms`, `error`. See `worker.go`'s `execute` and `demo_queue.go`'s `Enqueue`.

**`jobs.queue.depth`** is the queue-backlog gauge `docs/internal/09-observability.md`'s must-instrument table names for this module: the current count of `StatusPending`/`StatusRetrying` `Job`s, labeled **only** by `job_type` and `status` — never `tenant_id`, per root `CLAUDE.md`'s Prometheus-cardinality rule, mirroring `observability.Middleware`'s identical split between low-cardinality metric labels and high-cardinality log/span attributes. `DemoQueue.Start` wires it via `meter := otel.Meter(name)` then `meter.Int64ObservableGauge(...)` — the same "obtain the meter, then construct a named instrument with `metric.With*` options" convention `observability.Middleware` itself uses for its own `Int64Counter`/`Float64Histogram` — so it reports real data once a host has called `observability.Init`, and is a harmless no-op otherwise. A failure to register it does not prevent `Start` from launching the dispatcher/workers — it is logged as a warning and `Start` continues.

## The persistence model is platform data, not tenant data

`jobRecord` (`store.go`) deliberately does **not** implement `dbkit.TenantScoped` — no `GetTenantID` method, no embedded `dbkit.TenantModel`. Per `docs/internal/04-data-and-tenancy.md`'s data-domain table and `dbkit/AGENTS.md`'s "Known limitations", this makes it platform data: the dispatcher's claim query scans eligible `Job`s **across every tenant at once**, in priority order, to decide what to run next and to enforce per-tenant concurrency limits — an access pattern `dbkit.Repository[T]` (whose every method resolves and filters by exactly one tenant from `ctx`, per `dbkit`'s own tenant-scoping plugin) cannot serve, and whose generic constraint (`Repository[T TenantScoped]`) would not even compile against a model like this. `tenant_id` is still a real, indexed column — read explicitly by the per-tenant concurrency gate and by `Queue.Get`/`Cancel`'s own access check (`callerMayAccess`) — it is simply never auto-injected as a query filter the way it would be for a `TenantScoped` model. `store_test.go`'s `TestJobRecord_NotTenantScoped` (`tenancytest.AssertNotTenantScoped`) is the standing, CI-enforced proof of this property, exactly as the backend coding standard §3.3 requires for platform data.

The `jobs` table itself is created imperatively (`store.go`'s `createJobsTableSQL`, a plain `CREATE TABLE IF NOT EXISTS`) rather than through `dbkit.MigrationRegistry` — the same bootstrapping pattern `dbkit` uses for its own `schema_migrations` table, applied here for a different reason: this table is a demo-profile-only implementation detail with no other consumer (production's `Queue` is Redis/asynq-backed and never creates it), so routing it through cross-module, Atlas-generated, versioned migration machinery built for schema that ships and evolves across both profiles would be disproportionate. The SQL is still written to be portable across both dbkit dialects (no PostgreSQL-only features), even though only SQLite is exercised — see Known limitations.

## Retry, backoff and dead-letter

A `Job`'s `Attempts` is incremented at claim time (`pending`/`retrying` → `running`), before `Handle` runs. On failure, `execute` compares `Attempts` against `MaxRetries`:

- `Attempts <= MaxRetries`: → `StatusRetrying`, with `ScheduledAt` moved forward by `backoffDelay(Attempts)` — `backoffBase * 2^(Attempts-1)`, capped at `backoffMax` (`DemoQueue`'s `WithBackoff` option; defaults `DefaultBackoffBase`/`DefaultBackoffMax`).
- `Attempts > MaxRetries`: → `StatusDeadLetter` (total attempts made = `MaxRetries + 1`), and, if the registered `Handler` also implements `FailureHook`, its `OnFailure` runs once.

A claimed `Job` whose `Type` has no registered `Handler` (`ErrHandlerNotRegistered`) is treated exactly like any other `Handle` failure — retried, then dead-lettered — rather than dropped or looped forever, so a startup-ordering mistake (a `Task` enqueued before its `Handler` registers) can resolve itself, and a genuine mismatch surfaces in `DeadLetterJobs` instead of vanishing silently.

## Typical integration

```go
db, err := dbkit.Open(ctx, dbkit.Options{Dialect: dbkit.DialectSQLite, DSN: dsn})
// handle err

queue := jobs.NewDemoQueue(db, jobs.WithWorkerCount(8), jobs.WithTenantConcurrencyLimit(2))
if err := queue.RegisterHandler(&ImageGenHandler{svc: svc}); err != nil {
    // handle err
}
if err := queue.Start(ctx); err != nil {
    // handle err
}
defer queue.Close(shutdownCtx)

id, err := queue.Enqueue(ctx, jobs.Task{
    Type:           "ai.generate_smile",
    TenantID:       tenant,
    Payload:        payloadBytes,
    IdempotencyKey: "smile-gen:" + requestID, // derived from the business operation, never random
}, jobs.WithPriority(jobs.PriorityHigh), jobs.WithMaxRetries(2))
```

A `Handler` implementation, receiving a `ctx` that already carries `job.TenantID`:

```go
func (h *ImageGenHandler) Type() string { return "ai.generate_smile" }

func (h *ImageGenHandler) Handle(ctx context.Context, job *jobs.Job, progress jobs.ProgressFn) (jobs.Result, error) {
    // ctx already carries job.TenantID -- a dbkit.Repository[T] call here
    // needs no extra tenant plumbing of its own.
    progress(10, "starting")
    out, err := h.svc.Generate(ctx, job.Payload)
    if err != nil {
        return jobs.Result{}, err // retried, then dead-lettered -- see below
    }
    progress(100, "done")
    return jobs.Result{Data: out}, nil
}

// OnFailure runs once, only after every retry is exhausted.
func (h *ImageGenHandler) OnFailure(ctx context.Context, job *jobs.Job, cause error) {
    h.credits.Refund(ctx, job.TenantID, job.IdempotencyKey) // business compensation lives here, not in jobs
}
```

See `example_test.go`'s `Example` and `ExampleNewHandlerFunc` for the same shape, compiled and run.

## Testing

One test file per source file (backend coding standard §13): `job_test.go`, `task_test.go`, `handler_test.go`, `queue_test.go`, `store_test.go`, `worker_test.go`, `demo_queue_test.go`, plus `example_test.go` for the `Example*` functions. `demo_queue_test.go` is the end-to-end suite (real `DemoQueue`, real dispatcher/worker goroutines, real SQLite): retry/backoff, idempotency (also covered at the storage layer in `store_test.go`, including under real concurrent `Enqueue` calls), priority ordering, delayed/scheduled execution, dead-letter plus `FailureHook`, per-tenant concurrency limiting, progress reporting, and the tenant-context-rebuild trap's end-to-end proof. `worker_test.go` covers the same trap at the unit level, plus the backoff formula and the per-tenant concurrency-gating primitives under `-race` (backend coding standard §13: "concurrency hot spots... require `-race` tests").

`isJobNotFound` (`job_test.go`) matches `ErrJobNotFound` by `.Code` via `apperr.As`, not by identity — the same discipline `dbkit`'s own `isRecordNotFound` test helpers use, since `WithParam`/`WithCause` always derive a new `*apperr.Error` instance (see `apperr`'s own doc comment).

## Rules

- **Never call a `Handler`'s `Handle` or `OnFailure` with any context other than one built by `jobContext(job.TenantID)`.** This is "The tenant context trap" above, closed by construction in `worker.go`'s `execute` — do not "simplify" it by threading the dispatcher's own loop context through instead, and do not assume any context available at a call site already carries the right tenant.
- **Do not add business-specific logic to this package.** `FailureHook` is the queue's entire failure-compensation surface; a queue-level "if job.Type == ... refund credits" branch would violate the module boundary root `CLAUDE.md`'s "Asynchronous work" discipline draws — see "Failure compensation stays out of this layer".
- **Do not give `jobRecord` a `GetTenantID` method or embed `dbkit.TenantModel` into it.** Doing so would make it satisfy `dbkit.TenantScoped`, and the tenant-scoping plugin would then fail closed on the dispatcher's cross-tenant claim query, which runs on a context that deliberately carries no tenant. See "The persistence model is platform data, not tenant data".
- **Do not use `dbkit.Repository[T]` for `jobRecord`.** Its generic constraint requires `TenantScoped`, which `jobRecord` must not implement — use the plain `*gorm.DB` functions in `store.go` instead, exactly as `dbkit/AGENTS.md` documents for platform data.
- **Do not persist a `context.Context`, or store one in `DemoQueue`'s own fields.** `Start`/`Close` take a `ctx` parameter for their own synchronous work only; the dispatcher/worker goroutines' lifecycle is controlled by `stopCh`/`wg`, and each `Handle` call's context is built fresh by `jobContext`, independent of `DemoQueue`'s own lifecycle (see `Close`'s own doc comment for why: closing the queue must not abruptly truncate a business operation already in flight).
- **Do not add a new `EnqueueOption` or change `Queue`/`Handler`/`Job`/`Task`'s shape without weighing the production implementation.** These are the pinned contract a Redis/asynq-backed implementation (a separate, later task) must satisfy — see this file's own intro.
- **Do not skip `tenancytest.AssertNotTenantScoped` for `jobRecord`** because it "obviously" is not tenant-scoped — its entire purpose is catching an accidental regression (`jobRecord` starting to satisfy `dbkit.TenantScoped` without anyone noticing), which would otherwise show up in production as jobs "mysteriously" not being picked up across tenants.
- **Do not assume `Cancel` interrupts an already-running `Handle` call.** See Known limitations below.

## Known limitations

- **`Cancel` does not preempt an in-flight `Handle` call.** Cancelling a `StatusPending`/`StatusRetrying` `Job` prevents it from ever being dispatched. Cancelling a `StatusRunning` one immediately marks it `StatusCancelled` in the database — and every completion write (`completeSucceeded`/`completeRetrying`/`completeDeadLetter`) is itself conditioned on the row still being `StatusRunning`, so whatever outcome the still-executing `Handle` call eventually reaches is correctly discarded rather than resurrecting the `Job` out of `StatusCancelled` — but the `Handle` call's own goroutine keeps running (burning CPU/IO/wall-clock) until it returns naturally or its configured timeout fires; nothing preemptively cancels its `context.Context`. Closing this fully would mean threading a `map[JobID]context.CancelFunc` through the worker pool — a real enhancement, not built in this round.
- **This module's own tests exercise SQLite only, never `dbkit/dbtest.NewPostgres`.** Every other dbkit-consuming module in this repo tests both dialects because its schema ships in both the demo and production profiles. `DemoQueue`'s persistence is different: it is a demo-profile-only implementation detail with no production analog at all (production is Redis/asynq-backed, per this file's intro) — there is no "production dialect" of this schema to verify. The DDL is still written portably (no PostgreSQL-only features) as a matter of discipline, not because it is expected to run there.
- **No queue-wide, cross-`Handler` observability of `DeadLetterJobs` beyond a plain list.** There is no requeue/retry-from-dead-letter API, and no pagination on `DeadLetterJobs` — reasonable for now, since nothing in this milestone consumes it beyond the guarantee that a dead-lettered `Job` remains visible and queryable.
- **The dispatcher is a single goroutine.** `claimOne`'s `WHERE id = ? AND status = ?` guard makes a claim race-safe regardless, but there is currently exactly one dispatcher per `DemoQueue`, so today that guard is insurance against a future change rather than something the current code path exercises concurrently.
- **`Enqueue`'s idempotency is scoped per tenant, not globally.** Two different tenants may use the identical `IdempotencyKey` string without colliding (`createJobsIdempotencySQL`'s unique index is on `(tenant_id, idempotency_key)`) — this is deliberate, not a gap: idempotency keys are business-operation identifiers meaningful within one tenant's own operations.

## Error index

| Sentinel | Triggered by | Handling |
|---|---|---|
| `ErrJobNotFound` (`jobs.job_not_found`) | `Queue.Get`/`Cancel` for an id that does not exist, or exists under a tenant `ctx` cannot access | Match with `apperr.As(err).Code`, not identity — see `isJobNotFound` in `job_test.go`. Not a bug to handle specially: this is the deliberately-collapsed "not found or not yours" response |
| `ErrInvalidTask` (`jobs.invalid_task`) | `Enqueue`, for an empty `Task.Type` or `Task.TenantID` | Fix the caller; nothing is persisted |
| `ErrDuplicateHandlerType` (`jobs.duplicate_handler_type`) | `DemoQueue.RegisterHandler`, for a `Type` already registered on that instance | Almost always a wiring bug (registering the same `Handler` twice, or two `Handler`s claiming the same `Type`) |
| `ErrHandlerNotRegistered` (`jobs.handler_not_registered`) | A worker claims a `Job` whose `Type` has no registered `Handler` | Treated as an ordinary `Handle` failure (retried, then dead-lettered) — check `DeadLetterJobs` and the structured "job exhausted retries" log line, then fix the missing `RegisterHandler` call |

The tenant-context-rebuild discipline is also stated at the root: `CLAUDE.md`'s "Traps Specific to This Codebase" and the backend coding standard §7.
