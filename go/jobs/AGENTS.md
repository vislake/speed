# jobs

jobs is speed's asynchronous task queue: the `Queue`/`Task`/`Job`/`Handler` contract every deployment mode implements, `StandaloneQueue` (the standalone deployment mode's implementation — an in-process worker pool backed by a SQLite-persisted task table, living in this module's own root package, whose non-test third-party imports are confined to the module's existing `gorm.io/gorm`/`go.opentelemetry.io/otel`/`github.com/google/uuid`), `asynq.Queue` (the distributed deployment mode's implementation — Redis via `github.com/hibiken/asynq` — living in this module's `queue/asynq` subpackage; see "Packaging: why asynq.Queue is a subpackage" below for why it is split out rather than sitting in the root package alongside `StandaloneQueue`), and `Scheduler` (the portable periodic-task driver — it reads the periodic tasks modules declared on `pkgcore.ComponentRegistry.Schedules` and enqueues them through `Queue.Enqueue`, so it runs unchanged on either deployment mode; see "Periodic scheduling" below). It sits above `tenancy` and `observability` in the module dependency graph (`pkgcore -> dbkit / observability -> tenancy -> config / jobs -> ...`) and is itself a dependency of every module that needs to run something asynchronously: `storage` (derivative generation), `notification` (delivery + retry), `billing` (invoice generation), `ai-gateway` (generation jobs), `integration` (webhook delivery), `compliance` (retention/export jobs).

**Three dependencies, used for different reasons.** `observability` is used throughout (`obs.FromContext` for every log line this package emits, `otel.Meter` for the queue-depth gauge) — see `worker.go`, `queue_standalone.go`, `queue/asynq/worker.go` and `queue/asynq/queue.go`. `dbkit` is used through the `*gorm.DB` a caller passes into `NewStandaloneQueue`, plus `dbkit.FitColumnValue` for the write-boundary fit of descriptive text (see `store.go`'s `fitDescriptiveText`): this package never calls `dbkit.Open` itself, and never imports `dbkit.Repository[T]` — see "The persistence model is platform data, not tenant data" below for why. This has no analog in `asynq.Queue` at all: it holds no `*gorm.DB` and creates no schema — its entire persistence is Redis, reached exclusively through the third-party `asynq` library's own client/server/inspector types plus this subpackage's own thin `redis.UniversalClient`-backed cancellation-marker bookkeeping (`queue/asynq/queue.go`). `tenancy` is a dependency only because this module's own tests use `tenancy/tenancytest.AssertNotTenantScoped`; no non-test `.go` file in either the root package or `queue/asynq` imports it.

**`hibiken/asynq` and `redis/go-redis/v9` are direct dependencies of this module, but only `queue/asynq`'s own files import either of them** — the distributed deployment mode runs on Redis, `hibiken/asynq` is the mature library that ships its own retry/delay/scheduling/Web-UI machinery (not worth reimplementing), and a dependency a consumer never asked for must not land in its own `go.mod`: hence the imports live only in `queue/asynq`'s files. `testcontainers-go/modules/redis` is an additional dependency used **only** by `integration_test/`, gated behind the `integration` build tag — it never appears in any non-test import, and a plain `go build`/`go vet`/`go test ./...` never needs Docker or Redis. See "Testing" below for the two-tier layout this makes possible, and "Packaging: why asynq.Queue is a subpackage" below for the measured cost this packaging choice removes from a `StandaloneQueue`-only consumer.

## Packaging: why asynq.Queue is a subpackage

`asynq.Queue` lives in its own `queue/asynq` subpackage, not in this module's root package beside `StandaloneQueue`. Had it sat in the root package, EVERY consumer of this module — including one that only ever runs the standalone deployment mode and never constructs an `asynq.Queue` at all — would carry `hibiken/asynq`, `redis/go-redis/v9` and their own transitive dependencies (`robfig/cron/v3`, `spf13/cast`, `golang.org/x/time` among them) in its own `go.mod`/`go.sum`: Go resolves dependencies per *package*, not per symbol, so importing only the root package would still pay for every import its `asynq` files carried. A subpackage isolates `go.mod`/`go.sum`/minimal-version-selection completely (a new Go module would buy nothing on top under this codebase's lockstep versioning), removing that cost for exactly the consumers who never asked to pay it, while `StandaloneQueue` and the portable `Queue`/`Task`/`Job`/`Handler`/`EnqueueOption` contract stay in this module's own root package, unchanged in behavior — their non-test third-party imports are confined to the module's existing `gorm.io/gorm`, `go.opentelemetry.io/otel` and `github.com/google/uuid`, never `hibiken/asynq` or `redis/go-redis/v9`. A backend implementation never sits in the same package as the interface it implements, and which backends a binary contains is the assembling application's decision.

**Measured by the codebase's prescribed method** (a throwaway module requiring only this module's root package — `var q jobs.Queue` is enough to force resolution — `go mod tidy` under `GOWORK=off`, counting `// indirect` entries in the resulting `go.mod`): the split removed `github.com/hibiken/asynq`, `github.com/robfig/cron/v3`, `github.com/spf13/cast` and `golang.org/x/time` from a `StandaloneQueue`-only consumer's `go.mod`/`go.sum` entirely — re-run that measurement to re-derive the current counts. `github.com/redis/go-redis/v9` is unaffected by the split: it remains indirect through `go/pkgcore`'s own root package, which bundles its Redis-backed `KVStore`/`EventBus` implementations the same way — a separate module-level site, tracked and measured on its own terms there. Three real consumers exhibit the same shape end to end: `go/notification`, `go/storage` and `examples/reference-app` never import `queue/asynq` — they depend on `jobs.Queue` and wire whichever implementation their own host chooses.

The `asynq-only-in-jobs` and `redis-only-in-pkgcore-and-jobs` depguard rules in the repository root's `.golangci.yml` exempt `!**/go/jobs/queue/asynq/**` — not the whole `!**/go/jobs/**` — so a business file dropped directly under this module's root package that reaches for `hibiken/asynq` or `go-redis` fails lint rather than silently reintroducing the cost the split removes.

### `job.go`

| Signature | Purpose |
|---|---|
| `type JobID string` | A `Job`'s identity. Generated by `Enqueue`, never caller-supplied |
| `type Status string` + `StatusPending/Running/Retrying/Succeeded/DeadLetter/Cancelled` | A `Job`'s lifecycle state. See "State transitions" below for the full diagram |
| `func (Status) Terminal() bool` | Reports `Succeeded`, `DeadLetter` or `Cancelled` — states no worker ever transitions out of |
| `type Priority int` + `PriorityLow=0/Normal=5/High=10` | Dispatch priority, scoped to a tenant's fair-share slice on `StandaloneQueue`: higher runs first and ties break by `ScheduledAt` ascending *within* one tenant's own share of a candidate window — across tenants the round-robin rotation takes precedence, so a lower-Priority Job of one tenant is claimed before a higher-Priority second Job of another (see "Per-tenant fairness" below); mapped onto three fixed weighted queues in `asynq.Queue` (see "Distributed: asynq.Queue" below) |
| `type Result struct { Data []byte }` | A succeeded `Job`'s opaque output — a contract between the `Task`'s producer and its `Handler`, never interpreted by the queue itself |

### `register_handlers.go`

| Signature | Purpose |
|---|---|
| `func RegisterHandlers(q *StandaloneQueue, decls map[string]any) error` | The drain primitive `Wire` composes, callable directly by a host whose declarations do not live on a `pkgcore.ComponentRegistry` (a host-owned map): every entry of `decls` — keyed by job type, the shape `pkgcore.JobHandlerRegistrar.Handlers()` exposes — must be a `jobs.Handler`, registered through `q.RegisterHandler`, which keys the queue by the handler's own `Type()`. ## The tenant context trap

**This is the single most important thing to get right in this package**, and it applies **identically to both implementations** — a Redis-backed worker consuming a task minutes or hours after `Enqueue` ran has exactly the same "the original context is long gone" problem an in-process one does, just with a different persistence layer underneath. A `Handle` call run under the wrong context executes tenant business under the wrong — or no — tenant.

**StandaloneQueue.** A `Task`'s `Enqueue` call and the eventual `Handle` call that processes it run on **completely different contexts, potentially minutes or hours apart**: the `context.Context` active when `Enqueue` was called is long gone by the time a worker goroutine reads the row back out of SQLite — it was never persisted, because a `context.Context` cannot be. If a worker naively called `handler.Handle(someAmbientCtx, job, progress)` with whatever context its own dispatch loop happens to be running on, `job.TenantID` and the tenant `Handle`'s own `ctx` carries would silently disagree — or, since the dispatcher's internal loops run on a bare `context.Background()`, there would be no tenant at all, and any `dbkit.Repository[T]` call inside `Handle` would fail closed with `pkgcore.ErrNoTenant`.

**This is closed by construction, not by convention.** `worker.go`'s `jobContext(tenant pkgcore.TenantID) context.Context` is the ONE place a tenant is attached for a `Handle`/`OnFailure` call: `execute` calls it with `rec.TenantID` — the tenant recorded on the `Job` itself when it was enqueued — every single time, before applying the per-attempt timeout and calling `Handle`. No code path in `StandaloneQueue` calls `Handle` any other way.

**asynq.Queue: the same trap, a different rebuild point.** `Task.TenantID` cannot ride inside asynq's own `Task.Payload` (that field must stay exactly the caller's own opaque bytes, per `Task.Payload`'s and `Job.Payload`'s doc comments) — it rides in asynq's `Task.Headers` instead (`queue/asynq/store.go`'s `headerTenantID`, written by `buildTaskHeaders` at `Enqueue` time). `Headers` are part of asynq's own `base.TaskMessage` and survive retries and archiving unchanged (confirmed by reading asynq's `processor.go`: every retry/archive/error-handler path reconstructs the `Task` via `NewTaskWithHeaders(msg.Type, msg.Payload, msg.Headers)`). `queue/asynq/worker.go`'s `processTask` is the ONE place a tenant is attached for `asynq.Queue`: `handleCtx := pkgcore.WithTenant(ctx, tenantID)`, with `tenantID` read from `t.Headers()[headerTenantID]` — never from anywhere else. If that header is ever empty (never expected for a `Task` this package's own `Enqueue` created — see `errTaskMissingTenant`'s own doc comment), the attempt fails closed rather than calling `Handle` with no tenant at all.

**Why `ctx`, not a fresh `context.Background()`, is `handleCtx`'s base for `asynq.Queue` — a deliberate difference from `StandaloneQueue`'s `jobContext`.** `StandaloneQueue.jobContext` is built over `context.Background()`, explicitly NOT derived from the dispatcher's own lifecycle, so that closing the queue never abruptly cancels a `Handle` call already in flight. `asynq.Queue.processTask` instead builds `handleCtx` on top of `ctx`, the per-task `context.Context` asynq's own processor constructs fresh for every attempt (`asynqcontext.New`, scoped to exactly this one dequeue, deadline-bounded by the Task's own `Timeout`/`Deadline` options). This is not a shortcut; it is what makes two things work correctly:

- **asynq's own per-attempt timeout enforcement becomes `Handle`'s own timeout enforcement**, instead of this package reimplementing `context.WithTimeout` on top of a fresh, uncoupled context — exactly the "prefer configuring/wrapping asynq's own primitives" instruction this implementation was built under. A `Handle` call built on a *disconnected* fresh context would keep running even after asynq's processor had already decided (via `ctx.Done()`) that the attempt timed out and requeued it for retry — burning CPU/IO on work asynq itself no longer considers current.
- **`Inspector.CancelProcessing` (used by `asynq.Queue.Cancel` for an already-`Active` Job) becomes able to interrupt a real, in-flight `Handle` call**, because asynq's cancellation pub/sub mechanism cancels exactly this `ctx` (via a `map[taskID]context.CancelFunc` internal to asynq's processor), which `handleCtx` is now downstream of. This is strictly *better* than `StandaloneQueue`'s own documented "does not preempt" limitation, not a violation of it — `Queue.Cancel`'s doc comment only ever promises a running Job "is allowed to" keep executing, never that it is guaranteed to.
- Closing the *queue* (`asynq.Queue.Close`) still does not abruptly cancel an in-flight `Handle` call either way: `asynq.Server.Shutdown()` does not cancel a running attempt's `ctx` on its own — it stops pulling new tasks and, after `Config.ShutdownTimeout` elapses, requeues whatever is still active back to Redis while the orphaned goroutine keeps running to its own natural completion or per-attempt deadline. See "Close vs Shutdown" below.

**Proof, not just a promise:**
- `worker_test.go`'s `TestJobContext_*` trio proves `StandaloneQueue`'s mechanism at the unit level (see their own doc comments).
- `queue_standalone_test.go`'s `TestStandaloneQueue_RebuildsTenantContext_HandlerUsesOnlyJobTenant` proves the same guarantee end to end for `StandaloneQueue`, through a real `dbkit.Repository[T]` call.
- `integration_test/tenant_context_test.go`'s `TestRedisQueue_RebuildsTenantContext` proves the identical guarantee end to end for `asynq.Queue`, against a **real asynq.Server dequeuing from a real Redis** (via testcontainers-go) — the same real `dbkit.Repository[T]`-based technique, so both deployment modes are held to the exact same, non-tautological standard: the `Task` is enqueued from a context carrying no tenant at all, so a passing test can only be explained by the worker's own rebuild, never by anything leaking through from the call site.

**Why `Task` carries its own `TenantID` instead of `Enqueue` resolving it from `ctx`.** Unlike an HTTP request handler, `Enqueue` is legitimately called from places with no single ambient tenant — a platform-level scheduler enqueuing one cleanup `Task` per tenant in a loop, for example. This mirrors `pkgcore.Event.TenantID`'s identical design for the same reason, and is exactly as true for `asynq.Queue.Enqueue` as it is for `StandaloneQueue.Enqueue`. `Task.TenantID` is required non-empty (`ErrInvalidTask`) — every `Job` must be attributable to a tenant, unlike `Event`, which supports a zero-value tenant for genuinely system-wide facts.

## Failure compensation stays out of this layer

Compensation belongs to the business module, never the queue layer: *the queue offers an `OnFailure` hook; refunding credits and similar compensation belongs to the business module.* `FailureHook` (`handler.go`) is that hook, and the **entire** extent of this package's involvement in failure compensation, for **both** implementations: a `Handler` that needs to run business-specific logic once a `Job` exhausts its retries — refunding a pay-per-use credit reservation, for example — implements `OnFailure` alongside `Handle`. Neither `StandaloneQueue` nor `asynq.Queue` special-cases a `Task.Type`, knows what "refund credits" means, or contains any compensation logic of its own — that boundary is enforced by `FailureHook` simply having no more surface than `OnFailure(ctx, job, cause)`. The two implementations do differ in exactly *when*, relative to dead-letter persistence, that surface fires — see "Dead-letter mapping" below and `handler.go`'s `FailureHook` doc comment.

`FailureHook` is not the queue's only way to learn a Job ended — the bus-carried terminal signal ("The terminal signal: `jobs.job.terminal`" below) is the cross-module counterpart — and the two surfaces are deliberately not merged; `handler.go`'s `FailureHook` doc comment states the boundary in both directions.

`StandaloneQueue.execute` calls it directly, once `completeDeadLetter` has persisted `StatusDeadLetter`. `asynq.Queue` cannot do the equivalent directly — asynq's `Handler.ProcessTask` (what `processTask` implements) has already returned by the time asynq itself decides whether an attempt's failure retries or archives — so `asynq.Queue` wires `asynq.Config.ErrorHandler` (`queue/asynq/worker.go`'s `handleError`/`handleErrorAttempt`) instead, the only hook point asynq offers for "a Handler failed." `handleErrorAttempt` replicates asynq's own archive-vs-retry boundary (`retried >= maxRetry`, read via the same `asynq.GetRetryCount`/`GetMaxRetry` a `Handler` could call itself) purely to decide whether *this* is the terminal attempt — it schedules or persists nothing, so this is reading asynq's own documented `MaxRetry` contract, not reimplementing its retry machinery. See "Distributed: asynq.Queue" → "Dead-letter mapping" for the full reasoning and its one documented edge case.

## The terminal signal: `jobs.job.terminal`

**Both implementations publish one `jobs.job.terminal` event (`EventJobTerminal`, payload `JobTerminalEvent` — `events.go`) on the bus they were configured with (`jobs.Put` / `asynq.Put`) whenever a Job reaches a terminal status: succeeded, dead-lettered or cancelled.** It is how a module learns a Job ended without polling it. The queue interprets nothing: the payload is a set of facts (job id, task type, terminal status, error, attempts, completed moment; never a `Result` body), `Event.TenantID` is the Job row's own tenant — a platform-scoped task's sentinel included, which a subscriber must not resolve as a real tenant — and what a subscriber does with the facts is its own concern (see `FailureHook`'s doc comment for the boundary against `OnFailure`, and `EventJobTerminal`'s own for the full consumer contract: at-least-once delivery and subscriber idempotency, the row as the truth — including the asynq leg's publish-before-archive caveat — and a subscriber's own reconciliation net where completeness matters).

**`StandaloneQueue` publishes from a row-level outbox: the Job row itself.** `terminal_published_at` (a `jobs` column on both dialects) is the marker, and its semantics are one sentence: *a terminal row with `terminal_published_at IS NULL` owes exactly one publish*. The obligation is the row's own state — the three terminal writes (`completeSucceeded`/`completeDeadLetter`/`markCancelled`) create it simply by moving the row to a terminal status, and a discarded attempt outcome (a concurrent Cancel won) creates none because it writes nothing. The publisher (`runTerminalPublisher`, `worker.go`) is launched by `Start` only when a bus is configured and strictly after the writer registration was acquired — the same single-writer gate the dispatcher runs under, so a multi-replica race on the outbox is closed by construction — and it publishes owed rows oldest-first (by the merged `completed_at`/`updated_at` transition order) at the poll cadence, **stamping the row only after `Publish` returned nil**. A failed publish or a failed stamp leaves the row owed, so the next pass republishes it: a duplicate, never a silent loss. Its immediate first pass is the crash catch-up — rows an earlier process left owed are republished at the next `Start`, the recovery spirit `resetInterruptedRecords` applies to execution — and `Close` deliberately runs no special flush (anything still owed belongs to the next `Start`). The upgrade backfill (the column add plus `terminal_published_at = the change moment` for every already-terminal row, both in one transaction per dialect, probed through each dialect's own column catalog) pins that the signal's contract starts at the change: historical terminal states are never republished, a re-run of the schema pass never re-stamps an owed row, and `idx_jobs_terminal_pending` (a partial index on `terminal_published_at IS NULL`) keeps the pass proportional to the owed set rather than the never-deleted terminal history. A cancelled row's terminal moment lives in its `updated_at`, because `markCancelled` records no `completed_at` — that is what the payload reports as `CompletedAt` for `StatusCancelled`, the pin both implementations share (`asynq.Queue` reports its cancellation marker's own timestamp, the moment `Cancel` recorded).

**`asynq.Queue` publishes directly, with no outbox, at its three terminal points**: the success record in `processTaskUncancelled`, the archive-bound dead-letter branch of `handleErrorAttempt`, and `Cancel` after the cancellation marker is durably written. The ordering is publish-before-asynq's-own-completion/archive write — the same concession `FailureHook.OnFailure` already documents for that implementation, and the reason a subscriber must not depend on the row having reached its terminal state by the time the event arrives. No outbox is needed on this leg because asynq's own redelivery converts a crash between the publish and the completion write into a repeated terminal arrival — a duplicate event rather than a lost one. A failed `Publish` is logged and never retried on this leg; the consumer contract's reconciliation clause is the completeness answer (see Known limitations for the leg's own bounds).

**The event type ships as the exported constant plus this documentation, not as a registry catalog entry.** `jobs` carries no module contract, and `pkgcore.EventRegistrar.Publishes` is a documentation-and-mapping contract rather than a publish precondition — the registrar's own wording — so no declaration path for non-module publishers was added: the catalog records what a module declares, and a subscriber reaches this event through the constant and this section.

## Periodic scheduling: `Scheduler` and the `Schedules` seat

**A periodic task exists because a module declared it, not because a host loop remembered to enqueue it.** Modules declare their periodic tasks on `pkgcore.ComponentRegistry.Schedules` (the `pkgcore.PeriodicTask` shape: job type, window `Every`, `Scope` — `Platform` or `PerTenant` — and the two enqueue inputs, `KeyPrefix` and the platform-scope `PlatformTenant` sentinel), and `jobs.Scheduler` is the driver that reads those declarations and enqueues them. Declaring means scheduled: a host that starts a scheduler over the finished registry schedules every declaration, and its single lever is whether a scheduler starts at all — there is no per-declaration approval step. A module declares a task exactly where it also registers that task's handler, so every declaration has an executor in the composition that made it.

**One tick walks the declarations in declaration order.** Each `Platform`-scope declaration is enqueued once, under its own sentinel tenant (`Task.TenantID`; pki's `_pki_platform_scan`/`_pki_platform_crl` are the precedents — a platform-wide task belongs to no single tenant, and one sentinel per task type keeps the two tasks' Job rows distinguishable wherever they are listed by tenant). Each `PerTenant`-scope declaration is expanded through the host's `TenantLister` — resolved once per tick, like the single universe resolution a hand-written host ticker performs — and enqueued once per tenant, each under that tenant's own context (`pkgcore.WithTenant`). The tick body is synchronous: every enqueue completes before the next tick can fire, and `time.Ticker` drops a tick rather than queueing it, so a slow tick can never pile up a backlog. A failed enqueue, and a failed tenant listing (which skips that tick's per-tenant declarations), are logged and retried on the next tick; the schedule never stops on an error.

**The idempotency key is where the cadence lives, and it must be byte-identical to the module's own.** Every enqueue carries a window-scoped key — the declaration's `KeyPrefix` + the tenant segment (per-tenant scope only) + the tick instant truncated to the declaration's `Every` on the absolute clock, as UTC RFC 3339 (`ScheduleWindowStart` + `ScheduleIdempotencyKey`/`SchedulePlatformIdempotencyKey`). Same-window ticks therefore resolve one key and collapse onto one job however many replicas tick; the first tick of a later window resolves a fresh key and the task runs again; a dead-lettered task poisons only its own window. Each declaring module's own `Enqueue*` method derives the same string from the same inputs, so a scheduler tick and a manual enqueue landing in one window dedupe onto one job rather than running the window twice — the per-site key-identity proofs live in each module's own window tests. The declared `Every` and the module's own window constant must agree for the same reason (pki declares its configured scan window, `WithExpiryScanWindow` included).

**Composition.** A `Scheduler` holds no state, only calls `Queue.Enqueue`, and runs unchanged on both deployment modes. Multiple replicas may each run one: convergence is the window-scoped key, not a leadership election — the same safety a hand-written host ticker had. Scheduling without executing on the same replica (a host that never called `StandaloneQueue.Start`) is a legal composition, as is the ordinary one where the replica schedules and drains. The reference app (`examples/reference-app/internal/app`) is the worked example: one scheduler over `reg.Schedules` with its configured-tenants-∪-D3-ledger universe as the lister, started on the same `APP_DISABLE_QUEUE_WORKER` gate that guards the queue worker.

## Observability

Every log line this package emits goes through `obs.FromContext(ctx)` (never a package-level or hand-built logger), with a constant message and `snake_case` key-value attributes — `job_id`, `job_type`, `tenant_id` (via `ctx`'s own tenant, attached automatically by `obs.FromContext`), `attempts`, `duration_ms`, `retry_in_ms`, `error`. See `worker.go`'s `execute`, `queue_standalone.go`'s `Enqueue`, and `queue/asynq/worker.go`'s `processTaskUncancelled`/`handleErrorAttempt`.

**`jobs.queue.depth`** is the queue-backlog gauge `docs/internal/09-observability.md`'s must-instrument table names for this module, wired by both `StandaloneQueue.Start` and `asynq.Queue.Start` via the shared `instrumentationName` constant (`queue_standalone.go`) — but with **different label sets**, and deliberately so. `StandaloneQueue.registerQueueDepthGauge` groups its SQL query by `(job_type, status)`, since a SQL `GROUP BY` can do that cheaply. `asynq.Queue.registerQueueDepthGauge` instead reports `(queue, status)`, where `queue` is one of the three priority tiers (`critical`/`default`/`low`): asynq's own `Inspector.GetQueueInfo` aggregates backlog **per queue**, not per job type, and listing every pending/retry task just to count them by type on every metrics-collector scrape would be disproportionate. The label set stays bounded to those three tiers, but the callback reports only the tiers asynq's own registry actually names, discovered per scrape from `Inspector.Queues()` rather than probed as a fixed set: asynq registers a queue only when its first task lands on it, and `GetQueueInfo` for a never-registered tier answers an internal NotFound that does not wrap the exported `asynqlib.ErrQueueNotFound` — so the fixed-set probe the callback used to make failed every Collect on a fresh deployment until a task had reached each tier (the defect the enumeration fixes; the real-Redis regression is `integration_test/queue_depth_gauge_test.go`'s `TestRedisQueue_DepthGauge_UnregisteredTierDoesNotFailCollect`, which fails on the pre-fix callback with `NOT_FOUND: queue "critical" does not exist`). Both label sets are low-cardinality and neither ever includes `tenant_id`, per root `CLAUDE.md`'s Prometheus-cardinality rule — a specific tenant's backlog is still a job for structured logs and trace attributes, on both deployment modes.

**`jobs.job.duration` / `jobs.job.attempts` / `jobs.job.dead_letter`** cover the must-instrument table's remaining task-queue rows beyond backlog depth — execution duration percentiles, failure rate, retry count and dead-letter count — on `StandaloneQueue` today: `queue_standalone.go`'s `registerJobMetrics` wires a `Float64Histogram` and two `Int64Counter`s (mirroring `observability.Middleware`'s own Counter/Histogram pattern for the HTTP row of the same table), recorded by `worker.go`'s `recordJobMetrics`/`recordDeadLetter` at the exact three points `execute` already logs "job succeeded" / "job attempt failed, scheduling retry" / "job exhausted retries, moving to dead letter". All three are labeled `(job_type, status)` (`jobs.job.dead_letter` by `job_type` alone), `status` being one of `StatusSucceeded`/`StatusRetrying`/`StatusDeadLetter` — never `tenant_id`, for the identical cardinality reason `jobs.queue.depth` gives above. Failure rate and retry count are both derived from `jobs.job.attempts` by slicing on `status` rather than each getting a dedicated instrument.

**The same three are wired on `asynq.Queue`** (`queue/asynq/queue.go`'s `registerJobMetrics`, recorded from `Start` with the identical fail-open contract), closing the recorded gap that once limited these rows to `StandaloneQueue` (the Known-limitations bullet below records the closed state). The recording sites mirror `StandaloneQueue`'s three outcome points onto the structure asynq actually offers: a success records at `processTaskUncancelled`'s own "job succeeded" log point (the mirror of `execute`'s success record, measured from the same attempt start), and a failed attempt's outcome records at `handleErrorAttempt` — the module's own replicated archive-vs-retry boundary, the one point that knows whether asynq will retry (`StatusRetrying`) or archive (`StatusDeadLetter`, plus the dead-letter Counter) — with the attempt's measured duration carried from the attempt to that decision point by an internal error wrapper (`failedAttemptError`/`wrapFailedAttempt` in `queue/asynq/worker.go`), since asynq's ErrorHandler hook receives no timing metadata of its own. Three deliberate divergences from `StandaloneQueue`'s rows, all consequences of asynq's hook structure and each recorded at its own code site: the outcome records fire BEFORE asynq's own settlement write (there is no post-settlement hook — the same ordering concession `FailureHook.OnFailure` already documents for this Queue); a retryable tenant-concurrency bounce or cancellation-marker refusal records nothing (no Handle ran, no retry budget was consumed — not a failure in the metrics' sense), while an ARCHIVE-bound terminal-attempt bounce does record the dead-letter outcome, since asynq archives it and `DeadLetterJobs` lists it; and an outcome whose attempt duration was never measured — a Handle panic asynq's own processor recovered, or that terminal-attempt bounce — records its attempts Counter row without a duration data point (`recordJobMetricsAttemptOnly`), the Histogram measuring only durations that were measured. A cancelled outcome records under none of the rows, exactly like `StandaloneQueue`'s cancel-wins discipline.

**`jobs.queue.depth`'s callback outlives the queue, by design — read the lifecycle contract before hosting a queue.** An OTel `ObservableGauge` callback cannot unregister itself (the API offers no such operation), so both queues' depth-gauge callbacks live for the whole process and are replayed onto every `MeterProvider` the process ever installs (otel's global delegation, once per process). A host that closes a queue and then shuts down its metrics provider — `observability.Init`'s shutdown performs a final collection, which runs every replayed callback — will therefore observe the gauge answering after `Close`. The contract that keeps this safe: `registerQueueDepthGauge` (both `queue_standalone.go` and `queue/asynq/queue.go`) holds `depthGaugeMu`'s read lock across its stopped-check **and** its query, `Close` holds the write lock while signaling the stop and letting go of the data source, and a stopped queue's callback answers nil instead of touching the data source — so a host is free to close the queue's database (or shared Redis client) as soon as `Close` returns, with no callback left mid-query. One `asynq.Queue` nuance: its `Close` signals the stop only on the success path that actually releases Redis; on the `ctx.Done` path nothing stops and the callback legitimately keeps answering. The regression pair `TestStandaloneQueue_DepthGauge_StopsQueryingAfterClose` and `TestQueue_DepthGauge_StoppedQueueDoesNotQueryRedis` pins both halves.

## The persistence model is platform data, not tenant data

This section is `StandaloneQueue`-specific; `asynq.Queue` has no GORM model, no `dbkit.Repository[T]` question, and no `tenancytest.AssertNotTenantScoped` proof to run at all — its only persistence is Redis, reached exclusively through asynq's own client/server/inspector, plus this package's own cancellation-marker keys (`queue/asynq/queue.go`'s `cancelMarkerKey`), which are plain `redis.UniversalClient` `GET`/`SET` calls carrying no tenant-scoping mechanism of their own (they are keyed by opaque `JobID`, and every caller-facing read of them — `Get`, `Cancel` — is already downstream of `callerMayAccess`'s own tenant check against the *task's* `tenant_id` header).

`jobRecord` (`store.go`) deliberately does **not** implement `dbkit.TenantScoped` — no `GetTenantID` method, no embedded `dbkit.TenantModel`. This makes it platform data: the dispatcher's claim query scans eligible `Job`s **across every tenant at once** — interleaved round-robin by tenant, with `Priority` ordering the rows *within* each tenant's own share (see "Per-tenant fairness" below) — to decide what to run next and to enforce per-tenant concurrency limits — an access pattern `dbkit.Repository[T]` cannot serve, and whose generic constraint would not even compile against a model like this. `tenant_id` is still a real, indexed column — read explicitly by the per-tenant concurrency gate and by `Queue.Get`/`Cancel`'s own access check (`callerMayAccess`, shared verbatim by `asynq.Queue`) — it is simply never auto-injected as a query filter. `store_test.go`'s `TestJobRecord_NotTenantScoped` (`tenancytest.AssertNotTenantScoped`) is the standing, CI-enforced proof of this property.

The `jobs` table itself is created imperatively (`store.go`'s dialect-branched `createJobsTableSQL`/`ensureJobsSchema`) rather than through `dbkit.MigrationRegistry` — an implementation detail specific to the standalone deployment mode, with no other consumer, since `asynq.Queue` creates no schema at all (asynq manages its own Redis key layout internally). The table's DDL is deliberately NOT a single portable statement: the payload and result byte columns are `BLOB` on SQLite and `BYTEA` on PostgreSQL (which has no `BLOB` type — a `BLOB`-typed `CREATE TABLE` fails there with `type "blob" does not exist`), so `ensureJobsSchema` selects the dialect's own statement at Start time, the same `db.Name()` branch the `claimed_by` column add uses. Both dialect spellings are exercised for real: the SQLite one by every `StandaloneQueue` unit test, the PostgreSQL one by the module's PostgreSQL integration leg (`integration_test/postgres_schema_test.go`, `dbtest.NewPostgres` + a real `StandaloneQueue` boot and row round trip) — SQLite-only coverage alone would never execute the DDL on the dialect that rejects it.

## Per-tenant fairness is two mechanisms at two different layers, on StandaloneQueue

"One tenant's backlog cannot starve another's" is the sum of two independent guarantees, not one — each closes a gap the other cannot:

- **Candidate SELECTION** (`store.go`'s `claimCandidates`): every dispatch tick's read of eligible rows interleaves round-robin across distinct tenants — each tenant's own highest-priority, oldest eligible row before any tenant's second, its second before any third, and so on (`ROW_NUMBER() OVER (PARTITION BY tenant_id ORDER BY priority DESC, scheduled_at ASC)`, then `ORDER BY` that rank first) — rather than a flat `ORDER BY priority DESC, scheduled_at ASC LIMIT claimBatchSize` over every tenant's rows at once. Without this, a single tenant with a backlog at or beyond `claimBatchSize` (100) truly-eligible rows, every one older than another tenant's own eligible rows, would fill the *entire* candidate window every tick — a different tenant's row would never even be **read back from the database**, regardless of concurrency limits, for as long as the flooding tenant's backlog stayed at or above `claimBatchSize`. The gap is pinned, not hypothetical: `candidate_window_fairness_test.go`'s `TestDispatchOnce_CandidateWindowDoesNotStarveOtherTenants` fails against the naive query and passes against the interleaved one. Priority therefore orders *within* a tenant's own share — and, at the same wave position, *between* tenants' head-of-line rows — never across a tenant's fair-share boundary: with tenant-a holding two `PriorityHigh` Jobs and tenant-b one `PriorityLow` one, a candidate window reads `[a-high, b-low, a-high]`, the shape `store_test.go`'s `TestClaimCandidates_FairShareRotationAcrossTenants_PriorityWithinTenantShare` pins.
- **Concurrency ADMISSION** (`worker.go`'s `tryReserveTenantSlot`/`releaseTenantSlot`, `dispatchOnce`'s skip-and-continue loop over whatever the query above already returned): a tenant already at `q.tenantConcurrency` running Jobs is skipped without claiming — `dispatchOnce` moves on to the next (possibly different-tenant) candidate in the same batch rather than stalling — see `TestPerTenantConcurrencyLimiting`. This alone says nothing about which rows make it into the batch to begin with, which is exactly the gap the interleaving above closes.

`asynq.Queue` (below) only ever needed the second mechanism — asynq's own dequeue has no equivalent of "read `claimBatchSize` candidates, then decide"; there is no batch to interleave, since asynq itself already decides dequeue order once per task, so the "Per-tenant concurrency limiting" section below documents *that* implementation's admission-only guarantee and should not be read as also covering a StandaloneQueue-style candidate-selection concern that does not exist for asynq in the first place.

## Distributed: asynq.Queue

`asynq.Queue` — `Queue` in its own `go/jobs/queue/asynq` subpackage (see "Packaging: why asynq.Queue is a subpackage" above) — is the distributed deployment mode's `jobs.Queue` implementation. This section keeps the naming convention that subpackage's own source uses throughout: `asynq.X` names one of ITS OWN exported members (`asynq.Queue`, `asynq.NewQueue`, `asynq.WithConcurrency`, and so on — all reached by importing `github.com/vislake/speed/go/jobs/queue/asynq`), while a bare, unqualified `asynq` (never followed by a capitalized member name in backticks) means the third-party `github.com/hibiken/asynq` library itself, which that subpackage's own source imports under the alias `asynqlib` specifically to keep its own package name (`asynq`) unambiguous in code — this document does not carry that alias into every prose mention, so read `asynq.Config`/`asynq.Task`/`asynq.TaskInfo`/`asynq.RetryDelayFunc` and similar capitalized-member mentions below as the third-party library's own types (`asynqlib.*` in the actual source), never this subpackage's.

This section is the mapping table the configure-don't-reimplement instruction produced: for every concern this package's contract defines, what asynq already provides natively, what needed a thin layer on top, and why. `asynq.Queue` implements the **exact same** `Queue`/`Task`/`Job`/`Handler`/`EnqueueOption` shapes `StandaloneQueue` does — nothing in this section changes any of those types.

### Task / Job / EnqueueOption → asynq primitives

| This package | asynq primitive | Notes |
|---|---|---|
| `Task.Type` | `asynq.Task`'s `typename` | Exact match, no asynq `ServeMux` prefix-routing involved — see "Why no `asynq.ServeMux`" below |
| `Task.Payload` | `asynq.Task.Payload()` | Unchanged bytes, never re-encoded — `Task.Headers` carries this package's own metadata instead (below), so `Payload` stays exactly what the caller gave `Enqueue` |
| `Task.TenantID` | `asynq.Task.Headers()["tenant_id"]` | `queue/asynq/store.go`'s `headerTenantID`. See "The tenant context trap" above |
| `Task.IdempotencyKey` | `asynq.TaskID(...)` (client Enqueue option) + `Headers()["idempotency_key"]` | See "Idempotency" below |
| `Job.CreatedAt` | `Headers()["created_at"]` (Unix nanoseconds) | asynq's own `TaskInfo` has **no** creation-time field at all — this package supplies one via `Headers`, the only durable, retry-surviving channel asynq offers for caller metadata |
| `EnqueueOption` `WithPriority` | `asynq.Queue(name)` (one of three fixed queues) + `Config.Queues` weights | See "Priority → queue mapping" below |
| `EnqueueOption` `WithMaxRetries` | `asynq.MaxRetry(n)` | Direct pass-through |
| `EnqueueOption` `WithTimeout` | `asynq.Timeout(d)` | Direct pass-through — this is also what bounds `handleCtx`, see "The tenant context trap" above |
| `EnqueueOption` `WithDelay` / `WithScheduledAt` | `asynq.ProcessAt(resolved.scheduledAt)` | `resolveEnqueueOptions` (shared with `StandaloneQueue`) already resolves both into one absolute time; asynq itself decides Pending-vs-Scheduled from whether that time is in the future |
| `Job.Status` | `asynq.TaskState` (+ this package's own cancellation-marker overlay) | See `queue/asynq/store.go`'s `statusFromTaskState` and "Cancel" below |
| `Job.Attempts` | `asynq.TaskInfo.Retried` (+1 in some states) | See `queue/asynq/store.go`'s `attemptsFromTaskInfo` — **not** simply `Retried+1` in every state; its own doc comment traces the exact asynq internals (`internal/rdb`'s `Retry`/`Archive` Lua scripts) this formula is pinned against, with a table test (`queue/asynq/store_test.go`) covering every case |
| `Job.MaxRetries` | `asynq.TaskInfo.MaxRetry` | Direct pass-through |
| `Job.Error` | `asynq.TaskInfo.LastErr` | Direct pass-through, same caveat as `StandaloneQueue`'s: operator-visible text, not a structured error |
| `Job.Result` | `resultEnvelope.Data`, read out of `TaskInfo.Result` | See "Progress reporting" below |

**Always-set `asynq.Retention` on every `Enqueue` call.** This is not optional tuning — it is required for `Get()` to work at all for a succeeded `Job`. Left unset, asynq deletes a completed task's entire record the instant it succeeds; `Get()` immediately after success would then report `ErrJobNotFound` instead of `StatusSucceeded`, silently breaking the single most basic use of this package. `asynq.DefaultCompletedRetention` (24h, overridable via `asynq.WithCompletedRetention`) is how long a succeeded `Job` stays visible to `Get()` — unlike `StandaloneQueue`'s SQLite row, which is never deleted. See Known limitations.

**Why no `asynq.ServeMux`.** asynq ships a `ServeMux` for longest-prefix routing of task types to handlers — a real feature, but one this package does not need: `Task.Type` is always matched **exactly** against a registered `Handler.Type()`, mirroring `StandaloneQueue`'s own `map[string]Handler` exactly. `asynq.Queue` registers a single `asynq.HandlerFunc` (`processTask`) directly with `asynq.Server.Start`, doing its own exact-match lookup via the same `handlers` map/mutex shape `StandaloneQueue` uses (duplicated, not shared — see `tryReserveTenantSlot`'s own doc comment for why touching `StandaloneQueue`'s fields was avoided). One concrete benefit: a claimed `Job` with no registered `Handler` reports the **exact same** `ErrHandlerNotRegistered` sentinel on both deployment modes, rather than `asynq.Queue` surfacing `ServeMux`'s own `asynq.ErrHandlerNotFound` text instead (which `ServeMux`'s fixed, non-overridable `NotFoundHandler()` would have forced).

### Priority → queue mapping

asynq's native priority mechanism is **named, weighted queues** (`Config.Queues map[string]int`, e.g. `{"critical":6,"default":3,"low":1}` — asynq's own documented example ratio, used verbatim as this package's default), processed proportionally to weight while all are non-empty. This package defines exactly three fixed queue names (`queue/asynq/store.go`: `queueCritical`/`Default`/`Low`) and maps `Priority` onto them: `>= PriorityHigh` → `critical`, `<= PriorityLow` → `low`, everything else → `default`.

**This is coarser than `StandaloneQueue`'s fully continuous `Priority` ordering**, and deliberately so: asynq's model is a small number of named queues, not a per-job numeric sort key, and a queue-per-tenant or queue-per-arbitrary-priority scheme would make every dequeue poll (which iterates the configured queue list) scale with tenant count instead of staying O(1) — see "Per-tenant concurrency limiting" below for why a queue-per-tenant scheme was rejected on the same grounds. A caller enqueuing with `Priority(7)` gets `default`, and `Get()` reports it back as `PriorityNormal` (5), not 7 — `priorityForQueue` is a many-to-one collapse's approximate inverse, not a lossless round-trip. `asynq.WithQueueWeights` overrides the three weights; it cannot add a fourth queue.

### Idempotency

`Task.IdempotencyKey`, when non-empty, becomes part of a **deterministic asynq TaskID**: `"idem:" + tenantID + ":" + idempotencyKey` (`asynq.Queue.Enqueue`) — and the deterministic id *is* the dedupe's durable record: while a task under that id exists anywhere in the three priority queues, any `Enqueue` for the same (`TenantID`, key) pair returns that first task's id (the JobID `Get`/`Cancel`/`DeadLetterJobs` resolve by), exactly like `StandaloneQueue`'s own unique-index-based `insertRecord` does for SQLite.

**What "derived" means here — and what it does not mean.** `Task.IdempotencyKey`'s doc comment defines the term this section and the integration example's "derived from the business operation, never random" comment use: derived means deterministic — a replay of the same operation reproduces the key — and says nothing about secrecy. The composition above is verbatim, so a key that embeds credentials or personal data (an email-shaped `"invite:" + address` key, the first shape a careless caller reaches for) surfaces that text word-for-word in the JobID, in the `job_id` attributes this queue's enqueue and claim-recovery log lines carry, and in the Job's own persisted record. The queue performs no content screening of its own — the caller-side warning on `Task.IdempotencyKey` is the whole gate — and go/observability's redaction cannot be the backstop: its value-shape net catches credential shapes, never PII, and `job_id` is exempt from even that scan so log lines stay joinable. Build keys from the operation's own opaque identifiers, exactly as the example does, and hash a PII-bearing identity into the key where that is all the operation has.

**The one subtlety asynq's native mechanism cannot cover, and this package's own layer on top of it: the uniqueness check is scoped PER QUEUE.** asynq's `ErrTaskIDConflict` check (`internal/rdb`'s `enqueueCmd` Lua script) only ever looks at `asynq:{<qname>}:t:<taskID>` for the single queue the task is enqueued into — confirmed against the pinned v0.26.0 source. Two same-key `Enqueue` calls at different `WithPriority`s would each pass their own queue's check and create **two independent, concurrently-executing copies of one Job** — the exact double-execution the idempotency contract exists to prevent. `asynq.Queue.Enqueue` therefore serializes concurrent first-inserts of one key through a **claim key** in this package's own namespaced keyspace (`queue/asynq/queue.go`'s `idempotencyClaimKey`, a short-TTL Redis `SET NX`): the winner re-probes all three queues (a completed enqueue may already own the key — dedupe on it), inserts at its own `WithPriority`'s queue, and releases the claim; losers wait for the winner's task to become visible (milliseconds) or for the claim to lapse if the winner crashed mid-insert, then take over. Per-priority delivery semantics survive — the first keyed `Enqueue` still lands in the priority queue its own `WithPriority` selected, and the surviving Job reports that priority — and the dedupe is queue-independent. Proven under genuine Redis-level concurrency (ten simultaneous same-priority `Enqueue` calls racing against real asynq/Redis, plus the cross-priority pair) by `TestAsynqQueue_ConformsToQueueContract`'s `idempotency_concurrent_enqueue_dedupes_to_one_handle_call` and `idempotency_same_key_across_priorities_dedupes_to_first_job` subtests (`integration_test/queue_conformance_test.go`, via the shared `queuetest.AssertConforms` suite).

**One real difference from `StandaloneQueue`, worth stating plainly: idempotency is not permanent in the distributed deployment mode.** `StandaloneQueue`'s SQLite unique index holds forever (the row is never deleted, "for as long as the first Job's record lives... on StandaloneQueue that lifetime is unconditional... regardless of what that first Job's outcome was" — `Task.IdempotencyKey`'s own doc comment, which states both modes' lifetimes side by side). asynq's dedupe record only holds for as long as asynq itself still has a live record under that id: indefinitely while Pending/Scheduled/Retry/Active, until `completedRetention` elapses once succeeded, or until evicted from asynq's own bounded-size archive once dead-lettered. A duplicate `Enqueue` call arriving after either window closes creates a **new**, independent `Job` rather than returning the original's id. See Known limitations. The one contract consequence a key *caller* must design around is stated on `Task.IdempotencyKey` itself: a key names one business-operation instance, so a task whose operation repeats over time (a periodic sweep) must scope its key to the period it is for — which is exactly what go/storage's and go/compliance's sweep keys do with their window-start suffix.

### Progress reporting

`ProgressFn` calls are persisted via `asynq.Task.ResultWriter()`, a mechanism asynq documents specifically for writing result/progress data from inside a running `Handler` — `Write` can be called any number of times, each call overwriting the prior one, and the latest write is immediately visible through `Inspector.GetTaskInfo` (i.e. through `Queue.Get`) regardless of whether the task is still `Active` or has already reached a terminal state. This is exactly "configuring asynq's own primitive correctly" rather than inventing a parallel Redis structure purely for progress.

The bytes written are `queue/asynq/store.go`'s `resultEnvelope{StartedAt, ProgressPct, ProgressMsg, Data}`, JSON-encoded — one struct doing double duty as both the progress channel and the final-success-result channel, because asynq's `ResultWriter`/`TaskInfo.Result` is a single `[]byte` slot, not two. `processTaskUncancelled` writes an envelope with `StartedAt` set (and progress at its zero value) **before** calling `Handle` — read back by `Get()` as `Job.StartedAt`, mirroring `StandaloneQueue`'s worker handoff (`markAttemptStarted`) stamping `started_at` at the moment a worker actually starts the attempt — then again on every `progress()` call, then once more on success with `Data` set to the `Handler`'s returned `Result.Data`.

**One deliberate, low-stakes difference from `StandaloneQueue`: progress resets to zero at the start of every new attempt**, rather than carrying a failed attempt's last-reported percentage forward the way `StandaloneQueue` does (`StandaloneQueue` only "carries it forward" because nothing ever resets it — no test in this package asserts on that carry-over behavior specifically). Recovering the previous envelope to preserve it across a retry would cost an extra `Inspector.GetTaskInfo` round trip on every attempt start purely to avoid a momentary 0% display during a retry — not judged worth it.

### Per-tenant concurrency limiting

**What asynq offers natively, and why neither fits:**
- **Named, weighted queues (`Config.Queues`)** — already used for `Priority` (above). Using one queue per tenant instead would make asynq's own per-poll queue iteration scale with tenant count, and a real deployment can have far more tenants than a small, fixed queue list should ever hold — rejected for the same O(1)-queue-count reason "Priority → queue mapping" gives.
- **Task grouping / `GroupAggregator`** — this is asynq's *batch aggregation* feature (combine N tasks in the same group into one before it ever reaches a `Handler`, e.g. batching notification sends), a completely different problem from limiting how many tasks belonging to one key may run **concurrently**. It offers no concurrency-limiting semantic at all, checked and rejected explicitly rather than overlooked.
- **`Config.Concurrency`** — a single global cap across every tenant and queue, the direct analog of `StandaloneQueue`'s `WithWorkerCount`. Necessary, but says nothing about how that shared pool is *distributed* across tenants.

**Conclusion: asynq has no built-in equivalent to "cap how many Jobs any one arbitrary, runtime-supplied tenant ID may run concurrently, out of a shared worker pool" — this needed a layer on top.** That layer is `queue/asynq/worker.go`'s `tryReserveTenantSlot`/`releaseTenantSlot`: the same `map[pkgcore.TenantID]int` + `sync.Mutex` shape `StandaloneQueue.dispatchOnce` uses, but applied at a different point in the pipeline, because asynq gives this package no way to peek at a task's tenant *before* dequeuing it off Redis the way `StandaloneQueue.dispatchOnce` can peek at a claim candidate before claiming it:

- `StandaloneQueue`: an over-limit candidate is **skipped without being claimed** — it stays `StatusPending`, `Attempts` untouched, and the dispatcher moves on to the next (possibly different-tenant) candidate in the same poll.
- `asynq.Queue`: by the time `processTask` runs, asynq has **already** dequeued the task and occupied one of `Config.Concurrency`'s global slots. Blocking inside `processTask` until a tenant slot frees up was considered and rejected: it would let one tenant's flood occupy every global concurrency slot with jobs that are all merely *waiting on each other*, which is precisely the starvation scenario per-tenant limiting exists to prevent. Instead, `processTask` bounces immediately — returns `errTenantAtCapacity` without ever calling `Handle` — freeing the global slot right away for the next dequeue, functionally equivalent to `StandaloneQueue`'s "skip and move on."

**The one piece that makes a fast bounce safe rather than merely fast: `asynq.Config.IsFailure`.** A naive bounce-and-retry would consume one of the Job's `MaxRetries` on every bounce, via asynq's own `internal/rdb` `Retry` Lua script (`if isFailure { Retried++ }`, confirmed by reading it directly) — a Job could then be dead-lettered purely from contention, having never actually run. `asynq.Queue`'s `Config.IsFailure` reports `false` specifically for `errTenantAtCapacity` (`queue/asynq/worker.go`'s `isFailure`), which the same Lua script honors by **not** incrementing `Retried` at all — so a throttled Job can bounce any number of times without ever burning into `MaxRetries`. `Config.RetryDelayFunc` (`retryDelay`) also special-cases the same error with a short, fixed, jittered delay (`asynq.WithThrottleRetryDelay`, default 200ms) instead of asynq's own exponential business-failure backoff, so a throttled tenant's backlog drains quickly once a slot frees rather than waiting out a multi-second exponential delay meant for genuine failures.

**The one edge `IsFailure` cannot cover: a bounce landing on a Job's FINAL allowed attempt.** asynq's own archive-vs-retry decision (`retried >= maxRetry`) is evaluated *before* `IsFailure` is ever consulted (confirmed by reading `processor.go`'s `handleFailedMessage` — its `switch` archives whenever `retried >= maxRetry` or the error is `SkipRetry`, with no `isFailure` branch at all). A bounce that lands exactly on what would otherwise be a Job's final allowed attempt is therefore **archived immediately** — the task is dead-lettered even though its last attempt never ran `Handle` (that is the price of not letting a permanently-contended Job retry forever). What this package guarantees instead is that such an archive-bound bounce is *not silent*: `handleErrorAttempt` (worker.go) fires the terminal attempt's `FailureHook.OnFailure` for it — a dead-letter that fires no `OnFailure` strands the Job's compensation, and the archive is the money event regardless of which error triggered it — and logs the bounce at `Error` level with its own message. A bounce with retries remaining, by contrast, consumes nothing and fires nothing. Proven against a real asynq/Redis pipeline by `integration_test/terminal_bounce_test.go`'s `TestRedisQueue_TerminalAttemptTenantBounce_ArchivesAndFiresFailureHook`, and at the unit level by `TestQueue_HandleErrorAttempt`'s terminal-bounce subtest.

Proven against a real `asynq.Server`/Redis, not a mock, by `integration_test/tenant_concurrency_test.go`'s `TestRedisQueue_PerTenantConcurrencyLimiting` — the same scenario shape as `queue_standalone_test.go`'s `TestPerTenantConcurrencyLimiting`, with `Config.Concurrency` deliberately small relative to the flood size so more than one of a flooding tenant's Jobs is dequeuable at once, the exact condition that would starve another tenant if bouncing blocked instead of returning immediately.

### Dead-letter mapping

A `Job` that exhausts its retries maps onto asynq's own **archived** state (`asynq.TaskStateArchived`) — asynq's own documented dead-letter equivalent ("archived and stored for inspection purposes"), reached automatically once asynq's own `retried >= maxRetry` check fires; this package never calls `Inspector.ArchiveTask` itself, since asynq already decides and performs this transition on its own. `asynq.Queue.DeadLetterJobs` maps onto `Inspector.ListArchivedTasks`, called once per priority queue with internal pagination (asynq's own page size default is small; this package fully drains each queue's archive rather than truncating at one page) — the direct analog of `StandaloneQueue.DeadLetterJobs`'s SQL `WHERE status = 'dead_letter'`.

**`FailureHook.OnFailure` has no direct asynq equivalent to hook into** — asynq's `Handler.ProcessTask` (`processTask`) has already returned by the time asynq itself decides an attempt's failure means archiving rather than retrying, and asynq offers no separate "task was just archived" callback. `Config.ErrorHandler` (`handleError`/`handleErrorAttempt`) is the closest available hook: it runs on **every** failed attempt, before that decision, so `handleErrorAttempt` replicates the same `retried >= maxRetry` boundary asynq's own processor uses (via `asynq.GetRetryCount`/`GetMaxRetry`, the same accessors a `Handler` itself could call) purely to recognize "this is the terminal one," then invokes `OnFailure` on a **freshly built** context (`pkgcore.WithTenant(context.Background(), tenantID)` + `q.defaultTimeout`) — never the just-failed attempt's own `ctx`, which may already be at or past its deadline — exactly mirroring `StandaloneQueue.execute`'s identical choice for the identical reason. The hook call itself is wrapped in `invokeOnFailure`'s panic recovery (`queue/asynq/worker.go`), the exact containment `StandaloneQueue` already had: asynq's own `processor.perform` recover covers ONLY the handler call, while its `ErrorHandler` — this package's `handleError` — runs outside it in `handleFailedMessage` (pinned v0.26.0 source), so without the recovery a panicking `OnFailure` would crash the whole process. See `queue/asynq/worker_test.go`'s `TestQueue_HandleErrorAttempt` for the unit-level proof (every case: retries remain, retries exhausted, no handler registered, handler without `FailureHook`, a bounce with retries remaining never fires the hook while an archive-bound terminal-attempt bounce does, a Cancel that landed during the terminal attempt silences the hook, and a panicking hook is recovered with the panic recorded) and `TestAsynqQueue_ConformsToQueueContract`'s `dead_letter_exhausts_retries_and_invokes_failure_hook` subtest (`integration_test/queue_conformance_test.go`) for the same guarantee against a real asynq/Redis pipeline, whose `integration_test/onfailure_panic_test.go` additionally proves a panicking hook leaves the real worker alive and processing later Jobs.

**This ordering choice is exactly the point where the two deployment modes' `FailureHook.OnFailure` contract stops being identical.** `handleErrorAttempt` runs (and thus `OnFailure` fires) BEFORE asynq's own archival write (`processor.go`'s `handleFailedMessage` calls the registered `ErrorHandler` unconditionally ahead of the `switch` that decides retry-vs-archive; confirmed against the pinned `github.com/hibiken/asynq@v0.26.0` source, not assumed) — there is no way to reorder this from inside the library, since asynq exposes no post-archive hook to move the call to. `StandaloneQueue`, by contrast, only invokes `OnFailure` once its own dead-letter `UPDATE` has actually persisted (`worker.go`'s `execute`, gated on `completeDeadLetter`'s transition report). Concretely: a `FailureHook.OnFailure` that reads its own `Job` back through `Queue.Get` observes `StatusDeadLetter` under `StandaloneQueue` but `StatusRunning` under this package's `Queue` — see `handler.go`'s `FailureHook` doc comment for the authoritative, mode-by-mode statement of this, and `TestAsynqQueue_OnFailure_ObservesTaskNotYetArchived` (`integration_test/failure_hook_ordering_test.go`) for the proof against a real asynq/Redis backend. A `FailureHook` implementation must therefore never depend on its own job's dead-letter persistence already having happened by the time `OnFailure` runs — the `OnFailure` call itself is the one and only "this Job has failed for good" signal, on both deployment modes.

**A concurrent Cancel silences `OnFailure` on this Queue exactly as on `StandaloneQueue`.** `handleError` consults the cancellation marker before `handleErrorAttempt` runs `OnFailure` on a terminal attempt, and `handleErrorAttempt` skips the hook when the marker is present — mirroring, at the failure hook point, the same cancel-wins semantics `StandaloneQueue.execute` gets from `completeDeadLetter`'s no-transition report (jobs' `worker.go`). Because asynq's own dispatch loop routes a ctx-cancelled or lease-expired terminal attempt through `handleFailedMessage` and thus through this same hook point, the marker check also covers attempts the handler never got to fail on its own — a Cancel that interrupted the attempt still must not let compensation run. Two ordering facts make the check sound rather than racy: `Queue.Cancel` (queue.go) writes the marker **before** sending its best-effort `CancelProcessing` signal, so every failure-processing path that signal itself triggers observes the cancellation as already durable; and `processTask`'s pre-dispatch marker check means a re-dequeued task never reaches `Handle` either. What this Queue cannot do is stop asynq's own archival write, which the dispatch loop still performs after the ErrorHandler returns — the raw task record of a cancelled Job can land in asynq's archive, invisible to this package's API (Get/`DeadLetterJobs` keep reporting `StatusCancelled` from the marker) but visible to `Inspector`/asynqmon. Proven against a real asynq/Redis pipeline by `integration_test/cancel_failure_hook_test.go`'s `TestRedisQueue_CancelDuringFinalAttempt_SkipsOnFailureHook`.

**Approximation accepted:** `q.defaultTimeout` stands in for the Job's own exact per-attempt timeout, which asynq's context accessors do not expose (`TaskID`/`RetryCount`/`MaxRetry`/`QueueName` only) — recovering the exact value would cost an extra `Inspector` round trip solely for this bound. A cosmetic one too: a throttle bounce still overwrites `TaskInfo.LastErr` with its own message (asynq's retry Lua script always records `LastErr`, regardless of `IsFailure`), so a Job dead-lettered by a terminal-attempt bounce (above) shows the bounce's message as its last error and hands the same message to `OnFailure`'s `cause` rather than the last genuine failure's.

### Cancel

`Cancel`'s only **permanent, authoritative** effect is the cancellation marker (`queue/asynq/queue.go`'s `writeCancelMarker`/`readCancelMarker`: a plain `redis.UniversalClient` key, `asynqjobs:cancelled:<id>`, namespaced clearly apart from every key asynq itself owns). `Get()` reports `StatusCancelled` from this marker **unconditionally**, regardless of whatever asynq's own underlying state naturally becomes — exactly mirroring `StandaloneQueue`'s `markCancelled` + its completion functions' `WHERE status = 'running'` no-op guard, which makes a still-in-flight attempt's eventual outcome unable to resurrect a cancelled Job.

**`Cancel` does NOT call `Inspector.DeleteTask` for a not-yet-running Job.** `DeleteTask` removes the task's entire `TaskInfo` record; a subsequent `Get()` would then find nothing to combine the cancellation marker with, and would report `ErrJobNotFound` for a Job the caller explicitly cancelled — indistinguishable from a Job that never existed. That failure is only reachable through a real delete against a real backend — a unit test built on a hand-constructed `*asynq.TaskInfo` can never exercise it — which is why the property is pinned, against a real Redis, by `TestAsynqQueue_ConformsToQueueContract`'s `cancel_tenant_isolation_and_idempotency` subtest (`integration_test/queue_conformance_test.go`): its Cancel-then-`Get()` leg would answer `ErrJobNotFound` for a deleted record. Instead:

1. `Cancel` leaves the task's own asynq record alone, and just writes the marker — **before** sending any `CancelProcessing` signal (the marker write comes first so that every failure-processing path the signal's interruption can trigger, including `handleErrorAttempt`'s own marker check, observes the cancellation as already durable; see "Dead-letter mapping" above). For an already-`Active` Job it then best-effort signals `Inspector.CancelProcessing` — see "The tenant context trap" above for why that can actually interrupt a running `Handle` call for `asynq.Queue`, unlike `StandaloneQueue`.
2. `processTask` checks for exactly this same marker as the very **first** thing it does, before even the handler lookup — if found, it returns `nil` without ever calling `Handle`, which asynq records as an ordinary successful completion (retained for `completedRetention`, exactly like a real success) rather than a retry or an archive. The check fails **closed**: a marker that cannot be *read* (Redis answered an error, never "no marker") refuses the run with `errCancelMarkerUnreadable` — a Job whose cancellation state cannot be verified might be cancelled and must not execute — redelivering on the short throttle delay without consuming retry budget until the read works again (see "Cancel" in the Error index and `marker_read_fail_closed_test.go`).
3. `Get()`'s marker-overlay (step 0 above) then reports `StatusCancelled` for that Job regardless, using the still-fully-intact `TaskInfo` for every other field (`Type`, `Payload`, `TenantID`, etc.). The overlay itself fails **closed** on the same unreadable-marker condition, by the same reasoning as step 2's refusal, restated for the reporting direction: a marker that cannot be *read* makes `Get()`/`DeadLetterJobs` return an error rather than report the Job's natural asynq state — a skipped-run Cancelled Job's task record reads as `Completed`, so a swallowed read failure would answer `StatusSucceeded` with an empty Result — the answer `go/ai-gateway/image_gateway.go`'s documented poll pattern ("once `Job.Status` is `jobs.StatusSucceeded`, `json.Unmarshal(job.Result.Data, ...)`") would then fail on as "unexpected end of JSON input". The cost argument transfers too: the marker is permanent, so a caller's retried read necessarily gets the right answer — a transient marker outage delays the report instead of corrupting it. Unlike the dispatch side's refusal (`errCancelMarkerUnreadable`, a named sentinel in the Error index), the reporting-side read failure is a plain wrapped error (`jobs: read cancellation marker: ...`): it is a normal "retry the call" answer, not a coded outcome any caller branches on.

This correctly satisfies "cancelling a `StatusPending`/`StatusRetrying` Job prevents it from ever being dispatched" (`Handle` never runs) without ever breaking `Get()`'s visibility contract. The accepted cost: every dispatched task now costs one extra Redis round trip (the marker check) even when never cancelled, and asynq's own internal processed/failed counters (visible via `Inspector.GetQueueInfo` or `asynqmon`) count a cancelled-before-dispatch Job as "processed" — asynq has no third bucket for "revoked."

Cancelling an `Active` Job is proven by `integration_test/cancel_test.go`'s `TestRedisQueue_Cancel_RunningJob`: `Get()` reports `StatusCancelled` **immediately**, without waiting for the in-flight (best-effort-interrupted) `Handle` call to actually return. The companion case — a Cancel that lands while the **terminal** attempt is in flight must also suppress the `FailureHook.OnFailure` that attempt's failure would otherwise trigger, in every interleaving asynq offers (the handler's own error, or a ctx cancellation the `CancelProcessing` signal caused) — is proven by `integration_test/cancel_failure_hook_test.go`'s `TestRedisQueue_CancelDuringFinalAttempt_SkipsOnFailureHook`; see "Dead-letter mapping" above for the mechanism.

### Close vs Shutdown

`asynq.Queue.Close(ctx)` keeps the same signature shape as `StandaloneQueue.Close(ctx)` for bootstrap-code ergonomics, but wraps a genuinely different underlying primitive. `asynq.Server.Shutdown()` takes no arguments at all — it waits for in-flight attempts up to `Config.ShutdownTimeout` (a **construction-time** setting, default 8s, not a per-call parameter), and if that elapses first, requeues whatever is still active back to Redis rather than waiting indefinitely; the orphaned goroutine itself is not force-cancelled (Go cannot do that) and keeps running to its own natural completion or per-attempt deadline — the exact same *shape* of behavior `StandaloneQueue.Close` documents for itself ("does not itself cancel an in-flight Handle call... waits... up to ctx's deadline"), just bounded by a value fixed at construction instead of supplied per call. `asynq.Queue.Close`'s own `ctx` parameter bounds how long *this call* waits for `Shutdown()` to finish, layered on top, not fed into asynq's own timeout.

## Retry, backoff and dead-letter

**StandaloneQueue.** Claiming a `Job` is deliberately **two-phase**: `claimOne` flips the row `pending`/`retrying` → `running` (stamping it with the claiming queue's writer token) at dispatch time, but the attempt is only *counted* at the worker handoff — `markAttemptStarted` increments `Attempts` and stamps `StartedAt` the moment a worker actually takes possession of the row, right before `Handle` runs. A Job that sits claimed-but-not-started therefore honestly reports through `Get()` as `StatusRunning` with `Attempts` not yet including an attempt no `Handle` has made, and an unclean exit in the claim-to-handoff window never consumes an attempt that never ran. On failure, `execute` compares `Attempts` against `MaxRetries`: `Attempts <= MaxRetries` → `StatusRetrying`, `ScheduledAt` moved forward by `backoffDelay(Attempts)` (`backoffBase * 2^(Attempts-1)`, capped at `backoffMax`); `Attempts > MaxRetries` → `StatusDeadLetter` (total attempts made = `MaxRetries + 1`), and, if the registered `Handler` also implements `FailureHook`, its `OnFailure` runs once. Every outcome's log line and metrics — success, retry and dead-letter alike — are recorded only **after** the conditional write (`completeSucceeded`/`completeRetrying`/`completeDeadLetter`) reports a genuine transition — never before the write, and never at all for an attempt whose outcome a concurrent `Cancel` already discarded (the no-transition case): exactly one truthful record, the `job cancelled before its <outcome> could <land>, outcome discarded` Info line, is emitted for such an attempt, so a cancelled Job shows up in none of the outcome logs or `jobs.job.attempts`/`jobs.job.dead_letter` counters.

**An outcome write that FAILS (as opposed to no-op'ing) converges through the same terminal machinery as a handler failure — the row is never left `StatusRunning` with no way forward.** If persisting an attempt's outcome errors — the success result, the retry scheduling or the dead-letter all alike — the row is still `StatusRunning`, the exact state a handler failure leaves, so `execute` settles the attempt as failed with an internal cause naming the persistence failure (`settleFailedAttempt`, worker.go): a retry is scheduled while attempts remain, and a budget-exhausted attempt dead-letters with the standard `OnFailure` run. The semantics of re-running after an unconfirmable success are deliberately the module's existing at-least-once ones: a crash between `Handle` returning and its outcome write landing already re-runs the row at the next `Start` (`resetInterruptedRecords`), so an outcome write that fails mid-process converges the same way instead of stranding the row until a restart — a live process has no lease and no reaper to move a row stuck in `StatusRunning`, so only the restart path could ever move it. Only a persistence failure whose own convergence write fails in turn is left for the next `Start`'s recovery: two consecutive write failures mean the database is refusing writes outright, and nothing further can be persisted in-process. Proven by `worker_test.go`'s `TestExecute_SuccessWriteFailure_SchedulesRetry_InsteadOfLeavingRowRunning` and `TestExecute_SuccessWriteFailure_OnFinalAttempt_DeadLettersWithCauseAndHook`.

**asynq.Queue.** The identical `Attempts`/`MaxRetries` arithmetic holds (see the mapping table's `attemptsFromTaskInfo` entry above and its own doc comment for the exact per-state formula), but the retry/archive **decision and the backoff delay itself are asynq's own**, not this package's: `asynq.MaxRetry` (set from `resolved.maxRetries` on every `Enqueue`) is what asynq compares its own `Retried` counter against, and `Config.RetryDelayFunc` (defaulting to `asynq.DefaultRetryDelayFunc`, an exponential Sidekiq-style formula — overridable via `asynq.WithRetryDelayFunc`) computes the delay, for every failure that is not a tenant-concurrency bounce (see "Per-tenant concurrency limiting" above). This package's own `backoffDelay`/`WithBackoff` (`worker.go`/`queue_standalone.go`) have no `asynq.Queue` equivalent by design — asynq already has a configurable backoff formula, and `asynq.WithRetryDelayFunc` is that same tuning knob shifted to asynq's own extension point rather than reimplemented.

A claimed `Job` whose `Type` has no registered `Handler` (`ErrHandlerNotRegistered`, the exact same sentinel on both deployment modes) is treated exactly like any other `Handle` failure on both — retried, then dead-lettered — rather than dropped or looped forever, so a startup-ordering mistake can resolve itself, and a genuine mismatch surfaces in `DeadLetterJobs` instead of vanishing silently.

}

    // handle err
}

    TenantID:       tenant,

    // ctx already carries job.TenantID -- a dbkit.Repository[T] call here

}

    h.credits.Refund(ctx, job.TenantID, job.IdempotencyKey) // business compensation lives here, not in jobs
}

## Rules

- **Never call a `Handler`'s `Handle` or `OnFailure` with any context other than one carrying exactly `job.TenantID` via `pkgcore.WithTenant`.** For `StandaloneQueue` this means `jobContext(job.TenantID)` (`worker.go`'s `execute`); for `asynq.Queue` this means `pkgcore.WithTenant(ctx, tenantID)` built from `t.Headers()[headerTenantID]` (`queue/asynq/worker.go`'s `processTaskUncancelled`/`handleErrorAttempt`). Do not "simplify" either by threading some other ambient context through instead, and do not assume any context available at a call site already carries the right tenant.
- **Do not add business-specific logic to this package**, on either deployment mode. `FailureHook` is the queue's entire failure-compensation surface — see "Failure compensation stays out of this layer".
- **Do not give `jobRecord` a `GetTenantID` method or embed `dbkit.TenantModel` into it** (`StandaloneQueue` only — see "The persistence model is platform data, not tenant data").
- **Do not use `dbkit.Repository[T]` for `jobRecord`** (`StandaloneQueue` only, same reasoning).
- **Do not persist a `context.Context`, or store one in `StandaloneQueue`'s or `asynq.Queue`'s own fields.** Each `Handle`/`OnFailure` call's context is built fresh, independent of the queue's own `Start`/`Close` lifecycle either way — see "Close vs Shutdown" for `asynq.Queue`'s version of this, and `StandaloneQueue.Close`'s own doc comment for the original.
- **Do not add a new `EnqueueOption` or change `Queue`/`Handler`/`Job`/`Task`'s shape without weighing BOTH implementations.** These are the pinned contract both `StandaloneQueue` and `asynq.Queue` satisfy — a change here is expensive on two implementations, not one, so public API stays frozen unless a breaking change is intentional.
- **Do not skip `tenancytest.AssertNotTenantScoped` for `jobRecord`** (`StandaloneQueue` only) because it "obviously" is not tenant-scoped.
- **Do not assume `Cancel` interrupts an already-running `Handle` call on `StandaloneQueue`.** `asynq.Queue`'s `Cancel` does best-effort attempt to, via `Inspector.CancelProcessing` — see "The tenant context trap" and "Cancel" above for why that is possible there and not on `StandaloneQueue`, and why neither is a hard guarantee.
- **Do not call `Inspector.DeleteTask` from `asynq.Queue.Cancel`.** This looks like the obvious way to stop asynq from processing a not-yet-run Job, and is wrong — see "Cancel"'s own section above for why `DeleteTask` breaks `Get()`'s visibility contract and the marker-plus-`processTask`-early-exit design is the shape used instead.
- **Do not enqueue an asynq task without `asynq.Retention` set.** Omitting it deletes a succeeded task's record immediately, breaking `Get()` for the success path — see "Task / Job / EnqueueOption → asynq primitives" above.
- **Do not let a per-tenant-concurrency bounce (`errTenantAtCapacity`) increment asynq's own retry counter.** `Config.IsFailure` reporting `false` for it is what makes an unbounded number of bounces safe — see "Per-tenant concurrency limiting" above; removing or bypassing that would reintroduce the "dead-lettered purely from contention" bug it exists to prevent.
- **Do not use `asynq.ServeMux` for handler dispatch.** This package's own exact-match `map[string]Handler` (mirroring `StandaloneQueue`'s) is what keeps `ErrHandlerNotRegistered` identical across both deployment modes — see "Why no `asynq.ServeMux`" above.
- **Do not call `handler.Handle` or `hook.OnFailure` directly from `StandaloneQueue.execute`.** Always go through `worker.go`'s `invokeHandle`/`invokeOnFailure`, which recover a panic raised inside either call into an ordinary `Handle` failure instead of letting it crash the whole worker-pool process — every tenant's in-flight and queued Jobs, not just the one that panicked. `asynq.Queue` needs no equivalent: asynq's own `processor.perform` already recovers the same call for free.
- **Do not let `StandaloneQueue.execute` call `Handle` for a `jobRecord` whose `tenant_id` column is empty.** `execute`'s dispatch `switch` checks `rec.TenantID == ""` (`errStandaloneJobMissingTenant`) as its own case, before the `default` case that calls `invokeHandle` — mirror that same shape if this is ever refactored, the way it already mirrors `asynq.Queue.processTaskUncancelled`'s `errTaskMissingTenant` check.
- **Do not remove `StandaloneQueue.Start`'s single-writer gate.** The `queue_writers` registration acquisition (refusing `ErrQueueWriterActive`) is what makes `resetInterruptedRecords`' reset of every `StatusRunning` row safe — without it a second writer resets and re-claims the first writer's mid-`Handle` rows into a double execution. Keep the order: acquire the registration, THEN reset, THEN launch; keep the heartbeat on its own goroutine (`worker.go`'s `runWriterHeartbeat`), NEVER on the dispatcher's poll tick — the dispatcher cannot reach its tick while blocked on the worker handoff or after `Close` has shut it down, exactly the periods a held row must stay fenced — and keep `Close` stopping that keeper only after every worker has finished, immediately before releasing the registration; and keep the claim's ownership stamp (`claimOne` writing `claimed_by`) and the reset's `claimed_by != owner` WHERE clause in step with it. Two further halves of the same ownership discipline must stay in step too: the registration row's stale moment (`stale_at`) is authored by the owning queue itself — acquire and every beat write last beat plus the OWNER's own `writerStaleAfter`, and a taking `Start` judges an incumbent ONLY by that authored moment, never by a window derived from the taker's own poll interval (a taker-side window would let a slow-cadence live incumbent be stolen into a double execution); and every execution write an attempt makes — `completeSucceeded`/`completeRetrying`/`completeDeadLetter`, and `updateProgress` with them — carries `claimed_by = owner` in its WHERE, so an attempt whose row another writer took over can neither settle nor stamp the sibling's row, its no-op'd outcome surfacing through `worker.go`'s `logDiscardedOutcome` as the double-execution anomaly it is, never as a cancellation.
- **Do not let a cancellation-marker read failure proceed to `Handle`.** `asynq.Queue`'s pre-dispatch marker check fails closed (`errCancelMarkerUnreadable`): a Job whose cancellation state cannot be verified must not execute. Keep `isFailure` reporting false for the refusal (no retry budget burned) and the short throttle delay on redelivery.
- **Do not count an attempt at the claim.** `StandaloneQueue`'s two-phase claim counts `Attempts` and stamps `StartedAt` only at the worker handoff (`markAttemptStarted`); counting at `claimOne` would inflate `Get()`'s report for a claimed-but-not-started Job and consume attempts a crash never let run.
- **Do not publish a terminal event outside the publish pass on `StandaloneQueue`.** The pass is the only publisher and `stampTerminalPublished` the only writer of `terminal_published_at`, and the stamp must stay strictly after a successful `Publish` — an inline publish at a terminal write, or a stamp before/independently of the publish, would break the outbox's "terminal row with a NULL stamp owes exactly one publish" definition (a lost event, or a never-sent event marked sent). Keep the pass's launch behind the writer registration in `Start`, and keep the nil-bus composition (no bus, no pass) — a pass without a bus would stamp rows nothing published.
- **Do not move the asynq publish points after asynq's own completion/archive writes, and do not add a fourth one.** The three points (`processTaskUncancelled`'s success record, `handleErrorAttempt`'s archive-bound branch, `Cancel` after the marker write) are the places the terminal decision is actually made; the publish-before-completion ordering is asynq's own hook structure (there is no post-archive hook), and the contract's row-is-truth clause depends on it. A failed `Publish` stays logged, never propagated into the retry/terminal path — the transition it announces has already happened.
- **Do not merge `FailureHook` and the terminal event into one surface.** `OnFailure` is in-process, dead-letter-only and per-Handler (compensation's home); `EventJobTerminal` is bus-carried, three-status and cross-module (the signal). A change that makes one do the other's job reopens the boundary `handler.go` documents.

## Known limitations

**Shared by both deployment modes:**
- **No queue-wide, cross-`Handler` observability of `DeadLetterJobs` beyond a plain list.** No requeue-from-dead-letter API on either deployment mode, and no *caller-facing* pagination (`asynq.Queue.DeadLetterJobs` paginates internally against asynq's own `Inspector`, but still returns one flat slice).
- **`Enqueue`'s idempotency is scoped per tenant, not globally**, on both deployment modes — deliberate, not a gap (idempotency keys are business-operation identifiers meaningful within one tenant's own operations).

**`StandaloneQueue`-specific**:
- **`Cancel` does not preempt an in-flight `Handle` call.** See "Rules" above for the contrast with `asynq.Queue`.
- **The `StandaloneQueue` schema's PostgreSQL dialect is exercised by the module's integration tier, not its unit tier** — `integration_test/postgres_schema_test.go` boots a real `StandaloneQueue` over `dbtest.NewPostgres` and proves the dialect-branched DDL (`BYTEA` columns — see the schema section above) builds, a row round-trips payload and result bytes, and the partial idempotency index dedupes on a real PostgreSQL. The distributed deployment mode's own Queue implementation (`asynq.Queue`) has no SQL schema at all, so this leg exists because a standalone-mode queue over real PostgreSQL is an ordinary composition, not because a second queue dialect needs verifying.
- **The dispatcher is a single goroutine.**
- **Exactly one live `StandaloneQueue` per jobs table.** `Start` refuses a second live writer (`ErrQueueWriterActive`, via the `queue_writers` registration row a dedicated heartbeat goroutine — `worker.go`'s `runWriterHeartbeat` — refreshes once per poll interval), because a second writer would reset and re-claim the first writer's mid-`Handle` rows into a double execution. The heartbeat deliberately does NOT ride the dispatcher's poll tick, and outlives `stopCh`: the registration must stay fresh while a worker holds a row — through the dispatcher's blocked handoff and through `Close`'s drain of in-flight `Handle`s, however long the drain runs — and a graceful `Close` releases it only after every worker has finished. Each registration row carries its own stale moment (`stale_at`, authored at acquire and refreshed at every beat as last beat plus the OWNER's own `writerStaleAfter` — two seconds or ten of ITS OWN poll intervals), and a taking `Start` judges the incumbent by that authored moment alone, never by a window derived from the taker's own configuration: two queues configured with different poll intervals — an overlapping rolling restart, an accidentally started second process with different settings — each keep their own registrations out of the other's reach, and a crashed process's registration is stolen at most its own `writerStaleAfter` after its last beat. Residual hazards worth naming (each logged every tick and operator-visible, and each genuinely not preventable without per-claim leases): a live queue whose OWN heartbeats cannot reach the database for longer than its own stale window — the keeper itself wedged, or the database frozen that long; a busy worker or a draining `Close` no longer qualifies — can still have its registration stolen while its workers run; and a registration row written by a release predating the `stale_at` column carries no stale moment at all (its writer's cadence is unknowable), so during a rolling upgrade across that boundary a taking `Start` judges such a row by a deliberately conservative fixed window (one minute) over its last heartbeat instead. An incumbent beating at a cadence different from the taker's own is NOT among these residuals — the row says when it goes stale, in its own numbers, and the taker reads that. What remains lease-shaped is only what is listed above; a slow-cadence live writer is not lease-shaped, because the authored stale moment already covers it.
- **A claimed-but-not-started Job reports honestly**: `Attempts` counts only attempts a worker actually started (the two-phase claim's handoff), so `Get()` during the claim-to-handoff window shows `StatusRunning` with `Attempts` not yet inflated, and a crash in that window consumes no attempt.

**`asynq.Queue`-specific:**
- **The `jobs.job.duration`/`jobs.job.attempts`/`jobs.job.dead_letter` metrics are wired on this Queue; what remains is recorded, not silent.** `registerJobMetrics` plus the recording sites in `queue/asynq/worker.go` give this Queue the same three outcome rows `StandaloneQueue` records (see "Observability" above for the full mapping). The honest residuals of the distributed form: every outcome record fires before asynq's own settlement write (no post-settlement hook exists; same concession as `FailureHook.OnFailure`), a retryable bounce records nothing while an archive-bound terminal bounce records the dead-letter outcome without a duration point, a recovered Handle panic records its outcome without a duration point, and the retry-vs-archive classification at the failure site can race a Cancel landing in the microseconds before asynq's own decision (StandaloneQueue's authoritative-row accounting discards that outcome; this Queue's record stands — bounded to a cancel racing a failure, documented at `handleErrorAttempt`). The regression suite is `queue/asynq/job_outcome_metrics_recording_test.go` (unit: registration, every outcome row, the bounce/cancel exclusions, the attempt-only branch) plus `integration_test/job_metrics_test.go`'s real-Redis leg for the success-site record.
- **Idempotency is bounded by asynq's own retention windows, not permanent** — see "Idempotency" above for exactly which windows and why.
- **A succeeded Job's visibility to `Get()` is bounded by `completedRetention` (default 24h), and a cancelled Job's by `cancelledRetention` (default 30 days)** — unlike `StandaloneQueue`'s SQLite rows, which are kept forever. Both are configurable (`asynq.WithCompletedRetention`/`asynq.WithCancelledRetention`) but neither can be made literally infinite without unbounded Redis growth becoming the operator's problem instead.
- **`Priority` is collapsed onto three fixed queues, not a continuous ordering** — see "Priority → queue mapping" above. `asynq.WithQueueWeights` retunes the three; it cannot add a fourth.
- **A per-tenant-concurrency bounce landing on a Job's otherwise-final allowed attempt is archived immediately rather than bounced again** — but the archive fires the Job's `FailureHook.OnFailure` and logs the bounce, never a silent dead-letter; see "Per-tenant concurrency limiting" above for the full mechanism and its proof. The same archive-bound rule covers an attempt refused because its cancellation marker could not be read.
- **`jobs.queue.depth` is labeled `(queue, status)` here, `(job_type, status)` on `StandaloneQueue`** — see "Observability" above for why asynq's own `Inspector.GetQueueInfo` cannot cheaply produce the finer label.
- **A cancelled-before-dispatch Job, and a per-tenant-concurrency bounce, both show up in asynq's own internal processed/failed counters (visible via `Inspector`/`asynqmon`) under "processed" or with a stale `LastErr`, not under any dedicated bucket of their own** — asynq has none; this package's own `Job.Status`/`Job.Error` remain correct regardless (see "Cancel" and "Dead-letter mapping" above), only asynq's own raw operational stats are approximate for these two cases. A third such case is a Cancel that lands during an already-terminal attempt: its raw task record can still be archived by asynq's own dispatch loop (see "Dead-letter mapping"), so asynq's archive may list a Job this package's API reports as `StatusCancelled`.
- **This package does not stand up asynq's own Web UI (`asynqmon`)** — that is a separate, independently deployable process/Docker image pointed at the same Redis, an operational/deployment concern outside a Go library's own scope, not something `asynq.Queue` embeds or launches.
- **The terminal signal's completeness has two recorded bounds on this leg, both deliberate.** A success event can be permanently missing after an outage longer than `DefaultCompletedRetention` (24h): the publish-before-completion ordering converts a crash into a duplicate, but once the completed record has expired there is nothing left for a backfill scan to find — dead-lettered events do not share this bound, since the archive is durable. A Start-time backfill scan over expired records is deliberately NOT shipped yet: it is deferred in `docs/internal/28-job-terminal-signal-and-periodic-schedule.md`'s open questions until this leg gains a real consumer (the reference app does not import `queue/asynq`), and the consumer contract's own reconciliation clause is the answer until then. The second bound is the success site's no-marker-re-read residual, shared with the outcome metrics: a Cancel that lands while an attempt runs and whose interruption the handler ignores (Handle returns nil anyway) publishes `StatusSucceeded` for a Job `Get()` reports as `StatusCancelled`, and an unreadable cancellation marker at the archive-bound branch publishes `StatusDeadLetter` for one the marker would have shown cancelled. Both are bounded to a cancel racing a terminal outcome, both are covered by the contract's row-is-truth clause, and both are documented at their code sites (`processTaskUncancelled` and `handleErrorAttempt` in `queue/asynq/worker.go`).
