# billing

go/billing owns speed's Plan/Feature/Entitlement domain model, a channel-agnostic Subscription/Invoice model, and the credits ledger -- the second, parallel billing mode credit-based (pay-per-use) products use alongside subscriptions. This file is the module-level discipline that ships with `go/billing` to consuming projects; the design rationale is `docs/internal/06-billing-and-metering.md`, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: round 1 (the foundation round), the gateway round, the credit-consumer round, and the credit-ledger audit round, described together below.** Round 1 shipped the Feature/Plan/Grant/Entitlements domain model with tenant-custom Plan lookup precedence, a channel-agnostic Subscription/Invoice model whose lifecycle is driven by a plain Go call, and the credits ledger (`credit_balance`, the append-only `credit_transaction` log, and the reserve → confirm/refund pattern, transactionally safe under concurrent deductions). The gateway round added: the `PaymentGateway` interface and `PaymentGatewayRegistry` (`gateway.go`), the tenant-scoped `PaymentEvent` model and its insert-first-dedup repository (`payment_event.go`), the active-polling fallback (`job.go`), and three real provider implementations under `go/billing/gateway` (`stripe`, `alipay`, `wechat` -- see that subpackage's own `AGENTS.md`). The credit-consumer round shipped no new `go/billing` code at all -- `CreditService`'s public API was already complete -- and instead wired it into a real, paid reference-app action for the first time: `examples/reference-app/internal/smilesim` now reserves, confirms and refunds credits around its own async AI smile-simulation job, discharging the "no reference-app consumer" gap this file's own previous revision recorded for `CreditService`. That previous revision was also stale on one other point, corrected here: `go/ai-gateway` no longer "does not exist" -- it shipped, with two real reference-app consumers of its own (`internal/consult`, `internal/smilesim`), before this round ever started; this round is what finally gives `CreditService` a real caller sitting next to it. The credit-ledger audit round closed the one remaining gap the credit-consumer round's own previous revision recorded here: `CreditService`'s five state-changing methods (`Grant`/`PreDeduct`/`Confirm`/`Refund`/`Expire`) now call `go/dbkit/audit`'s `Emit` after their own database transaction has already committed, under the exact five action names `Register` has declared since round 1 -- see "In scope in the credit-ledger audit round" below for the full write-up, and "Known limitations" for what this still does not cover. What none of these four rounds ships: actual money movement through a live payment-gateway consumer (no reference-app or other caller calls `CreateCharge` against a real Stripe/Alipay/WeChat account) or an HTTP surface for `go/billing` itself. Judge what exists by the code, not by this sentence.

## Scope

**In scope through round 1.** `Feature`/`FeatureKind`, `Plan`/`Grant`/`Money`/`BillingInterval`, and `Entitlements`/`Decision` (`model.go`) -- the domain shapes `docs/internal/06-billing-and-metering.md`'s own Go sketch names, adapted to this repository's real conventions (see "Design choice: Plan's tenant-scoping duality" below for the one deliberate storage-shape departure from the sketch's literal `TenantID *string`). `PlanStore`/`PlanService` (`plan.go`): CRUD plus `Resolve`, the tenant-custom-Plan lookup precedence a tenant-custom row for `(tenantID, key)` overrides the platform-wide row for `key` when both exist, falling back to the platform-wide row otherwise. `EntitlementsService` (`entitlements.go`): the `Entitlements.Check` implementation -- the single judgment entry point business code is meant to call; for a Quota-kind Feature it reads `go/metering`'s real-time counter through the small `UsageReader` interface (never a summary table, which has aggregation delay and would let an over-quota request through), and never itself decides anything about credits. `go/ai-gateway` has since shipped and is wired to `CreditService` (see the credit-consumer round below), but not to `Entitlements.Check` -- that judgment path still has no real caller anywhere in this codebase; see Known limitations. `Subscription`/`SubscriptionRepository`/`SubscriptionService` (`subscription.go`): a channel-agnostic internal domain concept with no payment-channel reference of any kind, whose lifecycle (`created`/`active`/`past_due`/`canceled`) is driven by a plain Go call this round (`Activate`/`MarkPastDue`/`Cancel`), publishing `EventSubscriptionStatusChanged` on every transition. `Invoice`/`InvoiceRepository` (`invoice.go`): the equally channel-agnostic billing-document counterpart. The credits ledger (`credit_balance.go`, `credit_transaction.go`, `credit_service.go`): `CreditBalance` (per-tenant `available`/`reserved`), the append-only `CreditTransaction` log (`grant`/`deduct`/`refund`/`expire`), and `CreditService`'s `PreDeduct`/`Confirm`/`Refund`/`Grant`/`Expire`/`Balance` -- the reserve → confirm/refund pattern every "pay-per-use that might fail" business operation needs, transactionally safe under concurrent deductions against the same balance (see "Concurrency: `applyBalanceDelta`" below). `pkgcore.Module` wiring (`module.go`): permissions for plan/subscription/credit administration, audit actions for the credit ledger's five state-changing operations (declared since round 1 and, since the credit-ledger audit round, genuinely emitted by every one of `CreditService`'s five methods -- see "In scope in the credit-ledger audit round" below), and the two published domain events (`billing.plan.changed`, `billing.subscription.status_changed`). A godoc `Example` (`example_test.go`) walking round 1's whole shape in one pass -- round 1's own compensating obligation for shipping with no reference-app consumer at all at the time; `CreditService` has since gained one (the credit-consumer round below), `Plan`/`Subscription`/`Invoice`/`Entitlements` still have none (see Known limitations).

**In scope in the gateway round.** `ChannelReference`/`ChannelStatus`/`NormalizedEventType`/`NormalizedEvent`/`ChargeRequest`/`ChargeHandle` and the `PaymentGateway` interface (`gateway.go`) -- the provider-agnostic seam a channel implementation satisfies, grounded in what `SubscriptionService`/`InvoiceRepository` actually need (creating a channel-side subscription or order, verifying and normalizing an inbound webhook, and re-querying a channel's authoritative status for a `ChannelReference`) rather than an abstract guess; `PaymentGatewayRegistry`, the package-level `pkgcore.SeamRegistry[PaymentGateway]` a provider subpackage's own `init()` registers into, mirroring `go/pki`'s `SignerRegistry`. `PaymentEvent`/`PaymentEventRepository` (`payment_event.go`): the tenant-scoped, durable, deduplicated record of every inbound webhook delivery `docs/internal/06`'s insert-first-to-dedup rule requires, keyed uniquely on `(channel, provider_event_id)`, with dual-dialect migrations (`migrations/{sqlite,postgres}/0006_create_billing_payment_events.sql`) matching round 1's own conventions. `PollingService`/`Module.WithQueue`/`Module.WithGateways` (`job.go`, `module.go`): the active-polling fallback `docs/internal/06`'s own "a callback may arrive before the order-creation response returns, or may never arrive at all" rule requires -- a `jobs`-scheduled, tenant-scoped task (`taskTypePoll`) re-querying every stuck `PaymentEvent` row through its owning channel's `PaymentGateway.QueryStatus`, claimed on `reg.Jobs` only when a host wires a queue via `WithQueue`, exactly like `go/storage`'s and `go/pki`'s own periodic tasks. Four new error codes (`billing.webhook_signature_invalid`, `.webhook_payload_unrecognized`, `.channel_reference_not_found`, `.payment_event_not_found`). Three real provider implementations, `go/billing/gateway/{stripe,alipay,wechat}` -- see that subpackage's own `AGENTS.md` for the full write-up, including the measured dependency cost of each and exactly what remains untestable without live credentials.

**In scope in the credit-consumer round.** No new `go/billing` code at all -- `CreditService`'s public API (`PreDeduct`/`Confirm`/`Refund`/`Grant`/`Balance`) was already complete and already tested. This round is entirely `examples/reference-app`'s own wiring, discharging the mandatory-first-consumer rule root `CLAUDE.md`'s "Reference App" section states ("a module API that it does not actually use is not considered done") for `CreditService` specifically: `internal/smilesim.Service.Simulate` reserves `CreditsPerSimulation` credits via `PreDeduct` BEFORE calling `aigateway.Gateway.GenerateImage` at all -- an insufficient balance returns `ErrInsufficientCredits` and go/ai-gateway (and any real vendor behind it) is never reached -- using an idempotency key minted once per generation request (`"smilesim:" + uuid.NewString()`) and reused for every later settlement call, since `PreDeduct` must run before go/ai-gateway's own job id even exists (`internal/smilesim/service.go`'s own `Simulate` doc comment has the full reasoning for why the job id itself cannot be the key here, unlike a more ordinary "reserve after enqueue" shape). `NotifyOnCompletion` -- the same poll-driven completion hook that already published `EventSimulationCompleted` -- settles that reservation once the async job reaches a terminal status: `Confirm` on `StatusSucceeded`, `Refund` on `StatusDeadLetter`/`StatusCancelled`, both safely idempotent under a repeated poll via `CreditService`'s own compare-and-swap contract. A follow-up round closed a real gap in that first cut: settlement was reachable ONLY through a client's own poll, and the job-id-to-idempotency-key mapping lived in a plain in-memory Go map, so a reservation whose caller stopped polling (or whose process restarted mid-flight) could stay `Reserved` forever with no path to settle it. `internal/smilesim` now persists that mapping in its own small `smilesim_credit_reservations` table (`reservation_store.go`, created imperatively like `go/jobs`' own `jobsTable`, not through a versioned migration -- it is an implementation detail private to this one package) and runs a periodic `ReconcileOutstandingCredits` sweep (`reconcile.go`, started by `StartReconciler` at boot, mirroring `go/config`'s own anti-loss poller) that settles any reservation whose job has already reached a terminal status through the same `jobs.Queue.Get` a real client would poll -- independent of whether anything ever polls, and surviving a process restart since the mapping itself is durable. `CreditService`'s own API needed no change for this: it is entirely a durability and reachability fix in the consumer's own bookkeeping. `examples/reference-app/cmd/server/demo_credits.go`'s `seedDemoCredits` grants each demo tenant a starting balance through a real `CreditService.Grant` call at boot -- explicitly NOT a payment, the deliberate, documented stand-in for a real credit-pack-purchase leg this round does not build (no live Stripe/Alipay/WeChat credentials exist in this environment; see `go/billing/gateway/AGENTS.md`). The mandatory end-to-end proof, `examples/reference-app/cmd/server/billing_credit_flow_test.go`, drives the real composed HTTP stack through all three scenarios: a sufficient balance generates successfully and is genuinely debited (read back through a real `CreditService.Balance` call over a second database connection, never merely trusted from the job's own reported status); an insufficient balance is refused before the fake AI-gateway endpoint is ever reached (asserted on that fake server's own request counter); and a failed generation (a fake vendor endpoint that always answers 500, exhausting go/jobs' retries into `StatusDeadLetter`) leaves the reservation refunded back to the pre-reservation balance.

**In scope in the credit-ledger audit round.** `CreditService`'s five state-changing methods (`Grant`, `PreDeduct` -- the reserve half -- `Confirm`, `Refund`, `Expire`) now each call `go/dbkit/audit`'s `Emit` under the exact action name `Register` has declared since round 1 (`AuditActionCreditGrant`/`AuditActionCreditDeductReserve`/`AuditActionCreditDeductConfirm`/`AuditActionCreditRefund`/`AuditActionCreditExpire`), following the identical declarative pattern `examples/reference-app/internal/notes/handler.go`'s `recordNoteCreatedAudit` already established as this codebase's real, working answer to "a business module explicitly calls `audit.Emit` after a state-changing operation succeeds" -- no new wiring shape was invented for this round. `credit_service.go`'s `emitCreditAudit` is the one place every call site funnels through: it is invoked only AFTER the mutating `dbkit.WithTenantSession` transaction has already committed, never from inside the closure, so `audit.Emit`'s own write opens a fresh, uncontended database session rather than nesting inside one still open -- the identical same-file `SQLITE_BUSY` hazard this file's own "Audit trail collection" precedent (mirrored from `go/dbkit/AGENTS.md`) documents for `AuditBus`'s automatic write-capture plugin, sidestepped here exactly the way notes' own handler sidesteps it, by construction rather than by avoiding the shared connection. A publish failure is logged at Error level and never turns an already-committed credit mutation into a reported failure to the caller, matching notes' own `recordNoteCreatedAudit` contract exactly.

The Resource every one of the five audited actions records is the `CreditTransaction` row itself (`Type: "credit_transaction"`, `ID` the ledger row's own id) -- the actual append-only fact each method adds to the ledger, mirroring notes' own choice to audit the created `Note` rather than some other aggregate it happens to touch. `Changes.After` carries the delta the specific call applied (`amount`, and `reason` when the caller supplied one) plus, best effort, the tenant's resulting balance (`resulting_available`/`resulting_reserved`). That resulting balance is read by `readBalanceForAudit`, called from INSIDE the same `dbkit.WithTenantSession` transaction that applies the operation's own delta, immediately after `applyBalanceDelta` and before commit -- deliberately NOT a separate query opened after commit (an earlier revision of this round did exactly that, via `CreditBalanceRepository.FindByID`, and a code-review pass caught the real correctness gap it left open: two concurrent operations mutating the SAME tenant's balance could have the first one's post-commit read observe the SECOND'S already-committed delta too, so its audit event would report a `resulting_available` that never corresponds to its own operation -- see `TestCreditService_Grant_ConcurrentGrantForSameTenant_BlocksUntilPriorTransactionCommits` in `credit_service_test.go` for the deterministic reproduction and fix proof, using the test-only `testHookAfterBalanceDelta` seam). Reading inside the transaction instead ties the read to exactly this operation's own applied delta: `applyBalanceDelta`'s own prior `UPDATE` holds the row locked until this transaction commits, so no concurrent transaction's write can land in between, on either dialect. A failure to read that resulting balance (logged, never blocking) simply omits the two balance fields from that one event -- it must never turn an already-succeeded credit mutation into a reported failure, or into a rolled-back transaction. `Result` is always `{Success: true}`: every call site invokes `emitCreditAudit` only once its own mutating transaction has already committed, so an audited action that reaches it has by definition succeeded.

Two of the five methods needed a genuine-state-change guard, not merely "call Emit on success", because both are idempotent under retry: `PreDeduct`'s fresh-reservation branch sets an internal `reserved` flag (false on the branch that instead finds an already-existing row for the same `IdempotencyKey`), and `resolve` (`Confirm`/`Refund`'s shared core) sets an internal `resolved` flag (false on the branch that finds the transaction already in the target terminal state) -- `emitCreditAudit` is called only when the flag is true, so a harmless retry of an already-settled reservation never produces a second audit record for an operation that did not happen this call. `Grant` and `Expire` need no such guard: both mint a fresh `uuid.NewString()` transaction id on every call (they are NOT idempotent under retry -- see Known limitations below, unchanged from before this round), so every successful call is by construction a genuinely new ledger entry. `Balance` remains entirely unaudited, exactly as `Register`'s declaration (five actions, never six) has always implied -- it performs no write.

`CreditService.events`/`.auditActions` are two new unexported fields wired post-construction by `module.go`'s `Register` (`m.credits.events = bus; m.credits.auditActions = reg.AuditActions`), the identical pattern `PlanService.events`/`SubscriptionService.events` already use -- `NewCreditService`'s own exported signature is untouched, so every pre-existing call site (every unit test in this package, `examples/reference-app/cmd/server/billing_credit_flow_test.go`'s own `openBillingCredits` helper) keeps compiling and behaving unchanged: a `CreditService` built directly through `NewCreditService` has `events == nil`, and `emitCreditAudit`'s own nil check makes every one of its five callers a complete no-op with respect to auditing, mirroring notes' own `Handler.bus == nil` short-circuit exactly.

`credit_service_test.go` is this round's unit-level proof: one test per method asserting the exact action name, `Resource`, `Result` and a real, useful `Changes.After` payload (never merely "Emit was called"), plus two negative proofs that the idempotent-retry paths of `PreDeduct` and `Confirm` do not double-emit, and one proof that `Balance` never emits at all. The reference-app end-to-end proof is `examples/reference-app/cmd/server/billing_credit_flow_test.go`'s `TestSmileSimulation_SuccessfulReserveConfirm_PersistsAuditEvents` and `TestSmileSimulation_FailedGeneration_PersistsRefundAuditEvent`: both drive `internal/smilesim`'s real reserve/confirm/refund cycle through the REAL composed HTTP stack (the same rig `TestSmileSimulation_SufficientCredits_DebitsBalance`/`TestSmileSimulation_FailedGeneration_RefundsReservation` already use) and read the resulting `audit_events` rows back through a SECOND connection to the same SQLite file via a real `audit.Repository.ListByTenant` call -- never a mock or an in-memory event assertion -- exactly the "buildServer hands out neither its `*gorm.DB` nor a module's own service" pattern `server_test.go`'s own `TestBuildServer_NoteCreate_PersistsAuditEvent` already established for notes. This is deliberately the same wiring choice notes' own test proves: an explicit `audit.Emit` call sharing `billingModule`'s and `auditModule`'s one database connection, never `dbkit.Options.AuditBus`'s automatic write-capture plugin, for the identical same-file `SQLITE_BUSY` reason. One pre-existing test in each of `server_test.go` and `examples/reference-app/integration_test/redis_eventbus_composition_test.go` needed a small, expected update alongside this round's own new tests: `TestBuildServer_NoteCreate_PersistsAuditEvent`'s and the Redis composition test's own tenant-acme assertion used to expect exactly one audit event for the whole tenant; now that `cmd/server/demo_credits.go`'s boot-time `seedDemoCredits` call is itself a real `CreditService.Grant`, tenant-acme (and tenant-globex, also demo-seeded) genuinely carries its own `billing.credit.grant` row from boot onward, so both tests now filter for the `notes.note.create` action specifically rather than assuming the tenant's whole audit trail holds nothing else -- a real, expected consequence of this round landing correctly, not a regression either test needed to paper over.

## Design choice: Plan's tenant-scoping duality

**Why `Plan` deliberately does not implement `dbkit.TenantScoped`.** `docs/internal/06-billing-and-metering.md`'s own Go sketch spells `Plan.TenantID` as `*string // nil = platform-wide; set = tenant-custom` -- illustrative Go, not this module's literal storage shape (the task that opened this round says as much: "the doc's sketch is illustrative, not literal Go to paste verbatim"). `Plan` is a genuinely dual-domain table (`docs/internal/04-data-and-tenancy.md`'s data-domain classification): a platform-wide row (`TenantID == ""`) is platform data, meant to be visible to *any* tenant's `Resolve` lookup; a tenant-custom row is that one tenant's private data. No single dbkit data-domain capability spans both faces of the same table -- `dbkit.TenantScoped`'s own isolation plugin would hide every platform-wide row from a tenant-scoped query, which is exactly the opposite of what "fall back to platform-wide when no tenant-custom Plan exists" requires.

This is not a novel problem: `go/config`'s own `configs` table (`system` → `tenant` scope tiers) solves the identical duality, and `Plan` adopts its exact answer, column for column -- a plain, `NOT NULL` `tenant_id` string column holding the empty-string sentinel (`platformScopeSentinel`) for a platform-wide row (empty rather than `NULL`, for the same reason `go/config`'s `row` and `go/dbkit/audit`'s `AuditEvent` both document: `NULL`s are distinct in a PostgreSQL unique index, so two platform rows for one key could coexist under `NULL` where the empty string collapses them into the one row the `(tenant_id, key)` unique index promises), reached through a plain `*gorm.DB` (`PlanStore`, never `dbkit.Repository[T]` -- the generic constraint requires `TenantScoped`, which this table must *not* implement), isolation proven with `tenancytest.AssertNotTenantScoped` rather than `AssertIsolated` (`TestPlan_AssertNotTenantScoped`, `plan_test.go`). The scoping this table actually needs -- "a tenant only ever sees its own custom Plans plus the platform-wide catalog, never another tenant's custom Plans" -- is enforced by `PlanStore.Resolve`'s own two-step lookup for read paths that resolve by `Key`, never by dbkit's isolation plugin. A caller-supplied Plan *id* (as opposed to `Key`) is a second path into the same table that `Resolve` does not cover, and `SubscriptionService.Create` is the one write path that accepts one (`CreateInput.PlanID`): it re-checks the resolved Plan's scope itself -- `Plan.IsPlatformWide()` or `Plan.TenantID` equal to the ctx tenant, refusing anything else with the same `ErrPlanNotFound` a genuinely missing id gets -- rather than trusting the id to already be scoped correctly.

A reviewer expecting `dbkit.Repository[Plan]` here, or flagging the missing `AssertIsolated` suite, should read this section (and `go/config/AGENTS.md`'s identical precedent) before treating either as a gap.

## Design choice: `CreditTransaction` does not embed `dbkit.Repository[T]`

`CreditTransaction` genuinely **is** tenant data (unlike `Plan` above) -- every row belongs to exactly one tenant, with no cross-tenant reader the way `go/metering`'s `Dispatcher` needs for its own `OutboxRecord`. But `CreditTransactionRepository` deliberately does **not** embed `dbkit.Repository[CreditTransaction]` the way every other tenant repository in this codebase does: embedding would promote `Repository[T]`'s own `Update` and `Delete` methods onto this type, which is exactly the mutability an append-only financial ledger must never offer -- the same "must be reconstructable/auditable from the transaction log alone" rigor `go/dbkit/audit`'s `AuditEvent`/`Repository` already establishes for this codebase's other append-only ledger. `CreditTransactionRepository` exposes only `Insert` and two read methods (`Get`, `ListByTenant`), mirroring `audit.Repository`'s own "`Insert`, `Get`, `ListByTenant`, and NO `Update` or `Delete` method at all" shape; `TestCreditTransactionRepository_HasNoUpdateOrDeleteMethod` proves it with the identical reflection check `go/dbkit/audit/repository_test.go`'s own `TestRepository_HasNoUpdateOrDeleteMethod` uses (Go has no way to assert "this type lacks a method" any other way that fails loudly on a future regression).

`CreditTransaction`'s primary key is the composite `(id, tenant_id)`, not `id` alone: a Deduct row's `ID` is the *caller's own* `IdempotencyKey` (see `CreditService.PreDeduct`'s doc comment), which is therefore not globally unique across tenants -- two different tenants may reasonably reuse the same idempotency-key string for their own, unrelated operations. This is the identical composite-key shape `go/metering`'s `UsageSummary` and `go/dbkit/audit`'s `IngestReceipt` both already use for the same reason, and `TestCreditTransactionRepository_SameIDDifferentTenants_DoesNotCollide` is the standing proof.

`CreditTransactionRepository`'s own CAS updates (inside `CreditService.resolve`, the `Confirm`/`Refund` shared core) go through `dbkit.WithTenantSession` plus a hand-written `session.Where(...).Updates(...)` call -- never `.Table`/`.Model`/`.Raw` (the three entry points `tools/semgrep_rules/raw-gorm-bypass.yml` flags) -- the identical sanctioned "raw-SQL escape hatch" shape `go/notification`'s `ContactService.consumePendingCode` already uses for an identical compare-and-swap need on a genuinely tenant-scoped table reached outside `dbkit.Repository[T]`.

## Concurrency: `applyBalanceDelta`, the ledger's one write primitive

Every `CreditService` balance mutation (`PreDeduct`, `Confirm`, `Refund`, `Grant`, `Expire`) funnels through one function, `applyBalanceDelta` (`credit_service.go`): a single database-arbitrated `UPDATE` that adds `availableDelta` to `Available` and `reservedDelta` to `Reserved`, guarded in the SAME statement so neither bucket can go negative (`WHERE ... available + availableDelta >= 0 AND reserved + reservedDelta >= 0`) -- never a Go-level read-modify-write. This is what makes concurrent callers safe: two `UPDATE` statements against the same row are serialized by the database itself (ordinary row locking, no dialect-specific atomic-increment feature required -- plain, portable SQL that runs identically on SQLite and PostgreSQL), so the second to run sees the first's already-applied change and its own guard evaluates against the *post-first-update* values, never a stale read a Go-level read-modify-write could race on. `TestCreditService_PreDeduct_ConcurrentOverBalance_OnlyOneSucceeds` (`credit_service_test.go`), run under `-race`, is the round's mandated proof: two concurrent `PreDeduct` calls whose combined `Amount` exceeds the tenant's balance cannot both succeed -- exactly one does, the balance ends up consistent, and the loser's own `CreditTransaction` row was never written (the whole attempt rolls back inside one database transaction).

`applyBalanceDelta` is a raw `.Exec(...)` call, not `dbkit.Repository[T]`'s own `Update` (a full-row `Save`, incapable of server-side arithmetic) and not a struct passed to GORM's `.Updates()` (which silently *omits* any field left at its Go zero value from the `SET` clause -- fatal here, since `Available` or `Reserved` legitimately reaching exactly zero must still be written). `.Exec` is a narrower surface than the three entry points (`.Table`/`.Model`/`.Raw`) the raw-gorm-bypass semgrep rule flags, and is the exact "raw SQL escape hatch" `backend-coding-standards` §3.2 sanctions for a genuine need like this one -- with the tenant passed explicitly into the `WHERE` clause (mandatory here, not merely defense in depth, since `.Exec` bypasses the ORM callback chain the isolation plugin hooks into) and an isolation test (`TestCreditBalanceRepository_AssertIsolated` proves the underlying table's own tenant scoping; every `applyBalanceDelta` call site runs inside `dbkit.WithTenantSession`, so on PostgreSQL the row-level-security GUC is also engaged as a second, database-level backstop underneath this application-level guard).

`CreditService.ensureBalance` materializes a tenant's first `CreditBalance` row (all-zero) with `INSERT ... ON CONFLICT (id) DO NOTHING` -- the identical dialect-neutral upsert clause `go/config`'s `store.put` already uses -- so two callers racing to touch a brand-new tenant's balance for the first time (`TestCreditService_Grant_ConcurrentCallsForANewTenant_BothSucceed`, also under `-race`) never both try to `Create` the same row.

## Design choice: `PaymentGateway`/`PaymentGatewayRegistry` live in billing's root package, never in `billing/gateway`

`docs/internal/06-billing-and-metering.md`'s own dependency-direction-must-be-one-way paragraph states the rule this section explains: `go/billing/gateway` (and its `stripe`/`alipay`/`wechat` sub-subpackages) may import `go/billing`, but `go/billing`'s own root package must never import `go/billing/gateway` or anything under it. That rule only holds if the seam a caller depends on -- the `PaymentGateway` interface, and the registry a provider registers into -- is declared somewhere neither side of the one-way edge would need to cross to reach it. Declaring both in `go/billing`'s own root package is what makes that true: a caller (business code today; a later round's live webhook endpoint eventually) depends on `billing.PaymentGateway` and resolves an implementation through `billing.PaymentGatewayRegistry`, never importing `go/billing/gateway` at all, while `go/billing/gateway/stripe`'s own `init()` imports `go/billing` (for `PaymentGateway`, `NormalizedEvent` and friends) to register itself. Putting the interface in the subpackage instead would force exactly the import edge the rule forbids: `go/billing`'s own domain code (`SubscriptionService`, a later round's webhook handler) would need to import `go/billing/gateway` to name the interface at all, which is precisely how `stripe.Subscription`-shaped types leak into the domain model over time -- the concrete failure mode the design doc warns about by name.

This is the identical shape `go/pki`'s `Signer`/`SignerRegistry` already established for its own `vault`/`kmsaws` provider split (`go/pki/signer_registry.go`'s own doc comment), applied here for the first time in `go/billing`. `PaymentGatewayRegistry` ships with no built-in implementation pre-registered, unlike `pkgcore`'s own `EventBusRegistry`/`KVStoreRegistry`/`MailerRegistry`/`ObjectStoreRegistry`: every `PaymentGateway` genuinely needs a provider SDK or a hand-rolled channel client, so there is no zero-dependency default the way `LocalSigner` is for `SignerRegistry`. `Module.WithGateways` is the `WithSigner`-shaped direct-injection half of the same duality `SignerRegistry`'s own doc comment describes: a host that already holds a constructed `PaymentGateway` (typically via `PaymentGatewayRegistry.Build` against a blank-imported provider subpackage) hands the resulting map to `PollingService` through it, rather than every call site doing its own name lookup.

The CI-enforced half of this rule -- three `depguard` entries in `.golangci.yml`, one per provider subpackage, each narrowed to that subpackage alone (not the whole `go/billing/gateway` tree) -- lives with the provider subpackages themselves; see `go/billing/gateway/AGENTS.md`'s own write-up of the full mechanism, including the SDK-choice rationale for each of the three providers and the measured dependency cost of each.

## Design choice: `PaymentEvent` is genuinely tenant-scoped, unlike `Plan`'s dual-domain shape

Round 1's `Plan` table (see "Design choice: Plan's tenant-scoping duality" above) is deliberately NOT tenant-scoped because a platform-wide row must be visible to every tenant's lookup. `PaymentEvent` has no such platform-wide face: every row belongs to exactly one tenant's payment history, decoded from the channel-side object's own metadata at webhook-verification time (`NormalizedEvent.TenantID`'s own doc comment describes the round trip -- `ChargeRequest`'s identifiers are attached to the created object via whichever metadata mechanism the channel offers, and `VerifyWebhook` decodes them back out). `PaymentEvent` therefore implements `dbkit.TenantScoped` and is reached through `dbkit.Repository[PaymentEvent]` -- the ordinary shape every other genuinely tenant-owned table in this module already uses, proven with `tenancytest.AssertIsolated` (`payment_event_test.go`), never `AssertNotTenantScoped`.

The uniqueness constraint the migration applies, `uq_billing_payment_events_channel_event` on `(channel, provider_event_id)`, is deliberately NOT further scoped by `tenant_id`: a channel's own event id is already globally unique across that channel's entire account, so widening the key to include `tenant_id` would only let a bug that mis-decodes `TenantID` silently create two rows for the one event it actually was -- the exact double-processing dedup exists to prevent. `PaymentEventRepository.InsertIfNew` is the sanctioned way to observe this constraint: it returns `(true, nil)` for a genuinely new event and `(false, nil)` -- never an error -- for one already recorded, which a caller MUST treat as "already handled, do nothing else" per `docs/internal/06`'s insert-first-to-dedup rule.

## Design choice: no config items this round

Unlike `go/metering`'s and `go/pki`'s own round-1 precedent (declaring a config schema without a live read this round), `go/billing`'s `Register` declares **zero** config items. There is no round-1 code path with a natural candidate: no trial-period length, grace-period duration, or default-credit-expiry-window is read, computed, or even referenced by anything `SubscriptionService`, `CreditService` or `EntitlementsService` actually does this round -- every one of those knobs belongs to the scheduler/gateway machinery a later round adds (dunning after a `past_due` subscription, a `jobs`-driven expiry sweep for `CreditService.Expire`). Inventing a config item now, with no code path to attach it to, is precisely the speculative-declaration pattern `go/metering/AGENTS.md`'s own "no `metering.unknown_feature`" section and `go/pki/AGENTS.md`'s "no `pki:revoke`" section both name and reject. `TestModule_Register_DeclaresItsSurface`'s `"no config items are declared"` subtest is the standing proof this stays true.

## Known limitations

- **`CreditService`'s five methods now call `audit.Emit` -- once a real gap, now fixed.** The credit-ledger audit round wired every one of `Grant`/`PreDeduct`/`Confirm`/`Refund`/`Expire` to `go/dbkit/audit`'s declarative `Emit` under the exact five action names `Register` has declared since round 1 -- see "In scope in the credit-ledger audit round" above for the full write-up. What this does NOT cover: an `audit.Emit` failure is logged at Error level and never retried or queued for later delivery, the identical "log, never return" contract notes' own `recordNoteCreatedAudit` accepts for the same reason (the underlying credit mutation already committed by the time `emitCreditAudit` runs, so a caller must never see an already-successful operation reported as a failure) -- a lost audit write in that narrow window has no compensating recovery path here, exactly as none exists for notes' own identical call. The resulting-balance fields in `Changes.After` (`resulting_available`/`resulting_reserved`) are similarly best-effort in one direction only: a genuine read failure (logged, inside `readBalanceForAudit`) simply omits the two fields from that one event, never blocking or failing the credit mutation itself. They are NOT best-effort with respect to concurrency any more, though: an earlier revision of this round read the resulting balance via a separate, post-commit `CreditBalanceRepository.FindByID` call, which had a real correctness gap under concurrent mutations of the same tenant's balance (a code-review finding, since fixed) -- see the "Changes.After" paragraph above for the mechanism and `TestCreditService_Grant_ConcurrentGrantForSameTenant_BlocksUntilPriorTransactionCommits` for the regression proof. Reading inside the mutating transaction closes that gap entirely: the resulting-balance fields are now exactly as reliable as the mutation itself, never merely a best-effort snapshot of "the balance at some nearby moment".
- **`SubscriptionService.Active` assumes at most one `active` subscription per tenant.** It scans the tenant's full subscription list in Go and returns the first `active` one found; a tenant with two concurrently active subscriptions (not something this round's own code can create, since nothing enforces single-subscription-per-tenant at the database level either) would have the second silently ignored. A later round wanting genuine multi-subscription support needs its own uniqueness decision here.
- **`CreditService.Expire` is not idempotent under retry.** Its `CreditTransaction.ID` is a fresh `uuid.NewString()` every call, unlike `PreDeduct`'s caller-supplied `IdempotencyKey` -- this round ships the mechanism a future expiry scheduler would call, not the scheduler itself. A later round wiring a real `jobs`-driven sweep needs its own idempotency key, the same shape `go/storage`'s `EnqueueExpirySweep` already establishes for an identical "scheduled sweep must not double-apply" need.
- **No PostgreSQL integration tier for this module's own tables.** See Testing above.
- **`CreditService` now has a real reference-app consumer; `Plan`/`Subscription`/`Invoice`/`Entitlements` and the payment-gateway lifecycle still do not.** The credit-consumer round wired `internal/smilesim` into `CreditService`'s `PreDeduct`/`Confirm`/`Refund`/`Grant`/`Balance` end to end (see "In scope in the credit-consumer round" above) -- root `CLAUDE.md`'s mandatory-first-consumer rule is discharged for that surface specifically, not for `go/billing` as a whole. `Plan`/`Subscription`/`Invoice` and `EntitlementsService.Check` still have none: `docs/internal/06`'s full pay-per-use-AND-subscription credit flow needs real payment-channel credentials to be meaningful end to end, which this environment does not have (see `go/billing/gateway/AGENTS.md`). The compensating obligation for THAT remaining gap is unchanged from before: round 1's real, runnable godoc `Example` (`example_test.go`) walking Plan creation, Subscription activation, both `Entitlements.Check` grant kinds, and the credits ledger's reserve → confirm pattern in one pass, plus the gateway round's own three provider-package `Example`s each (construction, `PaymentGatewayRegistry` self-registration, and `ExampleGateway_VerifyWebhook` -- a real, doc-rendered signature verification plus normalization against a constructed fixture) -- the identical pattern `go/pki`'s X.509 layer and `go/metering`'s own round both already establish for the same situation.
- **Credit settlement's reachability and durability, once a real gap, is now fixed -- and what still isn't.** The credit-consumer round's first cut settled a reservation ONLY through `NotifyOnCompletion`, itself reachable only by a client polling the job-status route, with the job-id-to-idempotency-key mapping held in a plain in-memory map -- a reservation could be left `Reserved` forever if nobody kept polling, or if the process restarted while a job was still running, with no error and no log distinguishing that case from an ordinary, intentionally-unwired `CreditService`. A follow-up round fixed both halves: `internal/smilesim.ReservationStore` durably persists the mapping (surviving a restart) and `Service.ReconcileOutstandingCredits`/`StartReconciler` periodically settle any reservation whose job has already finished, independent of any poll -- see "In scope in the credit-consumer round" above for the mechanism. What this fix does NOT cover: a failure to persist the reservation row itself, immediately after a successful `PreDeduct` and enqueue (an exceedingly narrow window -- a database write failing at exactly that moment) is still logged and left for manual reconciliation rather than automatically recovered, since there is no durable record to recover from in that specific case; and the reconciliation sweep's interval (`DefaultReconcileInterval`, 5 minutes) means a never-polled reservation's balance correction can lag by up to that long, never instantly, unlike the poll-driven fast path.
- **The credit-consumer round's demo credit seed is a `Grant`, never a payment.** `examples/reference-app/cmd/server/demo_credits.go`'s `seedDemoCredits` grants each demo tenant a fixed starting balance at boot so `internal/smilesim`'s reserve/confirm/refund wiring has something real to reserve against -- it is explicitly NOT a "buy a credit pack" flow, and no real Stripe/Alipay/WeChat sandbox purchase exists anywhere in this codebase (see `go/billing/gateway/AGENTS.md`'s "no live credentials" note). A real credit-pack-purchase HTTP flow remains a later round's work, whenever this environment gains live payment-provider credentials.
- **`seedDemoCredits`'s own idempotence is bounded, deliberately.** `CreditService.Grant` is not idempotent under retry (a fresh `uuid.NewString()` transaction id every call), so `seedDemoCredits` guards a second boot against the same database file by checking the tenant's balance is still all-zero before granting again -- a tenant that has genuinely spent its way down to exactly zero on its own would be re-seeded. Acceptable for a reference app's own demo feature (`demo_credits.go`'s own doc comment states this explicitly), not a pattern a real deployment's credit-pack purchase flow should copy.
- **`PollingService.Poll` does not drive any `Subscription`/`Invoice` transition.** It updates `PaymentEvent.Status` alone from what `PaymentGateway.QueryStatus` reports -- a deliberate round boundary, not an oversight: no HTTP surface exists yet to receive a live webhook in the first place, so there is no live processing loop for the polling fallback to feed into, and half-wiring one without a real caller to prove it against is exactly the kind of speculative build-ahead this file declines elsewhere for the identical reason (see the Scope table's "Driving `Subscription`/`Invoice` transitions from a `PaymentEvent`" row). A later round's live webhook endpoint is where a `PaymentEvent`'s `Status` actually starts driving billing's own domain state.
- **No live consumer calls `CreateCharge`/`QueryStatus`/`VerifyWebhook` against a real payment channel.** Every provider package's real, offline-verifiable cryptography is genuinely implemented and genuinely tested (see `go/billing/gateway/AGENTS.md`'s own "What remains untestable without live credentials" section for the itemized, honest split between what is and is not exercised this round). No reference-app or other consumer holds live Stripe/Alipay/WeChat Pay credentials to call any of the three providers' `CreateCharge`/`QueryStatus` against a real account, or to receive a real webhook delivery from one.
- **The root `CLAUDE.md` census entry for `go/billing` is follow-up work outside this history's stated scope**, the same deferral `go/pki`'s, `go/integration`'s and `go/metering`'s own onboarding rounds recorded for themselves (`fast-check.yml`'s own header comment says so explicitly).
