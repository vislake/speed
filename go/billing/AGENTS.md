# billing

go/billing owns speed's Plan/Feature/Entitlement domain model, a channel-agnostic Subscription/Invoice model, and the credits ledger -- the second, parallel billing mode credit-based (pay-per-use) products use alongside subscriptions. This file is the module-level discipline that ships with `go/billing` to consuming projects; the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Metrics instrumentation.** The 09-table "payment" row is instrumented at the sites this module genuinely has (`metrics.go`, unit-tested through ManualReaders in `metrics_test.go` and each provider's own VerifyWebhook suite — alipay and wechat in `notify_test.go`, stripe in `gateway_test.go`): `billing.invoice.transition` (applied status transitions, from/to labeled -- recorded only where the guarded compare-and-swap UPDATE genuinely applied, refused moves never count) and `billing.invoice.open_dwell` (time an invoice stayed open, recorded at the transition out), both owned by `InvoiceRepository.setStatus`; and `billing.webhook.verify`, one shared counter on the billing meter that each provider's real `VerifyWebhook` records onto with its own channel label (stripe/alipay/wechat) and an outcome classified from the returned error's nilness through a defer over the named return. The shared register/record helpers are the one additive export on the billing root. The row's "intermediate-state ORDER count" is deliberately carried by invoices (the ledger's orders) rather than double-instrumented on the Subscription lifecycle's own intermediate-state vocabulary, recorded in `metrics.go`'s doc comment; the webhook outcome stays a succeeded/failed binary -- the finer signature-vs-payload classification is a diagnostic refinement the 09-table's first-alert list does not name.


## Status

**Shipped surface.** The Feature/Plan/Grant/Entitlements domain model with tenant-custom Plan lookup precedence, a channel-agnostic Subscription/Invoice model whose lifecycle is driven by a plain Go call, and the credits ledger (`credit_balance`, the append-only `credit_transaction` log, and the reserve → confirm/refund pattern, transactionally safe under concurrent deductions). The payment-gateway layer adds the `PaymentGateway` interface and `PaymentGatewayRegistry` (`gateway.go`), the tenant-scoped `PaymentEvent` model and its insert-first-dedup repository (`payment_event.go`), the active-polling fallback (`job.go`), and three real provider implementations under `go/billing/gateway` (`stripe`, `alipay`, `wechat` -- see that subpackage's own `AGENTS.md`). The reference app consumes both of billing's halves end to end: `internal/smilesim` reserves, confirms and refunds credits around its async AI smile-simulation job, and go/ai-gateway's entitlement gate judges every `Chat`/`ChatStream`/`GenerateImage` call against a real `EntitlementsService.Check` (both wirings detailed in the Scope section below). The module's own HTTP surface is a deliberately read-only OpenAPI fragment -- two GET operations under `/api/v1/billing` -- mounted and consumed end to end by the reference app's credits view (see the HTTP-surface subsection below). What is not shipped: actual money movement through a live payment-gateway consumer -- no reference-app or other caller calls `CreateCharge` against a real Stripe/Alipay/WeChat account (see Known limitations).

**Dialect-portable and provider-boundary semantics.** (1) `PreDeduct`'s idempotent-retry recovery never aborts the transaction that reads its own earlier reservation back: the duplicate insert runs as `ON CONFLICT DO NOTHING`, because a unique-violation error inside an open transaction poisons it on PostgreSQL (SQLSTATE 25P02) while SQLite tolerates a failed statement -- the divergence only a real-PostgreSQL tier can show, which is why go/billing carries one (see Testing). (2) `gateway/stripe`'s `CreateCharge` attaches the correlation identifiers under `subscription_data.metadata` too (a Checkout Session's own metadata is never copied onto the subscription Stripe creates at completion), and `normalizeInvoice` reads them from the invoice's real `parent.subscription_details.metadata` snapshot rather than the invoice's own metadata field -- without both, the renewal events (`invoice.paid`/`invoice.payment_failed`/`customer.subscription.updated`) would be refused as unrecognized on real deliveries. (3) `gateway/alipay`'s `normalizeNotify` distinguishes refund notifications: a partial-refund `TRADE_SUCCESS` (carrying `refund_fee`/`gmt_refund`) is refused loudly rather than normalized into an event byte-identical to the payment the dedup ledger would swallow, and a full-refund `TRADE_CLOSED` maps to `NormalizedEventRefunded`/`ChannelStatusRefunded` while an unpaid-timeout `TRADE_CLOSED` keeps mapping to `ChargeFailed`. (4) `EntitlementsService.Check` fails closed on a string grant value that is not the `GrantValueUnlimited` sentinel instead of reading any string as Unlimited. (5) The fixture shapes these behaviors rest on are the real provider delivery shapes -- the stripe invoice fixtures carry the identifiers in the parent snapshot, never hand-seeded onto the invoice, and the alipay fixtures carry the real notify parameter vocabulary.

**The poll failure log is bounded, never raw provider text.** `PollingService.Poll`'s `QueryStatus`-failure log line never records the raw gateway error under the "error" attribute. A `PaymentGateway` error is external-provider free text by construction -- the `wechatAPIError` message a WeChat Pay APIv3 refusal body carries, alipay's query-failed envelope fields (`Msg`/`SubMsg`), a Stripe SDK error -- and the poll line is the one log point every gateway's errors converge on, so the failure branch there is where the discipline has to hold. go/observability's redaction layer masks secret-shaped values and sensitive attribute-key names, never arbitrary free text under a benign, ubiquitous key like "error", so the log point bounds the value itself: the line carries a `failure_class` attribute holding `pollFailureClass`'s answer -- the error's own apperr code when it is (or wraps) a typed `*apperr.Error` (the code space today holds `billing.channel_reference_not_found`; a gateway mapping more provider conditions onto billing codes automatically refines the line), and the fixed literal `unclassified` otherwise. The code is read from the error's `Code` only, never by stringifying the error -- an apperr with an unbounded cause renders `code: cause`, so even the typed case must not reach the log as text; a status code is deliberately not logged either, because none is available in bounded form at this point (`apperr.Status` is a suggested API-response status, not the channel's own answer). The discipline lives at the log point, not in the gateway files: each provider's own error text stays what it is, simply never logged raw. The persistence side carries no such field at all -- no `LastError`/`ErrorMessage`-shaped column or field exists anywhere in billing's non-test code. `TestPollingService_Poll_QueryFailureLogsClassificationNeverRawText` scripts two failure shapes carrying a distinctive fragment -- an opaque gateway error and a typed billing error with the fragment as its unbounded cause -- and asserts that no attribute of the poll log carries the fragment: `failure_class` holds the bounded classification.

**Update, quota and webhook edge semantics.** (1) `PlanStore.Update` with an empty `plan.ID` answers the coded `ErrPlanNotFound` up front instead of silently INSERTING a new row: GORM's `Save` performs a Create whenever the primary key is blank (the Where clause notwithstanding), and no stored Plan can carry an empty ID (Create generates a UUID when left blank). `Save` is this module's only insert-capable update shape; every other row mutation -- subscription, credit, payment-event and invoice guarded updates -- is a `.Updates(...)` with `RowsAffected` as the arbiter and cannot insert. (2) A `FeatureKindQuota` `Check` on an `EntitlementsService` built without a `UsageReader` (nil) fails closed with the coded `ErrUsageReaderUnconfigured` (`billing.usage_reader_unconfigured`, an `apperr.Internal` configuration error) on the first such call -- never a panic on the nil interface call and never a guessed allowance (a zero-usage guess would fail open for an over-quota tenant). Boolean and Unlimited features never consult the reader and are unaffected. (3) The Quota decision never truncates the float64 usage count toward zero at the decision point: used counts round UP (ceil) to whole units, the tenant-hostile direction, so 99.9 used + 1 requested cannot pass a limit of 100. (4) `Decision.Remaining` is a `*int64` whose nil IS the unbounded marker: an unbounded decision -- Boolean/Unlimited features, and the `feature_disabled`/`no_subscription` answers -- surfaces nil, a distinguishable absence a UI-shaped consumer can never render as a real remaining count; there is no `-1` sentinel, which would collide with the genuine `-1` raw headroom a bounded overage decision legitimately reports. The exported `DecisionRemainingUnbounded` sentinel constant does not exist in this API -- `Remaining != nil` is the check; this is an intentional pre-release API shape (no released consumer or HTTP surface predates it), loud at compile time for any consumer that compared against a sentinel. (5) `billing.plan_not_found`'s message interpolation is aligned: all four call sites (`PlanStore.Get`/`Update`, `PlanStore.Resolve`, `SubscriptionService.Create`) carry the looked-up value under the same `id` parameter name the locale templates interpolate, so the rendered message quotes the value on every path. (6) `go/billing/gateway/alipay`'s `VerifyWebhook` enforces a delivery-freshness ceiling: a delivery whose signed `notify_time` parameter sits more than `notifyTimeTolerance` (300s, mirroring stripe's `webhook.DefaultTolerance` and wechat's `notifyTimestampTolerance`) from now is refused with the authentication-class `ErrWebhookSignatureInvalid`. Alipay async notifications carry no signature-bearing HTTP header -- the RSA2 signature covers the form parameters, `notify_time` included -- so `notify_time` is the field the ceiling reads after the signature verifies (it is per-delivery-attempt, each attempt carrying its own `notify_id`, so genuine redeliveries are not aged out); a missing or unparseable `notify_time` is refused the same way: there is nothing to bound.

**A KEYED `Expire` is the at-most-once write a scheduled expiry sweep needs; the sweep itself is not shipped.** `Expire`'s input type (`PreDeductInput`, shared with `PreDeduct`) carries an optional `IdempotencyKey` for `Expire`: a keyed `Expire` mints its CreditTransaction under the caller's own deterministic key (the identical ledger-ID-as-idempotency-key shape `PreDeduct`'s mandatory key uses) and inserts through the same `ON CONFLICT DO NOTHING` `insertIdempotent` core, so a retried call with the same per-window key -- a jobs-driven sweep rerunning its window after a crash or a timeout, the `go/storage` `EnqueueExpirySweep` shape -- is answered with the first run's own row. A retry must never double-apply an expiry the first run already applied, so it records no second deduction and no second audit event: the retry branch's `expired` flag is false, the identical reserved-flag discipline `PreDeduct` documents for its own retry branch, and `emitCreditAudit` fires only when this call genuinely appended its own row. Only an existing expire row can be a retry's own earlier run: the ledger's row-ID namespace is shared across every row type, so a key that names a row of another kind is refused with the coded `ErrIdempotencyKeyCollision` (`billing.idempotency_key_collision`, catalog text in both locale bundles) rather than reported as a successful expiry it was not. A keyed first attempt refused with `ErrInsufficientCredits` rolls its whole transaction back -- its just-inserted row included -- so the key is never burned and a later, better-funded run with the same key is a fresh attempt again. The unkeyed form (a fresh UUID per call, strict insert after the balance CAS) is not idempotent under retry: it is the one-off, operator-driven shape, deliberately never the shape a retrying caller may use. The sweep itself is not shipped: which credits expire, when, in what amount, on what cadence is product policy this module's data model cannot anchor -- no grant-vintage or expiry-window column exists anywhere in the ledger -- so the sweep depends on (a) that product-policy decision and (b) a `jobs`-wiring host, as the Scope table row and the Known limitations bullet below record; the host half is not this module's own work. The error index below lists `billing.idempotency_key_collision`, `billing.invalid_reason` and `billing.unsupported_currency` among the codes the module's surfaces answer with.

## Scope

**The domain model, the subscription and invoice lifecycle, and the credits ledger.** `Feature`/`FeatureKind`, `Plan`/`Grant`/`Money`/`BillingInterval`, and `Entitlements`/`Decision` (`model.go`) -- the domain shapes the billing design's own Go sketch names, adapted to this repository's real conventions (see "Design choice: Plan's tenant-scoping duality" below for the one deliberate storage-shape departure from the sketch's literal `TenantID *string`). `PlanStore`/`PlanService` (`plan.go`): CRUD plus `Resolve` under the tenant-custom-Plan lookup precedence -- a tenant-custom row for `(tenantID, key)` overrides the platform-wide row for `key` when both exist, falling back to the platform-wide row otherwise. `EntitlementsService` (`entitlements.go`): the `Entitlements.Check` implementation -- the single judgment entry point business code is meant to call; for a Quota-kind Feature it reads `go/metering`'s real-time counter through the small `UsageReader` interface (never a summary table, which has aggregation delay and would let an over-quota request through), and never itself decides anything about credits. Through `examples/reference-app`, go/ai-gateway is wired to both of billing's halves: `internal/smilesim` reserves credits against `CreditService` before calling the gateway, and `internal/app/server.go`'s `aigateway.WithEntitlements` closure over `billingModule.Entitlements()` -- the `EntitlementsFunc` adapter `go/ai-gateway/seams.go` documents -- makes `EntitlementsService.Check` the real judgment behind go/ai-gateway's own `checkEntitlement` gate (both wirings detailed below). `Subscription`/`SubscriptionRepository`/`SubscriptionService` (`subscription.go`): a channel-agnostic internal domain concept with no payment-channel reference of any kind, whose lifecycle (`created`/`active`/`past_due`/`canceled`) is driven by a plain Go call (`Activate`/`MarkPastDue`/`Cancel`), publishing `EventSubscriptionStatusChanged` on every transition, plus the read-or-establish helper `EnsureActive` (the tenant's Active subscription on any Plan returned untouched; none means create and activate one) that both the reference app's boot seed and its self-service provisioning chain call. "At most one `active` subscription per tenant" is a database-enforced invariant: the partial unique index `uq_billing_subscriptions_one_active` (`migrations/{sqlite,postgres}/0007_single_active.sql`), which a second activation meets as a duplicate-key refusal that `EnsureActive` converges by re-reading the winner (see Known limitations). `Invoice`/`InvoiceRepository` (`invoice.go`): the equally channel-agnostic billing-document counterpart. The credits ledger (`credit_balance.go`, `credit_transaction.go`, `credit_service.go`): `CreditBalance` (per-tenant `available`/`reserved`), the append-only `CreditTransaction` log (`grant`/`deduct`/`refund`/`expire`), and `CreditService`'s `PreDeduct`/`Confirm`/`Refund`/`Grant`/`Expire`/`Balance` -- the reserve → confirm/refund pattern every "pay-per-use that might fail" business operation needs, transactionally safe under concurrent deductions against the same balance (see "Concurrency: `applyBalanceDelta`" below). `the module contract` wiring (`module.go`): permissions for plan/subscription/credit administration, audit actions for the credit ledger's five state-changing operations -- declared and genuinely emitted by every one of `CreditService`'s five methods after its transaction commits (see the audit-trail subsection below) -- and the two published domain events (`billing.plan.changed`, `billing.subscription.status_changed`). A godoc `Example` (`example_test.go`) walks the module's whole shape in one pass -- Plan creation, Subscription activation, both `Entitlements.Check` grant kinds, and the credits ledger's reserve → confirm pattern. It is the compensating obligation for the surfaces with no real caller: `CreditService` has one (`internal/smilesim`), `Plan`/`Subscription`/`Entitlements` have theirs through the demo seed and gateway wiring below; `Invoice` still has none (see Known limitations).

**The payment-gateway seam, the payment-event ledger, and the polling fallback.** `ChannelReference`/`ChannelStatus`/`NormalizedEventType`/`NormalizedEvent`/`ChargeRequest`/`ChargeHandle` and the `PaymentGateway` interface (`gateway.go`) -- the provider-agnostic seam a channel implementation satisfies, grounded in what `SubscriptionService`/`InvoiceRepository` actually need (creating a channel-side subscription or order, verifying and normalizing an inbound webhook, and re-querying a channel's authoritative status for a `ChannelReference`) rather than an abstract guess; `PaymentGatewayRegistry`, the package-level `pkgcore.SeamRegistry[PaymentGateway]` a provider subpackage's own `init()` registers into, mirroring `go/pki`'s `SignerRegistry`. `PaymentEvent`/`PaymentEventRepository` (`payment_event.go`): the tenant-scoped, durable, deduplicated record of every inbound webhook delivery the insert-first-to-dedup rule requires, keyed uniquely on `(channel, provider_event_id)`, with dual-dialect migrations (`migrations/{sqlite,postgres}/0006_create_billing_payment_events.sql`). `PollingService`/`Module.WithQueue`/`Module.WithGateways` (`job.go`, `module.go`): the active-polling fallback the "a callback may arrive before the order-creation response returns, or may never arrive at all" rule requires -- a `jobs`-scheduled, tenant-scoped task (`taskTypePoll`) re-querying every stuck `PaymentEvent` row through its owning channel's `PaymentGateway.QueryStatus`, claimed on `reg.JobsSeat()` only when a host wires a queue via `WithQueue`, exactly like `go/storage`'s and `go/pki`'s own periodic tasks; a queue-wired module also declares the poll's periodic schedule on the `pkgcore.ComponentRegistry.Schedules` seat (`job.go`'s `pollSchedule`, one per-tenant task per `pollIdempotencyWindowSize` window), so a host that runs a `jobs.Scheduler` over the finished registry polls every tenant at the module's own cadence without writing a schedule point of its own -- a queue-less module declares nothing, the same gate its handler registration uses. Four error codes ship with the surface (`billing.webhook_signature_invalid`, `.webhook_payload_unrecognized`, `.channel_reference_not_found`, `.payment_event_not_found`). Three real provider implementations live under `go/billing/gateway/{stripe,alipay,wechat}` -- see that subpackage's own `AGENTS.md` for the full write-up, including the measured dependency cost of each and exactly what remains untestable without live credentials.

**The reference-app consumer: credits in `internal/smilesim`.** The wiring is entirely `examples/reference-app`'s own; `CreditService`'s public API (`PreDeduct`/`Confirm`/`Refund`/`Grant`/`Balance`) needed no change to serve it, and this wiring is what discharges the mandatory-first-consumer rule ("a module API that the reference app does not actually use is not considered done") for `CreditService` specifically: `internal/smilesim.Service.Simulate` reserves `CreditsPerSimulation` credits via `PreDeduct` BEFORE calling `aigateway.Gateway.GenerateImage` at all -- an insufficient balance returns `ErrInsufficientCredits` and go/ai-gateway (and any real vendor behind it) is never reached -- using an idempotency key minted once per generation request (`"smilesim:" + uuid.NewString()`) and reused for every later settlement call, since `PreDeduct` must run before go/ai-gateway's own job id even exists (`internal/smilesim/service.go`'s own `Simulate` doc comment has the full reasoning for why the job id itself cannot be the key here, unlike a more ordinary "reserve after enqueue" shape). `OnJobTerminal` -- `internal/smilesim`'s subscriber to the queue's terminal signal (`jobs.EventJobTerminal`), installed on the app's bus by `internal/app` at assembly time -- settles that reservation at the job's terminal transition itself: `Confirm` on `StatusSucceeded`, `Refund` on `StatusDeadLetter`/`StatusCancelled`; `NotifyOnCompletion`'s poll-driven call remains as the second leg for a transition no signal was seen for, and both legs run the same settlement core and publish `EventSimulationCompleted` through its once-only latch, safely idempotent under repeat via `CreditService`'s own compare-and-swap contract. Settlement never depends on a client's own poll, and the job-id-to-idempotency-key mapping never lives only in memory: `internal/smilesim` persists that mapping in its own small `smilesim_credit_reservations` table (`reservation_store.go`, created imperatively like `go/jobs`' own `jobsTable`, not through a versioned migration -- it is an implementation detail private to this one package) and runs a periodic `ReconcileOutstandingCredits` sweep (`reconcile.go`, started by `StartReconciler` at boot, mirroring `go/config`'s own anti-loss poller) that settles any reservation whose job has already reached a terminal status through the same `jobs.Queue.Get` a real client would poll -- independent of whether anything ever polls, and surviving a process restart since the mapping itself is durable; a reservation whose caller stopped polling (or whose process restarted mid-flight) cannot stay `Reserved` forever with no path to settle it. `CreditService`'s own API needed no change for this: it is entirely a durability and reachability property of the consumer's own bookkeeping. `examples/reference-app/internal/app/demo/demo_credits.go`'s `SeedDemoCredits` grants each demo tenant a starting balance through a real `CreditService.Grant` call at boot -- explicitly NOT a payment, the deliberate, documented stand-in for a real credit-pack-purchase leg (no live Stripe/Alipay/WeChat credentials exist in this environment; see `go/billing/gateway/AGENTS.md`). The end-to-end proof, `examples/reference-app/flowtests/billing_credit_flow_test.go`, drives the real composed HTTP stack through all three scenarios: a sufficient balance generates successfully and is genuinely debited (read back through a real `CreditService.Balance` call over a second database connection, never merely trusted from the job's own reported status); an insufficient balance is refused before the fake AI-gateway endpoint is ever reached (asserted on that fake server's own request counter); and a failed generation (a fake vendor endpoint that always answers 500, exhausting go/jobs' retries into `StatusDeadLetter`) leaves the reservation refunded back to the pre-reservation balance.

**The credits ledger's audit trail.** `CreditService`'s five state-changing methods (`Grant`, `PreDeduct` -- the reserve half -- `Confirm`, `Refund`, `Expire`) each call `go/dbkit/audit`'s `Emit` under the exact action name `Register` declares (`AuditActionCreditGrant`/`AuditActionCreditDeductReserve`/`AuditActionCreditDeductConfirm`/`AuditActionCreditRefund`/`AuditActionCreditExpire`), following the declarative pattern `examples/reference-app/internal/notes/handler.go`'s `recordNoteCreatedAudit` established as this codebase's working answer to "a business module explicitly calls `audit.Emit` after a state-changing operation succeeds". `credit_service.go`'s `emitCreditAudit` is the one place every call site funnels through: it is invoked only AFTER the mutating `dbkit.WithTenantSession` transaction has already committed, never from inside the closure, so `audit.Emit`'s own write opens a fresh, uncontended database session rather than nesting inside one still open -- the same-file `SQLITE_BUSY` hazard `go/dbkit/AGENTS.md`'s "Audit trail collection" section documents for `AuditBus`'s automatic write-capture plugin is sidestepped here the way notes' own handler sidesteps it, by construction rather than by avoiding the shared connection. A publish failure is logged at Error level and never turns an already-committed credit mutation into a reported failure to the caller, matching notes' own `recordNoteCreatedAudit` contract exactly.

The Resource every one of the five audited actions records is the `CreditTransaction` row itself (`Type: "credit_transaction"`, `ID` the ledger row's own id) -- the actual append-only fact each method adds to the ledger, mirroring notes' own choice to audit the created `Note` rather than some other aggregate it happens to touch. `Changes.After` carries the delta the specific call applied (`amount`, and `reason` when the caller supplied one) plus, best effort, the tenant's resulting balance (`resulting_available`/`resulting_reserved`). That resulting balance is read by `readBalanceForAudit`, called from INSIDE the same `dbkit.WithTenantSession` transaction that applies the operation's own delta, immediately after `applyBalanceDelta` and before commit -- deliberately NOT a separate query opened after commit: two concurrent operations mutating the SAME tenant's balance could otherwise have the first one's post-commit read observe the SECOND'S already-committed delta too, so its audit event would report a `resulting_available` that never corresponds to its own operation. Reading inside the transaction instead ties the read to exactly this operation's own applied delta: `applyBalanceDelta`'s own prior `UPDATE` holds the row locked until this transaction commits, so no concurrent transaction's write can land in between, on either dialect. `TestCreditService_Grant_ConcurrentGrantForSameTenant_BlocksUntilPriorTransactionCommits` (`credit_service_test.go`) is the deterministic reproduction and fix proof, using the test-only `testHookAfterBalanceDelta` seam. A failure to read that resulting balance (logged, never blocking) simply omits the two balance fields from that one event -- it must never turn an already-succeeded credit mutation into a reported failure, or into a rolled-back transaction. `Result` is always `{Success: true}`: every call site invokes `emitCreditAudit` only once its own mutating transaction has already committed, so an audited action that reaches it has by definition succeeded.

Two of the five methods carry a genuine-state-change guard, not merely "call Emit on success", because both are idempotent under retry: `PreDeduct`'s fresh-reservation branch sets an internal `reserved` flag (false on the branch that instead finds an already-existing row for the same `IdempotencyKey`), and `resolve` (`Confirm`/`Refund`'s shared core) sets an internal `resolved` flag (false on the branch that finds the transaction already in the target terminal state) -- `emitCreditAudit` is called only when the flag is true, so a harmless retry of an already-settled reservation never produces a second audit record for an operation that did not happen this call. `Grant` needs no such guard: it mints a fresh `uuid.NewString()` transaction id on every call (not idempotent under retry -- see Known limitations below), so every successful call is by construction a genuinely new ledger entry. An UNKEYED `Expire` is the same. A KEYED `Expire` is the one case that needs the guard: `PreDeductInput.IdempotencyKey` makes its transaction id the caller's own deterministic key, so the keyed form is idempotent under retry -- a retry returns the first run's already-existing row, changing nothing on this call -- and the same flag discipline applies under the name `expired` (false on the retry branch): `emitCreditAudit` fires only when this call genuinely appended its own row. `Balance` remains entirely unaudited, exactly as `Register`'s declaration (five actions, never six) has always implied -- it performs no write.

`CreditService.events`/`.auditActions` are two unexported fields wired post-construction by `module.go`'s `Register` (`m.credits.events = bus; m.credits.auditActions = reg.AuditActionsSeat()`), the identical pattern `PlanService.events`/`SubscriptionService.events` use -- `NewCreditService`'s exported signature is untouched, so every pre-existing call site (every unit test in this package, `examples/reference-app/flowtests/billing_credit_flow_test.go`'s own `openBillingCredits` helper) keeps compiling and behaving unchanged: a `CreditService` built directly through `NewCreditService` has `events == nil`, and `emitCreditAudit`'s own nil check makes every one of its five callers a complete no-op with respect to auditing, mirroring notes' own `Handler.bus == nil` short-circuit exactly.

`credit_service_test.go` is the unit-level proof of the audit wiring: one test per method asserting the exact action name, `Resource`, `Result` and a real, useful `Changes.After` payload (never merely "Emit was called"), plus two negative proofs that the idempotent-retry paths of `PreDeduct` and `Confirm` do not double-emit, and one proof that `Balance` never emits at all. The reference-app end-to-end proof is `examples/reference-app/flowtests/billing_credit_flow_test.go`'s `TestSmileSimulation_SuccessfulReserveConfirm_PersistsAuditEvents` and `TestSmileSimulation_FailedGeneration_PersistsRefundAuditEvent`: both drive `internal/smilesim`'s real reserve/confirm/refund cycle through the REAL composed HTTP stack (the same rig `TestSmileSimulation_SufficientCredits_DebitsBalance`/`TestSmileSimulation_FailedGeneration_RefundsReservation` use) and read the resulting `audit_events` rows back through a SECOND connection to the same SQLite file via a real `audit.Repository.ListByTenant` call -- never a mock or an in-memory event assertion -- exactly the "buildServer hands out neither its `*gorm.DB` nor a module's own service" pattern `flowtests/server_test.go`'s own `TestBuildServer_NoteCreate_PersistsAuditEvent` established for notes. This is deliberately the same wiring choice notes' own test proves: an explicit `audit.Emit` call sharing `billingModule`'s and `auditModule`'s one database connection, never `dbkit.Options.AuditBus`'s automatic write-capture plugin, for the identical same-file `SQLITE_BUSY` reason. Two pre-existing tests reflect the demo seed's audit rows rather than assuming an empty tenant trail: `TestBuildServer_NoteCreate_PersistsAuditEvent` (`flowtests/server_test.go`) and `examples/reference-app/integration_test/redis_eventbus_composition_test.go`'s own tenant-acme assertion both filter for the `notes.note.create` action specifically, because `internal/app/demo/demo_credits.go`'s boot-time `SeedDemoCredits` call is itself a real `CreditService.Grant` -- tenant-acme (and tenant-globex, also demo-seeded) genuinely carries its own `billing.credit.grant` row from boot onward.

**The reference-app consumer: entitlement judgment.** The wiring lives in `examples/reference-app` and required no `go/billing` change -- `EntitlementsService.Check`'s public API was complete and unit-tested before its first caller -- and it discharges the mandatory-first-consumer rule for `Entitlements.Check`, the judgment surface with no caller until the wiring described here. The wiring uses the sanctioned seam shape: `internal/app/server.go` constructs the ai-gateway module with `aigateway.WithEntitlements(billingModule.Entitlements())`, an `EntitlementsFunc` closure -- the adapter `go/ai-gateway/seams.go` itself documents as the bridge between two same-tier modules that mirror each other's shapes structurally and never import each other -- so go/ai-gateway's own `checkEntitlement`, which runs on every `Chat`/`ChatStream`/`GenerateImage` call before any provider is reached, judges against a real `billing.EntitlementsService.Check` for every request this app serves. The keys it judges are `"model:"` + the `LogicalModel` each route asks for, and the demo seed grants exactly those keys by importing the very constants the routes run on (`internal/consult`'s `"model:chat:default"`, `internal/smilesim`'s `"model:image:smile-simulation"`), never hand-copied strings that could drift. Because this app wires `billing.NewModule(db, nil)` -- no `UsageReader` -- the seed's grants are Boolean (`Value: true`), never Quota-kind, and that is the design's own answer rather than an evasion: "can this tenant use model X at all" is the Boolean question the per-model gate semantics name for exactly these grants. A Quota-kind grant under a nil reader fails closed with the coded `ErrUsageReaderUnconfigured` -- never a panic on the nil interface call, and never a guessed allowance -- while Boolean grants remain the right shape for these per-model gates precisely because they need no counter at all, the same optional-seam posture go/ai-gateway's own optional `Entitlements` option follows for a host that leaves it unwired. `internal/app/demo/demo_entitlements.go`'s `SeedDemoEntitlements` runs at boot next to `SeedDemoCredits` and resolves-else-creates the platform-wide demo Plan (key `"demo"`) stamped with those two grants, then gives every tenant in `cfg.HostTenants` an Active subscription through a real `PlanService.Resolve` / `SubscriptionService.EnsureActive` pair under each tenant's own context -- the plain-Go-call stand-in for a payment channel's confirmation, never a purchase (the Scope table's payment rows below still name that gap). The end-to-end proof, `examples/reference-app/flowtests/entitlements_flow_test.go`, drives the real composed HTTP stack through one happy path and one refusal path per ai-gateway half: a seeded demo tenant's consult `Suggest` call and smile-simulation generation both clear the gate and genuinely reach the fake provider endpoints, while canceling tenant-acme's demo subscription mid-test through a real `SubscriptionService.Cancel` on a second database connection makes the SAME request shapes fail with go/ai-gateway's own coded `ErrEntitlementDenied` 403 (`aigateway.entitlement_denied`, model and reason params) before any provider is reached -- `Check` fresh-reads the tenant's subscription row on every call, so the cancellation takes effect immediately with no cache to invalidate. What is not discharged stays honestly named: `Invoice` still has no caller at all; the Quota/`UsageReader` judgment path has no real caller (Boolean demo grants are this app's whole story; a quota-kind caller needs a host that wires a usage reader); and no real payment-channel event drives a `Subscription` into existence -- the seeded Active subscription is the demo stand-in for that confirmation, exactly as `internal/app/demo/demo_entitlements.go`'s own package doc comment says.

**The HTTP surface.** The module's HTTP surface is its own OpenAPI fragment (`api/openapi.yaml`): `Module.OpenAPISpec()` returns the embedded spec, and `module.go`'s `Register` builds and mounts the fragment's `Handler` at `apiPath` `/api/v1/billing` through `reg.RoutesSeat().Mount`. The fragment is deliberately READ-ONLY, a decision recorded in the fragment's header: the credit consumption this codebase actually performs is service-side by construction (`internal/smilesim`'s reserve/confirm/refund wiring calls `CreditService`'s Go API in-process; nothing about it travels over HTTP), so the two operations a credit view and a refund-observability story genuinely need are the two GETs the fragment ships -- `billing_getCreditBalance` (`GET /api/v1/billing/credits/balance`, the number, read through the same `CreditService.Balance` business code uses) and `billing_listCreditTransactions` (`GET /api/v1/billing/credits/transactions`, the recent window of the append-only ledger, newest first, bounded by the `limit` parameter 1-100 default 50). A refund is observable on that read surface as its deduct row's status having become `refunded` -- the module's type/status vocabulary on the wire (`grant`/`deduct`/`expire` types; `pending`/`confirmed`/`refunded` statuses; "refund" deliberately not a row type, exactly as `credit_transaction.go` models it) -- never a silent balance change. The write surface stays absent on purpose, and that absence is the honest consequence of the read-only decision, stated here rather than hidden: the day a caller-driven write journey exists (an operator grant or refund the credit view itself triggers), it adds the POST operations, gated on the module's already-declared `PermissionCreditManage` -- nothing would call such an endpoint today, and shipping one nothing calls is the speculative build-ahead this scope table declines elsewhere. What the fragment does not ship is likewise recorded rather than half-built: `limit` narrowing happens in the handler by truncating `CreditService`'s full newest-first listing (see Known limitations). The tooling wiring is in place: Taskfile `api:gen` carries this fragment's leg, `api-contract.yml` regenerates and porcelain-gates `billing-server.gen.go`, and the fragment's two operations join the merged `contracts/speed.yaml` document -- the credit view calls them through the generated SDK; Known limitations records the tooling detail in full.

Handler (`handler.go`) implements the generated `api.ServerInterface` behind a `var _ api.ServerInterface` compile-time assertion, reads the tenant from the request context (`mustTenant`, the storage-shaped defensive call -- a host must never allowlist these routes, so tenancy.Middleware has already rejected anything tenant-less), and answers the {code, params} envelope of this module's own error index: the two refusal codes the surface can actually produce (`billing.invalid_limit` for an integer `limit` outside the 1-100 bound, `billing.invalid_request` for a `limit` that is not an integer at all -- the malformed query is refused by the spec-generated parameter binder before the handler runs, and `NewHandler` installs a custom `ErrorHandlerFunc` through `api.HandlerWithOptions` in place of oapi-codegen's default plain-text `http.Error`, the sharing-handler precedent, so the answer is always the coded envelope, never a raw binder message) plus `billing.internal_error`, the folding code for a non-`apperr` failure, all three with matching entries in both locale bundles. The read plumbing needed one small service addition: `CreditService.Transactions` (`credit_service.go`), the ledger's read-back surface over the repository's existing tenant-scoped `ListByTenant` (a never-touched tenant answers an empty list, never a missing-row error), with its own runnable godoc `Example` (`ExampleCreditService_Transactions`). `module_test.go` pins the surface: `OpenAPISpec()` is asserted non-empty and naming both fragment paths, and Register's one mounted route is asserted present at `apiPath`.

The reference app is the mandatory first consumer end to end. `internal/app/demo/demo_subject.go` gates the mounted path for real -- `BillingRoutePath` entry in `DemoRouteRules` gated by `rbac.GuardRoutes` on `billingPermissionFor`'s answer directly: billing's three-segment permission strings ride the standard gate, whose splitter cuts at the LAST separator ("billing:credit" + "read"/"manage"; `rbac.Permission(resource, action)`'s join maps the halves straight back onto the catalog entry). The composed proof, `flowtests/billing_http_flow_test.go`, pins the surface's four behaviors over the real stack: (a) a real smile simulation's consumption reads back as the post-consumption balance AND its ledger rows through the fragment's routes; (b) the tenant boundary holds over HTTP -- tenant-acme's spend is invisible to tenant-globex's balance and ledger reads, and the demo reader (no billing permission) is refused with `rbac.permission_denied`; (c) `limit=0` answers `billing.invalid_limit` with the structured bound and `limit=abc` answers the `billing.invalid_request` envelope, never a raw error; (d) the pre-existing billing service-level suite runs unchanged. The suite also pins the refund-observability property the fragment exists to serve: a reservation released by a real service-side `CreditService.Refund` reads back over the routes as its deduct row's status becoming `refunded`, balance restored to the full seed alongside.

## Design choice: Plan's tenant-scoping duality

**Why `Plan` deliberately does not implement `dbkit.TenantScoped`.** The billing design's Go sketch spells `Plan.TenantID` as `*string // nil = platform-wide; set = tenant-custom` -- illustrative Go, not this module's literal storage shape. `Plan` is a genuinely dual-domain table: a platform-wide row (`TenantID == ""`) is platform data, meant to be visible to *any* tenant's `Resolve` lookup; a tenant-custom row is that one tenant's private data. No single dbkit data-domain capability spans both faces of the same table -- `dbkit.TenantScoped`'s own isolation plugin would hide every platform-wide row from a tenant-scoped query, which is exactly the opposite of what "fall back to platform-wide when no tenant-custom Plan exists" requires.

This is not a novel problem: `go/config`'s own `configs` table (`system` → `tenant` scope tiers) solves the identical duality, and `Plan` adopts its exact answer, column for column -- a plain, `NOT NULL` `tenant_id` string column holding the empty-string sentinel (`platformScopeSentinel`) for a platform-wide row (empty rather than `NULL`, for the same reason `go/config`'s `row` and `go/dbkit/audit`'s `AuditEvent` both document: `NULL`s are distinct in a PostgreSQL unique index, so two platform rows for one key could coexist under `NULL` where the empty string collapses them into the one row the `(tenant_id, key)` unique index promises), reached through a plain `*gorm.DB` (`PlanStore`, never `dbkit.Repository[T]` -- the generic constraint requires `TenantScoped`, which this table must *not* implement), isolation proven with `tenancytest.AssertNotTenantScoped` rather than `AssertIsolated` (`TestPlan_AssertNotTenantScoped`, `plan_test.go`). The scoping this table actually needs -- "a tenant only ever sees its own custom Plans plus the platform-wide catalog, never another tenant's custom Plans" -- is enforced by the store's own signatures, never by dbkit's isolation plugin. Read paths that resolve by `Key` go through `PlanStore.Resolve`'s own two-step lookup. The by-id paths are scope-guarded the same way: `PlanStore.Get(ctx, tenantID, id)` returns only the row the named tenant scope itself owns, `PlanStore.Update(ctx, tenantID, plan)` writes only such a row (the WHERE carries both id and scope, and the plan struct being saved must carry the scope too, so an update can neither touch another tenant's row nor move one of the caller's own rows into another scope), and the one deliberate cross-scope read is named for what it does: `GetPlatformPlan` reads the platform-wide catalog by id, which is what `SubscriptionService.Create` (the one write path that accepts a caller-supplied Plan *id*, `CreateInput.PlanID`) and `EntitlementsService.Check` use as the second step of a Get-then-GetPlatformPlan lookup when the id names a platform-wide Plan rather than the tenant's own custom one. Rows outside the named scope answer the same `ErrPlanNotFound` a genuinely missing id gets, in every path.

Do not treat the missing `dbkit.Repository[Plan]` embed or the missing `AssertIsolated` suite as a gap: both follow from the dual-domain nature above -- the identical answer `go/config`'s own `configs` table gives.

## Design choice: `CreditTransaction` does not embed `dbkit.Repository[T]`

`CreditTransaction` genuinely **is** tenant data (unlike `Plan` above) -- every row belongs to exactly one tenant, with no cross-tenant reader the way `go/metering`'s `Dispatcher` needs for its own `OutboxRecord`. But `CreditTransactionRepository` deliberately does **not** embed `dbkit.Repository[CreditTransaction]` the way every other tenant repository in this codebase does: embedding would promote `Repository[T]`'s own `Update` and `Delete` methods onto this type, which is exactly the mutability an append-only financial ledger must never offer -- the same "must be reconstructable/auditable from the transaction log alone" rigor `go/dbkit/audit`'s `AuditEvent`/`Repository` already establishes for this codebase's other append-only ledger. `CreditTransactionRepository` exposes only `Insert` and two read methods (`Get`, `ListByTenant`), mirroring `audit.Repository`'s own "`Insert`, `Get`, `ListByTenant`, and NO `Update` or `Delete` method at all" shape; `TestCreditTransactionRepository_HasNoUpdateOrDeleteMethod` proves it with the identical reflection check `go/dbkit/audit/repository_test.go`'s own `TestRepository_HasNoUpdateOrDeleteMethod` uses (Go has no way to assert "this type lacks a method" any other way that fails loudly on a future regression).

`CreditTransaction`'s primary key is the composite `(id, tenant_id)`, not `id` alone: a Deduct row's `ID` is the *caller's own* `IdempotencyKey` (see `CreditService.PreDeduct`'s doc comment), which is therefore not globally unique across tenants -- two different tenants may reasonably reuse the same idempotency-key string for their own, unrelated operations. This is the identical composite-key shape `go/metering`'s `UsageSummary` and `go/dbkit/audit`'s `IngestReceipt` both already use for the same reason, and `TestCreditTransactionRepository_SameIDDifferentTenants_DoesNotCollide` is the standing proof.

`CreditTransactionRepository`'s own CAS updates (inside `CreditService.resolve`, the `Confirm`/`Refund` shared core) go through `dbkit.WithTenantSession` plus a hand-written `session.Where(...).Updates(...)` call -- never `.Table`/`.Model`/`.Raw` (the three entry points the raw-gorm-bypass semgrep rule flags) -- the sanctioned "raw-SQL escape hatch" shape `go/notification`'s `ContactService.consumePendingCode` uses for an identical compare-and-swap need on a genuinely tenant-scoped table reached outside `dbkit.Repository[T]`.

## Concurrency: `applyBalanceDelta`, the ledger's one write primitive

Every `CreditService` balance mutation (`PreDeduct`, `Confirm`, `Refund`, `Grant`, `Expire`) funnels through one function, `applyBalanceDelta` (`credit_service.go`): a single database-arbitrated `UPDATE` that adds `availableDelta` to `Available` and `reservedDelta` to `Reserved`, guarded in the SAME statement so neither bucket can go negative (`WHERE ... available + availableDelta >= 0 AND reserved + reservedDelta >= 0`) -- never a Go-level read-modify-write. This is what makes concurrent callers safe: two `UPDATE` statements against the same row are serialized by the database itself (ordinary row locking, no dialect-specific atomic-increment feature required -- plain, portable SQL that runs identically on SQLite and PostgreSQL), so the second to run sees the first's already-applied change and its own guard evaluates against the *post-first-update* values, never a stale read a Go-level read-modify-write could race on. `TestCreditService_PreDeduct_ConcurrentOverBalance_OnlyOneSucceeds` (`credit_service_test.go`), run under `-race`, is the mandated proof: two concurrent `PreDeduct` calls whose combined `Amount` exceeds the tenant's balance cannot both succeed -- exactly one does, the balance ends up consistent, and the loser's own `CreditTransaction` row was never written (the whole attempt rolls back inside one database transaction).

`applyBalanceDelta` is a raw `.Exec(...)` call, not `dbkit.Repository[T]`'s own `Update` (a full-row `Save`, incapable of server-side arithmetic) and not a struct passed to GORM's `.Updates()` (which silently *omits* any field left at its Go zero value from the `SET` clause -- fatal here, since `Available` or `Reserved` legitimately reaching exactly zero must still be written). `.Exec` is a narrower surface than the three entry points (`.Table`/`.Model`/`.Raw`) the raw-gorm-bypass semgrep rule flags, and is the "raw SQL escape hatch" sanctioned for a genuine need like this one -- with the tenant passed explicitly into the `WHERE` clause (mandatory here, not merely defense in depth, since `.Exec` bypasses the ORM callback chain the isolation plugin hooks into) and an isolation test (`TestCreditBalanceRepository_AssertIsolated` proves the underlying table's own tenant scoping; every `applyBalanceDelta` call site runs inside `dbkit.WithTenantSession`, so on PostgreSQL the row-level-security GUC is also engaged as a second, database-level backstop underneath this application-level guard).

`CreditService.ensureBalance` materializes a tenant's first `CreditBalance` row (all-zero) with `INSERT ... ON CONFLICT (id) DO NOTHING` -- the identical dialect-neutral upsert clause `go/config`'s `store.put` uses -- so two callers racing to touch a brand-new tenant's balance for the first time (`TestCreditService_Grant_ConcurrentCallsForANewTenant_BothSucceed`, also under `-race`) never both try to `Create` the same row.

## Design choice: `PaymentGateway`/`PaymentGatewayRegistry` live in billing's root package, never in `billing/gateway`

The dependency-direction rule this section guards: `go/billing/gateway` (and its `stripe`/`alipay`/`wechat` sub-subpackages) may import `go/billing`, but `go/billing`'s own root package must never import `go/billing/gateway` or anything under it. That rule only holds if the seam a caller depends on -- the `PaymentGateway` interface, and the registry a provider registers into -- is declared somewhere neither side of the one-way edge would need to cross to reach it. Declaring both in `go/billing`'s own root package is what makes that true: a caller depends on `billing.PaymentGateway` and resolves an implementation through `billing.PaymentGatewayRegistry`, never importing `go/billing/gateway` at all, while `go/billing/gateway/stripe`'s own `init()` imports `go/billing` (for `PaymentGateway`, `NormalizedEvent` and friends) to register itself. Putting the interface in the subpackage instead would force exactly the import edge the rule forbids: `go/billing`'s own domain code (`SubscriptionService`, a webhook handler) would need to import `go/billing/gateway` to name the interface at all -- precisely how `stripe.Subscription`-shaped types leak into the domain model over time, the concrete failure mode this arrangement exists to prevent.

This is the identical shape `go/pki`'s `Signer`/`SignerRegistry` established for its own `vault`/`kmsaws` provider split (`go/pki/signer_registry.go`'s own doc comment). `PaymentGatewayRegistry` ships with no built-in implementation pre-registered, unlike `pkgcore`'s own `the event bus component registrations`/`the kv component registrations`/`the mailer component registrations`/`the objectstore component registrations`: every `PaymentGateway` genuinely needs a provider SDK or a hand-rolled channel client, so there is no zero-dependency default the way `LocalSigner` is for `SignerRegistry`. `Module.WithGateways` is the `WithSigner`-shaped direct-injection half of the same duality `SignerRegistry`'s own doc comment describes: a host that already holds a constructed `PaymentGateway` (typically via `PaymentGatewayRegistry.Build` against a blank-imported provider subpackage) hands the resulting map to `PollingService` through it, rather than every call site doing its own name lookup.

The CI-enforced half of this rule -- three `depguard` entries in `.golangci.yml`, one per provider subpackage, each narrowed to that subpackage alone (not the whole `go/billing/gateway` tree) -- lives with the provider subpackages themselves; see `go/billing/gateway/AGENTS.md`'s own write-up of the full mechanism, including the SDK-choice rationale for each of the three providers and the measured dependency cost of each.

## Design choice: `PaymentEvent` is genuinely tenant-scoped, unlike `Plan`'s dual-domain shape

`Plan`'s table (see "Design choice: Plan's tenant-scoping duality" above) is deliberately NOT tenant-scoped because a platform-wide row must be visible to every tenant's lookup. `PaymentEvent` has no such platform-wide face: every row belongs to exactly one tenant's payment history, decoded from the channel-side object's own metadata at webhook-verification time (`NormalizedEvent.TenantID`'s own doc comment describes the round trip -- `ChargeRequest`'s identifiers are attached to the created object via whichever metadata mechanism the channel offers, and `VerifyWebhook` decodes them back out). `PaymentEvent` therefore implements `dbkit.TenantScoped` and is reached through `dbkit.Repository[PaymentEvent]` -- the ordinary shape every other genuinely tenant-owned table in this module uses, proven with `tenancytest.AssertIsolated` (`payment_event_test.go`), never `AssertNotTenantScoped`.

The uniqueness constraint the migration applies, `uq_billing_payment_events_channel_event` on `(channel, provider_event_id)`, is deliberately NOT further scoped by `tenant_id`: a channel's own event id is already globally unique across that channel's entire account, so widening the key to include `tenant_id` would only let a bug that mis-decodes `TenantID` silently create two rows for the one event it actually was -- the exact double-processing dedup exists to prevent. `PaymentEventRepository.InsertIfNew` is the sanctioned way to observe this constraint: it returns `(true, nil)` for a genuinely new event and `(false, nil)` -- never an error -- for one already recorded. That is the row-level half of the insert-first-to-dedup rule, proven on its own; the processing half -- the shape a live webhook handler's insert-plus-side-effects must take, since an insert-then-effects recipe on top of this method cannot be atomic -- is deliberately undetermined until the webhook-processing chain is connected (see `InsertIfNew`'s own doc comment).

## Design choice: no config items

`go/billing`'s `Register` declares **zero** config items. There is no code path with a natural candidate: no trial-period length, grace-period duration, or default-credit-expiry-window is read, computed, or even referenced by anything `SubscriptionService`, `CreditService` or `EntitlementsService` actually does -- every one of those knobs belongs to scheduler/gateway machinery that is not built here (dunning after a `past_due` subscription, a `jobs`-driven expiry sweep for `CreditService.Expire`). Declaring a config item with no code path to attach it to is precisely the speculative-declaration pattern this codebase rejects by precedent (the "no `metering.unknown_feature`" and "no `pki:revoke`" notes in the sibling modules' own AGENTS.md files). `TestModule_Register_DeclaresItsSurface`'s `"no config items are declared"` subtest is the standing proof this stays true.

## Known limitations

- **The five state-changing methods call `audit.Emit` after commit; an emit failure is not recovered.** Every one of `Grant`/`PreDeduct`/`Confirm`/`Refund`/`Expire` emits under the exact five action names `Register` declares -- see the audit-trail subsection above for the full write-up. What this does NOT cover: an `audit.Emit` failure is logged at Error level and never retried or queued for later delivery -- the identical "log, never return" contract notes' own `recordNoteCreatedAudit` accepts for the same reason (the underlying credit mutation already committed by the time `emitCreditAudit` runs, so a caller must never see an already-successful operation reported as a failure) -- a lost audit write in that narrow window has no compensating recovery path here, exactly as none exists for notes' own identical call. The resulting-balance fields in `Changes.After` (`resulting_available`/`resulting_reserved`) are similarly best-effort in one direction only: a genuine read failure (logged, inside `readBalanceForAudit`) simply omits the two fields from that one event, never blocking or failing the credit mutation itself. They are NOT best-effort with respect to concurrency: reading inside the mutating transaction makes the resulting-balance fields exactly as reliable as the mutation itself, never a snapshot of "the balance at some nearby moment" -- see the audit-trail subsection's `Changes.After` paragraph for the mechanism and `TestCreditService_Grant_ConcurrentGrantForSameTenant_BlocksUntilPriorTransactionCommits` for the proof.
- **At most one `active` subscription per tenant, enforced by the database.** `SubscriptionService.Active` returns the tenant's one Active row, and the partial unique index `uq_billing_subscriptions_one_active` (`migrations/{sqlite,postgres}/0007_single_active.sql`: `UNIQUE (tenant_id) WHERE status = 'active'`) makes that a real invariant rather than a read-side assumption -- created, past_due and canceled rows stay unconstrained, and a canceled subscription is never revived (the next ensure mints a new row). The enforced semantic a direct `Activate` caller meets: activating a second subscription for a tenant that already holds an Active one is refused with an error wrapping `gorm.ErrDuplicatedKey` (match it with `errors.Is`; not `ErrInvalidSubscriptionTransition`, since the move itself is legal), where two coexisting Active rows were previously reachable. `SubscriptionService.EnsureActive` is the convergence for the racing creator: its refused activation is answered by a re-read of the winning row (the loser's created-status row stays as an inert orphan no read path adopts), proven under `-race` by `TestSubscriptionService_ConcurrentEnsureActive_ConvergesToOneActive` and pinned sequentially by `TestSubscriptionService_SecondActiveForOneTenant_RefusedByTheDatabaseIndex`. Genuine multi-subscription support would be its own design (`Active`'s single-row signature and the entitlement merge rules) and would drop this index.
- **`CreditService.Expire`'s idempotency is the caller's choice, and the scheduled sweep itself is not shipped.** A KEYED `Expire` (`PreDeductInput.IdempotencyKey`, which becomes the row's own ID through the same `insertIdempotent` core `PreDeduct` uses) is idempotent under retry: a sweep rerunning its own window under the same deterministic per-tenant+period key finds the first run's row and applies no second deduction and records no second audit event; a key that names a row of another kind is refused with `ErrIdempotencyKeyCollision`; and a refused first attempt (`ErrInsufficientCredits`) rolls its own row back so the key is never burned. The UNKEYED form (fresh `uuid.NewString()` every call) is NOT idempotent under retry -- it is the one-off, operator-driven shape. What is not shipped is the sweep itself: which credits expire, when, in what amount, on what cadence is product policy this module's data model cannot anchor (no grant-vintage or expiry-window column exists in the ledger), so a real `jobs`-driven sweep needs (a) that product-policy decision and (b) a host that schedules per-tenant sweep tasks (the `go/storage` `EnqueueExpirySweep` shape). The module supplies the at-most-once write such a sweep needs, never the policy.
- **`PreDeduct`'s idempotent retry never aborts its own transaction.** The retry path does not recover from a duplicate insert: the duplicate `(id, tenant_id)` insert is prevented up front, and the existing row is read back on the same still-open `dbkit.WithTenantSession` transaction. A statement error inside an open transaction aborts it on PostgreSQL (SQLSTATE 25P02) -- so a retried `PreDeduct`, a caller whose first attempt has already committed retrying after a timeout, would get an error instead of its own earlier reservation, on the money path itself -- while SQLite tolerates a failed statement inside an open transaction, which is why only a real-PostgreSQL tier can show the divergence; go/billing's own PostgreSQL tier is the standing proof (see Testing). The insert runs as `ON CONFLICT DO NOTHING` (reporting a duplicate as `inserted == false` with no error, through the repository's separate `insertIdempotent` core -- the strict `insert` is unchanged for `Grant`/`Expire`, whose fresh UUIDs have no retry contract), the transaction stays healthy, and the read-back returns the existing row -- when it is the caller's own earlier Deduct row; a key that names a row of another kind (a Grant, an Expire, an unkeyed row's UUID) is refused with `ErrIdempotencyKeyCollision` rather than answered as a reservation it was not -- on either dialect. What it does NOT cover: a duplicated-UUID `Grant`/`Expire` still errors mid-transaction (a genuine, unreachable-in-practice surprise, correct on both dialects), and the audit-write and balance-read best-effort contracts documented in the audit-trail bullet above are unchanged. The rest of the family carries no such shape: `resolve` (`Confirm`/`Refund`) performs no insert-then-recover, `ensureBalance` already uses `ON CONFLICT DO NOTHING`, and `PaymentEventRepository.InsertIfNew` catches its duplicate inside its own short `Create` transaction, never on a caller's still-open one.
- **Consumer status: `CreditService`, `Plan`/`Subscription`/`Entitlements.Check` have real reference-app callers; `Invoice`, the Quota/`UsageReader` judgment path and the payment-gateway lifecycle do not.** `internal/smilesim` consumes `CreditService`'s `PreDeduct`/`Confirm`/`Refund`/`Grant`/`Balance` end to end, and `examples/reference-app/internal/app/server.go`'s `aigateway.WithEntitlements` closure over `billingModule.Entitlements()` makes `EntitlementsService.Check` genuinely judge every `Chat`/`ChatStream`/`GenerateImage` call the app serves, with `internal/app/demo/demo_entitlements.go`'s boot-time seed driving real `PlanService.Resolve`/`Create` and `SubscriptionService.EnsureActive` calls along the way (see the reference-app subsections above) -- the mandatory-first-consumer rule is discharged for those surfaces specifically, not for `go/billing` as a whole. `Invoice` (both `invoice.go`'s repository and the row a real subscription lifecycle would eventually settle) and the payment-gateway lifecycle (a live `CreateCharge` call, and any `PaymentEvent`-driven `Subscription`/`Invoice` transition) still have no reference-app or other caller: the full pay-per-use-AND-subscription credit flow needs real payment-channel credentials to be meaningful end to end, which this environment does not have (see `go/billing/gateway/AGENTS.md`). The Quota/`UsageReader` judgment path of `EntitlementsService.Check` likewise has no real caller -- this app wires `billing.NewModule(db, nil)`, so its demo grants are Boolean by design (`internal/app/demo/demo_entitlements.go`), and a host exercising a quota-kind grant against genuine metering consumption does not exist. The compensating obligation for THOSE remaining gaps: the real, runnable godoc `Example` (`example_test.go`) keeps walking Plan creation, Subscription activation, both `Entitlements.Check` grant kinds, and the credits ledger's reserve → confirm pattern in one pass, plus the gateway layer's own three provider-package `Example`s each (construction, `PaymentGatewayRegistry` self-registration, and `ExampleGateway_VerifyWebhook` -- a real, doc-rendered signature verification plus normalization against a constructed fixture) -- the identical pattern `go/pki`'s X.509 layer and `go/metering` establish for the same situation. The host halves of those gaps (the reference-app/metering composition for the Quota/`UsageReader` path, and the reference-app halves of the payment-gateway lifecycle) are a wiring host's own work, not this module's, and nothing here is built for them: no caller exists in this module or in-workspace that would exercise a quota-kind grant, drive an `Invoice`, or settle a `Subscription` from a payment event.
- **Credit settlement never depends on a client polling -- with two documented residual edges.** `internal/smilesim.ReservationStore` durably persists the job-id-to-idempotency-key mapping (surviving a restart), and `Service.ReconcileOutstandingCredits`/`StartReconciler` periodically settle any reservation whose job has already finished, independent of any poll -- see the reference-app credits subsection above for the mechanism. What this does NOT cover: a failure to persist the reservation row itself, immediately after a successful `PreDeduct` and enqueue (an exceedingly narrow window -- a database write failing at exactly that moment), is logged and left for manual reconciliation rather than automatically recovered, since there is no durable record to recover from in that specific case; and the reconciliation sweep's interval (`DefaultReconcileInterval`, 5 minutes) means a never-polled reservation's balance correction can lag by up to that long, never instantly, unlike the poll-driven fast path.
- **The demo credit seed is a `Grant`, never a payment.** `examples/reference-app/internal/app/demo/demo_credits.go`'s `SeedDemoCredits` grants each demo tenant a fixed starting balance at boot so `internal/smilesim`'s reserve/confirm/refund wiring has something real to reserve against -- it is explicitly NOT a "buy a credit pack" flow, and no real Stripe/Alipay/WeChat sandbox purchase exists anywhere in this codebase (see `go/billing/gateway/AGENTS.md`'s "no live credentials" note). A real credit-pack-purchase HTTP flow does not ship -- it would need live payment-provider credentials, which this environment lacks.
- **`SeedDemoCredits`'s own idempotence is bounded, deliberately.** `CreditService.Grant` is not idempotent under retry (a fresh `uuid.NewString()` transaction id every call), so `SeedDemoCredits` guards a second boot against the same database file by checking the tenant's balance is still all-zero before granting again -- a tenant that has genuinely spent its way down to exactly zero on its own would be re-seeded. Acceptable for a reference app's own demo feature (`internal/app/demo/demo_credits.go`'s own doc comment states this explicitly), not a pattern a real deployment's credit-pack purchase flow should copy.
- **`PollingService.Poll` does not drive any `Subscription`/`Invoice` transition.** It updates `PaymentEvent.Status` and `Amount` alone from what `PaymentGateway.QueryStatus` reports -- no HTTP surface exists to receive a live webhook in the first place, so there is no live processing loop for the polling fallback to feed into, and half-wiring one without a real caller to prove it against would be exactly the kind of speculative build-ahead this file declines elsewhere for the identical reason (see the Scope table's "Driving `Subscription`/`Invoice` transitions from a `PaymentEvent`" row). An inbound webhook endpoint is where a `PaymentEvent`'s `Status` would actually start driving billing's own domain state.
- **`Poll` persists `QueryStatus`'s re-queried amount -- a resolved payment is never ledgered at a zero amount.** `normalizeCheckoutSession`'s completed-but-unpaid handling (see `go/billing/gateway/AGENTS.md`) deliberately zeroes `Amount` on the `ChannelStatusPending` row it inserts for an unsettled session -- exactly the row this polling fallback is meant to resolve. `markStatus` takes and persists a `Money` alongside `status` (via GORM's `Select` to force the write even when the freshly-queried amount happens to be zero-valued, since a struct-based `Updates` otherwise silently drops zero fields), and `Poll` passes through `QueryStatus`'s own re-queried amount rather than discarding it -- a row that resolves to `ChannelStatusSucceeded` therefore records the real `AmountCents`/`Currency`, never the zero-valued amount it was inserted with. Since `checkout.session.async_payment_succeeded` is itself unrecognized (see the gateway AGENTS.md's own note), this polling fallback is often the ONLY path that ever promotes such a row out of `Pending`; a discarded amount would permanently record a genuinely successful, money-moved payment in the audit ledger as a zero-amount success. `TestPaymentEventRepository_MarkStatus_OverwritesZeroAmount` and `TestPollingService_Poll_ResolvesZeroedAmountRow` are the regression tests.
- **No live consumer calls `CreateCharge`/`QueryStatus`/`VerifyWebhook` against a real payment channel.** Every provider package's real, offline-verifiable cryptography is genuinely implemented and genuinely tested (see `go/billing/gateway/AGENTS.md`'s own "What remains untestable without live credentials" section for the itemized, honest split between what is and is not exercised). No reference-app or other consumer holds live Stripe/Alipay/WeChat Pay credentials to call any of the three providers' `CreateCharge`/`QueryStatus` against a real account, or to receive a real webhook delivery from one.
- **Lifecycle writes are database-arbitrated: subscription transitions, payment-event marks and invoice status moves.** (1) `SubscriptionService.transition` is a guarded UPDATE whose WHERE carries the row id AND the status the move was validated from, with `RowsAffected` as the arbiter (`SubscriptionRepository.compareAndSetStatus`, the identical shape `CreditService.resolve`'s CAS uses). Two racing transitions cannot both commit from the same stale read: whichever write lands first wins, a losing `MarkPastDue` that validated from the same `Active` read is retried from the fresh status while the move stays legal (bounded by `maxTransitionAttempts`, a livelock guard), and it is refused with `ErrInvalidSubscriptionTransition` only when the fresh status genuinely makes the move illegal -- a successfully canceled (terminal) subscription can never be silently overwritten back to `PastDue`, because no legal move exists out of `Canceled`, so no stale guard can ever match it and `Canceled` is terminal under any interleaving. `TestSubscriptionService_ConcurrentCancelAndMarkPastDue_CanceledIsTerminal` is the regression (150 racing iterations; the invariant "Cancel returned success => the row is Canceled" holds every iteration). (2) `PaymentEventRepository.markStatus`'s UPDATE's WHERE carries the row's own current status (`Pending`) -- a mark can only ever be the row's first transition out of `Pending` -- and a guard that affects no row is disambiguated by re-reading: a missing row is `ErrPaymentEventNotFound`, an already-resolved one is a nil no-op (the record stands). A later, stale mark can therefore never regress a resolution the ledger row has already committed (a second overlapping poll pass, or a poll racing the webhook that resolved the row). `TestPaymentEventRepository_MarkStatus_CannotRegressResolvedRow` is the regression. (3) `InvoiceRepository.setStatus` validates every move against `invoiceTransitions` (Open -> Paid/Void; Paid and Void terminal), the exact legal-table shape `subscriptionTransitions` uses, refusing anything else with `billing.invalid_invoice_transition` (`ErrInvalidInvoiceTransition`, catalog text in both locale bundles) -- so `Void` on a `Paid` invoice is refused rather than silently rewriting the record of a collected payment. `TestInvoiceRepository_VoidOnPaidInvoice_Refused` is the regression.
- **The transactions route's recent window is served by truncating the service's full listing, not by a keyset-paginated read.** `Handler.BillingListCreditTransactions` narrows `CreditService.Transactions`' full newest-first result to the requested `limit` in the handler (handler.go's own doc comment says so, and `api/openapi.yaml`'s operation description says so too) -- a memory trade-off, never a correctness one, since the window is exactly the newest rows of an ordering the service already produces. A tenant whose ledger genuinely outgrows the recent window (this is an append-only ledger; a long-lived tenant's history grows without bound) needs a keyset-paginated service read and a cursor on the fragment; neither is shipped -- the gap is recorded here rather than half-building a cursor nothing calls.
- **The fragment is wired into the repository's API-contract tooling.** Taskfile `api:gen` carries this fragment's leg (the pinned `go run ...oapi-codegen@v2.8.0 -config oapi-codegen.yaml openapi.yaml` invocation, run from `go/billing/api`), `.github/workflows/api-contract.yml` regenerates and porcelain-gates `billing-server.gen.go` on the toolchain-touching path set,, and the fragment joins the merged `contracts/speed.yaml` document -- and through it orval's frontend SDK -- like every platform module's fragment does (docs/internal/21-api-contract.md's module-driven inclusion policy: a platform module's fragment is a merge member whether or not an in-workspace web consumer calls it, since the api-contract consistency gates pin the generated surface).
- **`Reason` is a declared bounded phrase, not free text.** Every reason-taking entry point (`PreDeduct`/`Grant`/`Expire`) validates a non-empty `Reason` through `validateReason` before anything is written, refusing a violation with the coded `ErrInvalidReason` (`billing.invalid_reason`, catalog text in both locale bundles): ASCII letters and digits joined by `:` `_` `-`, at most 255 characters -- the shape of the module's own documented vocabulary ("ai_generation:job_123", "plan:pro:monthly_included", "expiry:2026-09-policy"), closed to prose but deliberately not to an enum (consumers name their own tags, job ids and policy periods). The constraint exists because the same text is copied verbatim into the audit trail's `Changes` column (`emitCreditAudit`), where `go/dbkit/audit`'s Diff content contract (its `emit.go` doc) forbids content a caller could slip PII into: the reason is machine-readable annotation with a declared shape, never free text, so nothing reaching the permanent audit column is ever free-form. What this does not do: an empty reason stays legal, the ledger column itself stays a `VARCHAR(255)` with the module enforcing its bound in Go on both dialects, and a host reaching past `CreditService` to write a `CreditTransaction` row directly is outside the module's own write surface.
- **The poll-fallback idempotency key is window-scoped, and `PlanStore`'s by-id `Get`/`Update` are tenant-scoped.** (1) the poll's key is never tenant-constant: it carries the absolute-clock window (`jobs.ScheduleWindowStart`, `now.Truncate(pollIdempotencyWindowSize)`), chosen equal to `DefaultPollStuckAfter` (15 minutes) -- a poll cadence finer than the stuck threshold has nothing extra to detect, and the window bounds a stuck payment's unpolled time at one stuck period.
