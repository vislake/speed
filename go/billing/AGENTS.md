# billing

go/billing owns speed's Plan/Feature/Entitlement domain model, a channel-agnostic Subscription/Invoice model, and the credits ledger -- the second, parallel billing mode credit-based (pay-per-use) products use alongside subscriptions. This file is the module-level discipline that ships with `go/billing` to consuming projects; the design rationale lives in `docs/internal/06-billing-and-metering.md`, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Metrics instrumentation.** The 09-table "payment" row is instrumented at the sites this module genuinely has (`metrics.go`, unit-tested through ManualReaders in `metrics_test.go` and each provider's `webhook_metrics_test.go`): `billing.invoice.transition` (applied status transitions, from/to labeled -- recorded only where the guarded compare-and-swap UPDATE genuinely applied, refused moves never count) and `billing.invoice.open_dwell` (time an invoice stayed open, recorded at the transition out), both owned by `InvoiceRepository.setStatus`; and `billing.webhook.verify`, one shared counter on the billing meter that each provider's real `VerifyWebhook` records onto with its own channel label (stripe/alipay/wechat) and an outcome classified from the returned error's nilness through a defer over the named return. The shared register/record helpers are the one additive export on the billing root. The row's "intermediate-state ORDER count" is deliberately carried by invoices (the ledger's orders) rather than double-instrumented on the Subscription lifecycle's own intermediate-state vocabulary, recorded in `metrics.go`'s doc comment; the webhook outcome stays a succeeded/failed binary -- the finer signature-vs-payload classification is a diagnostic refinement the 09-table's first-alert list does not name.


**Status: the domain model, the credits ledger, the gateway seam and a read-only HTTP surface are all real and tested.** The module ships `Feature`/`Plan`/`Grant`/`Entitlements` with tenant-custom Plan lookup precedence, a channel-agnostic `Subscription`/`Invoice` lifecycle driven by a plain Go call, the credits ledger (`credit_balance`, the append-only `credit_transaction` log, and the reserve -> confirm/refund pattern, transactionally safe under concurrent deductions), the `PaymentGateway` interface and registry (`gateway.go`) with three real provider implementations under `go/billing/gateway` (`stripe`, `alipay`, `wechat` -- see that subpackage's own `AGENTS.md`), the tenant-scoped `PaymentEvent` ledger and its insert-first-dedup repository (`payment_event.go`), the active-polling fallback (`job.go`), and a read-only HTTP fragment (balance, recent credit transactions, invoice list/detail) mounted through `reg.Routes.Mount`. Actual money movement through a live wired payment-gateway consumer is NOT shipped -- no caller invokes `CreateCharge` against a real Stripe/Alipay/WeChat account. Judge what exists by the code, not by this sentence.

## Consumers and wiring

- `examples/reference-app/internal/smilesim` is a real, paid consumer of `CreditService`: it reserves `CreditsPerSimulation` credits via `PreDeduct` BEFORE calling `aigateway.Gateway.GenerateImage` (an insufficient balance returns `ErrInsufficientCredits` and the gateway is never reached), using an idempotency key minted once per generation request and reused for every later settlement call, and settles the reservation through `Confirm` on success or `Refund` on dead-letter/cancel. Its `ReservationStore` persists the job-id-to-idempotency-key mapping (surviving restarts) and a periodic `ReconcileOutstandingCredits` sweep settles any reservation whose job has already reached a terminal status -- independent of whether anything ever polls (see `examples/reference-app/internal/smilesim`'s own docs).
- `examples/reference-app/cmd/server/server.go` wires `aigateway.WithEntitlements(billingModule.Entitlements())` -- the `EntitlementsFunc` closure adapter `go/ai-gateway/seams.go` documents -- so go/ai-gateway's own `checkEntitlement` gate, which runs on every `Chat`/`ChatStream`/`GenerateImage` call before any provider is reached, judges against a real `EntitlementsService.Check`. `demo_entitlements.go`'s boot-time seed resolves-else-creates the platform-wide demo Plan and gives every demo tenant an Active subscription through real `PlanService`/`SubscriptionService` calls.
- `cmd/server/demo_credits.go`'s `seedDemoCredits` grants each demo tenant a starting balance through a real `CreditService.Grant` call at boot -- explicitly NOT a payment, the deliberate stand-in for a real credit-pack-purchase leg (no live payment-provider credentials exist in this environment; see `go/billing/gateway/AGENTS.md`).
- The overage-threshold event's relationship is comment-only so far: `OverageModeNotify` and the entitlement code name `EventOverageThresholdCrossed` as the signal that mode relies on, while no code in either module subscribes to it (see go/metering/overage.go's own doc comment).

What still has no real caller: `Invoice` (repository and lifecycle), the payment-gateway lifecycle (a live `CreateCharge`, and any `PaymentEvent`-driven `Subscription`/`Invoice` transition), and the Quota/`UsageReader` judgment path of `EntitlementsService.Check` (this app wires no usage reader, so its demo grants are Boolean by design; a host exercising a quota-kind grant against genuine metering consumption remains unwritten). A real pay-per-use-AND-subscription credit flow needs live payment-channel credentials to be meaningful end to end.

## Scope

**Shipped surface.** `Feature`/`FeatureKind`, `Plan`/`Grant`/`Money`/`BillingInterval`, and `Entitlements`/`Decision` (`model.go`). `PlanStore`/`PlanService` (`plan.go`): CRUD plus `Resolve`, the tenant-custom lookup precedence (a tenant-custom row for `(tenantID, key)` overrides the platform-wide row for `key` when both exist, falling back to the platform-wide row otherwise), with by-id reads and writes scoped to the named tenant and the one deliberate cross-scope read named `GetPlatformPlan`. `EntitlementsService` (`entitlements.go`): the `Entitlements.Check` implementation -- for a Quota-kind Feature it reads `go/metering`'s real-time counter through the small `UsageReader` interface (never a summary table, which has aggregation delay and would let an over-quota request through), rounding the used count UP against the grant's integer limit, and it never itself decides anything about credits. `Subscription`/`SubscriptionRepository`/`SubscriptionService` (`subscription.go`): a channel-agnostic internal domain concept with no payment-channel reference of any kind, whose lifecycle (`created`/`active`/`past_due`/`canceled`) is driven by a plain Go call (`Activate`/`MarkPastDue`/`Cancel`), publishing `EventSubscriptionStatusChanged` on every transition; every transition is database-arbitrated (a guarded UPDATE whose WHERE carries the status the move was validated from, with `RowsAffected` as the arbiter, retried from the fresh status while the move stays legal). `Invoice`/`InvoiceRepository` (`invoice.go`): the equally channel-agnostic billing-document counterpart with the same guarded-transition discipline. The credits ledger (`credit_balance.go`, `credit_transaction.go`, `credit_service.go`): `CreditBalance` (per-tenant `available`/`reserved`), the append-only `CreditTransaction` log (`grant`/`deduct`/`expire`; a `refund` is a Deduct row's resolution, not its own row), and `CreditService`'s `PreDeduct`/`Confirm`/`Refund`/`Grant`/`Expire`/`Balance`/`Transactions`. `ChannelReference`/`ChannelStatus`/`NormalizedEventType`/`NormalizedEvent`/`ChargeRequest`/`ChargeHandle` and the `PaymentGateway` interface plus `PaymentGatewayRegistry` (`gateway.go`). `PaymentEvent`/`PaymentEventRepository` (`payment_event.go`). `PollingService`/`Module.WithQueue`/`Module.WithGateways` (`job.go`, `module.go`). `pkgcore.Module` wiring (`module.go`): permissions (`billing:plan:manage`, `billing:subscription:read`/`manage`, `billing:credit:read`/`manage`), audit actions for the credit ledger's five state-changing operations, the two published domain events (`billing.plan.changed`, `billing.subscription.status_changed`), and the HTTP fragment mounted at `/api/v1/billing`.

**The five audited credit actions.** `Grant`/`PreDeduct` (the reserve half)/`Confirm`/`Refund`/`Expire` each call `go/dbkit/audit`'s `Emit` under the exact declared action name, through the one shared `emitCreditAudit` helper, only AFTER the mutating transaction has genuinely committed (never from inside the closure) -- so the audit write opens a fresh, uncontended session rather than nesting inside one still open, sidestepping the same-file `SQLITE_BUSY` hazard of `AuditBus`'s automatic write-capture plugin the same way the notes module's explicit `Emit` does. An `Emit` failure is logged at Error level and never turns an already-committed credit mutation into a reported failure. The idempotent-retry branches carry a genuine-state-change guard (`reserved`, `resolved`, `expired` flags), so a retry that changed nothing emits nothing; `Balance` never emits. `Changes.After` carries the applied delta (`amount`, `reason` when supplied) plus, best effort, the tenant's resulting balance -- read from INSIDE the same transaction as the mutation, immediately after the balance delta and before commit, so the reported resulting balance is exactly this operation's own post-delta state, never a nearby moment's snapshot a concurrent operation could have perturbed.

**Gateway details.** Each provider subpackage self-registers from its own `init()` under `"gateway.stripe"`/`"gateway.alipay"`/`"gateway.wechat"`. `CreateCharge` differs by channel by design: Stripe creates a genuine recurring subscription (called once per `Subscription` at first activation; Stripe's billing engine generates later cycles, announced through its own webhook events); Alipay/WeChat Pay create one one-time Native (QR) order per `Invoice`, since neither channel offers a periodic-charge primitive at this repository's target tier -- their native recurring (withhold) products are deliberately not implemented. All three attach `TenantID`/`SubscriptionID`/`InvoiceID` to the channel-side object through the channel's metadata mechanism (Stripe's `Metadata` plus `subscription_data.metadata`, WeChat's `attach`, Alipay's `passback_params`) and decode them back in `VerifyWebhook` -- no provider package holds a mapping table of its own. `PollingService.Poll` re-queries stuck `Pending` rows through `QueryStatus` and records status AND the re-queried amount on the row; its failure log line carries the bounded `failure_class` classification, never raw gateway error text. See `go/billing/gateway/AGENTS.md` for the per-provider write-ups, the SDK-choice rationale and measured dependency cost, and what remains untestable without live credentials.

## Deliberately not shipped

| Not here | Where it belongs / why |
|---|---|
| An HTTP surface receiving live webhooks | Not shipped: verification/normalization logic and the registry are real, but no inbound endpoint is mounted and no `Subscription`/`Invoice` transition is driven from a verified `NormalizedEvent` (see Known limitations) |
| Actual money movement through a live, wired consumer | Not shipped: no caller invokes `CreateCharge` against a real Stripe/Alipay/WeChat account; provider packages build and sign real requests and verify real signatures offline |
| Alipay/WeChat native periodic-withhold billing | Never, by design: neither channel offers a periodic-charge primitive at this repository's target tier -- see `go/billing/gateway/AGENTS.md` |
| Multiple concurrent subscriptions per tenant | Not shipped: `SubscriptionService.Active` assumes at most one active subscription per tenant (see Known limitations) |
| The credit-expiry sweep (which credits expire, when, in what amount, on what cadence) | Not shipped: it is product policy this module's data model cannot anchor (no grant-vintage or expiry-window data exists in the ledger), plus a host's `jobs` wiring; `CreditService.Expire` supplies the at-most-once write such a sweep needs (`ExpireInput.IdempotencyKey`) -- see Known limitations |
| Keyset-paginated reads for the ledger / invoice windows | Not shipped: the fragment's recent window is served by truncating the service's full newest-first listing (see Known limitations) |
| Dynamic config items | Not shipped by design: `Register` declares zero config items -- no code path reads one (see "Design choice: no config items" below) |

## Design choice: Plan's tenant-scoping duality

**Why `Plan` deliberately does not implement `dbkit.TenantScoped`.** `Plan` is a genuinely dual-domain table: a platform-wide row (`TenantID == ""`) is platform data, meant to be visible to *any* tenant's `Resolve` lookup; a tenant-custom row is that one tenant's private data. No single dbkit data-domain capability spans both faces of the same table -- `dbkit.TenantScoped`'s own isolation plugin would hide every platform-wide row from a tenant-scoped query, which is exactly the opposite of what "fall back to platform-wide when no tenant-custom Plan exists" requires.

This is not a novel problem: `go/config`'s own `configs` table (`system` -> `tenant` scope tiers) solves the identical duality, and `Plan` adopts its exact answer, column for column -- a plain, `NOT NULL` `tenant_id` string column holding the empty-string sentinel (`platformScopeSentinel`) for a platform-wide row (empty rather than `NULL`, for the same reason `go/config`'s `row` and `go/dbkit/audit`'s `AuditEvent` both document: `NULL`s are distinct in a PostgreSQL unique index, so two platform rows for one key could coexist under `NULL` where the empty string collapses them into the one row the `(tenant_id, key)` unique index promises), reached through a plain `*gorm.DB` (`PlanStore`, never `dbkit.Repository[T]` -- the generic constraint requires `TenantScoped`, which this table must *not* implement), isolation proven with `tenancytest.AssertNotTenantScoped` rather than `AssertIsolated` (`TestPlan_AssertNotTenantScoped`, `plan_test.go`). The scoping this table actually needs -- "a tenant only ever sees its own custom Plans plus the platform-wide catalog, never another tenant's custom Plans" -- is enforced by the store's own signatures, never by dbkit's isolation plugin. By-id reads and writes are scope-guarded: `PlanStore.Get(ctx, tenantID, id)` returns only the row the named tenant scope itself owns, `PlanStore.Update(ctx, tenantID, plan)` writes only such a row (the WHERE carries both id and scope, and the plan struct being saved must carry the scope too), and the one deliberate cross-scope read is named for what it does: `GetPlatformPlan`. Rows outside the named scope answer the same `ErrPlanNotFound` a genuinely missing id gets, in every path.

## Design choice: `CreditTransaction` does not embed `dbkit.Repository[T]`

`CreditTransaction` genuinely **is** tenant data (unlike `Plan` above) -- every row belongs to exactly one tenant, with no cross-tenant reader. But `CreditTransactionRepository` deliberately does **not** embed `dbkit.Repository[CreditTransaction]`: embedding would promote `Repository[T]`'s own `Update` and `Delete` methods onto this type, which is exactly the mutability an append-only financial ledger must never offer -- the same rigor `go/dbkit/audit`'s `AuditEvent`/`Repository` already establishes for this codebase's other append-only ledger. `CreditTransactionRepository` exposes only `Insert` and two read methods (`Get`, `ListByTenant`); `TestCreditTransactionRepository_HasNoUpdateOrDeleteMethod` proves it with the identical reflection check `go/dbkit/audit/repository_test.go`'s own uses.

`CreditTransaction`'s primary key is the composite `(id, tenant_id)`, not `id` alone: a Deduct row's `ID` is the *caller's own* `IdempotencyKey`, which is therefore not globally unique across tenants -- the identical composite-key shape `go/metering`'s `UsageSummary` uses for the same reason.

## Concurrency: `applyBalanceDelta`, the ledger's one write primitive

Every `CreditService` balance mutation funnels through one function, `applyBalanceDelta` (`credit_service.go`): a single database-arbitrated `UPDATE` that adds `availableDelta` to `Available` and `reservedDelta` to `Reserved`, guarded in the SAME statement so neither bucket can go negative (`WHERE ... available + availableDelta >= 0 AND reserved + reservedDelta >= 0`) -- never a Go-level read-modify-write. Two concurrent `UPDATE` statements against the same row are serialized by the database itself (ordinary row locking, plain portable SQL that runs identically on SQLite and PostgreSQL), so the second to run sees the first's already-applied change. `TestCreditService_PreDeduct_ConcurrentOverBalance_OnlyOneSucceeds` (`credit_service_test.go`), run under `-race`, is the proof: exactly one of two racing over-balance `PreDeduct` calls succeeds, the balance ends up consistent, and the loser's own `CreditTransaction` row was never written (the whole attempt rolls back inside one database transaction).

`applyBalanceDelta` is a raw `.Exec(...)` call, not `dbkit.Repository[T]`'s own `Update` (a full-row `Save`, incapable of server-side arithmetic) and not a struct passed to GORM's `.Updates()` (which silently *omits* any field left at its Go zero value from the `SET` clause -- fatal here, since `Available` or `Reserved` legitimately reaching exactly zero must still be written). `.Exec` is a narrower surface than the three entry points (`.Table`/`.Model`/`.Raw`) the raw-gorm-bypass semgrep rule flags -- with the tenant passed explicitly into the `WHERE` clause (mandatory here, not merely defense in depth, since `.Exec` bypasses the ORM callback chain the isolation plugin hooks into) and an isolation test proving the underlying table's own tenant scoping; every `applyBalanceDelta` call site runs inside `dbkit.WithTenantSession`, so on PostgreSQL the row-level-security GUC is also engaged underneath this application-level guard.

`CreditService.ensureBalance` materializes a tenant's first `CreditBalance` row (all-zero) with `INSERT ... ON CONFLICT (id) DO NOTHING` -- the identical dialect-neutral upsert clause `go/config`'s `store.put` already uses -- so two callers racing to touch a brand-new tenant's balance for the first time never both try to `Create` the same row.

## Design choice: `PaymentGateway`/`PaymentGatewayRegistry` live in billing's root package, never in `billing/gateway`

The dependency direction is one-way: `go/billing/gateway` (and its `stripe`/`alipay`/`wechat` sub-subpackages) may import `go/billing`, but `go/billing`'s own root package must never import `go/billing/gateway` or anything under it. That rule only holds if the seam a caller depends on -- the `PaymentGateway` interface, and the registry a provider registers into -- is declared somewhere neither side of the one-way edge would need to cross to reach it. Declaring both in `go/billing`'s own root package is what makes that true: a caller (business code today; a live webhook endpoint eventually) depends on `billing.PaymentGateway` and resolves an implementation through `billing.PaymentGatewayRegistry`, never importing `go/billing/gateway` at all, while `go/billing/gateway/stripe`'s own `init()` imports `go/billing` to register itself. Putting the interface in the subpackage instead would force exactly the import edge the rule forbids -- and a provider-specific type would leak into the domain model over time.

This is the identical shape `go/pki`'s `Signer`/`SignerRegistry` established for its own provider split. `PaymentGatewayRegistry` ships with no built-in implementation pre-registered: every `PaymentGateway` genuinely needs a provider SDK or a hand-rolled channel client, so there is no zero-dependency default. `Module.WithGateways` is the direct-injection half of the same duality: a host that already holds a constructed `PaymentGateway` hands the resulting map to `PollingService` through it, rather than every call site doing its own name lookup. The CI-enforced half -- three `depguard` entries in `.golangci.yml`, one per provider subpackage, each narrowed to that subpackage alone -- lives with the provider subpackages themselves; see `go/billing/gateway/AGENTS.md`'s own write-up of the full mechanism.

## Design choice: `PaymentEvent` is genuinely tenant-scoped, unlike `Plan`'s dual-domain shape

`PaymentEvent` has no platform-wide face: every row belongs to exactly one tenant's payment history, decoded from the channel-side object's own metadata at webhook-verification time (`NormalizedEvent.TenantID`'s own doc comment describes the round trip). `PaymentEvent` therefore implements `dbkit.TenantScoped` and is reached through `dbkit.Repository[PaymentEvent]`, proven with `tenancytest.AssertIsolated`.

The uniqueness constraint `uq_billing_payment_events_channel_event` on `(channel, provider_event_id)` is deliberately NOT further scoped by `tenant_id`: a channel's own event id is already globally unique across that channel's entire account, so widening the key to include `tenant_id` would only let a bug that mis-decodes `TenantID` silently create two rows for the one event it actually was -- the exact double-processing dedup exists to prevent. `PaymentEventRepository.InsertIfNew` observes the constraint by returning `(true, nil)` for a genuinely new event and `(false, nil)` -- never an error -- for one already recorded. That is the row-level half of the insert-first-to-dedup rule, proven on its own; the processing half (the shape a live webhook handler's insert-plus-side-effects must take) is deliberately undetermined while no live webhook-processing chain exists -- see `InsertIfNew`'s own doc comment.

## Design choice: no config items

`go/billing`'s `Register` declares **zero** config items. There is no code path with a natural candidate: no trial-period length, grace-period duration, or default-credit-expiry-window is read, computed, or even referenced by anything `SubscriptionService`, `CreditService` or `EntitlementsService` actually does -- every one of those knobs belongs to scheduler/gateway machinery that does not exist (dunning after a `past_due` subscription, a `jobs`-driven expiry sweep). Inventing a config item with no code path to attach it to is the speculative-declaration pattern the error indexes of `go/metering` and `go/pki` name and reject. `TestModule_Register_DeclaresItsSurface`'s `"no config items are declared"` subtest is the standing proof this stays true.

## Known limitations

- **`SubscriptionService.Active` assumes at most one `active` subscription per tenant.** It scans the tenant's full subscription list in Go and returns the first `active` one found; nothing enforces single-subscription-per-tenant at the database level, so a tenant with two concurrently active subscriptions would have the second silently ignored. A genuine multi-subscription model needs its own uniqueness decision.
- **`CreditService.Expire`'s idempotency is the caller's choice; the jobs-driven sweep itself does not ship.** A KEYED `Expire` (`ExpireInput.IdempotencyKey`, which becomes the row's own ID through the same `insertIdempotent` core `PreDeduct` uses) is idempotent under retry: a sweep rerunning its own window under the same deterministic per-tenant+period key finds the first run's row, applies no second deduction and records no second audit event; a key naming a row of another kind is refused with `ErrIdempotencyKeyCollision`; a refused first attempt (`ErrInsufficientCredits`) rolls its own row back so the key is never burned. The UNKEYED form (fresh `uuid.NewString()` every call) is NOT idempotent under retry -- it is the one-off, operator-driven shape. The sweep itself -- which credits expire, when, in what amount, on what cadence -- is product policy this module's data model cannot anchor (no grant-vintage or expiry-window data exists in the ledger), and the scheduler that runs it is a host's `jobs` wiring (the `go/storage` `EnqueueExpirySweep` shape).
- **Recovery code must never depend on a failed statement leaving its transaction usable.** `PreDeduct`'s idempotent-retry read-back runs on the caller's own still-open transaction; on PostgreSQL a unique-violation statement error aborts that transaction (SQLSTATE 25P02), so the insert runs as `ON CONFLICT DO NOTHING` (reporting a duplicate as `inserted == false` with no error, through the repository's `insertIdempotent` core -- the strict `insert` stays for `Grant`/`Expire`, whose fresh UUIDs have no retry contract), the transaction stays healthy, and the read-back returns the existing row on either dialect. The PostgreSQL integration tier is the standing proof. A duplicated-UUID `Grant`/`Expire` still errors mid-transaction -- a genuine, unreachable-in-practice surprise, correct on both dialects. The same non-poisoning discipline governs `ensureBalance`'s `ON CONFLICT DO NOTHING` and `foldIntoSummaryOnce`-shaped receipts elsewhere in this codebase's modules.
- **An audit-write loss has no compensating recovery path.** `emitCreditAudit` failures are logged at Error level and never retried or queued for later delivery -- the underlying credit mutation already committed by the time the emit runs, so a caller must never see an already-successful operation reported as a failure; a lost audit write in that narrow window has no recovery path, exactly as for the notes module's identical call. The resulting-balance fields are omitted from the one event when their in-transaction read fails (logged, never blocking) -- they are otherwise exactly as reliable as the mutation itself, since they are read inside the mutating transaction.
- **`Invoice`, the payment-gateway lifecycle and the Quota/`UsageReader` path have no real caller.** `CreditService`'s surfaces and `Entitlements.Check`'s Boolean/Unlimited judgment have real consumers (see "Consumers and wiring"); `Invoice`, the payment-gateway lifecycle (a live `CreateCharge`, any `PaymentEvent`-driven transition) and the Quota judgment path do not. A full pay-per-use-AND-subscription credit flow needs real payment-channel credentials to be meaningful end to end, which this environment does not have (see `go/billing/gateway/AGENTS.md`).
- **The credit demo seed is a `Grant`, never a payment.** `seedDemoCredits` grants each demo tenant a starting balance at boot so the smilesim wiring has something real to reserve against -- explicitly NOT a "buy a credit pack" flow, and no real Stripe/Alipay/WeChat sandbox purchase exists anywhere in this codebase. A real credit-pack-purchase HTTP flow remains unwired, whenever this environment gains live payment-provider credentials. `Grant` is not idempotent under retry, so `seedDemoCredits` guards a second boot by checking the tenant's balance is still all-zero before granting again -- a tenant that has genuinely spent its way down to exactly zero would be re-seeded; acceptable for a reference app's own demo feature, not a pattern a real deployment's purchase flow should copy.
- **`PollingService.Poll` does not drive any `Subscription`/`Invoice` transition.** It updates `PaymentEvent.Status` and `Amount` alone from what `PaymentGateway.QueryStatus` reports. No HTTP surface exists yet to receive a live webhook in the first place, so there is no live processing loop for the polling fallback to feed into. A live webhook endpoint is where a `PaymentEvent`'s `Status` actually starts driving billing's own domain state.
- **The fragment's recent windows are served by truncating the services' full listings, not by keyset-paginated reads.** `Handler` narrows `CreditService.Transactions`'/`InvoiceRepository.ListByTenant`'s full newest-first result to the requested `limit` in the handler -- a memory trade-off, never a correctness one, since the window is exactly the newest rows of an ordering the services already produce. A tenant whose ledger or invoice history genuinely outgrows the recent window needs a keyset-paginated service read and a cursor on the fragment.
- **No live consumer calls `CreateCharge`/`QueryStatus`/`VerifyWebhook` against a real payment channel.** Every provider package's real, offline-verifiable cryptography is genuinely implemented and genuinely tested (see `go/billing/gateway/AGENTS.md`'s "What remains untestable without live credentials" section for the itemized, honest split).
- **`Reason` is a declared bounded phrase, not free text.** Every reason-taking entry point validates a non-empty `Reason` through `validateReason` before anything is written: ASCII letters and digits joined by `:` `_` `-`, at most 255 characters -- the shape of the module's own documented vocabulary, closed to prose but deliberately not to an enum (consumers name their own tags, job ids and policy periods). The constraint exists because the same text is copied verbatim into the audit trail's `Changes` column, where the audit Diff content contract forbids content a caller could slip PII into. An empty reason stays legal; the ledger column itself stays a `VARCHAR(255)` with the module enforcing its bound in Go on both dialects; a host reaching past `CreditService` to write a `CreditTransaction` row directly is outside the module's own write surface.
- **Subscription and invoice lifecycle writes are database-arbitrated compare-and-swaps.** Every `SubscriptionService.transition` and `InvoiceRepository.setStatus` is a guarded UPDATE whose WHERE carries the row id AND the status the move was validated from, with `RowsAffected` as the arbiter, retried from the fresh status while the move stays legal (bounded by `maxTransitionAttempts`) and refused with the coded transition error only when the fresh status genuinely makes the move illegal -- so a `Cancel` that committed can never be silently overwritten by a `MarkPastDue` that validated from a stale read, no legal move exists out of `Canceled` (terminal under any interleaving), and a `Void` can never rewrite a `Paid` invoice.
- **The poll-fallback idempotency key is window-scoped.** `pollIdempotencyKey` carries the absolute-clock window (`now.Truncate(pollIdempotencyWindowSize)`, the window equal to `DefaultPollStuckAfter`): same-window enqueues collapse into one job (the concurrency protection), a later window's enqueue is a new job (periodicity restored), and a dead-lettered window poisons only itself -- a tenant-constant key would give each tenant exactly one poll task per database file on StandaloneQueue, whose idempotency is unconditional, and would let a dead-lettered poll silence its tenant's later enqueues entirely. `poll_window_test.go` pins all three properties against a real `jobs.StandaloneQueue`.
- **`PlanStore` by-id reads and writes are tenant-scope-guarded.** `Get`/`Update` reach exactly the named scope's own rows; the one deliberate cross-scope by-id read is `GetPlatformPlan`, and `SubscriptionService.Create`/`EntitlementsService.Check` resolve a subscription's platform-referencing `PlanID` through a Get-then-GetPlatformPlan two-step answering the identical `ErrPlanNotFound` for a foreign tenant's id.
