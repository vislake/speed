# billing/gateway

`go/billing/gateway` is billing's payment-channel adapter layer: three sub-subpackages, `stripe`, `alipay` and `wechat`, each a real `billing.PaymentGateway` implementation for one payment channel. This file is the subpackage-level discipline that ships with `go/billing/gateway` to consuming projects; the design rationale lives in `docs/internal/06-billing-and-metering.md`'s domestic-plus-international dual payment-mode section, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: three real provider implementations, each with genuinely implemented and tested offline cryptography.** `stripe`, `alipay` and `wechat` each implement `billing.PaymentGateway` (declared in `go/billing`'s own root package, `gateway.go`) and ship component descriptors (`component.go`) selectable through the composition configuration. What is NOT shipped: an HTTP surface for receiving live webhooks (no inbound endpoint is mounted anywhere), Alipay/WeChat native recurring billing (explicitly out of scope -- see "The domestic-leg trade-off" below), and live-account verification (see "What remains untestable without live credentials" below). Judge what exists by the code, not by this sentence.

## The one-way dependency rule

**`go/billing/gateway` (and its three sub-subpackages) may import `go/billing`. `go/billing`'s own root package must never import `go/billing/gateway` or anything under it.** This is the mechanism that keeps the core design principle -- "`Subscription` is an internal domain concept, a payment channel is merely the collector" -- true in code rather than only in prose.

The dependency runs both ways INSIDE the gateway subpackage tree: the three sub-subpackages import this root package for the helpers they share (`shared.go`'s order-number derivation, CNY guard, header lookup, gateway-URL resolution and PEM key parsing), so each helper exists once rather than per provider. The root package never imports the sub-subpackages -- it has no provider-specific import and carries no provider SDK, so a consumer of the shared helpers pulls in nothing channel-shaped.

The mechanism is the identical component-descriptor shape `go/pki`'s signer providers established for their own splits (`go/pki/signer/vault`, `go/pki/signer/kmsaws`):

- `go/billing`'s root package (`gateway.go`) declares `PaymentGateway`, an interface with three methods (`CreateCharge`, `VerifyWebhook`, `QueryStatus`) grounded in what `SubscriptionService`/`InvoiceRepository` actually need, and the provider-agnostic types every implementation exchanges with a caller (`ChargeRequest`/`ChargeHandle`, `NormalizedEvent`, `ChannelStatus`, `NormalizedEventType`, `ChannelReference`). None of these types ever carries a provider-specific field -- no `stripe.Subscription`-shaped field, no Alipay notify param map.
- No provider component is selected by default: every `PaymentGateway` genuinely needs a provider SDK or a hand-rolled channel client, so there is no zero-dependency default the way `LocalSigner` is for pki's `signer.local`.
- Each sub-subpackage registers its component from its own `init()` (`component.go`): `stripe` as `"gateway.stripe"`, `alipay` as `"gateway.alipay"`, `wechat` as `"gateway.wechat"`. A host that never blank-imports a provider subpackage never selects that name, and a request naming an unselected component fails with `pkgcore.ErrUnknownComponent`.
- Each descriptor implements the `"gateway"` module, contributing a member of the `"gateway"` catalog (`ProvidesMember` of `(*billing.PaymentGateway)(nil)`) and declaring 0 capabilities: several channels coexist as selected members, read by name through `pkgcore.Members` / `pkgcore.Build`. A composition block spells the identical key set the flat construction path documents, and each descriptor's `New` funnels through the package's one construction path (`gatewayFromConfig` → `NewGateway`, which owns the required-field checks and key parsing), so the two shapes cannot diverge.
- A host that already holds a constructed `PaymentGateway` value (built from a provider component it selected in the composition, or by calling a provider's own `NewGateway` directly) wires it wherever one is needed by value -- `billing.WithGateways(map[string]PaymentGateway{...})` for the active-polling fallback (`go/billing/job.go`'s `PollingService`), or a live webhook endpoint when one exists. This mirrors the component-selection-vs-direct-injection duality `go/pki`'s signer story documents: selection is for name-plus-block resolution (a `ComponentConfig`, an environment-driven bootstrap), direct injection is for a caller that already did the wiring.

Enforcement is two-layered:

- **Compile-time / packaging**: no provider SDK's import ever appears in `go/billing`'s own root package. Go's module-graph pruning (`go >= 1.17`) means a consumer that imports only `go/billing`'s root package never pulls a provider SDK's dependency closure into its own build.
- **CI-enforced**: three `depguard` rules in the repository's `.golangci.yml` (`stripe-sdk-only-in-billing-gateway-stripe`, `alipay-sdk-only-in-billing-gateway-alipay`, `wechat-sdk-only-in-billing-gateway-wechat`), each narrowed to its own implementation subpackage.

## The domestic-leg trade-off

- **Stripe (international)**: `CreateCharge` creates a genuine, ongoing Stripe subscription (a Checkout Session in `"subscription"` mode, with an inline recurring price for the requested amount) -- called ONCE per `billing.Subscription`, at its first activation. Stripe's own billing engine generates every later cycle's invoice and charge on its own, announced through its own webhook events -- `checkout.session.completed`/`.expired`/`.async_payment_failed` for the first cycle, and `invoice.paid`/`invoice.payment_failed`/`customer.subscription.updated` (canceled transitions only) for every later renewal cycle, all six recognized by `stripe/event.go`'s `normalizeEvent`; a caller does not call `CreateCharge` again for later cycles of the same `Subscription`.
- **Alipay / WeChat Pay (domestic)**: neither channel offers a periodic-charge primitive at this repository's target tier (the surveyed state of both channels' published APIs), so `CreateCharge` creates ONE one-time order (Alipay's `alipay.trade.precreate`, WeChat Pay's `POST /v3/pay/transactions/native` -- both the Native/QR-code product) for ONE `billing.Invoice`. A caller re-runs `CreateCharge` once per internally-tracked billing cycle instead. Alipay's periodic-withhold product and WeChat Pay's delegated-withhold agreement product -- distinct, higher-compliance-burden API families -- are deliberately not implemented.

Both domestic providers attach `req.TenantID`/`SubscriptionID`/`InvoiceID` to the created channel-side object using whichever metadata mechanism the channel offers -- Alipay's `passback_params` common request parameter, WeChat Pay's `attach` field on the Native order -- JSON-encoded as `{"t":...,"s":...,"i":...}`, and `VerifyWebhook` decodes it back out of the matching notification. Stripe attaches them twice over: on the Checkout Session's own `Metadata` map (what the `checkout.session.*` events carry) AND on `subscription_data.metadata`, the subset of session parameters Stripe applies to the SUBSCRIPTION it creates when the session completes -- a Checkout Session's own metadata is NOT copied onto that subscription, and every later lifecycle object (the subscription itself, each renewal invoice's `parent.subscription_details.metadata` snapshot) only carries the keys because of that second copy. This round-trip is what lets `NormalizedEvent.TenantID`/`SubscriptionID`/`InvoiceID` be populated without any provider package holding a table mapping a `ChannelReference` back to a tenant.

## Provider-by-provider notes

### `stripe`

Uses the official `github.com/stripe/stripe-go/v82` SDK -- the only Go client Stripe itself publishes. Built over the SDK's per-resource `Client` types (`checkout/session.Client{B: stripe.Backend, Key: string}`), not the newer `stripe.Client` aggregate the SDK's own docs now recommend for new integrations -- a deliberate, documented departure: `stripe.Client`'s own per-resource fields are concrete, unexported struct types with no interface module, while `stripe.Backend` is a real, first-class interface the SDK's own doc comment says exists explicitly "to enable mocking for during testing if needed". This package's testing strategy for `CreateCharge`/`QueryStatus` depends on that module; the per-resource `Client` type is marked `Deprecated` in the SDK's own doc comments but remains fully shipped and functional as of the pinned version. `gateway.go`'s own doc comment carries the full write-up.

`VerifyWebhook` uses `webhook.ConstructEventWithOptions` with `IgnoreAPIVersionMismatch: true` -- a real, deliberate choice, not a security shortcut: the plain `webhook.ConstructEvent` also refuses an event whose own `api_version` does not match the exact Stripe API version this pinned SDK release was generated against, which would make webhook verification fail closed for essentially any real merchant account whose webhook endpoint is pinned to a different (often much older) API version than this dependency's release cadence. The HMAC-SHA256 signature itself -- never the `api_version` field -- is what actually proves a delivery is genuine, and that check is never weakened.

**Webhook/query agreement.** `normalizeCheckoutSession` mirrors `QueryStatus`'s own `sessionStatus` on the one point the two must agree: a "complete" session that is still `PaymentStatusUnpaid` (delayed settlement) normalizes to `NormalizedEventChargePending`/`ChannelStatusPending`, never a false `Succeeded` -- the row then lands exactly where `PollingService`'s active-polling fallback looks for stuck rows. `QueryStatus` expands `"subscription"` on its `Get` call (set directly on `CheckoutSessionParams`'s own top-level `Expand` field -- the embedded `Params.AddExpand` is deprecated in stripe-go v82 precisely because newer generated params types shadow it with their own `Expand` field, and calling `AddExpand` silently mutates a field the request never serializes), and the Complete/Unpaid branch consults the expanded `Subscription.Status`: `incomplete_expired` (Stripe voids the still-unpaid first invoice once its 23-hour collection window closes), `canceled`, or `unpaid` (the `send_invoice` collection method's equivalent, defensive since `CreateCharge` never requests it) all resolve to `ChannelStatusFailed`; every other status (`incomplete` while Stripe's smart retries are still in play, or no `Subscription` expanded at all) stays `ChannelStatusPending`. The two rows never collapse into one -- `checkout.session.async_payment_failed`'s own `ProviderEventID` dedups to its own row, since the dedup key is the channel's own event id, not the session -- but the original row is never permanently unresolvable: once the Subscription reaches its own terminal state, both rows agree on `Failed`.

**Renewal recognition.** `normalizeInvoice` recognizes `invoice.paid`/`invoice.payment_failed` (mapping to `NormalizedEventChargeSucceeded`/`ChargeFailed` with the invoice's own `AmountPaid`/`AmountDue`), and `normalizeSubscriptionUpdated` recognizes `customer.subscription.updated` ONLY for a transition into `stripego.SubscriptionStatusCanceled` (mapping to `NormalizedEventSubscriptionCanceled`) -- every other subscription status is still refused as `ErrWebhookPayloadUnrecognized`, since the Active/PastDue-shaped transitions this same event fires for are already announced, with a real settled amount, by the two invoice events, and a subscription object itself carries no `Money` to attach a second, amount-less signal to. `normalizeInvoice` reads the identifiers from the invoice's `parent.subscription_details.metadata` snapshot (Stripe captures the subscription's metadata there at finalization; the invoice's own metadata field is empty unless separately set), and an invoice event whose identifiers sit anywhere else is refused as `ErrWebhookPayloadUnrecognized` like any other uncorrelatable event.

**Known limitation: `NormalizedEvent.InvoiceID` is stale past the first renewal cycle.** The parent snapshot carries forward the id `CreateCharge` attached to the FIRST cycle's own `billing.Invoice`, verbatim, on every LATER cycle's Stripe-generated invoice too -- this package has no way to mint a fresh `billing.Invoice` id for a cycle it was never asked to create one for (`CreateCharge` is called exactly once, at `Subscription` activation). A live webhook-processing loop -- none exists yet, see `go/billing/AGENTS.md`'s Known limitations -- is where a genuine per-cycle `billing.Invoice` would need to be created before this identifier round-trips meaningfully past cycle one.

**A Data-less event is refused, never a crash.** `stripego.Event.Data` is a POINTER (nil when a delivery's JSON carries no `data` object); `normalizeEvent` guards up front, and an event with no data object (or an empty one) is `ErrWebhookPayloadUnrecognized` like any other payload this package cannot parse into a known event. `TestGateway_VerifyWebhook_EventWithoutData_RefusedNotCrashed` pins it.

**Measured dependency cost**: **+1** -- `github.com/stripe/stripe-go/v82` itself, which carries zero further transitive dependencies of its own.

### `alipay`

No third-party SDK: Alipay publishes no official Go SDK, and no single community package dominates the way `stripe-go` does for Stripe. Signature verification (RSA2 = RSA-SHA256) and the request/response shapes are implemented directly against Alipay's own published open-platform documentation (`https://opendocs.alipay.com/common/02kdnc`) using only the standard library's `crypto/rsa`, `crypto/sha256` and `crypto/x509` -- the identical choice `go/pki`'s own root package makes for `LocalSigner`.

Two distinct signature algorithms are implemented, both real RSA2, applied to three canonical forms -- the request-signing and inbound-notification parameter sets are ASYMMETRIC, per Alipay's own documented scheme:

- **Outgoing requests** (`sign.go`'s `requestSignContent`, used by `signParams`): every non-empty request parameter EXCEPT `sign` itself (which is only added to the parameter set after signing), sorted ascending by key, joined `key1=value1&key2=value2&...` using each value's raw (URL-decoded) form. **`sign_type` participates** -- Alipay's own reference SDKs and the documented request-signing rule include it, and Alipay's gateway includes it when it verifies the request.
- **Inbound notifications** (`sign.go`'s `signContent`, used by `VerifySignature`): the same canonical form with `sign` AND `sign_type` both excluded -- the reduced set Alipay's own server signs its async notifications over.
- **API response envelopes** (`response.go`'s `verifyResponseEnvelope`): Alipay's response-verification algorithm is byte-sensitive to the response object's EXACT serialization as Alipay itself produced it (key order, whitespace, escaping), so this verifies against the raw byte substring `encoding/json.RawMessage` preserves for the response field -- never a re-serialized/re-ordered reconstruction, which would not match Alipay's own signature even for a genuine, unmodified response.

`normalizeNotify`'s `EventID` is deliberately NOT Alipay's own `notify_id` -- that field is unique per DELIVERY ATTEMPT, not per underlying trade event (a redelivery of the same event carries a DIFFERENT `notify_id`), which would defeat `payment_events`' insert-first-dedup rule entirely if used as the dedup key. The stable key across redeliveries is the synthesized `out_trade_no:trade_status` pair, since Alipay redelivers the identical status transition verbatim until acknowledged. `TestGateway_VerifyWebhook_RedeliveryProducesSameEventID` is the standing proof.

**Refund notifications are distinguished, never mistaken for the payment.** Alipay's own status definitions say a paid trade only leaves `TRADE_SUCCESS` on a FULL refund (landing as `TRADE_CLOSED`), while a PARTIAL refund keeps the trade at `TRADE_SUCCESS` and re-sends the `TRADE_SUCCESS` async notification -- either way the refund-bearing notification carries `refund_fee` (the refunded amount) and `gmt_refund` (the refund time), which a timeout closure of an unpaid trade never does:

- A partial-refund notification must never normalize into an event byte-identical to the original payment (`NormalizedEventChargeSucceeded`, `EventID` `out_trade_no:TRADE_SUCCESS`) -- the `payment_events` insert-first-dedup ledger would swallow the refund signal as a duplicate of the payment and the platform would never learn a refund happened. The trade-notify vocabulary carries no per-refund-occurrence identifier to build a dedup-safe refund `EventID` from (the refund-occurrence identity `wechat`'s REFUND.* notifications do carry -- their own `out_refund_no`, which that leg's decode keys its EventID on -- is exactly what Alipay's trade notifications lack), so a `TRADE_SUCCESS`/`TRADE_FINISHED` notification carrying the refund fields is refused loudly as `ErrWebhookPayloadUnrecognized`, never guessed at -- the same refusal posture `wechat` applies to the refund signals ITS vocabulary cannot represent (`REFUND.ABNORMAL`/`REFUND.CLOSED`).
- A full-refund `TRADE_CLOSED` maps to `NormalizedEventRefunded`/`ChannelStatusRefunded` (first use of the refunded vocabulary by a provider, `EventID` `out_trade_no:TRADE_CLOSED` -- distinct from the payment's own `TRADE_SUCCESS` id, stable across redeliveries); a `TRADE_CLOSED` without the refund fields -- an unpaid trade closed by timeout -- keeps mapping to `ChargeFailed`.
`QueryStatus`'s `tradeStatusToChannelStatus` consults the same refund marker (`refund_fee`, via the shared `carriesRefund` detection, so the notify and query payload shapes can never drift): closed-with-refund answers `ChannelStatusRefunded`, closed-without (or with `"0.00"`) stays `Failed`, and a partial refund (which keeps the trade at `TRADE_SUCCESS`) stays `Succeeded`.

**Amount and currency boundaries are enforced before anything reaches the wire.** Non-positive amounts are refused at the `CreateCharge` boundary with `billing.ErrInvalidAmount` before anything is formatted or sent; `formatAmount` renders a negative defensively as sign-correct `"-29.50"` (never `"-29.-50"`, never sign-dropped); `parseAmount` refuses a negative string outright (never silently dropping its sign). Alipay's Native (QR-code) product only ever settles in CNY: `CreateCharge` refuses any `req.Amount.Currency` other than CNY (case-insensitively) with `billing.ErrUnsupportedCurrency`, so a caller-supplied non-CNY amount can never be silently sent (and collected) as if it were the same number of CNY cents; `QueryStatus`'s own `Currency: "CNY"` in its returned `billing.Money` is honest by construction -- the query response carries no currency field, and every order `QueryStatus` can be asked about genuinely is CNY. The outgoing request's `timestamp` common parameter renders in China Standard Time (UTC+8) -- the same fixed zone `alipayLocation()` parses Alipay's `gmt_*` fields in -- so a host outside UTC+8 does not send timestamps skewed by its whole UTC offset.

`CreateCharge`'s outgoing HTTP call is abstracted behind `httpDoer` (`Do(req) (*http.Response, error)`, structurally satisfied by `*http.Client`), the same stub-the-transport approach `go/pki/signer/kmsaws`'s `kmsClient` interface uses for the AWS SDK, applied at the HTTP layer here since Alipay has no Go SDK to stub.

**Measured dependency cost**: **+0** -- pure standard library, no new module dependency at all beyond what importing `go/billing` itself already costs.

### `wechat`

WeChat Pay's own officially maintained Go SDK (`github.com/wechatpay-apiv3/wechatpay-go`) exists but is deliberately NOT adopted: its own certificate-management layer (`core/downloader`) is built to periodically download WeChat Pay's current platform certificates over the network and cache them -- machinery this package has no live account to exercise or verify -- and adopting it would mean carrying an unverified, untested certificate-rotation dependency rather than the explicit, host-supplied platform public key this package uses instead (see "Known limitation: static platform certificate" below). Signature verification, resource decryption and the request/response shapes are implemented directly against WeChat Pay's own published APIv3 documentation using only the standard library's `crypto/rsa`, `crypto/sha256`, `crypto/aes` and `crypto/cipher` -- the identical "implement directly against the documented format" choice `alipay` makes.

Two real cryptographic mechanisms, both genuinely exercised:

- **RSA-SHA256 signatures** (`sign.go`): `requestSignMessage` (method + canonical URL + timestamp + nonce + body, WeChat Pay's `WECHATPAY2-SHA256-RSA2048` Authorization scheme for outgoing requests) and `notifySignMessage` (timestamp + nonce + body, for both an inbound webhook notification's `Wechatpay-Signature` header and an API response's own signature header -- WeChat Pay signs both identically).
- **AEAD_AES_256_GCM resource decryption** (`decrypt.go`): every webhook notification's `resource` field is a real encrypted envelope, decrypted against the merchant's 32-byte APIv3 key -- a second, independent integrity check beneath the outer RSA signature, since a forged notification would have to forge BOTH the outer signature AND this AEAD authentication tag.

**Known limitation: static platform certificate.** WeChat Pay APIv3 signs both outbound API responses and inbound webhook notifications with certificates it itself issues and periodically rotates, discoverable through a `GET /v3/certificates` call this package does not implement. `Config.PlatformPublicKeyPEM` takes the platform's current public key directly, and a host is responsible for keeping it current -- an expired or rotated certificate makes `VerifySignature` fail closed with a verification error, never a silent accept.

**Refund-result notifications are decoded; the decode's boundary is what this paragraph records, not an absence.** WeChat Pay delivers `REFUND.SUCCESS`/`REFUND.ABNORMAL`/`REFUND.CLOSED` notifications for a refunded order, carrying a distinct resource shape (`refund` object, not `transaction`); `notify.go`'s `decodeRefundResource` handles them, with the boundary drawn exactly where the module's normalized-event vocabulary stays truthful:

- `REFUND.SUCCESS` -- a refund that actually happened -- decodes into `NormalizedEventRefunded`/`ChannelStatusRefunded` (the wiring `alipay`'s full-refund leg already consumed), with a dedup-safe per-refund `EventID` (`out_refund_no` + `:` + `refund_status` -- stable across WeChat's redeliveries, distinct from the payment's own `out_trade_no`-keyed id, and distinct per refund occurrence since each refund of an order carries its own `out_refund_no`, the per-refund-occurrence identity `alipay`'s own refusal notes its trade-notify vocabulary lacks), the refunded trade (`out_trade_no`) as `ChannelReference` -- the agreement point with `QueryStatus`, which reports `ChannelStatusRefunded` for the same order -- and the refunded amount (`amount.refund`) as `Amount`, partial and full collapsing to the one refunded value per those types' own doc comments.
- `REFUND.ABNORMAL` and `REFUND.CLOSED` -- a refund that did NOT complete: no money returned, the original charge stands, and the merchant must act through WeChat Pay's own refund machinery -- are refused loudly as `ErrWebhookPayloadUnrecognized` with the state named, never mapped onto a refunded event that never happened (the same never-guess posture `alipay` applies to its partial-refund `TRADE_SUCCESS` notifications).
- The envelope's `event_type` and the resource's `refund_status` must agree, and the merchant-side identifiers the decode builds its key and reference from (`out_refund_no`, `out_trade_no`) must be present; mismatches and absences are refused, never decoded.

One structural consequence is recorded on `billing.NormalizedEvent` itself (go/billing/gateway.go): WeChat Pay's refund object -- and its refund-creation API -- define no attach or merchant-metadata field of any kind, so a decoded refund event's `TenantID`/`SubscriptionID`/`InvoiceID` are empty BY NATURE of the payload, with the doc comment's blank-identifier refusal narrowed to the shapes that should carry identifiers and are missing them. A caller needing attribution resolves the refund event's `ChannelReference` against its own records. The decode's regressions live in `wechat/notify_test.go` (`TestGateway_VerifyWebhook_RefundSuccess_DecodesToRefundedEvent` and the partial-refund, abnormal/closed-refusal, event-type-mismatch, missing-identifier and redelivery-stability tests around it).



**Freshness and escaping boundaries.** `VerifyWebhook` checks the delivery's `Wechatpay-Timestamp`: a captured, replayed notification whose signature stays valid must not be accepted no matter how old. The header's Unix timestamp must sit within `notifyTimestampTolerance` (300 seconds) of now, in either direction; a stale delivery is refused with `ErrWebhookSignatureInvalid` exactly like any other authentication-class failure, and an unparseable timestamp is refused the same way. `QueryStatus` percent-escapes the `out_trade_no` reference exactly once, up front, with `url.PathEscape`, and that same escaped form feeds both the Authorization header's canonical URL and the requested URL -- WeChat Pay's APIv3 scheme requires the two to be byte-identical, and a raw reference holding URL metacharacters (a `#` fragment delimiter, say) would otherwise split them apart. Currency is CNY-only and enforced exactly as in `alipay` (`CreateCharge` refuses non-CNY with `billing.ErrUnsupportedCurrency`); unlike `alipay`, `QueryStatus` reads `Currency` straight from WeChat Pay's own response body, never hardcoded.

`CreateCharge`/`QueryStatus`'s outgoing HTTP call is abstracted behind the identical `httpDoer` interface `alipay` uses, for the identical reason (no Go SDK adopted to stub instead).

**No sandbox exists for this API surface.** WeChat Pay's only test environment is the simulation system its own merchant documentation describes (the "Payment acceptance guide -- common rules", under the product docs' V2 section), and that system is V2-only and micropay-only: it supports only the micropay product's success/abnormal test cases, its abnormal cases are triggered by a request header, and even it requires a real merchant sign-in plus a dedicated sandbox signing key. This package implements APIv3 (`POST /v3/pay/transactions/native` and friends under `WECHATPAY2-SHA256-RSA2048`), which no WeChat Pay sandbox or simulation environment covers -- no APIv3 sandbox host, no sandbox certificate material, nothing configurable short of a real registered merchant account making real small-amount payments. `wechat` therefore ships no integration leg by vendor reality, not by omission.

**Measured dependency cost**: **+0** -- pure standard library, identical to `alipay`.

## What remains untestable without live credentials

Every provider package's REAL, offline-verifiable cryptography is genuinely implemented and genuinely tested -- signature verification and (for `wechat`) resource decryption run against fixtures each package constructs and signs/encrypts itself with locally generated key material, never stubbed out or left unimplemented -- and the integration tiers below take the HTTP dialogue as far as each vendor's test infrastructure allows. What remains honestly NOT exercised, per family:

- **`stripe`**: the credential-free stripe-mock tier (see "Integration tiers" below) proves this package's real HTTP dialogue against a server enforcing Stripe's own OpenAPI-derived schema, but stripe-mock is stateless, fixture-driven and signs no webhook delivery -- what still needs a live Stripe test-mode account is a Checkout Session completed by a real payer, a webhook delivery actually signed by Stripe's own servers, and Stripe's genuine error taxonomy (404/`resource_missing` and friends) as the SDK parses it from a real HTTP error response.
- **`alipay`**: the env-gated sandbox leg (see "Integration tiers" below) proves both directions of the RSA2 dialogue against Alipay's genuine gateway whenever an operator's sandbox credentials are present; what no server-side leg can drive is the payment itself -- the sandbox's payment client is Android-only and sandbox testing supports balance payment only, so the created order stays at `WAIT_BUYER_PAY`, and `VerifyWebhook` against a genuinely Alipay-delivered async notification (which only fires after such a payment) remains untested against the sandbox. Production-environment verification has not been performed.
- **`wechat`**: no sandbox or simulation environment exists for the APIv3 surface this package implements (vendor evidence in the `wechat` section above), so anything beyond the unit tier's real-but-locally-signed cryptography requires a real registered merchant account making real small-amount payments in WeChat Pay's production environment -- `CreateCharge`/`QueryStatus` against the live APIv3 gateway, response/notification signatures from WeChat Pay's own platform certificates, and genuine AEAD-encrypted webhook deliveries.

## Active-polling fallback

`go/billing/job.go`'s `PollingService` (root package, not this subpackage) is the active-polling fallback: a callback may arrive before the order-creation response returns, or may never arrive at all, so a `jobs`-scheduled task (`taskTypePoll`, tenant-scoped, mirroring `go/storage`'s `taskTypeExpirySweep`) periodically re-queries every `ChannelStatusPending` `PaymentEvent` row older than `DefaultPollStuckAfter` through that row's owning channel's `PaymentGateway.QueryStatus` -- the same never-trust-the-callback-body re-query webhook processing uses, run proactively. It does not itself drive any `Subscription`/`Invoice` transition (see `go/billing/AGENTS.md`'s Known limitations for why that boundary exists); it updates `PaymentEvent.Status` and `Amount` alone.

- **Unit tests, per provider**: no Docker, no network, no live credentials required for any test in this subpackage.
