# billing/gateway

`go/billing/gateway` is billing's payment-channel adapter layer: three sub-subpackages, `stripe`, `alipay` and `wechat`, each a real `billing.PaymentGateway` implementation for one payment channel. This file is the subpackage-level discipline that ships with `go/billing/gateway` to consuming projects; the design rationale is `docs/internal/06-billing-and-metering.md`'s domestic-plus-international dual payment-mode section, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: the gateway round.** This round gives the package its first real content: the three provider subpackages below, each implementing `billing.PaymentGateway` (declared in `go/billing`'s own root package, `gateway.go`) and self-registering into `billing.PaymentGatewayRegistry`. It does NOT ship an HTTP surface for receiving live webhooks (a later round mounts the actual inbound endpoint), Alipay/WeChat native recurring billing (explicitly out of scope -- see "The domestic-leg trade-off" below), AI gateway integration, or reference-app wiring as a live consumer (no live credentials this round holds -- see "What remains untestable without live credentials" below). Judge what exists by the code, not by this sentence.

## The one-way dependency rule

**`go/billing/gateway` (and its three sub-subpackages) may import `go/billing`. `go/billing`'s own root package must never import `go/billing/gateway` or anything under it.** This is not a style preference; it is the mechanism that keeps `docs/internal/06-billing-and-metering.md`'s core design principle -- "`Subscription` is an internal domain concept, a payment channel is merely the collector" -- true in code rather than only in prose.

The mechanism is the identical `database/sql`-driver-registration pattern `go/pki`'s `SignerRegistry` already established for this session's own provider splits (`go/pki/signer/vault`, `go/pki/signer/kmsaws`):

- `go/billing`'s root package (`gateway.go`) declares `PaymentGateway`, an interface with three methods (`CreateCharge`, `VerifyWebhook`, `QueryStatus`) grounded in what `SubscriptionService`/`InvoiceRepository` actually need, and the provider-agnostic types every implementation exchanges with a caller (`ChargeRequest`/`ChargeHandle`, `NormalizedEvent`, `ChannelStatus`, `NormalizedEventType`, `ChannelReference`). None of these types ever carries a provider-specific field -- no `stripe.Subscription`-shaped field, no Alipay notify param map -- which is the concrete failure mode `docs/internal/06`'s own warning names.
- `go/billing.PaymentGatewayRegistry` is a package-level `pkgcore.SeamRegistry[PaymentGateway]`, empty by default (unlike `pkgcore`'s own `EventBusRegistry` and friends, no built-in implementation is pre-registered here -- every `PaymentGateway` genuinely needs a provider SDK or a hand-rolled channel client, so there is no zero-dependency default the way `LocalSigner` is for `SignerRegistry`).
- Each of this package's three sub-subpackages registers itself from its own `init()`: `stripe` under `"gateway.stripe"`, `alipay` under `"gateway.alipay"`, `wechat` under `"gateway.wechat"`. A host that never blank-imports a provider subpackage never resolves that name, and building an unregistered name fails with `pkgcore.ErrUnknownImplementation`, naming it.
- A host that already holds a constructed `PaymentGateway` value (built via `PaymentGatewayRegistry.Build`, or by calling a provider's own `NewGateway` directly) wires it wherever one is needed by value -- `billing.WithGateways(map[string]PaymentGateway{...})` for the active-polling fallback (`go/billing/job.go`'s `PollingService`), or a later round's live webhook endpoint. This mirrors the `WithSigner`-vs-`SignerRegistry` duality `go/pki`'s own `signer_registry.go` documents: the registry is for name-plus-`Config` resolution (a `Preset`, an environment-driven bootstrap), direct injection is for a caller that already did the wiring.

Enforcement is two-layered, matching every other provider split this session has shipped:

- **Compile-time / packaging**: no provider SDK's import ever appears in `go/billing`'s own `go.mod` requirement list as anything other than what a subpackage needs -- Go's module-graph pruning (`go >= 1.17`) means a consumer that imports only `go/billing`'s root package never pulls a provider SDK's dependency closure into its own build, the identical mechanism `CLAUDE.md`'s own "prefer a subpackage over a new module" rule measures for `pkgcore/config`'s `koanf`.
- **CI-enforced**: three new `depguard` rules in the repository's `.golangci.yml` (`stripe-sdk-only-in-billing-gateway-stripe`, `alipay-sdk-only-in-billing-gateway-alipay`, `wechat-sdk-only-in-billing-gateway-wechat`), each narrowed to its own implementation subpackage -- not the whole module -- mirroring `go/observability`'s exporter-split rules and `go/pki`'s own `vault`/`kmsaws` rules, since `go/billing`'s own root package (where `PaymentGateway` and `PaymentGatewayRegistry` live) must not import any of the three either, which is the whole point of the split.

## The domestic-leg trade-off (a pragmatic trade-off)

`docs/internal/06-billing-and-metering.md` states this trade-off by name, and it drives every method's own shape:

- **Stripe (international)**: `CreateCharge` creates a genuine, ongoing Stripe subscription (a Checkout Session in `"subscription"` mode, with an inline recurring price for the requested amount) -- called ONCE per `billing.Subscription`, at its first activation. Stripe's own billing engine generates every later cycle's invoice and charge on its own, announced through its own webhook events -- `checkout.session.completed`/`.expired`/`.async_payment_failed` for the first cycle, and `invoice.paid`/`invoice.payment_failed`/`customer.subscription.updated` (canceled transitions only) for every later renewal cycle, all six recognized by `stripe/event.go`'s `normalizeEvent` as of the 2026-09 bug-fix round below; a caller does not call `CreateCharge` again for later cycles of the same `Subscription`.
- **Alipay / WeChat Pay (domestic)**: neither channel offers a periodic-charge primitive at this repository's target tier (an accurate statement as of this round's own survey of both channels' published APIs), so `CreateCharge` creates ONE one-time order (Alipay's `alipay.trade.precreate`, WeChat Pay's `POST /v3/pay/transactions/native` -- both the Native/QR-code product) for ONE `billing.Invoice`. A caller re-runs `CreateCharge` once per internally-tracked billing cycle instead -- this round deliberately does NOT implement Alipay's periodic-withhold product or WeChat Pay's delegated-withhold agreement product, both distinct, higher-compliance-burden API families explicitly out of this round's scope.

Both domestic providers attach `req.TenantID`/`SubscriptionID`/`InvoiceID` to the created channel-side object using whichever metadata mechanism the channel offers -- Alipay's `passback_params` common request parameter, WeChat Pay's `attach` field on the Native order -- JSON-encoded as `{"t":...,"s":...,"i":...}`, and `VerifyWebhook` decodes it back out of the matching notification. Stripe attaches them twice over: on the Checkout Session's own `Metadata` map (what the `checkout.session.*` events carry), and -- since the P1 round -- on `subscription_data.metadata`, the subset of session parameters Stripe applies to the SUBSCRIPTION it creates when the session completes (a Checkout Session's own metadata is NOT copied onto that subscription). Every later lifecycle object -- the subscription itself, and each renewal invoice's `parent.subscription_details.metadata` snapshot -- only carries the keys because of that second copy. This round-trip is what lets `NormalizedEvent.TenantID`/`SubscriptionID`/`InvoiceID` be populated without any provider package holding a table of its own mapping a `ChannelReference` back to a tenant.

## Provider-by-provider notes

### `stripe`

Uses the official `github.com/stripe/stripe-go/v82` SDK -- the only Go client Stripe itself publishes, and the idiomatic choice. Built over the SDK's per-resource `Client` types (`checkout/session.Client{B: stripe.Backend, Key: string}`), not the newer `stripe.Client` aggregate the SDK's own docs now recommend for new integrations -- a deliberate, documented departure: `stripe.Client`'s own per-resource fields are concrete, unexported struct types with no interface seam, while `stripe.Backend` is a real, first-class interface the SDK's own doc comment says exists explicitly "to enable mocking for during testing if needed". This package's entire testing strategy for `CreateCharge`/`QueryStatus` depends on that seam; the per-resource `Client` type is marked `Deprecated` in the SDK's own doc comments but remains fully shipped and functional as of the pinned version. `gateway.go`'s own doc comment carries the full write-up.

`VerifyWebhook` uses `webhook.ConstructEventWithOptions` with `IgnoreAPIVersionMismatch: true` -- a real, deliberate choice, not a security shortcut: the plain `webhook.ConstructEvent` also refuses an event whose own `api_version` does not match the exact Stripe API version this pinned SDK release was generated against, which would make webhook verification fail closed for essentially any real merchant account whose webhook endpoint is pinned to a different (often much older) API version than this dependency's release cadence. The HMAC-SHA256 signature itself -- never the `api_version` field -- is what actually proves a delivery is genuine, and that check is never weakened.

**Measured dependency cost** (this repository's own required method: a throwaway module, `GOWORK=off go mod tidy`, count `// indirect` entries, diffed against the identical measurement with no provider subpackage imported): **+1** -- `github.com/stripe/stripe-go/v82` itself, which carries zero further transitive dependencies of its own.

**2026-09 bug-fix round (webhook/query agreement + renewal recognition).** Three real defects an audit (and a later adversarial review of the same round) caught and this round closed:

- `normalizeEvent`'s `checkout.session.completed` branch used to map unconditionally to `NormalizedEventChargeSucceeded`/`ChannelStatusSucceeded`, never consulting the session's own `payment_status` -- disagreeing with `QueryStatus`'s own `sessionStatus`, which DOES check it, for the identical session under delayed settlement (a "complete" session that is still `PaymentStatusUnpaid`). Fixed: `normalizeCheckoutSession` now mirrors `sessionStatus`'s exact agreement point, recording the new `billing.NormalizedEventChargePending`/`ChannelStatusPending` for that case -- the row then lands exactly where `PollingService`'s active-polling fallback already looks for stuck rows, instead of a false `Succeeded` no poll would ever revisit.
- The recognized-event table used to carry only the three first-cycle checkout events, so Stripe's own renewal announcements -- `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated` -- all fell to `ErrWebhookPayloadUnrecognized`, silently dropping a real renewal success, failure or cancellation. Fixed: `normalizeInvoice` recognizes the two invoice events (mapping to `NormalizedEventChargeSucceeded`/`ChargeFailed` with the invoice's own `AmountPaid`/`AmountDue`), and `normalizeSubscriptionUpdated` recognizes `customer.subscription.updated` ONLY for a transition into `stripego.SubscriptionStatusCanceled` (mapping to `NormalizedEventSubscriptionCanceled`) -- every other subscription status is still refused as `ErrWebhookPayloadUnrecognized`, since the Active/PastDue-shaped transitions this same event fires for are already announced, with a real settled amount, by the two invoice events, and a subscription object itself carries no `Money` to attach a second, amount-less signal to.

- A third defect, found by a later adversarial review of this same round, was in `sessionStatus` (`gateway.go`) itself, not `event.go`: `checkout.session.async_payment_failed`'s own webhook row lands correctly at `ChannelStatusFailed` (`normalizeCheckoutSession`'s `eventTypeCheckoutSessionExpired`/`eventTypeCheckoutSessionAsyncFailed` branch), but the ORIGINAL `checkout.session.completed`-but-unpaid row the bullet above produces could never be resolved by `QueryStatus` re-querying the same session: stripe-go v82's `CheckoutSessionStatus` is only `{open, complete, expired}` and `CheckoutSessionPaymentStatus` is only `{paid, unpaid, no_payment_required}` -- neither enum carries a "failed" value, and a session that completed via redirect before its async payment later, definitively failed never reverts to `expired`. `QueryStatus` re-queried at any later time answered `ChannelStatusPending` FOREVER for that one session, permanently stranding the `PaymentEvent` row `PollingService.Poll`'s whole job is to resolve -- exactly the disagreement this round's own fix was meant to close, just for a different session shape. Fixed: `QueryStatus` now expands `"subscription"` on its `Get` call (set directly on `CheckoutSessionParams`'s own top-level `Expand` field -- the embedded `Params.AddExpand` is deprecated in stripe-go v82 precisely because newer generated params types shadow it with their own `Expand` field, and calling `AddExpand` silently mutates a field the request never serializes), and `sessionStatus`'s Complete/Unpaid branch now consults the expanded `Subscription.Status`: `incomplete_expired` (Stripe voids the still-unpaid first invoice once its 23-hour collection window closes with no successful payment), `canceled`, or `unpaid` (the `send_invoice` collection method's equivalent, defensive since `CreateCharge` never requests it) all resolve to `ChannelStatusFailed`; every other status (`incomplete` while Stripe's smart retries are still in play, or no `Subscription` expanded at all) stays `ChannelStatusPending`, unchanged from before. This does not collapse the two rows into one -- `checkout.session.async_payment_failed`'s own `ProviderEventID` still dedups to its own row, since the module's dedup key is the channel's own event id, not the session -- but it does mean the original row is no longer *permanently* unresolvable: once the Subscription reaches its own terminal state, both rows agree on `Failed`. `TestGateway_QueryStatus_CompleteUnpaidTerminalSubscription_ReportsFailed`/`_CompleteUnpaidRetryingSubscription_StillPending`/`_RequestsSubscriptionExpand` are the regression tests, the first failing on the pre-fix `sessionStatus`.

**P1 round: the correlation metadata now reaches the renewal events, and `normalizeInvoice` reads it where real deliveries carry it.** Two defects, both only visible once the unit fixtures modeled Stripe's real delivery shapes:

- `CreateCharge` attached the identifiers only to the Checkout Session's own `Metadata`. Stripe does not copy a session's metadata onto the Subscription it creates at completion -- only `subscription_data.metadata` is applied to that Subscription -- so the subscription, and every object downstream of it, carried no `speed_*` keys: `customer.subscription.updated` deliveries were refused as unrecognized, and no renewal invoice had anything to correlate. `CreateCharge` now sends the same three keys under `subscription_data.metadata` (the session-level copy stays, for the `checkout.session.*` events).
- `normalizeInvoice` read the identifiers off the Invoice object's own `metadata` field. A real subscription-generated invoice does not carry the subscription's metadata there: Stripe captures it as an immutable snapshot at finalization under `parent.subscription_details.metadata` (stripe-go v82.5.1's own field comment; populated for invoices created on or after 2023-06-29), and the invoice's own metadata field is empty unless separately set. `normalizeInvoice` now reads the snapshot, and an `invoice.paid`/`invoice.payment_failed` delivery whose identifiers sit anywhere else is refused as `ErrWebhookPayloadUnrecognized` like any other uncorrelatable event. The gateway tests' invoice fixtures were corrected from the old hand-seeded invoice-level-metadata shape to the real parent-snapshot shape, with a negative test pinning that invoice-level-only metadata stays refused (`TestGateway_VerifyWebhook_InvoicePaid_InvoiceLevelMetadataOnly_StillUnrecognized`).

**Known limitation: `NormalizedEvent.InvoiceID` is stale past the first renewal cycle.** The parent snapshot carries forward the id `CreateCharge` attached to the FIRST cycle's own `billing.Invoice`, verbatim, on every LATER cycle's Stripe-generated invoice too -- this package has no way to mint a fresh `billing.Invoice` id for a cycle it was never asked to create one for (`CreateCharge` is called exactly once, at `Subscription` activation). A later round's live webhook processing loop -- none exists yet, see `go/billing/AGENTS.md`'s own Known limitations -- is where a genuine per-cycle `billing.Invoice` would need to be created before this identifier round-trips meaningfully past cycle one.

**2026-09 P2/P3 hardening round: a Data-less event used to crash the process.** `stripego.Event.Data` is a POINTER (nil when a delivery's JSON carries no `data` object), and `normalizeEvent`'s dispatch functions dereferenced `event.Data.Raw` unconditionally -- a signed, recognized event type whose payload lacked `data` panicked with a nil-pointer dereference inside webhook processing instead of refusing the delivery (P3-11). `normalizeEvent` now guards up front: an event with no data object (or an empty one) is `ErrWebhookPayloadUnrecognized` like any other payload this package cannot parse into a known event -- never a crash, never a synthesized event. `TestGateway_VerifyWebhook_EventWithoutData_RefusedNotCrashed` signs a genuine `checkout.session.completed` delivery with no `data` field (pre-fix: nil-pointer panic; post-fix: clean refusal).

**2026-09 sandbox round: a real stripe-mock integration leg.** `integration_test/` (under this subpackage, `-tags=integration`, Docker-backed, picked up by go/billing's existing full-check integration-tiers row since that job runs `go test -tags=integration ./...` from the module root) boots `stripe/stripe-mock:v0.203.0` -- the official Stripe mock server (github.com/stripe/stripe-mock, Stripe-published Docker image, tag pinned to the upstream release) -- and drives the package's REAL HTTP dialogue against it. The gap the leg closes: every unit test reaches the gateway through `newGatewayWithBackend`'s scripted `stripe.Backend` double, whose `Call` implementation DISCARDS the wire-encoded request body it is handed (it records method/path/idempotency-key/expand/metadata and answers with canned JSON), and no unit test ever constructs the real HTTP stack `NewGateway` uses -- so nothing checked what stripe-go's own serializer puts on the wire against anything implementing Stripe's documented API contract, and a body a live Stripe account would refuse sailed through the double. The leg runs `NewGateway` over stripe-go's genuine HTTP backend (base URL pointed at the mock via `stripe.BackendConfig.URL`) and proves, against a server whose parameter validation is real (a control test demonstrates the mock answers 400 with Stripe's own error envelope to a request carrying an unrecognized parameter, so the acceptance is not a rubber stamp): `CreateCharge`'s POST `/v1/checkout/sessions` is accepted and decodes into a `ChargeHandle` (`TestGateway_CreateChargeAndQueryStatus_RealStripeMockDialogue`), and `QueryStatus`'s GET `/v1/checkout/sessions/{id}?expand[]=subscription` maps the mock fixture's open session to `ChannelStatusPending`. The mock needs no credential of any kind -- the value is arbitrary, though its SHAPE is validated (`sk_test_` plus alphanumerics; discovered live when the leg's first key draft was refused with 401) -- and it does not sign webhook deliveries (verified in its source), so the tier's second file (`webhook_delivery_test.go`) drives the delivery shape the implementation actually consumes -- a genuinely signed payload POSTed over real HTTP into a handler that hands `VerifyWebhook` net/http's own canonicalized header map -- including the tampered-body refusal, while the signature itself stays SDK-generated (`webhook.GenerateTestSignedPayload`). Still on the live-account boundary (see "What remains untestable without live credentials" below): a session completed by a real payer, a delivery actually signed by Stripe's servers, and Stripe's live error taxonomy.

### `alipay`

No third-party SDK: Alipay publishes no official Go SDK, and no single community package dominates the way `stripe-go` does for Stripe (several partial, inconsistently maintained options exist, none carrying Ant Group's own name or a release cadence this codebase could depend on with confidence). Signature verification (RSA2 = RSA-SHA256) and the request/response shapes are implemented directly against Alipay's own published open-platform documentation (`https://opendocs.alipay.com/common/02kdnc`) using only the standard library's `crypto/rsa`, `crypto/sha256` and `crypto/x509` -- the identical choice `go/pki`'s own root package makes for `LocalSigner`.

Two distinct signature algorithms are implemented, both real RSA2, applied to three canonical forms -- the request-signing and inbound-notification parameter sets are ASYMMETRIC, per Alipay's own documented scheme, and the split is deliberate:

- **Outgoing requests** (`sign.go`'s `requestSignContent`, used by `signParams`): every non-empty request parameter EXCEPT `sign` itself (which is only added to the parameter set after signing), sorted ascending by key, joined `key1=value1&key2=value2&...` using each value's raw (URL-decoded) form. **`sign_type` participates** -- Alipay's own reference SDKs and the documented request-signing rule include it, and Alipay's gateway includes it when it verifies the request.
- **Inbound notifications** (`sign.go`'s `signContent`, used by `VerifySignature`): the same canonical form with `sign` AND `sign_type` both excluded -- the reduced set Alipay's own server signs its async notifications over.
- **API response envelopes** (`response.go`'s `verifyResponseEnvelope`): Alipay's response-verification algorithm is byte-sensitive to the response object's EXACT serialization as Alipay itself produced it (key order, whitespace, escaping), so this verifies against the raw byte substring `encoding/json.RawMessage` preserves for the response field -- never a re-serialized/re-ordered reconstruction, which would not match Alipay's own signature even for a genuine, unmodified response, since Go's own JSON re-serialization is not guaranteed byte-identical to Alipay's.

`normalizeNotify`'s `EventID` is deliberately NOT Alipay's own `notify_id` -- that field is unique per DELIVERY ATTEMPT, not per underlying trade event (a redelivery of the same event carries a DIFFERENT `notify_id`), which would defeat `payment_events`' insert-first-dedup rule entirely if used as the dedup key. The stable key across redeliveries is the synthesized `out_trade_no:trade_status` pair, since Alipay redelivers the identical status transition verbatim until acknowledged. `TestGateway_VerifyWebhook_RedeliveryProducesSameEventID` is the standing proof.

**P1 round: refund notifications are distinguished, never mistaken for the payment.** Alipay's own status definitions say a paid trade only leaves `TRADE_SUCCESS` on a FULL refund (landing as `TRADE_CLOSED`), while a PARTIAL refund keeps the trade at `TRADE_SUCCESS` and re-sends the `TRADE_SUCCESS` async notification -- either way the refund-bearing notification carries `refund_fee` (the refunded amount) and `gmt_refund` (the refund time), which a timeout closure of an unpaid trade never does. Two defects followed from mapping every `TRADE_SUCCESS` to a succeeded charge and every `TRADE_CLOSED` to a failed one:

- A partial-refund notification normalized into an event BYTE-IDENTICAL to the original payment (`NormalizedEventChargeSucceeded`, `EventID` `out_trade_no:TRADE_SUCCESS`), so the `payment_events` insert-first-dedup ledger swallowed the refund signal as a duplicate of the payment -- the platform would never learn a refund happened. The trade-notify vocabulary carries no per-refund-occurrence identifier to build a dedup-safe refund `EventID` from, so this round's answer mirrors `wechat`'s own `REFUND.*` posture exactly: a `TRADE_SUCCESS`/`TRADE_FINISHED` notification carrying the refund fields is refused loudly as `ErrWebhookPayloadUnrecognized`, never guessed at (`TestGateway_VerifyWebhook_PartialRefundNotify_IsRefusedNotMistakenForThePayment`).
- A full-refund `TRADE_CLOSED` mapped to `NormalizedEventChargeFailed` -- a fully refunded charge recorded as a failed payment. `normalizeNotify` now tells the two `TRADE_CLOSED` fates apart by the refund fields: with them, the event is `NormalizedEventRefunded`/`ChannelStatusRefunded` (first use of the refunded vocabulary by a provider, `EventID` `out_trade_no:TRADE_CLOSED` -- distinct from the payment's own `TRADE_SUCCESS` id, stable across redeliveries); without them, an unpaid trade closed by timeout keeps mapping to `ChargeFailed` (`TestGateway_VerifyWebhook_FullRefundTradeClosed_MapsToRefunded` and `..._TradeClosedUnpaidTimeout_StillChargeFailed`).

`CreateCharge`'s outgoing HTTP call is abstracted behind `httpDoer` (`Do(req) (*http.Response, error)`, structurally satisfied by `*http.Client`), the same stub-the-transport approach `go/pki/signer/kmsaws`'s `kmsClient` interface uses for the AWS SDK, applied at the HTTP layer here since Alipay has no Go SDK to stub.

**2026-09 P2/P3 hardening round: request signing's `sign_type` asymmetry, the poll path's refund detection, the outbound timestamp's time zone, and amount-boundary validation.** Four defects an adversarial review found, all closed with offline tests:

- `signParams` used to sign outgoing requests with the NOTIFY-side canonical form (`sign_type` excluded), because one function served both directions. Alipay's documented scheme is asymmetric (see the canonical-forms list above, sourced from `opendocs.alipay.com/common/02kdnc`'s own implement-signing-yourself section and Alipay's own reference SDKs): a request's canonical string includes `sign_type`, while notification verification excludes it. Every outgoing request was therefore signed over a string missing a parameter Alipay's gateway includes when it verifies -- a signature mismatch on the first real call, invisible to the unit tests because they signed and verified with the same (wrong) function. Fixed: `requestSignContent` (sign_type included) now serves `signParams`, `signContent` (sign_type excluded) serves notify verification alone. `TestGateway_CreateCharge_OutgoingSignatureCoversSignType` re-verifies the outgoing signature with an independently-built request-side canonical form (it failed pre-fix with a verification error), and `TestGateway_CreateCharge_SignsAndParsesPrecreate` now uses that independent verifier too.
- `tradeStatusToChannelStatus` mapped every `TRADE_CLOSED` query answer to `ChannelStatusFailed`, so the active-polling fallback recorded a fully refunded, closed trade as a failed payment. `alipay.trade.query`'s response carries the same refund marker the P1-4 notify detection reads -- `refund_fee` (its `trade_status` definition itself says `TRADE_CLOSED` covers a timeout-closed unpaid trade or a fully refunded paid trade) -- and `tradeStatusToChannelStatus` now consults it (via `carriesRefund`, the shared detection `notifyCarriesRefund`'s `refund_fee` leg now delegates to, so the two payload shapes can never drift): closed-with-refund answers `ChannelStatusRefunded`, closed-without (or with `"0.00"`) stays `Failed`, and a partial refund (which keeps the trade at `TRADE_SUCCESS`) stays `Succeeded`. `TestGateway_QueryStatus_TradeClosedWithFullRefund_ReportsRefunded`/`..._TradeClosedWithoutRefundFee_StillFailed`/`..._TradeSuccessWithPartialRefundFee_StillSucceeded` pin all three.
- The outgoing request's `timestamp` common parameter was rendered in the HOST's local time zone; Alipay's gateway reads it as China Standard Time (UTC+8), the same fixed zone `alipayLocation()` already parses Alipay's `gmt_*` fields in, so a host outside UTC+8 sent timestamps skewed by its whole UTC offset. `call()` now renders through `time.Now().In(alipayLocation())`. `TestGateway_CreateCharge_TimestampRenderedInAlipayTimeZone` forces `time.Local` to UTC and asserts the sent timestamp parses, in the alipay zone, within two seconds of now (pre-fix it sat exactly eight hours away).
- `CreateCharge` validated nothing about the amount: zero or negative cents reached Alipay's wire as `"0.00"` or the garbage `"-29.-50"`. Non-positive amounts are now refused at the boundary with `billing.ErrInvalidAmount` before anything is formatted or sent; `formatAmount` renders a negative defensively as sign-correct `"-29.50"` (never `"-29.-50"`, never sign-dropped); and `parseAmount` refuses a negative string outright instead of the pre-fix behavior of returning 50 for `"-0.50"` (sign silently dropped) or -2850 for `"-29.50"`. `TestGateway_CreateCharge_RefusesNonPositiveAmount`/`TestFormatAmount_Negative_NotGarbled`/`TestParseAmount_RefusesNegativeOrSignDropping` pin all three.

**Measured dependency cost**: **+0** -- pure standard library, no new module dependency at all beyond what importing `go/billing` itself already costs.

**Currency: CNY only, enforced.** Alipay's Native (QR-code) product only ever settles in CNY -- `CreateCharge` refuses any `req.Amount.Currency` other than CNY (case-insensitively) with `billing.ErrUnsupportedCurrency`, via a 2026-09 bug-fix round: `formatAmount` used to convert cents to Alipay's decimal-yuan string with no check at all, silently sending (and collecting from the payer) a caller-supplied non-CNY amount as if it were the same number of CNY cents. `QueryStatus`'s own `Currency: "CNY"` in its returned `billing.Money` is unchanged code but is now honest by construction rather than a hardcoded assumption: Alipay's `alipay.trade.query` response carries no currency field of its own, and every order `QueryStatus` can be asked about genuinely is CNY, since `CreateCharge`'s own check refuses every other currency before an order can ever be created. `TestGateway_CreateCharge_RefusesNonCNYCurrency`/`_AcceptsLowercaseCNY` pin both halves.

**2026-09 sandbox round: an env-gated leg against Alipay's real sandbox.** `integration_test/` (under this subpackage, `-tags=integration`) carries one leg, `TestGateway_Sandbox_PrecreateAndQuery`, that drives `CreateCharge`/`QueryStatus` over the package's real HTTP client against Alipay's genuine sandbox environment -- Alipay does operate a real sandbox (open.alipaydev.com; the opendocs support page opendocs.alipay.com/support/01rbcw confirms the FACE_TO_FACE_PAYMENT product this package uses is sandbox-testable, needs no signing of its own, and names the fixed sandbox gateway https://openapi-sandbox.dl.alipaydev.com/gateway.do, the endpoint `Config.GatewayURL` exists to point at). Unlike stripe-mock the sandbox is a real Ant-hosted gateway that authenticates every request against a real sandbox application, so the leg is gated on that application's own credentials, injected through environment variables (`ALIPAY_SANDBOX_APP_ID`, `ALIPAY_SANDBOX_APP_PRIVATE_KEY`, `ALIPAY_SANDBOX_ALIPAY_PUBLIC_KEY`; `ALIPAY_SANDBOX_NOTIFY_URL` optional); without them the leg SKIPS ITSELF with an explicit recorded note naming the missing variables and the console they come from, mirroring the reference-app e2e suite's `E2E_PLATFORM_STAFF_PASSWORD` self-skip shape. When it runs, both directions of the RSA2 dialogue are proven against Alipay's own gateway -- properties the unit tier's locally-generated key pair could never prove: this package's request signature is ACCEPTED by the sandbox (a bad signature is answered with a signed business-error envelope and the leg fails with the sandbox's own code text), and a genuinely Alipay-signed response envelope verifies against the real sandbox public key, with the created order read back at `ChannelStatusPending` (WAIT_BUYER_PAY). What no server-side leg can drive: paying the order requires Alipay's Android-only sandbox client (sandbox testing supports balance payment only, per the same opendocs page), so the asynchronously-notified post-payment half -- `VerifyWebhook` against a genuinely Alipay-delivered notification -- remains on the untestable boundary the "What remains untestable without live credentials" section below records.

### `wechat`

WeChat Pay's own officially maintained Go SDK (`github.com/wechatpay-apiv3/wechatpay-go`) exists but is deliberately NOT adopted: its own certificate-management layer (`core/downloader`) is built to periodically download WeChat Pay's current platform certificates over the network and cache them, machinery this round has no live account to exercise or verify, and adopting it would mean carrying an unverified, untested certificate-rotation dependency rather than the explicit, host-supplied platform public key this package uses instead (see "Known limitation: static platform certificate" below). Signature verification, resource decryption and the request/response shapes are implemented directly against WeChat Pay's own published APIv3 documentation using only the standard library's `crypto/rsa`, `crypto/sha256`, `crypto/aes` and `crypto/cipher` -- the identical "implement directly against the documented format" choice `alipay` makes.

Two real cryptographic mechanisms, both genuinely exercised:

- **RSA-SHA256 signatures** (`sign.go`): `requestSignMessage` (method + canonical URL + timestamp + nonce + body, WeChat Pay's `WECHATPAY2-SHA256-RSA2048` Authorization scheme for outgoing requests) and `notifySignMessage` (timestamp + nonce + body, for both an inbound webhook notification's `Wechatpay-Signature` header and an API response's own signature header -- WeChat Pay signs both identically).
- **AEAD_AES_256_GCM resource decryption** (`decrypt.go`): every webhook notification's `resource` field is a real encrypted envelope, decrypted against the merchant's 32-byte APIv3 key -- a second, independent integrity check beneath the outer RSA signature, since a forged notification would have to forge BOTH the outer signature AND this AEAD authentication tag.

**Known limitation: static platform certificate.** WeChat Pay APIv3 signs both outbound API responses and inbound webhook notifications with certificates it itself issues and periodically rotates, discoverable through a `GET /v3/certificates` call this package does not implement. `Config.PlatformPublicKeyPEM` takes the platform's current public key directly, and a host is responsible for keeping it current -- an operational gap recorded here explicitly rather than silently accepted: an expired or rotated certificate makes `VerifySignature` fail closed with a verification error, never a silent accept.

**Known limitation: refund notifications are not decoded.** WeChat Pay also delivers `REFUND.SUCCESS`/`REFUND.ABNORMAL`/`REFUND.CLOSED` webhook notifications for a refunded order, carrying a distinct resource shape (`refund` object, not `transaction`) this round's `notify.go` does not decode -- `eventTypeTransactionSuccess` is the only `event_type` this package recognizes; every other value, refund notifications included, is refused as `ErrWebhookPayloadUnrecognized`, never guessed at. A later round adding refund handling needs its own decode path and its own `NormalizedEventRefunded` wiring -- the type is no longer unused in the vocabulary: `go/billing/gateway/alipay`'s full-refund leg has consumed it since the P1 round (see the `alipay` section above), so WeChat's later round has an in-repo precedent for the wiring.

`CreateCharge`/`QueryStatus`'s outgoing HTTP call is abstracted behind the identical `httpDoer` interface `alipay` uses, for the identical reason (no Go SDK adopted to stub instead).

**2026-09 P2/P3 hardening round: the query URL's reference escaping and notification freshness.** Two defects an adversarial review found, both closed with offline tests:

- `QueryStatus` interpolated the `out_trade_no` reference RAW into both the Authorization header's canonical URL and the request URL. WeChat Pay's APIv3 scheme requires the signed canonical URL and the requested URL to be byte-identical; a reference derived from a caller's idempotency key that held URL metacharacters split the two apart -- a raw `#` is a fragment delimiter, which Go's HTTP client stripped (along with the `mchid` query that followed it) from the request actually sent while the signature still covered the un-stripped string, guaranteeing a signature mismatch at WeChat Pay for any such key. `QueryStatus` now percent-escapes the reference exactly once, up front, with `url.PathEscape`, and that same escaped form feeds both the signature and the request. `TestGateway_OutTradeNoWithSpecialCharacters_RoundTrips` drives an idempotency key holding `|` and `#` through the full create-then-query round trip, asserting the request's wire identity (`RequestURI`) is the escaped canonical URL and re-verifying the signature over it.
- `VerifyWebhook` checked nothing about the delivery's `Wechatpay-Timestamp`: a captured, replayed notification whose signature stayed valid forever was accepted no matter how old. The header's Unix timestamp must now sit within `notifyTimestampTolerance` (300 seconds, the same window stripe-go's webhook handling applies to Stripe deliveries in this module's stripe leg) of now, in either direction; a stale delivery is refused with `ErrWebhookSignatureInvalid` exactly like any other authentication-class failure, and an unparseable timestamp is refused the same way. `TestGateway_VerifyWebhook_StaleTimestamp_Refused` (a genuinely signed delivery ten minutes old) and `..._CurrentTimestamp_StillAccepted` pin both sides.

**Measured dependency cost**: **+0** -- pure standard library, identical to `alipay`.

**Currency: CNY only, enforced.** WeChat Pay's Native (QR-code) product only ever settles in CNY -- `CreateCharge` refuses any `req.Amount.Currency` other than CNY (case-insensitively) with `billing.ErrUnsupportedCurrency`, via the same 2026-09 bug-fix round as `alipay`'s identical fix: the outgoing order body used to hardcode `"currency":"CNY"` into every request with no check on what `req.Amount.Currency` actually named, silently sending (and collecting from the payer) a caller-supplied non-CNY amount as if it were the same number of CNY cents. Unlike `alipay`, `QueryStatus` here was already honest before this round -- it reads `Currency` straight from WeChat Pay's own response body (`resp.Amount.Currency`), never hardcoded, so no query-side change was needed. `TestGateway_CreateCharge_RefusesNonCNYCurrency`/`_AcceptsLowercaseCNY` pin the refusal.

**2026-09 sandbox round: no sandbox exists for this API surface -- boundary recorded, no leg added.** The round surveyed WeChat Pay's test environments before deciding whether an env-gated leg was possible, and the verdict is that there is nothing to gate against: WeChat Pay's only test environment is the simulation system its own merchant documentation describes (the "Payment acceptance guide -- common rules", pay.wechatpay.cn/doc/v2/merchant/4011984810, under the product docs' V2 section), and that system is V2-only and micropay-only -- a request reaches it by inserting an `xdc/apiv2sandbox` path segment into the V2 host, it supports only the micropay product's success/abnormal test cases (the order-creation APIs, unifiedorder and the like, are explicitly not supported there), its abnormal cases are triggered by a request header (`Wechatpay-Negative-Test` -- the "request-header flagging" the Config comment on `GatewayURL` refers to), and even it requires a real merchant sign-in plus a dedicated sandbox signing key fetched through `xdc/apiv2getsignkey`. This package implements APIv3 (`POST /v3/pay/transactions/native` and friends under `WECHATPAY2-SHA256-RSA2048`), which no WeChat Pay sandbox or simulation environment covers: no APIv3 sandbox host, no sandbox certificate material, nothing configurable short of a real registered merchant account making real small-amount payments. `wechat` therefore ships no integration leg by vendor reality, not by omission -- the same boundary the package's own doc.go records, and the honest reason "Real verification against WeChat Pay's sandbox" cannot appear on the to-do list of the section below.

## What remains untestable without live credentials

Every provider package's REAL, offline-verifiable cryptography is genuinely implemented and genuinely tested -- signature verification and (for `wechat`) resource decryption run against fixtures each package constructs and signs/encrypts itself with locally generated key material, never stubbed out or left unimplemented -- and the sandbox round has since taken the HTTP dialogue as far as each vendor's test infrastructure allows. What remains honestly NOT exercised, mirroring the precedent `go/pki/AGENTS.md`'s own AWS KMS entry sets for an identical situation, per family:

- **`stripe`**: the credential-free stripe-mock tier (see the `stripe` section above) proves this package's real HTTP dialogue against a server enforcing Stripe's own OpenAPI-derived schema, but stripe-mock is stateless, fixture-driven and signs no webhook delivery -- what still needs a live Stripe test-mode account is a Checkout Session completed by a real payer (any session the mock returns is permanently "open", so `QueryStatus`'s Succeeded/Failed/Expired mappings and the `expand[]=subscription` terminal-subscription branch are exercised on real wire responses only to the extent the unit fixtures already prove them), a webhook delivery actually signed by Stripe's own servers, and Stripe's genuine error taxonomy (404/`resource_missing` and friends) as the SDK parses it from a real HTTP error response.
- **`alipay`**: the env-gated sandbox leg (see the `alipay` section above) proves both directions of the RSA2 dialogue against Alipay's genuine gateway whenever an operator's sandbox credentials are present; what no server-side leg can drive is the payment itself -- the sandbox's payment client is Android-only and sandbox testing supports balance payment only, so the created order stays at `WAIT_BUYER_PAY`, and `VerifyWebhook` against a genuinely Alipay-delivered async notification (which only fires after such a payment) remains untested against the sandbox. Production-environment verification has not been performed.
- **`wechat`**: no sandbox or simulation environment exists for the APIv3 surface this package implements (vendor evidence in the `wechat` section above), so anything beyond the unit tier's real-but-locally-signed cryptography requires a real registered merchant account making real small-amount payments in WeChat Pay's production environment -- `CreateCharge`/`QueryStatus` against the live APIv3 gateway, response/notification signatures from WeChat Pay's own platform certificates, and genuine AEAD-encrypted webhook deliveries. This is stated plainly rather than left implicit, per `go/pki/AGENTS.md`'s own precedent for an identical gap (its AWS KMS entry).

## Active-polling fallback

`go/billing/job.go`'s `PollingService` (root package, not this subpackage) is the mandatory active-polling fallback `docs/internal/06-billing-and-metering.md` requires: a callback may arrive before the order-creation response returns, or may never arrive at all, so a `jobs`-scheduled task (`taskTypePoll`, tenant-scoped, mirroring `go/storage`'s `taskTypeExpirySweep`) periodically re-queries every `ChannelStatusPending` `PaymentEvent` row older than `DefaultPollStuckAfter` through that row's owning channel's `PaymentGateway.QueryStatus` -- the SAME never-trust-the-callback-body re-query `docs/internal/06`'s own "callbacks cannot be trusted" rule requires of live webhook processing, run here proactively. It does not itself drive any `Subscription`/`Invoice` transition (see `go/billing/AGENTS.md`'s Known limitations for why that boundary exists this round); it updates `PaymentEvent.Status` alone.
