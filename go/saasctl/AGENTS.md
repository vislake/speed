# saasctl

saasctl is speed's consumer CLI — the Go half of the product's consumer story (`docs/internal/02-repo-and-release.md` is the design authority). speed ships as independently released modules, not an application; saasctl is the tool that shapes the application a consumer actually runs. It manages the boundary where a project meets the speed modules it pulls in: materializing the project skeleton (`new`), rewriting a project's speed module requires to one lockstep version when a new release lands (`upgrade`), applying the speed modules' SQL migrations to a generated project's database (`db migrate`), and showing how a generated project's bootstrap configuration resolves (`config print`) — all four wired in this build. A consumer's code is theirs; the boundary is this CLI's.

The command surface is deliberately small and deliberately stdlib: dispatch is `flag` subcommand handling in `main.go`, no cobra or any third-party CLI dependency. Everything saasctl says is developer tooling, so help text, errors and generated-code comments are English everywhere.

| Concern | Where |
|---|---|
| Command dispatch and the root usage text | `main.go` |
| The `new` command: usage/exit-code contract, `--with` parsing and closure validation, speed-root discovery, materialization | `internal/new/new.go` |
| The `upgrade` command: usage/exit-code contract, the in-place go.mod rewrite, the offline structural self-check | `internal/upgrade/` |
| The `db` command group: the `migrate` subcommand's usage/exit-code contract, the migration universe, the SQLite apply | `internal/db/` |
| The `config` command group: the `print` subcommand's usage/exit-code contract, the provenance rendering | `internal/config/` |
| The generated project's bootstrap configuration twin (shared by `db migrate` and `config print`): env surface, defaults, development keys, error texts | `internal/appconfig/` |
| The shared go.mod context of the `db` and `config` groups (module path, app name, speed requires) | `internal/project/` |
| The embedded project skeleton tree and its invariants | `internal/template/` |
| The release-version regex + validator (twin of lockstep-release.py's `VERSION_PATTERN`) | `internal/version/` |
| Package doc comment | `doc.go` |

## Status: what this build wires

This build wires all four commands: `new`, `upgrade`, `db migrate` and `config print` — the latter two landed with the saasctl milestone's B3 round. The remaining maintenance surface (dynamic-config value print and editing, the web-side scaffolds) is listed under Known limitations and deferred work. In this build saasctl needs a speed checkout on disk at run time (see Speed-root resolution) — nothing is published, so every materialization points at a checkout. `web/package.json` rewriting and the frontend-scaffold tool (`create-saas-app`) belong to a separate round.

## The embedded template (`internal/template/`)

The project `saasctl new` materializes is not synthesized in code: it is an embedded tree of real files (`project/` under `internal/template/`) that are a working app by construction — they were produced during development by materializing, `go mod tidy`-ing and building them against a real speed checkout, then converting the paths back to tokens for embedding. The tree mirrors the reference app's `cmd/server` shape with every demo-specific piece removed: no notes module, no demo tenants, grants, membership store or subject resolver, no seeded data. A generated project is an honest skeleton whose host seams — authn's `MembershipReader`, org's `SubjectResolver`, the config resolver — are left unwired and fail closed per each module's contract, each named by a doc comment in the generated files as the owner's first task.

Three conventions hold the template together, each test-pinned on the template side and enforced again from `internal/new`'s side (the two packages cannot import each other's tests, so both sides assert their half of the shared ground truth):

- **Compile containment (A2).** Every embedded `.go` file starts with the line `//go:build ignore`, so the template tree never compiles, vets or lints as part of this module; `new` strips exactly that one line (plus its blank line) at materialization. The generated project's compile-correctness is proven by real builds of materialized apps, never by compiling the assets in place. A template edit that forgets the marker fails in two places: the embed-tree walk in `embed_test.go` and `StripBuildIgnore`'s error path when `new` materializes.
- **Selection (A5).** Only two files differ between selections: `selection/<key>/go.mod.txt` and `selection/<key>/server.go` (the go.mod require set with replace directives, and the import, module-construction and middleware set). The go.mod document carries the inert `.txt` name through the embed for a mechanical reason — go:embed's directory scan refuses to descend into a subdirectory containing a file named `go.mod`, reading such a directory as a nested module root, so a `go.mod` named as such would silently vanish from the embedded tree — and `new` renames it to `go.mod` at materialization. `<key>` is `SelectionKey`'s canonical rendering — sorted module names joined with `+`, or `none` for the empty set. The v0.1 switchable universe is `{authn, rbac, org}`: the three implemented modules that participate in the minimal combination. The required five (pkgcore, dbkit, tenancy, config, observability) have no off option. Every legal selection ships an embedded directory; an extra directory is dead weight the template tests refuse.
- **Tokens (A4).** Two tokens appear in template files and nowhere else: `__APP_NAME__` (the module path, derived at `new` time from the target directory's base name) and `__SPEED_ROOT__` (the resolved speed checkout path). Materialization substitutes them; tests assert no token survives in a materialized tree, so a template edit introducing a third token fails until the substitution learns it.

The five legal selections are the minimal combination `{authn, rbac, org}` plus its four closures. Each selection's `server.go` composes its modules in a fixed order that is also the migration-registration order (`[]pkgcore.Module{...}`); `config.go` (shared) parses the full uniform env surface of a generated project — `SPEED_CONFIG_KEY`, `SPEED_ORG_INDEX_KEY`, `SPEED_DB_PATH`, `SPEED_DEPLOYMENT_MODE`, `PORT` — so a consumer's bootstrap contract never changes with the selection.

`go/pki` is not a sixth switchable module: it follows `authn` silently (`docs/internal/22-pki.md`'s section on where pki sits in saasctl's module selection set), so the four `authn`-containing selections' `server.go` each wire a `pki.NewModule(db)` as the `KeySource` `authn.WithKeySource` requires, and their `go.mod.txt` carries `go/pki` (plus its own first `go/jobs` dependency) among the require/replace set. The `none` selection needs neither, having no signing keys to manage at all. `pki`'s own tables persist across restarts in the generated project's SQLite file — no development-seed key derivation is needed the way the pre-pki `authn.KeySet` default once required, since the key is created once by `pki.Service.EnsurePurpose` (lazily, on `Signer`'s first `Issue` call) and then simply already exists on every later boot.

## The `new` contract

`saasctl new [flags] <target-directory>` materializes the skeleton into a new directory and prints the written files plus next steps. The exit-code contract, pinned by tests:

- **0** — success, and `-h`/`--help` (help is printed, nothing is written).
- **2** — usage errors: bad flags, a wrong argument count, a target whose base name cannot serve as a module path (the name becomes the go.mod module path; the grammar is stricter than `go mod init`'s own — no leading dot or dash, no space, no trailing dot, no `.` or `..` — and every accepted name is one `go mod init` accepts, probed against go 1.25), or an invalid `--with` value.
- **1** — execution errors: an unresolvable speed root, an existing non-empty target, an I/O failure.

`--with` is positive selection with downward-closure validation: selecting `rbac` or `org` without `authn` is an error naming `authn` as implied (their routes need an authenticating layer), and unknown names are rejected listing the valid set. There is no `--without`: closing `authn` is expressed by not listing it, and dependents cannot be selected without it — the v0.1 correction note to `docs/internal/11-cross-cutting.md`'s module-switch section.

An existing non-empty target is refused before anything is written (only an existing *empty* directory is accepted and filled); on a write failure everything the run created is removed again. The written file list is fixed and relative, never derived from a walk of the target, so a hostile or stale target tree cannot smuggle paths into the write.

## The `upgrade` contract

`saasctl upgrade --version <v> [go.mod]` rewrites a consumer go.mod's speed requires to one target version — the lockstep-release story (`docs/internal/02-repo-and-release.md`): the version number is the whole compatibility surface, so all of a project's `github.com/vislake/speed/go/*` requires move together. The default path is `go.mod` in the working directory; `[go.mod]` names a different file. The rewrite touches only the version token of each speed require line — nothing else in the file changes, byte for byte: third-party requires (and their `// indirect` markers), replace blocks, comments, blank lines and formatting survive because the rewrite edits the parsed syntax tree in place and prints it back through `golang.org/x/mod/modfile`, the Go team's own parser, deliberately never hand-serialized. The set of modules rewritten is derived from the file's own require lines, never hardcoded.

`--version` is required at this stage: nothing publishes before M4, so the target release version is never discovered — the operator supplies it. It is validated by `internal/version` against the same grammar as the release tooling (`^v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z-]+(\.[0-9A-Za-z-]+)*)?$`), and every speed require must end at the validated version or the run fails. The exit-code contract matches `new`: 0 for success and help, 2 for usage errors (missing or invalid `--version`, too many positional arguments), 1 for execution errors (a missing or malformed go.mod, a go.mod with no speed requires — nothing to rewrite is an error, so a consumer pointed at the wrong file learns it immediately rather than silently succeeding). A second run over an already-rewritten file reports nothing changed and exits 0 (idempotence is pinned by tests). After the rewrite the result is re-parsed from bytes and structurally self-checked offline — every speed require at the target version, the file well-formed, replace directives exactly as they were — before anything is written back, with the file's original mode preserved.

## The `db migrate` contract

`saasctl db migrate [go.mod]` applies the SQL migrations of the speed modules a consumer project requires to the project's SQLite database — the operator-driven twin of the Apply the generated app's own startup performs, over the same bootstrap environment the app boots from (`SPEED_DEPLOYMENT_MODE`, `SPEED_DB_PATH`, ...). The default database path (`SPEED_DB_PATH` unset, `<app name>.db`) is resolved next to the `[go.mod]` argument rather than the caller's working directory — the directory the generated app is documented to run from, where its default database lands — so a go.mod argument naming another directory's project migrates that project's own database whichever directory the command is invoked from; an explicit `SPEED_DB_PATH` is used exactly as the app would use it. The migration universe is the intersection of the go.mod's own `github.com/vislake/speed/go/*` requires with the root modules that ship their own migrations — authn, config, org, pki and rbac, in alphabetical order — each constructed through its own `NewModule` (authn with a throwaway dev-shaped blind-index key that never issues or stores anything, and a `KeySource` that is pki's own `*Module.Service()` rather than a fabricated fake -- `buildAuthnAndPKI` builds authn and pki TOGETHER, sharing exactly one `*pki.Module` instance between authn's `WithKeySource` and pki's own migration registration, since two separately constructed `*pki.Module` values would both report `Name() == "pki"` and collide on `dbkit.MigrationRegistry.Register`; pki's own migrations register only when the project's go.mod genuinely requires `go/pki` -- a project wiring authn with its own, non-pki-backed `KeySource` must not have this command create `pki_signing_keys` and friends uninvited). Each module's sqlite migration files apply through dbkit's MigrationRegistry, one transaction per module, every file recorded in `schema_migrations` as it lands, so a re-run applies only what is not yet recorded and reports the database up to date when nothing is left — idempotence is pinned by tests against real re-runs. Building either module here performs no I/O and never calls any of pki's `EnsurePurpose`/`ActiveSigner`/`VerificationKeys` methods: migration application is raw versioned SQL, never `AutoMigrate`, so it never parses either module's GORM model structs and neither module's own encryption serializer needs registering in this command at all.

Refusals are deliberate and name their reason. A go.mod with no speed requires is probably not a generated project; one that requires only non-migration-shipping speed modules is told so, with its requires list and the pointer that its app's own startup Apply composes its schema. A deployment mode other than standalone is refused before the database is touched — the distributed mode's schema lives in PostgreSQL, which this command never touches. A database file that already exists is migrated only when it carries the `schema_migrations` ledger: a ledgerless existing file is refused with repair guidance rather than guessed at, and so is a path that exists and is not a regular file. The report line on success names the database and the newly applied counts per module; the exit-code contract matches the sibling commands (0 success and help, 2 usage errors, 1 execution errors).

## The `config print` contract

`saasctl config print [go.mod]` renders how a generated project's bootstrap configuration resolves: the app name comes from the go.mod's module path, and the five bootstrap variables — `SPEED_DEPLOYMENT_MODE`, `PORT`, `SPEED_DB_PATH`, `SPEED_CONFIG_KEY`, `SPEED_ORG_INDEX_KEY` — resolve through the appconfig twin of the generated project's own `cmd/server/config.go`, the embedded template's file (the twin relationship is pinned by `TestAppConfigIsTheGeneratedProjectsTwin`, which reads that file). Each of the five lines shows the resolved value and its provenance — the variable that carried it, or the default it fell back to. The two key variables are secrets: their value column renders `[redacted]` whatever the environment holds, never the key bytes and never a hint of their shape. Malformed input is refused with the same errors the generated app's own bootstrap would refuse with — a malformed deployment mode surfaces pkgcore's parse error, a malformed key names the app and the variable — so what this command prints or refuses is exactly what the app it maintains would boot on or refuse. Exit codes: 0 success and help, 2 usage errors, 1 execution errors.

## Speed-root resolution

The go.mod `replace` directives point at a speed checkout — the transition-state shape a consumer go.mod carries until the M4 first-release cleanup (requires at `v0.0.0-00010101000000-000000000000`, `replace ... => <speed-root>/go/<m>` for every workspace module in the graph, full indirect require block, no go.sum: the first consumer-side `go mod tidy` builds it, normal for a fresh Go project). The checkout path resolves in three tiers: `--speed-root` flag, then the `SPEED_ROOT` environment variable, then a walk up the working directory's ancestors for a `go.work` whose `use` entries include `go/pkgcore` (the pattern of `tools/release/lockstep-release.py`'s `find_repo_root`, sharpened so an unrelated go.work up the tree cannot be mistaken for a speed checkout). A resolved path is validated to actually hold that go.work before anything is written.

## Testing

The module's unit suite runs entirely offline (no testcontainers, no network — the materialization tests fabricate a fake speed checkout as a temp directory holding a `go.work`, and compare materialized bytes against the embedded assets with tokens substituted, which is also the go.mod golden check). Run from the module directory: `go build ./...`, `go vet ./...`, `golangci-lint run ./...`, `go test ./... -race`. Layout follows the repository convention: `new_test.go` covers `new.go`, `embed_test.go` covers the template package's invariants, `version_test.go` covers the version validator, `upgrade_test.go` covers `upgrade.go` against fixture go.mods under `internal/upgrade/testdata/` (a full consumer go.mod, a hand-mixed-version one, a third-party-only one), and the B3-round packages follow the same naming: `internal/appconfig/appconfig_test.go` covers `appconfig.go` (its twin test reads the embedded template's `cmd/server/config.go`), `internal/project/project_test.go` covers `project.go`, `internal/db/db_test.go` covers the group dispatch of `db.go` while `migrate_test.go` covers the migrate subcommand of `migrate.go` against the go.mod fixtures under `internal/db/testdata/` (a config-only one, the full four-module one, a fifth-module one that additionally requires `go/pki`, a tenancy-only one, a no-speed one) — applying the real modules' sqlite migration files to fresh SQLite files and re-running over the same file to pin the ledger and the up-to-date report, `TestMigrate_PKIRequired_MigratesPKITablesToo` separately pinning that `pki`'s own tables are migrated only when the project's go.mod genuinely requires `go/pki`, not merely because `authn` is present — and `internal/config/config_test.go` covers the group dispatch of `config.go` while `print_test.go` covers the print subcommand of `print.go`. Each package ships its own runnable godoc example in its `example_test.go`.

The real proof — materializing each legal selection to a temp directory and running a genuine `go mod tidy` (network) and `go build` there — is the development proof behind the committed template goldens (the go.mod files embedded in `internal/template/project/selection/` are the tidy-pruned results of exactly that run, converted back to tokens), and it doubles as this module's mandatory-first-consumer evidence: saasctl's consumers are generated projects, not the reference app, and the generated projects really compile. The end-to-end consumer proof — `new` → `go mod tidy` (network) → `go build` → boot → smoke — was run as the B4 milestone's round gate, and the template assets' committed goldens were re-verified byte-identical against it.

The B4 proof procedure, repeatable end to end under a temp directory and a temp `SPEED_DB_PATH` (`saasctl db migrate` resolves the unset-`SPEED_DB_PATH` default next to the go.mod argument, so it can run from any directory against a project's go.mod; booting the built app resolves the same default against the process working directory, so boot from the generated project's own directory or set `SPEED_DB_PATH` explicitly):

- `saasctl new` twice with `--speed-root` naming the speed checkout — once with defaults and once with `--with=authn` — and confirm the selection changes what is wired: the default app reports `authn+org+rbac` and its `server.go` imports `org` and `rbac`, the authn-only app reports `authn` and imports neither.
- A genuine `go mod tidy` and `go build ./cmd/server` in each generated project: real compile of the materialized template, first consumer-side tidy writing the go.sum the template does not ship, and the post-tidy go.mod byte-identical to the committed golden with tokens substituted.
- Boot the built binary against its SQLite file and smoke the composed HTTP chain. healthz and `/api/config/public` answer 200; register answers 201 with the created account; and the authn/tenancy chain answers per contract: a wrong password is 401 `authn.invalid_credentials`, a bad bearer token is 401 `authn.token_invalid`, and a route outside the pre-auth allowlist reached anonymously is 403 `tenancy.tenant_unresolved`. One plan item is not satisfiable on a generated skeleton and is recorded as such: a *correct-password* password login cannot return 200, because the skeleton (by the A3 adjudication) ships no demo membership store, tenants or grants, and authn's contract re-verifies the caller's tenant membership through the host-injected `MembershipReader` on every sign-in — a nil reader fails closed — so the honest smoke answers are 403 `authn.tenant_membership_unavailable` for a correct password (credentials verified, membership gate refused), with or without a named `tenant_id`. A generated project whose logins must succeed wires its own `MembershipReader`; the generated code names that seam as the host's first task, and this module must not fake membership to make the plan item pass.
- Fresh database + `saasctl db migrate` against the generated project's own go.mod: reports the applied ledger (`23 migration files (authn 9, config 1, org 4, pki 7, rbac 2)` for the default `authn+org+rbac` selection, which -- unlike `org` and `rbac` -- requires `pki` even though `pki` itself is never a `--with` choice), a re-run reports the database up to date, and booting the app against that same file no-ops its startup `Apply` (the `schema_migrations` ledger is unchanged across the boot) — CLI-then-boot and boot-only agree.
- `saasctl upgrade --version vX.Y.Z` on the tidied go.mod: every speed require rewritten to the one version (the `// indirect` markers and the `replace` block untouched), and a second run reports nothing to rewrite.
- `saasctl config print` with `SPEED_*` set reports each value `from <ENV>` with the key variables `[redacted]`; with the environment empty it reports the defaults with their provenance and the keys as development defaults.

## Known limitations and deferred work

- `db migrate`'s module universe is the migration-shipping root modules present in the project go.mod's speed requires — subpackage modules such as `go/dbkit/audit` stay deliberately outside the CLI universe: audit migrations apply through the app's own startup `Apply` when the app wires `audit.New` (the reference-app pattern), and startup Apply is idempotent via `schema_migrations`, so CLI-then-boot and boot-only agree.
- saasctl ships no integration tier; pr-full's integration matrix is untouched. PostgreSQL legs of anything saasctl drives are proven by the owning modules' own integration tiers.
- Deferred with authority (see `docs/internal/02-repo-and-release.md` and the roadmap): `create-saas-app` and the web-side template (frontend-scaffold round); `saasctl openapi generate` (app-owned API-fragment flow, `docs/internal/21-api-contract.md`); dynamic-config print of `configs`-table values with tenant scopes and schema-driven redaction; a switchable universe beyond `{authn, rbac, org}`; the scaffold-verify workflow's M4 dual-mode boot gate; version discovery for `upgrade` without `--version` (nothing publishes before M4).
