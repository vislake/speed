# saasctl

saasctl is speed's consumer CLI — the Go half of the product's consumer story. speed ships as independently released modules, not an application; saasctl is the tool that shapes the application a consumer actually runs. It manages the boundary where a project meets the speed modules it pulls in: materializing the project skeleton (`new`), rewriting a project's speed module requires to one lockstep version when a new release lands (`upgrade`), applying the speed modules' SQL migrations to a generated project's database (`db migrate`), and showing how a generated project's bootstrap configuration resolves (`config print`) — all four wired in this build. A consumer's code is theirs; the boundary is this CLI's.

The command surface is deliberately small and deliberately stdlib: dispatch is `flag` subcommand handling in `main.go`, no cobra or any third-party CLI dependency. Everything saasctl says is developer tooling, so help text, errors and generated-code comments are English everywhere.

| Concern | Where |
|---|---|
| Command dispatch and the root usage text | `main.go` |
| The `new` command: usage/exit-code contract, `--with` parsing and closure validation, speed-root discovery, materialization | `internal/new/new.go` |
| The `upgrade` command: usage/exit-code contract, the in-place go.mod rewrite, the offline structural self-check | `internal/upgrade/` |
| The `db` command group: the `migrate` subcommand's usage/exit-code contract, the migration universe, the SQLite apply | `internal/db/` |
| The `config` command group: the `print` subcommand's usage/exit-code contract, the provenance rendering | `internal/config/` |
| The generated project's bootstrap configuration twin (shared by `db migrate` and `config print`): env surface, defaults, development keys, error texts | `internal/appconfig/` |
| The shared go.mod context of the `db` and `config` groups (module path, app name, speed requires) | `internal/project/` |
| The embedded project skeleton tree and its invariants | `internal/template/` |
| The release-version regex + validator (twin of lockstep-release.py's `VERSION_PATTERN`) | `internal/version/` |
| Package doc comment | `doc.go` |

## What this build wires

This build wires all four commands: `new`, `upgrade`, `db migrate` and `config print`. The remaining maintenance surface (dynamic-config value print and editing, the web-side scaffolds) is listed under "Known limitations and deferred work". In this build saasctl needs a speed checkout on disk at run time (see Speed-root resolution) — no usable release is published, so every materialization points at a checkout. `web/package.json` rewriting and the frontend-scaffold tool (`create-saas-app`) do not exist here.

## The embedded template (`internal/template/`)

The project `saasctl new` materializes is not synthesized in code: it is an embedded tree of real files (`project/` under `internal/template/`) that are a working app by construction — they were produced by materializing, `go mod tidy`-ing and building them against a real speed checkout, then converting the paths back to tokens for embedding. The tree mirrors the reference app's `cmd/server` shape with every demo-specific piece removed: no notes module, no demo tenants, grants, membership store or subject resolver, no seeded data. A generated project is an honest skeleton whose host seams — authn's `MembershipReader`, org's `SubjectResolver`, the config resolver — are left unwired and fail closed per each module's contract, each named by a doc comment in the generated files as the owner's first task.

Three conventions hold the template together, each test-pinned on the template side and enforced again from `internal/new`'s side (the two packages cannot import each other's tests, so both sides assert their half of the shared ground truth):

- **Compile containment (A2).** Every embedded `.go` file starts with the line `//go:build ignore`, so the template tree never compiles, vets or lints as part of this module; `new` strips exactly that one line (plus its blank line) at materialization. The generated project's compile-correctness is proven by real builds of materialized apps, never by compiling the assets in place. A template edit that forgets the marker fails in two places: the embed-tree walk in `embed_test.go` and `StripBuildIgnore`'s error path when `new` materializes.
- **Selection (A5).** Only two files differ between selections: `selection/<key>/go.mod.txt` and `selection/<key>/server.go` (the go.mod require set with replace directives, and the import, module-construction and middleware set). The go.mod document carries the inert `.txt` name through the embed for a mechanical reason — go:embed's directory scan refuses to descend into a subdirectory containing a file named `go.mod`, reading such a directory as a nested module root, so a `go.mod` named as such would silently vanish from the embedded tree — and `new` renames it to `go.mod` at materialization. `<key>` is `SelectionKey`'s canonical rendering — sorted module names joined with `+`, or `none` for the empty set. The switchable universe is `{authn, rbac, org}`: the three modules that participate in the minimal combination. The required five (pkgcore, dbkit, tenancy, config, observability) have no off option. Every legal selection ships an embedded directory; an extra directory is dead weight the template tests refuse.
- **Tokens (A4).** Two tokens appear in template files and nowhere else: `__APP_NAME__` (the module path, derived at `new` time from the target directory's base name) and `__SPEED_ROOT__` (the resolved speed checkout path). Materialization substitutes them; tests assert no token survives in a materialized tree, so a template edit introducing a third token fails until the substitution learns it.
- **The shared host kernel.** The host-neutral composition — the assembly engine (configuration load, the component-assembly drive, the HTTP face and the serve/graceful-shutdown lifecycle), authn's mount path, the liveness/allowlist surface, the mounted-route label seed and the fixed middleware chain — is not template-owned content at all: it lives in the platform module `github.com/vislake/speed/go/app` (the engine in the root package, the chain in `go/app/chain`, the seam bridges in `go/app/bridges`), which every materialized project and the reference app import. Both hosts assemble through the engine and compose from one shared source, and `tools/check_host_composition.py` is the gate that keeps it that way: it fails when either host tree re-declares the kernel's symbols, re-grows its statements (the serve loop, the `/healthz`, `/metrics`, `/api/v1/authn` literals) or re-issues the assembly calls the engine owns (`pkgcore.NewKernel`, `.Bootstrap(`, `dbkit.Open`, the migration registry, `http.NewServeMux`, the jobs wiring, `signal.NotifyContext`, `chain.Chain`, `obs.Init`) in its own code — outside the host-owned assembly-core files its allowances name, where those calls are the host's own shape rather than a re-grown copy of the engine's: the five selections' `server.go` files and the reference app's `internal/app/server.go`, `internal/app/component.go` and `internal/app/host_wiring.go`. Any other host file re-issuing a banned call still fires. To change shared host behavior, change `go/app` — a behavior only one host should have does not belong in the kernel and stays in that host's own files.

The five legal selections are the minimal combination `{authn, rbac, org}` plus its four closures. Each selection's `server.go` is its host's whole composition: it registers the host's own components (the crypto and tenancy-resolver providers, the database and observability copies, the module overrides) on a fresh `pkgcore.ComponentRegistry` and drives the assembly through `go/app`'s `Assemble` with a `LoadSpec` carrying the shared `hostConfig`, the loader options (`ConfigEnvPrefix` and `bootstrapDevDefaults`) and a `CompositionOverrides` block that selects the module components in the order their migrations apply. `cmd/server/main.go` (shared) then serves through the selection's own `runServer`, which overlays the shutdown signals, waits them out and shuts the assembly down through `go/app`'s `Shutdown`. `config.go` (shared) resolves the full uniform env surface of a generated project through `go/pkgcore/config`'s loader — the host target pins each host variable's exact name with `config:"env=…"` tags and pre-sets the three scalar defaults, the six platform key materials come from the importing module components' own `BootstrapKeys` declarations (resolved by the assembly's loader through its declaration-driven entry, each variable under the loader's derived spelling of its declared key path, with `bootstrapDevDefaults` as the documented development fallback table), and a transform parses, validates and refuses the text-typed host variables — `APP_DEPLOYMENT_MODE`, `APP_DB_PATH`, `PORT`, the infrastructure groups (`APP_REDIS_ADDR`, the `APP_S3_*`/`APP_SMTP_*` groups, `APP_SMS_GATEWAY_URL`) and `APP_OTLP_ENDPOINT` — so a consumer's bootstrap contract never changes with the selection, and a generated project is a consumer of the same loader and the same engine the reference app drives.

`go/pki` is not a sixth switchable module: it follows `authn` silently, so the four `authn`-containing selections' compositions select its module component (the host's own capability-carrying copy) and the authn override takes the `KeySource` `authn.WithKeySource` requires from the constructed `*pki.Module`'s `Service()`, and their `go.mod.txt` carries `go/pki` (plus its own first `go/jobs` dependency) among the require/replace set. The `none` selection needs neither, having no signing keys to manage at all. `pki`'s own tables persist across restarts in the generated project's SQLite file — no development-seed key derivation is needed, since the key is created once by `pki.Service.EnsurePurpose` (lazily, on `Signer`'s first `Issue` call) and then simply already exists on every later boot.

## The generated project's key materials

A generated project's `config.go` (shared across every selection) carries the six platform key materials as `bootstrapDevDefaults`, the declared defaults table the assembly's loader options hand over, and the declarations themselves ride the importing module components (`BootstrapKeys`), which the engine's loader resolves through its declaration-driven entry; the table's documented dev byte sequences are the loader's lowest-priority source. Each key reads from the environment under the loader's own derivation of its declared key path — the path uppercased with its dots doubled under the `APP_` prefix: `APP_CONFIG__CIPHER_KEY` (the config module's cipher, declared path `config.cipher_key`), `APP_ORG__INVITATION_EMAIL_INDEX_KEY` (org's invitation blind indexer), `APP_AUTHN__BLIND_INDEX_KEY` (authn's email/phone blind indexer), `APP_AUTHN__PII_CIPHER_KEY` (the cipher sealing authn's encrypted PII columns), `APP_PKI__LOCAL_KEY_CIPHER_KEY` (the cipher sealing pki's persisted signing-key column) and `APP_NOTIFICATION__CONTACT_INDEX_KEY` (notification's contact-index key, carried uniformly for a composition that later wires the module). A set variable must hold 64 hex characters (a 32-byte key); the loader decodes it, and a malformed value fails the load naming the key path and the variable the loader read, never an opaque cipher error later. The declarations pin no variable names and no root key of their own — a deployment that wants root-key derivation installs `ConfigRootKeyEnv`/`ConfigKeyDerivation` as loader options, which this skeleton deliberately does not. Every one of the six is a fallback behind its env variable's path — there is no key material that can only be reached as a source constant, so an operator who sets the variables controls every key byte. The appconfig twin, `config print`, the README's env table and the drift-proof parity tests keep the two sides equal.

## Distributed-mode infrastructure wiring

Every one of the five selections' `cmd/server/config.go` (shared verbatim across selections — see the Selection convention above) and `server.go` (the per-selection `composition()` block) carries the SAME conditional infrastructure-seam wiring the reference app's `internal/app/server.go` proves: a generated project's distributed deployment mode composes real implementations of the `eventbus`, `kv`, `mailer` and `objectstore` seams, while its own database always speaks SQLite (its `server.go` imports exactly one dialect driver, `go/dbkit/dialect/sqlite`, so the database component it selects has a dialect to open). The env var NAMES this template resolves are its own `APP_*` prefix, the same convention the reference app uses (a generated project's and the reference app's are independent, consumer-owned bootstrap surfaces — nothing requires the two to agree). Four environment variables drive the seam wiring:

- `APP_REDIS_ADDR` — composes a real Redis-backed implementation of BOTH the `eventbus` and `kv` seams (the two components share one client they build and close themselves; wiring only one of the two can never let a distributed composition pass the assembly's capability validation, which compares every selected component against the declared mode's requirement — `MultiReplicaSafe` for distributed — regardless of which business modules a selection wires).
- `APP_S3_ENDPOINT`/`APP_S3_BUCKET`/`APP_S3_ACCESS_KEY`/`APP_S3_SECRET_KEY` (all four required together, `APP_S3_REGION`/`APP_S3_USE_SSL`/`APP_S3_BUCKET_LOOKUP` optional) — composes a real S3-compatible `ObjectStore` for the `objectstore` seam.
- `APP_SMTP_HOST`/`APP_SMTP_PORT` (required together, `APP_SMTP_USERNAME`/`APP_SMTP_PASSWORD` optional) — composes a real SMTP `Mailer` for the `mailer` seam.
- `APP_SMS_GATEWAY_URL` — selects the real HTTP SMS transport component (`sms.http`) in the four `authn`-containing selections only (resolved in every selection's `config.go`, consumed only where `server.go` wires `authn`, exactly like the platform key variables' own asymmetric consumption). Absent under standalone, the composition stays on the console SMS component; absent under distributed, the seam is left deliberately unwired and `authn.NewModule`'s own validation fails closed with `ErrMissingDistributedSMSSender` — never a silently-kept console sender nobody in a distributed replica pool is reading.

`APP_OTLP_ENDPOINT` is not a seam variable but rides the same conditional shape, carried in each selection's `server.go` as the host's own observability component configuration: set, the component's `Prepare` hands it to `obs.Init` as `obs.WithOTLPEndpoint` and traces and metrics are pushed to that collector; unset, the local exporters are wired and the shared host kernel's `/metrics` route serves the in-process Prometheus scrape output. Both exporter factories are registered by `main.go`'s blank imports (`go/observability/exporter/otlp` and `go/observability/exporter/prometheus`): a host that removes the OTLP import and keeps setting the endpoint gets a startup error naming the missing import, a host that removes the Prometheus import gets a `/metrics` route answering 404, and a host that lets the endpoint select the OTLP exporters also gets a 404 at `/metrics` — by design, since there is no local registry being kept to scrape. The endpoint travels into the component's configuration block only when the variable is non-empty, and `OTLPEndpoint` reaches that block through the same loader-resolved `serverConfig` as every other bootstrap value.

Every one of these is additive and off by default: with none of them set, `configFromEnv` resolves byte-identically to the standalone-only shape, and every committed golden (`internal/template/project/selection/*/server.go`, `*/go.mod.txt`) reflects that — the standalone `go run ./cmd/server` experience is unchanged. Setting `APP_DEPLOYMENT_MODE=distributed` with none of the four seam variables set fails the assembly closed with `ErrCapabilityUnsatisfied`, naming whichever seam the composition left on an in-process implementation first. The database component the composition selects is the host's own copy of the built-in `db.sqlite` descriptor, carrying the capabilities the project's database placement has (`APP_DB_PATH` names one shared file — point a distributed deployment's replicas at the same file, or select a client/server database component instead).

The selections' `go.mod.txt` documents are re-derived through this module's own regeneration procedure (materialize → genuine `go mod tidy` against the real network → genuine `go build` → convert the resulting `go.mod` back to token form), never hand-edited: `github.com/redis/go-redis/v9` and `github.com/minio/minio-go/v7` are indirect requires in every selection, since no selection's own code imports either directly — only `pkgcore`'s `eventbus/redis`, `kv/redis` and `objectstore/s3` subpackages, subpackages of the already-direct `go/pkgcore` require, do — while `gorm.io/gorm` is a direct require wherever the selection's own code reads the constructed `*gorm.DB` (the authn and org overrides).

## The `new` contract

`saasctl new [flags] <target-directory>` materializes the skeleton into a new directory and prints the written files plus next steps. The exit-code contract, pinned by tests:

- **0** — success, and `-h`/`--help` (help is printed, nothing is written).
- **2** — usage errors: bad flags, a wrong argument count, a target whose base name cannot serve as a module path (the name becomes the go.mod module path; the grammar is stricter than `go mod init`'s own — no leading dot or dash, no space, no trailing dot, no `.` or `..` — and a name that passes it must also pass `module.CheckImportPath`, the exact validator the go command itself runs on a module path, which refuses the reserved Windows device names on every platform, so every accepted name is one `go mod init` accepts and every refusal lands before anything is created), or an invalid `--with` value.
- **1** — execution errors: an unresolvable speed root, a resolved speed root whose path would break the produced go.mod's grammar (the produced go.mod document is passed through `modfile.Parse`, the go command's own parser, before anything is created, and a document that does not parse refuses the run naming the checkout path: the replace directives embed that path verbatim, and a path containing a space or parentheses — legal on the filesystem, rejected by the go.mod grammar — would ship a skeleton no `go mod tidy` accepts), an existing non-empty target, an I/O failure.

`--with` is positive selection with downward-closure validation: selecting `rbac` or `org` without `authn` is an error naming `authn` as implied (their routes need an authenticating layer), and unknown names are rejected listing the valid set. There is no `--without`: closing `authn` is expressed by not listing it, and dependents cannot be selected without it.

An existing non-empty target is refused before anything is written (only an existing *empty* directory is accepted and filled); on a write failure everything the run created is removed again. The written file list is fixed and relative, never derived from a walk of the target, so a hostile or stale target tree cannot smuggle paths into the write. The go.mod is the one file this command produces that an external tool consumes, so the delegate-to-authority rule this file records below applies to it: before anything is created — the target directory included — the produced document (the embedded asset with this run's app name and speed-root path substituted) must pass `modfile.Parse`, the exact parser the go command runs over a go.mod. The check sits on the produced document rather than on the speed-root input, which is what lets it cover every resolution tier (the `--speed-root` flag, `SPEED_ROOT` and the ancestor-go.work discovery) without any tier enumerating the grammar's breaking characters, and the bytes the gate accepts are the bytes the write loop lands.

## The `upgrade` contract

`saasctl upgrade --version <v> [go.mod]` rewrites a consumer go.mod's speed requires to one target version — the lockstep-release story: the version number is the whole compatibility surface, so all of a project's `github.com/vislake/speed/go/*` requires move together. The default path is `go.mod` in the working directory; `[go.mod]` names a different file. The rewrite touches only the version token of each speed require line — nothing else in the file changes, byte for byte: third-party requires (and their `// indirect` markers), replace blocks, comments, blank lines and formatting survive because the rewrite edits the parsed syntax tree in place and prints it back through `golang.org/x/mod/modfile`, the Go team's own parser, deliberately never hand-serialized. The set of modules rewritten is derived from the file's own require lines, never hardcoded.

`--version` is required: no usable release is published yet and version discovery is not implemented, so the operator supplies the target release version. It is validated by `internal/version` against the same grammar as the release tooling (`^v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z-]+(\.[0-9A-Za-z-]+)*)?$`), and every speed require must end at the validated version or the run fails. The exit-code contract matches `new`: 0 for success and help, 2 for usage errors (missing or invalid `--version`, too many positional arguments), 1 for execution errors (a missing or malformed go.mod, a go.mod with no speed requires — nothing to rewrite is an error, so a consumer pointed at the wrong file learns it immediately rather than silently succeeding). A second run over an already-rewritten file reports nothing changed and exits 0 (idempotence is pinned by tests). After the rewrite the result is re-parsed from bytes and structurally self-checked offline — every speed require at the target version, the file well-formed, replace and exclude directives exactly as they were — before anything is written back, with the file's original mode preserved. The self-check additionally refuses a go.mod whose replace or exclude directives defeat the rewritten requires: a module-to-module replace pinning a speed module to a version other than the target wins over its require line at build time, and an exclude of a speed module at the target version itself tells the go command that version is unusable — either way a clean upgrade report over the file would be a lie about the version the project actually builds (local-directory replaces carry no version and are never caught by this rule). This package rewrites go.mod files only; the web packages' lockstep requires are not rewritten here.

## The `db migrate` contract

`saasctl db migrate [go.mod]` applies the SQL migrations of the speed modules a consumer project requires to the project's SQLite database — the operator-driven twin of the Apply the generated app's own startup performs, over the same bootstrap environment the app boots from (`APP_DEPLOYMENT_MODE`, `APP_DB_PATH`, ...). The default database path (`APP_DB_PATH` unset, the fixed `app.db` — the literal the generated app's own `cmd/server/config.go` shares, never derived from the module path, so a renamed module cannot fork the file CLI and app open) is resolved next to the `[go.mod]` argument rather than the caller's working directory — the directory the generated app is documented to run from, where its default database lands — so a go.mod argument naming another directory's project migrates that project's own database whichever directory the command is invoked from; an explicit `APP_DB_PATH` always wins, an absolute value used exactly as the app would use it and a relative one resolved against the `[go.mod]` argument's directory the same way the anchored default is. The migration universe is the intersection of the go.mod's own `github.com/vislake/speed/go/*` requires with the root modules that ship their own migrations — authn, config, org, pki and rbac, in alphabetical order — each constructed through its own `NewModule` (authn with a throwaway dev-shaped blind-index key that never issues or stores anything, and a `KeySource` that is pki's own `*Module.Service()` — `buildAuthnAndPKI` builds authn and pki TOGETHER, sharing exactly one `*pki.Module` instance between authn's `WithKeySource` and pki's own migration registration, since two separately constructed `*pki.Module` values would both report `Name() == "pki"` and collide on `dbkit.MigrationRegistry.Register`; pki's own migrations register only when the project's go.mod genuinely requires `go/pki` — a project wiring authn with its own, non-pki-backed `KeySource` must not have this command create `pki_signing_keys` and friends uninvited). Each module's sqlite migration files apply through dbkit's MigrationRegistry, one transaction per module, every file recorded in `schema_migrations` as it lands, so a re-run applies only what is not yet recorded and reports the database up to date when nothing is left — idempotence is pinned by tests against real re-runs. Building either module here performs no I/O and never calls any of pki's `EnsurePurpose`/`ActiveSigner`/`VerificationKeys` methods: migration application is raw versioned SQL, never `AutoMigrate`, so it never parses either module's GORM model structs and neither module's own encryption serializer needs registering in this command at all.

Refusals are deliberate and name their reason. A go.mod with no speed requires is probably not a generated project; one that requires only non-migration-shipping speed modules is told so, with its requires list and the pointer that its app's own startup Apply composes its schema. A database file that already exists is migrated only when it carries the `schema_migrations` ledger: a ledgerless existing file is refused with repair guidance rather than guessed at, and so is a path that exists and is not a regular file. The report line on success names the database and the newly applied counts per module; the exit-code contract matches the sibling commands (0 success and help, 2 usage errors, 1 execution errors).

`APP_DEPLOYMENT_MODE` may be standalone or distributed. Refusing any mode but standalone would rest on a premise that does not hold for what a generated project actually does: every selection's `cmd/server/server.go` blank-imports exactly `go/dbkit/dialect/sqlite`, with no environment variable or option anywhere in the generated wiring that selects a second dialect, under either deployment mode — the same fact the reference app's own distributed-mode proof records for itself (it runs two replicas against one shared SQLite file, an explicit, accepted deviation). A generated project's distributed deployment mode changes which infrastructure SEAMS compose real implementations (see "Distributed-mode infrastructure wiring" above); it does not change which SQL dialect the project's own database speaks, so refusing `migrate` on a dialect argument that is currently false would block a real, working operation for no reason tied to anything this command does. The genuine, still-real concern: concurrent writers against the same SQLite file can still hit `SQLITE_BUSY`. `dbkit.Open` carries a bounded `busy_timeout` (its dialect factory appends `_pragma=busy_timeout(5000)` to every DSN it opens) but still pools up to 25 connections, so a write that still meets an uncommitted holder once the bounded wait is spent — or upgrades a read-then-write transaction, which SQLite's deadlock avoidance refuses immediately; no timeout waits it out — fails with the real error. This is a hazard this command shares with the generated app's OWN startup `Apply` (which already runs unconditionally on every boot regardless of deployment mode), and one that is not specific to the distributed mode at all (an operator invoking `migrate` twice concurrently, or while a standalone-mode replica is already booting against the same file, carries the identical risk). The repository's accepted mitigation for the identical shared-SQLite-file topology is sequential ordering, never a database lock — so `migrate`'s own safe-use contract is exactly that: run it to completion before booting any replica. `migrate.go`'s own `migrate` function doc comment carries the full argument.

## The `config print` contract

`saasctl config print [go.mod]` renders how a generated project's bootstrap configuration resolves: the app name comes from the go.mod's module path, and the full bootstrap env surface — `APP_DEPLOYMENT_MODE`, `PORT`, `APP_DB_PATH`, the six key variables in the loader's derived spellings (`APP_CONFIG__CIPHER_KEY`, `APP_ORG__INVITATION_EMAIL_INDEX_KEY`, `APP_AUTHN__BLIND_INDEX_KEY`, `APP_AUTHN__PII_CIPHER_KEY`, `APP_PKI__LOCAL_KEY_CIPHER_KEY`, `APP_NOTIFICATION__CONTACT_INDEX_KEY`), `APP_REDIS_ADDR`, `APP_OTLP_ENDPOINT`, the `APP_S3_*` group (`APP_S3_ENDPOINT`/`APP_S3_BUCKET`/`APP_S3_ACCESS_KEY`/`APP_S3_SECRET_KEY`/`APP_S3_REGION`/`APP_S3_USE_SSL`/`APP_S3_BUCKET_LOOKUP`), the `APP_SMTP_*` pair (`APP_SMTP_HOST`/`APP_SMTP_PORT`/`APP_SMTP_USERNAME`/`APP_SMTP_PASSWORD`) and `APP_SMS_GATEWAY_URL` — resolves through the appconfig twin of the generated project's own `cmd/server/config.go`, the embedded template's file (the twin relationship is pinned by `TestAppConfigIsTheGeneratedProjectsTwin` and, for the env-name set specifically, the drift-proof `TestAppConfigEnvSetMatchesTheTemplateExactly`, both of which read that file). Each line shows the resolved value and its provenance — the variable that carried it, or the default (or seam) it fell back to. Every value reported is the value the generated app would actually use, and the sqlite path row is the one row whose value resolves one step further than the bootstrap itself: a relative database path — the `app.db` default when `APP_DB_PATH` is unset, or a relative `APP_DB_PATH` — is used by the app relative to the directory it runs from (the go.mod argument's directory, exactly the anchoring `db migrate` applies), so the row's value column shows the effective file, resolved through `cfg.EffectiveDBPath` (internal/appconfig), the single shared function `db migrate` opens its database through — the file print reports and the file migrate opens are the same by construction. When the raw input and the effective file differ — a relative `APP_DB_PATH` — the raw value stays visible in the source column too, so "the value" and "the effective value" are both shown. Print's completeness rules mirror the generated app's own bootstrap exactly: an S3 group or SMTP pair that is only partially set is refused with the same coded error the app's own `configFromEnv` would refuse with, rather than silently ignored — the twin's whole purpose is that print refuses precisely when the generated app would refuse to boot. The six key variables plus the S3 secret key, the SMTP password and the SMS gateway URL — a URL only by shape, authn's HTTP SMS transport keeping no credential channel separate from its endpoint, so an operator who must authenticate to the gateway puts the credentials inside the URL — are secrets: their value column renders `[redacted]` whatever the environment holds, never the bytes and never a hint of their shape — which variables are secrets is the single `redactedEnv` declaration in `print.go`, consulted by every rendered row (a sensitive variable not declared there prints its plaintext by default, and the whole-output tests force every added row past that list either way). Malformed scalar input is refused the same way — a malformed deployment mode surfaces pkgcore's parse error, a malformed key names the app and the variable — so what this command prints or refuses is exactly what the app it maintains would boot on or refuse. Exit codes: 0 success and help, 2 usage errors, 1 execution errors.

## Speed-root resolution

The go.mod `replace` directives point at a speed checkout — the transition-state shape a consumer go.mod carries until the next release's cleanup (require version strings are placeholders the replaces override: a zero pseudo-version, except where another speed module requires the same module at a real version, in which case that version stands; `replace ... => <speed-root>/go/<m>` for every workspace module in the graph, full indirect require block, no go.sum: the first consumer-side `go mod tidy` builds it, normal for a fresh Go project). The checkout path resolves in three tiers: `--speed-root` flag, then the `SPEED_ROOT` environment variable, then a walk up the working directory's ancestors for a `go.work` whose `use` entries include `go/pkgcore` (the pattern of `tools/release/lockstep-release.py`'s `find_repo_root`, sharpened so an unrelated go.work up the tree cannot be mistaken for a speed checkout). A resolved path is validated to actually hold that go.work before anything is written.

## Produced artifacts pass their consumer's parser

One rule, three instances in this build: **whenever this tool produces a file that an external tool consumes, that file must pass the external tool's own parser/validator before delivery.**

- `new` validates its target's base name — the module path a generated go.mod will declare — with `module.CheckImportPath`, the exact validator the go command itself runs on a module path (the gate that refuses the reserved Windows device names on every platform), before anything is created.
- `upgrade` re-parses its rewritten go.mod from bytes (`modfile.Parse`) and structurally self-checks it before anything is written back (see the upgrade contract above).
- `new` hands the go.mod document it is about to materialize to `modfile.Parse` before anything is created: the replace directives embed the resolved speed-root path verbatim, the go.mod grammar is not every filesystem path's grammar, and a checkout path the grammar rejects would otherwise ship a skeleton no `go mod tidy` accepts while `new` exited 0 over it.

The delegate shape beats a producer-side character-set check three ways: it needs no enumeration of where the consumer's lexer breaks; it guards the artifact rather than the input, so every producer-side input path is covered at once (the go.mod check covers a speed root resolved by `--speed-root`, `SPEED_ROOT` or the ancestor-go.work discovery whether or not that tier validated its input); and any new token a template edit introduces is covered automatically. A future file-producing command whose output another tool consumes belongs in this list.

## Reported values are effective values

`config print` exists to answer which file and which value the generated app would actually use, and the rule it answers by is the strong form: **every value config print reports must be the value the generated app would actually use; when the raw input and the effective value differ, both are shown.** The one config item with a resolution step beyond the bootstrap today is the SQLite database path: a relative value (the `app.db` default or a relative `APP_DB_PATH`) resolves against the directory the app runs from, the go.mod argument's directory, through `cfg.EffectiveDBPath` — internal/appconfig's one shared function, which `db migrate` opens its database through and `config print` renders, so the file print reports and the file migrate opens are byte-identical by construction. The row's value column shows the effective file; the raw value and its provenance stay in the source column when the two differ.

## Testing

The module's unit suite runs entirely offline (no testcontainers, no network — the materialization tests fabricate a fake speed checkout as a temp directory holding a `go.work`, and compare materialized bytes against the embedded assets with tokens substituted). That byte comparison is a pin of the MATERIALIZER against the committed assets, and deliberately nothing more: it is not a freshness check on the go.mod documents, since both sides of the comparison are the same asset — a go.mod.txt golden gone stale relative to what the speed modules now require passes it unchanged, and nothing automatic catches that staleness today (the scaffold-verify leg's real tidy+build covers one selection and would silently repair a stale require set rather than fail). Regenerating the five goldens through the real tidy procedure whenever a speed module's dependency set changes is the only check that exists. Run from the module directory: `go build ./...`, `go vet ./...`, `golangci-lint run ./...`, `go test ./... -race`. Layout follows the repository convention: `new_test.go` covers `new.go`, `embed_test.go` covers the template package's invariants and pins the generated project README against the template it ships beside — the Go version prerequisite against every selection's go.mod.txt, a bidirectional set equality between the README's documented environment variables and the ones `cmd/server/config.go` actually parses, and a named-identifier check that every `dev*` key the README mentions is a real declaration somewhere in the template (never a stale name) — `version_test.go` covers the version validator, `upgrade_test.go` covers `upgrade.go` against fixture go.mods under `internal/upgrade/testdata/` (a full consumer go.mod, a hand-mixed-version one, a third-party-only one), and the remaining packages follow the same naming: `internal/appconfig/appconfig_test.go` covers `appconfig.go` (its twin test reads the embedded template's `cmd/server/config.go`), `internal/project/project_test.go` covers `project.go`, `internal/db/db_test.go` covers the group dispatch of `db.go` while `migrate_test.go` covers the migrate subcommand of `migrate.go` against the go.mod fixtures under `internal/db/testdata/` (a config-only one, the full four-module one, a fifth-module one that additionally requires `go/pki`, a tenancy-only one, a no-speed one) — applying the real modules' sqlite migration files to fresh SQLite files and re-running over the same file to pin the ledger and the up-to-date report, `TestMigrate_PKIRequired_MigratesPKITablesToo` separately pinning that `pki`'s own tables are migrated only when the project's go.mod genuinely requires `go/pki`, not merely because `authn` is present — and `internal/config/config_test.go` covers the group dispatch of `config.go` while `print_test.go` covers the print subcommand of `print.go`. Shared test support is its own package, the `eventbustest`/`tenancytest` shape: `internal/appconfig/appconfigtest` holds `AssertKeys`, which derives the bootstrap environment surface from `appconfig.Load`'s own behavior and fails a caller whose variable list does not name that surface exactly — the module root's `main_test.go`, `internal/config/print_test.go` and `internal/db/migrate_test.go` each carry their own list pinned through it — and its own `assert_keys_test.go` exercises the comparison's reject paths, which a failing assertion cannot reach in-process. Runnable godoc examples live in `example_test.go` files in six packages (`internal/appconfig`, `internal/config`, `internal/db`, `internal/project`, `internal/upgrade`, `internal/version`); the root `main` package, `internal/new` and `internal/template` ship none.

The real proof — materializing each legal selection to a temp directory and running a genuine `go mod tidy` (network) and `go build` there — is the development proof behind the committed template goldens (the go.mod files embedded in `internal/template/project/selection/` are the tidy-pruned results of exactly that run, converted back to tokens), and it doubles as this module's mandatory-first-consumer evidence: saasctl's consumers are generated projects, not the reference app, and the generated projects really compile. The end-to-end consumer proof — `new` → `go mod tidy` (network) → `go build` → boot → smoke — was the module's acceptance gate, and the template assets' committed goldens were re-verified byte-identical against it.

The end-to-end proof procedure, repeatable under a temp directory and a temp `APP_DB_PATH` (`saasctl db migrate` resolves the unset-`APP_DB_PATH` default next to the go.mod argument, so it can run from any directory against a project's go.mod; booting the built app resolves the same default against the process working directory, so boot from the generated project's own directory or set `APP_DB_PATH` explicitly):

- `saasctl new` twice with `--speed-root` naming the speed checkout — once with defaults and once with `--with=authn` — and confirm the selection changes what is wired: the default app reports `authn+org+rbac` and its `server.go` imports `org` and `rbac`, the authn-only app reports `authn` and imports neither.
- A genuine `go mod tidy` and `go build ./cmd/server` in each generated project: real compile of the materialized template, first consumer-side tidy writing the go.sum the template does not ship, and the post-tidy go.mod byte-identical to the committed golden with tokens substituted.
- Boot the built binary against its SQLite file and smoke the composed HTTP chain. healthz and `/api/v1/config/public` answer 200; register answers 201 with the created account; and the authn/tenancy chain answers per contract: a wrong password is 401 `authn.invalid_credentials`, a bad bearer token is 401 `authn.token_invalid`, and a non-authn route outside the tenancy allowlist reached anonymously is 403 `tenancy.tenant_unresolved` (authn's own subtree is exempt from tenant resolution by structure -- its pre-auth operations need no allowlist entries at all, which is what lets enterprise SSO's dynamic per-tenant provider names `oidc:<tenant>` reach authn's own handler; see the templates' `runServer` and `composeFace` doc comments for the full reasoning). One plan item is not satisfiable on a generated skeleton and is recorded as such: a *correct-password* password login cannot return 200, because the skeleton ships no membership store, tenants or grants, and authn's contract re-verifies the caller's tenant membership through the host-injected `MembershipReader` on every sign-in — a nil reader fails closed. The honest smoke answer for a correct password is IDENTICAL to the wrong-password answer above: 401 `authn.invalid_credentials`, with or without a named `tenant_id` — the login endpoint discloses nothing about whether the password verified, the specific reason (no resolvable membership) being recorded in the login history rather than the response. The skeleton still fails closed. A generated project whose logins must succeed wires its own `MembershipReader`; the generated code names that seam as the host's first task, and this module must not fake membership to make the plan item pass.
- Fresh database + `saasctl db migrate` against the generated project's own go.mod: reports the applied ledger — `applied 34 migration files (authn 12, config 1, org 9, pki 9, rbac 3)` for the default `authn+org+rbac` selection, which, unlike `org` and `rbac`, requires `pki` even though `pki` itself is never a `--with` choice. The per-module counts are the modules' own sqlite migration sets at the time of the run, so no total here is a frozen constant: `migrate_test.go`'s fixtures pin the applied report and fail loudly when a set moves, `TestFullUniverseLedgerCountsMatchTheModulesOwnMigrationTrees` pins the ledger maps to the modules' own migration trees, and `TestAgentsMdMigrationCountsMatchTheRegistry` keeps this quoted report equal to what a real run reports. A re-run reports the database up to date, and booting the app against that same file no-ops its startup `Apply` (the `schema_migrations` ledger is unchanged across the boot) — CLI-then-boot and boot-only agree.
- `saasctl upgrade --version vX.Y.Z` on the tidied go.mod: every speed require rewritten to the one version (the `// indirect` markers and the `replace` block untouched), and a second run reports nothing to rewrite.
- `saasctl config print` with `APP_*` set reports each value `from <ENV>` with the key variables `[redacted]`; with the environment empty it reports the defaults with their provenance and the keys as development defaults. In either environment the sqlite path row reports the EFFECTIVE file — a relative database path anchored to the go.mod argument's directory, byte-identical to the file `db migrate` opened in the earlier bullet — keeping the raw value visible when it differs.

The distributed-mode leg of this same real proof runs for one selection, locally and repeatably in CI: `go/saasctl/integration_test/scaffold_dual_mode_test.go`'s `TestScaffoldNewProject_AuthnOrgRbac_BootsInBothDeploymentModes` (build-tagged `integration`, this module's Docker-backed tier) materializes the `authn+org+rbac` selection (`internal/new.Run`, in-process), runs a genuine `go mod tidy` against the real network and a genuine `go build`, runs `saasctl db migrate` (`internal/db.Run`, in-process) and a full boot-and-smoke cycle (healthz 200, `/api/v1/config/public` 200, a real register 201, then a graceful SIGINT and a clean exit) under the standalone default, then repeats the identical migrate-and-boot cycle under `APP_DEPLOYMENT_MODE=distributed` against real Redis, RustFS (S3-compatible) and Mailpit containers this test starts itself with `testcontainers-go` — the same image pins the reference app's own distributed-mode integration test uses, so every Docker-backed tier in this repository exercises the same server behavior. `.github/workflows/scaffold-verify.yml` runs this test on `workflow_dispatch` and a daily schedule. This is a real gate, not the full acceptance itself: it covers one of five legal selections (see this file's "Distributed-mode infrastructure wiring" section for why the other four's own contribution — the general seam-wiring prose — is identical and therefore not separately re-proven in CI, a deliberate, explicitly-recorded scope reduction), no web-side scaffold exists to verify at all, and no multi-replica convergence proof exists for a generated project (unlike the reference app's own integration test, which drives two replicas across a real EventBus/KVStore boundary) — a generated project has no business modules of its own to drive such a proof against, and inventing demo ones here would defeat the skeleton's own "no demo-specific piece" contract.

## Known limitations and deferred work

- `db migrate`'s module universe is the migration-shipping root modules present in the project go.mod's speed requires — subpackage modules such as `go/dbkit/audit` stay deliberately outside the CLI universe: audit migrations apply through the app's own startup `Apply` when the app wires `audit.New` (the reference-app pattern), and startup Apply is idempotent via `schema_migrations`, so CLI-then-boot and boot-only agree.
- saasctl's unit suite (`internal/*`) stays entirely offline; `go/saasctl/integration_test/` is this module's Docker-backed tier and is NOT part of `full-check.yml`'s integration-tiers matrix — it runs only through `scaffold-verify.yml`'s own schedule/dispatch, a deliberate placement (this tier materializes and boots a whole separate project rather than exercising this module's own code against a database, the shape every other row in that matrix has) rather than a gap in that matrix. PostgreSQL legs of anything saasctl drives are proven by the owning modules' own integration tiers.
- The distributed-mode template wiring and its CI dual-mode boot proof cover ONE of the five legal selections (`authn+org+rbac`) end to end; the other four (`none`, `authn`, `authn+rbac`, `authn+org`) carry the identical general seam-wiring code (config.go's env-var parsing is verbatim shared; each server.go's `composition()` block is the same conditional-selection prose, adapted only for which modules that selection wires) and were proven to materialize, `go mod tidy` and `go build` correctly by a manual pass, but do not have their own CI-wired dual-mode BOOT proof — a deliberate, explicitly-recorded scope reduction (this file's Testing section has the reasoning).
- Deferred: `create-saas-app` and the web-side template (frontend scaffold); `saasctl openapi generate` (app-owned API-fragment flow); dynamic-config print of `configs`-table values with tenant scopes and schema-driven redaction; a switchable universe beyond `{authn, rbac, org}`; the other four selections' own CI-wired dual-mode boot proof (see the bullet above); a multi-replica convergence proof for a generated project (the reference app's own integration-test-shaped proof, which needs business modules to drive it that a generated skeleton deliberately does not carry); version discovery for `upgrade` without `--version` (no usable release exists yet).
