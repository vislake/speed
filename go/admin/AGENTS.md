# admin

go/admin is the operations-console backend: the platform-staff-facing operations surface over capabilities that already live in every other module. This file is the module-level discipline that ships with `go/admin` to consuming projects. Judge what exists by the code, not by this file; where this file and the code disagree, the code wins.

## Scope

The module's surface, each item naming the code that implements it:

- **Tenant ledger** (`model.go`'s `Tenant`, `tenant_repository.go`, `tenant_service.go`): a platform-data table (`admin_tenants`, `dbkit.AssertNotTenantScoped`) recording which tenants the platform believes exist -- an operator convenience, never the authoritative source of tenant existence. Populated two ways: `Module.Register` subscribes to org's real `org.node.created` event, and `TenantService.handleOrgNodeCreated` lazily creates an active, blank-`DisplayName` row the first time a tenant's ROOT node appears (`org.OrgNode.IsRoot()`'s discriminator: `ParentID == ""`, never node depth); and manual CRUD through `POST`/`GET`/`PATCH /api/v1/admin/tenants`. `TenantService.SetStatus` records an explicit `admin.tenant.status_changed` audit event on every ledger edit. The ledger write path guards concurrent edits with a compare-and-set `UPDATE` (`TenantRepository.applyGuardedPatch`): the second of two racing PATCHes is refused with `ErrTenantConcurrentUpdate` instead of silently overwriting the first.
- **Tenant-suspension enforcement** (`tenant_service.go`'s `TenantService.Status`): `*TenantService` implements the optional `tenancy.TenantStatusResolver` interface (`go/tenancy/tenant_status.go`) structurally -- admin is its one real implementer, but the seam itself does not know admin exists. A host wires `tenancy.WithTenantStatusResolver(adminModule.Tenants())` into its own `tenancy.Middleware` call; once wired, a resolved tenant whose ledger `Status` is `suspended` is refused with the coded `tenancy.tenant_suspended` error on the very next request against it, on every non-allowlisted route behind the host's `tenancy.Middleware` (other modules' routes included -- admin's own never sit behind that middleware to begin with). `WithAllowlist` beats the status gate exactly as it beats a resolution failure; the reference app allowlists every pre-auth entry, so a suspended tenant's users can keep signing in and refreshing tokens while non-allowlisted routes refuse. `Status` reports `active` (never `suspended`) for a tenant absent from the ledger entirely, so the ledger's own eventual-consistency lag can never turn into a false suspension; any other repository failure propagates and the tenancy layer turns it into the coded 500 `tenancy.tenant_status_unavailable` rather than assuming the tenant is active. Unwired hosts see zero behavior change. Proven end to end against the real reference-app HTTP stack in `examples/reference-app/cmd/server/admin_flow_test.go`'s `TestAdminFlow_SuspendTenant_BlocksThenResumeAllows_EndToEnd`.
- **Impersonation pipeline** (`model.go`'s `ImpersonationGrant`, `impersonation_repository.go`, `impersonation_service.go`, `pipeline.go`): a short-lived (`defaultGrantTTL`, a fixed 30-minute constant, no renewal operation), explicitly revocable authorization credential -- never a real authn access/refresh token minted for the target user. `POST/DELETE/GET /api/v1/admin/impersonation(/{id})` start, end and list grants. `ImpersonationMiddleware` (see "The impersonation request pipeline" below) substitutes the target user's identity for the rest of one request when a valid `X-Admin-Impersonation` grant id is presented, alongside the administrator's own still-verified access token. The five load-bearing properties -- the credential stays the administrator's own real token, permission checks downstream use the target's own Subject, the middleware fails closed on an invalid/expired/ended grant, every record produced for the request carries the dual identity (Actor target, OnBehalfOf administrator), and the mandatory non-unsubscribable security notification fires once at grant start -- are each pinned by a real test (see "Testing"). Ending a grant early (operator `DELETE`, or the automatic permission-revocation end below) goes through the same guarded write (`ImpersonationRepository.SaveGuarded`, refusing `ErrImpersonationGrantEnded` when two ends race).
- **Cross-tenant user search** (`search.go`): `authn.Service.SearchUsers` does the identity lookup behind `GET /api/v1/admin/users`, and `SearchService.MembershipsOf` composes the membership half behind `GET /api/v1/admin/users/{id}/memberships` by looping over every tenant in admin's own ledger and calling `org.MemberService.Get` once per candidate tenant. Both halves run under `tenancy.WithSystemContext` grants named by the shared `SystemPurposeAdminCrossTenant` purpose, so every operator-performed cross-tenant read leaves the audited `tenancy.system_context.entered` trail: `Users` under one platform-wide grant (authn's search has no tenant in scope at all), `MembershipsOf` under one grant per candidate tenant. No bypass method was added to `org` or `authn`. A per-tenant lookup failure for any reason other than "no membership" aborts the whole call rather than silently omitting a tenant.
- **Audit query and export** (`audit.go`, `export.go`): a thin HTTP shell over `compliance.AuditQuery.Query`/`QueryAcrossTenants`/`Get`. `GET /api/v1/admin/audit-events` translates its query parameters into `compliance.QueryFilter` -- including the `onBehalfOf` dimension, the impersonation-accountability read: it narrows to rows written during an impersonation session whose real administrator (the row's on-behalf-of identity, never its actor, since the impersonated user is the actor on such a row) is the named operator id -- paginates the result in Go, and serves each event's `changes` (the before/after diff) back, so the operator who wrote an impersonation reason can read it back for as long as the trail exists. The cross-tenant path's tenant list is drawn from the ledger plus the platform-level empty-string pseudo-tenant `QueryAcrossTenants` names. `POST /api/v1/admin/audit-events/export` enqueues one `go/jobs` task (`ExportService`, itself the registered `jobs.Handler`) rather than running `compliance.ExportService.Export` synchronously inside the request; the handler returns the enqueued job's id immediately, and the worker's `Handle` call marshals the completed export's outcome (object key, the minted `go/sharing` share id and its expiry) into the job's own `Result` -- deliberately never the one-time delivery token, a bearer credential that must not be persisted with the job record (see `export.go`'s `exportJobResult` doc comment). A partial export (`compliance.ErrExportPartialFailure`) is terminal handling, not a retryable error: the work already delivered, so `Handle` completes the job with the partial result recorded and an `admin.audit_export` event carrying `Success false` with the failing participants named. `compliance.AuditQuery` itself does no pagination -- an inherited, not re-solved, limitation.
- **Role management** (`role.go`): a thin wrapper over `rbac.Service`'s real `DefineRole`/`AssignRole`/`RevokeRole`/`RestoreRole`/`EnsureBuiltinRoles` plus the `DeclaredPermissions` read (the frozen permission-catalog snapshot `rbac`'s `Module.Attach` builds). `GET/POST /api/v1/admin/roles` and `POST /api/v1/admin/roles/{id}/bindings` are the HTTP surface; `RestoreRole` and `EnsureBuiltinRoles` are reachable at the `RoleService` level only (no HTTP route -- see "Known limitations"). `admin.role.assigned`/`admin.role.revoked` are deliberately not declared as this module's own audit actions: `rbac.AssignRole`/`RevokeRole` already publish their own domain events carrying the Actor this module's calls supply through `rbac.WithSubject`. Every tenant-naming write runs `checkTenantWritable` first: `rbac.SystemDomain` is refused outright with `ErrRolesSystemDomainForbidden` (see "The SystemDomain boundary" below).
- **Usage/billing dashboard** (`usage.go`): `GET /api/v1/admin/usage-summary`, a per-tenant stitch of `go/metering`'s `SummaryRepository.List` and `go/billing`'s `CreditService.Balance`/`SubscriptionService.Active` -- no new database table of its own. Read-only against `go/metering`'s tables and admin's own ledger, but not against `go/billing`'s credits ledger: the `Balance` leg materialises one zero-valued `billing_credit_balances` row per ledger tenant that has none yet (billing's own documented materialize-on-first-read contract), and that is the whole of what the GET writes. `go/metering` and `go/billing` are wired through independently **optional** `WithMetering`/`WithBilling` options: a host wiring neither gets `ErrUsageModulesNotWired`; a host wiring only one gets that module's dimension present on every row and the other's fields absent (`nil`), never a refusal. **Neither module is wired into the reference app itself** -- see "Known limitations".
- **Notification send-record search** (`send_records.go`): `GET /api/v1/admin/notifications/send-records`, wrapping `notification.SendRecordRepository.ListByFilter` (filtering by tenant/channel/status/time-range, newest-first). A named `tenantId` is the single-tenant path (one system-context grant around one call); an absent one is the cross-tenant path, looping every ledger tenant under the same audited mechanism and concatenating in ledger order.

**The SystemDomain boundary**: every `admin:*` permission is evaluated in `rbac.SystemDomain`, the platform-operations pseudo-tenant whose role catalog is the platform's internal domain. The boundary is closed on both halves: a grant may not be SCOPED to the system domain as an impersonation target (`ErrImpersonationTargetForbidden`) and roles or bindings may not be WRITTEN into it through the role surface (`ErrRolesSystemDomainForbidden`, enforced by `checkTenantWritable`) -- the role catalog is single and global with no domain partitioning, and no permission in the catalog is fine-grained enough to separate "may manage a customer tenant's roles" from "may delegate platform-operator authority". Hosts administer system-domain roles and bindings out of band, directly against `rbac.Service` under a system-tenant context, the shape the reference app's `seedDemoPlatformStaff` takes.

## Wiring contract

`admin.NewModule(db *gorm.DB, opts ...Option)` never touches the database; `db` is opened and migrated by the host before `Bootstrap` ever calls `Register`, exactly like every other module. Five options are **mandatory** -- `Register` refuses to proceed (before declaring anything) without each, each with its own named error:

- `WithAuthn(*authn.Module)` -- not `*authn.Service` directly. `authn.Module.Service()` is documented nil until authn's own `Register` has built it, and admin's own `Register` reads `authnModule.Service()` lazily, at Register time, never at option-application time (which runs before `Bootstrap`). This is why `Module.DependsOn()` returns `[]string{"authn"}` -- the one real registration-order dependency this module has; every other runtime read (`orgModule.Members()`, `complianceModule.AuditQuery()`, `notificationModule.Deliveries()`) is safe regardless of order, because each of those three values is built inside its own module's `NewModule` constructor, not its `Register`.
- `WithOrg(*org.Module)` -- the search path's membership composition and the ledger's event subscription both need it.
- `WithCompliance(*compliance.Module)` -- the audit-query HTTP shell has no read path, and the export leg has no manifest to gather, without one. The host constructs this with the same `*audit.Repository` (over the same database connection) its own `dbkit/audit` wiring already uses, and typically also wires `compliance.WithSharing(...)` itself so `ExportService.Export` can actually deliver -- admin does not require that of the host, but the export job fails at `Handle` time with `compliance.ErrSharingRequired` if the host's own `compliance.Module` was never given one.
- `WithNotification(*notification.Module)` -- the mandatory impersonation-started security notification has no transport without one, and the send-record search reads through `notificationModule.Deliveries().SendRecords()`.
- `WithQueue(queue jobs.Queue)` -- the audit-export leg enqueues onto it (`reg.Jobs.Handle(jobTypeAuditExport, ...)`); `compliance.ExportService.Export` gathers, stores and delivers a tenant's complete audit export in one call, which must never run synchronously inside an HTTP request.

Two further options are **optional**: `WithMetering(*metering.Module)` and `WithBilling(*billing.Module)`, independently. Neither missing option fails `Bootstrap`; `UsageService.Summary` instead answers with that dimension absent from every row, refusing outright (`ErrUsageModulesNotWired`) only when both are missing -- a dashboard with nothing to stitch is a wiring gap, while one with a single dimension is a partial answer.

`rbac.Service` is wired through neither shape above. `Module.AttachRBAC(svc *rbac.Service)` is a distinct method the host calls once, POST-Bootstrap, immediately after its own `rbacModule.Attach(registry)` succeeds: `rbac.Service` exists only after that call, which must run strictly after `Bootstrap` returns because `Attach` freezes the permission catalog once every module has registered -- so a construction-time option could never hand admin a usable service at the one point (Register) admin could read it. Both `RoleService` (`Module.Roles()`) methods and `ImpersonationService.Start` (`Module.Impersonation()`) fail closed with `ErrRBACServiceRequired` until `AttachRBAC` has been called -- `Start`'s gate keeps impersonation grants from being born while the automatic permission-revocation end that must be able to cut them off cannot run (see below).

admin sits at the top of the module dependency graph, so unlike most business modules it is explicitly permitted to import the concrete packages of every module below it directly (`go/authn`, `go/org`, `go/rbac`, `go/tenancy`, `go/compliance`, `go/notification`, `go/metering`, `go/billing`, `go/jobs`, `go/dbkit`, `go/pkgcore`, `go/observability`) rather than through a structurally-typed, no-import seam. It still must not create a cross-module foreign key or hand-write another module's tenant filter; every cross-tenant read goes through `tenancy.WithSystemContext` plus the downstream module's own existing method.

### The impersonation request pipeline

The fixed middleware chain is `authn.Middleware -> tenancy.Middleware(authn.NewPrincipalResolver())`. Impersonation inserts `admin.ImpersonationMiddleware(impersonationSvc)` between the two, never reordering the chain itself:

```go
authn.Middleware(verifier)(
    admin.ImpersonationMiddleware(adminModule.Impersonation())(
        tenancy.Middleware(authn.NewPrincipalResolver())(mux), // trailing ...Option args, if any, are unaffected
    ),
)
```

It is an ordinary `net/http` middleware, not a `tenancy.Resolver` decorator, because `tenancy.Resolver.Resolve` returns a bare `(pkgcore.TenantID, error)` and `tenancy.Middleware`'s only side effect is `pkgcore.WithTenant` -- a decorated Resolver could change which tenant is injected but has no channel to swap which USER the rest of the pipeline believes it is talking to. The middleware reads the real `authn.Principal` from the request context, checks the `X-Admin-Impersonation` header against the grant store, and on a valid, unexpired, non-ended grant substitutes an `authn.Principal` naming the target user and target tenant for everything downstream.

A request carrying no header, or one naming a grant that is missing/expired/ended/belongs to a different administrator, passes through completely unmodified -- the fail-closed contract `ImpersonationMiddleware`'s doc comment and `pipeline_test.go` both pin. A grant is honored only when its `AdminUserID` matches the current request's own verified Principal, so a leaked or guessed grant id is useless to any other administrator.

The substituted principal deliberately carries nothing that belongs to the administrator's own session: its `SessionID` is the GRANT's id (authn's session lifecycle keys on a session id alone, so inheriting the administrator's would let an impersonated request sign the administrator out of their own console session), and its `AMR` is empty (the administrator's authentication methods describe how the ADMINISTRATOR proved themselves -- inheriting them would let an administrator's own second factor satisfy an MFA gate as the target). Display names are deliberately not resolved at this layer: the middleware performs no user-record lookup of its own, so context actors stay id-only here; the impersonation audit events themselves -- `admin.impersonation.started`/`ended` -- are produced by `ImpersonationService.recordAudit`, which resolves both names against the users table at record time.

The middleware sets `pkgcore.WithActor(target)` + `pkgcore.WithOnBehalfOf(admin)` on the substituted context, so every audit record produced for the rest of the request -- admin's own explicit `Emit` calls and any other module's automatic write capture or explicit `Emit` alike -- carries the dual identity with no further wiring. `ImpersonationMiddleware` sits between `authn.Middleware` and `tenancy.Middleware` in the fixed chain, so an impersonated request still resolves a tenant context; admin's own routes are gated externally (an `rbac.RequirePermission` wrap in `rbac.SystemDomain`, mirroring how the reference app gates notes and storage) and deliberately never sit behind `ImpersonationMiddleware`.

### Start's validate-and-notify pass

`ImpersonationService.Start` refuses with `ErrImpersonationNotWired` when `Module.Register`'s attach has not run (the pre-Register window, reachable through the public `Module.Impersonation()` getter before `Bootstrap`), and with `ErrRBACServiceRequired` when `AttachRBAC` has not run; the service constructor is unexported, so `NewModule` is the only sanctioned path to a service. Every other validation (empty reason, missing target, self-targeting, a `rbac.SystemDomain` target, a target with no authn account, a target holding no membership in the target tenant) happens before anything is written.

When the target checks pass, `Start` runs the mandatory, non-unsubscribable security notification pass (`NotificationTypeImpersonationStarted`, dispatched through the notification module, copy static with zero recipient-visible parameters) BEFORE the grant row is created, and refuses the whole call if the dispatch cannot be enqueued: a "mandatory" notification attempted only after the grant already succeeded could never be un-sent. The target's existence and locale are resolved from the users table (an explicit `StartInput.Locale` is trusted verbatim; otherwise the target's own `authn.User.Locale` is used, falling back to `authn.DefaultLocale`), and tenant membership is validated through `org.MemberService.Get` -- both under one cross-tenant system-context grant entered once per `Start` call, so no second, needless `tenancy.system_context.entered` record is published. A fresh per-start `OccurrenceID` accompanies each dispatch so notification's derived delivery key treats every start as its own delivery instead of deduping it into the previous start's record.

### The automatic permission-revocation end

A live grant must not outlive its administrator's `admin:impersonate` permission. `ImpersonationService` subscribes to rbac's `EventRoleBindingRevoked` and `EventRoleChanged` (both published synchronously on the same reliable bus path rbac's own cross-replica cache invalidation uses) and re-verifies through a real `rbac.Service.Can` call -- never trusting the event alone, since the revoked binding may not have been the subject's only source of the permission -- before ending every affected live grant with the system named as `OnBehalfOf` (`systemEndedByReason`). This works only once `Module.AttachRBAC` has attached a real service, which is why `Start` refuses to let a grant be born before then; the two event-side review paths Warn rather than silently skip should an event reach them in that state.

### The tenant-ledger Status vocabulary

The ledger's `Status` column is typed with `go/tenancy`'s own `TenantStatus`; `TenantService.Status` returns a stored value as-is, with no translation between the ledger and the seam. The seam's own gate refuses any status other than `tenancy.TenantStatusActive` by default, so a future third ledger state a tenant must not be served under (an archived tenant, say) refuses automatically once declared as a `tenancy.TenantStatus` value, with no code change in this module; serving traffic under a new state requires the deliberate widening of `go/tenancy`'s own check, which is where that decision belongs. Consumers referencing an admin-local `TenantStatus` type or its constants use `tenancy.TenantStatus`/`tenancy.TenantStatusActive`/`tenancy.TenantStatusSuspended` instead; the persisted wire strings and admin's HTTP surface are unchanged.

## Data model

Two platform-data tables (`dbkit.AssertNotTenantScoped`, never `dbkit.TenantScoped`), both written through `dbkit.Open()`'s plain `*gorm.DB` directly -- never `dbkit.Repository[T]`:

- `admin_tenants` (`Tenant`): `tenant_id` (PK), `display_name`, `status` (`active`/`suspended`), `suspended_reason`, `suspended_at` (nil means not currently suspended -- derived from the `Status` transition by `TenantRepository.Update`, never a caller-supplied value), `created_at`, `created_by` (empty on the event-driven path), `notes`.
- `admin_impersonation_grants` (`ImpersonationGrant`): `id` (PK, a random 128-bit hex credential, never derived from `admin_user_id`/`target_user_id`), `admin_user_id`, `target_user_id`, `target_tenant_id`, `reason` (required, itself part of the audit trail), `created_at`, `expires_at`, `ended_at`/`ended_by` (nil/empty until explicitly ended).

## HTTP surface

`go/admin/api/openapi.yaml` is the module's own OpenAPI fragment, generated by pinned oapi-codegen v2.8.0 into a committed `admin-server.gen.go`, implemented by `Handler` behind a `var _ api.ServerInterface` compile-time assertion. The fragment is a registered member of `tools/api_fragments.json` and runs in the Taskfile `api:gen` task and the api-contract pipeline's regenerate-then-porcelain-gate enforcement. Every route requires an `rbac.SystemDomain` permission and does not go through ordinary `tenancy.Middleware` tenant resolution -- these are platform-operations routes about tenants, not routes scoped to one. `Handler` resolves the calling operator's identity from `authn.PrincipalFromContext` (`callerUserID`), never from a request parameter, header or body, and every write path attributes that operator on its audit event.

## Known limitations

- **The usage-summary GET performs one documented write.** Its billing leg reads balances through `billing.CreditService.Balance`, whose documented materialize-on-first-read contract creates one zero-valued `billing_credit_balances` row per ledger tenant that has none yet -- nothing for a tenant that already has a row, nothing on any other table, nothing further on a repeated summary (`usage.go`'s doc comments state this consequence exactly). A write-free dashboard needs a `go/billing` balance read that answers "no row" without first creating one; `CreditService.Transactions` reads the credit-transaction ledger, not the balance, and `Balance` is the only balance read billing's composed surface exposes.
- **Audit-query pagination is Go-side slicing over an already-fully-materialized result**, inherited from `compliance.AuditQuery`'s identical limitation -- not re-solved here. The send-record search inherits the identical shape: `Limit`/`Offset` apply per tenant, not to the concatenated cross-tenant result as a whole.
- **The impersonation grant's TTL is a fixed constant, not configurable** through `go/config`. The automatic permission-revocation end closes a live grant immediately when its administrator's `admin:impersonate` permission is revoked; the fixed TTL remains the outer bound for every other way a grant could outlive its administrator's actual authority.
- **No rate limiting or anomaly detection on impersonation** (an administrator starting many grants in a short window). This is `observability`/`compliance` territory, outside admin's own surface.
- **`go/metering` and `go/billing` are not wired into the reference app**, and the usage-dashboard surface carries the same three compensating obligations `go/pki`'s "X.509 layer: still no real consumer" section records for its own unconsumed layer: (1) a compiled, executed godoc `Example` naming the real read path (`usage_example_test.go`'s `ExampleUsageService_Summary`, whose pinned `Output` can only come from what metering's own `SummaryRepository.List` actually returned); (2) this limitation, stated plainly -- `UsageService` is real and tested against real `metering.Module`/`billing.Module` instances, but the reference app's own `cmd/server/server.go` does not construct either module, so in that app the usage-summary route answers 500 `ErrUsageModulesNotWired`; and (3) a deliberately unfrozen API -- the usage-dashboard surface is explicitly not covered by the codebase's public-API-as-frozen rule, since no production host has ever wired it: the first real consumer's integration may change `UsageService.Summary`'s signature, `UsageSummaryRow`'s field shape, or the `/api/v1/admin/usage-summary` operation's request/response shapes without that being a design failure.
- **`RestoreRole` and `EnsureBuiltinRoles` expose no HTTP route.** Both are real, tested `RoleService` methods (mirroring `rbac.Service`'s own real methods), reachable at the Service level only -- the identical posture `org.TreeService.Restore` already has.
- **Downstream audit capture rows during an impersonated request stay id-only.** Neither a user-lookup seam on `ImpersonationMiddleware` nor display names snapshotted onto the grant row at Start time exists; the impersonation's own events resolve both names at record time (see `pipeline.go`'s middleware doc comment).
- **The export leg's download link cannot be relayed through admin itself.** `Enqueue` returns only the job id; the one-time delivery token is never persisted with the job record, and no admin surface provides the synchronous channel over which a caller could receive the token to hand its recipient (see `export.go`'s `exportJobResult` doc comment).
