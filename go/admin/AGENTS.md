# admin

go/admin is the operations-console backend: the platform-staff-facing operations surface over capabilities that already live in every other module. This file is the module-level discipline that ships with `go/admin` to consuming projects; the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

## Scope

**In scope:**

- **Tenant ledger** (`model.go`'s `Tenant`, `tenant_repository.go`, `tenant_service.go`): a platform-data table (`admin_tenants`, `dbkit.AssertNotTenantScoped`) recording which tenants the platform believes exist, an operator convenience and never the authoritative source of tenant existence. Populated two ways: `Module.Register` subscribes to org's real `org.node.created` event, and `TenantService.handleOrgNodeCreated` lazily creates an active, blank-`DisplayName` row the first time a tenant's ROOT node appears (`org.OrgNode.IsRoot()`'s real discriminator, `ParentID == ""` -- **not** node depth, verified against `go/org/model.go`); and manual CRUD through `POST`/`GET`/`PATCH /api/v1/admin/tenants`. `TenantService.SetStatus` records an explicit `admin.tenant.status_changed` audit event on every ledger edit. The ledger write path guards concurrent edits with a compare-and-set `UPDATE` (`TenantRepository.applyGuardedPatch`): the second of two racing PATCHes is refused with `ErrTenantConcurrentUpdate` instead of silently overwriting the first.
- **Tenant-suspension enforcement** (`tenant_service.go`'s `TenantService.Status`): `*TenantService` implements the `tenancy.TenantStatusResolver` interface (`go/tenancy/tenant_status.go`) structurally -- admin is its one real implementer, but the seam itself does not know admin exists, the identical no-import-in-either-direction shape `org.FeatureGate`/`rbac.SubtreeResolver` use. A host wires `tenancy.WithTenantStatusResolver(adminModule.Tenants())` into its own `tenancy.Middleware` call; once wired, a resolved tenant whose ledger `Status` is `suspended` is refused with the coded `tenancy.tenant_suspended` error on the very next request against it, on every non-allowlisted route behind the host's `tenancy.Middleware` (other modules' routes included -- admin's own never sit behind that middleware at all). `WithAllowlist` beats the status gate exactly as it beats a resolution failure, so a route the host allowlisted never enforces a suspension; the reference app allowlists every pre-auth entry (registration, all sign-in channels, token refresh, the social authorize/callback pair), so a suspended tenant's users can keep signing in and refreshing tokens, only non-allowlisted routes refusing. `PATCH /api/v1/admin/tenants/{id}` therefore has real teeth, with no additional admin route: the enforcement rides the host's own middleware wiring. `Status` reports `active` (never `suspended`) for a tenant absent from the ledger entirely, so the ledger's own eventual-consistency lag can never turn into a false suspension. Unwired hosts see zero behavior change -- the seam is entirely optional and off by default. Any other repository failure propagates and the tenancy layer turns it into the coded 500 `tenancy.tenant_status_unavailable` rather than assuming the tenant is active. Proven end to end against the real reference-app HTTP stack in `examples/reference-app/flowtests/admin_flow_test.go`'s `TestAdminFlow_SuspendTenant_BlocksThenResumeAllows_EndToEnd` (suspend, confirm refusal, resume, confirm success again).
- **Impersonation, the full pipeline** (`model.go`'s `ImpersonationGrant`, `impersonation_repository.go`, `impersonation_service.go`, `pipeline.go`): a short-lived (`defaultGrantTTL`, 30 minutes, no renewal), explicitly revocable authorization credential -- **never** a real authn access/refresh token minted for the target user. `POST/DELETE/GET /api/v1/admin/impersonation(/{id})` start, end and list grants. `ImpersonationMiddleware` (see "The impersonation request pipeline" below) substitutes the target user's identity for the rest of one request when a valid `X-Admin-Impersonation` grant id is presented, alongside the administrator's own still-verified access token. The five mandatory properties (credential unchanged, permission check uses the target's own Subject, fail-closed on an invalid/expired/ended grant, dual-identity audit via explicit `audit.Emit`, mandatory non-unsubscribable notification on start) are each pinned by a real test -- see "Testing" below. Ending a grant early (an operator `DELETE`, or the automatic permission-revocation end, whose machinery "Security and correctness properties" below describes) goes through the same guarded write (`ImpersonationRepository.SaveGuarded`, refusing `ErrImpersonationGrantEnded` when two ends race).
- **Cross-tenant user search** (`search.go`): `authn.Service.SearchUsers` does the identity lookup; `SearchService.MembershipsOf` composes the second half -- which tenants a user belongs to -- by looping over every tenant in the ledger above and calling `org.MemberService.Get` once per candidate tenant under a `tenancy.WithSystemContext` grant (the cross-tenant read mechanism, last bullet below). Both halves leave the audited system-context trail naming the platform operator who performed the read: `Users` (the search half) under one platform-wide grant -- authn's search has no tenant in scope at all -- and `MembershipsOf` under one grant per candidate tenant. No bypass method was added to `org`. Why the search half must leave the trail even though its downstream call needs no tenant-isolation escape hatch is argued in "Security and correctness properties" below.
- **Audit query and export** (`audit.go`, `export.go`): a thin HTTP shell over `compliance.AuditQuery.Query`/`QueryAcrossTenants`/`Get`, plus the export leg -- `POST /api/v1/admin/audit-events/export` enqueues one `go/jobs` task (`ExportService`, itself the registered `jobs.Handler`) rather than running `compliance.ExportService.Export` synchronously inside the request (long-running work never runs synchronously inside an HTTP request); the handler returns the enqueued job's id immediately, and the worker's `Handle` call marshals the completed export's object key plus its `go/sharing` delivery (share id and expiry -- deliberately never the one-time token, since a bearer credential must not be persisted with the job record, so it dies in `Handle`'s own frame instead; see `export.go`'s `exportJobResult` doc comment) into the job's own `Result`. A partial export (`compliance.ErrExportPartialFailure`) is terminal handling, not a retryable error: the work already delivered, so `Handle` completes the job with the partial result recorded and an `admin.audit_export` event carrying `Success false` with the failing participants named. `GET /api/v1/admin/audit-events` translates its query parameters into `compliance.QueryFilter` and paginates the result in Go (`compliance.AuditQuery` itself does no pagination -- an inherited known limitation, deliberately not re-solved here). Its `onBehalfOf` query parameter narrows the result to rows written during an impersonation session whose real administrator -- the row's on-behalf-of identity, never its actor, since the impersonated user is the actor on such a row -- is the named operator id: the impersonation-accountability read dimension that makes the dual-identity write side usable. The cross-tenant path's tenant list is drawn from the ledger plus the platform-level empty-string pseudo-tenant.
- **Role management** (`role.go`): a thin wrapper over `rbac.Service`'s `DefineRole`/`AssignRole`/`RevokeRole`/`RestoreRole`/`EnsureBuiltinRoles` plus `DeclaredPermissions` (exposing the frozen permission-catalog snapshot `Module.Attach` builds). `GET/POST /api/v1/admin/roles` and `POST /api/v1/admin/roles/{id}/bindings` are the HTTP surface (`RestoreRole`/`EnsureBuiltinRoles` are reachable at the `RoleService` level only, no HTTP route -- the identical posture `org.TreeService.Restore` has). `RoleService` is wired through a distinct, POST-BOOTSTRAP `Module.AttachRBAC(svc *rbac.Service)` call rather than a `WithXxx(*rbac.Module)` construction-time `Option` -- see "Wiring contract" below for why. Every tenant-naming write runs `checkTenantWritable` first: `rbac.SystemDomain` is refused outright with `ErrRolesSystemDomainForbidden` (see "Security and correctness properties" below). `admin.role.assigned`/`admin.role.revoked` are **not** declared as this module's own audit actions: `rbac.AssignRole`/`RevokeRole` already publish their own domain events, and `RoleService`'s wrapper calls them exactly as any other caller would -- the role-change trail belongs to rbac's own events.
- **Usage/billing dashboard** (`usage.go`): `GET /api/v1/admin/usage-summary`, a per-tenant stitch of `go/metering`'s `SummaryRepository.List` and `go/billing`'s `CreditService.Balance`/`SubscriptionService.Active` -- no database table of its own. The dashboard is read-only against `go/metering`'s and admin's own tables, but **not** against `go/billing`'s credits ledger: the `Balance` leg materialises one zero-valued `billing_credit_balances` row per ledger tenant that has none yet (billing's own documented materialize-on-first-read contract), and that one row per rowless tenant is the whole of what the GET writes (see "Known limitations"). `go/metering` and `go/billing` are wired through **optional** `WithMetering`/`WithBilling` options (unlike the mandatory wiring options): a host wiring neither gets `ErrUsageModulesNotWired` from `UsageService.Summary`; a host wiring only one gets that module's dimension present on every row and the other's fields absent (`nil`), never a refusal. See "Wiring contract" below for why these two are optional rather than mandatory. **Both are wired into the reference app**: `examples/reference-app/internal/app/server.go` constructs `go/metering` and passes `admin.WithMetering`/`admin.WithBilling` at its admin-module site, and the app's `go/ai-gateway` module construction records real usage into `go/metering` through the gateway's `UsageRecorder` seam, so `GET /api/v1/admin/usage-summary` answers 200 with real per-tenant data there (see "Known limitations"' consumer record).
- **Notification send-record search** (`send_records.go`): `GET /api/v1/admin/notifications/send-records`, wrapping `notification.SendRecordRepository.ListByFilter` (filtering by tenant/channel/status/time-range, ordered newest-first exactly like `repository.go`'s existing `ListForRecipient`). `tenantId` absent is the cross-tenant path (the cross-tenant read mechanism, looping every tenant in the ledger above); present is the single-tenant path, one direct call.
- **The cross-tenant read mechanism**, used by the impersonation notification dispatch, the user search AND its membership composition, the cross-tenant audit query, the usage dashboard and the cross-tenant send-record search alike: `tenancy.WithSystemContext(ctx, bus, pkgcore.SystemReason{Actor: operatorUserID, Purpose: SystemPurposeAdminCrossTenant})`, then the downstream module's own existing per-tenant method, looped in application code across however many tenants are relevant (or entered exactly once, around a single platform-wide call that has no tenant in scope at all -- the search half, whose audit record the wrapper itself is). `pkgcore.SystemReason` is `{Actor string; Purpose SystemPurpose; Ticket string}` -- `Actor` is a plain `string`, not a `pkgcore.Actor` struct, and there is no `Detail` field -- and every call passes the operator's user id as a bare string (`go/pkgcore/tenant.go`). Never a `ListAcrossTenants` bypass on any downstream module, never a second unscoped database connection. The wrapper is the audit record of a platform-operator cross-tenant read, whatever the downstream call's own mechanics: a downstream call that needs no tenant-isolation escape hatch must still leave the trail -- the search, which returns plaintext email and phone, is covered for exactly that reason (see "Security and correctness properties" below).

**Explicitly out of scope**: tenant-creation enforcement (the ledger stays a non-authoritative convenience by design), administrator operation dual-approval workflows, and platform-level rate-limiting/anomaly detection on admin actions (impersonation included) -- each a deliberate, documented exclusion, not an oversight.

## Wiring contract

`admin.NewModule(db *gorm.DB, opts ...Option)` never touches the database; `db` is opened and migrated by the host before the assembly ever calls `Register`, exactly like every other module. The following options are **mandatory** -- `Register` refuses to proceed (before declaring anything) without each:

- `WithAuthn(*authn.Module)` -- **not** `*authn.Service` directly. `authn.Module.Service()` is documented nil until authn's own `Register` has built it, and admin's own `Register` reads `authnModule.Service()` lazily, at Register time, never at option-application time (which runs before the assembly). This is why `Module.DependsOn()` returns `[]string{"authn"}` -- the one real registration-order dependency this module has; every other runtime read (`orgModule.Members()`, `complianceModule.AuditQuery()`, `notificationModule.Deliveries()`) is safe regardless of order, because each of those three is built inside its own module's `NewModule` constructor, not its `Register`.
- `WithOrg(*org.Module)` -- the membership composition and the ledger's event subscription both need it.
- `WithCompliance(*compliance.Module)` -- the audit-query HTTP shell has no read path, and the export leg has no manifest to gather, without one. The host constructs this with the SAME `*audit.Repository` (over the same database connection) its own `dbkit/audit` wiring already uses, and typically also wires `compliance.WithSharing(...)` itself so `ExportService.Export` can actually deliver -- admin does not require that of the host, but the audit-export job fails at `Handle` time with `compliance.ErrSharingRequired` if the host's own `compliance.Module` was never given one.
- `WithNotification(*notification.Module)` -- the mandatory impersonation-started security notification has no transport without one, and the send-record search reads through `notificationModule.Deliveries().SendRecords()`.
- `WithQueue(queue jobs.Queue)` -- the audit-export leg enqueues onto it (`reg.JobsSeat().Handle(jobTypeAuditExport, ...)`, mirroring `go/storage`'s and `go/notification`'s own `WithQueue`/`WithDeliveryQueue`); `compliance.ExportService.Export` gathers, stores and delivers a tenant's complete audit export in one call, which must never run synchronously inside an HTTP request.

Missing any of them fails the assembly with a named error (`ErrAuthnServiceRequired`, `ErrOrgModuleRequired`, `ErrComplianceModuleRequired`, `ErrNotificationModuleRequired`, `ErrQueueRequired`) -- the same "fail with a named missing seam" shape `org`'s `ErrEmailIndexerRequired` and `config`'s `ErrCipherRequired` use.

Two further options are **optional**, independently of each other: `WithMetering(*metering.Module)` and `WithBilling(*billing.Module)`. Neither is mandatory because admin must not force a host with no metering or billing dimension to stand up two modules purely so it can boot -- both are wired into the reference app (see "Scope"), but a host that wires only one, or neither, still boots. Neither missing option fails the assembly; `UsageService.Summary` instead answers with that dimension's row fields absent (`nil`) -- `MeteringSummaries`, `CreditBalance` and `ActiveSubscription` are present on a row only when their owning module is wired -- never fabricated, never a reason to refuse the whole call -- and refuses outright (`ErrUsageModulesNotWired`) only when BOTH are missing.

The `rbac.Service` seam is wired through neither shape above: `Module.AttachRBAC(svc *rbac.Service)` is a distinct method the host calls once, after the assembly, immediately after its own `rbacModule.Attach(registry)` succeeds. A construction-time `WithXxx(*rbac.Module)` `Option` cannot work for this one seam: `rbac.Service` is produced only by `rbacModule.Attach(reg)`, which by `go/rbac`'s own contract must run strictly AFTER the assembly returns (it freezes the permission catalog once every module has registered), while admin's own `Module.Register` runs DURING the assembly, a full cycle earlier -- calling `Attach` from inside `Register` would freeze the catalog before some other, later-registering module had its own turn to declare permissions (see `role.go`'s `RoleService` doc comment and `AttachRBAC`'s own for the full reasoning). Both `RoleService` (`Module.Roles()`) methods AND `ImpersonationService.Start` (`Module.Impersonation()`) fail closed with `ErrRBACServiceRequired` until `AttachRBAC` has been called -- Start's gate keeps impersonation grants from being born while the automatic permission-revocation end that must be able to cut them off cannot run.

admin sits at the top of the module dependency graph, directly above `compliance`, so unlike most business modules it is explicitly permitted to import the concrete packages of every module below it directly -- `go/authn`, `go/org`, `go/rbac`, `go/tenancy`, `go/compliance`, `go/notification`, `go/metering`, `go/billing`, `go/jobs`, `go/dbkit`, `go/pkgcore`, `go/observability` -- rather than through a structurally-typed, no-import seam. The one thing it must not do is create a cross-module foreign key or hand-write another module's `WHERE tenant_id = ?` filter; every cross-tenant read goes through the audited `tenancy.WithSystemContext` wrapper (the cross-tenant read mechanism, "Scope" above) plus the downstream module's own existing method.

### The impersonation request pipeline

The fixed middleware chain is `authn.Middleware -> tenancy.Middleware(authn.NewPrincipalResolver())` -- `authn.Middleware` installs the verified `authn.Principal`, and `tenancy.Middleware`'s only side effect is `pkgcore.WithTenant`: its `Resolver` seam is `Resolve(r *http.Request) (pkgcore.TenantID, error)`, a bare tenant id with no channel to also substitute which USER the rest of the pipeline believes it is talking to (`tenancy.Middleware` never touches the `authn.Principal`). Impersonation therefore inserts `admin.ImpersonationMiddleware(impersonationSvc)` between the two -- an ordinary `net/http` middleware that reads the real `authn.Principal` and calls `authn.WithPrincipal` to substitute one for the rest of the request -- never reordering the chain itself:

```go
authn.Middleware(verifier)(
    admin.ImpersonationMiddleware(adminModule.Impersonation())(
        tenancy.Middleware(authn.NewPrincipalResolver())(mux), // trailing ...Option args, if any, are unaffected
    ),
)
```

A request carrying no `X-Admin-Impersonation` header, or one naming a grant that is missing/expired/ended/belongs to a different administrator, passes through completely unmodified -- the fail-closed contract `ImpersonationMiddleware`'s doc comment and `pipeline_test.go` both pin. A valid grant substitutes an `authn.Principal` naming the target user and target tenant (the administrator's own `SessionID`/`AMR` carried over unchanged, so the credential remains the admin's own real, still-verified token) and sets `pkgcore.WithActor(target)` + `pkgcore.WithOnBehalfOf(admin)` on the context, so every audit record produced for the rest of the request -- admin's own explicit `Emit` calls and any other module's automatic write capture or explicit `Emit` alike -- carries the correct dual identity with no further wiring.

admin's OWN routes are gated the ordinary way (an `rbac.RequirePermission` wrap in `rbac.SystemDomain`, external to this module, mirroring how the reference app gates `notes`/`storage`) and do **not** sit behind `ImpersonationMiddleware` -- that decorator's effect is on the REST of the application's routes only.

### Tenant-suspension enforcement

`go/tenancy` carries one optional seam (`tenant_status.go`): `TenantStatusResolver` (`Status(ctx, tenant) (TenantStatus, error)`) and `WithTenantStatusResolver(r)`, a `tenancy.Middleware` `MiddlewareOption`. When wired, `Middleware` consults it immediately after resolving a request's tenant (before injecting it into context) and refuses with the coded `tenancy.tenant_suspended` (403) or `tenancy.tenant_status_unavailable` (500, on a resolver error) error rather than proceeding -- both fail-closed, matching `Resolver`'s own discipline; an allowlisted request that proceeds with no tenant at all never consults the resolver, since there is nothing to look up a status for. Unwired (the default) is a no-op.

`*TenantService` (`Module.Tenants()`) implements `TenantStatusResolver` structurally -- the seam itself carries no import of `go/admin` in either direction, the identical shape `org.FeatureGate`/`rbac.SubtreeResolver` use. A host wires `tenancy.WithTenantStatusResolver(adminModule.Tenants())` into its own `tenancy.Middleware(...)` call, entirely OUTSIDE this module (`Module.Register` does not touch `go/tenancy`'s `Middleware` at all -- it has no reason to, since the seam is consumed by the HOST's own request-pipeline construction, not by admin's routes, which never sit behind ordinary `tenancy.Middleware` to begin with). `TenantService.Status` reports `tenancy.TenantStatusActive` (never `tenancy.TenantStatusSuspended`) for a tenant absent from the ledger entirely, so the ledger's own eventual-consistency lag (a brand-new tenant whose lazy registration has not landed yet) can never read as a false suspension; any other repository failure propagates as a real error, which the tenancy-layer seam turns into the 500 refusal above rather than assuming the tenant is active on an unreachable ledger.

The ledger row's `Status` column is typed with `go/tenancy`'s own `TenantStatus` -- there is exactly one status vocabulary between the ledger and the seam, never an admin-local duplicate with a hand-written translation beside it, because a translation step between two vocabularies is where a future third state could silently fall through (a second vocabulary that answered "anything not suspended" as active would fail open). There is nothing to translate: `TenantService.Status` returns a stored value as-is, and the seam's own gate refuses anything other than `tenancy.TenantStatusActive` by default -- so a future third ledger state a tenant must not be served under (an archived tenant, say) refuses automatically once declared as a `tenancy.TenantStatus` value, with no code change in this module, and a state requests SHOULD flow for requires the deliberate widening of `go/tenancy`'s own check, which is where that decision belongs. Host code names the vocabulary through `tenancy.TenantStatus` / `tenancy.TenantStatusActive` / `tenancy.TenantStatusSuspended`; the persisted wire strings and admin's HTTP surface carry those same values.

## Data model

Two platform-data tables (`dbkit.AssertNotTenantScoped`, never `dbkit.TenantScoped`), both written through `dbkit.Open()`'s plain `*gorm.DB` directly -- never `dbkit.Repository[T]`, matching `go/authn`'s `users` table and `go/config`'s `row` precedent:

- `admin_tenants` (`Tenant`): `tenant_id` (PK), `display_name`, `status` (`active`/`suspended`), `suspended_reason`, `suspended_at` (nil means not currently suspended -- derived from the `Status` transition by `TenantRepository.Update`, never a caller-supplied value), `created_at`, `created_by` (empty on the event-driven path), `notes`.
- `admin_impersonation_grants` (`ImpersonationGrant`): `id` (PK, a random 128-bit hex credential, never derived from `admin_user_id`/`target_user_id`), `admin_user_id`, `target_user_id`, `target_tenant_id`, `reason` (required), `created_at`, `expires_at`, `ended_at`/`ended_by` (nil/empty until explicitly ended).

## HTTP surface

`go/admin/api/openapi.yaml` is the module's own OpenAPI fragment, generated by the pinned oapi-codegen v2.8.0 into a committed `admin-server.gen.go`, implemented by `Handler` behind a `var _ api.ServerInterface` compile-time assertion. The fragment is regenerated and porcelain-gated by the `api-contract.yml` pipeline on the backend side only -- like org's and storage's fragments, it is not among the fragments the frontend SDK merge consumes -- and its leg runs in `Taskfile.yml`'s `api:gen` task, with the fragment registered in `tools/api_fragments.json`'s manifest alongside the others. Every route requires an `rbac.SystemDomain` permission (`admin:access`, `admin:tenants_manage`, `admin:search_users`, `admin:impersonate`, `admin:audit_read`, `admin:audit_export`, `admin:roles_manage`, `admin:usage_read`, `admin:notifications_read`) and does **not** go through ordinary `tenancy.Middleware` tenant resolution -- these are platform-operations routes about tenants, not routes scoped to one. `Handler` resolves the calling operator's identity from `authn.PrincipalFromContext`, never from a request parameter, header or body.

| Method | Path | Feature |
|---|---|---|
| `GET`/`POST` | `/api/v1/admin/tenants` | Tenant ledger |
| `GET`/`PATCH` | `/api/v1/admin/tenants/{id}` | Tenant ledger; PATCH takes effect through `tenancy.WithTenantStatusResolver` (no dedicated suspension route) |
| `GET` | `/api/v1/admin/users` | Cross-tenant user search |
| `GET` | `/api/v1/admin/users/{id}/memberships` | Membership composition (cross-tenant read mechanism) |

| `DELETE` | `/api/v1/admin/impersonation/{id}` | Impersonation: end |

## Security and correctness properties

- **The impersonation-started notification is enforced before the grant exists.** `Start` runs its notification obligation (`notifyStarted`) BEFORE the grant row is ever created, and a failure to enqueue is a real, propagated error: `ErrImpersonationTargetNotFound` for an unresolvable target, `ErrImpersonationNotificationUnavailable` for every other resolution/system-context/dispatch failure. `Start` never returns success over a notification that could not even be enqueued -- the mandatory notice must never be silently skipped. What stays out of this module's hands is actual transport delivery: delivery, its retries and its eventual dead-lettering remain `notification`'s own asynchronous business, unobserved here, as for any other `Dispatch` caller. `StartInput.Locale` is resolved automatically when empty, through the notice's locale chain in `resolveNotificationLocale`: the target's own `authn.User.Locale` first (read through the mandatory `WithAuthn` seam, which `ImpersonationService.attach` carries among the host seams it wires -- the recipient's own value outranks every requester-supplied signal), then `StartInput.RequesterLanguage` (the starting administrator's request language, which the HTTP handler negotiates against the merged catalog and passes; a handler with no catalog attached passes "" and skips the tier), then `authn.DefaultLocale` when none of them resolves -- the identical terminal fallback `authn`'s own verification-code delivery already uses, for the identical reason: `notification.Dispatch`'s `validate()` refuses a `RecipientClassUser` delivery with an empty locale, so a caller omitting `locale` must not receive a 201 with the security notification silently never enqueued. An explicit `locale` is trusted verbatim. Pinned by `TestImpersonationService_ResolveNotificationLocale_Chain` and the end-to-end `TestImpersonationService_Start_RequesterLanguageTier_RendersTheNoticeInIt` (the notice's inbox row renders in the requester's language).
- **The notice leaks nothing about the operator to the impersonated user.** The impersonated user must never read the operator's free-text justification -- text that can name an active investigation of the suspected party -- or the administrator's identity. The notice's copy is static (its templates interpolate nothing), so `admin.impersonation_started`'s declaration marks ZERO recipient-visible params -- `RecipientVisibleParams: []string{}`, an explicit empty declaration, never the nil value, which in `go/notification`'s type carries the no-restriction meaning -- and the dispatch carries no `Params` at all; the reason and the administrator's identity stay in the grant row and the dual-identity audit trail, where the auditor, not the impersonated user, reads them -- `go/notification` persists `Dispatch.Params` verbatim into the recipient's inbox row and inbox API, so a notice whose dispatch carried the reason would hand the impersonated user the operator's own justification and identity. The declaration is enforced by `go/notification` itself: `Dispatch` refuses any parameter outside the declared set with `ErrDispatchParamsNotAllowed`, and the delivery path narrows stale in-flight payloads down to the declared set. The protection is doubly structural: the copy is static and the type's dispatch carries no `Params`, so even a future declaration slip could not ride a copy-inert parameter into the row -- go/notification's copy gate refuses parameters no template references. Nothing distinguishes one start's notice from the next in notification's derived delivery key (the content is identical), so each `Start` also draws a fresh `OccurrenceID` -- 16 random bytes hex-encoded by `newImpersonationNoticeOccurrenceID`, deliberately no credential -- and dispatches under notification's first-class "identical content, new occurrence" marker, which never renders and never persists, so the mandatory notice arrives once per simulated login as its own delivery instead of being deduped into the previous start's record. Both halves are pinned against real delivery: `TestImpersonationService_Start_NotificationParams_CarryNoInternalFields` (impersonation_service_test.go -- two real `Start` calls through a capturing notifier: no `Params`, the serialized dispatch embeds neither the reason text nor the administrator's id, and each start's `OccurrenceID` is fresh and distinct) and `TestImpersonationService_Start_NotificationRow_CarriesNoInternalParams` (impersonation_service_start_dispatch_test.go -- a real `Start` through the REAL `notification.DeliveryService` and queue handler, the notice's inbox row then read back through notification's own repository with empty params), while `module_test.go`'s declaration-shape test pins the empty list on the type itself.
- **The impersonation reason settles into the audit record, and the audit shell serves it back.** `recordAudit`'s started event carries the operator's `reason` in its `after` snapshot, next to `target_tenant_id` and `expires_at`, on the append-only dual-identity row, where it outlives the grant -- the reason is itself part of the audit: the only other grant read-back (`ListActive`) shows a grant just while it is active, so the justification an operator wrote must stay readable once the grant has ended. The audit shell (`GET /api/v1/admin/audit-events`) serves an event's `changes` back: `AdminAuditEvent` carries the before/after diff, so an operator can read why an impersonation happened from the same trail that says it happened, for as long as the trail exists. The read-back lives on the audit shell rather than as a grant-by-id endpoint because the started audit event is the designed, append-only record of every grant -- active or ended -- and the shell's changes element serves every audited action's diff, not one field of one resource. Pinned by `TestImpersonationService_Start_AuditChanges_CarryTheReason` (impersonation_service_test.go) and `TestHandler_AdminListAuditEvents_ServesChangesBackToTheOperator` (audit_test.go).
- **The audit shell filters by the on-behalf-of administrator.** `GET /api/v1/admin/audit-events` accepts an `onBehalfOf` query parameter, threaded identically to `actor` (generated `AdminListAuditEventsParams` -> `AuditFilter` -> `compliance.QueryFilter.OnBehalfOf`), narrowing the result to rows written during an impersonation session whose real administrator is the named operator id; the response rows carry that identity as `onBehalfOfId`/`onBehalfOfType`. An attribute that can only be written and never queried does not exist for accountability: an administrator who never appears as `actor` on an impersonation-era row must still be findable, and an endpoint that ignored the parameter would answer 200, looking complete while returning everything -- the silent-failure shape this behavior exists to exclude. Pinned end to end by `TestHandler_AdminListAuditEvents_FiltersByOnBehalfOf` (handler_test.go): four rows in one tenant -- two impersonation-era rows of admin-1, one of admin-2, one ordinary row -- and `?tenantId=...&onBehalfOf=admin-1` returns exactly the first two and no others.
- **The audit-export path attributes the calling operator.** Exporting a tenant's complete audit trail must leave a trace of itself in that same trail. `AdminExportAuditEvents` resolves the operator through `callerUserID` like every other write path and forwards it into `Enqueue`, which takes `operatorUserID` and refuses an empty one (`ErrExportOperatorRequired`) before anything reaches the queue; the identity travels inside the job's own payload (workers rebuild `ctx` from the job record alone and inherit nothing from the enqueuing request), and `Handle` records the `admin.audit_export` action, with the operator as `Actor`, once the export actually completes. This is a single-identity attribution, never `OnBehalfOf`: admin's own routes deliberately never sit behind `ImpersonationMiddleware` (see "The impersonation request pipeline" above), so `callerUserID` always names the real operator here, never a substituted impersonation target. Pinned by `export_test.go`'s `TestHandler_AdminExportAuditEvents_AttributesOperatorAndEmitsAuditAction`.
- **Cross-tenant user search leaves the audited trail on both of its halves.** The audited `tenancy.WithSystemContext` wrapper is the audit record of a platform-operator cross-tenant read, whatever the downstream call's own mechanics: a downstream call that needs no tenant-isolation escape hatch must still leave the trail, because the trail records who the platform operator is and what they read -- and the search half is the more sensitive read: it returns plaintext email and phone (columns encrypted at rest by authn's PII serializer, read out as plaintext Go strings), up to 200 rows, from a query that is truly platform-level, with no tenant in scope at all. The same rule is written generally in `send_records.go`'s doc comment -- a read of one tenant's records by a platform operator is exactly the cross-tenant operation the audited system-context mechanism exists to cover -- and applies to every platform-operator read, the user search among the most sensitive of them. `SearchService.Users` takes `actorUserID` -- the platform operator, never the searched-for user -- and runs the single `SearchUsers` call under one `tenancy.WithSystemContext` grant (`SystemPurposeAdminCrossTenant`), publishing exactly one `tenancy.system_context.entered` record per search. `handler.go`'s `AdminSearchUsers` resolves the operator from the verified Principal (`callerUserID`) like every other admin read of another module's data; an absent Principal is refused with `ErrPrincipalRequired`, the same answer the memberships route gives. `MembershipsOf` covers its per-candidate-tenant reads with one grant each, as the cross-tenant read mechanism prescribes. `module.go`'s `SystemPurposeAdminCrossTenant` doc comment enumerates the surfaces that read under this purpose. Pinned by `handler_test.go`'s `TestHandler_AdminSearchUsers_LeavesAuditedTrailNamingOperator` (the search answers 200 and exactly one system-context record lands carrying the OPERATOR as Actor under `SystemPurposeAdminCrossTenant`) and `search_test.go`'s `TestSearchService_Users_SearchLeavesAuditedSystemContext` at the service boundary.
- **The SystemDomain boundary holds on the granting side as well as the subject side.** The subject side: admin's routes evaluate `Subject{rbac.SystemDomain, caller}` only, and `ErrImpersonationTargetForbidden` refuses a grant SCOPED to the system domain as an impersonation target. The granting side: `rbac.SystemDomain` is the pseudo-tenant every admin:* permission is evaluated in -- an ordinary tenant-id string nothing branches on -- and the role catalog is single and global with no domain partitioning, admin's own admin:* permissions living inside it; a caller holding ONLY `admin:roles_manage` (a persona a reference host can genuinely create, since `/roles` is reachable with that one permission) could otherwise define a role carrying `admin:impersonate` -- or any admin:* -- in the system domain and bind it to themselves, collapsing the distinct admin:* permission boundaries into one. Every tenant-naming write in `RoleService` (`DefineRole`/`AssignRole`/`RevokeRole`/`RestoreRole`/`EnsureBuiltinRoles`) therefore runs `checkTenantWritable` first, which refuses `rbac.SystemDomain` with `ErrRolesSystemDomainForbidden` (`admin.roles_system_domain_forbidden`, an `apperr.Invalid` like its subject-side twin) before `rbac.Service` is ever reached -- unconditionally, mirroring `ErrImpersonationTargetForbidden`'s own rationale: no admin permission is fine-grained enough to separate "may manage a customer tenant's roles" from "may delegate platform-operator authority", so the only safe default is refusing the pseudo-tenant outright. SystemDomain's role catalog and bindings remain fully administrable out of band, directly against `rbac.Service` under a system-tenant context -- the shape the reference app's own `SeedDemoPlatformStaff` uses. Pinned by `role_test.go`'s `TestRoleService_SystemDomain_RolesManageOnlyCaller_CannotEscalate` (define refused, bind of an out-of-band-seeded powerful role refused, revoke/restore/ensure-builtin refused, `Can` false throughout) and `TestRoleService_RealTenant_RolesManageOnlyCaller_ManagesRolesStill` (the same caller runs the full lifecycle in a real tenant), with the refusal's wire code pinned as a literal (`rolesSystemDomainForbiddenCode`).
- **A live grant ends the moment its administrator's permission is revoked.** Grant validity is the grant row's own state -- `Lookup` checks `Active` and `AdminUserID`, never the administrator's current `rbac` permission -- so an administrator whose `admin:impersonate` is revoked mid-grant (through `rbac.RevokeRole`, or a role redefinition dropping the permission) must stop substituting the target's identity at revocation time, not at the grant's TTL expiry. The enforcement is event-driven rather than a per-request `rbac.Can` re-check inside `ImpersonationMiddleware` -- a per-request permission check on every impersonated request across the whole app would cost strictly more than this mechanism, which adds nothing to the request path at all. `ImpersonationService` subscribes to `rbac.EventRoleBindingRevoked`/`rbac.EventRoleChanged` (both published synchronously on the same reliable bus path `rbac`'s own cross-replica cache invalidation depends on) and re-verifies `rbac.Service.Can` -- never trusting the event alone, since a second granting role must keep the grant alive -- before ending every affected live grant, with `OnBehalfOf` recorded as `pkgcore.ActorTypeSystem` rather than the administrator. `Module.AttachRBAC` wires `ImpersonationService.attachRBAC` alongside `RoleService`'s own, under the same post-assembly-only timing constraint. And no grant can be born while that machinery is unattached: `ImpersonationService.Start` refuses with `ErrRBACServiceRequired` (the same named error `RoleService.require` answers on the identical seam) until `AttachRBAC` has run, and the two event-side review paths Warn instead of silently skipping should an event reach them in that state -- defense in depth, so the never-wired host's state stays visible rather than mute. Pinned by `TestImpersonationService_Start_BeforeAttachRBAC_Refused` and `TestImpersonationService_RoleRevokedBeforeAttachRBAC_Warns` (both in `impersonation_service_test.go`); the automatic end itself is pinned by `TestImpersonationService_Start_AdminRoleRevoked_LiveGrantAutomaticallyEnded` and its negative counterpart `TestImpersonationService_Start_AdminKeepsPermissionViaOtherRole_GrantSurvives` (both in `impersonation_service_start_dispatch_test.go`, against a real `rbac.Service` wired through `AttachRBAC`). The `rbac_service_required` bundle texts name both affected surfaces.
- **`Start` validates the target before any grant exists.** An explicit `StartInput.Locale` never bypasses the target's own `authn` lookup: `resolveNotificationLocale`'s existence check runs unconditionally whenever `authnSvc` is wired, reusing the one lookup, never a second. And a grant for a nonexistent or non-member target is never issued: `validateTargetMembership` (`org.MemberService.Get` under the same system-context grant the notification dispatch already needs) refuses a real-but-non-member target with `ErrImpersonationTargetNotMember`. Pinned by `TestImpersonationService_Start_TargetNotAMember_RefusedWithNoGrant`; the locale-resolution tests grant real membership, which the membership check requires of them.
- **A service exists only fully attached.** `ImpersonationService` construction is package-private (`newImpersonationService`): the only sanctioned path to a service is `NewModule`, whose `Register` always attaches the mandatory host seams -- authn target-existence and locale resolution, org membership validation, the notification transport. A service whose attach never ran would silently skip the entire validate-and-notify pass and write a grant row anyway, so `Start` fails closed with `ErrImpersonationNotWired` whenever attach has not run -- the pre-Register window, reachable through the public `Module.Impersonation()` getter before the assembly, is loud instead of silently degraded, mirroring `RoleService`'s own fail-closed `ErrRBACServiceRequired` contract before `AttachRBAC`. The per-seam nil tolerances inside the validate-and-notify pass exist only for the in-package unit-test shapes whose attach passes a subset of the seams; none is reachable through a public path. Pinned by `TestImpersonationService_Start_UnwiredService_Refused` (both legs -- pre-Register `Module.Impersonation()` and the bare repo-only constructor); `example_test.go`'s `Example()` documents the same fail-closed contract.
- **The end-state write paths refuse concurrent second writes.** `TenantRepository.Update` and `ImpersonationService.End` run their read-then-write under a conditional-UPDATE guard (`TenantRepository.applyGuardedPatch`, `ImpersonationRepository.SaveGuarded` -- the same idiom `go/notification/send_record.go`'s own `SaveGuarded` uses): of two racing writes on one shared snapshot -- a suspend racing a resume, or two `End` calls on one grant -- the second is refused (`ErrTenantConcurrentUpdate`, `ErrImpersonationGrantEnded`) rather than silently winning with a stale read or double-recording `admin.impersonation.ended`.
- **A failed `DisplayName` lookup in the usage summary is never silent.** `UsageService.Summary`'s per-row `DisplayName` resolution Warn-logs a lookup failure rather than leaving an unexplained blank name with no signal anywhere -- and never aborts the whole call, since `DisplayName` is cosmetic.
- **Handler decode failures report a decode error, not a missing field.** Six handler sites wrap a raw `json.Decode` failure (malformed JSON, a field of the wrong wire type) in `ErrRequestBodyInvalid`; the field-specific codes (`admin.tenant_id_required`, and `admin.impersonation_target_required` for `AdminStartImpersonation`) are reserved for an actually-missing field after a successful decode -- a caller must not be told a specific field was missing when the body did not decode.

## Known limitations

- **The usage-summary GET performs one documented write.** Its billing leg reads balances through `billing.CreditService.Balance`, whose documented materialize-on-first-read contract (`go/billing/credit_service.go`) creates one zero-valued `billing_credit_balances` row per ledger tenant that has none yet -- nothing for a tenant that already has a row, nothing on any other table, nothing further on a repeated summary (`usage.go`'s doc comments state this consequence exactly, so the claim and the call agree). What would remove the write entirely is a `go/billing` balance read that answers "no row" for a tenant that has never touched credits without first creating that row: `CreditService.Transactions` reads the credit-transaction ledger, not the balance, and `Balance` is the only balance read billing's composed surface exposes -- so a write-free dashboard is a recorded `go/billing` API gap, not something this module can do alone.
- **Audit-query pagination is Go-side slicing over an already-fully-materialized result**, inherited from `compliance.AuditQuery`'s own identical, documented limitation -- not re-solved here. The cross-tenant send-record search inherits the identical shape: `Limit`/`Offset` apply PER TENANT, not to the concatenated cross-tenant result as a whole.
- **The impersonation grant's TTL (30 minutes) is a fixed constant, not configurable** through `go/config` -- the automatic permission-revocation end closes a live grant immediately when its administrator's `admin:impersonate` permission is revoked, rather than only at natural TTL expiry; the fixed TTL remains the outer bound for every OTHER way a grant might otherwise outlive its administrator's actual authority.
- **No rate limiting or anomaly detection on impersonation** (an administrator starting many grants in a short window) -- this is `observability`/`compliance` territory, outside admin's own surface.
- **The usage dashboard has a real consumer, with its API deliberately left unfrozen.** `examples/reference-app/internal/app/server.go` constructs a real `metering.Module` and passes `admin.WithMetering(meteringModule)`/`admin.WithBilling(billingModule)` at its admin-module site, and the rows the dashboard reads are fed for real because the app's `go/ai-gateway` module construction wires the gateway's `UsageRecorder` seam (`WithUsageRecorder`) to `meteringModule.Recorder()` -- the analytics-grade (fail-open) tier, the only one the seam's `Record(ctx, event)` shape can carry (the billing-grade `Enqueue` path demands the caller's own transaction handle) -- so every real consult/smilesim AI call folds its `ai.chat_tokens` usage into real `metering_usage_summaries` rows that `UsageService.Summary` then reads per tenant in the ledger. The composed answer -- 200 with the recorded usage present for the system-domain operator -- is pinned by `examples/reference-app/flowtests/usage_summary_flow_test.go` and by the usage-summary leg of `flowtests/admin_flow_test.go`'s reachability test. The dashboard's read path is documented by an executed godoc `Example` against a real `metering.Module` (see "Testing"), and `usage_test.go`'s wired tests execute the same path -- `TestUsageService_Summary_StitchesMeteringAndBilling` reads a real ingested row back through the same call. The API stays deliberately unfrozen: no production host has wired this surface and found a parameter it could not actually supply, so a breaking change in service of the first production integration remains explicitly permitted rather than a design failure. None of this changes the dashboard's one documented write (a zero-valued `billing_credit_balances` row per rowless ledger tenant, first item above), which the reference-app wiring inherits unchanged.
- **No HTTP route exists for `RestoreRole` or `EnsureBuiltinRoles`.** Both are real, tested `RoleService` methods (mirroring `rbac.Service`'s own real methods 1:1), reachable at the Service level only -- the identical posture `org.TreeService.Restore` has.
