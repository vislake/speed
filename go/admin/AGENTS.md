# admin

go/admin is the operations-console backend: the platform-staff-facing operations surface over capabilities that already live in every other module. This file is the module-level discipline that ships with `go/admin` to consuming projects; the design rationale is `docs/internal/23-admin.md`, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: round 2 of 2 landed** (docs/internal/23-admin.md section 8's own round split). Round 1 shipped D3 (the tenant ledger, event-driven lazy population plus manual CRUD), D5 in full (the impersonation pipeline), D6 (cross-tenant user search plus membership composition), and D7's read side (the audit-query HTTP shell). **Round 2** adds D4's enforcement half (suspending a tenant in the ledger now actually refuses requests against it, through a new optional `go/tenancy` seam), D8 (role management wrapping `rbac.Service`), D9 (the cross-tenant usage/billing dashboard, stitched from `go/metering`/`go/billing`, no new table), D10 (notification send-record search, wrapping a new `notification.SendRecordRepository` method) and D7's export leg (an asynchronous audit-event export through `go/jobs`, delivered through `go/sharing` via `compliance.ExportService`). Judge what exists by the code, not by this sentence.

## Scope

**In scope (round 1 + round 2, both landed):**

- **D3 -- tenant ledger** (`model.go`'s `Tenant`, `tenant_repository.go`, `tenant_service.go`): a platform-data table (`admin_tenants`, `dbkit.AssertNotTenantScoped`) recording which tenants the platform believes exist, an operator convenience and never the authoritative source of tenant existence. Populated two ways: `Module.Register` subscribes to org's real `org.node.created` event, and `TenantService.handleOrgNodeCreated` lazily creates an active, blank-`DisplayName` row the first time a tenant's ROOT node appears (`org.OrgNode.IsRoot()`'s real discriminator, `ParentID == ""` -- **not** node depth, a correction round 1 made against the design document's own initial assumption, verified against `go/org/model.go`); and manual CRUD through `POST`/`GET`/`PATCH /api/v1/admin/tenants`. `TenantService.SetStatus` records an explicit `admin.tenant.status_changed` audit event on every ledger edit.
- **D4 -- tenant-suspension enforcement** (`tenant_service.go`'s `TenantService.Status`): `*TenantService` implements the new `tenancy.TenantStatusResolver` interface (`go/tenancy/tenant_status.go`) structurally -- admin is its one real implementer, but the seam itself does not know admin exists, the identical no-import-in-either-direction shape `org.FeatureGate`/`rbac.SubtreeResolver` already use. A host wires `tenancy.WithTenantStatusResolver(adminModule.Tenants())` into its own `tenancy.Middleware` call; once wired, a resolved tenant whose ledger `Status` is `suspended` is refused with the coded `tenancy.tenant_suspended` error on the very next request against it, on every non-allowlisted route behind the host's `tenancy.Middleware` (other modules' routes included -- admin's own never sit behind that middleware to begin with) -- and `WithAllowlist` beats the status gate exactly as it beats a resolution failure, so a route the host allowlisted never enforces a suspension; the reference app allowlists every pre-auth entry (registration, all sign-in channels, token refresh, the social authorize/callback pair), so a suspended tenant's users can keep signing in and refreshing tokens, only non-allowlisted routes refusing -- `PATCH /api/v1/admin/tenants/{id}` therefore now has real teeth, with no new admin route of its own. `Status` reports `active` (never `suspended`) for a tenant absent from the ledger entirely, so the ledger's own eventual-consistency lag can never turn into a false suspension. Unwired hosts see zero behavior change -- the seam is entirely optional and off by default. Proven end to end against the real reference-app HTTP stack in `examples/reference-app/cmd/server/admin_flow_test.go`'s `TestAdminFlow_SuspendTenant_BlocksThenResumeAllows_EndToEnd` (suspend, confirm refusal, resume, confirm success again) -- the one round-2 deliverable with a genuinely observable behavior change in a live request pipeline, per this round's own brief.
- **D5 -- impersonation, the full pipeline** (`model.go`'s `ImpersonationGrant`, `impersonation_repository.go`, `impersonation_service.go`, `pipeline.go`): a short-lived (`defaultGrantTTL`, 30 minutes, no renewal), explicitly revocable authorization credential -- **never** a real authn access/refresh token minted for the target user (docs/internal/23-admin.md's D5 rejected-alternative rationale). `POST/DELETE/GET /api/v1/admin/impersonation(/{id})` start, end and list grants. `ImpersonationMiddleware` (see "The impersonation request pipeline" below) substitutes the target user's identity for the rest of one request when a valid `X-Admin-Impersonation` grant id is presented, alongside the administrator's own still-verified access token. The five mandatory properties (credential unchanged, permission check uses the target's own Subject, fail-closed on an invalid/expired/ended grant, dual-identity audit via explicit `audit.Emit`, mandatory non-unsubscribable notification on start) are each pinned by a real test -- see "Testing" below.
- **D6 -- cross-tenant user search** (`search.go`): `authn.Service.SearchUsers` (round 1's one purely-additive change to `go/authn`) does the identity lookup; `SearchService.MembershipsOf` composes the second half -- which tenants a user belongs to -- by looping over every tenant in admin's own D3 ledger and calling `org.MemberService.Get` once per candidate tenant under a `tenancy.WithSystemContext` grant (D2's mechanism, below). Both halves now leave D2's audited trail naming the platform operator who performed the read: `Users` (the search half) under one platform-wide grant -- authn's search has no tenant in scope at all -- and `MembershipsOf` under one grant per candidate tenant. No bypass method was added to `org`. The search half originally skipped the wrapper entirely (authorization was reasoned about, audit was not); the asymmetry inside D6 and its fix are recorded under "Security fix: D6's user search" below.
- **D7 -- audit query and export** (`audit.go`, `export.go`): a thin HTTP shell over `compliance.AuditQuery.Query`/`QueryAcrossTenants`/`Get` (round 1), plus round 2's export leg -- `POST /api/v1/admin/audit-events/export` enqueues one `go/jobs` task (`ExportService`, itself the registered `jobs.Handler`) rather than running `compliance.ExportService.Export` synchronously inside the request (root `CLAUDE.md`'s asynchronous-work discipline); the handler returns the enqueued job's id immediately, and the worker's `Handle` call marshals the completed export's object key plus its `go/sharing` delivery (share id and expiry -- deliberately never the one-time token, P1-B: a bearer credential must not be persisted with the job record, so it dies in `Handle`'s own frame instead; see `export.go`'s `exportJobResult` doc comment) into the job's own `Result`. `GET /api/v1/admin/audit-events` translates its query parameters into `compliance.QueryFilter` and paginates the result in Go (`compliance.AuditQuery` itself does no pagination -- an inherited, not a re-solved, known limitation). Its `onBehalfOf` query parameter (P2-1) narrows the result to rows written during an impersonation session whose real administrator -- the row's on-behalf-of identity, never its actor, since the impersonated user is the actor on such a row -- is the named operator id: the impersonation-accountability read dimension that makes the dual-identity write side usable. The cross-tenant path's tenant list is drawn from D3's own ledger plus the platform-level empty-string pseudo-tenant.
- **D8 -- role management** (`role.go`): a thin wrapper over `rbac.Service`'s already-real `DefineRole`/`AssignRole`/`RevokeRole`/`RestoreRole`/`EnsureBuiltinRoles` plus the new `DeclaredPermissions` (this round's one purely-additive change to `go/rbac`, exposing the frozen permission-catalog snapshot `Module.Attach` builds). `GET/POST /api/v1/admin/roles` and `POST /api/v1/admin/roles/{id}/bindings` are the HTTP surface (`RestoreRole`/`EnsureBuiltinRoles` are reachable at the `RoleService` level only, no HTTP route this round -- the identical posture `org.TreeService.Restore` already has). `RoleService` is wired through a distinct, POST-BOOTSTRAP `Module.AttachRBAC(svc *rbac.Service)` call rather than a `WithXxx(*rbac.Module)` construction-time `Option` -- see "Wiring contract" below for why. `admin.role.assigned`/`admin.role.revoked` remain **not** declared as this module's own audit actions: `rbac.AssignRole`/`RevokeRole` already publish their own domain events, and `RoleService`'s wrapper calls them exactly as any other caller would, so that division of responsibility (recorded as a round-1 decision) is unchanged.
- **D9 -- usage/billing dashboard** (`usage.go`): `GET /api/v1/admin/usage-summary`, a per-tenant stitch of `go/metering`'s `SummaryRepository.List` and `go/billing`'s `CreditService.Balance`/`SubscriptionService.Active` -- no new database table of its own. The dashboard is read-only against `go/metering`'s and admin's own tables, but **not** against `go/billing`'s credits ledger: the `Balance` leg materialises one zero-valued `billing_credit_balances` row per ledger tenant that has none yet (billing's own documented materialize-on-first-read contract), and that one row per rowless tenant is the whole of what the GET writes (P2-2 -- see "Corrections against the design document" item 6 and "Known limitations"). `go/metering` and `go/billing` are wired through **optional** `WithMetering`/`WithBilling` options (unlike the four round-1 mandatory seams): a host wiring neither gets `ErrUsageModulesNotWired` from `UsageService.Summary`; a host wiring only one gets that module's dimension present on every row and the other's fields absent (`nil`), never a refusal. See "Wiring contract" below for why these two are optional rather than mandatory. **Neither `go/metering` nor `go/billing` is wired into the reference app itself this round** -- see "Known limitations".
- **D10 -- notification send-record search** (`send_records.go`): `GET /api/v1/admin/notifications/send-records`, wrapping the new `notification.SendRecordRepository.ListByFilter` (this round's one purely-additive change to `go/notification`, filtering by tenant/channel/status/time-range, ordered newest-first exactly like `repository.go`'s existing `ListForRecipient`). `tenantId` absent is the cross-tenant path (D2's mechanism, looping every tenant in admin's own D3 ledger); present is the single-tenant path, one direct call.
- **D2 -- the cross-tenant read mechanism**, used by D5's notification dispatch, D6's user search AND membership composition, D7's cross-tenant query, D9's dashboard and D10's cross-tenant search alike: `tenancy.WithSystemContext(ctx, bus, pkgcore.SystemReason{Actor: operatorUserID, Purpose: SystemPurposeAdminCrossTenant})`, then the downstream module's own existing per-tenant method, looped in application code across however many tenants are relevant (or entered exactly once, around a single platform-wide call that has no tenant in scope at all -- D6's search half, whose audit record the wrapper itself is). Never a `ListAcrossTenants` bypass on any downstream module, never a second unscoped database connection. Why D6's two halves were ever treated differently, and why that was wrong, is answered under "Security fix: D6's user search" below: the wrapper is the audit record of a platform-operator cross-tenant read, whatever the downstream call's own mechanics -- a downstream call that needs no tenant-isolation escape hatch must still leave the trail, and the one D6 half that skipped it (the search) was the one returning plaintext email and phone.

**Explicitly out of scope, both rounds** (docs/internal/23-admin.md section 9): tenant-creation enforcement (D3's ledger stays a non-authoritative convenience by design), administrator operation dual-approval workflows, and platform-level rate-limiting/anomaly detection on admin actions (impersonation included) -- each a deliberate, documented exclusion, not an oversight.

## Corrections against the design document

docs/internal/23-admin.md's own closing line invites exactly this: if a downstream module's real signature has since drifted from what the document cites, the real code wins and the document should be corrected accordingly. Round 1 re-verified every cited signature against the real source before writing code against it, and found three real mismatches:

1. **The root-node discriminator is `OrgNode.ParentID == ""`, not node depth.** The document's D3 section describes `org` events without naming the exact field; round 1's own task brief speculated `Depth == 0`. `go/org/model.go`'s real `OrgNode.IsRoot()` is `func (n OrgNode) IsRoot() bool { return n.ParentID == "" }` -- `tenant_service.go`'s `handleOrgNodeCreated` uses that field, and `TestTenantService_HandleOrgNodeCreated_ChildNode_DoesNotRegister` is the regression test that would catch a reversion to depth.
2. **`pkgcore.SystemReason.Actor` is a plain `string`, not a `pkgcore.Actor` struct.** The document's D2 code sample writes `Actor: pkgcore.Actor{Type: ..., ID: staffID}`; the real declaration (`go/pkgcore/tenant.go`) is `SystemReason{Actor string; Purpose SystemPurpose; Ticket string}` -- no `Detail` field either (the document's sample also names one; the real third field is `Ticket`). Every `tenancy.WithSystemContext` call in this module passes the operator's user id as a bare string.
3. **D5's mechanism is a request-pipeline `http.Handler` middleware, not a `tenancy.Resolver` decorator.** The document describes `admin.ImpersonationAwareResolver` "wrapping" `authn.NewPrincipalResolver()`. The real `tenancy.Resolver` interface is `Resolve(r *http.Request) (pkgcore.TenantID, error)` -- a bare tenant id, with no channel to also substitute which USER the rest of the pipeline believes it is talking to (`tenancy.Middleware`'s only side effect is `pkgcore.WithTenant`; it never touches the `authn.Principal` `authn.Middleware` already installed). `pipeline.go`'s `ImpersonationMiddleware` is therefore an ordinary `net/http` middleware inserted between `authn.Middleware` and `tenancy.Middleware` in the chain, reading the real `authn.Principal` and calling `authn.WithPrincipal` to substitute one for the rest of the request -- see `ImpersonationMiddleware`'s own doc comment for the full reasoning. This satisfies every one of the document's actual requirements (the admin's own token is still what verified; neither `authn` nor `tenancy` learns admin exists) while matching what the real interfaces can express.

Round 2 found two further mismatches, both about wiring shape rather than a single signature:

4. **D8's `rbac.Service` cannot be wired through a `WithXxx(*rbac.Module)` construction-time `Option` the way authn/org/compliance/notification are**, even though the design document does not distinguish it from those four. `rbac.Service` is produced only by `rbacModule.Attach(reg)`, which by `go/rbac`'s own contract must run strictly AFTER `pkgcore.Kernel.Bootstrap` returns (it freezes the permission catalog once every module has registered). admin's own `Module.Register` runs DURING `Bootstrap`, a full cycle earlier -- calling `Attach` from inside it would freeze the catalog before some other, later-registering module had its own turn to declare permissions. The real wiring seam is `Module.AttachRBAC(svc *rbac.Service)`, a distinct call the host makes once, immediately after its own `rbacModule.Attach(registry)` succeeds -- see `role.go`'s `RoleService` doc comment and `AttachRBAC`'s own for the full reasoning. Every `RoleService` method fails closed with `ErrRBACServiceRequired` until then, rather than a nil-service panic, and so does `ImpersonationService.Start` since the P2-3 follow-up (see "Follow-up fixes"): the same attached service backs the automatic permission-revocation end of impersonation grants, and a grant born while it is unattached could silently outlive its administrator's `admin:impersonate`.
5. **D9's `go/metering`/`go/billing` wiring is deliberately OPTIONAL, not mandatory** the way the four round-1 seams are, and the design document does not say which. Making them mandatory would have forced the reference app -- which does not otherwise use either module yet (root `CLAUDE.md`'s own census: "no reference-app consumer yet" for both, as of this round) -- to stand up two modules purely so admin could boot, an integration scope far beyond D9's own "read-only aggregation over already-real per-tenant methods" brief. `WithMetering`/`WithBilling` are therefore independently optional `Option`s; `UsageService.Summary` refuses only when NEITHER is wired at all (`ErrUsageModulesNotWired`), and each row's `MeteringSummaries`/`CreditBalance`/`ActiveSubscription` fields are simply absent when their owning module was never wired, never fabricated and never a reason to refuse the whole call.
6. **D9's dashboard is not read-only against `go/billing`'s credits ledger, whatever the "read-only aggregation" phrase item 5 quotes from the design brief implies.** The billing leg of `UsageService.Summary` reads each tenant's balance through `billing.CreditService.Balance` -- the only balance read billing's composed surface offers -- and `Balance`'s own documented materialize-on-first-read contract (`go/billing/credit_service.go`) writes one zero-valued `billing_credit_balances` row for a ledger tenant that has no row yet. A `GET /api/v1/admin/usage-summary` therefore performs exactly one kind of write: one such row per rowless tenant, nothing for a tenant that already has a row, nothing on any other table, and nothing further when the same tenant is summarized again. `usage.go`'s doc comments and this file's D9 bullet state exactly this consequence, so the claim and the call agree (P2-2): "read-only" now qualifies only what is actually read-only -- go/metering's own tables and admin's own ledger. A genuinely write-free balance column would need a billing balance read that answers "no row" for a tenant that has never touched credits without first creating that row; billing exposes none today, and that gap is recorded under "Known limitations".

## Wiring contract

`admin.NewModule(db *gorm.DB, opts ...Option)` never touches the database; `db` is opened and migrated by the host before `Bootstrap` ever calls `Register`, exactly like every other module. Five options are **mandatory** -- `Register` refuses to proceed (before declaring anything) without each:

- `WithAuthn(*authn.Module)` -- **not** `*authn.Service` directly. `authn.Module.Service()` is documented nil until authn's own `Register` has built it, and admin's own `Register` reads `authnModule.Service()` lazily, at Register time, never at option-application time (which runs before `Bootstrap`). This is why `Module.DependsOn()` returns `[]string{"authn"}` -- the one real registration-order dependency this module has; every other runtime read (`orgModule.Members()`, `complianceModule.AuditQuery()`, `notificationModule.Deliveries()`) is safe regardless of order, because each of those three is built inside its own module's `NewModule` constructor, not its `Register`.
- `WithOrg(*org.Module)` -- D6's membership composition and D3's event subscription both need it.
- `WithCompliance(*compliance.Module)` -- D7's audit-query HTTP shell has no read path, and its export leg has no manifest to gather, without one. The host constructs this with the SAME `*audit.Repository` (over the same database connection) its own `dbkit/audit` wiring already uses, and (round 2) typically also wires `compliance.WithSharing(...)` itself so `ExportService.Export` can actually deliver -- admin does not require that of the host, but D7's export job fails at `Handle` time with `compliance.ErrSharingRequired` if the host's own `compliance.Module` was never given one.
- `WithNotification(*notification.Module)` -- D5's mandatory impersonation-started security notification has no transport without one, and (round 2) D10's send-record search reads through `notificationModule.Deliveries().SendRecords()`.
- `WithQueue(queue jobs.Queue)` (round 2) -- D7's export leg enqueues onto it (`reg.Jobs.Handle(jobTypeAuditExport, ...)`, mirroring `go/storage`'s and `go/notification`'s own `WithQueue`/`WithDeliveryQueue`); `compliance.ExportService.Export` gathers, stores and delivers a tenant's complete audit export in one call, which must never run synchronously inside an HTTP request (root `CLAUDE.md`'s asynchronous-work discipline).

Missing any of the five fails `Bootstrap` with a named error (`ErrAuthnServiceRequired`, `ErrOrgModuleRequired`, `ErrComplianceModuleRequired`, `ErrNotificationModuleRequired`, `ErrQueueRequired`) -- the same "fail with a named missing seam" shape `org`'s `ErrEmailIndexerRequired` and `config`'s `ErrCipherRequired` already use.

Two further options are **optional** (round 2, D9): `WithMetering(*metering.Module)` and `WithBilling(*billing.Module)`, independently -- see "Corrections against the design document" item 5 above for why these are not mandatory the way the five above are. Neither missing option fails `Bootstrap`; `UsageService.Summary` instead answers with that dimension absent from every row, refusing outright (`ErrUsageModulesNotWired`) only when BOTH are missing.

D8's `rbac.Service` is wired through neither shape above: `Module.AttachRBAC(svc *rbac.Service)` is a distinct method the host calls once, POST-Bootstrap, immediately after its own `rbacModule.Attach(registry)` succeeds -- see "Corrections against the design document" item 4 above for why a construction-time `Option` cannot work for this one seam. Both `RoleService` (`Module.Roles()`) methods AND `ImpersonationService.Start` (`Module.Impersonation()`) fail closed with `ErrRBACServiceRequired` until `AttachRBAC` has been called -- Start's gate (the P2-3 follow-up under "Follow-up fixes") keeps impersonation grants from being born while the automatic permission-revocation end that must be able to cut them off cannot run.

admin sits at the top of the module dependency graph (root `CLAUDE.md`'s own diagram: `... -> compliance -> admin`), so unlike most business modules it is explicitly permitted to import the concrete packages of every module below it directly -- `go/authn`, `go/org`, `go/rbac`, `go/tenancy`, `go/compliance`, `go/notification`, `go/metering`, `go/billing`, `go/jobs`, `go/dbkit`, `go/pkgcore`, `go/observability` -- rather than through a structurally-typed, no-import seam. The one thing it still must not do is create a cross-module foreign key or hand-write another module's `WHERE tenant_id = ?` filter; every cross-tenant read goes through D2's `tenancy.WithSystemContext` plus the downstream module's own existing method.

### The impersonation request pipeline

The fixed middleware chain (`docs/internal/01-architecture.md`) is `authn.Middleware -> tenancy.Middleware(authn.NewPrincipalResolver())`. Impersonation inserts `admin.ImpersonationMiddleware(impersonationSvc)` between the two, never reordering the chain itself:

```go
authn.Middleware(verifier)(
    admin.ImpersonationMiddleware(adminModule.Impersonation())(
        tenancy.Middleware(authn.NewPrincipalResolver())(mux), // trailing ...Option args, if any, are unaffected
    ),
)
```

A request carrying no `X-Admin-Impersonation` header, or one naming a grant that is missing/expired/ended/belongs to a different administrator, passes through completely unmodified -- the fail-closed contract `ImpersonationMiddleware`'s doc comment and `pipeline_test.go` both pin. A valid grant substitutes an `authn.Principal` naming the target user and target tenant (the administrator's own `SessionID`/`AMR` carried over unchanged -- property (a): the credential is still the admin's own real, still-verified token) and sets `pkgcore.WithActor(target)` + `pkgcore.WithOnBehalfOf(admin)` on the context, so every audit record produced for the rest of the request -- admin's own explicit `Emit` calls and any other module's automatic write capture or explicit `Emit` alike -- carries the correct dual identity with no further wiring.

admin's OWN routes are gated the ordinary way (an `rbac.RequirePermission` wrap in `rbac.SystemDomain`, external to this module, mirroring how the reference app gates `notes`/`storage`) and do **not** sit behind `ImpersonationMiddleware` -- that decorator's effect is on the REST of the application's routes only.

### Tenant-suspension enforcement (D4, round 2)

`go/tenancy` gained one new, optional seam this round (`tenant_status.go`): `TenantStatusResolver` (`Status(ctx, tenant) (TenantStatus, error)`) and `WithTenantStatusResolver(r)`, a new `tenancy.Middleware` `MiddlewareOption`. When wired, `Middleware` consults it immediately after resolving a request's tenant (before injecting it into context) and refuses with the coded `tenancy.tenant_suspended` (403) or `tenancy.tenant_status_unavailable` (500, on a resolver error) error rather than proceeding -- both fail-closed, matching `Resolver`'s own discipline; an allowlisted request that proceeds with no tenant at all never consults the resolver, since there is nothing to look up a status for. Unwired (the default), `Middleware`'s behavior is byte-for-byte unchanged from before this seam existed.

`*TenantService` (`Module.Tenants()`) implements `TenantStatusResolver` structurally -- the seam itself carries no import of `go/admin` in either direction, the identical shape `org.FeatureGate`/`rbac.SubtreeResolver` already use. A host wires `tenancy.WithTenantStatusResolver(adminModule.Tenants())` into its own `tenancy.Middleware(...)` call, entirely OUTSIDE this module (`Module.Register` does not touch `go/tenancy`'s `Middleware` at all -- it has no reason to, since the seam is consumed by the HOST's own request-pipeline construction, not by admin's routes, which never sit behind ordinary `tenancy.Middleware` to begin with). `TenantService.Status` reports `tenancy.TenantStatusActive` (never `tenancy.TenantStatusSuspended`) for a tenant absent from the ledger entirely, so D3's own eventual-consistency lag (a brand-new tenant whose lazy registration has not landed yet) can never read as a false suspension; any other repository failure propagates as a real error, which the tenancy-layer seam turns into the 500 refusal above rather than assuming the tenant is active on an unreachable ledger.

The ledger row's `Status` column is typed with `go/tenancy`'s own `TenantStatus` (P3-4's consolidation deleted the admin-local `admin.TenantStatus` duplicate and the hand-written translation beside it -- the pre-consolidation shape answered "anything not suspended" as active, the silent fail-open this one-type shape closes by construction: with no second vocabulary there is no translation step a future third state can fall through). There is nothing to translate between the ledger and the seam: `TenantService.Status` returns a stored value as-is, and the seam's own gate refuses anything other than `tenancy.TenantStatusActive` by default -- so a future third ledger state a tenant must not be served under (an archived tenant, say) refuses automatically once declared as a `tenancy.TenantStatus` value, with no code change in this module, and a state requests SHOULD flow for requires the deliberate widening of `go/tenancy`'s own check, which is where that decision belongs. Consumers that referenced the deleted `admin.TenantStatus` type or its constants must switch to `tenancy.TenantStatus` / `tenancy.TenantStatusActive` / `tenancy.TenantStatusSuspended`; the persisted wire strings and admin's HTTP surface are unchanged.

## Data model

Two platform-data tables (`dbkit.AssertNotTenantScoped`, never `dbkit.TenantScoped`), both written through `dbkit.Open()`'s plain `*gorm.DB` directly -- never `dbkit.Repository[T]`, matching `go/authn`'s `users` table and `go/config`'s `row` precedent:

- `admin_tenants` (`Tenant`): `tenant_id` (PK), `display_name`, `status` (`active`/`suspended`), `suspended_reason`, `suspended_at` (nil means not currently suspended -- derived from the `Status` transition by `TenantRepository.Update`, never a caller-supplied value), `created_at`, `created_by` (empty on the event-driven path), `notes`.
- `admin_impersonation_grants` (`ImpersonationGrant`): `id` (PK, a random 128-bit hex credential, never derived from `admin_user_id`/`target_user_id`), `admin_user_id`, `target_user_id`, `target_tenant_id`, `reason` (required), `created_at`, `expires_at`, `ended_at`/`ended_by` (nil/empty until explicitly ended).

## HTTP surface

`go/admin/api/openapi.yaml` is the sixth module fragment (after notes, org, authn, storage, notification), generated by the same pinned oapi-codegen v2.8.0 into a committed `admin-server.gen.go`, implemented by `Handler` behind a `var _ api.ServerInterface` compile-time assertion. This round wires the fragment into `.github/workflows/api-contract.yml`'s regenerate-then-diff gate (backend-only, mirroring org's and storage's own single-fragment entries) -- round 1's "neither Taskfile.yml's api:gen task nor this workflow includes this fragment yet" gap is closed on the CI side; `Taskfile.yml`'s own task list still does not name admin explicitly, a separate, smaller gap left for a future round (the same two-round split `go/pki`'s own Taskfile-then-CI gap closure took). Every route requires an `rbac.SystemDomain` permission (`admin:access`, `admin:tenants_manage`, `admin:search_users`, `admin:impersonate`, `admin:audit_read`, `admin:audit_export`, `admin:roles_manage`, `admin:usage_read`, `admin:notifications_read`) and does **not** go through ordinary `tenancy.Middleware` tenant resolution -- these are platform-operations routes about tenants, not routes scoped to one. `Handler` resolves the calling operator's identity from `authn.PrincipalFromContext`, never from a request parameter, header or body.

## Security fixes

Two real defects a peer-session audit found and a coordinator re-verified against `main` were closed in a module-internal security-fix round, both against this file's own "five mandatory properties" (D5) and "who exported which tenant, when" (D7's export leg) claims:

- **D5 property (e), the mandatory notification, was mandatory in name only.** `Start` forwarded an OPTIONAL request `locale` field straight into `notification.Dispatch`, whose `validate()` refuses a `RecipientClassUser` delivery with an empty `Locale`; `notifyStarted`'s failure was Warn-logged and swallowed, so a caller omitting `locale` got a 201 with the security notification silently never enqueued -- untested precisely because every existing test drove `Start` through a `fakeNotifier` that never ran the real `validate()`. Fixed: `StartInput.Locale` is now resolved automatically when empty -- `resolveNotificationLocale` reads the target's own `authn.User.Locale` through the already-mandatory `WithAuthn` seam (`ImpersonationService.attach` gained a fourth `*authn.Service` parameter), falling back to `authn.DefaultLocale` when the user has never chosen one, the identical fallback `authn`'s own verification-code delivery already uses for the identical reason. An explicit `locale` is still trusted verbatim. `notifyStarted` now runs BEFORE the grant row is ever created and its failure is a real, propagated error (`ErrImpersonationTargetNotFound` for an unresolvable target, `ErrImpersonationNotificationUnavailable` for every other resolution/system-context/dispatch failure) -- `Start` never again returns success over a notification that could not even be enqueued. What stays exactly as documented: actual transport delivery, its retries and its eventual dead-lettering remain `notification`'s own asynchronous business, unobserved here, as for any other `Dispatch` caller.
- **D7's export leg was the one admin write path attributing nobody.** `AdminExportAuditEvents` never called `callerUserID`, `ExportService.Enqueue`/`Handle` carried no operator identity into the job, and `Register` declared no `admin.audit_export` action -- exporting a tenant's complete audit trail left no trace of itself in that same trail, and a host's hand-maintained permission-gate table missing this one sub-path would let it run anonymously. Fixed: `AdminExportAuditEvents` now calls `callerUserID` like every other write path and forwards it into `Enqueue`, which now takes `operatorUserID` and refuses an empty one (`ErrExportOperatorRequired`) before anything reaches the queue; the identity travels inside the job's own payload (workers rebuild `ctx` from the job record alone and inherit nothing from the enqueuing request) and `Handle` records the new `admin.audit_export` action, with the operator as `Actor`, once the export actually completes. This is a single-identity attribution, never `OnBehalfOf`: admin's own routes deliberately never sit behind `ImpersonationMiddleware` (see "The impersonation request pipeline" above), so `callerUserID` always names the real operator here, never a substituted impersonation target.
Both fixes ship with tests reproducing the exact pre-fix defect (`impersonation_service_locale_test.go`'s real-dispatch scenarios; `export_test.go`'s `TestHandler_AdminExportAuditEvents_AttributesOperatorAndEmitsAuditAction`), each verified to fail to compile against the unfixed code.

## Security fix: the system-domain role surface (2026-09)

A reviewer line-verified escalation path through D8's role surface was closed in a module-internal round, the granting-side half of the SystemDomain boundary the two impersonation fixes above guarded on the subject side only:

- **D8's role surface let a roles_manage-only caller grant themselves every other admin:* permission.** `RoleService`'s tenant-naming writes (`DefineRole`/`AssignRole`/`RevokeRole`/`RestoreRole`/`EnsureBuiltinRoles`) took the tenant from the request and rejected only the empty string, so `rbac.SystemDomain` -- the pseudo-tenant every admin:* permission is evaluated in, an ordinary tenant-id string nothing branches on -- was accepted as an ordinary request tenant. The role catalog is single and global with no domain partitioning and admin's own admin:* permissions live in it, so a caller holding ONLY `admin:roles_manage` (a persona the reference host can genuinely create, since `/roles` is reachable with that one permission) could define a role carrying `admin:impersonate` -- or any admin:* -- in the system domain and bind it to themselves, collapsing the nine permission boundaries D1 draws into one. The subject-resolving side of this boundary was already closed (admin's routes evaluate `Subject{rbac.SystemDomain, caller}` only, and `ErrImpersonationTargetForbidden` refuses a grant SCOPED to the system domain as an impersonation target); the granting side was not. Fixed in `role.go`: every tenant-naming write now runs `checkTenantWritable`, which refuses `rbac.SystemDomain` with the new `ErrRolesSystemDomainForbidden` (`admin.roles_system_domain_forbidden`, `apperr.Invalid` like its twin) before `rbac.Service` is ever reached -- unconditionally, mirroring `ErrImpersonationTargetForbidden`'s own rationale: no admin permission is fine-grained enough to separate "may manage a customer tenant's roles" from "may delegate platform-operator authority", so the only safe default is refusing the pseudo-tenant outright. SystemDomain's role catalog and bindings remain fully administrable out of band, directly against `rbac.Service` under a system-tenant context -- the shape the reference app's own `seedDemoPlatformStaff` already uses, and the shape `impersonation_service_locale_test.go`'s two P2-3 tests were converted to after this fix caught them seeding their administrator's system-domain roles through `RoleService` itself. `role_test.go`'s `TestRoleService_SystemDomain_RolesManageOnlyCaller_CannotEscalate` pins the escalation end to end (define refused, bind of an out-of-band-seeded powerful role refused, revoke/restore/ensure-builtin refused, `Can` false throughout; it fails against the pre-fix code with the define succeeding), `TestRoleService_RealTenant_RolesManageOnlyCaller_ManagesRolesStill` pins the positive half (the same caller still runs the full lifecycle in a real tenant), and the refusal's wire code is pinned as a literal (`rolesSystemDomainForbiddenCode`) so the regression runs against the unfixed code that has no sentinel yet. One reference-app flow test, `TestAdminFlow_AuditExport_RequiresExportPermission`, carved its two probe roles through this now-refused HTTP path and needs a host-side conversion to direct `rbac.Service` seeding (a consumer-side change tracked separately); every other reference-app admin flow, including all business-tenant role management, is unaffected.

## Security fix: D6's user search -- the un-audited half of D6's own two halves (2026-09)

A frozen-criteria rescan found the asymmetry INSIDE D6, not between D6 and another decision: one design item, two halves, one of them audited and one not. The first half (`search.go`'s `Users`, behind `GET /api/v1/admin/users`) was "a thin passthrough" to `authn.Service.SearchUsers` whose doc reasoned only about authorization -- "the `admin:search_users` permission check is the HTTP handler's job, per D6" -- and said nothing about audit; the second half (`MembershipsOf`, the same D6) explicitly took `actorUserID`, its doc stating it "identifies the platform operator making this cross-tenant read, for `pkgcore.SystemReason.Actor` -- never the searched-for userID", walking `tenancy.WithSystemContext` per tenant. And the unaudited half is the more sensitive read: the search returns plaintext email and phone -- columns encrypted at rest by authn's PII serializer, read out as plaintext Go strings -- up to 200 rows, from a query that is truly platform-level ("with no tenant in scope at all"). The most forceful precedent was the codebase's own wording from P2-7's fix (`send_records.go`'s doc): "a read of one tenant's records by a platform operator is exactly the cross-tenant operation D2's audited system-context mechanism exists to cover" -- a rule written generally, implemented one instance at a time, with the missed instance MORE sensitive than the covered one (delivery metadata vs plaintext email plus phone).

**Why the two halves were ever treated differently** (the answer the fix writes into this file's D2 bullet too): D2's mechanism was understood by its escape-hatch framing -- a per-tenant `WithSystemContext` GRANT around a downstream tenant-scoped call that needed the grant. The search half performs no tenant-scoped downstream call at all: authn's `SearchUsers` is platform-wide by design and needs no escape hatch, so round 1 gave it no wrapper -- and the wrapper is also the audit record of the operator's cross-tenant read, which is exactly what the search half then lacked. The audit obligation does not track the downstream call's need for the grant; it tracks who the platform operator is and what they read, and it is discharged by the same audited wrapper whether the covered call is per-tenant (MembershipsOf) or one platform-wide call (the search).

**The fix** (`search.go`): `SearchService.Users` now takes `actorUserID` -- the platform operator, never the searched-for user -- and runs the single `SearchUsers` call under one `tenancy.WithSystemContext` grant (`SystemPurposeAdminCrossTenant`), publishing exactly one `tenancy.system_context.entered` record per search. `handler.go`'s `AdminSearchUsers` resolves the operator from the verified Principal (`callerUserID`) like every other admin read of another module's data; an absent Principal is refused with `ErrPrincipalRequired`, the same answer the memberships route already gave. `MembershipsOf` is byte-for-byte unchanged -- its audit behaviour stays exactly as it was. `module.go`'s `SystemPurposeAdminCrossTenant` doc now names both halves of D6 (and the round-2 users it had drifted from listing). Regressions: `handler_test.go`'s `TestHandler_AdminSearchUsers_LeavesAuditedTrailNamingOperator` drives the real composed HTTP handler -- the search answers 200 and exactly one system-context record lands carrying the OPERATOR as Actor under `SystemPurposeAdminCrossTenant`; against the unfixed code it fails at runtime with the search publishing zero records ("the search leaving no audit row"). `search_test.go`'s `TestSearchService_Users_SearchLeavesAuditedSystemContext` pins the same assertion at the service boundary (and fails to compile against the unfixed, operator-less signature, per this file's established fail-before convention for signature-changing fixes).

## Security fix: the impersonation-started notice leaks to its target (P1-2, 2026-09)

## Audit-read fix: the audit-events endpoint had no on-behalf-of filter (P2-1, 2026-09)

- **P2-1: `GET /api/v1/admin/audit-events` could not answer "what did this administrator do during their impersonation sessions?".** The impersonation audit hard rule is write-side compliant -- every impersonation-era row carries the impersonated user as `Actor` and the real administrator as `OnBehalfOf` (the dual-identity record, `pipeline.go`) -- but the hard rule's purpose is read-side accountability, and the endpoint's filter surface, like `compliance.QueryFilter` itself, stopped at `actor`. The response already carried `onBehalfOfId`/`onBehalfOfType` per row, but an attribute that can only be written and never queried does not exist for accountability -- and it failed SILENTLY: an administrator who never appears as `actor` on an impersonation-era row was unfindable, and the investigator's answer (200, no error, no warning) looked complete. The endpoint now accepts an `onBehalfOf` query parameter, threaded identically to `actor` (generated `AdminListAuditEventsParams` -> `AuditFilter` -> `compliance.QueryFilter.OnBehalfOf`; the compliance half has its own record in that module's `AGENTS.md`). The end-to-end regression `TestHandler_AdminListAuditEvents_FiltersByOnBehalfOf` (handler_test.go) drives the real composed handler with four rows in one tenant -- two impersonation-era rows of admin-1, one of admin-2, one ordinary row -- and pins that `?tenantId=...&onBehalfOf=admin-1` returns exactly the first two and no others; on the pre-fix code the request ignored the unknown parameter and answered 200 with all four rows, the silent-failure signature this fix exists to close.

## Known limitations

- **D9's usage-summary GET performs one documented write.** Its billing leg reads balances through `billing.CreditService.Balance`, whose documented materialize-on-first-read contract creates one zero-valued `billing_credit_balances` row per ledger tenant that has none yet -- nothing for a tenant that already has a row, nothing on any other table, nothing further on a repeated summary (P2-2; `usage.go`'s doc comments state this consequence exactly, so the claim and the call agree). What would remove the write entirely is a `go/billing` balance read that answers "no row" for a tenant that has never touched credits without first creating that row: `CreditService.Transactions` reads the credit-transaction ledger, not the balance, and `Balance` is the only balance read billing's composed surface exposes -- so a write-free dashboard is a recorded `go/billing` API gap, not something this module can do alone.
- **D7's audit-query pagination is Go-side slicing over an already-fully-materialized result**, inherited from `compliance.AuditQuery`'s own identical, documented limitation -- not re-solved here. D10's cross-tenant send-record search inherits the identical shape: `Limit`/`Offset` apply PER TENANT, not to the concatenated cross-tenant result as a whole.
- **The impersonation grant's TTL (30 minutes) is a fixed constant, not configurable** through `go/config` yet -- this bound now matters less than it used to, since the follow-up round above (P2-3) ends a live grant immediately when its administrator's `admin:impersonate` permission is revoked, rather than only at natural TTL expiry; the fixed TTL remains the outer bound for every OTHER way a grant might otherwise outlive its administrator's actual authority.
- **No rate limiting or anomaly detection on impersonation** (an administrator starting many grants in a short window) -- docs/internal/23-admin.md's section 9 defers this to `observability`/`compliance`, out of scope for admin itself in either round.
- **`go/metering` and `go/billing` are not wired into the reference app.** D9's `UsageService` is real and tested against real `metering.Module`/`billing.Module` instances (`usage_test.go`), but the reference app's own `cmd/server/server.go` does not construct either module or pass `admin.WithMetering`/`admin.WithBilling` -- a deliberate, documented exception mirroring `go/pki`'s X.509 layer and `go/billing`'s/`go/metering`'s own "no reference-app consumer yet" state (root `CLAUDE.md`'s census), rather than standing up two modules' worth of unrelated business wiring purely to satisfy this module's own mandatory-first-consumer rule for a usage dashboard (whose only write is the documented balance-row materialisation -- see "Corrections against the design document" item 6). Wiring them for real is a `go/billing`/`go/metering` decision (their own natural first caller is `go/ai-gateway`'s pay-per-use credit flow, per their own `AGENTS.md`), not admin's to make unilaterally.
- **`Taskfile.yml`'s `api:gen` task does not name `admin` explicitly.** This round closed the `.github/workflows/api-contract.yml` half of round 1's disclosed gap; the Taskfile half is a separate, smaller gap left for a future round (see "HTTP surface" above).
- **D8 exposes no HTTP route for `RestoreRole` or `EnsureBuiltinRoles`.** Both are real, tested `RoleService` methods (mirroring `rbac.Service`'s own real methods 1:1), reachable at the Service level only -- the identical posture `org.TreeService.Restore` already has.
