# integration

go/integration is a tenant's outward-facing API surface: API keys a tenant issues to its own scripts and third-party systems, and the three-layer rate limiting that protects the platform, the tenant and the individual key from one another. This file is the module-level discipline that ships with `go/integration` to consuming projects; the design rationale is `docs/internal/07-platform-services.md`'s integration section, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: round 5 of at least 5.** Round 1 shipped API key issuance, listing, rotation and revocation, plus the three-layer rate-limiting composition on top of `go/ratelimit` and its HTTP 429 translation as a reusable middleware. Round 2 shipped the design doc's other half: outbound webhooks -- tenant-configured subscriptions, the internal-to-public event schema mapping mechanism, event-driven delivery via `go/jobs`, HMAC signing, SSRF-protected delivery (creation-time and dial-time), and retry with dead-lettering. Round 3 is a cross-module soft-delete-adoption backlog item (following `go/org`'s and `go/rbac`'s own rounds): `WebhookSubscription` adopts `dbkit.SoftDeletable`, `Service.RestoreWebhookSubscription` undoes a mark-delete, and this module gains its first-ever PostgreSQL integration tier -- see "Soft deletion" below for the full round. Round 4 retired round 2's own "no reference-app consumer yet" exception for the outbound-webhook surface: the reference app wires a real `EventMapping` over `org.member.joined`, mounts one hand-written, permission-gated route (`examples/reference-app/cmd/server/webhooks.go`) that lets a demo tenant create a subscription, and its own `webhook_flow_test.go` drives a REAL HMAC-signed HTTP delivery -- independently re-verified, not merely observed as "a request arrived" -- against a real receiver process it controls, plus a real, unmodified retry-then-dead-letter proof that runs this module's own `jobs`-backed retry horizon to exhaustion (7 total attempts, no 8th). That round also broke this module's still-not-frozen public API for the first time, per round 2's own explicit permission for that: the test-only, unexported `withHTTPClient`/`withWebhookURLValidator` seams (`module.go`) became the exported `WithWebhookHTTPClient`/`WithWebhookURLValidator` options, since a real host -- not just this module's own white-box tests -- turned out to need them (see "Seams" below). Round 4 left round 1's API-key surface (issuance/listing/rotation/revocation) untouched -- it still carried round 1's own "no reference-app consumer yet" exception and `Module.OpenAPISpec()` still returned `nil` for this module. **Round 5 closes exactly that gap**: a real OpenAPI fragment (`api/openapi.yaml`) and spec-generated HTTP surface (`api/integration-server.gen.go`, `handler.go`) for round 1's four operations, mounted in the reference app through the SAME generic route-mounting machinery every other module's fragment already uses (`reg.Routes.Mount`, `mountModuleRoutes`), gated on `integration:apikey:read`/`integration:apikey:manage` through a new router-level gate the mismatch between this module's three-segment permission names and `rbac.RequirePermissionFunc`'s own two-segment contract required (`guardIntegrationAPIKeyRoute`, `demo_subject.go` -- the same shape mismatch `wireIntegrationWebhooks` already found and worked around for this module's other permission pair), and driven end to end by `examples/reference-app/cmd/server/apikey_flow_test.go`. See "Reference app: mandatory first consumer (round 1's API-key surface)" below for the full record, including what this round's own `SubjectResolver` seam is and is not responsible for. Judge what exists by the code, not by this sentence.

## Scope

**In scope round 1** (unchanged by round 2). One table (`integration_api_keys`) with dual-dialect versioned SQL migrations, registered through `dbkit.MigrationRegistry` the same way every other module does. `Service` (`service.go`): `Create` (generates the raw key, returns it to the caller exactly once), `List` (never exposes the raw key or its hash), `Rotate` (create-new + revoke-old, documented below) and `Revoke`. `LayeredLimiter` (`ratelimit.go`): three independent `go/ratelimit.Allow` calls -- global, tenant, key -- composed with short-circuit-on-first-denial semantics, built entirely from `go/ratelimit`'s existing public API with no change to that package. `HTTPGuard` (`httpguard.go`): the handler-layer translation of a denied `LayeredDecision` into a 429 response with `Retry-After` and `X-RateLimit-*` headers -- a directly usable `net/http` middleware. ## Data model

One table, tenant data (`docs/internal/04-data-and-tenancy.md`): `integration_api_keys`, isolation proven by `tenancytest.AssertIsolated` (`repository_test.go`), never `AssertNotTenantScoped` -- a key belongs to exactly one tenant, never to the individual who created it (`CreatedBy` is an id reference, not an ownership tie; see model.go's own doc comment).

**The primary key is `(id)` alone**, matching `go/storage`'s `Object` precedent rather than a composite `(tenant_id, id)` key: `id` is an application-generated UUID (`uuid.NewString`), globally unique on its own, so `tenant_id` rides along as a plain, non-key column promoted by the embedded `dbkit.TenantModel`.

**The key material is never stored.** `Hash` is the hex-encoded SHA-256 of the raw key value `Service.Create` generates once and returns to the caller; it is never persisted, logged, or returned by any other call. `keygen.go`'s `newAPIKeyToken` explains why plain SHA-256 (not a deliberately-slow password hash) is the right primitive here: the input is 32 bytes of `crypto/rand` full-entropy randomness, not a human-chosen secret, so there is no dictionary an attacker could use to make a slow hash worth paying for -- the same reasoning `go/org`'s invitation token hashing already documents. `Prefix` is the plaintext, non-secret display portion (`sk_` plus eight characters of the encoded random value) a key list shows so an operator can tell two keys apart without ever seeing the rest.

**Scopes are frozen at issuance, never re-derived.** `APIKey.Scopes` is the subset of `CreatedBy`'s permissions `Service.Create` validated at the moment the key was issued, through the mandatory `PermissionLister` seam. A later change to the creator's own permissions -- promoted, demoted, or removed from the tenant entirely -- never widens or shrinks an already-issued key; the design doc is explicit that a key's scope does not change along with its creator's later permission changes. Changing what a key may do means issuing a new one (`Rotate`); nothing in this module ever rewrites `Scopes` after `Create`.

**The creator leaving does not revoke the key.** `CreatedBy` is the responsible party on record, not an ownership tie -- the design doc is explicit that it is unacceptable for an integration to break just because someone left the tenant. `APIKeySummary.CreatorLeft`, computed at `List` time through the optional `MembershipChecker` seam, is the visibility the design doc does ask for, so a tenant administrator notices a key needs a new owner of record without the key itself being touched.

**Every key has a mandatory, forced expiry.** `ExpiresAt` is required; `Service.Create` defaults an unspecified request to `MaxAPIKeyLifetime` (one year) from now and refuses a request asking for anything further out (`ErrExpiryExceedsMaximum`) or already past (`ErrExpiryInPast`), per the design doc's forced-expiry-ceiling rule -- a key that never expires is the most common credential-leak surface, so this is refused rather than silently clamped.

### Round 2's two tables

Both tenant data, isolation proven by `tenancytest.AssertIsolated` (`webhook_repository_test.go`), both primary-keyed `(id)` alone on the identical `integration_api_keys` precedent above.

**`integration_webhook_subscriptions`** (`WebhookSubscription`, `webhook_model.go`): `URL` (validated by `ValidateWebhookURL` at creation and update time -- see "Outbound webhook delivery" below), `EventTypes` (a JSON array of PUBLIC event types, never internal `pkgcore.Event.Type` strings -- see that field's own doc comment for why the two vocabularies are kept apart), `Secret` (the per-subscription HMAC key, encrypted at rest under `WebhookSecretSerializerName` -- a host registers it with `dbkit.RegisterEncryptedSerializer` before opening the database, exactly like `go/org`'s `EmailSerializerName` and `go/notification`'s `ContactAddressSerializerName`), `Active` (the pause/resume gate), `CreatedBy`.

**`Secret` is reversibly encrypted, never hashed -- unlike `APIKey.Hash`.** This is the one place round 2's storage choice looks, at a glance, like it contradicts round 1's own "the key material is never stored" rule above. It does not: an API key hash only ever needs to be COMPARED (a lookup by hash), while a webhook secret must be READ BACK IN PLAINTEXT on every delivery attempt to compute that attempt's HMAC signature (`webhook_signature.go`'s `signWebhookPayload`). A one-way digest cannot serve that purpose. See `WebhookSecretSerializerName`'s own doc comment in `webhook_model.go` for the full argument, including why the encryption key must be a different secret from any blind-index key this module might grow later (`dbkit.NewCipher`'s own doc comment).

**`integration_webhook_deliveries`** (`WebhookDelivery`, `webhook_model.go`): the delivery log docs/internal/07 requires -- `SubscriptionID`, `EventType`/`EventVersion` (the PUBLIC identity, copied from the `EventMapping` that produced the row), `IdempotencyKey` (the fan-out dedupe key, `deriveWebhookDeliveryKey` in `webhook_delivery.go`), `Payload` (the exact rendered body, computed once and never recomputed on retry -- see that field's own doc comment for why), `Status` (`DeliveryStatusPending`/`Failed`/`Delivered`/`DeadLetter`), `Attempts`, `LastStatusCode`, `LastError`, `LastAttemptAt`, `DeliveredAt`. **One row per (subscription, event), not one row per HTTP attempt** -- a retry updates the SAME row in place; see the type's own doc comment for why. `idx_integration_webhook_deliveries_subscription_created_at` serves `Service.ListRecentWebhookDeliveries`'s "recent deliveries for this subscription" read; `uq_integration_webhook_deliveries_tenant_subscription_key` is what makes fan-out idempotent under an at-least-once `EventBus`.

## Soft deletion

`WebhookSubscription` implements `dbkit.SoftDeletable` (`DeletedAt *time.Time` / `DeletedBy string`, the exact field shape and tags `examples/reference-app/internal/notes.Note` established as the precedent, and that `go/org`'s `OrgNode`/`Membership` round and `go/rbac`'s `RoleBinding` round both reused). That flips `dbkit.Repository[WebhookSubscription].Delete` -- called by `Service.DeleteWebhookSubscription`'s `webhookRepo.Delete(ctx, id)` -- from a physical `DELETE` onto a mark-delete `UPDATE`, and gives the model a working `dbkit.Repository[WebhookSubscription].Restore`, which `Service.RestoreWebhookSubscription` wraps.

**`WebhookSubscription` alone, of this module's models.** `APIKey` is untouched: `Service.Revoke` already sets `RevokedAt` through an ordinary `repo.Update` call and never calls `Delete` at all, so it already followed the "mark, don't destroy" philosophy natively, with its own domain-specific state field, before this round existed -- adopting `SoftDeletable` on top of that would add a second, redundant deletion mechanism to the same row. `WebhookDelivery` is untouched too: it is a transient, append-only delivery-attempt log with no `Delete` operation anywhere in this module, the identical "nothing to retrofit" reasoning `go/rbac`'s round applied to `Role`/`RolePermission`. `DeleteWebhookSubscription`'s `webhookRepo.Delete(ctx, id)` call is this module's one real delete-shaped operation against a row without its own domain-specific revocation mark, exactly why this round targeted it and only it -- the identical reasoning `go/org`'s round applied to pick `OrgNode`+`Membership` over `org_invitations`, and `go/rbac`'s round applied to pick `RoleBinding` over `Role`/`RolePermission`.

**No partial-unique-index conversion needed, unlike `go/org`'s and `go/rbac`'s identical adoptions.** Both of those rounds needed one because the table they touched carried a real unique index a soft-deleted row would keep occupying, permanently blocking reuse of the same tuple. `integration_webhook_subscriptions` carries no unique index beyond its primary key -- `idx_integration_webhook_subscriptions_tenant_active` (`migrations/{sqlite,postgres}/0002_create_integration_webhook_subscriptions.sql`) is a plain, non-unique index, so a mark-deleted row occupying it reserves nothing another row would need. `migrations/{sqlite,postgres}/0004_add_soft_delete.sql` therefore adds only the two soft-delete columns, with no index change at all -- one less moving part than either precedent round needed.

**`DeleteWebhookSubscription`'s existing error handling and doc comment needed only a wording update, not a behavior change.** `dbkit.Repository[T].Delete` reports `dbkit.ErrRecordNotFound` on zero rows affected whether the branch taken is a physical `DELETE` or, now, a mark-delete `UPDATE` (`go/dbkit/repository.go`'s `Delete`/`softDelete`) -- the promoted method's contract is unchanged from `DeleteWebhookSubscription`'s point of view, and so is `webhook_delivery.go`'s `handleDeliveryJob`: its own `webhookRepo.FindByID` lookup on a delivery's subscription is hidden from a mark-deleted row by dbkit's soft-delete auto-scope plugin exactly as it was made impossible by a physical `DELETE` before this round, so an in-flight delivery enqueued before a subscription's deletion still settles `DeliveryStatusDeadLetter` with "webhook subscription no longer exists", unchanged (`TestService_handleDeliveryJob_SubscriptionMarkDeleted_DeliveryRowUnaffected` pins this explicitly, alongside the pre-existing `TestService_handleDeliveryJob_SubscriptionDeleted_TerminatesWithoutRetry`, which needed no change at all to keep passing). What DID need a wording fix: `DeleteWebhookSubscription`'s own doc comment said "permanently removes", and `handleDeliveryJob`'s said "none will reappear by retrying" -- both true of a physical `DELETE`, both no longer quite true now that `RestoreWebhookSubscription` exists. Both comments are corrected in place; see webhook_service.go and webhook_delivery.go.

**The Restore-safety decision: Restore always forces `Active = false`, a deliberate divergence from `go/org`'s and `go/rbac`'s own "changes nothing but the two soft-delete columns" precedent.** Both of those modules' `Restore` methods change nothing about the restored row beyond `deleted_at`/`deleted_by` (`go/org/AGENTS.md`'s and `go/rbac/AGENTS.md`'s own "Soft deletion" sections, and `assign.go`'s `RestoreRole` doc comment, record the reasoning in their own domains). This round does not carry that precedent over unchanged, because the two situations are not the same hazard. `go/org`'s and `go/rbac`'s `Restore` calls resume a purely INTERNAL fact -- an organization membership, an authorization grant -- evaluated fresh against the rest of the system on every read, with no further action happening on its own. Restoring a `WebhookSubscription` with `Active` still `true` is different in kind: `webhook_delivery.go`'s `handleDomainEvent` fans out to every ACTIVE subscription automatically, on every matching domain event, entirely without further human action. An unconditional restore would therefore silently resume POSTing the tenant's live event data to an external, third-party URL nobody has looked at again since the subscription was deleted, however long ago that was and however stale its URL or receiving system might now be -- a real-world side effect leaving this process, not an internal state change this codebase can reason about the safety of the way it can for an org membership or an rbac grant. `Service.RestoreWebhookSubscription` therefore always sets `Active = false` after the promoted `Restore` call, regardless of what `Active` held at the moment of deletion (`TestService_RestoreWebhookSubscription_ForcesActiveFalse_EvenIfActiveAtDelete` and its PostgreSQL re-run, `TestPostgres_RestoreWebhookSubscription_UndoesTheDelete`, both seed an ACTIVE subscription specifically to pin this). This costs the caller exactly one extra explicit step -- an `UpdateWebhookSubscription` call setting `Active` back to `true` -- to resume delivery, which is the same "no implicit side effect on a structural edit" discipline this codebase already applies elsewhere (`go/org/AGENTS.md`'s identical framing for why `TreeService.Delete` does not re-parent orphans and does not cascade `Restore`). Beyond that one field, `RestoreWebhookSubscription` follows the established precedent exactly: it does not re-validate the row against `CreateWebhookSubscription`'s own preconditions (its URL is not re-run through `ValidateWebhookURL`, for instance) and reports the identical collapsed not-found signal `dbkit.Repository[T].Restore`'s own doc comment describes -- an id with nothing to restore and an id that exists but is not currently mark-deleted are indistinguishable, matching `go/org`'s `MemberService.Restore` and `go/rbac`'s `RestoreRole`.

**No cross-replica cache-invalidation concern, unlike `go/rbac`'s round.** `go/rbac`'s `RestoreRole` had to publish `EventRoleBindingRestored` and have `Module.Attach` subscribe to it, because rbac caches authorization decisions per subject and a stale cached denial on one replica would otherwise outlive the anti-loss TTL. This module caches nothing: `webhook_delivery.go`'s `handleDomainEvent` calls `webhookRepo.ListActiveByTenant` fresh, straight against the database, on every single matching domain event -- there is no in-memory decision cache anywhere in this module for a restore (or a delete, or an update) to invalidate. `Service.RestoreWebhookSubscription` therefore only needs `AuditActionWebhookSubscriptionRestore`, the audit-trail symmetry described below; no domain event is published, matching `CreateWebhookSubscription`/`UpdateWebhookSubscription`/`DeleteWebhookSubscription`'s own identical choice (this module publishes no domain event of its own on any webhook-subscription mutation, only audit records -- `module.go`'s `Register` subscribes to OTHER modules' events for fan-out, but never publishes any of its own).

**Audit symmetry.** `AuditActionWebhookSubscriptionRestore` (`"integration.webhook_subscription.restore"`) is emitted by `RestoreWebhookSubscription` through the same `emitWebhookAudit` helper `Create`/`Update`/`DeleteWebhookSubscription` already use, completing the create/update/delete/restore quartet `module.go`'s `auditActionDecls` declares.

**Known limitation.** `RestoreWebhookSubscription` does not re-validate the restored row's `URL` against `ValidateWebhookURL` -- a caller wanting that re-checked calls `UpdateWebhookSubscription` afterward (which does re-validate on any `URL` change), the same "call the ordinary mutation for a full re-check" answer `go/rbac`'s own known limitation gives for `RestoreRole`.

**A pre-existing PostgreSQL column-type bug, found and fixed by this round's own new integration tier.** `WebhookSubscription.Secret` stores CIPHERTEXT under `WebhookSecretSerializerName`, but the PostgreSQL migration set declared it `VARCHAR(512)` since round 2 first shipped it -- AES-256-GCM ciphertext is effectively random binary data, which is essentially never valid UTF-8 text, and PostgreSQL enforces its configured encoding on every `VARCHAR`/`TEXT` value. Writing a genuine encrypted secret through this column failed with `invalid byte sequence for encoding "UTF8"` the very first time `integration_test/postgres_softdelete_test.go` -- this module's first-ever PostgreSQL integration tier of any kind -- actually exercised it. This was never caught before because this module had no PostgreSQL integration tier until this round; the unit tier's SQLite database has no fixed column encoding to violate. `migrations/postgres/0005_fix_webhook_secret_column_type.sql` brings the column to `BYTEA`, matching `go/org`'s identical `Invitation.Email`/`EmailSerializerName` precedent (`BYTEA` on PostgreSQL, `BLOB` on SQLite) exactly. This is the first migration in this module -- and, as far as this round's own review of the repository found, the first in the whole codebase -- with no `sqlite/` sibling: SQLite's dynamic typing already stores arbitrary binary through a `VARCHAR`-declared column without error, so nothing on that dialect needed to change, and `dbkit.MigrationRegistry.Apply` reads each dialect's own subdirectory independently with no cross-dialect pairing requirement. `webhook_model.go`'s `Secret` field's `gorm` tag dropped its now-meaningless `size:512` hint accordingly (this codebase never uses `AutoMigrate`, so the tag never drove the actual column type either way). Bundled into this round rather than filed as a separate fix because it directly blocked this round's own mandated PostgreSQL integration tier (item 8) against the exact table this round already touches; `TestPostgres_DeleteWebhookSubscription_MarksInsteadOfPhysicallyRemoving` and `TestPostgres_RestoreWebhookSubscription_UndoesTheDelete` are the reproducing tests this bug fix ships with, per this repository's bug-fix-needs-a-test rule -- both genuinely fail against the pre-fix column type and pass after.

## Seams

**`PermissionLister` (mandatory for any non-empty `Scopes` request).** `Service.Create` calls it exactly once per request to validate that the requested `Scopes` are a genuine subset of the creator's own permissions right now. `go/rbac`'s `Authorizer.ListPermissions(ctx, sub Subject) ([]string, error)` is the real, already-shipped method this interface mirrors structurally -- no new `rbac` method was invented for this round; a host wires it with a one-line closure, spreading `rbac.Subject`'s two fields into plain parameters so this module needs no `rbac.Subject` value to call it. This module still does not import `go/rbac` for it, for the same reason `org.FeatureGate` and `rbac.SubtreeResolver` are structurally-typed seams rather than direct imports across the module boundary: `go/rbac` carries `dbkit`, `gorm` and its own migrations along with it, and every one of those becomes a cost every consumer of this otherwise storage-and-ratelimit-only module would pay just to reference one interface's shape. An empty `Scopes` request needs no lister at all -- there is nothing to check a request for zero scopes against -- so a `Module` built with no `WithPermissionLister` option can still issue scope-less keys; a non-empty request with none wired fails closed with `ErrPermissionListerUnavailable` rather than silently skipping the check.

**Why one-at-a-time, not a bulk check.** `go/rbac`'s public API has no "is this whole set of permissions held" call, only `ListPermissions` (list everything a subject holds) and, presumably, a single-permission check elsewhere in its `Authorizer` -- this round validates each requested scope by testing set membership against `ListPermissions`'s answer, which needs exactly one `rbac` call per `Create`/`Rotate` regardless of how many scopes are requested. If `go/rbac` grows a genuine bulk "are these N permissions all held" call in a later round, `validateScopes` in `service.go` is the one place that would change to use it.

**`MembershipChecker` (optional).** Answers whether a given user is still an active member of a tenant, the one fact `Service.List` needs for `APIKeySummary.CreatorLeft`. Unlike `PermissionLister`, this is a display convenience, not a security control -- nothing about whether a key authenticates, what it may do, or whether it keeps working depends on `CreatorLeft`'s value. A host that wires none simply never sees the flag raised: `List` reports `CreatorLeft` as `false` for every row, exactly as if every creator were still active. Membership is owned by whichever module actually tracks who belongs to a tenant -- `go/org`'s roster in this codebase, but nothing requires that; the design doc's own text only ever says "creator has left", never naming `org` or `authn` as the source of truth, so this is a structurally-typed interface exactly like `org.FeatureGate` and `rbac.SubtreeResolver`.

Both seams follow the `PermissionListerFunc`/`MembershipCheckerFunc` adapter shape `http.HandlerFunc` popularized, so a host wires a closure without declaring a named type.

**`EventMapping` / `WithEventMapping` (round 2, optional -- a `Module` with none declared simply never subscribes to anything).** See `eventmapping.go`'s own doc comment for the full design rationale; summarized here because it is this round's central design decision.

The design doc requires an explicit internal-event-to-public-schema mapping layer, populated by "a business module's own `Register` call". Implementing that literally would mean adding a field to `pkgcore.Registry` -- explicitly out of this round's scope (`pkgcore` is the dependency floor of the whole monorepo; widening its contract is a decision for whoever owns it, not a side effect of one module's round) -- or `go/integration` importing every business module directly, which the root `CLAUDE.md`'s module-boundary rule forbids outright. `WithEventMapping` is the third option: a `Module` construction-time `Option`, wired by the HOST (which already imports both the business module and `go/integration`, the one place in the whole program allowed to see across every module boundary at once), following the EXACT shape round 1's own `WithPermissionLister`/`WithMembershipChecker` already established for reaching a sibling module without an import edge. A business module's own `Register` call still contributes the CATALOG half of the mapping contract for free and unprompted: `pkgcore.EventDecl`'s own doc comment already says declaring an event is "a documentation and mapping contract" `integration` is meant to read; only the TRANSFORM function -- code, not data, closing over a payload shape `go/integration` may not import -- needs the host's hand, and only the host sits above both modules to provide it.

`WithEventMapping` must run before `Module.Register`, unlike `WithPermissionLister` (whose seam is read lazily, at call time): `Register` subscribes to every declared mapping's `InternalType` on `reg.Events` synchronously, during the one legal declaration phase (`reg.Events.Subscribe` performs no I/O, so this stays inside `Register`'s "must not perform I/O; it only declares" contract), and it can only subscribe to what `NewModule`'s options have already told it about.

**`WithWebhookURLValidator` / `WithWebhookHTTPClient` (round 4, optional -- a `Module` with neither declared gets `ValidateWebhookURL`'s and `newSafeHTTPClient`'s real, strict production behavior, unchanged).** Promoted from round 2's own unexported, this-module's-tests-only `withWebhookURLValidator`/`withHTTPClient` (`module.go`) once a real host -- the reference app, wiring round 2's surface end to end for the first time in round 4 -- found it had no other way to prove a genuine signed HTTP delivery against a receiver it actually controls: every receiver process this repository's own test infrastructure can stand up offline (an `httptest.Server`, or a sibling Docker container reached the way this repository's other Docker-backed integration tiers reach theirs) resolves to either loopback or RFC 1918 private address space, both of which `ValidateWebhookURL`'s real, unmodified SSRF check correctly refuses -- there being no such address for a real receiver a test controls, this is not a gap the module's own design left open by oversight, it is the SSRF protection working exactly as intended against the one class of address every offline receiver happens to have.

Both options must be wired TOGETHER, never one alone: `WithWebhookURLValidator` overrides only the creation-time check (`Service.CreateWebhookSubscription`/`UpdateWebhookSubscription`), while `WithWebhookHTTPClient` overrides only the dial-time transport a delivery attempt actually sends through (`Service.attemptDelivery`) -- overriding one without the other would either refuse the subscription before it is ever created, or accept it at creation time only to have every delivery attempt refused at dial time instead. This mirrors `go/authn`'s own identical precedent, `WithHTTPSMSSenderClient` (`go/authn/sms.go`), which exists for the exact same reason against its own SSRF-guarded SMS gateway client. A production host must never call either: doing so does not weaken any OTHER `Module`'s or any OTHER composition's SSRF enforcement (each `Module` instance carries its own `urlValidator`/`httpClient` fields, `module.go`'s `Module` struct), but it does weaken THIS instance's, permanently, for as long as that instance runs.

## Rate limiting

`LayeredLimiter.Allow` evaluates the global, tenant and key layers in that fixed order, short-circuiting on the first denial: a request already known to be denied at the global layer never touches the tenant or key counters at all. A zero-value `ratelimit.Limit` on any of `LayeredLimits`' three fields disables that layer entirely (`Allow` never calls the underlying `Limiter` for it), so `LayeredLimits{}`'s zero value legally disables all three -- every request is allowed. This module never modifies `go/ratelimit` itself; the three layers are entirely a composition of its existing `Limiter.Allow(ctx, key, limit)` call, one per layer, matching the design doc's own layering description.

`HTTPGuard.Middleware` wraps an `http.Handler`, deriving the tenant and key dimensions from the request through a host-supplied `Extractor` function -- this module takes no position on how a host authenticates a request or resolves its tenant. A denied `LayeredDecision` becomes a 429 with `Retry-After` (whole seconds, rounded up per RFC 9110 §10.2.3) and `X-RateLimit-Remaining`/`X-RateLimit-Reset`/`X-RateLimit-Layer` headers; an error from the underlying limiter itself (a `KVStore` failure) becomes a 500, never a silent allow -- `go/ratelimit.Limiter`'s own doc comment is explicit that it decides no fail-open policy on the caller's behalf, and `HTTPGuard` honors that.

## Outbound webhook delivery

**The pipeline (`webhook_delivery.go`).** `Module.Register` subscribes `Service.handleDomainEvent` (through a `Module`-level forwarding wrapper the same shape `webhookDeliveryHandler` uses for the job side, both explained in "Register-time wiring, Attach-time Service" below) to every declared `EventMapping.InternalType`. On a matching event: skip if the event carries no tenant (mirroring `org.handleUserCreated`'s identical no-tenant skip); list the tenant's ACTIVE subscriptions whose `EventTypes` includes the mapping's `PublicType` (`matchingSubscriptions` -- a Go-side filter over a JSON column, never a SQL one, per this module's dual-dialect rule); run the mapping's `Transform` and wrap it in the versioned public envelope `{event: {type, version}, data: ...}` (`buildEnvelope`); for each matching subscription, create (or, on a redelivery, find) the `WebhookDelivery` row under its derived idempotency key and enqueue one `jobs.Task` (job type `integration.webhook.deliver`) per subscription. **`handleDomainEvent` NEVER returns a non-nil error** -- the in-memory `EventBus`'s `Publish` joins a subscriber's error back into the PUBLISHING module's own call (`pkgcore.memoryEventBus.Publish`'s own doc comment), so a webhook wiring problem here must never surface as a failure of, say, `org`'s own membership-creation call. Every failure is logged at `Warn` and swallowed, the identical resilience contract `org.handleUserCreated` documents for the identical reason.

**Delivery execution (`Service.handleDeliveryJob`, the `jobs.Handler` half).** One HTTP `POST` of the row's stored `Payload` to the subscription's `URL`, signed per "HMAC signing" below. A subscription deleted or paused after its delivery was enqueued is treated as terminal (`DeliveryStatusDeadLetter`, no retry) rather than retried against a receiver the tenant no longer wants, or one that no longer has a secret to sign against. A 2xx response settles the row `DeliveryStatusDelivered`; anything else -- a non-2xx status or a transport error -- settles it `DeliveryStatusFailed` and returns the error, which is `jobs`' own signal to retry.

**Retry and dead-lettering.** Enqueued with `jobs.WithMaxRetries(webhookMaxRetries)` (6, chosen deliberately larger than `jobs.DefaultMaxRetries`'s 3 -- a webhook receiver is far more likely to be down for a transient few minutes than an in-process handler is). `jobs.StandaloneQueue` (or the distributed mode's asynq-backed queue) owns the exponential backoff and the retry-count bookkeeping entirely -- this module adds none of its own, per `go/jobs`'s own retry contract. Once retries are exhausted, `jobs` calls this module's `jobs.FailureHook.OnFailure` (`Service.onWebhookDeliveryDeadLetter`, wrapped the same way `handleDeliveryJob` is), which settles the row `DeliveryStatusDeadLetter` -- the root `CLAUDE.md`'s "the queue offers an `OnFailure` hook ... belongs to the business module" rule, applied here as simply recording the terminal state.

**HMAC signing (`webhook_signature.go`).** Every delivered request carries `HeaderWebhookID` (the delivery's own id, for a receiver's own dedupe), `HeaderWebhookTimestamp` (Unix seconds), and `HeaderWebhookSignature` (`"v1=" + hex(HMAC-SHA256(secret, "<timestamp>.<raw body>"))`). The timestamp is signed INSIDE the covered content, not merely alongside it as an unsigned header -- see `webhook_signature.go`'s own file comment for why that is what makes replay rejection possible at all (a captured genuine pair cannot be replayed under a forged, later timestamp). `WebhookReplayTolerance` (5 minutes) is exported purely as documented guidance for a receiver's own verification code; this module signs and stamps, and has no receiving side of its own to enforce the tolerance against.

**SSRF protection, at two different times (`ssrf.go`).** `ValidateWebhookURL` runs at subscription creation and update time: refuses a malformed URL, a disallowed scheme, or one resolving to any loopback/private/link-local/multicast/CGNAT address (`isBlockedIP`) -- the mandatory proof (`ssrf_test.go`'s `TestValidateWebhookURL_PrivateIPLiteral_Blocked`) is exactly the private-IP-refused test this round's own instruction called non-negotiable. `newSafeHTTPClient`'s `Transport.DialContext` re-validates the CONNECTING address on every delivery ATTEMPT, dialing the specific IP it just checked directly rather than trusting a second, independent hostname resolution -- this is what actually defeats DNS rebinding (a URL whose DNS answer changed between subscription creation and delivery), which a creation-time-only check cannot. It also automatically covers HTTP redirects, since Go's `http.Client` re-dials through this same guarded `DialContext` for a redirect's `Location`.

**Fan-out idempotency.** `deriveWebhookDeliveryKey` hashes `(subscriptionID, publicType, publicVersion, renderedBody)`; `handleDomainEvent` probes for an existing `WebhookDelivery` under that key before creating a new one, and `uq_integration_webhook_deliveries_tenant_subscription_key` is the database-level backstop for two concurrent handlers racing the same redelivered event. `jobs.Task.IdempotencyKey` is set to the identical key as a second, independent line of defense at the queue layer.

**Register-time wiring, Attach-time `Service`.** `Module.Register` must subscribe to events and register the job handler before a `Service` exists (`Service` is built in `Attach`, which round 1 already established runs strictly after `Bootstrap` returns). Both `Module.handleDomainEvent` and `webhookDeliveryHandler` (a small `jobs.Handler`/`jobs.FailureHook` adapter type) are `Module`-level forwarding wrappers: they read `m.service` at CALL time (which, for real traffic, is always after `Attach` has run) and log-and-swallow (event side) or return a retryable error (job side) on the rare case they run before it.

**Round 5 retires round 1's own "no reference-app consumer yet" exception** -- per the root `CLAUDE.md`'s mandatory-first-consumer rule -- and, per that same file's public-API-is-frozen rule, freezes round 1's public API for real: `Service.Create`/`List`/`Rotate`/`Revoke`'s signatures, and every exported type this round's `Handler`/`api` package depend on, are no longer the "not frozen, may still break" surface rounds 1 through 4 left them as. **The HTTP surface (`api/openapi.yaml`, `api/integration-server.gen.go`, `handler.go`) -- see "In scope round 5" above for what each file adds.** `Handler` holds a reference to `*Module` itself, not to a `*Service` -- a deliberate departure from org's, storage's, notification's, sharing's and admin's own `NewHandler` shape, all of which build `Handler` directly from concrete services `NewModule` already built. **What this proof does NOT, and cannot yet, demonstrate.** "Rotate" and "Revoke" above are proven only as row-state transitions -- the predecessor's `Revoked`/`RevokedAt` reads back true through the very same session-authenticated `list` call a tenant administrator makes to manage their own keys. Neither this test nor any other test in this codebase ever uses a captured raw key value as a bearer credential against any endpoint, because no such endpoint exists: `go/integration` ships no `Authenticate`/`Verify` method (see "No inbound request authentication" under Known limitations, and `keygen.go`'s own doc comment on `hashAPIKeyToken`), so there is no lookup path anywhere in this codebase that could ever be fed a presented key to refuse. Concretely, the property "a request bearing a rotated-away or revoked key is refused" is unverifiable today and is not verified by this round or any prior one -- a real, currently-undischarged testing gap relative to that specific claim, though a deliberate, documented scope boundary rather than a regression: round 1's own design explicitly deferred request authentication to a later round. The follow-up is exactly that later round: once an `Authenticate`/`Verify` path exists, it must ship with its own test proving a rotated-away/revoked key is refused against the real composed HTTP stack, matching the shape of the proof above.

**Why `HTTPGuard`/`LayeredLimiter` stay unwired in front of this surface** -- see "In scope round 5" above for the full reasoning: they rate-limit a request authenticated BY one of these keys against a host's own inbound API surface, a materially different thing from a tenant administrator managing their own keys through their own ordinary session. Wiring them here would conflate the two.

## Known limitations

- **No inbound request authentication.** This module issues, lists, rotates and revokes keys, but nothing here verifies an incoming request's presented key against the stored hash, and `LastUsedAt` is never written by this round's code. `uq_integration_api_keys_tenant_hash` exists now so a later round's lookup needs no migration of its own. **Consequence for testing:** with no `Authenticate`/`Verify` path, no test anywhere in this codebase can present a rotated-away or revoked raw key as a bearer credential and observe it refused -- round 5's own acceptance proof (see "Reference app: mandatory first consumer (round 1's API-key surface)" above) only proves the row's `Revoked` state through the ordinary session-authenticated `list` call, never through an actual authenticated request using the old key. That specific property stays unverified until the later round that ships `Authenticate`/`Verify` also ships the test proving it against the real composed HTTP stack.
- **`Rotate` is not atomic.** The new key's `Create` and the predecessor's `Revoke` are two separate database writes, not one transaction -- `dbkit.Repository[T]` exposes no cross-call transaction seam a business module can reach. A failure between the two leaves two live keys rather than zero, a safe-direction surplus (never a lockout) that `Rotate` reports to its caller rather than silently swallowing. See `service.go`'s `Rotate` doc comment for the full argument.
- **No expiry-sweep job.** `idx_integration_api_keys_tenant_expires_at` exists now; nothing in this round enqueues or runs a sweep against it. This module does not depend on `go/jobs` yet.
- **`MaxAPIKeyLifetime` is a package-level constant, not a dynamic configuration item.** Reading one from `go/config` would add a dependency edge this module's position in `docs/internal/01-architecture.md`'s graph does not have, paid for by every consumer that boots this module without config. A host that genuinely needs a different ceiling is a later round's `WithMaxAPIKeyLifetime` option.
- **Round 2's own webhook-SUBSCRIPTION-CRUD surface (`CreateWebhookSubscription`/`UpdateWebhookSubscription`/`DeleteWebhookSubscription`) still has no mounted HTTP surface and no reference-app consumer of its own.** Round 1's API-key surface no longer belongs in this bullet -- round 5 gave it both an HTTP surface and a reference-app consumer, and froze its public API; see "Reference app: mandatory first consumer (round 1's API-key surface)" above. Round 2's own delivery PIPELINE (the part `webhooks.go`'s hand-mounted demo route and `webhook_flow_test.go` exercise) is unaffected by either statement -- see "Reference app: mandatory first consumer (round 2's webhook surface)" above for what that half already has.
- **`RestoreWebhookSubscription` does not re-validate the restored row.** See "Soft deletion" above's own Known limitation.
- **No manual redelivery.** `DeliveryStatusDeadLetter` is a real, observable terminal state (`Service.ListRecentWebhookDeliveries`), but nothing in this round re-enqueues a specific dead-lettered delivery. See the scope table above for why the row shape already anticipates it.
- **A dead-lettered delivery is not distinguished from a "the subscription was deleted/paused" early refusal in `Status` alone.** Both settle as `DeliveryStatusDeadLetter` (see `handleDeliveryJob`'s own doc comment for why reusing the one terminal-failure status was chosen over inventing a third) -- an operator tells them apart by `LastError`'s text, which is not a stable, matchable code. A later round that needs to distinguish them programmatically will want a real code here instead of free text.
- **A delivery's `Payload` is computed once, at fan-out time, from whatever the `EventMapping.Transform` produced then.** If a later release changes what a `Transform` returns for the SAME `PublicVersion` (a bug fix within a version, not a genuine schema break), an already-enqueued-but-not-yet-delivered row still sends the OLD rendering on retry. This is intentional -- an HMAC signature must cover a byte-for-byte stable body across every retry of one delivery -- but is worth knowing before "just retry it" is assumed to pick up a mapping fix.
- **Delivery is not exactly-once on the send side.** A crash between the receiver accepting the request and this module's own `Update` call recording `DeliveryStatusDelivered` leaves the row `DeliveryStatusPending`/`Failed`, and the next retry re-sends -- a real, if narrow, double-delivery window, the same class of gap `go/notification`'s own delivery pipeline documents for its identical settle-after-send shape.
- **No per-tenant or per-subscription delivery-volume rate limiting.** Unlike round 1's own three-layer `LayeredLimiter` for inbound API traffic, nothing in this round bounds how many webhook deliveries one tenant's event volume can generate. Not named in this round's own instruction; a later round's concern if a runaway event source ever makes it one.

## Adjudications a reviewer should not "correct"

**The primary key is `(id)` alone, not `(tenant_id, id)`.** See "Data model" above -- `id` is a globally-unique application-generated UUID, matching `go/storage`'s `Object` precedent rather than the composite-key shape a module-local id would need.

**Rate limiting is never hard-wired to any specific storage key naming beyond this module's own `layerStorageKey` prefix.** `LayeredLimiter.Allow` treats `globalKey`, `tenantKey` and `apiKeyID` as opaque caller-supplied strings, exactly as `go/ratelimit.Limiter.Allow` itself treats its own `key` parameter -- this module adds no interpretation of what those strings mean.

**`Rotate` carries `Scopes` forward from the predecessor, but re-validates them against the creator's CURRENT permissions rather than trusting them as already-proven.** This is not a bypass of `Create`'s own scope check: routing the predecessor's scopes back through `Create` means a creator whose permissions shrank since the predecessor was issued can have a `Rotate` fail with `integration.scope_not_held_by_creator` on a scope it no longer holds. This is a deliberate, safe-direction consequence of "scope validation happens at issuance" applying to every issuance, including a rotation's, not a special carve-out.

**`ExpiresAt` is NOT carried forward on `Rotate`.** A rotation gets a fresh full-lifetime expiry (`Create`'s own default), not a continuation of the predecessor's absolute timestamp -- copying that timestamp would defeat the point of rotating a key that is itself close to (or, for a caller rotating a stale-but-still-live key, already past) its own expiry.

**`WebhookSubscription.Secret` is reversibly encrypted, not hashed like `APIKey.Hash`.** See "Round 2's two tables" above -- this is a deliberate divergence from round 1's own "the key material is never stored" pattern, not an inconsistency: a webhook secret must be read back in plaintext to sign every delivery attempt, while an API key hash only ever needs to be compared.

**`EventMapping` is wired through a `Module` construction-time `Option` (`WithEventMapping`), never a `pkgcore.Registry` field.** See "Seams" above's `EventMapping` entry for the full rationale -- this round was explicitly scoped to leave `pkgcore` untouched, and the `Option` shape reuses round 1's own established seam-wiring convention rather than inventing a new one.

**A dead-lettered delivery reuses `DeliveryStatusDeadLetter` for three distinct causes** (retries genuinely exhausted, the subscription was deleted after enqueue, the subscription was paused after enqueue) **rather than three separate statuses.** This was a deliberate choice to keep the state machine to the two terminal states `webhook_model.go`'s own doc comment documents (`Delivered`, `DeadLetter`) rather than growing a third and fourth just to distinguish "why" from "what" -- an operator reads `LastError`'s text for the why. See "Known limitations" above for the follow-up this leaves for a later round.

**`handleDomainEvent` and the job-side `webhookDeliveryHandler` are both `Module`-level methods/types, not `Service`-level, even though they forward almost everything to `Service`.** This is not incidental placement: `Module.Register` must call `reg.Events.Subscribe` and `reg.Jobs.Handle` before a `Service` exists at all (`Service` is built in `Attach`, which runs strictly after `Bootstrap`'s `Register` phase completes across every module) -- see "Register-time wiring, Attach-time `Service`" above.

**`RestoreWebhookSubscription` forces `Active = false`, unlike `go/org`'s and `go/rbac`'s own Restore methods, which change nothing beyond the two soft-delete columns.** Do not "fix" this into matching their precedent -- it is a deliberate, reasoned divergence, not an inconsistency this codebase forgot to bring into line. See "Soft deletion" above for the full argument: resuming automatic outbound HTTP delivery to an external, third-party URL is a materially different kind of side effect from resuming an internal permission or membership grant, and this module treats it accordingly.

**`migrations/postgres/0005_fix_webhook_secret_column_type.sql` has no `sqlite/` sibling.** Do not add one -- see "Soft deletion" above's own paragraph on this migration for why SQLite genuinely needs no equivalent change, and `go/dbkit/migrations.go`'s `migrationFiles` for why `dbkit.MigrationRegistry.Apply` has no cross-dialect pairing requirement that would make an asymmetric migration set invalid.

**Round 5's HTTP-mounted API-key CRUD surface (`api/openapi.yaml`, `handler.go`) does NOT sit behind `HTTPGuard`/`LayeredLimiter`, and this is not an oversight to "finish."** See "In scope round 5" above for the full argument: those exist to rate-limit a request AUTHENTICATED BY an already-issued key against a host's own inbound API surface (a surface this module still does not build -- "Deliberately not in scope" above), never the ordinary, session-authenticated administrative act of managing one's own keys -- gated by rbac exactly like every other module's own management surface, none of which sit behind `go/ratelimit` either. Wiring the two together would conflate a request a key AUTHENTICATES with a request that merely MANAGES keys.

**`Handler` (round 5, `handler.go`) holds a `*Module`, not a `*Service`, unlike every other module's own `Handler`.** Do not "simplify" this to match org's/storage's/notification's/sharing's/admin's shape -- it cannot: this module's own `Service` is built in `Attach`, strictly after `Register` (round 1's own established shape), so a `Handler` built during `Register` (as `reg.Routes.Mount` requires) has no `Service` to hold yet. Reading `m.service` at call time is the fix, mirroring `handleDomainEvent`'s and `webhookDeliveryHandler`'s own identical technique -- see "Reference app: mandatory first consumer (round 1's API-key surface)" above.
