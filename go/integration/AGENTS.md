# integration

go/integration is a tenant's outward-facing API surface: API keys a tenant issues to its own scripts and third-party systems, the three-layer rate limiting that protects the platform, the tenant and the individual key from one another, and outbound webhooks that turn a business module's internal domain events into signed HTTP deliveries. This file is the module-level discipline that ships with `go/integration` to consuming projects; the design rationale is `docs/internal/07-platform-services.md`'s integration section, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: implemented and consumed end to end.** The module ships API key issuance, listing, rotation and revocation plus `Service.Authenticate` (authenticate.go) for verifying a presented key as a bearer credential, the three-layer rate-limiting composition on top of `go/ratelimit` with its HTTP 429 translation, outbound webhooks (subscription management, the internal-to-public event schema mapping mechanism, event-driven delivery via `go/jobs`, HMAC signing, SSRF-protected delivery at creation and dial time, and retry with dead-lettering), manual redelivery of a dead-lettered delivery (`Service.RedeliverWebhookDelivery`), a host-scheduled API-key expiry sweep (`Service.EnqueueAPIKeyExpirySweep`/`Service.SweepExpiredAPIKeys`), the host-configurable key lifetime (`WithMaxAPIKeyLifetime`), rotation audit linkage, soft-delete/restore for webhook subscriptions, and a spec-generated HTTP surface covering both halves (the four apikey operations and six webhook operations under `/api/v1/integration`). The reference app is the mandatory first consumer of every surface. What is deliberately not shipped is recorded in "Known limitations". Judge what exists by the code, not by this file.

## Scope

**API keys.** One table (`integration_api_keys`) with dual-dialect versioned SQL migrations. `Service` (`service.go`): `Create` (generates the raw key, returns it to the caller exactly once), `List` (never exposes the raw key or its hash), `Rotate` (create-new + revoke-old, documented in "Adjudications" below), `Revoke`, and `Authenticate` (`authenticate.go`: resolves a presented raw key to its owning tenant from the hash alone, refuses with one outward-identical `ErrAuthenticationFailed` a key that does not exist, is revoked, or is expired, and best-effort records `LastUsedAt`). `LayeredLimiter` (`ratelimit.go`): three independent `go/ratelimit.Allow` calls -- global, tenant, key -- composed with short-circuit-on-first-denial semantics, built entirely from `go/ratelimit`'s existing public API. `HTTPGuard` (`httpguard.go`): the handler-layer translation of a denied `LayeredDecision` into a 429 response with `Retry-After` and `X-RateLimit-*` headers -- a directly usable `net/http` middleware. `AuthMiddleware` (`middleware.go`): the HTTP transport of `Authenticate`, reading the bearer credential from `HeaderAPIKey` (`X-API-Key`), attaching the resolved tenant and `*AuthenticatedAPIKey` to request context on success, and optionally gated pre-auth by a rate-limit guard (`WithAuthenticationGuard`). `pkgcore.Module` wiring: permissions (`integration:apikey:read`, `integration:apikey:manage`), audit actions (`integration.apikey.create`/`.revoke` -- no `.rotate`: `Service.Rotate` records a rotation as its two ordinary create/revoke events).

**Outbound webhooks.** Two tables (`integration_webhook_subscriptions`, `integration_webhook_deliveries`, `webhook_model.go`) with dual-dialect versioned SQL migrations. `Service`'s second surface: `CreateWebhookSubscription`/`ListWebhookSubscriptions`/`UpdateWebhookSubscription`/`DeleteWebhookSubscription`/`RestoreWebhookSubscription`/`ListRecentWebhookDeliveries` (`webhook_service.go`). `EventMapping` and `WithEventMapping` (`eventmapping.go`, `module.go`) -- the internal-to-public event schema mapping registry a host populates at `NewModule` construction time. `Module.Register` subscribes to every declared mapping's `InternalType` on the host's `pkgcore.EventBus` and registers the webhook-delivery `jobs.Handler`/`jobs.FailureHook` on `reg.Jobs` (`webhook_delivery.go`). `ValidateWebhookURL` and `newSafeHTTPClient` (`ssrf.go`) -- the two-layer SSRF defense (creation-time refusal, dial-time re-check). `signWebhookPayload` and the `HeaderWebhook*`/`WebhookReplayTolerance` exports (`webhook_signature.go`) -- the HMAC-SHA256-over-timestamp-and-body signing scheme. New permissions (`integration:webhook:read`, `integration:webhook:manage`) and audit actions (`integration.webhook_subscription.create`/`.update`/`.delete`/`.restore`), all bilingual.

**HTTP surface.** One OpenAPI fragment (`api/openapi.yaml`) covering ten operations under `/api/v1/integration`: `integration_createAPIKey`/`integration_listAPIKeys`/`integration_rotateAPIKey`/`integration_revokeAPIKey` and, under `/webhooks`, `integration_listWebhookSubscriptions`/`integration_createWebhookSubscription`/`integration_updateWebhookSubscription`/`integration_deleteWebhookSubscription`/`integration_restoreWebhookSubscription`/`integration_listWebhookDeliveries`, generated by the pinned oapi-codegen into a committed `api/integration-server.gen.go` and implemented by `handler.go`'s `Handler` behind a `var _ api.ServerInterface` compile-time assertion. Every operation is a thin HTTP translation of an existing `Service` method -- no new business rule lives in the fragment or the handler. The two request-body operations that carry a creator (`integration_createAPIKey`, `integration_createWebhookSubscription`) resolve it through the `SubjectResolver` seam, never a request field, and fail closed with `integration.subject_unresolved` when none is wired. Create and webhook-update decode through the strict `decodeRequiredJSON` (a genuinely empty body is refused); apikey create decodes through `decodeOptionalJSON`. Delete and restore answer 204; restore carries the Service rule that a restored subscription always comes back `Active = false`; the partial-failure answers of the three creates answer the operation's ORDINARY success with the credential in its normal field plus `auditRecordMissing: true` -- a credential never rides in an error envelope.

**Deliberately not in scope:**

| Not here | Why |
|---|---|
| An HTTP surface for manual redelivery of a dead-lettered `WebhookDelivery` | `Service.RedeliverWebhookDelivery` re-enqueues a specific dead-lettered delivery for a fresh attempt cycle -- Service-level only; nothing mounts it on the fragment. A consumer that needs redelivery on the wire drives a fragment operation from the method |
| Platform-blacklist-style writers, per-tenant delivery-volume rate limiting, per-webhook-type opt-out | Not named in the design's webhook paragraph |
| A scheduled, delivery-independent webhook URL re-validation job | `newSafeHTTPClient`'s dial-time re-check re-validates on every delivery attempt, which is the moment that actually matters |
| An automatically scheduled API-key expiry sweep | `Service.EnqueueAPIKeyExpirySweep`/`Service.SweepExpiredAPIKeys` are host-scheduled optional work: the module registers the sweep handler on `reg.Jobs`, but a host composes the per-tenant schedule itself, and one that runs no workers can boot with no queue at all. `Authenticate` checks `IsExpired` on every call, so an unswept, past-expiry row is refused correctly -- the sweep only reclaims disk, never correctness |
| `integration:apikey:rotate`/`:revoke` as separate permissions from `:manage`, or `integration:webhook:update`/`:delete` as separate permissions from `:manage` | The design's permission list treats each entity's lifecycle management as one capability |
| Soft-deleting `APIKey` | Already non-destructive via its own `RevokedAt` mark |
| Cascading `Restore`, or re-validating a restored `WebhookSubscription`'s `URL`/`EventTypes` against `Create`'s own rules | See "Soft deletion" below's known limitation |
| A production, non-demo inbound API gateway (request logging, per-route scope enforcement against `AuthenticatedAPIKey.Scopes`, a real product surface beyond the reference app's one demo route) | `AuthenticatedAPIKey.Scopes` is returned to the caller precisely so a REAL host can build that enforcement itself; this module ships no opinion on how a route maps to a required scope |
| Wiring `HTTPGuard`/`LayeredLimiter` in front of the session-authenticated management CRUD surface | Those exist to rate-limit a request AUTHENTICATED BY one of these API keys against a host's own inbound API surface; the CRUD surface is a tenant administrator managing their own keys through an ordinary session, gated by rbac exactly like every other module's management surface |

## Data model

**`integration_api_keys`** -- tenant data, isolation proven by `tenancytest.AssertIsolated` (`repository_test.go`), never `AssertNotTenantScoped`: a key belongs to exactly one tenant, never to the individual who created it (`CreatedBy` is an id reference, not an ownership tie).

**The primary key is `(id)` alone**, matching `go/storage`'s `Object` precedent rather than a composite `(tenant_id, id)` key: `id` is an application-generated UUID (`uuid.NewString`), globally unique on its own, so `tenant_id` rides along as a plain, non-key column promoted by the embedded `dbkit.TenantModel`.

**The key material is never stored.** `Hash` is the hex-encoded SHA-256 of the raw key value `Service.Create` generates once and returns to the caller; it is never persisted, logged, or returned by any other call. `keygen.go`'s `newAPIKeyToken` explains why plain SHA-256 (not a deliberately-slow password hash) is the right primitive here: the input is 32 bytes of `crypto/rand` full-entropy randomness, not a human-chosen secret, so there is no dictionary an attacker could use to make a slow hash worth paying for -- the same reasoning `go/org`'s invitation token hashing already documents. `Prefix` is the plaintext, non-secret display portion (`sk_` plus eight characters of the encoded random value) a key list shows so an operator can tell two keys apart without ever seeing the rest.

**Scopes are frozen at issuance, never re-derived.** `APIKey.Scopes` is the subset of `CreatedBy`'s permissions `Service.Create` validated at the moment the key was issued, through the mandatory `PermissionLister` seam. A later change to the creator's own permissions -- promoted, demoted, or removed from the tenant entirely -- never widens or shrinks an already-issued key; the design is explicit that a key's scope does not change along with its creator's later permission changes. Changing what a key may do means issuing a new one (`Rotate`); nothing in this module ever rewrites `Scopes` after `Create`.

**The creator leaving does not revoke the key.** `CreatedBy` is the responsible party on record, not an ownership tie -- the design is explicit that it is unacceptable for an integration to break just because someone left the tenant. `APIKeySummary.CreatorLeft`, computed at `List` time through the optional `MembershipChecker` seam, is the visibility the design does ask for, so a tenant administrator notices a key needs a new owner of record without the key itself being touched.

**Every key has a mandatory, forced expiry.** `ExpiresAt` is required; `Service.Create` defaults an unspecified request to the Service's configured lifetime -- `WithMaxAPIKeyLifetime`'s value when the host set one, `MaxAPIKeyLifetime`'s one year otherwise -- from now, and refuses a request asking for anything further out than that same lifetime (`ErrExpiryExceedsMaximum`) or already past (`ErrExpiryInPast`), per the design's forced-expiry-ceiling rule -- a key that never expires is the most common credential-leak surface, so this is refused rather than silently clamped. The ceiling and the unspecified-request default are deliberately one number, whether that number is the package default or a host's configured one.

**`integration_webhook_subscriptions`** (`WebhookSubscription`, `webhook_model.go`) -- tenant data, isolation proven by `tenancytest.AssertIsolated` (`webhook_repository_test.go`), primary-keyed `(id)` alone on the identical precedent above. `URL` (validated by `ValidateWebhookURL` at creation and update time), `EventTypes` (a JSON array of PUBLIC event types, never internal `pkgcore.Event.Type` strings -- see that field's own doc comment for why the two vocabularies are kept apart), `Secret` (the per-subscription HMAC key, encrypted at rest under `WebhookSecretSerializerName` -- a host registers it with `dbkit.RegisterEncryptedSerializer` before opening the database, exactly like `go/org`'s `EmailSerializerName` and `go/notification`'s `ContactAddressSerializerName`), `Active` (the pause/resume gate), `CreatedBy`. The model implements `dbkit.SoftDeletable` (see "Soft deletion" below).

**`Secret` is reversibly encrypted, never hashed -- unlike `APIKey.Hash`.** This is the one place the storage choice looks, at a glance, like it contradicts "the key material is never stored" above. It does not: an API key hash only ever needs to be COMPARED (a lookup by hash), while a webhook secret must be READ BACK IN PLAINTEXT on every delivery attempt to compute that attempt's HMAC signature (`webhook_signature.go`'s `signWebhookPayload`). A one-way digest cannot serve that purpose. See `WebhookSecretSerializerName`'s own doc comment in `webhook_model.go` for the full argument, including why the encryption key must be a different secret from any blind-index key (`dbkit.NewCipher`'s own doc comment). The column's PostgreSQL type is `BYTEA` (migration `0005_fix_webhook_secret_column_type.sql`), because AES-256-GCM ciphertext is binary data PostgreSQL's UTF-8 encoding would refuse in a `VARCHAR`; SQLite needs no sibling change.

**`integration_webhook_deliveries`** (`WebhookDelivery`, `webhook_model.go`) -- tenant data; the delivery log the design requires: `SubscriptionID`, `EventType`/`EventVersion` (the PUBLIC identity, copied from the `EventMapping` that produced the row), `IdempotencyKey` (the fan-out dedupe key, `deriveWebhookDeliveryKey` in `webhook_delivery.go`), `Payload` (the exact rendered body, computed once and never recomputed on retry -- see that field's own doc comment for why), `Status` (`DeliveryStatusPending`/`Failed`/`Delivered`/`DeadLetter`), `Attempts`, `LastStatusCode`, `LastError`, `LastAttemptAt`, `DeliveredAt`. **One row per (subscription, observed occurrence), not one row per HTTP attempt** -- a retry updates the SAME row in place; see the type's own doc comment for why. `idx_integration_webhook_deliveries_subscription_created_at` serves `Service.ListRecentWebhookDeliveries`'s read; `uq_integration_webhook_deliveries_tenant_subscription_key` is what makes fan-out idempotent under an at-least-once `EventBus`.

**`integration_api_key_hash_index`** (`apiKeyHashIndex`, `model.go`, migration `0006`) -- a narrow, two-column (`hash` primary key, `tenant_id`) platform-data table -- deliberately NOT `dbkit.TenantScoped`, isolation proven by `tenancytest.AssertNotTenantScoped` rather than `AssertIsolated` -- mirroring `go/sharing`'s `shareTokenIndex` almost exactly. It exists for one reason: `Service.Authenticate` must resolve a presented raw key's owning tenant BEFORE any tenant is in context at all (a genuinely inbound request authenticated by nothing but the key carries no separate tenant claim), and `integration_api_keys` cannot answer that -- it IS `dbkit.TenantScoped`, so a query against it with no tenant in context fails closed at the GORM plugin layer (`go/dbkit/tenant_scope.go`), and reaching around that with `db.Table`/`db.Model`/`db.Raw` would be exactly the bypass the Repository rule forbids. `APIKeyRepository.createWithHashIndex` writes both this row and its `APIKey` row in one transaction (`Service.Create`, and therefore `Service.Rotate` too); `tenantForHash` reads it with no tenant predicate at all (`APIKeyRepository`'s one deliberate exception to "every query is tenant-scoped"); `byHash` performs the ordinary tenant-scoped read once a tenant is resolved. The row is never updated or deleted by `Service.Revoke`, `Rotate` or anything else, with one deliberate exception: the API-key expiry sweep removes the pair together -- key row and hash-index row in one transaction, `APIKeyRepository.deleteWithHashIndex` -- once the key's `ExpiresAt` has passed, which is outward-safe because `Authenticate` answers a swept key the identical `ErrAuthenticationFailed` it always did, now at the tenant-resolution step. Otherwise the row stays in place after a key is revoked or expires, exactly like `shareTokenIndex` stays in place after a share is revoked, because `Authenticate` needs it to resolve a tenant and reach the ordinary read even for a key that will then be refused for being revoked or expired, answering with the identical `ErrAuthenticationFailed` a wrong key gets. See `model.go`'s own `apiKeyHashIndex` doc comment for the full "why a new table, not the existing `(tenant_id, hash)` index" argument.

## Soft deletion

`WebhookSubscription` implements `dbkit.SoftDeletable` (`DeletedAt *time.Time` / `DeletedBy string`, the exact field shape and tags `examples/reference-app/internal/notes.Note` established as the precedent, and that `go/org`'s `OrgNode`/`Membership` and `go/rbac`'s `RoleBinding` both reused). That flips `dbkit.Repository[WebhookSubscription].Delete` -- called by `Service.DeleteWebhookSubscription`'s `webhookRepo.Delete(ctx, id)` -- from a physical `DELETE` onto a mark-delete `UPDATE`, and gives the model a working `dbkit.Repository[WebhookSubscription].Restore`, which `Service.RestoreWebhookSubscription` wraps.

**`WebhookSubscription` alone, of this module's models.** `APIKey` is untouched: `Service.Revoke` already sets `RevokedAt` through an ordinary `repo.Update` call and never calls `Delete` at all, so it already followed the "mark, don't destroy" philosophy natively, with its own domain-specific state field -- adopting `SoftDeletable` on top of that would add a second, redundant deletion mechanism to the same row. `WebhookDelivery` is untouched too: it is a transient, append-only delivery-attempt log with no `Delete` operation anywhere in this module, the identical "nothing to retrofit" reasoning `go/rbac` applied to `Role`/`RolePermission`.

**No partial-unique-index conversion needed, unlike `go/org`'s and `go/rbac`'s identical adoptions.** Both of those needed one because the table they touched carried a real unique index a soft-deleted row would keep occupying, permanently blocking reuse of the same tuple. `integration_webhook_subscriptions` carries no unique index beyond its primary key -- `idx_integration_webhook_subscriptions_tenant_active` (migration `0002`) is a plain, non-unique index, so a mark-deleted row occupying it reserves nothing another row would need. Migration `0004_add_soft_delete.sql` therefore adds only the two soft-delete columns, with no index change at all.

**`DeleteWebhookSubscription`'s behavior is unchanged by the mechanism swap.** `dbkit.Repository[T].Delete` reports `dbkit.ErrRecordNotFound` on zero rows affected whether the branch taken is a physical `DELETE` or a mark-delete `UPDATE` -- the promoted method's contract is unchanged, and so is `webhook_delivery.go`'s `handleDeliveryJob`: its own `webhookRepo.FindByID` lookup on a delivery's subscription is hidden from a mark-deleted row by dbkit's soft-delete auto-scope plugin exactly as a physical `DELETE` would hide it, so an in-flight delivery enqueued before a subscription's deletion still resolves `dbkit.ErrRecordNotFound` and settles terminal (`TestService_handleDeliveryJob_SubscriptionMarkDeleted_DeliveryRowUnaffected` pins this explicitly). `handleDeliveryJob` settles terminal ONLY on a genuine record-not-found (marked `"webhook subscription was deleted"`), while any other subscription-lookup failure -- a transient store error, a secret that no longer decrypts -- is returned so `jobs` retries it, never dead-lettered as if the subscription were the problem (see `handleDeliveryJob`'s own doc comment and its `RetriesNotDeadLetters` regression test).

**The Restore-safety decision: Restore always forces `Active = false`, a deliberate divergence from `go/org`'s and `go/rbac`'s own "changes nothing but the two soft-delete columns" precedent.** Both of those modules' `Restore` methods change nothing about the restored row beyond `deleted_at`/`deleted_by` (see rbac's `RestoreRole` doc comment for the reasoning in its own domain). This module does not carry that precedent over unchanged, because the two situations are not the same hazard. `go/org`'s and `go/rbac`'s `Restore` calls resume a purely INTERNAL fact -- an organization membership, an authorization grant -- evaluated fresh against the rest of the system on every read, with no further action happening on its own. Restoring a `WebhookSubscription` with `Active` still `true` is different in kind: `webhook_delivery.go`'s `handleDomainEvent` fans out to every ACTIVE subscription automatically, on every matching domain event, entirely without further human action. An unconditional restore would therefore silently resume POSTing the tenant's live event data to an external, third-party URL nobody has looked at again since the subscription was deleted, however long ago that was and however stale its URL or receiving system might now be -- a real-world side effect leaving this process, not an internal state change this codebase can reason about the safety of the way it can for an org membership or an rbac grant. `Service.RestoreWebhookSubscription` therefore always lands the restored subscription PAUSED (`Active = false`) regardless of what `Active` held at the moment of deletion, and lands the unmark and the pause in ONE guarded write (`WebhookSubscriptionRepository.restorePaused`, a single UPDATE whose WHERE requires `deleted_at IS NOT NULL` and whose SET clears `deleted_at`/`deleted_by` and forces `Active = false` together) -- never as a restore-then-pause pair of separate writes, whose between-the-writes window would leave the row live-and-active (the exact state the fan-out matches) and whose failed pause would leave it permanently restored-ACTIVE behind an `ErrInternal` (see `restorePaused`'s and `RestoreWebhookSubscription`'s own doc comments, and `webhook_service_test.go`'s `TestService_RestoreWebhookSubscription_NoDeliveryCanFireBetweenRestoreAndPause` and `TestService_RestoreWebhookSubscription_PauseWriteFailure_LeavesNoRestoredActiveSubscription`). This costs the caller exactly one extra explicit step -- an `UpdateWebhookSubscription` call setting `Active` back to `true` -- to resume delivery, the same "no implicit side effect on a structural edit" discipline org's `TreeService.Delete` applies when it refuses to re-parent orphans or cascade `Restore`. Beyond that one field, `RestoreWebhookSubscription` follows the established precedent exactly: it does not re-validate the row against `CreateWebhookSubscription`'s own preconditions (its URL is not re-run through `ValidateWebhookURL`, for instance) and reports the identical collapsed not-found signal `dbkit.Repository[T].Restore`'s own doc comment describes -- an id with nothing to restore and an id that exists but is not currently mark-deleted are indistinguishable, matching `go/org`'s `MemberService.Restore` and `go/rbac`'s `RestoreRole`.

**No cache-invalidation concern, unlike `go/rbac`.** `go/rbac`'s restore had to publish an event and have `Module.Attach` subscribe to it, because rbac caches authorization decisions per subject. This module caches nothing: `handleDomainEvent` calls `webhookRepo.ListActiveByTenant` fresh, straight against the database, on every single matching domain event. `Service.RestoreWebhookSubscription` therefore only needs `AuditActionWebhookSubscriptionRestore`, the audit-trail symmetry that completes the create/update/delete/restore quartet `auditActionDecls` declares; no domain event is published (this module publishes no domain event of its own on any webhook-subscription mutation, only audit records).

**Known limitation.** `RestoreWebhookSubscription` does not re-validate the restored row's `URL` against `ValidateWebhookURL` -- a caller wanting that re-checked calls `UpdateWebhookSubscription` afterward (which does re-validate on any `URL` change), the same "call the ordinary mutation for a full re-check" answer `go/rbac`'s own known limitation gives for `RestoreRole`.

## Seams

**`PermissionLister` (mandatory for any non-empty `Scopes` request).** `Service.Create` calls it exactly once per request to validate that the requested `Scopes` are a genuine subset of the creator's own permissions right now. `go/rbac`'s `Authorizer.ListPermissions(ctx, sub Subject) ([]string, error)` is the real, already-shipped method this interface mirrors structurally -- a host wires it with a one-line closure, spreading `rbac.Subject`'s two fields into plain parameters so this module needs no `rbac.Subject` value to call it. This module still does not import `go/rbac` for it, for the same reason `org.FeatureGate` and `rbac.SubtreeResolver` are structurally-typed seams rather than direct imports across the module boundary: `go/rbac` carries `dbkit`, `gorm` and its own migrations along with it, and every one of those becomes a cost every consumer of this otherwise storage-and-ratelimit-only module would pay just to reference one interface's shape. An empty `Scopes` request needs no lister at all -- there is nothing to check a request for zero scopes against -- so a `Module` built with no `WithPermissionLister` option can still issue scope-less keys; a non-empty request with none wired fails closed with `ErrPermissionListerUnavailable` rather than silently skipping the check. `validateScopes` (service.go) is the one place that would change if `go/rbac` grew a genuine bulk "are these N permissions all held" call.

**`MembershipChecker` (optional).** Answers whether a given user is still an active member of a tenant, the one fact `Service.List` needs for `APIKeySummary.CreatorLeft`. Unlike `PermissionLister`, this is a display convenience, not a security control -- nothing about whether a key authenticates, what it may do, or whether it keeps working depends on `CreatorLeft`'s value. A host that wires none simply never sees the flag raised: `List` reports `CreatorLeft` as `false` for every row, exactly as if every creator were still active. Membership is owned by whichever module actually tracks who belongs to a tenant -- `go/org`'s roster in this codebase, but nothing requires that; the design's own text only ever says "creator has left", never naming `org` or `authn` as the source of truth, so this is a structurally-typed interface exactly like `org.FeatureGate` and `rbac.SubtreeResolver`.

**`SubjectResolver` (optional, but mandatory for the two request-body operations).** Reports the user id of a request's authenticated caller, read by `integration_createAPIKey` and `integration_createWebhookSubscription` -- the two operations whose payload carries a `CreatedBy` -- and passed on as their input's `CreatedBy`. Every other mounted operation needs no caller identity at all: `List` reads only the tenant; `Rotate`/`Revoke` resolve `CreatedBy` from the EXISTING key row (`Service.Rotate` carries the predecessor's own `CreatedBy` forward); webhook update preserves the existing row's `CreatedBy`; delete, restore and the deliveries listing need no creator. It is the identical structurally-typed, no-import seam `org.SubjectResolver` and `notification.SubjectResolver` declare -- same signature, same contract, so a host implementing either can hand the identical value to `WithSubjectResolver` here with no adapter code. A nil resolver, or one that reports `ok=false`, makes the two creates fail closed with `ErrSubjectUnresolved` rather than inventing a default creator.

Both function-shaped seams follow the `PermissionListerFunc`/`MembershipCheckerFunc` adapter shape `http.HandlerFunc` popularized, so a host wires a closure without declaring a named type.

**`EventMapping` / `WithEventMapping` (optional -- a `Module` with none declared simply never subscribes to anything).** See `eventmapping.go`'s own doc comment for the full design rationale; summarized here because it is the module's central outbound-webhook design decision. The design requires an explicit internal-event-to-public-schema mapping layer. Implementing that literally would mean adding a field to `pkgcore.Registry` -- the dependency floor of the whole monorepo; widening its contract is a decision for whoever owns it, not a side effect of one module -- or `go/integration` importing every business module directly, which the module-boundary rule forbids outright. `WithEventMapping` is the third option: a `Module` construction-time `Option`, wired by the HOST (which already imports both the business module and `go/integration`, the one place in the whole program allowed to see across every module boundary at once), following the EXACT shape `WithPermissionLister`/`WithMembershipChecker` established for reaching a sibling module without an import edge. A business module's own `Register` call still contributes the CATALOG half of the mapping contract for free and unprompted: `pkgcore.EventDecl`'s own doc comment already says declaring an event is "a documentation and mapping contract" `integration` is meant to read; only the TRANSFORM function -- code, not data, closing over a payload shape `go/integration` may not import -- needs the host's hand, and only the host sits above both modules to provide it.

`WithEventMapping` must run before `Module.Register`, unlike `WithPermissionLister` (whose seam is read lazily, at call time): `Register` subscribes to every declared mapping's `InternalType` on `reg.Events` synchronously, during the one legal declaration phase (`reg.Events.Subscribe` performs no I/O, so this stays inside `Register`'s "must not perform I/O; it only declares" contract), and it can only subscribe to what `NewModule`'s options have already told it about.

**`WithWebhookURLValidator` / `WithWebhookHTTPClient` (optional, test/demo seams -- a `Module` with neither declared gets `ValidateWebhookURL`'s and `newSafeHTTPClient`'s real, strict production behavior, unchanged).** The seams exist because the repository has no way to stand up a "real" receiver an offline test can prove a genuine signed HTTP delivery against without hitting exactly the class of address SSRF protection exists to refuse: every receiver process this repository's own test infrastructure can stand up offline (an `httptest.Server`, or a sibling Docker container reached the way this repository's other Docker-backed integration tiers reach theirs) resolves to either loopback or RFC 1918 private address space, both of which `ValidateWebhookURL`'s real, unmodified SSRF check correctly refuses -- there being no such address for a real receiver a test controls, this is not a gap the module's own design left open by oversight, it is the SSRF protection working exactly as intended against the one class of address every offline receiver happens to have.

Both options must be wired TOGETHER, never one alone: `WithWebhookURLValidator` overrides only the creation-time check (`Service.CreateWebhookSubscription`/`UpdateWebhookSubscription`), while `WithWebhookHTTPClient` overrides only the dial-time transport a delivery attempt actually sends through (`Service.attemptDelivery`) -- overriding one without the other would either refuse the subscription before it is ever created, or accept it at creation time only to have every delivery attempt refused at dial time instead. This mirrors pkgcore's own identical precedent, `WithHTTPSMSSenderClient` (`pkgcore/http_sms_sender.go`), which exists for the exact same reason against its SSRF-guarded SMS gateway client. A production host must never call either: doing so does not weaken any OTHER `Module`'s or any OTHER composition's SSRF enforcement (each `Module` instance carries its own `urlValidator`/`httpClient` fields), but it does weaken THIS instance's, permanently, for as long as that instance runs.

**`WithAuthenticationGuard` (optional).** Wires the rate-limit guard `AuthMiddleware` applies to authentication attempts BEFORE any `Authenticate` call -- see the "Rate-limiting belongs OUTSIDE authentication" paragraph for why that ordering exists and what pre-auth `Extractor` identifiers mean. Read at build time when `AuthMiddleware.Middleware` wraps the chain (the guard's whole effect is the composition it produced then; there is deliberately no setter that could make a post-construction change look effective); a `Module` built without it behaves exactly as it always did.

## Rate limiting

`LayeredLimiter.Allow` evaluates the global, tenant and key layers in that fixed order, short-circuiting on the first denial: a request already known to be denied at the global layer never touches the tenant or key counters at all. A zero-value `ratelimit.Limit` on any of `LayeredLimits`' three fields disables that layer entirely (`Allow` never calls the underlying `Limiter` for it), so `LayeredLimits{}`'s zero value legally disables all three -- every request is allowed. A negative `Rate` is refused up front as a configuration error, never treated as a second "disabled" spelling. This module never modifies `go/ratelimit` itself; the three layers are entirely a composition of its existing `Limiter.Allow(ctx, key, limit)` call, one per layer, matching the design's own layering description.

`HTTPGuard.Middleware` wraps an `http.Handler`, deriving the tenant and key dimensions from the request through a host-supplied `Extractor` function -- this module takes no position on how a host authenticates a request or resolves its tenant. A denied `LayeredDecision` becomes a 429 with `Retry-After` (whole seconds, rounded up per RFC 9110), `X-RateLimit-Remaining` (hits left), `X-RateLimit-Layer`, and `X-RateLimit-Reset` -- which carries the instant the window resets as a Unix EPOCH timestamp in seconds (GitHub's semantics for that header name; the seconds-until-reset countdown has its own home in `Retry-After`); an error from the underlying limiter itself (a `KVStore` failure) becomes a 500, never a silent allow -- `go/ratelimit.Limiter`'s own doc comment is explicit that it decides no fail-open policy on the caller's behalf, and `HTTPGuard` honors that.

**Rate-limiting belongs OUTSIDE authentication.** `WithAuthenticationGuard` (a `Module` option; see Seams) lets `AuthMiddleware` run a guard over authentication attempts themselves, BEFORE any `Authenticate` call: a request bearing a forged `X-API-Key` otherwise reaches `Authenticate`'s lookups with no bound at all -- it is refused, but refused after paying for two database lookups, and never charged against any rate-limit budget, since a guard composed behind authentication never even sees it. The guard's `Extractor` runs pre-auth, so it derives no resolved tenant/key (empty identifiers are ordinary keys to `LayeredLimiter.Allow`); a host may also derive identifiers from the request itself, authn's login-limit precedent being the model (attempt limits per identifier and per IP, checked before the credential is).

## Outbound webhook delivery

**The pipeline (`webhook_delivery.go`).** `Module.Register` subscribes `Service.handleDomainEvent` (through a `Module`-level forwarding wrapper the same shape `webhookDeliveryHandler` uses for the job side, both explained in "Register-time wiring, Attach-time Service" below) to every declared `EventMapping.InternalType`. On a matching event: skip if the event carries no tenant (mirroring `org.handleUserCreated`'s identical no-tenant skip); list the tenant's ACTIVE subscriptions whose `EventTypes` includes the mapping's `PublicType` (`matchingSubscriptions` -- a Go-side filter over a JSON column, never a SQL one, per the dual-dialect rule); run the mapping's `Transform` and wrap it in the versioned public envelope `{event: {type, version}, data: ...}` (`buildEnvelope`); for each matching subscription, create (or, on a redelivery, find) the `WebhookDelivery` row under its derived idempotency key and enqueue one `jobs.Task` (job type `integration.webhook.deliver`) per subscription. **`handleDomainEvent` NEVER returns a non-nil error** -- the in-memory `EventBus`'s `Publish` joins a subscriber's error back into the PUBLISHING module's own call, so a webhook wiring problem here must never surface as a failure of, say, `org`'s own membership-creation call. Every failure is logged at `Warn` and swallowed, the identical resilience contract `org.handleUserCreated` documents for the identical reason.

**Delivery execution (`Service.handleDeliveryJob`, the `jobs.Handler` half).** One HTTP `POST` of the row's stored `Payload` to the subscription's `URL`, signed per "HMAC signing" below. A subscription deleted or paused after its delivery was enqueued is treated as terminal (no retry) rather than retried against a receiver the tenant no longer wants, or one that no longer has a secret to sign against. A 2xx response settles the row `DeliveryStatusDelivered`; anything else -- a non-2xx status or a transport error -- settles it `DeliveryStatusFailed` and returns the error, which is `jobs`' own signal to retry.

**Retry and dead-lettering.** Enqueued with `jobs.WithMaxRetries(webhookMaxRetries)` (6, chosen deliberately larger than `jobs.DefaultMaxRetries`'s 3 -- a webhook receiver is far more likely to be down for a transient few minutes than an in-process handler is). `jobs.StandaloneQueue` (or the distributed mode's asynq-backed queue) owns the exponential backoff and the retry-count bookkeeping entirely -- this module adds none of its own, per `go/jobs`'s own retry contract. Once retries are exhausted, `jobs` calls this module's `jobs.FailureHook.OnFailure` (`Service.onWebhookDeliveryDeadLetter`, wrapped the same way `handleDeliveryJob` is), which settles the row `DeliveryStatusDeadLetter` -- the rule that business compensation belongs to the business module, never the queue layer, applied here as simply recording the terminal state.

**HMAC signing (`webhook_signature.go`).** Every delivered request carries `HeaderWebhookID` (the delivery's own id, for a receiver's own dedupe), `HeaderWebhookTimestamp` (Unix seconds), and `HeaderWebhookSignature` (`"v1=" + hex(HMAC-SHA256(secret, "<timestamp>.<raw body>"))`). The timestamp is signed INSIDE the covered content, not merely alongside it as an unsigned header -- see `webhook_signature.go`'s own file comment for why that is what makes replay rejection possible at all (a captured genuine pair cannot be replayed under a forged, later timestamp). `WebhookReplayTolerance` (5 minutes) is exported purely as documented guidance for a receiver's own verification code; this module signs and stamps, and has no receiving side of its own to enforce the tolerance against.

**SSRF protection, at two different times (`ssrf.go`).** `ValidateWebhookURL` runs at subscription creation and update time: refuses a malformed URL, a disallowed scheme, or one resolving to any loopback/private/link-local/multicast/CGNAT address (`isBlockedIP`). `newSafeHTTPClient`'s `Transport.DialContext` re-validates the CONNECTING address on every delivery ATTEMPT, dialing the specific IP it just checked directly rather than trusting a second, independent hostname resolution -- this is what actually defeats DNS rebinding (a URL whose DNS answer changed between subscription creation and delivery), which a creation-time-only check cannot. It also automatically covers HTTP redirects, since Go's `http.Client` re-dials through this same guarded `DialContext` for a redirect's `Location`. Both refusals apply the SAME no-oracle rule to their error text: a blocked destination reached through DNS is reported without the resolved address, since echoing it would turn the refusal into an internal-DNS reconnaissance oracle -- the creation-time half carries no `ip` param for the resolution path (`errors.go`'s `ErrWebhookURLBlocked` doc comment), and the dial-time half's refusal text names the host alone (the caller's own, zero disclosure), the resolved address going to the server-side log at the refusal site instead, never into the delivery row's `LastError` -- which the deliveries-log API serves back to the tenant.

**Fan-out idempotency.** `deriveWebhookDeliveryKey` hashes `(subscriptionID, publicType, publicVersion, renderedBody, occurrenceAt)`; `handleDomainEvent` probes for an existing `WebhookDelivery` under that key before creating a new one, and `uq_integration_webhook_deliveries_tenant_subscription_key` is the database-level backstop for two concurrent handlers racing the same event. `jobs.Task.IdempotencyKey` is set to the identical key as a second, independent line of defense at the queue layer. `occurrenceAt` is the fan-out's occurrence marker: one reading of the service clock, stamped at the subscription boundary per event arrival. It is what stops the dedupe from silently dropping a genuinely NEW occurrence whose public body is byte-identical to an older one's (a member removed and later re-added, when the mapping's payload names only the member) -- a lost delivery a receiver can never recover. The trade: `pkgcore.Event` carries no occurrence identity of its own (no id, no timestamp), so a redelivery observed at a later clock reading is treated as a distinct occurrence and delivered again -- at-least-once behavior receivers dedupe against through `HeaderWebhookID` -- while a same-instant redelivery still merges. See `deriveWebhookDeliveryKey`'s and `enqueueDelivery`'s own doc comments.

**Register-time wiring, Attach-time `Service`.** `Module.Register` must subscribe to events and register the job handler before a `Service` exists (`Service` is built in `Attach`, which runs strictly after `Bootstrap` returns). Both `Module.handleDomainEvent` and `webhookDeliveryHandler` (a small `jobs.Handler`/`jobs.FailureHook` adapter type) are `Module`-level forwarding wrappers: they read `m.service` at CALL time (which, for real traffic, is always after `Attach` has run) and log-and-swallow (event side) or return a retryable error (job side) on the rare case they run before it. `Handler` is built the same way, for the same reason -- see `handler.go`'s own "Built differently from every other module's Handler" doc comment.

**Inbound authentication.** The demo route `examples/reference-app/internal/app/integration_authenticate.go`'s `IntegrationWhoamiPath` (`GET /api/v1/demo/integration/whoami`) is a minimal, deliberately-labeled demo endpoint -- explicitly NOT a real product feature -- gated by `integration.AuthMiddleware` carrying a rate-limit guard wired through the module's `WithAuthenticationGuard` option, so the guard runs BEFORE any `Authenticate` call: a forged or unrecognized `X-API-Key` request pays the guard's budget instead of reaching `Authenticate`'s lookups with no bound at all, and once that budget is spent answers 429 with authentication never running. The route carries no `rbac.Authorizer` dependency and needs none: unlike the session-authenticated, permission-checked management actions, this route IS the authentication layer for a different kind of caller entirely (a script or third-party system holding nothing but the API key itself) -- `Authenticate`'s own refusal is the whole of this route's access control. `examples/reference-app/cmd/server/apikey_authenticate_flow_test.go` drives create (through the ordinary session-authenticated CRUD surface) → authenticate with the fresh raw key (succeeds, resolving the right tenant and key id) → authenticate with no credential (refused) → authenticate with a never-issued key (refused, identically) → rotate → authenticate with the OLD raw key (refused) → authenticate with the NEW key (succeeds) → revoke → authenticate with the now-revoked key (refused, identically to every other refusal reason) -- through the composed HTTP stack.

**The permission-gate mismatch the module's own three-segment permission names force on any rbac-gated host.** `internal/app/demo_subject.go`'s router-level gate reproduces `rbac.RequirePermissionFunc`'s fail-closed shape by hand rather than calling it, because `rbac.RequirePermissionFunc` splits a permission string on its FIRST colon (`splitPermission`, `go/rbac/middleware.go`) and refuses outright, regardless of what the caller holds, when the action half contains a SECOND colon -- and this module's permission strings (`"integration:apikey:read"`, `"integration:webhook:manage"`, ...) are exactly that shape, so the convenience wrapper cannot gate this fragment's routes at all. `integrationPermissionFor` picks the permission a request must hold by sub-path (`/webhooks` → the webhook pair, otherwise the apikey pair), and the gate cuts its answer at the LAST colon into `resource` and `action` (`"integration:apikey"` and `"read"`/`"manage"`, or `"integration:webhook"` and the webhook pair's own two verbs), calling `az.Can` directly. The gate reads `X-Demo-User` through `DemoSubjectResolver` to decide WHO may act; the handler-side `CreatedBy` attribution goes through the module's own `integration.SubjectResolver` seam (this app's `DemoOrgSubjectResolver`), which reads `X-Demo-User-Id` alone -- a create that passes the gate but carries no `X-Demo-User-Id` is refused 401 `integration.subject_unresolved`, never attributed to a default user.

## Known limitations

- **`Rotate` is not atomic.** The new key's `Create` and the predecessor's `Revoke` are two separate database writes, not one transaction -- `dbkit.Repository[T]` exposes no cross-call transaction seam a business module can reach. A failure between the two leaves two live keys rather than zero, a safe-direction surplus (never a lockout) that `Rotate` reports to its caller rather than silently swallowing. See `service.go`'s `Rotate` doc comment for the full argument.
- **The API-key expiry sweep is host-scheduled optional work, never an automatic job.** `Service.EnqueueAPIKeyExpirySweep`/`Service.SweepExpiredAPIKeys` exist (the sweep handler is registered on `reg.Jobs` during `Register`), but nothing schedules them -- a host composes the per-tenant schedule as it sees fit, and a host that runs no workers can boot this module with no queue at all and is never forced to wire one it cannot drain. Correctness never depended on the sweep: `Authenticate`'s per-call `IsExpired` check refuses an unswept, past-expiry row correctly -- the sweep only reclaims disk.
- **`MaxAPIKeyLifetime` is a package constant and a NewModule option, never a go/config item.** Reading a ceiling from `go/config` would add a dependency edge this module's position in the module graph does not have, paid for by every consumer that boots this module without config; a host that needs a different ceiling-and-default configures `WithMaxAPIKeyLifetime` instead.
- **`RestoreWebhookSubscription` does not re-validate the restored row.** See "Soft deletion" above's own Known limitation.
- **Manual redelivery is Service-level only; no HTTP surface mounts it.** `Service.RedeliverWebhookDelivery` re-enqueues a specific dead-lettered delivery of the caller's tenant (only dead-lettered rows may be redelivered; the re-enqueued job runs under a fresh cycle-scoped key; the row flips back to pending under a guarded write). A consumer that needs redelivery on the wire drives a fragment operation from the method.
- **A dead-lettered delivery is not distinguished from a "the subscription was deleted/paused" early refusal in `Status` alone.** Both settle as `DeliveryStatusDeadLetter` (see `handleDeliveryJob`'s own doc comment for why reusing the one terminal-failure status was chosen over inventing a third) -- an operator tells them apart by `LastError`'s text, which is not a stable, matchable code. Distinguishing them programmatically would need a real code here instead of free text.
- **A delivery's `Payload` is computed once, at fan-out time, from whatever the `EventMapping.Transform` produced then.** If a later release changes what a `Transform` returns for the SAME `PublicVersion` (a bug fix within a version, not a genuine schema break), an already-enqueued-but-not-yet-delivered row still sends the OLD rendering on retry. This is intentional -- an HMAC signature must cover a byte-for-byte stable body across every retry of one delivery -- but is worth knowing before "just retry it" is assumed to pick up a mapping fix.
- **Delivery is not exactly-once on the send side.** A crash between the receiver accepting the request and this module's own `Update` call recording `DeliveryStatusDelivered` leaves the row `DeliveryStatusPending`/`Failed`, and the next retry re-sends -- a real, if narrow, double-delivery window, the same class of gap `go/notification`'s own delivery pipeline documents for its identical settle-after-send shape.
- **No per-tenant or per-subscription delivery-volume rate limiting.** Unlike the three-layer `LayeredLimiter` for inbound API traffic, nothing bounds how many webhook deliveries one tenant's event volume can generate. Not named in the design's webhook paragraph.

## Adjudications a reviewer should not "correct"

**The primary key is `(id)` alone, not `(tenant_id, id)`.** See "Data model" above -- `id` is a globally-unique application-generated UUID, matching `go/storage`'s `Object` precedent rather than the composite-key shape a module-local id would need.

**Rate limiting is never hard-wired to any specific storage key naming beyond this module's own `layerStorageKey` prefix.** `LayeredLimiter.Allow` treats `globalKey`, `tenantKey` and `apiKeyID` as opaque caller-supplied strings, exactly as `go/ratelimit.Limiter.Allow` itself treats its own `key` parameter -- this module adds no interpretation of what those strings mean.

**`Rotate` carries `Scopes` forward from the predecessor, but re-validates them against the creator's CURRENT permissions rather than trusting them as already-proven.** This is not a bypass of `Create`'s own scope check: routing the predecessor's scopes back through `Create` means a creator whose permissions shrank since the predecessor was issued can have a `Rotate` fail with `integration.scope_not_held_by_creator` on a scope it no longer holds. This is a deliberate, safe-direction consequence of "scope validation happens at issuance" applying to every issuance, including a rotation's, not a special carve-out.

**`ExpiresAt` is NOT carried forward on `Rotate`.** A rotation gets a fresh full-lifetime expiry (`Create`'s own default), not a continuation of the predecessor's absolute timestamp -- copying that timestamp would defeat the point of rotating a key that is itself close to (or, for a caller rotating a stale-but-still-live key, already past) its own expiry. The create and revoke halves are NOT one transaction either -- `dbkit.Repository[T]` exposes no cross-call transaction seam -- and the surplus of two live keys on a mid-way failure is reported to the caller, never silent.

**`WebhookSubscription.Secret` is reversibly encrypted, not hashed like `APIKey.Hash`.** See "Data model" above -- this is a deliberate divergence from "the key material is never stored", not an inconsistency: a webhook secret must be read back in plaintext to sign every delivery attempt, while an API key hash only ever needs to be compared.

**`EventMapping` is wired through a `Module` construction-time `Option` (`WithEventMapping`), never a `pkgcore.Registry` field.** See "Seams" above's `EventMapping` entry for the full rationale -- `pkgcore` is the dependency floor of the monorepo and its widening is not one module's decision, and the `Option` shape reuses the established seam-wiring convention.

**A dead-lettered delivery reuses `DeliveryStatusDeadLetter` for three distinct causes** (retries genuinely exhausted, the subscription was deleted after enqueue, the subscription was paused after enqueue) **rather than three separate statuses.** This was a deliberate choice to keep the state machine to the two terminal states `webhook_model.go`'s own doc comment documents (`Delivered`, `DeadLetter`) rather than growing a third and fourth just to distinguish "why" from "what" -- an operator reads `LastError`'s text for the why. See "Known limitations" above for the follow-up this leaves.

**`handleDomainEvent` and the job-side `webhookDeliveryHandler` are both `Module`-level methods/types, not `Service`-level, even though they forward almost everything to `Service`.** This is not incidental placement: `Module.Register` must call `reg.Events.Subscribe` and `reg.Jobs.Handle` before a `Service` exists at all (`Service` is built in `Attach`, which runs strictly after `Bootstrap`'s `Register` phase completes across every module) -- see "Register-time wiring, Attach-time `Service`" above.

**`RestoreWebhookSubscription` forces `Active = false`, unlike `go/org`'s and `go/rbac`'s own Restore methods, which change nothing beyond the two soft-delete columns.** Do not "fix" this into matching their precedent -- it is a deliberate, reasoned divergence, not an inconsistency this codebase forgot to bring into line. See "Soft deletion" above for the full argument: resuming automatic outbound HTTP delivery to an external, third-party URL is a materially different kind of side effect from resuming an internal permission or membership grant, and this module treats it accordingly.

**`migrations/postgres/0005_fix_webhook_secret_column_type.sql` has no `sqlite/` sibling.** Do not add one -- see "Data model" above for why SQLite genuinely needs no equivalent change, and `go/dbkit/migrations.go`'s `migrationFiles` for why `dbkit.MigrationRegistry.Apply` has no cross-dialect pairing requirement that would make an asymmetric migration set invalid.

**The HTTP-mounted CRUD surface does NOT sit behind `HTTPGuard`/`LayeredLimiter`, and this is not an oversight to "finish."** See "Deliberately not in scope" above for the full argument: those exist to rate-limit a request AUTHENTICATED BY an already-issued key against a host's own inbound API surface, never the ordinary, session-authenticated administrative act of managing one's own keys -- gated by rbac exactly like every other module's own management surface, none of which sit behind `go/ratelimit` either. Wiring the two together would conflate a request a key AUTHENTICATES with a request that merely MANAGES keys.

**`Handler` (`handler.go`) holds a `*Module`, not a `*Service`, unlike every other module's own `Handler`.** Do not "simplify" this to match org's/storage's/notification's/sharing's/admin's shape -- it cannot: this module's own `Service` is built in `Attach`, strictly after `Register`, so a `Handler` built during `Register` (as `reg.Routes.Mount` requires) has no `Service` to hold yet. Reading `m.service` at call time is the fix, mirroring `handleDomainEvent`'s and `webhookDeliveryHandler`'s own identical technique.

**`Service.Authenticate` resolves its tenant from the presented key alone and requires none in `ctx` -- unlike every other `Service` method, all of which call `pkgcore.MustTenantFromContext`.** Do not "fix" this into requiring a tenant in `ctx` too, and do not assume the migration `0001` comment on `uq_integration_api_keys_tenant_hash` ("every lookup this module ever performs already knows its tenant from request context") still describes this method -- it does not, and that comment is deliberately left unedited as a historical record rather than rewritten to match the actual design. See "Data model" above and `authenticate.go`'s own "Tenant resolution" doc comment section for the full argument: a genuinely inbound API-key-authenticated request carries no separate tenant claim of its own, the identical situation `go/sharing`'s `AccessPublic` answers for an anonymous share-link visitor, and `integration_api_keys` cannot answer it directly because it is `dbkit.TenantScoped` -- a query against it with no tenant in context fails closed, not open.

**`AuthMiddleware` (`middleware.go`) reads its bearer credential from `HeaderAPIKey` ("X-API-Key"), never `Authorization: Bearer`.** Do not "fix" this to match `go/authn.Middleware`'s more common convention -- it cannot, in any host whose outermost middleware layer is `go/authn.Middleware` (this reference app included): that middleware already claims the `Authorization` header globally and unconditionally, and its own doc comment states a present-but-unverifiable bearer credential is refused with an immediate 401 -- reusing `Authorization` for an API key would 401 every API-key-authenticated request at `go/authn.Middleware`, before `AuthMiddleware` (mounted below it in the chain) ever ran at all. See `middleware.go`'s own `HeaderAPIKey` doc comment for the full argument, including why this is a real, verified-in-tree conflict rather than a hypothetical one.

**The reference app's demo route (`IntegrationWhoamiPath`) is deliberately NOT gated by `rbac.Authorizer`.** Do not add a permission check here -- this route's whole purpose is to demonstrate authenticating a caller that holds nothing but the API key itself (a script or third-party system, never an authn session), so `Service.Authenticate`'s own refusal already is this route's access control; layering rbac on top would conflate two different callers' authentication mechanisms into one route.

**The partial-failure answers of the three creates are SUCCESS responses carrying `auditRecordMissing: true`, even though the underlying `Service` call returned an error.** Do not "fix" this back into an error response because Service returned `(created, err)` -- the HTTP translation is exactly the point: the operation succeeded as far as the caller is concerned (the key or subscription exists and works, its material shown exactly once), and the credential must not travel in an error envelope, a channel that flows into logs, tickets and bug reports rather than being treated as secret-carrying. Service's own `(created, err)` partial contract is unchanged and stays; only the wire translation of the partial is a success.

**The dial-time blocked-refusal text names the host but never the resolved address, and the delivery row's `last_error` therefore never carries an internal IP.** Do not "restore" the resolved address to the error text for debuggability -- the text is served back to the tenant through `integration_listWebhookDeliveries`, making it an internal-DNS reconnaissance oracle (the same reasoning `errors.go`'s `ErrWebhookURLBlocked` applies to the creation-time answer). The detail an operator genuinely needs is logged server-side through `obs` at the refusal site (`host`/`ip` attributes).
