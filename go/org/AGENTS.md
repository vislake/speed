# org

Multi-level organization trees for a tenant. This file is the module-level discipline that ships with `go/org` to consuming projects.

**Status.** The module ships the tree, the roster and the invitation flow (models, dual-dialect migrations, the tree operations, memberships, the `Scope` module consumers accept without importing org, invitations with their rate-limited delivery through the `pkgcore.Mailer` module, the resilient `authn.user.created` subscription, the registry wiring, the error catalog and the bilingual message bundle); the HTTP surface (`api/openapi.yaml`, the generated `api.ServerInterface`, `Handler`, the `SubjectResolver` module); the PostgreSQL `integration_test/` tier (the dialect-identity proof and all three repositories' `AssertIsolated` suite, re-run against a real server); and the reference app wired as this module's mandatory first consumer end to end (`examples/reference-app/internal/app/server.go`, `flowtests/org_flow_test.go`) — a multi-level tree, an invitation issued and accepted, and the roster read back correctly scoped to a subtree. `OrgNode` and `Membership` additionally implement `dbkit.SoftDeletable` (see "Soft deletion" below): `Delete`/`Remove` mark-delete instead of physically removing a row, and `TreeService.Restore` / `MemberService.Restore` undo that. What is not landed is named in this file's "Out of scope" table, the "Known limitations" section and "Soft deletion" below.

## Scope

**In scope.** The organization tree: one root per tenant, arbitrary depth beneath it, nodes carrying a business-defined `Kind`. Creating, renaming, moving and deleting nodes; ancestor, child, subtree and descendant queries. The roster: one membership per person per tenant, bound to a node, with the subtree beneath it as their data scope. Invitations: issuing, delivering, withdrawing and accepting them. The read-only `Scope` view authorization and data-visibility consumers use. The subscription that gives a brand-new user a workspace.

**Out of scope, deliberately.**

| Not here | Where it belongs | Why |
|---|---|---|
| `users` — the table, the type, the concept beyond an id string | `authn` | Identity data. org learns a user id from a domain event or an authenticated subject and stores nothing else — the canonical module-boundary example and the defining constraint of this module |
| Roles on a membership | `rbac` | The design sketches `Membership.Roles []string`; org does not store one. Role state is rbac's policy keyed by (tenant, user, node path), and a `[]string` column has no portable dual-dialect representation anyway — native arrays are banned |
| Sending anything other than the invitation email | `notification` | Business modules publish domain events and let subscribers decide what to send |
| Revoking a removed member's sessions | `authn` | org publishes `org.member.removed`; session state is authn's, and reaching into it is what the event exists to avoid |
| Reading `org.max_depth` / `org.invitation_ttl` from dynamic configuration | — | See "org declares no dynamic-config schema" |
| PostgreSQL RLS policies on `org_nodes` | Deployment / ops | `dbkit` supplies the session-variable wiring only; provisioning the role and the policy is deployment-side, per its own "Out of scope" |
| The authenticated `SubjectResolver` a real deployment needs | `authn` | This module ships only the interface and a fail-closed default (401 `org.subject_unresolved` when unwired). A real implementation reads a verified access token's claims |

## Adjudications

### Materialized path plus parent edge — not a closure table, not a recursive CTE

Each node stores `ParentID` (the authoritative structural edge) and `Path` (the derived query index). `TreeService` writes both together; a row where they disagree is corrupt, not a supported state.

A closure table costs O(depth) rows per node and rewrites O(subtree × depth) rows per move, to buy ancestor queries the path already answers by splitting a string in Go. A recursive CTE works on both engines today, but portability here is by construction rather than by "both happen to support it".

**The dialect-identity proof lives in `path.go`'s doc comment and is enforced by `path_test.go`**, not asserted in prose. Its load-bearing property: the id alphabet is `[0-9a-f-]`, so neither LIKE metacharacter (`%`, `_`) can occur, no `ESCAPE` clause is ever written, and — the real hazard — SQLite's ASCII-case-insensitive `LIKE` and PostgreSQL's case-sensitive one select identical rows, because no two distinct stored paths can differ only by case. **Changing the id scheme to anything containing uppercase characters (a Crockford-base32 ULID, say) breaks this and must not be done without re-adjudicating the whole representation.** `TestValidateNodeID_UUIDNewString_IsAlwaysInTheAlphabet` fails the build if the generator ever drifts.

The path carries a **trailing** separator, which is what makes "self and descendants" a plain prefix test for variable-length ids: `/a/` is not a prefix of `/ab/`, while `/a` would be. `TestSubtreePrefix_SiblingSharingAnIDPrefix_DoesNotMatch` and `TestTreeService_Move_SiblingSharingAnIDPrefix_IsNotDraggedAlong` pin it from both ends.

A move rewrites paths **in Go**, never with a SQL `replace()`. That keeps the only structurally risky operation free of dialect-specific SQL.

### `parent_id` is an empty-string sentinel, not `NULL`

The design sketches `ParentID *string`; the column here is `NOT NULL DEFAULT ''`. The sibling-uniqueness index is `UNIQUE(tenant_id, parent_id, name)`, and `NULL` is distinct from itself in a unique index on both engines — so two roots with the same name would coexist under `NULL`. `go/config/migrations/postgres/0001_create_configs.sql` solved the identical problem the identical way on its `tenant_id` column. `TestRepository_SiblingNameUniqueness_IsEnforcedByTheDatabase`'s last subtest is the regression guard.

### `org_nodes` is tenant data, and its primary key is `id` alone

Tenant data, so `Repository` embeds `dbkit.Repository[OrgNode]` and `tenancytest.AssertIsolated` — not `AssertNotTenantScoped` — is the correct suite.

`OrgNode` embeds `dbkit.TenantModel` rather than declaring `TenantID` with its own `primaryKey` tag, so the primary key is `id` alone. That is legitimate here for the same reason it is in `examples/reference-app/internal/notes`: the id is an application-generated UUID, already globally unique, so a plain indexed `tenant_id` column is enough. **Do not add a `primaryKey` tag by shadowing the promoted `TenantID` field** — `dbkit`'s `tenant_scope.go` documents exactly how that silently breaks `GetTenantID` and denies a row to its own owner.

One consequence worth knowing when writing tests: two tenants can never hold byte-identical *valid* paths, since paths are built from globally unique ids. The adversarial identical-path case is therefore exercised one layer down, against hand-seeded rows, in `repository_test.go`.

### Deleting never re-parents orphans

A node with children reports `org.node_has_children` unless the caller explicitly asks for a cascade. Re-parenting orphans to the grandparent would silently widen the data scope of every member bound beneath the deleted node — a privilege escalation performed by a delete. The tenant root is never deletable.

### Moving the root needs no rule of its own

Every node of a tenant descends from its single root, so every candidate target is one of the root's own descendants and the cycle check already refuses it (`org.cycle_not_allowed`). That falls out of the one-root invariant, which is database-arbitrated: `uq_org_nodes_single_root`, a partial unique index on `(tenant_id)` over the root-shaped rows — `WHERE parent_id = ''`, narrowed to live rows by `0008_single_root_live.sql`'s `deleted_at IS NULL` in the same way 0004 narrowed the sibling-name and membership indexes — admits at most one LIVE root row per tenant however it is created (a host writing through the exported `Repository` surface included), and a mark-deleted root's slot is free again the moment its mark-delete commits; `CreateRoot`'s `findRoot` pre-check plus a `gorm.ErrDuplicatedKey` translation into `org.root_already_exists` are the two faces of the same coded answer. Do not add a separate "root is not movable" branch -- with a second root unconstructible, every candidate target really is one of the single root's own descendants.

### `memberships` is LINK data, and link data IS tenant-scoped

This is the adjudication most likely to be "corrected" in review, so it is stated at length.

Link data is isolated by `tenant_id` exactly like tenant data, and `AssertIsolated` is mandatory for both. So `Membership` implements `dbkit.TenantScoped`, `MembershipRepository` embeds `dbkit.Repository[Membership]`, and `TestMembershipRepository_AssertIsolated` is the suite it runs.

The confusion this exists to prevent: `users` is identity data and is deliberately **not** tenant-scoped, because one person belongs to several tenants. That is precisely *why* the bridging row must be tenant-scoped — it is the per-tenant half of that relationship, and a membership readable across tenants would expose one tenant's roster to another. `AssertNotTenantScoped` on this table would assert the opposite of the requirement.

`org` creates no identity or platform table at all, so `AssertNotTenantScoped` appears nowhere in this module.

### The invitation email is the verification-class exception, not a waiver of it

The security rules forbid messaging an unverified address — the verification message itself is the only exception, and it is rate limited.

**The invitation IS that message.** It is the single consent-establishing message org ever sends, it carries the token the invitee is waiting for, and org sends **nothing else** to somebody who never accepts: no reminders, no automatic resends, nothing promotional. A new message only goes out when a member makes a fresh explicit `Invite` call, and that call revokes the previous token.

It is rate limited on two independent dimensions, composed by the caller as `ratelimit.Limiter`'s contract requires (one `Allow` per dimension, any denial denying):

| Key | Budget | Protects |
|---|---|---|
| `org:invite:tenant:<tenantID>` | 50 / hour | the platform, from a compromised member account |
| `org:invite:email:<blindIndex>` | 3 / 24h | the recipient, from being invited into harassment |

**The second key is built from the HMAC blind index, never the address.** A rate-limit key lives in the KV store, is visible in Redis and turns up in diagnostics; an email address in one is a PII leak. `TestInviteService_Invite_RateLimitKeyIsTheBlindIndexNotTheAddress` consumes the budget under the index-derived key and then shows the next invite denied — if the service ever keyed on plaintext, that test fails.

A notification module may subscribe to `org.member.invited` and take delivery over; a host that does turns the `org.invitation_email` flag off and this leg goes quiet with no code change.

### The invitation token is never stored, and the address is encrypted but queryable

The token is 32 bytes from `crypto/rand`, base64url-encoded for the link and returned exactly once in `InviteResult.Token`. The row keeps `token_hash`, the hex SHA-256 of it. A leaked backup therefore yields no usable link. (SHA-256 rather than a password hash is correct here: the input is full-entropy randomness, so there is no dictionary to slow anybody down with.)

`InviteResult.Token` is a bearer credential — whoever holds it joins the tenant. It must never reach an API response body, a log line, an event payload or a trace attribute. `TestMail_NoPlaintextTokenOrAddressInLogs` captures everything org logs through a whole invite-and-accept cycle and fails if either the token or the address appears.

The address is encrypted at rest through the serializer named by `org.EmailSerializerName`, registered by the module's own `org.RegisterEmailSerializer(cipher)` (which refuses a nil cipher rather than registering one that would silently store plaintext), and made queryable by the blind indexer the host builds with `org.NewEmailIndexer(key)` — the module's own constructor over its exported `EmailIndexColumn` and `dbkit.NormalizeEmail`, so the column's exact SQL name never crosses the host boundary as a hand-typed string (see that constant's doc comment for why dbkit refuses an empty name but cannot guard a wrong one) — the exact facility this repository's rules require instead of a reimplementation. Every write goes through `Index`, every lookup through `Equal`. **The blind-index key must be a different secret from the encryption key**; the two constructors enforce that separation by construction.

`dbkit.NormalizeEmail` performs a structural gate of its own when it indexes (no `@`, an empty side of the `@`, a second `@`, a dotless or edge-dotted domain, whitespace/control or non-ASCII characters, or an overlong address are all errors). org still runs `validateInviteEmail` first: the refusal must be org's coded `ErrInvalidEmail`, and it must land before the address costs a rate-limit slot or a mail attempt.

### Acceptance is tenantless

Acceptance cannot require the caller to already hold a bearer token scoped to the inviting tenant: org's accept handler resolves the invitation strictly inside the tenant the request context carries, so a genuinely freshly invited person — no membership in the inviting tenant, and therefore no sign-in and no token at all — could never accept. The invitation is delivered by email to the addressed mailbox, which is the whole consent story; demanding a pre-existing tenant claim on top of the token makes the very flow invitations exist for impossible. Acceptance therefore resolves the invitation's own tenant from the token itself.

The invitation's own tenant is data only the invitation row knows, and that row is tenant data — unreachable from a context with no tenant, by design and, in distributed mode, by RLS. So `Accept` on a tenantless context resolves the tenant through `org_invitation_token_index`, a narrow, deliberately non-tenant-scoped `token_hash -> tenant_id` table written in the same transaction as every invitation (createPending) and read by exactly one method (`tenantForTokenHash`), then attaches the resolved tenant with `pkgcore.WithTenant` and runs the ordinary tenant-scoped flow unchanged — status checks, the single-use compare-and-swap, the membership creation, the event. The index row is never updated: a revoked or expired token still resolves its tenant so the tenantless path answers `org.invitation_revoked` / `org.invitation_expired` rather than a misleading "no such invitation". This is go/sharing's `AccessPublic` shape (its own `sharing_token_index`), adopted for org's invitation token; `invitationTokenIndex`'s doc comment in invitation.go carries the full data-domain argument, and `TestInvitationTokenIndex_AssertNotTenantScoped` proves the platform-data property.

The acceptor's IDENTITY is unchanged by the tenantless resolution: `SubjectResolver` attests who is accepting (the host's verified caller), the body carries the token only, and an unidentifiable caller is refused with `org.subject_unresolved`. A token is a bearer credential delivered to one mailbox; org cannot and does not verify that the acceptor's account owns that mailbox — in this codebase's model that verification belongs to the authenticating side (the host's own sign-in/identity story), and the recorded stance in the reference app's flow tests still holds: only the invitation's own email is what the token binds to.

Hosts must let the accept path through their own tenant-resolving middleware for the tenantless flow to work — the same allowlist treatment `go/sharing`'s public access path needs: `examples/reference-app` allows POST `/api/v1/org/invitations/accept` in tenancy.Middleware (internal/app/server.go's BuildServer), while every other org route stays behind tenant resolution. A host that does NOT allowlist it keeps tenant resolution in front of the accept path, memberless invitees included — its composition choice.

### Deleting a node with members in it is refused

`TreeService.Delete` asks the roster whether anybody is bound inside the subtree, and reports `org.node_has_members` if so — for a cascade as well as for a leaf. Without it a cascading delete would leave memberships pointing at rows that no longer exist, and a dangling membership is a person whose data scope can no longer be resolved.

org refuses rather than deleting the memberships too, for the same reason it refuses to re-parent orphans: silently changing who is in a tenant, or what they can see, is not something a structural edit should do on its own. Move the members first.

(`ScopeService.MemberNodeIDs` still fails **closed** on a dangling row it should never see — empty set plus a `Warn`, never an error and never everything.)

**The check runs inside the same locked transaction as the delete, not as a separate read before it.** A roster check as its own separate, unlocked read entirely BEFORE `deleteLeaf`/`deleteSubtree` ever opened their own transaction would leave a real, wide-open TOCTOU window on both dialects (no PostgreSQL-specific timing needed): a concurrent `MemberService.Add` binding a fresh membership to a node of the subtree could land in that gap and commit regardless, since the check already ran and found nothing. The check (`TreeService.memberGuardFor`, a closure) therefore runs inside `deleteLeaf`/`deleteSubtree`'s own transaction: `deleteLeaf` runs it right after the target node's lock succeeds (a leaf delete locks the only row it may remove), while `deleteSubtree` runs it only AFTER `lockSubtree` has locked every row of the subtree to a fixed point — locking the deleted node alone does not serialize against an `Add` targeting an INTERIOR descendant (which locks only its own row), and both sweeps' path-prefix derivation happens inside the lock so a racing `Move` can never make a cascade match zero rows while reporting success. `MemberService.ensure` (the shared core of `Add` and the `authn.user.created` subscriber) carries the matching half: it takes the identical `lockLiveNode` lock on its target node, inside one transaction with the membership insert, never a plain, unlocked `tree.Get` read followed by a wholly independent `Create`. The two serialize on the same row lock exactly like `CreateChild`/`Move`/`Restore` do against `Delete` (see "Concurrency" below) — proven reproducible on plain SQLite in `tree_test.go`'s `TestTreeService_ConcurrentDeleteAndMemberAdd_NeverDanglesAMembership`, with the interior-descendant leg proven deterministically against real PostgreSQL by `integration_test`'s `TestDeleteSubtree_MemberAddToInteriorDescendant_DuringCascade_NoDanglingMembership_Postgres`.

That guard alone does not make a dangling membership impossible in band by itself, because `MemberService.Restore` exists: remove a membership at node A (a mark-delete, so the members guard no longer sees it), delete node A (now memberless, so the delete succeeds), then restore the earlier membership — `Restore` deliberately does not re-validate the restored row against `Add`'s own rules, "the tenant's node still existing" among them (see "Soft deletion" below), so it comes back active and pointing at a node that is now mark-deleted, with no table written outside org's own service calls anywhere in the sequence. `TestScopeService_MemberNodeIDs_RestoredMembershipOnDeadNode_FailsClosed` reproduces exactly that sequence and re-proves the identical closed reading `MemberNodeIDs` already gives a hand-seeded dangling row.

### Soft deletion

`OrgNode` and `Membership` both implement `dbkit.SoftDeletable` (`DeletedAt *time.Time` / `DeletedBy string`, the same field shape and tags `examples/reference-app/internal/notes.Note` carries). That flips `dbkit.Repository[T].Delete` from a physical `DELETE` onto a mark-delete `UPDATE`, and gives both models a working `dbkit.Repository[T].Restore`. The two were picked because accidental deletion of a sub-org (cascade included) or a membership is exactly the "oops, get it back" scenario mark-delete exists for, unlike e.g. `go/integration`'s API keys, which already have their own domain-specific `Revoke`/`RevokedAt` semantic that serves the same purpose better than a generic soft-delete would. `org_invitations` was deliberately left untouched: an invitation is already single-use and expiring, a lifecycle shape a mark-delete does not obviously improve.

**The partial-unique-index migration, and why it is necessary.** A soft-deleted row still occupies whatever unique constraint it held while live, so mark-delete without narrowing this module's two real unique indexes — `uq_org_nodes_sibling_name ON org_nodes (tenant_id, parent_id, name)` and `uq_memberships_tenant_user ON memberships (tenant_id, user_id)` — would be a real functional regression: a deleted node's name, or a removed member's seat, would stay permanently unavailable for reuse, reserved by a row nobody can even see any more. `migrations/{sqlite,postgres}/0004_add_soft_delete.sql` (a new, append-only migration file — the pre-existing `0001`/`0002` files are never edited) adds the two soft-delete columns and then `DROP`s and re-`CREATE`s both indexes **under the same names**, scoped `WHERE deleted_at IS NULL` (the same partial-index shape `go/pki`'s `uq_pki_signing_keys_active_purpose` uses for the same "a value can repeat across states but not within one" reason). Reusing the index names means no other reference to them — `mapWriteError`'s `gorm.ErrDuplicatedKey` translation, this module's own tests — needed to change. `TestTreeService_Delete_ThenCreateChild_SameSiblingName_Succeeds` and `TestMemberService_Remove_ThenAdd_SameUser_Succeeds` prove that reuse works; `TestTreeService_CreateChild_DuplicateSiblingName_ReturnsDuplicateSiblingName` pins that two simultaneously-**live** rows with the same triple correctly collide — the partial index narrows what counts, it does not turn uniqueness off.

**Cascade delete marks every descendant.** `Repository.deleteSubtree` (the cascade branch `TreeService.Delete` calls) is a single cascading `UPDATE` — one statement, one transaction — so the atomicity property `Repository.deleteLeaf`'s own doc comment describes holds for it too. Every currently-live node whose path falls under the deleted subtree's prefix gets the *same* `deleted_at`/`deleted_by` in that one `UPDATE`, mirroring `dbkit`'s own unexported `softDelete` shape byte for byte (a real `*OrgNode`, `Model == Dest == &m`, never a map payload — see `Repository.deleteLeaf`'s doc comment for why a map payload would make audit capture lie about what was written). The `WHERE deleted_at IS NULL` guard means an already-soft-deleted descendant, from some earlier and unrelated mark-delete, is left untouched rather than having this call's attribution stamped over its own. `TestTreeService_Delete_WithCascade_MarksEveryLevelSoftDeletedAndRestorable` proves the shape end to end over a 3-level subtree: every level invisible to `Get` immediately after, and every level individually restorable afterward with its original parent and name, its `Path`/`Depth` re-derived from the parent it returns to (byte-identical to the originals in a tree untouched since the cascade — see the re-expression paragraph below) — the second half is the property a physical `DELETE` could never have offered, and is what a physical `DELETE` could never have offered.

**Restore is per-node, never cascading — a real design decision, not an oversight.** `TreeService.Restore(ctx, nodeID)` and `MemberService.Restore(ctx, membershipID)` both undo a single node's own mark-delete and re-read the row, mirroring the promoted `dbkit.Repository[T].Restore`'s id-based shape and its collapsed not-found signal (an id with nothing to restore, and an id that exists but is not currently mark-deleted, report the identical error — `org.node_not_found` / `org.membership_not_found` — so a caller cannot learn which case it hit from the error shape alone; the tree side's write is `restoreNodeTx`, the same conditional-`UPDATE` shape inlined so it can share `Restore`'s own transaction). Restoring a node undoes **exactly** the mark-delete of that one node; it does not restore any descendant a cascading `Delete` soft-deleted alongside it. Two options were on the table:

- *Cascading restore*, undoing whatever a matching cascading delete removed. The only way to identify "that cascade's rows" without inventing new state is to correlate on the batch's own `deleted_at`/`deleted_by` — but that is a heuristic, not an identity: two independent deletes landing on the identical timestamp is vanishingly unlikely yet not impossible, and worse, it cannot distinguish "deleted by that cascade" from "already independently, deliberately soft-deleted earlier for an unrelated reason" the moment the two overlap in the same subtree. Restoring the ancestor would then silently resurrect a row somebody removed on purpose for a reason of its own.
- *Independent, per-node restore* (**the one org ships**). It carries none of the above ambiguity, and it is the same "no implicit side effect on a structural edit" discipline this module already applies everywhere else: `Delete` does not re-parent orphans to the grandparent (that would silently widen a member's data scope — "Deleting never re-parents orphans" above) and does not delete memberships along with a node (`assertNoMembers` refuses instead — "Deleting a node with members in it is refused" above). A cascading `Restore` would be the exact same failure mode in reverse: an implicit, wide-reaching consequence of what looks like a single-node request.

`TestTreeService_Restore_IsNotCascading` pins the chosen behavior directly: restoring an ancestor cascade-deleted alongside a descendant leaves that descendant invisible, and the descendant is separately restorable by its own id. The resulting **known limitation**: a node restored this way can have descendants that stay mark-deleted — from the same earlier cascade, or from their own independent deletion — and `org` exposes no query today that lists a node's mark-deleted descendants to enumerate the ids a full-subtree restore would need. A future admin restore surface is the natural place to add one (see "Known limitations" below).

**Restore refuses to land a node on a dead parent.** Per-node-not-cascading means the OTHER half of a cascade can still be mark-deleted when a caller restores a descendant alone — `TestTreeService_Restore_DeadParent_RefusesRestore` reproduces exactly that: cascade-delete root → north → store, then `Restore(store)` alone, leaving `north` still dead. Landing `store` back as live in that state is not a cosmetic gap: `Subtree(root)`'s prefix-match `LIKE` scan cannot see that `north` is invisible, so it would surface `store` anyway, while `Ancestors(store)` and every `Children()`-based walk down from the root could not reach it, and `CreateChild(store.ID, ...)` would let a caller grow a fresh subtree hanging off the orphaned chain — exactly the "path disagrees with the parent chain" state path.go's own doc comment calls corrupt, not a supported one, with no equivalent safety net to the roster's dangling-membership `Warn` (below). `TreeService.Restore` therefore reads the node's stored `ParentID` first (`Repository.findByIDIncludingDeleted`, an `.Unscoped()` read that still stays fully tenant-scoped — the tenant-scope plugin does not check `Unscoped`, only the soft-delete one does) and refuses with `org.restore_parent_not_live` before writing anything when that parent is not currently live. The caller restores top-down, ancestor before descendant, exactly as `TestTreeService_Restore_IsNotCascading` already does for the still-live-ancestor case. The tenant root needs no such check: its `ParentID` is always the empty-string sentinel and it is never itself deletable (`ErrRootNotDeletable`).

**Restore re-expresses the row under its parent's current path.** A live parent can MOVE while its child is mark-deleted: Move's per-row rewrite carries `WHERE deleted_at IS NULL`, so a soft-deleted descendant is invisible to it and keeps the path naming the parent's OLD position. Clearing the markers without re-deriving `Path`/`Depth` would then resurrect a row whose materialized path disagrees with its own `ParentID` chain — the state path.go calls corrupt — reachable through nothing but documented operations: cascade-delete a subtree, restore its ancestor, move that ancestor, restore a descendant. The corruption is load-bearing for subtree scopes in BOTH directions: a scope anchored under the old branch keeps covering the resurrected row while the real parent's own subtree misses it. `TreeService.Restore` therefore re-expresses every row it brings back under the locked live parent's **current** path — the very `lockLiveNode` row the dead-parent check above uses, read inside the same transaction, so the path cannot go stale between derivation and write; in a tree untouched since the delete this reproduces the stored values exactly. Re-expression stays inside the module's depth envelope too: a parent can legally sit *at* `maxDepth` with a deleted child beneath it (Move's depth check sees only the live subtree), so a restore that would land the child at `maxDepth+1` — a row no `CreateChild` under that same parent could have produced — refuses with the same `ErrMaxDepthExceeded` that `CreateChild` answers. `tree_test.go`'s `TestTreeService_Restore_AfterAncestorMoved_ReexpressesUnderTheCurrentParent` pins the four-step sequence end to end (canonical `Path`/`Depth` on the restored row, the real parent's subtree covering it, the old branch's subtree not, `assertNoOrphans` clean), `TestTreeService_Restore_WouldLandBeyondMaxDepth_Refused` pins the refusal (the row stays dead), and `scope_service_test.go`'s `TestScopeService_MemberNodeIDs_AfterRestoreOfMovedAncestor_ResolvesUnderTheRealParent` proves the rbac-shaped reading: after the sequence a membership anchored at the real parent sees the restored descendant, one anchored under the old branch does not. The tenant root's re-expression is identity — a root's canonical path is built from its own id alone. The promoted `dbkit.Repository`-surface `Restore` (a host's documented escape hatch for the root slot) remains the raw marker clear; every tree-shaped restore goes through `TreeService.Restore`.

**Restore refuses to land a node on a slot a live row has since taken.** The narrowed partial indexes deliberately free a soft-deleted row's constraint slot for immediate reuse — a removed membership's `(tenant_id, user_id)` seat for a fresh `Add`, a deleted node's sibling-name slot for a fresh `CreateChild`, the root slot since `0008_single_root_live.sql` narrowed the 0007 index to live rows (0007's `parent_id = ''` scope alone never frees a mark-deleted root's slot, which is what 0008 narrows; a root can only be mark-deleted through the host-visible `Repository` surface, since `Delete` itself refuses it) — so clearing `deleted_at` can collide with the live replacement at the database. Both Restore paths translate that collision into the coded error the live-side operation reports (`org.membership_exists` from `MemberService.Restore`, `org.duplicate_sibling_name` from `TreeService.Restore` via the shared `mapWriteError`), never a bare `gorm.ErrDuplicatedKey`; the row the un-delete was racing stays the tenant's live one (`TestMemberService_Restore_SeatReused_AnswersMembershipExists`, `TestTreeService_Restore_ReusedSiblingNameSlot_AnswersDuplicateSiblingName`).

`Restore` on both services publishes its own event (`EventNodeRestored` / `EventMemberRestored`, alongside the existing `Created`/`Moved`/`Deleted` and `Invited`/`Joined`/`Removed` events) rather than reusing or suppressing the create/join events — a restore is its own fact, not indistinguishable from a fresh create.

**No HTTP surface for `Restore`.** Adding `OrgRestoreNode` / `OrgRestoreMember` operations would need an `api/openapi.yaml` change, a regeneration of `api/org-server.gen.go` through the pinned oapi-codegen toolchain, and — to gate them consistently with `OrgDeleteNode` / `OrgRemoveMember`'s own authZ — a route added to the *host's* rbac permission map, which lives outside this module entirely (in the consuming application's own wiring, `examples/reference-app` for the reference app). That last piece is not this module's to add, and doing it inconsistently would be worse than not doing it. `Restore` is fully usable as a `Module.Tree()` / `Module.Members()` service call.

### Three module interfaces that exist so no import does

`Scope` (scope.go), `FeatureGate` (module.go) and `SubjectResolver` (subject.go) are all interfaces whose every method signature is built from `context.Context`, `*http.Request`, `string`, `[]string`, `bool` and `error` — **no org type appears in any of them**. That is the whole mechanism: a consumer declares the identical method set in its own package and accepts org's implementation structurally.

- `Scope` is what rbac needs (a node's materialized path, a subtree's ids, a subject's reachable node set). org never imports rbac, and rbac never learns what an `OrgNode` is. `scope_test.go` declares `rbacShapedScope` locally, without naming org's own `Scope` type, and asserts `*ScopeService` satisfies it. **A method that returned `[]OrgNode` would destroy the property and force the import back**; that test is what stops it.
- `FeatureGate` is the same trick pointed at config: `*config.Service` satisfies it through its own `IsEnabled` method, and neither module imports the other. The host wires them together, and the host is the only place both names appear. `FeatureGateFunc` (module.go) is the func-to-interface adapter for wiring the module, and `examples/reference-app/internal/app/server.go` wires `org.FeatureGateFunc(configModule.Handle().IsEnabled)` — the config module's lazy handle, which is live from `config.Attach` on and reports the config module's own not-attached refusal before it — with no import of `org` inside `go/config` or vice versa.
- `SubjectResolver` is different in kind from the other two: it is not a peer-module interface (nothing else in the module graph implements it yet) but the interface an authenticating module fills. `Handler.resolveSubject` fails closed (401 `org.subject_unresolved`) when it is nil or returns `ok == false`, never inventing a default caller. `examples/reference-app/internal/app/server.go`'s `DemoOrgSubjectResolverFor` is an explicitly-labelled, clearly-unsafe-for-production stand-in closure (wrapped by `org.SubjectResolverFunc` at the wiring site) that reads an unauthenticated header, so the reference app can demonstrate the invite/accept flow end to end without a real identity layer.

### Two wirings are required at boot, and refused loudly

`Register` fails rather than starting half-configured, mirroring `config.Attach`'s `ErrCipherRequired`:

| Missing | Error | Why it cannot be deferred |
|---|---|---|
| `WithEmailIndexer` | `org.email_indexer_required` | an invitation whose address cannot be indexed can never be found again |
| `WithMailFrom` **and** `WithInvitationLinkBuilder`, while the invitation email is on | `org.invitation_mail_required` | `pkgcore.Mailer` rejects an empty `From` outright, and a message with no link is not actionable |

A host that lets something else deliver the invitation calls `WithInvitationEmailDisabled()` and needs neither mail option.

### org declares no dynamic-config schema

`maxDepth`, `maxNameLen`, the invitation TTL and the two rate-limit budgets are package constants, per option 3 of the backend standard's configuration rule. org must not import `config`, and `config.Service.Get` returns a config-owned `Value` type org cannot restate structurally the way the boolean `IsEnabled` gate can be. Declaring a schema org would then silently ignore would be a lying schema. `TestModule_Register_DeclaresItsSurface` asserts the absence deliberately.

Feature **flags** are different, and org does declare two: a flag is a boolean, and `FeatureGate` restates the one method needed to read one without naming a config type. The numbers stay constants, overridable per host through `WithMaxDepth` / `WithInvitationTTL`.

### The bootstrap key it declares

`Register` declares one process-start key on the component descriptor's `BootstrapKeys`: `org.invitation_email_index_key`, the HMAC key the invitation-address blind indexer is built from (`WithEmailIndexer` over `dbkit.NewBlindIndexer`). It is `hexkey` and Sensitive, its documented fallback is a non-secret development default, and it must be a DIFFERENT secret from the host's encryption key -- dbkit takes the two through separate constructors for exactly that reason, and an index built under a rotated key can never find its addresses again. The declaration states the contract; the host resolves the value and injects the indexer. org never reads the environment.

### The audit trail — automatic capture, not hand-written `Emit`

Every org write is audited through dbkit's **automatic** write-capture mechanism, never through hand-written `audit.Emit` calls at the write paths — the declared vocabulary and the mechanism's derived actions must stay exactly in step (see the register-vs-emit reconciliation below).

- **The three tenant-data models opt into `dbkit.Auditable`.** `OrgNode` (`AuditResourceTypeNode` = `"org.node"`), `Membership` (`"org.member"`) and `Invitation` (`"org.invitation"`). The deliberately narrow, non-tenant-scoped `invitationTokenIndex` bookkeeping row is NOT opted in. Each opted-in model's write publishes a `WriteCapturedEvent` from which `go/dbkit/audit`'s persister derives the action — and org declares in `Register` **exactly** the derived vocabulary its models can produce: `org.node.create` / `org.node.update`, `org.member.create` / `org.member.update`, `org.invitation.create` / `org.invitation.update`. The declared actions are constant expressions over the resource labels (`AuditResourceTypeNode + ".create"` and so on — module.go), the same derivation the mechanism performs at capture time, so model labels, declared vocabulary and mechanism cannot drift: a solo rename of a label propagates to every side in one edit, where two independent literals would let a label rename silently change what the mechanism derived while the declared actions kept their old strings — the persister's vocabulary gate would then answer with an alert and a dropped row, never an error. `TestModule_Register_DeclaresItsSurface` asserts the registry ends up with exactly these six actions, both directions.
- **org exports its capture scope.** `AuditableModels()` returns the three opted-in models — the slice a host lists verbatim in that connection's `Options.AuditModels`, so the host never keeps a hand-written model list that could drift from org's. The scope contract is asymmetric the same way the vocabulary gate is one-directional: `Open` refuses a listed model whose `Auditable` marker was removed after listing, but nothing can refuse a model that GAINED the marker while the scope forgot it (Open receives no model inventory — GORM's models register lazily, per statement), so adding the marker to an org model belongs to `AuditableModels()` in the same edit; `TestModule_AuditableModels_IsExactlyTheMarkedModels` pins the export to the marked models, and the reference app's `flowtests/org_audit_capture_test.go` proves each exported model's writes really land as rows through the composed stack.
- **Semantics land in the action-plus-diff, not in bespoke action names.** org's operations are only ever GORM `create` or `update` writes — every delete is a mark-delete UPDATE, nothing issues a physical DELETE — so no org row is ever recorded under a "delete" operation. Event-shaped names (`org.node.rename` / `move` / `delete`, `org.member.invite` / `accept` / `remove`) would name nothing the mechanism produces. The mapping: a rename, a move, a node mark-delete and a node/member restore each record as `...update` with the written columns in the changes diff telling which one it was; an invite records as `org.invitation.create`; an acceptance as `org.invitation.update` (the invitation's status flip) plus `org.member.create` (the membership row); a revoke as `org.invitation.update`; a member removal as `org.member.update` whose diff carries the new `deleted_at`/`deleted_by`.
- **What an invitation row records — and what it does not.** The `org.invitation.create` diff names the row (id, node, status, expiry) and carries the invitee's address-derived columns only as `[redacted]` markers: `email` because it is a GORM serializer field (the capture plugin redacts serializer fields automatically), `email_index` because the model declares dbkit's `audit:"redact"` capture opt-out on it. The index is not sensitive plaintext, but it is a stable linkable identifier of a guessable address, and the audit trail is the most permanent exit it could reach — append-only with no delete by design, tenant-readable (compliance's audit query runs under an ordinary tenant context) where the org rows themselves are subtree-readable — so a raw index in a diff would let a tenant member with audit read confirm a guessed address across subtrees they cannot see (the same reasoning that bars the index from event payloads and HTTP responses; `Invitation.EmailIndex`'s own doc comment carries it). `TokenHash` IS recorded, deliberately: the token is 32 fresh random bytes per invitation, so its SHA-256 has no candidate space, no stability to link on and no person-attributable meaning, and the only holder a recorded hash could confirm anything to already holds the credential itself (see the `AuditResourceType` doc comment in invitation.go).
- **Host wiring contract (the reference app is the first fulfilled host).** Capture installs per connection at `dbkit.Open`: the host must set `Options.AuditBus` to the bus its `go/dbkit/audit` persister module subscribes on, set that connection's `Options.AuditModels` to `org.AuditableModels()`, include org in the `the assembly` module set (its `Register` declares the six actions) and include `go/dbkit/audit`'s `Module` in the same set (it persists the rows). `examples/reference-app/internal/app/server.go`'s wiring comment on its own `dbkit.Open` call is the walkthrough.
- **Dual identity falls out of the context, with no org code.** The capture plugin reads `pkgcore.Actor`/`OnBehalfOf` off the write's own context, so an operation performed during administrator impersonation records both identities without org knowing impersonation exists — the reference app's `flowtests/org_audit_capture_test.go` drives a real impersonation-session member removal and node delete and asserts both columns on the resulting rows.
- **Lock-touch writes are recorded too — a known characteristic, not a leak.** org's concurrency discipline writes no-op row-lock UPDATEs (`touchLockByID` and `removeIfNotLastActive`'s lock statement) against opted-in models inside its own transactions, and the capture mechanism is statement-level: those touches are genuine `update` writes against an Auditable model and are captured like any other, as `...update` rows whose diff carries only `{deleted_by: ""}` and whose `ResourceID` is the locked node's id (the bulk lock's is empty). A reader distinguishes them from real changes by that empty diff. Keeping them out would need a statement-level filter in the mechanism itself, which is out of this module's scope; the repo-wide capture assessment tracks that as its input (see `go/dbkit/AGENTS.md`'s audit section). The `DeleteBy` attribution column org writes (`softDeleteActor`) and dbkit's own soft-delete share the same actor source, so a mark-delete row's diff and its `Actor` column always agree.
- **The notes double-record resolution is a host-connection concern, not org's.** notes.Note also implements `Auditable` but records its own trail through `audit.Emit`; the reference app keeps Note out of the capture scope by construction, since its scope is `org.AuditableModels()`, which contains only org's own models (see `go/dbkit/AGENTS.md`'s "Audit trail collection" section for the option's rationale).

### The authn subscription — `events.go`

`EventUserCreated` is the one coordination point with the parallel authn module, and the string appears in exactly one place in org. The handler's contract, all four cases tested:

1. **No publisher** — the subscription is installed and never fires. `Subscribe` cannot fail.
2. **Unrecognized payload** — `Warn`, **return nil**. On the in-memory bus a handler error propagates back into the publisher's `Publish`, so returning one would make org's ignorance look like a failed user creation inside authn.
3. **No tenant on the event** — `Debug`, do nothing. A self-registering user genuinely has no tenant yet; the tenant-creating path is an explicit `CreateRoot`.
4. **A tenant** — rebuild it with `pkgcore.WithTenant` (a remote-bus handler carries none), then idempotently ensure a root and a membership. A redelivered event creates neither a second root nor a second membership.

`userIDFromPayload` normalizes any payload shape through a JSON round-trip and probes `user_id` / `userId` / `UserID` / `userID`. **It never type-asserts the publisher's struct** — doing so would require importing it.

### Data access — `repository.go`

`Repository` embeds `*dbkit.Repository[OrgNode]` (Create / FindByID / Update / Delete / Restore / List promoted unchanged — `Delete`/`Restore` are mark-delete/undo, because `OrgNode` implements `dbkit.SoftDeletable`) and adds the query shapes `Repository[T]`'s minimal surface cannot express: `subtree`, `children`, `findRoot`, `byIDs`, `deleteLeaf`, `deleteSubtree` — all unexported, all reached through `TreeService` — plus the concurrency primitives `touchLockByID`, `lockLiveNode` and `lockSubtree` (`assertNameFreeTx` is the sibling-name pre-check in its transaction-bound form). See "Concurrency" below for what those three exist to close.

Read `deleteLeaf` before touching `Delete`. It counts the rows its own **mark-delete `UPDATE`** matched **inside** the transaction and rolls back when the count is not exactly one. A `children`-then-`Delete` pair would instead leave a window in which a concurrent create adds a child, and the delete would orphan it — `parent_id` pointing at a soft-deleted row, `path` naming a node no ordinary read can see. A self-referencing foreign key cannot close that gap either: SQLite leaves FKs unenforced unless `foreign_keys` is switched on, which would make the two dialects disagree. Do not "simplify" the in-transaction count back out into a pre-check. `deleteLeaf` and `deleteSubtree` both explicitly add `WHERE deleted_at IS NULL` to their match: only currently-live rows count toward "does this node have children" / "what does this cascade touch" — see "Soft deletion" above for `deleteSubtree`'s own cascade shape.

That in-transaction count is what makes `deleteLeaf` correct in isolation; it is not, on its own, what makes it safe against a CONCURRENT `CreateChild` or `Restore` locking the exact node being deleted (see "Concurrency" below) — both now take `lockLiveNode(nodeID)` as their transaction's own first statement (the blind touch, before the `LIKE`-prefix scan runs), which also yields the row's current path for the sweep prefix, for exactly that reason. A caller can no longer pass a stale prefix to either method at all — the prefix parameter is gone from both signatures.

Both `deleteLeaf` and `deleteSubtree` take a `guard func(tx *gorm.DB, prefix string) error` — the prefix being the sweep's own, derived under the lock — run against that same open transaction after `nodeID`'s own lock succeeds and the current prefix is derived, and (for `deleteSubtree` only) after `lockSubtree` has locked the whole subtree; `deleteLeaf` runs it strictly before its own mark-delete statement. A non-nil return aborts the whole transaction, unwrapped (via `apperr.As`, so a coded error like `org.node_has_members` never gets flattened into `org.internal_error`). `TreeService.memberGuardFor` (tree.go) is the one production caller; `repository_test.go`'s own direct tests of these two methods pass `nil`. See "Deleting a node with members in it is refused" above for why this parameter exists at all — it is what moved the roster check from its own separate, unlocked read into this exact transaction.

Each is written as option 1 of `go/dbkit/AGENTS.md`'s Known-limitations guidance — built on the same `*gorm.DB` isolation layer 1 protects, against a `TenantScoped` destination, inside `dbkit.WithTenantSession` so layer 3's RLS session variable is set too. **There is no `tenant_id = ?` string anywhere in this package, and no `db.Table` / `db.Model` / `db.Raw`**; `go/org` has no allowlist entry in either semgrep rule, deliberately.

| `SubjectResolver.Subject(r) (userID string, ok bool)`, plus `SubjectResolverFunc` (the func-to-interface adapter, `http.HandlerFunc`'s shape, so a host wires the module with a closure) | See "Three module interfaces that exist so no import does". Only `org_createInvitation` and `org_acceptInvitation` call it — every other operation reads only the tenant from context. This module's own authorization stops there: it is the HOST's job to gate the other nine operations on the permissions above, exactly as `storage`'s and `sharing`'s own handlers leave their enforcement to the host (see the `PermissionRead`/`PermissionManage`/... row above for where `examples/reference-app` does it) |

Every response type omits the invitation's plaintext address — and the address's blind index as well: `toInvitationResponse` reads neither `inv.Email` nor `inv.EmailIndex`. An HMAC digest is not an identifier safe to display: non-invertibility resists offline dictionary attacks only, never an online oracle, and since `org_createInvitation` accepts a caller-chosen address, a caller who can create invitations can collect (address, index) pairs under the deployment-wide, tenant-unsalted blind-index key — an echoed index would be a membership test for the address of every listed invitation. The response identifies the row (its invitation id, node, status, expiry), never the invitee. `OrgCreateInvitationRequest`'s `email` field is the one input the surface accepts in the clear, exactly once, on the way in.

`OrgAcceptInvitation` is the one handler method that does not read the tenant from context (`mustTenant`) — a freshly invited person holds no tenant claim, which is the whole point of the tenantless accept ("Acceptance is tenantless" above) — so the host must let exactly this one path through its tenant-resolving middleware, the same allowlist treatment `go/sharing`'s public path requires. Every other org method still requires a resolved tenant and is unchanged.

## TenantsOf — the one cross-tenant read

`MemberService.TenantsOf(ctx, userID)` closes the gap the reference app's sign-in machinery worked around for a long time: the "which tenants does this user belong to" half of the question `authn.MembershipReader` (go/authn/service.go) must be able to answer, which authn itself cannot ask org for directly (authn never imports org — the module exists precisely because the dependency must stay pointed the other way). The assembling application wires `MemberService.TenantsOf` behind the reader's `TenantsOf`, the same host-glue shape `Get` already serves for `ActiveMembership`. The natural order is org's own: ordered by tenant id, so two replicas and both engines answer identically; a host that prefers one tenant on a no-tenant sign-in reorders the answer itself.

**The gate.** TenantsOf is the module's only read that spans tenants by definition, and org refuses to serve "which organizations does this person belong to" to a caller holding only one organization's own context: without a system context (pkgcore.WithSystemContext; business code should use tenancy's audited wrapper) the method answers `org.system_context_required` before any database work. Like dbkit's HardDelete gate, org checks only the grant's presence, never who holds it — which modules may hold one at all is the caller-side whitelist, and the audit trail is the wrapper's. A tenant already in ctx neither satisfies nor defeats the gate and does not change the answer.

**The statement, and why it is not a tenant-scoped one.** The read is one query on `memberships` — `user_id = ? AND status = 'active' AND deleted_at IS NULL ORDER BY tenant_id` — scanning into `membershipTenantRow`, a deliberately non-TenantScoped projection: dbkit's isolation plugin scopes statements by destination model, so a tenant-scoped destination would either receive an injected tenant filter (wrong: the question spans tenants) or fail closed for lacking a tenant (wrong: the read is unscoped by design). This is the "higher layer that can make that decision deliberately and audit it" dbkit's own tenant_scope.go doc comment anticipates for the system-context escape hatch — org's MembershipRepository is that higher layer for the memberships table, with TenantsOf's gate as the deliberate decision point in front of it. It uses no `db.Table` / `db.Model` / `db.Raw` and no hand-written tenant filter (org carries no allowlist entry in either semgrep rule), and the partial index `migrations/{sqlite,postgres}/0009_memberships_user_lookup.sql` — the one sanctioned composite index in this codebase whose leading column is not `tenant_id` — makes the `user_id` half of the lookup an index read, not a scan. Do not "simplify" the destination back to `[]Membership` or route the read through `WithTenantSession`: the first reintroduces exactly the scoping the read must not have, the second requires a tenant the read does not have and would set an RLS GUC scoping the statement to one tenant.

**PostgreSQL RLS posture (known limitation).** The statement deliberately does not set `dbkit.WithTenantSession`'s session GUC — that mechanism scopes one statement to one tenant, the opposite of this read's meaning. A production PostgreSQL deployment whose RLS policies admit only per-tenant reads must therefore give the platform role its own admission for system-context reads of `memberships`; no distributed-mode deployment exists yet, so no concrete policy shape is proven — recorded here rather than silently assumed, exactly like dbkit's own system-context-gated HardDelete records its RLS interaction. The unit tier proves the read on SQLite; the PostgreSQL integration tier re-runs the module's per-tenant suites, which do not exercise a cross-tenant read by design.

**Migration 0009 is append-only like every file in this module's migration sets**, and the `sqlite/` and `postgres/` copies are byte-identical apart from the header note.

## Concurrency

Every tree write that decides something and then writes it is atomic — either one transaction with an explicit, dialect-neutral row lock taken before anything is trusted, or (`Remove`, `Invite`) one database-arbitrated conditional statement. The operations covered: `CreateChild`, `Move`, `MemberService.Remove`, `InviteService.Invite`, `Restore` and `Rename` (the one operation of the family whose read-then-write window sits between two statements of the SAME call). This section is the concurrency guarantee every consumer of this module gets: no operation leaves a separated read followed by an unguarded write that a second concurrent writer can interleave with.

**The lock primitive: `touchLockByID` / `lockLiveNode` (repository.go).** A no-op conditional `UPDATE` — `WHERE id = ? AND deleted_at IS NULL`, rewriting a column (`DeletedBy`) back to the value a live row always already holds — issued as a transaction's OWN FIRST statement. On PostgreSQL this takes the row's real write lock, held until commit, so a concurrent writer of the same row either has already committed (and this call's own re-evaluated `WHERE` clause correctly fails to match a row that died in the meantime) or is still open (and this call blocks behind it rather than racing a stale read). On SQLite, being the first statement of the transaction is what keeps the whole transaction out of the read-then-write lock-upgrade hazard an ordinary contending writer waits out via `busy_timeout` and succeeds once the holder commits; only a transaction that read something FIRST is refused immediately instead. `lockLiveNode` additionally reads the row back once locked (safe, since nothing else can change it before this transaction ends); `deleteLeaf`/`deleteSubtree` use the bare lock alone, ahead of their own bulk `LIKE`-prefix scan (see the data-access section above and the note below on why the scan alone is not enough).

**`CreateChild`.** The whole operation — locking the parent, reading its current `Path`, the sibling-name check, the insert — is one `dbkit.WithTenantSession` transaction. `lockLiveNode(parentID)` either blocks behind a concurrent `deleteLeaf` soft-deleting that same parent (and then correctly refuses once it commits) or forces that delete to wait behind THIS call instead of racing it. The window closed: a child landing under a parent a concurrent delete was mid-flight on.

**`Move`.** One transaction: `lockLiveNode` on the moved node, then on the new parent, THEN the subtree scan and every rewritten row, each its own conditioned `UPDATE` (`id` + `deleted_at IS NULL`) rather than a per-row `dbkit.Repository[OrgNode].Update` loop with no lock at all. Two overlapping `Move`s serialize on whichever row they lock first; a `Move` and a `CreateChild` targeting the same node serialize on that node's identical lock; a `Move` and a cascading `Delete` of the node being moved serialize the same way. A genuine PostgreSQL deadlock between two `Move`s whose lock orders cross (A locks X then wants Y while B locks Y then wants X) is real and detected by PostgreSQL itself — `withRetry` (below) is what turns that into a transparent retry rather than a surfaced failure.

Locking the moved node and the new parent alone stops one row short: the subtree scan that follows would still be a plain, unlocked `Find`, leaving every OTHER row of the subtree exposed for the whole rewrite. A `CreateChild` targeting an INTERIOR DESCENDANT of the moved subtree (never the moved node itself, which is already locked) takes its own `lockLiveNode` on that row, which `Move` never otherwise touches, so the two calls would never serialize on anything: its insert, bound to the descendant's old, pre-move `Path`, could land entirely within the gap between `Move`'s one-shot scan and that scan's later per-row rewrite, and the new grandchild's row would simply never appear in the set `Move` rewrites — confirmed against a real PostgreSQL server. `lockSubtree` (repository.go) replaces the single unlocked scan with a scan-lock-rescan loop: lock every row a scan returns, then scan again, repeating until a scan turns up nothing not already locked by this transaction — at which point no further insert can land uncontested under any row of the subtree, the same guarantee `lockLiveNode` gives a single row, extended to the whole set. `tree_test.go`'s `TestTreeService_ConcurrentMoveAndCreateChild_InteriorDescendant_TreeInvariantHolds` is the SQLite form (whose single-writer locking has not reproduced the gap); `integration_test/postgres_concurrency_test.go`'s `..._Postgres` twin is the tier that actually forces the window and reproduces the corruption reliably.

**`MemberService.Remove`.** `MembershipRepository.removeIfNotLastActive` replaces an `activeSample(ctx, 2)`-then-`Delete` pair (two independent transactions) with one transaction, two writes, no read in between: a blind bulk touch-lock of every currently-active row in the tenant (which also IS the active count, read for free off its own `RowsAffected`), then the targeted soft-delete, gated on that count. Two concurrent `Remove`s of a tenant's last two active members genuinely serialize on the shared row set the bulk touch locks, rather than both reading "2 active" before either commits. The cost, deliberately accepted: every `Remove` of an active member briefly write-locks every OTHER active membership row of the tenant too, not just its own target — acceptable at the roster sizes this module targets.

**`InviteService.Invite`.** `InvitationRepository.createPending` replaces a `SELECT`-then-per-row-`Update` revoke (itself separate from the row's own later `Create`) with one transaction, two writes, no read in between: a blind bulk revoke of whatever is pending for the address, then the insert — arbitrated by a real database constraint, `migrations/{postgres,sqlite}/0005_unique_pending_invitation.sql`'s partial unique index on `(tenant_id, email_index) WHERE status = 'pending'`. Two concurrent `Invite`s for the same address either both succeed (little overlap: the second's own revoke step correctly finds and supersedes the first's already-committed row) or one is refused with the coded `org.invitation_already_pending` (genuine overlap: the unique index lets only one insert land) — both are correct, and either way exactly one live token survives; see `invite_test.go`'s `TestInviteService_Invite_ConcurrentSameAddress_ExactlyOneLiveToken` doc comment for why the win/loss split itself is not what is asserted.

**`Restore`.** The parent-liveness check and the restore write are one transaction: `lockLiveNode(existing.ParentID)` first, then `restoreNodeTx` (the same conditional-`UPDATE` shape `dbkit.Repository[T].Restore` uses, inlined so it can share this transaction). A concurrent cascade `Delete` of that same parent cannot land in the gap between the two — it either has already soft-deleted the parent (and `Restore` correctly refuses) or is forced to wait behind this transaction (and, once it resumes, correctly discovers the just-restored row is live again and sweeps it into its own cascade too — both rows end up dead together, which is consistent, never the corrupt "child live, parent dead" state). `restoreNodeTx` also re-expresses the row under the locked parent's CURRENT path — writing `Path`/`Depth` (derived from the `lockLiveNode` row and validated, depth-bounded by `maxDepth`) together with the cleared markers — because Move's subtree rewrite cannot see mark-deleted descendants, and a bare marker-clear would resurrect a row deleted before its parent moved under a stale path; see "Soft deletion" above for the four-step sequence and the refusal shapes.

**`Rename`.** The rename is one transaction: `lockLiveNode(nodeID)` first, then the sibling-name check (`assertNameFreeTx`) and the name `UPDATE` — a conditioned statement (`id` + `deleted_at IS NULL`) writing only the `Name` column, the same shape `Move`'s per-row rewrites use, never a full-field write. A separated `s.Get` read followed by a standalone full-field `dbkit.Repository[OrgNode].Update` would be unsafe, because that `Update` is a full-field `Save` that writes the caller's in-memory model back over the whole row — a concurrent `Delete` soft-deleting the very node being renamed, landing between the two calls, would have its committed mark silently overwritten by the rename's stale pre-delete snapshot (`deleted_at` written back to `NULL`): a deleted node resurrected, live and renamed, with no error anywhere. The lock closes it exactly as it closes the other windows — the delete either commits first (and the rename's re-evaluated lock attempt fails to match a dead row, reporting `ErrNodeNotFound`) or blocks behind the rename's own transaction — and the conditioned `UPDATE` re-checks liveness at write time regardless. `assertNameFreeTx` is the transaction-bound form; the ctx-bound read helper no longer exists. `tree_test.go`'s `TestTreeService_ConcurrentRenameAndDelete_NeverResurrectsTheNode` is the regression proof, and unlike the other operations' SQLite stress tests it is deterministic: a second connection executes the mark-delete and holds its transaction open while the rename runs, which pins the window exactly.

**`Delete` × `MemberService.Add`.** This is not a "two independent writes with nothing between them" shape but a genuine check-then-act TOCTOU: `TreeService.Delete`'s members guard must not run as its own separate, unlocked read entirely BEFORE `deleteLeaf`/`deleteSubtree` open their own transaction, because a concurrent `MemberService.Add` binding a fresh membership to the subtree could land in that gap and commit regardless of what the cascade then did — a wide-open window on BOTH dialects, no PostgreSQL-specific timing needed. The check (`TreeService.memberGuardFor`) therefore runs inside `deleteLeaf`/`deleteSubtree`'s own transaction, and `MemberService.ensure` carries the matching half: it locks its target node (`lockLiveNode`) inside one transaction with the membership insert, rather than a plain `tree.Get` read followed by an independent `Create`. See "Deleting a node with members in it is refused" above for the full mechanism and the interior-descendant refinement (the cascade's guard runs only after `lockSubtree`); `tree_test.go`'s `TestTreeService_ConcurrentDeleteAndMemberAdd_NeverDanglesAMembership` is the regression proof, with the interior-descendant leg proven against real PostgreSQL.

**Why `deleteLeaf`/`deleteSubtree` ALSO need `touchLockByID`, not only the decision-side call sites above.** The bulk `UPDATE` on the delete side cannot be the side's only guard: PostgreSQL's re-check of a row a blocked `UPDATE` was waiting on (`EvalPlanQual`, under READ COMMITTED) re-verifies only the rows the statement's ORIGINAL scan already selected — it does not expand that candidate set to a row that came to match the `WHERE` clause only after the scan ran, a newly inserted child above all. Concretely: `deleteLeaf`'s `LIKE`-prefix scan could take its snapshot before a concurrent `CreateChild`'s `lockLiveNode` locked the same parent, then block on that lock; once `CreateChild` committed (inserting the child), `deleteLeaf`'s resumed `UPDATE` would NOT notice the new row — it never existed when the scan ran — so `matched` would stay 1 instead of 2, and the delete would proceed believing the node was still childless. Both `deleteLeaf` and `deleteSubtree` therefore take the row lock as their OWN first statement (`lockLiveNode(nodeID)`'s blind touch, before the bulk scan), so a concurrent `CreateChild`/`Restore`/`Move` locking that same node is forced to have already fully committed (or to block behind this call) before the scan that decides "does this node have children" / "what does this cascade touch" ever runs. `TreeService.Delete`'s own two write paths are wrapped in `withRetry` for the same reason `Move`'s are: the lock adds real PostgreSQL deadlock surface against the other operations' own locks.

**`withRetry` (concurrency.go).** This bounded retry loop is how the multi-statement write paths above run their transactions when a concurrent writer gets there first: `txRetryBudget` attempts with a small fixed backoff, retrying only on `dbkit.IsRetryableConflict` — SQLite's `SQLITE_BUSY`, or PostgreSQL's detected deadlock / serialization failure — and surfacing the coded `org.concurrent_update` when the budget is exhausted. Which paths are wrapped is `concurrency.go`'s `withRetry` doc comment's authority, not this paragraph's: it names the current set and the shape that earns the envelope, keeping this section's claims stable as the set changes. The two standing exceptions, `MemberService.Remove` and `InviteService.Invite`, are deliberate: each rewrite is one database-arbitrated transaction whose first statement takes every lock it will ever hold, the shape that cannot produce the overlapping-lock deadlock this envelope exists to retry. `dbkit.IsRetryableConflict` lives in `dbkit`, not here, deliberately: classifying a driver's own error shape needs either a type assertion against that driver's concrete error type (which would tie org — and every other dbkit consumer — to both SQL drivers at once, undoing the `dialect/sqlite` / `dialect/postgres` dependency split) or dbkit's own substring-matching classifier.

**Proof, and its honest limits.** `MemberService.Remove` and `InviteService.Invite`'s races are reliably reproducible with two real goroutines racing a real, file-backed SQLite database (`membership_test.go`'s `TestMemberService_Remove_ConcurrentLastTwoActiveMembers`, `invite_test.go`'s `TestInviteService_Invite_ConcurrentSameAddress_ExactlyOneLiveToken` — each repeats the pair `trials` times since any single pair's own reproduction rate was measured around one in five, not one in one). `CreateChild`/`Move`/`Restore`'s races sit between two DIFFERENT transactions' single statements, which no test can deterministically pause between without a test-only hook in production code; `tree_test.go`'s `TestTreeService_Concurrent*` tests instead run many rounds of two real operations racing and re-check the tree's structural invariant (`assertNoOrphans`: every live node's `ParentID` names another live node, and its `Path` is exactly that parent's plus its own id) after every round. `integration_test/postgres_concurrency_test.go` re-runs the same pairings against a real PostgreSQL server — the tier that actually caught the `deleteLeaf`/`deleteSubtree` gap above and the interior-descendant `Move` gap too, each of which the SQLite unit tier's coarser whole-file locking could not expose. The `Delete`×`MemberService.Add` pairing needed neither dialect's timing specifically — it was a wide-open gap with no locking on either side, which is why `tree_test.go`'s `TestTreeService_ConcurrentDeleteAndMemberAdd_NeverDanglesAMembership` reproduces it reliably on plain SQLite alone with no PostgreSQL twin needed. The `Rename` pairing is the family's fourth reliably-SQLite-reproducible member and its first fully deterministic one: its window sits between two statements of the SAME call, which a second connection holding the delete's transaction open pins exactly, so `TestTreeService_ConcurrentRenameAndDelete_NeverResurrectsTheNode` needs no round budget either.

## Known limitations

**`Repository[T].WithinSubtree(nodeID)` is not built.** It is a change to *dbkit's* public generic surface, not org's, and that surface grows with real consumers' shapes in hand. org exposes descendant ids instead; consumers filter with `IN ?`.

**Sibling-name collisions are pre-checked, and the database is the backstop.** Two concurrent creates racing on the same name both pass the pre-check; the `UNIQUE(tenant_id, parent_id, name)` index rejects the loser, and `mapWriteError` translates `gorm.ErrDuplicatedKey` back into `org.duplicate_sibling_name`, so the caller sees one error for one condition either way. This is a genuine, deliberate exception to the "lock before you trust it" discipline above: the database's own unique index IS the arbiter here, exactly the same shape Invite's database-arbitrated insert uses for pending invitations, so no additional row lock is needed.

**A membership is not moved when its node is.** `Move` rewrites paths, and `MemberNodeIDs` resolves the subtree at read time, so a member's scope follows the tree automatically — but nothing caches it for them. A consumer that *does* cache a node path must invalidate on `org.node.moved`.

**No operation writes `suspended` or `invited`.** `MembershipStatus*` declares the closed vocabulary the column may hold, and `Scope.MemberNodeIDs` already honors it — a suspended member sees nothing — but org ships no Suspend/Reinstate call, and an unaccepted invitee occupies no seat, so `invited` is never written either. Both statuses are readable and enforced; setting them is simply not shipped, not an accident.

**Invitations are not swept.** An unaccepted invitation stays `pending` in the table forever; expiry is evaluated at acceptance time, which is enough for correctness but leaves rows accumulating. A cleanup job would need the `jobs` queue wired into this module.

**Depth and name bounds are enforced in Go, not by the column widths.** SQLite does not enforce `VARCHAR(n)` under type affinity, so a standalone-mode deployment would otherwise accept what the distributed mode rejects.

**`Restore` is per-node, never cascading, and org exposes no query to enumerate a node's mark-deleted descendants.** See "Soft deletion" above for the full design rationale. A caller who cascade-deleted a subtree and wants it all back can read every descendant's id straight off the `org.node.deleted` event's own `DeletedNodeIds` field (every row the cascade actually removed, the node itself included, not merely `RemovedCount`'s bare tally) if it kept that delivery; `org` itself still provides no STORED listing of what a `Delete(cascade=true)` touched, or of what is currently mark-deleted beneath a node, for a caller who did not keep the event to restore against later; a restore-all flow would want a stored listing, most naturally an `Unscoped`-flavored subtree query alongside the existing `subtree`/`children`.

**No HTTP surface for `Restore`.** `TreeService.Restore` and `MemberService.Restore` are real, tested service-level methods with no `OrgRestoreNode` / `OrgRestoreMember` operation in `api/openapi.yaml` — an OpenAPI/codegen change plus a host-side rbac route this module cannot add on its own (see "Soft deletion" above).

**`org_invitations` did not adopt `SoftDeletable`.** Deliberately — see "Soft deletion" above.

## Rules

- **Never import `authn`, and never import any other business module's structs.** Users are id strings learned from events. An `authn` type in this module's import graph is a defect, not a shortcut.
- **Never declare `authn.user.created` with `reg.EventsSeat().Publishes`.** Only subscribe to it. Declaring another module's event type collides at bootstrap the moment both modules boot in one host; `TestModule_Register_DoesNotDeclareAuthnsEvent` guards it.
- **Never write an `OrgNode` row outside `TreeService`.** It is what keeps `ParentID` and `Path` in lockstep.
- **Never hand-write a tenant filter, and never reach for `db.Table` / `db.Model` / `db.Raw`.** See the Data access section.
- **Never introduce an id scheme outside `[0-9a-f-]`.** See the dialect-identity proof.
- **Never add a recursive CTE or a SQL string function over the `path` column.** Path arithmetic happens in Go.
- **Never localize an error into a returned string.** Return the code; the text lives in `locales/`.
- **Never capture `reg.Locales()`, `reg.Mailer()`, `reg.KVStore()` or `reg.EventBus()` during `Register`.** Store the registry and read them when you use them. `Registry.Locales()` is nil while modules register — this is the single easiest mistake in this module.
- **Never put an email address or an invitation token in a log line, an event payload, a rate-limit key, an error parameter or an API response.** Where an internal identifier must identify a recipient in the rate limiter's KV key, the blind index is what does it (an address in a Redis-visible key would be a PII leak — see "The invitation email is the verification-class exception, not a waiver of it" above). An event payload is deliberately NOT one of those places: it identifies the invitation by its id, and since the blind index is a stable linkable identifier of a guessable address, no derivation of the address rides `org.member.invited` either — a subscriber that must reach the invitee reads the invitation row (see "The audit trail" above and `MemberInvited`'s own doc comment). An API response is deliberately not one either: an echoed blind index is refused because creation yields (address, index) pairs (see "The HTTP surface" above). And the audit trail receives only the `[redacted]` markers of the address-derived columns, by capture-time redaction — org never writes audit rows itself (see "The audit trail" above).
- **Never render user-facing text from a Go string literal.** Even the automatic workspace name comes from the catalog; its only fallback is an identifier, never a word in one of the two languages.
- **Never send a second unsolicited message to an unaccepted invitee.** The single consent-establishing message is the entire exception org is allowed.
- **Never resolve the caller's identity from anything but `SubjectResolver`.** No handler method reads a body field, header or query parameter as a user id; `resolveSubject` is the one path in, and it fails closed.
- Migrations are versioned SQL, one file per dialect, byte-identical apart from the header note. No `AutoMigrate`, no `NOW()`, no `gen_random_uuid()`, no native arrays, no JSONB.

## Testing

Unit tests run with no external dependency: `go test ./... -race` from `go/org`. `internal/testutil.NewSQLite` applies the module's **real** migration files from zero through `dbkit.MigrationRegistry`, so every DB-backed test doubles as proof that those files run on an empty database.

`internal/testutil` deliberately does not import `go/org` — org's own tests are in `package org`, so a helper package importing org could not be imported back by them. `NewSQLite` therefore takes a module name and an `embed.FS`. `go/dbkit/internal/testutil` avoids the identical cycle the identical way.

Tests that touch `Invitation` must register the encrypted-email serializer first (`newInvitationTestDB` does it): the column is written through a named GORM serializer, and GORM cannot parse the model when nothing is registered under that name.

`events_test.go`'s `TestTreeService_NodeDeletedPayload_CarriesTheRealRemovedIDSet` pins `DeletedNodeIds`: exactly `[nodeID]` for a single, non-cascading delete, and every row a cascade actually removed — never reaching into an untouched sibling subtree — for one that cascades. `repository_test.go`'s `TestRepository_deleteSubtree` asserts the same set at the `Repository.deleteSubtree` layer directly.

`internal/testutil.NewPostgres` is the integration tier's counterpart, applying the identical files from `postgres/`, so the same assertions can run against both dialects by swapping the constructor alone. That tier is `integration_test/` (`//go:build integration`, `go test -race -tags=integration ./...` — Docker required): `postgres_tree_test.go` re-runs the A1 dialect-identity proof (the sibling-sharing-a-prefix subtree scan, a whole-subtree `Move`, a cascading delete, the max-depth bound) against a real PostgreSQL, `postgres_isolation_test.go` re-runs `tenancytest.AssertIsolated` for all three tenant-scoped repositories, including the encrypted-and-blind-indexed `Invitation.Email` column, and `postgres_concurrency_test.go` re-runs the racing-operation pairings of "Concurrency" above — including the interior-descendant `Move`×`CreateChild` pairing — against a real server, the tier that actually exercises PostgreSQL's READ COMMITTED window. It is wired into CI on `full-check.yml`'s `integration-tiers` matrix and into `Taskfile.yml`'s `INTEGRATION_DIRS`.
