# sharing

go/sharing implements public share links: a controlled entry point that lets an unauthenticated external visitor view one internal resource -- a patient viewing their own simulation result, a customer viewing a report, an anonymous one-time result page. This file is the module-level discipline that ships with `go/sharing` to consuming projects; the design rationale is `docs/internal/07-platform-services.md`'s sharing section, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: implemented and consumed end to end.** The module ships the Share domain model and its access log, the Service surface (Create, Access, AccessPublic, Revoke, Get, List, ListAccessLog), the jobs-driven expiry sweep, the five mandatory design rules each enforced with a passing test, two HTTP surfaces (`PathAccess`, the genuinely public access route; `PathShares`, the five owner-facing operations), `go/ratelimit` applied to every abuse-facing call site, access-log retention-sweep participation, and reference-app wiring as a real end-to-end HTTP consumer. The sections below describe each piece's current shape; what is deliberately not shipped is recorded in "Known limitations". The code is always the authority over this file.

## Scope

**What ships.** Two tables (`sharing_shares`, `sharing_access_log`, plus the deliberately narrow platform-data `sharing_token_index`) with dual-dialect versioned SQL migrations. `Service`: `Create` mints a share (forcing a default expiry, refusing an explicit request for one that never expires, hashing an optional password, drawing a fresh high-entropy token), `Access` resolves a bearer token into the share it names or refuses with one outward-identical answer, `AccessPublic` does the same for a genuinely unauthenticated caller by resolving the tenant from the token alone, `Revoke` withdraws a share with immediate effect, and `Get`/`List`/`ListAccessLog` serve an owner's own view. `Service.Sweep` plus the `sharing.expiry_sweep` jobs task mark expired or view-exhausted shares and refund interrupted view reservations. `pkgcore.Module` wiring: permissions (`sharing:read`, `sharing:create`, `sharing:revoke`), one audit action (`sharing.share.create_sensitive`), three declared domain events (`sharing.share.created`/`.accessed`/`.revoked`), and one configuration item (`sharing.default_expiry`). One HTTP route under `PathAccess` (`api/openapi.yaml`'s `sharing_accessShare`, `GET /api/v1/sharing/access`), genuinely public and unauthenticated -- a host must allowlist it with `tenancy.WithAllowlist` -- and five owner-facing operations under `PathShares` (`/api/v1/sharing/shares`): create, list, get, revoke, list access log. Every response the public route writes carries `Cache-Control: no-store`.

**Deliberately not in scope** (see "Known limitations" below for the reasoning behind each):

| Not here | Where it belongs | Why |
|---|---|---|
| A live consumer of `sharing.share.accessed` | A compliance audit trail | This module only publishes; the event announces every settled access, granted or denied, for a subscriber to consume |
| A browser-facing password-entry page for a protected share | A host's own frontend | `handler.go`'s route accepts the password over `HeaderSharePassword`; rendering an actual HTML prompt that collects and resends it is presentation-layer work no module in this codebase ships |

## Data model

Two tables, one tenant-scoped, one platform-data:

| Table | Domain | Repository shape | Isolation proof |
|---|---|---|---|
| `sharing_shares` | Tenant | `ShareRepository`, embeds `dbkit.Repository[Share]` | `tenancytest.AssertIsolated` |
| `sharing_access_log` | Tenant | `AccessLogRepository`, embeds `dbkit.Repository[AccessLogEntry]` | `tenancytest.AssertIsolated` |
| `sharing_token_index` | Platform | `ShareRepository`'s tenant-less lookup | `tenancytest.AssertNotTenantScoped` |

A share belongs to the tenant whose resource it exposes, and an access log entry belongs to the same tenant as the share it was recorded against. Neither table carries a SQL foreign key to the other, or to any cross-module row -- `AccessLogEntry.ShareID` is a plain, unenforced string column, following this codebase's blanket no-FK convention even for a same-module reference.

**`Share.TokenHash`, never `Share.Token`.** This module deliberately stores only the hex-encoded SHA-256 of the token (`token.go`'s `hashShareToken`), mirroring `go/org`'s `Invitation.TokenHash` precedent exactly. The raw token is returned to the caller of `Service.Create` exactly once, inside `CreateResult.Token`, and is never persisted anywhere. A leaked database backup therefore yields no usable share link, and `Service.Access`'s lookup is a hash comparison rather than a comparison against a stored secret.

**`Share.ExpiresAt` is a `*time.Time` that is never actually nil once a row exists.** The Go type is an optional shape (`Service.Create`'s own `CreateParams.ExpiresAt` really is optional), but `Service.Create` resolves a nil request into a concrete time before the row is ever written, and refuses outright (`ErrExpiryRequired`) a caller that explicitly asks for one that never expires (`CreateParams.Forever`). The column is declared `NOT NULL` as a second, database-level line of defense.

**`Share.PasswordHash` is an argon2id PHC digest, never plaintext.** `password.go` implements a small, self-contained argon2id hasher rather than importing `go/authn` for its `HashPassword`/`PasswordParams` -- `go/authn` is a heavy module several tiers away in the dependency graph, and pulling in its full SMS/OIDC/session surface for one hashing function would violate this codebase's "measure what a dependency costs" discipline. The WRITER hashes at fixed, un-configurable cost parameters (OWASP's first recommended configuration, matching `authn.DefaultPasswordParams`'s own floor); the READER (`verifySharePassword` through `decodeSharePasswordPHC`) re-derives the digest from the cost parameters stored INSIDE each hash, exactly as `authn.decodePHC` does for its own -- so a stored hash written under different parameters (a writer cost change, another tool) keeps verifying, and a cost change is never a migration over existing shares. The two implementations are deliberately not unified; if a policy-driven, host-configurable share password writer ever matters, that is this module's own future work, not a `go/authn` dependency. (Known limitation, recorded in full on the constants: the writer's cost parameters are package constants; the reader honors any valid stored parameters.)

**Limited shares count views through a compare-and-swap guard; unlimited shares through one atomic increment.** `ShareRepository.tryRecordView` (a `MaxViews`-limited share) matches the exact row state (`view_count = ?`) a caller last observed and refuses the write if the row has moved on -- the identical shape `org.InvitationRepository.acceptIfPending` uses for its own single-use guard -- rather than a raw SQL increment reached through `.Model(...)`, which this codebase's `raw-gorm-bypass` semgrep rule flags on any receiver. `Service.recordView`'s retry loop (bounded by `maxRecordViewAttempts`) re-reads a lost race and retries against the row's latest state, so ordinary concurrency between two viewers of one limited share is never misreported as "not accessible" -- only a share that has genuinely stopped being live short-circuits the loop as a real refusal. `TestService_Access_ConcurrentAccessesRespectMaxViews` races many goroutines against a `MaxViews`-limited share under `-race` and asserts exactly `MaxViews` of them are granted. An UNLIMITED share (`MaxViews` nil -- the common public-link shape) skips the CAS path entirely: there is no ceiling for it to arbitrate, so `recordView` records the view with one atomic server-side increment (`ShareRepository.tryIncrementView`, a raw `.Exec` whose hand-written `tenant_id` predicate and isolation test mirror `go/billing`'s `applyBalanceDelta` exactly -- see that method's own doc comment for why the raw surface is the sanctioned way to express server-side arithmetic here). A viewer of an unlimited share is refused only by genuine revocation or expiry, never by losing too many races against other viewers.

## The five mandatory rules

Every one of the design's five mandatory rules for sharing is enforced, each with a passing test:

1. **Tokens are cryptographically random, at least 128 bits, never derived from a predictable value.** `token.go`'s `newShareToken` draws 32 bytes (256 bits) from `crypto/rand` and nothing else. `TestNewShareToken_MeetsTheEntropyFloor`, `TestNewShareToken_IsUnpredictable`, `TestNewShareToken_LeakingOneTokenDoesNotRevealAnother` (`token_test.go`).
2. **A share created with no explicit expiry gets the tenant's configured default, and no request -- explicit or implicit -- can produce a never-expiring (or effectively never-expiring) link.** `Service.Create`'s `resolveExpiry` (nil `ExpiresAt`) resolves through the tenant's configured default, falling back to the 30-day `defaultShareExpiry`; `CreateParams.Forever` is refused outright (`ErrExpiryRequired`); and an EXPLICIT `ExpiresAt` is validated before it is accepted: it must lie strictly in the future and no further out than the tenant's operative explicit-expiry ceiling -- `MaxExplicitShareLifetime` (this module's exported 30-day ceiling on caller-supplied explicit values, distinct from the `defaultShareExpiry` default), RAISED to the tenant's configured default when that default is longer -- or it is refused with `ErrExpiryOutOfRange`, so `expiresAt 9999-12-31` cannot smuggle in the effectively-never-expiring link rule 2 forbids. The two roles are separate policy values (`MaxExplicitShareLifetime`'s own doc comment has the full reasoning): the ceiling governs caller-supplied explicit values only and is never applied to the tenant-configured default -- that value is the host's own policy through the `TenantConfigReader` seam, honored unchanged (`TestService_Create_TenantConfiguredDefaultBeyondCeiling_StillHonored`) -- and a tenant's configured default can only raise the operative ceiling, never lower it, which is what keeps the two paths consistent: a tenant whose own policy admits 90-day shares is never refusing a 45-day explicit request within that envelope while granting 90 days by omission (`TestService_Create_TenantDefaultAndExplicitExpiry_ShareOnePolicy` pins the same-policy regression). `TestService_Create_NoExpiryFallsBackToDefault`, `TestService_Create_NoExpiryUsesTenantConfiguredDefault`, `TestService_Create_ForeverRefused`, `TestService_Create_ExpiryInThePast_Refused`, `TestService_Create_ExpiryBeyondMaximum_Refused` (`service_test.go`).
3. **Revocation takes effect on the very next access check, with no caching involved.** `Service.Access` re-reads the row from the database on every call; there is no process-local or otherwise cached share state anywhere in this module. `TestService_Access_RevokedShare_ImmediatelyDenied` (`service_test.go`) is the exact create/access-succeeds/revoke/access-immediately-fails sequence the rule calls for. The `RevokedAt` write itself is a narrow guarded UPDATE (`ShareRepository.markRevoked`), never a whole-row write-back of a freshly read `Share` -- a full-row Save could silently roll back a view-count increment a concurrent granted access committed between the read and the write (`TestService_Access_ConcurrentViewsSurviveRevoke` races recordView calls against a mid-flight revoke under `-race` and requires every granted view to survive it). See "Revocation and caching" below for the obligation this places on the HTTP layer.
4. **Every access is logged, and a resource owner can read back who viewed a share and how many times.** `AccessLogEntry` (timestamp, IP, user agent, referrer, outcome) is written on every `Service.Access` call that resolves to a known share of the caller's tenant, granted or denied alike -- a store-failure path included (its attempt is logged as denied, the only outcome vocabulary for "could not be determined"); `Service.ListAccessLog` is the owner-facing read. For a GRANTED access the log row commits in the SAME guarded transaction as the view-count recording (`tryRecordView`/`tryIncrementView` insert the caller's granted entry only when their own UPDATE wins), so the count can never commit in a way a failed log row cannot roll back -- a log-failed attempt 500s without consuming the share (`TestService_Access_LogWriteFailure_NeverPermanentlyConsumesTheShare`); a DENIED row carries no share state and is written after the decision through the retried insert `AccessLogRepository.createWithRetry`. The caller-supplied metadata fields are truncated to their column bounds at the write boundary (`model.go`'s `accessLog*` constants, `service.go`'s `truncateAccessLogValue`) -- rune-safe and UTF-8-sanitized -- because under PostgreSQL an over-long or invalidly-encoded value would fail the INSERT and the access would leave no trail at all. And a FAILED log write is never swallowed: an `Access` whose log row did not commit -- granted or refused -- returns `ErrInternal` instead of answering as if the access had been processed, since a granted access with no trail is exactly the hole rule 4 exists to forbid (`TestService_Access_LogWriteFailure_FailsTheAccessInsteadOfLeavingNoTrail`, `TestService_Access_TruncatesOverlongLogMetadata`, `TestService_Access_RecordViewStoreFailure_StillLeavesLogAndEvent`; plus `TestService_Access_LogsEveryAttempt`, `TestService_Access_LogsDeniedAttemptsAgainstAKnownShare`).
5. **The share surface leaks nothing about the tenant: every refusal reason looks identical from the outside.** `Service.Access` answers an unrecognized token, a revoked share, an expired share, a view-exhausted share, and a missing or wrong password all with the exact same `ErrNotAccessible` -- same `Code`, same `Status`, no distinguishing `Params` -- mirroring the existence-disclosure suppression `go/authn` already applies to account enumeration. `TestService_Access_EveryRefusalReasonIsOutwardlyIdentical` (`service_test.go`) asserts this across all five reasons in one table-driven test. Two deliberate exceptions to the uniform answer exist, neither of them a refusal reason an outside caller can produce: a genuine STORE failure (the token lookup or the view recording cannot reach the database) surfaces as `sharing.internal_error` with an Error log rather than a 404-shaped `ErrNotAccessible`, so an operator sees the module is broken (`TestService_Access_UnknownTokenStoreFailure_AnswersInternalNotNotFound` and its `AccessPublic` twin); and the recognized-token constant-time equalization applies only to tokens that RESOLVE -- an unrecognized token on the unauthenticated surface is answered cheaply, by rate limit plus one token-index lookup, without the argon2id burn every recognized-token refusal path pays (see "Tenant resolution for an unauthenticated viewer" below for the timing consequences and why this is the anti-amplification choice, not a rule-5 leak). One further answer difference exists, producible by an outside caller, and it is deliberately not claimed by this rule's proof: a further wrong guess against a recognized, password-protected share whose per-token wrong-guess budget is spent answers `sharing.rate_limited` (429, `dimension` "token") where the identical refusal under budget answers the uniform `ErrNotAccessible`. That 429 discloses that the token exists, that the share is password-protected and that the wrong-guess budget is exhausted -- a recognized-token-path disclosure in this rule's own scope, recorded honestly, with why it is accepted, at the close of "Tenant resolution for an unauthenticated viewer" below.

## Sensitive-resource confirmation

The design's "sensitive resource sharing" note requires that creating a share for a resource carrying sensitive personal information is itself an audit event. `CreateParams.Sensitive` is an explicit, caller-supplied boolean -- this module deliberately builds no generic sensitivity-classification system; a create call simply says "this resource is sensitive" or does not.

When `Sensitive` is true, `Service.Create`'s `emitSensitiveAudit` fires the `sharing.share.create_sensitive` audit action through `go/dbkit/audit`'s **declarative `Emit` path**, not `dbkit.Options.AuditBus`'s automatic write-capture plugin. This is a deliberate choice, not an oversight: `AuditBus` must never point a persister at the same database a `dbkit.Repository[T]` write's own open transaction is still writing to, or the write-capture plugin's synchronous, same-goroutine publish deadlocks into `SQLITE_BUSY`. `emitSensitiveAudit` is called *after* `s.shares.Create` has already returned -- by which point `Create`'s own transaction has committed -- exactly mirroring `examples/reference-app/internal/notes/handler.go`'s `recordNoteCreatedAudit`, the established precedent for this exact hazard. A failure to emit the audit event is logged at Error level and never turns an otherwise successful share creation into an error for the caller: the "must alert, must not be silently dropped" rule for audit-write failures. `TestService_Create_SensitiveEmitsAuditEvent` / `TestService_Create_NotSensitiveEmitsNoAuditEvent` (`service_test.go`).

## Tenant-configured default expiry

`ConfigDefaultExpiry` (`sharing.default_expiry`) is declared on the registry by `Register`, with its `Default` set to `defaultShareExpiry` (30 days). The value is visible to `go/config`-backed hosts and editable through their own configuration machinery when they wire the read path; this module itself never imports `go/config`.

`Service`'s `TenantConfigReader` interface (`service.go`) is a structurally-typed, no-import seam -- `ShareDefaultExpiry(ctx, tenant) (time.Duration, bool, error)` -- the same shape `org.FeatureGate` and `org.Scope` use to reach `go/config`-shaped or `go/org`-shaped behavior without an import edge in either direction. `Module.WithTenantConfigReader` wires one in; without it (the default), `Service.Create` always falls back to `defaultShareExpiry`, which is exactly what rule 2's own "30 days if the tenant has not configured one" fallback means when nothing has been configured at all. The seam is fully implemented and tested (`TestService_Create_NoExpiryUsesTenantConfiguredDefault`, `TestService_Create_TenantConfigReaderReportingUnconfigured_FallsBackToDefault`) against a fake reader.

A configured default LONGER than this module's own 30-day ceiling doubles as that tenant's raised explicit-expiry ceiling: `resolveExpiry` refuses an explicit `ExpiresAt` only beyond `MaxExplicitShareLifetime`, raised to the configured default when the default exceeds it (`explicitExpiryCeiling`, `service.go`) -- a caller may never demand a longer lifetime than the tenant's own policy default admits, and is never refused a shorter one the module already grants by omission. `MaxExplicitShareLifetime` is an exported policy value precisely so a consumer that mints its own explicit-`ExpiresAt` shares can clamp against the same number `resolveExpiry` enforces: `go/compliance`'s export delivery is the one real consumer (`exportDeliveryExpiry` clamps its host-configured delivery window to this ceiling before calling `sharing.Create`).

**A live adapter over `*config.Service` is wired, in the reference app.** `examples/reference-app/internal/app/server.go`'s `SharingConfigReader` holds a `**config.Service` (a pointer to the host's own `configService` variable, dereferenced lazily) for the identical ordering reason `OrgFeatureGate` already established for `org.FeatureGate`: `config.Module.Attach` -- which produces the real `*config.Service` -- runs strictly after `Kernel.Bootstrap` returns, by which point `sharing.NewModule` (and its `WithTenantConfigReader` option) has already been called. `ShareDefaultExpiry` resolves the effective value through `config.Service.Get` (not the type-erasing `GetTyped`, since only `Get`'s own `Value.Scope` distinguishes a genuinely unconfigured tenant from one that merely resolves to the schema default) and reports `ok = false` when nothing was explicitly set at either the tenant or the system scope. `examples/reference-app/flowtests/tenant_config_reader_flow_test.go`'s `TestTenantConfigReader_Sharing_ConfiguredTenant_UsesConfiguredExpiry` and `TestTenantConfigReader_Sharing_UnconfiguredTenant_FallsBackToDefault` prove both halves end to end, over a real `config.Service.Set` write and a real `Service.Create` call: a tenant that configures one gets it, and a tenant that does not still gets `defaultShareExpiry`, unchanged.

## Revocation and caching

Rule 3's "revocation takes effect immediately" rule implies that a share page and the resource it serves **must declare `Cache-Control: no-store` and must never sit behind a CDN** -- CDN caching is the single most common way revocation silently fails to take effect. `Service.Access` itself has no caching problem (it re-reads the database on every call, per rule 3's own test above), and `handler.go`'s `Handler.SharingAccessShare` sets `Cache-Control: no-store` as its very first action -- before any other work, so every response the route can possibly produce carries it, success or refusal alike. This covers more than `SharingAccessShare`'s own body, too: `NewHandler` wires the mux with `api.HandlerWithOptions`, not the bare `api.HandlerFromMux`, precisely so a request the spec-generated parameter binder rejects before `SharingAccessShare` is ever called -- a missing or malformed `token`, a duplicated `X-Sharing-Password` header -- is answered by `handler.go`'s own `bindingErrorHandler` (`sharing.invalid_request`) rather than oapi-codegen's default `http.Error`, and that handler sets the same header first too. `TestHandler_SharingAccessShare_SetsNoStoreCacheControl` (`handler_test.go`) pins the success/refusal cases at the unit level, `TestHandler_SharingAccessShare_MissingTokenParam_Answers400` and `TestHandler_SharingAccessShare_DuplicatePasswordHeader_Answers400` pin the two binding-error cases the same way, and `TestBuildServer_SharingFlow_CreateAccessRevoke_EndToEnd` (the reference app's `flowtests/sharing_flow_test.go`) re-proves the success/refusal path over a real HTTP response from the composed stack. This module still cannot enforce "must never sit behind a CDN" itself -- that is a deployment-topology decision outside any module's reach -- but the header is the one lever a module can pull, and it is pulled unconditionally.

## Serving an access: a view is consumed on delivery, never on authorization

**The access route records a limited share's view only when the content was actually delivered.** `Handler.SharingAccessShare` (`handler.go`) runs the three-phase flow `Service.authorizeAttempt`'s own doc comment (`service.go`) describes: **authorize without recording** (`authorizePublicAccess`: the prelude's per-IP rate-limit check and token-to-tenant lookup, then every one of `Access`'s own refusal checks -- the tenant-scoped token lookup, the constant-time password check, current liveness -- with every refusal of a token that resolved to a known share settled as one denied row and one denied event, exactly as `Access` settles its own; a refusal answered before any share is on hand -- an over-budget caller's prelude 429 or an unrecognized token's `ErrNotAccessible` -- is settled by nothing, no row existing to attribute an entry to, while a per-token-budget 429's own wrong guess has already settled its denied row before the charge), **deliver** (the resolver open and the streamed response), and **consume only after the full body reached the viewer** (`settleAccessGranted`, committing the guarded view record and the granted log row in one transaction). Every serve shape that does not deliver -- the no-resolver answer, the resolver's own failure, a stream dying partway -- settles as **denied** (`settleAccessDenied`): one denied row and one denied event, no view consumed, so a `MaxViews=1` share survives a broken or flaky first attempt for a genuine retry. An in-process `Service.Access` caller keeps the record-at-authorization contract -- nothing the module can see can fail between that decision and the content changing hands -- so `accessAuthorized` records the view immediately on grant; the HTTP route is the one caller for whom the authorization is not the grant.

The route's settlement runs the same **reserve -> confirm/refund** shape go/billing's credits ledger (`CreditService.PreDeduct`/`Confirm`/`Refund`) and go/storage's transfer lifecycle use for a finite allowance that must be spent exactly when the work it pays for actually happened, carried by two columns on `sharing_shares` (`Share.ViewsReserved`/`ViewsReservedAt`, migration `0004_add_view_reservation.sql`):

1. **Reserve before serving** (`Service.reserveAccessView` / `ShareRepository.tryReserveView`): immediately after the authorization, a MaxViews-limited serve takes the share's single in-flight reservation -- a guarded write whose WHERE clause is the in-use refusal and the ceiling check in one. A concurrent second fetch while a serve is mid-delivery is refused up front with the identical outward `sharing.not_accessible`, never admitted to deliver and left to lose a settlement race. A limited share serves one viewer at a time by design (the count-shaped `views_reserved` column only ever holds 0 or 1); the alternative -- a reservation counter admitting up to MaxViews concurrent serves -- was rejected because the single-view guarantee never needs more than one serve in flight, and refusing the concurrent fetch before any delivery is the whole point.
2. **Confirm after delivery** (`Service.confirmAccessView` / `ShareRepository.tryConfirmView`): only once the full body reached the viewer is the reservation resolved into a spent view -- one guarded write increments `view_count`, clears the reservation and commits the granted log row in the same transaction. A share revoked or expired while its delivery was in flight refuses the confirm at the database and is settled as denied with its reservation released.
3. **Refund only on delivery failure** (`Service.refundAccessView` / `ShareRepository.tryRefundView`): the no-resolver answer, the resolver's own failure and the interrupted stream all refund the reservation alongside their denied settle -- the delivery-failure half of the guarantee, preserved -- while a delivery that SUCCEEDED is never refunded: if the confirm write itself fails, the reservation stays held (the view is spent, and every subsequent fetch is refused while it stands), matching billing's confirm-after-success semantics where a reservation is resolved only by its own confirm, never by a refund the delivered work did not earn. This is the exact two-direction guarantee: bytes not delivered never spend the view; bytes delivered are never given away unspent.
4. **Interrupted reservations are converged** (`Share.ViewsReservedAt` + `viewReservationTimeout`, 30 minutes): a serve that dies without resolving its reservation -- crash between reserve and confirm or refund -- leaves the reservation standing, and standing reservations are presumed interrupted once they outlive the timeout: the next access takes the stale reservation over (refreshing it) or, on the in-process `Access` path, the record CAS's stale-or-free clause converges it by spending the view it held, and the expiry sweep's reservation arm (`Service.Sweep`) refunds stale reservations on its regular pass. Nothing ever auto-converges a reservation younger than the timeout: an in-use share refuses, period.

**The sweep's idempotency key is window-scoped, so the sweep really runs on a regular pass.** `Module.EnqueueExpirySweep` derives its key from the `expirySweepWindowSize` window the enqueue falls in (`expirySweepIdempotencyKey`/`expirySweepWindowStart`, cleanup.go), not from the tenant alone: on a `jobs.StandaloneQueue`, whose resolved idempotency keys are held forever, the ticks inside one window still merge into the window's one job -- the concurrency protection the key exists for, so a tenant is never swept by two workers at once -- but the first tick of every later window resolves a fresh key and schedules the sweep again, at most one sweep per tenant per hour. A sweep job that dead-letters therefore poisons only its own window; the next window's tick is a new job. A tenant-only key, by contrast, would give each tenant exactly one sweep per database file: every later scheduled enqueue would silently resolve the first job, so a share that expired after that one sweep would never be marked, and an overage view reservation on a share nobody accesses again would never be refunded -- the legal recipient's one view lost to a reservation no sweep would ever clear. The windowed keying is pinned by `sweep_window_test.go` against a real `jobs.StandaloneQueue` over a real SQLite database: same-window collapse (regression-proof that the concurrency protection survives), a later window's enqueue creating a new job and running again, a dead-lettered window not poisoning later ones, and the single-module verification -- an overage reservation on a never-accessed-again share really refunded by the later window's sweep run, the share itself never revoked.

The five rules, rule 3's immediate revocation, the outward-identical refusal answers and the delivery-failure settlement shapes are all unchanged by the serving protocol: `Service.Access`/`AccessPublic` keep their record-at-authorization contract, with the record CAS (`tryRecordView`) now additionally refusing while a route serve holds a live reservation so the in-process path can never double-spend a delivery in flight. The regression pins are `handler_test.go`'s `TestHandler_SharingAccessShare_DeliveredServeWithFailedSettle_KeepsTheViewSpent` and `TestHandler_SharingAccessShare_SecondFetchDuringInFlightServe_Refused`, the repository-level guard tests in `repository_test.go`, and the `-race` single-flight tournament in `concurrency_test.go`. A delivery whose share ceased to be live mid-stream (revoked, expired, or exhausted by a concurrent viewer before the settle runs) is likewise settled denied: a delivery is recorded as granted only while the share is still live enough to hold the view it would consume. The route's outward answers are unchanged: every refusal still answers the identical `sharing.not_accessible`, an authorized-but-undeliverable serve still answers the distinct `sharing.resource_unavailable` 502 (`errors.go`'s own doc comment states that no view is consumed on that path), and rule 3's revocation still takes effect on the very next access check.

## Tenant resolution for an unauthenticated viewer

**The tenant is resolved *from the token itself*, before any tenant-scoped query ever runs.**

`Service.AccessPublic` (`service.go`) is the genuinely unauthenticated entry point: it takes a `ctx` that is not expected to carry a tenant at all. It resolves the owning tenant via `ShareRepository.tenantForTokenHash` (`repository.go`) -- a deliberately narrow, tenant-less lookup against `shareTokenIndex` (`model.go`), a table that maps a token's hash to its owning tenant and nothing else -- then attaches that tenant to `ctx` with `pkgcore.WithTenant` and re-enters `Service.Access`'s own implementation (`accessAuthorized`), its one difference from an in-process host call being `chargeTokenBudget` true: the anonymous surface's wrong-credential refusals pay the per-token wrong-guess budget (the per-IP budget is checked in the prelude either way, before the token is even resolved). Every one of `Access`'s own guarantees (rule 3's immediate revocation, rule 4's access logging, rule 5's outward-identical answers, the constant-time password check) therefore holds for an anonymous caller exactly as it holds for an authenticated one, because `AccessPublic` does not reimplement any of them -- it only supplies the one thing an anonymous caller cannot: a tenant. The one outward-answer exception to that guarantee is the spent wrong-guess budget's `sharing.rate_limited`, the single answer difference only this surface's own charge can produce -- recorded honestly, with what it discloses and why it is accepted, in the "Outward answer the wrong-guess budget does not hide" record at the close of this section.

**Why this direction, and not a system-context-shaped escape hatch searching across tenants:** the repository-wide architecture rules restrict `pkgcore.WithSystemContext` to `admin`, `compliance`, `jobs` and `authn`, and the only legitimate cross-tenant path is that one audited primitive -- a second, ad hoc escape hatch invented inside `sharing` for this one need would be exactly the uncontrolled proliferation that rule exists to prevent, and `sharing` is not on the whitelist regardless. Resolving the tenant from the token first needed no new primitive at all: `token_hash` is already effectively globally unique (`newShareToken` draws 256 bits of entropy from `crypto/rand`), so a lookup keyed on the hash alone, with no tenant predicate, can safely return the owning tenant before any tenant-scoped query runs -- and re-entering the ordinary `Access` afterward means every mandatory rule's enforcement point stays exactly where it already is, audited by the module's own test suite, rather than duplicated into a second code path that would have to be kept in step by hand.

**Why a new table, not a raw-SQL or `WithSystemContext` bypass on `sharing_shares` itself:** `dbkit`'s tenant-scope GORM plugin (`go/dbkit/tenant_scope.go`) fails every tenant-scoped query closed when `ctx` carries no tenant, by design and correctly -- it has no way to tell "this caller is allowed to look this up with no tenant" apart from an ordinary forgotten-tenant-filter bug. Escaping that plugin for `Share` (a genuinely tenant-scoped table) would mean either raw SQL -- forbidden by the repository-wide "do not reach for raw SQL to escape tenant filtering" rule outright -- or `pkgcore.WithSystemContext`, forbidden for the reason above. `shareTokenIndex` sidesteps the conflict entirely by never being tenant-scoped in the first place: it is **platform data**, the identical treatment `go/authn`'s `users` table, `go/jobs`'s `jobRecord` and `go/config`'s `row` already get for the same structural reason -- something that must be resolvable before a tenant is known cannot itself be tenant-scoped. It is reached only through `dbkit.Open()`'s plain `*gorm.DB` (never `dbkit.Repository[T]`, whose generic constraint requires `TenantScoped`, which this type must **not** implement), and its isolation suite is `tenancytest.AssertNotTenantScoped`, not `AssertIsolated` (`TestShareTokenIndex_AssertNotTenantScoped`, `repository_test.go`).

**Why this is not a general cross-tenant query capability:** the table carries exactly two columns -- a token hash and the tenant it belongs to -- and `tenantForTokenHash` returns a tenant id and nothing else: no `ResourceRef`, no `ShareID`, no `Share` row at all. A caller of this method learns only "which tenant does this hash belong to", never anything about the share itself; every other question is still answered exclusively by the ordinary tenant-scoped `Share` row `Access` reads after this lookup hands back a tenant. `ShareRepository.createWithTokenIndex` writes the `Share` row and its `shareTokenIndex` row in one transaction (`dbkit.WithTenantSession`), so a share is never left reachable by its owner while permanently unreachable by an anonymous visitor holding the same token.

**Outward answer the wrong-guess budget does not hide** (recorded honestly as this section's second residual, in the same discipline as the timing record directly below, never swept in with rule 5's own outward-identical-answer proof): the charge-after-judgment shape that keeps a leaked-link holder from holding the legitimate password-holder's correct attempt hostage answers the wrong guess that spends the last of the share's per-token budget with `sharing.rate_limited` -- 429, `dimension` "token" -- where the same wrong guess under budget answers the identical `ErrNotAccessible`. That 429 is a recognized-token-path answer difference in rule 5's own scope: only a caller presenting a token that resolves to a password-protected share ever reaches the charge, so only such a caller can provoke it, and it discloses exactly three facts -- the token exists (it names a share at all), the share it names is password-protected, and the wrong-guess budget is exhausted. It discloses nothing else: no tenant, no share id, and nothing about the share's liveness -- the wrong-credential branch runs before `Share.isLive`, so a revoked, expired or view-exhausted share's wrong guesses charge and answer the same way. (The per-IP budget answers the same code in the prelude, before any token is resolved, identically for a garbage token, with `dimension` "ip" -- it discloses nothing about any share.) The disclosure is accepted because the budget is the protection against guessing: a spent budget that answered indistinguishably from a wrong credential could not pace the guesser it exists to slow, who would have no way to know further guessing is futile until the window recovers -- the information the 429's `retry_after_seconds` param exists to carry -- while every futile attempt would still settle one denied row and one denied event, rule 4's own cost, against a budget that cannot admit it. The outward identity of every remaining answer is preserved: unrecognized tokens, under-budget wrong credentials, and revoked, expired and view-exhausted shares all answer the identical `ErrNotAccessible`, and the legitimate password-holder is never the party disclosed -- a correct attempt is never judged wrong, never reaches the charge, and never answers 429. `Service.authorizeAttempt`'s own doc comment in `service.go` records the same consequence on the mechanism's own site.

**Timing property this collapsing does not hide** (recorded honestly, not swept in with rule 5's own outward-identical-answer proof): an unrecognized token answers `ErrNotAccessible` after one repository read (`tenantForTokenHash`) and deliberately NO argon2id burn, while a recognized-but-refused token costs that same read plus `Access`'s own `byTokenHash` read and one argon2id check on top of it. The unrecognized path must not burn a dummy check too, because that burn would be the unauthenticated surface's scanner-amplification hole: a scanner spraying random tokens (each hashing differently, so per-token rate limits cannot bind it) would pay the platform a full argon2id verification per guess, capped only by the per-IP budget. Rule 5's constant-time equalization exists to hide which of the refusal REASONS applied to a presented share, and an attacker without a valid token cannot produce any recognized-token refusal at all -- so the equalization's real scope is exactly the recognized-token paths, where it remains complete. The residual delta discloses only "does this token exist at all" -- a property a valid token's own successful use already discloses to whoever holds it -- which rule 5 was never written to cover. `TestService_AccessPublic_UnknownTokenRefusalIsCheap` (a min-of-samples timing test, skipped under `-short`) pins the unknown path at a small fraction of a real verification's cost so the amplification hole cannot silently reopen.

## Owner-facing HTTP routes

Five owner-facing operations live under `PathShares` (`/api/v1/sharing/shares`), declared in the same `api/openapi.yaml` fragment `sharing_accessShare` already lives in and regenerated through the same `task api:gen` step (`oapi-codegen.yaml`'s `output: sharing-server.gen.go`, pinned oapi-codegen v2.8.0) -- a module contributes exactly one OpenAPI document per the api-contract convention.

**No separate permission, no new error code.** `Register` declares `PermissionRead`/`PermissionCreate`/`PermissionRevoke`, and every response code these five operations can answer with -- `sharing.resource_ref_required`, `sharing.expiry_required`, `sharing.invalid_max_views`, `sharing.share_not_found`, `sharing.rate_limited`, `sharing.internal_error` -- already exists, each already carrying a description in both locale files; `ErrInvalidRequest`'s own doc comment (`errors.go`) names its second source (`SharingCreateShare`'s `decodeJSON` failing to parse a request body at all, which never reaches the spec-generated parameter binder) rather than declaring a second code for what is, to a caller, the identical "the request could not be understood" answer.

**Mounting one `*Handler` at two paths.** `Handler` implements the single `api.ServerInterface` oapi-codegen generates from the whole fragment -- it cannot implement only the access route's method or only the five owner-facing ones, since Go requires every method of an interface a type asserts. `Module.Register` therefore mounts the identical `*Handler` value at both `PathAccess` and `PathShares` (two `reg.Routes.Mount` calls). This is correct, not merely convenient: the internal `http.ServeMux` `NewHandler` builds (via `api.HandlerWithOptions`) registers each operation's own exact, absolute path from the spec, and dispatches purely on the incoming request's literal path -- never on which host-level mount pattern matched it there first. A request for `/api/v1/sharing/access` can never reach a `PathShares`-rooted pattern and vice versa, so each mount's own host-applied gating stays scoped to exactly the requests it is meant for.

**The two paths are gated in opposite ways, and this is deliberate, not an inconsistency.** `PathAccess` remains genuinely unauthenticated: a host allowlists it with `tenancy.WithAllowlist` and `Handler` resolves its own identity concept (the bearer token) internally, through the authorize/settle trio "Serving an access" above describes. `PathShares` is the ordinary shape every other module's fragment already takes: never allowlisted, run downstream of `tenancy.Middleware`, with the tenant read from request context by the `Service` methods `Handler` calls -- `Handler` performs no authorization decision of its own for any of the five operations, exactly as `go/storage`'s and the reference app's own notes handler don't. A host's authorization layer (`rbac.RequirePermissionFunc` in the reference app) is what decides whether a request reaches `Handler` at all.

**`Service.List` is the one read the HTTP surface needed that no Service method served before it**, and it is deliberately narrow: `func (s *Service) List(ctx context.Context, limit int, beforeID string) ([]Share, error)` serves the tenant `ctx` carries, keyset-paginated (limit plus beforeID, `defaultListPageSize` 50 for a zero or negative limit), newest first, backed by `ShareRepository.listPage` (`repository.go`) -- `Get` and `ListAccessLog` both require a caller-known `shareID`, and no earlier need existed for "every share of this tenant". Unlike `Service.Sweep`'s own listing (`listExpiredOrExhausted`), this one is NOT filtered by liveness: a revoked or expired share still belongs to its tenant, and an owner-facing listing must still be able to show it -- `RevokedAt` on the returned row is exactly how the owner learns it is gone. `ExampleService_List` (`example_test.go`) is this method's compiled, runnable documentation, per the "a new public API must ship with... a compilable example" rule.

**`sharing_revokeShare` composes two existing methods, never a new one.** `Service.Revoke` itself returns only an `error` -- its callers are `Service`-level Go code that already holds the `Share` it is revoking. The HTTP surface's own contract (mirroring `go/pki`'s `pki_revokeSigningKey`/`pki_revokeCertificate` shape: the caller gets the resource's now-current state back) is satisfied at the `handler.go` layer instead: `SharingRevokeShare` calls `Service.Revoke` and then `Service.Get` of the same row, two ordinary Service calls, never a change to `Revoke`'s own signature. Idempotence carries through unchanged: revoking an already-revoked share still answers `200` with its current, unmodified state, exactly as `Service.Revoke`'s own contract promises.

**`sharing_listShares` is keyset-paginated, following `storage_listObjects`' own cursor shape rather than inventing a new one.** `Service.List(ctx, limit, beforeID)` (and its backing `ShareRepository.listPage`) serves the tenant's shares in pages of at most `limit` rows (1-200, `defaultListPageSize` 50 when the caller asks for none -- zero or negative) ordered by (created_at DESC, id DESC), and the caller echoes the last row's id as the next page's `beforeId`: the cursor is a keyset, not an offset, so a row created between two fetches shifts nothing. The mechanics mirror go/storage's `ObjectRepository.listPage` byte for byte, including the cursor probe: a `beforeId` naming no share of the caller's tenant -- one that never existed, or another tenant's share -- reports `dbkit.ErrRecordNotFound`, which `Service.List` translates onto the module's safe-to-disclose `ErrShareNotFound` (the same code `sharing_getShare` answers), never a page silently resumed from the wrong place. A share has no deletion path, so the only way a cursor row can "leave the listing" is never having belonged to the tenant at all. The listing stays liveness-unfiltered: revoked and expired shares still appear, `RevokedAt` on the row being exactly how an owner learns a share is gone. The HTTP operation carries `limit` and `beforeId` query parameters (spec + regenerated interface), and an explicit `limit` outside the 1-200 bound answers 400 `sharing.invalid_limit` (with `limit`/`min`/`max` params) before Service is reached, exactly as `storage_listObjects`' own handler checks its bound.

**Part of the merged `contracts/speed.yaml` document.** This fragment joins the merge -- and through it the generated `@speed/api-sdk` -- like every platform module's fragment does: the access route's raw-bytes shape and the absence of an in-workspace frontend consumer do not keep a platform module's fragment out of the merged document, since the generated surface is pinned by the api-contract consistency gates and does not rot from being uncalled (docs/internal/21-api-contract.md's module-driven inclusion policy).

## Retention sweep participation

**sharing registers a `pkgcore.RetentionParticipant` (retention_participant.go) so a host's compliance retention sweep reaps `sharing_access_log` entries past the tenant's retention window.** The log is tenant data that nothing ever reaped: rule 4's trail -- whose rows record viewer IPs and user agents -- grew without bound, exactly the unbounded PII retention an operator's retention window exists to bound. `Module.Register` registers `NewAccessLogRetentionParticipant` on `reg.Retention` under the reserved name `sharing.access_log` (owner module plus model, the mechanism's "notes.note" convention), so a host that boots sharing alongside go/compliance gets coverage with no further wiring; the registration is inert on a host that never runs retention sweeps. The participant's shape follows the notes participant (`examples/reference-app/internal/notes/retention_participant.go`) and go/compliance's own export-manifests participant:

- **Sweep** reaps the tenant's access-log entries whose recorded access time (`occurred_at`) is at or before the sweep's cutoff -- the "expired past the operator's retention window" reading the export-manifests participant gives the same cutoff. An access-log entry is LIVE data (the module has no soft-delete), so "expired" means age past the window, never a soft-delete marker. The reap hard-deletes one candidate row at a time through the repository's promoted `dbkit.HardDelete` under the system-context-carrying, tenant-carrying ctx the orchestrator supplies -- never a hand-written DELETE, never a bulk statement -- and the tenant-scoped candidate listing (`AccessLogRepository.listOlderThan`) plus HardDelete's own tenant-bound scope are what keep a sweep from ever reaping across tenants. A re-run converges: entries already removed report nothing, and an entry a concurrent pass removed between the listing and its own delete counts as gone, not as a failure (`dbkit.IsRecordNotFound` tolerance, the same reading the notes participant applies).
- **Erase** states the explicit nothing-to-erase answer, `(0, nil)`: no sharing row carries a subject attribution a right-to-erasure request could target -- a `Share` stores no creator user id and an `AccessLogEntry` no viewer user id (its viewer is often anonymous by design), so "erase this subject's rows" has no rows to name, and destroying a tenant's whole log on one subject's request would destroy other subjects' and anonymous viewers' records. The explicit declaration -- never a nil Erase, which the registrar refuses -- is what keeps an erasure request from reporting full success over a silently skipped participant, the identical reasoning go/compliance's export-manifests participant gives for its own `(0, nil)`.
- **Export stays nil** (the optional callback): sharing contributes no data to compliance's portability manifests, because a share is a tenant's pointer to a resource, never the resource's bytes -- the data behind a share lives in the resource's own store, whose own participant already contributes it. The absence costs a missing share-manifest section, never a false success.

## Reference app: mandatory first consumer

**The reference app is a real, end-to-end HTTP consumer of `go/sharing`, covering both HTTP surfaces.** The compensating godoc `Example` (`example_test.go`) remains and still passes -- it is simply no longer the *only* proof.

`internal/app/server.go` wires `sharing.NewModule(db, sharing.WithResourceResolver(...))`, its resolver a small adapter (`internal/app/sharing_resolver.go`'s `storageSharingResolver`) over the app's own `storageModule.ObjectService()` -- `sharing` never imports `go/storage` itself (`resolver.go`'s own doc comment explains why: the structurally-typed, no-import-edge seam shape this codebase uses throughout), so this composition is entirely the reference app's own, the same way `orgFeatureGate` and `demoOrgSubjectResolver` compose their own seams. The public access route is allowlisted in `tenancy.Middleware` (`sharing.PathAccess`, `GET` only) and marked `routePublic` in `internal/app/demo_subject.go`'s exhaustive route-guard table, for the identical structural reason `config`'s, `org`'s, `authn`'s and `notification`'s own `routePublic` entries are: an anonymous visitor holding a bearer token has no `Subject` an `rbac` permission check could evaluate at all. The owner-facing path (`sharing.PathShares`) is gated the opposite way in that same table: `demoRouteGuards[sharingSharesRoutePath]` names `sharingResource` (derived from `sharing.PermissionRead`/`PermissionCreate`/`PermissionRevoke`, mirroring `notesResource`'s and `storageResource`'s own derivation), and `guardModuleRoute` dispatches to a dedicated `sharingPermissionFor` selector rather than the generic `demoPermissionFor` read/write split -- the same `pkiPermissionFor`-style carve-out `demoRouteGuards`' own `pkiRoutePath` entry established, needed here because `sharing_createShare` and `sharing_revokeShare` are BOTH `POST` requests a method-only split cannot tell apart (`sharingPermissionFor` also checks the request's own path suffix, `/revoke`, which is safe to gate on for the identical reason the path-keyed table lookup itself is: the path is what routed the request here, never a value a caller supplies independently of it).

`flowtests/sharing_flow_test.go`'s `TestBuildServer_SharingFlow_CreateAccessRevoke_EndToEnd` drives the full acceptance shape end to end, entirely through real HTTP: create a share for a real, completed `go/storage` object through `sharing_createShare`, confirm it through `sharing_listShares` and `sharing_getShare`, access it as a genuinely unauthenticated visitor would through the real composed HTTP stack (no `Authorization` header, no demo user header), assert the served bytes match the object's own finalized checksum and that the response carries `Cache-Control: no-store`, read the resulting entry back through `sharing_listShareAccessLog`, revoke it (twice, proving idempotence) through `sharing_revokeShare`, and observe the very next access answer 404 `sharing.not_accessible`. A second test, `TestBuildServer_SharingFlow_UnknownToken_Answers404`, proves the access route is genuinely reachable with no `Principal` and no tenant at all -- a request `tenancy.Middleware` would otherwise 403 with `tenancy.tenant_unresolved` on any non-allowlisted path. A third, `TestBuildServer_SharingPermissionGate_EnforcesTheSharingPermissions` (the `sharing` mirror of storage's own `TestBuildServer_StoragePermissionGate_EnforcesTheStoragePermissions`), proves the permission gate actually closes: the read-only demo user (holding `notes:read` and nothing else) is refused both `POST` and `GET` on `PathShares` with `rbac.permission_denied`.

One composition subtlety the HTTP layer enforces: `Service.AccessPublic` resolves the tenant only inside its own call into `Access`, and never mutates the `*http.Request`'s context that reached the handler. `Handler.SharingAccessShare` therefore rebuilds the tenant from the granted `Share`'s own row (`share.GetTenantID()`, the `tenant_id` column the tenant-scope plugin populated when the row was written) before calling `ResourceResolver.OpenResource` -- a resolver that itself needs a tenant in ctx (like `storage.ObjectService.OpenContent`) would otherwise fail closed with `pkgcore.ErrNoTenant` on every granted access. `TestHandler_SharingAccessShare_ResolverSeesTheShareOwningTenant` (`handler_test.go`) is the unit-level regression test for this exact hazard, which the reference app's own flow test first surfaced -- why a real HTTP consumer, not only a godoc `Example`, is the standard this repository holds every module to.

## Known limitations

- **No live consumer of the `sharing.share.accessed` event.** The design names a compliance audit trail as the eventual subscriber; this module only publishes, per this repository's established publish-now-subscriber-later pattern.
- **`clientIP` (`handler.go`) trusts only the direct connection's `r.RemoteAddr`, never `X-Forwarded-For` or any other caller-supplied header.** This feeds both the access log and `ratelimit.go`'s per-IP rate-limit key, and a spoofable header for either would let an attacker rotate around their own rate limit for free. A host that terminates TLS behind a trusted reverse proxy and wants the proxy's forwarded address instead is expected to normalize `r.RemoteAddr` itself, ahead of this handler -- no per-deployment trusted-proxy configuration exists in this module.
- **No browser-facing password-entry page.** `handler.go`'s route accepts a share's password over `HeaderSharePassword`, but rendering an actual HTML prompt that collects and resends it is presentation-layer work no module in this codebase ships; a real deployment's frontend builds that page itself.
- **`Sweep`'s reaping is row hygiene, not a correctness dependency.** `Share.isLive` is evaluated fresh on every `Service.Access` call regardless of whether a sweep has ever run; `Sweep` only converges an owner-facing listing's `RevokedAt` column onto "yes, this is gone" for rows nothing has looked at since they expired. `shareTokenIndex` rows are never swept or cleaned up either -- see model.go's own doc comment for why that is harmless, not an oversight.
- **`Service.Access`'s outward-identical-answer property is proven for the reasons this module's code paths can produce (unknown token, revoked, expired, view-exhausted, missing/wrong password) and no others.** A new refusal reason added to `Access` must extend `TestService_Access_EveryRefusalReasonIsOutwardlyIdentical`'s table alongside it, or the new reason's outward shape goes unverified. That test asserts `Code`/`Status`/`Params` equality only; it does not measure or bound response latency, so `burnSharePasswordCheck`'s constant-time property (`password.go`) is enforced by code review and by every recognized-token refusal path being required to call it, not by an automated timing assertion. (The unknown-token path on the UNAUTHENTICATED surface is deliberately outside that property -- its cheapness is itself pinned by a timing test, `TestService_AccessPublic_UnknownTokenRefusalIsCheap`; see "Tenant resolution for an unauthenticated viewer" above.) The same limitation applies to `handler_test.go`'s HTTP-layer table.
- **The fragment's operations have no in-workspace frontend consumer.** The access route is a browser-navigated link and the owner-facing operations have no wired UI; both ship in the merged document and the generated `@speed/api-sdk` regardless -- the generated surface is pinned by the api-contract consistency gates and does not rot from being uncalled. A browser surface for share management would be the consumption proof (`@speed/sharing-ui` or a host page).
- **`PathShares` has no owner-facing frontend surface (`@speed/sharing-ui` or similar).** The reference app drives it directly over HTTP in `flowtests/sharing_flow_test.go`; a browser page for managing one's own shares is presentation-layer work no module or package in this codebase ships.
- **The reservation's timeout-based convergence carries a recorded residual on both sides of the ledger.** `viewReservationTimeout` (30 minutes) exists so a serve that dies without resolving its reservation is converged instead of wedging a MaxViews-limited share's remaining views forever -- and any timeout-based convergence cuts both ways. A serve slow enough to outlive the timeout and a second fetch arriving exactly then can both deliver (the ceiling is still enforced at confirm time, `tryConfirmView`'s `view_count < max_views` guard); symmetrically, a fully delivered serve whose confirm write fails persistently -- a store outage outlasting the timeout -- keeps the view spent only while its reservation stands, and once the stale reservation is converged the share can be fetched again. The alternative -- never converging a reservation -- would let one crashed serve permanently destroy a MaxViews=1 share's availability, the exact direction this module refuses to regress; both corners are recorded rather than hidden.
- **A MaxViews-limited share serves one viewer at a time.** While one serve is mid-delivery, a concurrent second fetch is refused even when views remain under the ceiling -- single-flight by design (the count-shaped `views_reserved` column only ever holds 0 or 1), chosen because the single-view guarantee never needs more than one serve in flight, and a reservation counter admitting MaxViews concurrent serves would re-open the delivered-but-unsettled race. A share meant to be fetched by several people at once is better served by an unlimited share or one share per recipient; the refusal is the same outward `sharing.not_accessible` either way.
- **The access-log table's append-only discipline is a module convention, not a database backstop.** Nothing in `sharing_access_log`'s migrations rejects an UPDATE or DELETE: the table must stay erasable for a compliance regime's retention and right-to-erasure paths (model.go's `AccessLogEntry` doc comment has the full reasoning). Only the module's own code ever appends or reads rows.

- `service_test.go` is this module's largest suite: every one of the five mandatory rules (see above), `Create`'s full validation and defaulting matrix, the sensitive-resource audit emission, the three domain events' publication, `Revoke`/`Get`/`ListAccessLog`'s owner-facing behavior including `-race`-covered concurrent-access tests, `AccessPublic`'s own suite -- resolving a tenant from a bare `context.Background()`, the unknown-token/revoked/password-protected refusal paths, and cross-tenant token isolation -- `List`'s suite: every tenant share returned including a revoked one, cross-tenant isolation, and the keyset surface (a zero limit serving the default page; an unknown or foreign beforeId answering `ErrShareNotFound` with the cursor named in its `id` parameter) -- and the regression suite: expiry range refusals, access-log metadata truncation and log-write failure surfacing, store-failure classification on both the authenticated and unauthenticated lookups, the store-failure path's log-and-event contract, the unlimited-share concurrency tournament, views surviving a concurrent revoke, the cheap-unknown-token timing pin, the expiry same-policy regression (`TestService_Create_TenantDefaultAndExplicitExpiry_ShareOnePolicy`), the log-failure atomicity regression (`TestService_Access_LogWriteFailure_NeverPermanentlyConsumesTheShare`), the confirm-store-failure contract (`TestService_ConfirmAccessView_StoreFailure_KeepsTheReservationHeld`), the mid-flight revoke settle (`TestService_ConfirmAccessView_RevokedMidFlight_RefundsAndSettlesDenied`), and the in-process path's respect for the route's in-flight reservation (`TestService_Access_RefusedWhileTheRouteHoldsTheReservation`).
- `concurrency_test.go` covers `withTxRetry`'s contract deterministically -- retry only on `dbkit.IsRetryableConflict` (SQLite's `SQLITE_BUSY`, PostgreSQL's deadlock/serialization failure), immediate unretried surface of any other error, the `txRetryBudget` attempt bound, and the raw last-conflict exhaustion answer. The retry is the cross-connection half of what keeps the guarded writes of `repository.go` (`tryRecordView`, `tryIncrementView`, `markRevoked` -- each a fresh `dbkit.WithTenantSession` transaction whose WHERE clauses re-evaluate the row's state on every attempt) green under real contention on the SQLite unit tier; it mirrors `go/org`'s `withRetry` (concurrency.go there) with one deliberate difference: exhausting the budget returns the last conflict error raw rather than a dedicated code, because every caller here already surfaces any store failure as `sharing.internal_error` and a conflict that outlasts the retry is the same internal failure the first conflict would have been -- see concurrency.go's own doc comment for that reasoning in full. The in-process half is `ShareRepository.writeMu`: `runGuardedWrite` orders this repository's own guarded writes behind it, which is what makes a revoke racing a sustained view-recording storm deterministic on SQLite -- the file-lock convoy such a storm forms can starve a retrying writer past any practical budget under the plain runner's harshest scheduling, and the ordering mutex (the serialization SQLite's single-writer semantics imposes anyway, made orderly) removes this module's own writers from that lottery entirely. The mutex is scoped to SQLite only: `serializeWrites` is set at construction from the dialector name, and on PostgreSQL `runGuardedWrite` takes no process-wide mutex at all -- the database's own row locks plus the retry are the honest mechanism there, and a cross-tenant mutex around whole transactions would only serialize unrelated tenants (one slow update blocking every other tenant's guarded write; the sweep taking the lock once per row across a huge tenant). `TestShareRepository_GuardedWritesStaySerializedOnSQLite` (`concurrency_test.go`) pins that the mutex stays engaged on the unit tier's SQLite database (a guarded write queues behind a held `writeMu`), and the module's PostgreSQL leg (`integration_test/postgres_mutex_scope_test.go`, run with `-tags=integration`) proves the inverse against a real server: two unrelated tenants' guarded writes proceed concurrently, one never blocking behind the other (deterministic -- tenant A's write is parked on a row lock the test holds and observed via `pg_locks` before tenant B is launched).

## Error index

| Code | `apperr` kind | Raised by |
|---|---|---|
| `sharing.resource_ref_required` | `Invalid` | `Service.Create` with an empty `ResourceRef` |
| `sharing.expiry_required` | `Invalid` | `Service.Create` with `CreateParams.Forever` true |
| `sharing.expiry_out_of_range` | `Invalid` | `Service.Create` with an explicit `ExpiresAt` outside the allowed bounds -- not strictly in the future, or beyond the tenant's operative explicit-expiry ceiling: `MaxExplicitShareLifetime` (30 days), raised to the tenant's configured default when longer (`resolveExpiry`) |
| `sharing.invalid_max_views` | `Invalid` | `Service.Create` with a non-positive `MaxViews` |
| `sharing.invalid_limit` | `Invalid` | `Handler.SharingListShares` with an explicit `limit` outside the 1-200 bound (`Service.List` itself serves `defaultListPageSize` for zero or negative) |
| `sharing.invalid_request` | `Invalid` | `Handler`'s `bindingErrorHandler` (`handler.go`), when the spec-generated parameter binder itself rejects a request -- a missing or malformed `token` query parameter, a duplicated `X-Sharing-Password` header; and `Handler.SharingCreateShare`'s `decodeJSON` when the request body itself cannot be parsed |
| `sharing.not_accessible` | `NotFound` | `Service.Access`/`AccessPublic`, for every refusal reason -- see rule 5 above |
| `sharing.share_not_found` | `NotFound` | `Service.Revoke`/`Get`/`ListAccessLog` for an unknown share id in the caller's tenant -- reached through the owner-facing HTTP surface (`sharing_getShare`, `sharing_revokeShare`, `sharing_listShareAccessLog`) exactly as it is through `Service` directly |
| `sharing.internal_error` | `Internal` | A storage error this module cannot classify -- including a store failure on `Access`'s token lookup or view recording (surfaced instead of a 404-shaped refusal, never silently flattened), and an access-log write failure (rule 4: an access whose trail did not commit is never answered as if it had) |
| `sharing.rate_limited` | `429` (struct literal, not a builder shape) | `Service.Create`/`AccessPublic` when the caller's `go/ratelimit` budget is exhausted (`ratelimit.go`) -- carries `dimension` and `retry_after_seconds` params |
| `sharing.resource_unavailable` | `502` (struct literal, not a builder shape) | `Handler.SharingAccessShare` when access was granted but the `ResourceResolver` (nil, or a failing call) could not open the resource -- deliberately distinct from `sharing.not_accessible`, see that error's own doc comment |
