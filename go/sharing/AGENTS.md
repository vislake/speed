# sharing

go/sharing implements public share links: a controlled entry point that lets an unauthenticated external visitor view one internal resource -- a patient viewing their own simulation result, a customer viewing a report, an anonymous one-time result page. This file is the module-level discipline that ships with `go/sharing` to consuming projects; the design rationale is `docs/internal/07-platform-services.md`'s sharing section, and the repository-wide rules are the root `CLAUDE.md` plus `.claude/skills/backend-coding-standards`.

**Status: rounds 1, 2 and 3 landed in this history.** Round 1 shipped the Share domain model and its access log, the Service that creates, accesses and revokes share links, the jobs-driven expiry sweep, and the module's `pkgcore.Module` wiring (permissions, one audit action, an event catalog, one configuration item). Round 2 closed every gap round 1 recorded as deliberately open: it resolved the tenant-resolution gap for a genuinely unauthenticated viewer (`Service.AccessPublic`, see "Tenant resolution for an unauthenticated viewer" below), shipped the module's one public HTTP route (`api/openapi.yaml`, `handler.go`), added the `ResourceResolver` seam that turns a Share's `ResourceRef` into actual bytes, applied `go/ratelimit` to both `Create` and `AccessPublic` (`ratelimit.go`), and wired the reference app as a real, end-to-end HTTP consumer (`examples/reference-app/cmd/server/sharing_flow_test.go`) -- retiring round 1's "No real consumer yet" section. Round 3 closed round 2's own "No owner-facing HTTP routes" gap: it added five owner-facing operations under a new mounted path, `PathShares` (`/api/v1/sharing/shares`) -- create, list, get, revoke, list access log -- each a thin HTTP translation of the identical `Create`/`Revoke`/`Get`/`ListAccessLog` Service methods round 1 already shipped, plus one small, deliberately minimal addition, `Service.List` (every share of the caller's tenant, newest first), added because no existing method served that read. See "Owner-facing HTTP routes" below for the full round-3 account. A reader checking a later main tree should still not assume this line is current without checking; the code is always the authority over this sentence.

## Scope

**In scope round 1.** Two tables (`sharing_shares`, `sharing_access_log`) with dual-dialect versioned SQL migrations. `Service`: `Create` mints a share (forcing a default expiry, refusing an explicit request for one that never expires, hashing an optional password, drawing a fresh high-entropy token), `Access` resolves a bearer token into the share it names or refuses with one outward-identical answer, `Revoke` withdraws a share with immediate effect, `Get`/`ListAccessLog` serve an owner's own view. `Service.Sweep` plus the `sharing.expiry_sweep` jobs task mark expired or view-exhausted shares. `pkgcore.Module` wiring: permissions (`sharing:read`, `sharing:create`, `sharing:revoke`), one audit action (`sharing.share.create_sensitive`), three declared domain events (`sharing.share.created`/`.accessed`/`.revoked`), and one configuration item (`sharing.default_expiry`).

**In scope round 2.** `Service.AccessPublic` resolves the tenant from a bearer token alone (no tenant anywhere in `ctx`) and re-enters the unchanged `Access` -- the resolved answer to "Tenant resolution for an unauthenticated viewer" below, backed by the new, deliberately narrow `shareTokenIndex` platform-data table and `ShareRepository.tenantForTokenHash`/`createWithTokenIndex` (`repository.go`, `model.go`). One HTTP route (`api/openapi.yaml`'s `sharing_accessShare`, `GET /api/v1/sharing/access`, exported as `PathAccess`), implemented by `handler.go`'s `Handler` behind a generated `api.ServerInterface`, genuinely public and unauthenticated -- a host must allowlist it with `tenancy.WithAllowlist`, the same mechanism `go/config`'s two pre-auth endpoints already use. The `ResourceResolver` seam (`resolver.go`) turns a granted share's `ResourceRef` into actual bytes, structurally typed (no import edge), satisfied in the reference app by an adapter over `*storage.ObjectService`. `go/ratelimit` applied to `Create` (per tenant) and `AccessPublic` (per IP and per token hash, `ratelimit.go`), built lazily over the host's `KVStore` through the same `hostSeams` seam `EventBus()` already used (extended with `KVStore()`). Every response the public route writes carries `Cache-Control: no-store`. The reference app wires the module end to end -- `sharing_resolver.go`'s adapter, `sharing_flow_test.go`'s real-HTTP create/access/revoke/refused cycle -- retiring "No real consumer yet" below.

**In scope round 3.** Five owner-facing operations under a second mounted path, `PathShares` (`/api/v1/sharing/shares`, exported the same way `PathAccess` is): `sharing_createShare` (POST), `sharing_listShares` (GET), `sharing_getShare` (GET `/{shareId}`), `sharing_revokeShare` (POST `/{shareId}/revoke`) and `sharing_listShareAccessLog` (GET `/{shareId}/access-log`), all declared in the SAME `api/openapi.yaml` fragment round 2 created and regenerated through the SAME `task api:gen` step. Every operation is a thin HTTP translation of an existing `Service` method (`handler.go`'s `SharingCreateShare`/`SharingListShares`/`SharingGetShare`/`SharingRevokeShare`/`SharingListShareAccessLog`) -- no new business rule lives in the fragment or the handler that `Service` did not already enforce, `sharing_revokeShare`'s response composing `Service.Revoke` (which itself returns no value) with a follow-up `Service.Get` of the same row purely to hand the caller its now-revoked state back, mirroring `go/pki`'s `pki_revokeSigningKey`/`pki_revokeCertificate` response shape. The one genuinely new piece is `Service.List` (`service.go`), a deliberately minimal addition backing `sharing_listShares` alone: no existing method served "every share of this tenant" (`Get`/`ListAccessLog` both require a caller-known `shareID`), so this round added the narrowest possible read -- `ShareRepository.listByTenant` (`repository.go`), ordered newest-first, revoked shares included since an owner-facing listing must still be able to show what happened to a share that is gone. `Module.Register` (`module.go`) mounts the SAME `*Handler` instance at both `PathAccess` and `PathShares`: this works because `Handler` implements the one generated `api.ServerInterface` covering every operation in the fragment, and oapi-codegen's internal router dispatches on a request's own literal path regardless of which host-level mount matched it there first. The two paths are gated in opposite ways by a host, and `PathShares` is deliberately the ordinary shape: unlike `PathAccess`, it is never allowlisted, runs downstream of `tenancy.Middleware` like every other module's fragment, and `Handler` performs no authorization decision of its own for it -- a host's own permission gate (`PermissionRead`/`PermissionCreate`/`PermissionRevoke`) is what a request must already have passed to reach it. See "Owner-facing HTTP routes" below for the full account, including why `sharing:create`/`sharing:read`/`sharing:revoke` needed no new permission and no new error code. The reference app wires `PathShares` end to end: `demo_subject.go`'s `demoRouteGuards` gates it on `sharingResource` through a dedicated `sharingPermissionFor` selector (mirroring `pkiPermissionFor`'s own carve-out, since a POST here means either `sharing:create` or `sharing:revoke` and a method-only split cannot tell them apart), and `sharing_flow_test.go`'s single end-to-end test now drives create, list, get, the public access route, list-access-log and a double revoke entirely through real HTTP, retiring round 2's `secondSharingService` second-connection workaround along with the round-2 gap it stood in for; a second test proves the permission gate closes on a demo user holding no `sharing` permission at all.

## Data model

Two tables, one tenant-scoped, both round 1's own design:

| Table | Domain | Repository shape | Isolation proof |
|---|---|---|---|
| `sharing_shares` | Tenant | `ShareRepository`, embeds `dbkit.Repository[Share]` | `tenancytest.AssertIsolated` |
| `sharing_access_log` | Tenant | `AccessLogRepository`, embeds `dbkit.Repository[AccessLogEntry]` | `tenancytest.AssertIsolated` |

Both are tenant data: a share belongs to the tenant whose resource it exposes, and an access log entry belongs to the same tenant as the share it was recorded against. Neither table carries a SQL foreign key to the other, or to any cross-module row -- `AccessLogEntry.ShareID` is a plain, unenforced string column, following this codebase's blanket no-FK convention even for a same-module reference.

**`Share.TokenHash`, never `Share.Token`.** The design sketch in `docs/internal/07-platform-services.md` shows a `Token` field on the model; this module deliberately stores only the hex-encoded SHA-256 of the token (`token.go`'s `hashShareToken`), mirroring `go/org`'s `Invitation.TokenHash` precedent exactly. The raw token is returned to the caller of `Service.Create` exactly once, inside `CreateResult.Token`, and is never persisted anywhere. A leaked database backup therefore yields no usable share link, and `Service.Access`'s lookup is a hash comparison rather than a comparison against a stored secret.

**`Share.ExpiresAt` is a `*time.Time` that is never actually nil once a row exists.** The Go type matches the design sketch's optional shape (`Service.Create`'s own `CreateParams.ExpiresAt` really is optional), but `Service.Create` resolves a nil request into a concrete time before the row is ever written, and refuses outright (`ErrExpiryRequired`) a caller that explicitly asks for one that never expires (`CreateParams.Forever`). The column is declared `NOT NULL` as a second, database-level line of defense.

**`Share.PasswordHash` is an argon2id PHC digest, never plaintext.** `password.go` implements a small, self-contained argon2id hasher rather than importing `go/authn` for its `HashPassword`/`PasswordParams` -- `go/authn` is a heavy module several tiers away in the dependency graph, and pulling in its full SMS/OIDC/session surface for one hashing function would violate this codebase's "measure what a dependency costs" discipline. The WRITER hashes at fixed, un-configurable cost parameters (OWASP's first recommended configuration, matching `authn.DefaultPasswordParams`'s own floor); the READER (`verifySharePassword` through `decodeSharePasswordPHC`) re-derives the digest from the cost parameters stored INSIDE each hash, exactly as `authn.decodePHC` does for its own -- so a stored hash written under different parameters (a future writer cost bump, another tool) keeps verifying, and a cost change is never a migration over existing shares. The two implementations are deliberately not unified; if a policy-driven, host-configurable share password writer ever matters, that is this module's own future round, not a `go/authn` dependency.

**Limited shares count views through a compare-and-swap guard; unlimited shares through one atomic increment.** `ShareRepository.tryRecordView` (a `MaxViews`-limited share) matches the exact row state (`view_count = ?`) a caller last observed and refuses the write if the row has moved on -- the identical shape `org.InvitationRepository.acceptIfPending` uses for its own single-use guard -- rather than a raw SQL increment reached through `.Model(...)`, which this codebase's `raw-gorm-bypass` semgrep rule flags on any receiver. `Service.recordView`'s retry loop (bounded by `maxRecordViewAttempts`) re-reads a lost race and retries against the row's latest state, so ordinary concurrency between two viewers of one limited share is never misreported as "not accessible" -- only a share that has genuinely stopped being live short-circuits the loop as a real refusal. `TestService_Access_ConcurrentAccessesRespectMaxViews` races many goroutines against a `MaxViews`-limited share under `-race` and asserts exactly `MaxViews` of them are granted. An UNLIMITED share (`MaxViews` nil -- the common public-link shape) skips the CAS path entirely: there is no ceiling for it to arbitrate, so `recordView` records the view with one atomic server-side increment (`ShareRepository.tryIncrementView`, a raw `.Exec` whose hand-written `tenant_id` predicate and isolation test mirror `go/billing`'s `applyBalanceDelta` exactly -- see that method's own doc comment for why the raw surface is the sanctioned way to express server-side arithmetic here). A viewer of an unlimited share is refused only by genuine revocation or expiry, never by losing too many races against other viewers -- under the old bounded-CAS code, sustained concurrency could starve a legitimate viewer into a false 404 once it lost `maxRecordViewAttempts` races in a row (reproduced in this round's `TestService_Access_ConcurrentUnlimitedViews_AllSucceedAndAllCount`, which races 40 accesses plus a 3,000-call recordView tournament and requires every view to be granted and counted).

## The five mandatory rules

Every rule `docs/internal/07-platform-services.md`'s own mandatory-rules list for sharing states is enforced, each with a passing test:

1. **Tokens are cryptographically random, at least 128 bits, never derived from a predictable value.** `token.go`'s `newShareToken` draws 32 bytes (256 bits) from `crypto/rand` and nothing else. `TestNewShareToken_MeetsTheEntropyFloor`, `TestNewShareToken_IsUnpredictable`, `TestNewShareToken_LeakingOneTokenDoesNotRevealAnother` (`token_test.go`).
2. **A share created with no explicit expiry gets the tenant's configured default, and no request -- explicit or implicit -- can produce a never-expiring (or effectively never-expiring) link.** `Service.Create`'s `resolveExpiry` (nil `ExpiresAt`) resolves through the tenant's configured default, falling back to the 30-day `defaultShareExpiry`; `CreateParams.Forever` is refused outright (`ErrExpiryRequired`); and an EXPLICIT `ExpiresAt` is validated before it is accepted: it must lie strictly in the future and no more than 30 days out -- the same ceiling rule 2 names for the default -- or it is refused with `ErrExpiryOutOfRange`, so `expiresAt 9999-12-31` cannot smuggle in the effectively-never-expiring link rule 2 forbids. (The tenant's CONFIGURED default is deliberately not re-capped against the ceiling: that value is the host's own policy through the `TenantConfigReader` seam, not a caller's end-run -- `TestService_Create_TenantConfiguredDefaultBeyondCeiling_StillHonored` pins the boundary.) `TestService_Create_NoExpiryFallsBackToDefault`, `TestService_Create_NoExpiryUsesTenantConfiguredDefault`, `TestService_Create_ForeverRefused`, `TestService_Create_ExpiryInThePast_Refused`, `TestService_Create_ExpiryBeyondMaximum_Refused` (`service_test.go`).
3. **Revocation takes effect on the very next access check, with no caching involved.** `Service.Access` re-reads the row from the database on every call; there is no process-local or otherwise cached share state anywhere in this module. `TestService_Access_RevokedShare_ImmediatelyDenied` (`service_test.go`) is the exact create/access-succeeds/revoke/access-immediately-fails sequence the design doc calls for. The `RevokedAt` write itself is a narrow guarded UPDATE (`ShareRepository.markRevoked`), never a whole-row write-back of a freshly read `Share` -- a full-row Save could silently roll back a view-count increment a concurrent granted access committed between the read and the write (`TestService_Access_ConcurrentViewsSurviveRevoke` races recordView calls against a mid-flight revoke under `-race` and requires every granted view to survive it). See "Revocation and caching" below for the obligation this places on a future HTTP layer.
4. **Every access is logged, and a resource owner can read back who viewed a share and how many times.** `AccessLogEntry` (timestamp, IP, user agent, referrer, outcome) is written on every `Service.Access` call that resolves to a known share of the caller's tenant, granted or denied alike -- a store-failure path included (its attempt is logged as denied, the only outcome vocabulary for "could not be determined"); `Service.ListAccessLog` is the owner-facing read. The caller-supplied metadata fields are truncated to their column bounds at the write boundary (`model.go`'s `accessLog*` constants, `service.go`'s `truncateAccessLogValue`) -- rune-safe and UTF-8-sanitized -- because under PostgreSQL an over-long or invalidly-encoded value would fail the INSERT and the access would leave no trail at all. And a FAILED log write is never swallowed: an `Access` whose log row did not commit -- granted or refused -- returns `ErrInternal` instead of answering as if the access had been processed, since a granted access with no trail is exactly the hole rule 4 exists to forbid (`TestService_Access_LogWriteFailure_FailsTheAccessInsteadOfLeavingNoTrail`, `TestService_Access_TruncatesOverlongLogMetadata`, `TestService_Access_RecordViewStoreFailure_StillLeavesLogAndEvent`; plus `TestService_Access_LogsEveryAttempt`, `TestService_Access_LogsDeniedAttemptsAgainstAKnownShare`).
5. **The share surface leaks nothing about the tenant: every refusal reason looks identical from the outside.** `Service.Access` answers an unrecognized token, a revoked share, an expired share, a view-exhausted share, and a missing or wrong password all with the exact same `ErrNotAccessible` -- same `Code`, same `Status`, no distinguishing `Params` -- mirroring the existence-disclosure suppression `go/authn` already applies to account enumeration. `TestService_Access_EveryRefusalReasonIsOutwardlyIdentical` (`service_test.go`) asserts this across all five reasons in one table-driven test. Two deliberate exceptions to the uniform answer exist, neither of them a refusal reason an outside caller can produce: a genuine STORE failure (the token lookup or the view recording cannot reach the database) surfaces as `sharing.internal_error` with an Error log rather than a 404-shaped `ErrNotAccessible`, so an operator sees the module is broken (`TestService_Access_UnknownTokenStoreFailure_AnswersInternalNotNotFound` and its `AccessPublic` twin); and the recognized-token constant-time equalization applies only to tokens that RESOLVE -- an unrecognized token on the unauthenticated surface is answered cheaply, by rate limit plus one token-index lookup, without the argon2id burn every recognized-token refusal path pays (see "Tenant resolution for an unauthenticated viewer" below for the timing consequences and why this is the anti-amplification choice, not a rule-5 leak).

## Sensitive-resource confirmation

Rule 4 of the doc's "sensitive resource sharing" note (not to be confused with the five mandatory rules' own numbering above): creating a share for a resource carrying sensitive personal information is itself an audit event. `CreateParams.Sensitive` is an explicit, caller-supplied boolean -- this module deliberately builds no generic sensitivity-classification system, per this round's own scope boundary; a create call simply says "this resource is sensitive" or does not.

When `Sensitive` is true, `Service.Create`'s `emitSensitiveAudit` fires the `sharing.share.create_sensitive` audit action through `go/dbkit/audit`'s **declarative `Emit` path**, not `dbkit.Options.AuditBus`'s automatic write-capture plugin. This is a deliberate choice, not an oversight: `go/dbkit/AGENTS.md`'s "Audit trail collection" section records that `AuditBus` must never point a persister at the same database a `dbkit.Repository[T]` write's own open transaction is still writing to, or the write-capture plugin's synchronous, same-goroutine publish deadlocks into `SQLITE_BUSY`. `emitSensitiveAudit` is called *after* `s.shares.Create` has already returned -- by which point `Create`'s own transaction has committed -- exactly mirroring `examples/reference-app/internal/notes/handler.go`'s `recordNoteCreatedAudit`, the established precedent for this exact hazard. A failure to emit the audit event is logged at Error level and never turns an otherwise successful share creation into an error for the caller, per `docs/internal/10-compliance-and-audit.md`'s "must alert, must not be silently dropped" rule. `TestService_Create_SensitiveEmitsAuditEvent` / `TestService_Create_NotSensitiveEmitsNoAuditEvent` (`service_test.go`).

## Tenant-configured default expiry

`ConfigDefaultExpiry` (`sharing.default_expiry`) is declared on the registry by `Register`, with its `Default` set to `defaultShareExpiry` (30 days) -- visible today, and eventually editable, through `go/config`'s own admin-console machinery once a host wires that path.

`Service`'s `TenantConfigReader` interface (`service.go`) is a structurally-typed, no-import seam -- `ShareDefaultExpiry(ctx, tenant) (time.Duration, bool, error)` -- the same shape `org.FeatureGate` and `org.Scope` use to reach `go/config`-shaped or `go/org`-shaped behavior without an import edge in either direction. `Module.WithTenantConfigReader` wires one in; without it (the default), `Service.Create` always falls back to `defaultShareExpiry`, which is exactly what rule 2's own "30 days if the tenant has not configured one" fallback means when nothing has been configured at all. The seam is fully implemented and tested (`TestService_Create_NoExpiryUsesTenantConfiguredDefault`, `TestService_Create_TenantConfigReaderReportingUnconfigured_FallsBackToDefault`) against a fake reader.

**A live adapter over `*config.Service` is now wired, in the reference app.** `examples/reference-app/cmd/server/server.go`'s `sharingConfigReader` holds a `**config.Service` (a pointer to the host's own `configService` variable, dereferenced lazily) for the identical ordering reason `orgFeatureGate` already established for `org.FeatureGate`: `config.Module.Attach` -- which produces the real `*config.Service` -- runs strictly after `Kernel.Bootstrap` returns, by which point `sharing.NewModule` (and its `WithTenantConfigReader` option) has already been called. `ShareDefaultExpiry` resolves the effective value through `config.Service.Get` (not the type-erasing `GetTyped`, since only `Get`'s own `Value.Scope` distinguishes a genuinely unconfigured tenant from one that merely resolves to the schema default) and reports `ok = false` when nothing was explicitly set at either the tenant or the system scope. `examples/reference-app/cmd/server/tenant_config_reader_flow_test.go`'s `TestTenantConfigReader_Sharing_ConfiguredTenant_UsesConfiguredExpiry` and `TestTenantConfigReader_Sharing_UnconfiguredTenant_FallsBackToDefault` prove both halves end to end, over a real `config.Service.Set` write and a real `Service.Create` call: a tenant that configures one gets it, and a tenant that does not still gets `defaultShareExpiry`, unchanged.

## Revocation and caching

Rule 3 (`docs/internal/07-platform-services.md`'s "revocation takes effect immediately" rule) is explicit that a share page and the resource it serves **must declare `Cache-Control: no-store` and must never sit behind a CDN** -- CDN caching is named as the single most common way revocation silently fails to take effect. **This obligation is discharged as of round 2.** `Service.Access` itself has no caching problem (it re-reads the database on every call, per rule 3's own test above), and `handler.go`'s `Handler.SharingAccessShare` sets `Cache-Control: no-store` as its very first action -- before any other work, so every response the route can possibly produce carries it, success or refusal alike. This covers more than `SharingAccessShare`'s own body, too: `NewHandler` wires the mux with `api.HandlerWithOptions`, not the bare `api.HandlerFromMux`, precisely so a request the spec-generated parameter binder rejects before `SharingAccessShare` is ever called -- a missing or malformed `token`, a duplicated `X-Sharing-Password` header -- is answered by `handler.go`'s own `bindingErrorHandler` (`sharing.invalid_request`) rather than oapi-codegen's default `http.Error`, and that handler sets the same header first too. `TestHandler_SharingAccessShare_SetsNoStoreCacheControl` (`handler_test.go`) pins the success/refusal cases at the unit level, `TestHandler_SharingAccessShare_MissingTokenParam_Answers400` and `TestHandler_SharingAccessShare_DuplicatePasswordHeader_Answers400` pin the two binding-error cases the same way, and `TestBuildServer_SharingFlow_CreateAccessRevoke_EndToEnd` (the reference app's `sharing_flow_test.go`) re-proves the success/refusal path over a real HTTP response from the composed stack. This module still cannot enforce "must never sit behind a CDN" itself -- that is a deployment-topology decision outside any module's reach -- but the header is the one lever a module can pull, and it is pulled unconditionally.

## Tenant resolution for an unauthenticated viewer

**Resolved in round 2, choosing the first of the two directions round 1 left open (see below): the tenant is resolved *from the token itself*, before any tenant-scoped query ever runs.**

`Service.AccessPublic` (`service.go`) is the genuinely unauthenticated entry point round 1's `Access` never was: it takes a `ctx` that is not expected to carry a tenant at all. It resolves the owning tenant via `ShareRepository.tenantForTokenHash` (`repository.go`) -- a deliberately narrow, tenant-less lookup against `shareTokenIndex` (`model.go`), a table that maps a token's hash to its owning tenant and nothing else -- then attaches that tenant to `ctx` with `pkgcore.WithTenant` and re-enters the ordinary, **completely unchanged** `Service.Access`. Every one of `Access`'s own guarantees (rule 3's immediate revocation, rule 4's access logging, rule 5's outward-identical answers, the constant-time password check) therefore holds for an anonymous caller exactly as it already held for an authenticated one, because `AccessPublic` does not reimplement any of them -- it only supplies the one thing an anonymous caller cannot: a tenant.

**Why this direction, and not the second one round 1 named** (a system-context-shaped escape hatch searching across tenants): root `CLAUDE.md`'s own architecture-discipline rules restrict `pkgcore.WithSystemContext` to `admin`, `compliance`, `jobs` and `authn`, and its own "Multi-tenant isolation" section is explicit that the *only* legitimate cross-tenant path is that one audited primitive -- a second, ad hoc escape hatch invented inside `sharing` for this one need would be exactly the uncontrolled proliferation that rule exists to prevent, and `sharing` is not on the whitelist regardless. Resolving the tenant from the token first needed no new primitive at all: `token_hash` is already effectively globally unique (`newShareToken` draws 256 bits of entropy from `crypto/rand`), so a lookup keyed on the hash alone, with no tenant predicate, can safely return the owning tenant before any tenant-scoped query runs -- and re-entering the ordinary `Access` afterward means every mandatory rule's enforcement point stays exactly where it already was, audited by round 1's own test suite, rather than duplicated into a second code path a reviewer would have to keep in step by hand.

**Why a new table, not a raw-SQL or `WithSystemContext` bypass on `sharing_shares` itself:** `dbkit`'s tenant-scope GORM plugin (`go/dbkit/tenant_scope.go`) fails every tenant-scoped query closed when `ctx` carries no tenant, by design and correctly -- it has no way to tell "this caller is allowed to look this up with no tenant" apart from an ordinary forgotten-tenant-filter bug. Escaping that plugin for `Share` (a genuinely tenant-scoped table) would mean either raw SQL -- forbidden by root `CLAUDE.md`'s "Do not reach for raw SQL to escape tenant filtering" rule outright -- or `pkgcore.WithSystemContext`, forbidden for the reason above. `shareTokenIndex` sidesteps the conflict entirely by never being tenant-scoped in the first place: it is **platform data** (`docs/internal/04-data-and-tenancy.md`'s data-domain table), the identical treatment `go/authn`'s `users` table, `go/jobs`'s `jobRecord` and `go/config`'s `row` already get for the same structural reason -- something that must be resolvable before a tenant is known cannot itself be tenant-scoped. It is reached only through `dbkit.Open()`'s plain `*gorm.DB` (never `dbkit.Repository[T]`, whose generic constraint requires `TenantScoped`, which this type must **not** implement), and its isolation suite is `tenancytest.AssertNotTenantScoped`, not `AssertIsolated` (`TestShareTokenIndex_AssertNotTenantScoped`, `repository_test.go`).

**Why this is not a general cross-tenant query capability:** the table carries exactly two columns -- a token hash and the tenant it belongs to -- and `tenantForTokenHash` returns a tenant id and nothing else: no `ResourceRef`, no `ShareID`, no `Share` row at all. A caller of this method learns only "which tenant does this hash belong to", never anything about the share itself; every other question is still answered exclusively by the ordinary tenant-scoped `Share` row `Access` reads after this lookup hands back a tenant. `ShareRepository.createWithTokenIndex` writes the `Share` row and its `shareTokenIndex` row in one transaction (`dbkit.WithTenantSession`), so a share is never left reachable by its owner while permanently unreachable by an anonymous visitor holding the same token.

**Timing property this collapsing does not hide** (recorded honestly, not swept in with rule 5's own outward-identical-answer proof): an unrecognized token answers `ErrNotAccessible` after one repository read (`tenantForTokenHash`) and deliberately NO argon2id burn, while a recognized-but-refused token costs that same read plus `Access`'s own `byTokenHash` read and one argon2id check on top of it. The gap was formerly smaller -- the unrecognized path used to burn one dummy check too -- until the rules-reinforcement round removed it, because that burn was the unauthenticated surface's scanner-amplification hole: a scanner spraying random tokens (each hashing differently, so per-token rate limits cannot bind it) paid the platform a full ~19 MiB argon2id verification per guess, capped only by the per-IP budget. Rule 5's constant-time equalization exists to hide which of the refusal REASONS applied to a presented share, and an attacker without a valid token cannot produce any recognized-token refusal at all -- so the equalization's real scope is exactly the recognized-token paths, where it remains complete. The residual delta discloses only "does this token exist at all" -- a property a valid token's own successful use already discloses to whoever holds it -- which rule 5 was never written to cover. `TestService_AccessPublic_UnknownTokenRefusalIsCheap` (a min-of-samples timing test, skipped under `-short`) pins the unknown path at a small fraction of a real verification's cost so the amplification hole cannot silently reopen.

## Owner-facing HTTP routes

Round 3 closed round 2's own "No owner-facing HTTP routes" limitation with five operations under `PathShares` (`/api/v1/sharing/shares`), declared in the same `api/openapi.yaml` fragment `sharing_accessShare` already lives in and regenerated through the same `task api:gen` step (`oapi-codegen.yaml`'s `output: sharing-server.gen.go`, pinned oapi-codegen v2.8.0) -- there was never a case for a second fragment file, since a module contributes exactly one OpenAPI document per `docs/internal/21-api-contract.md`'s own convention.

**No new permission, no new error code.** `Register` already declared `PermissionRead`/`PermissionCreate`/`PermissionRevoke` in round 1, for an HTTP surface that did not exist yet; this round is the first to actually gate an HTTP route on them. Likewise every response code these five operations can answer with -- `sharing.resource_ref_required`, `sharing.expiry_required`, `sharing.invalid_max_views`, `sharing.share_not_found`, `sharing.rate_limited`, `sharing.internal_error` -- already existed, each already carrying a description in both locale files; the one adjustment was broadening `ErrInvalidRequest`'s own doc comment (`errors.go`) to name its second source (`SharingCreateShare`'s `decodeJSON` failing to parse a request body at all, which never reaches the spec-generated parameter binder the code's original doc comment described) rather than declaring a second code for what is, to a caller, the identical "the request could not be understood" answer.

**Mounting one `*Handler` at two paths.** `Handler` implements the single `api.ServerInterface` oapi-codegen generates from the whole fragment -- it cannot implement only the access route's method or only the five owner-facing ones, since Go requires every method of an interface a type asserts. `Module.Register` therefore mounts the identical `*Handler` value at both `PathAccess` and `PathShares` (two `reg.Routes.Mount` calls). This is correct, not merely convenient: the internal `http.ServeMux` `NewHandler` builds (via `api.HandlerWithOptions`) registers each operation's own exact, absolute path from the spec, and dispatches purely on the incoming request's literal path -- never on which host-level mount pattern matched it there first. A request for `/api/v1/sharing/access` can never reach a `PathShares`-rooted pattern and vice versa, so each mount's own host-applied gating stays scoped to exactly the requests it is meant for.

**The two paths are gated in opposite ways, and this is deliberate, not an inconsistency.** `PathAccess` remains genuinely unauthenticated: a host allowlists it with `tenancy.WithAllowlist` and `Handler` resolves its own identity concept (the bearer token) internally, through `Service.AccessPublic`. `PathShares` is the ordinary shape every other module's fragment already takes: never allowlisted, run downstream of `tenancy.Middleware`, with the tenant read from request context by the `Service` methods `Handler` calls -- `Handler` performs no authorization decision of its own for any of the five operations, exactly as `go/storage`'s and the reference app's own notes handler don't. A host's authorization layer (`rbac.RequirePermissionFunc` in the reference app) is what decides whether a request reaches `Handler` at all.

**`Service.List` is the one new Go API this round adds**, and it is deliberately the narrowest possible addition: `func (s *Service) List(ctx context.Context) ([]Share, error)` returns every share of the tenant `ctx` carries, newest first, backed by a new `ShareRepository.listByTenant` (`repository.go`) rather than any existing method -- `Get` and `ListAccessLog` both require a caller-known `shareID`, and neither round 1 nor round 2 needed "every share of this tenant" for anything. Unlike `Service.Sweep`'s own listing (`listExpiredOrExhausted`), this one is NOT filtered by liveness: a revoked or expired share still belongs to its tenant, and an owner-facing listing must still be able to show it -- `RevokedAt` on the returned row is exactly how the owner learns it is gone. `ExampleService_List` (`example_test.go`) is this method's compiled, runnable documentation, per root `CLAUDE.md`'s "a new public API must ship with... a compilable example" rule.

**`sharing_revokeShare` composes two existing methods, never a new one.** `Service.Revoke` itself returns only an `error` -- it was never designed to hand back the row it just mutated, since round 1's only caller was `Service`-level Go code that already held the `Share` it was revoking. The HTTP surface's own contract (mirroring `go/pki`'s `pki_revokeSigningKey`/`pki_revokeCertificate` shape: the caller gets the resource's now-current state back) is satisfied at the `handler.go` layer instead: `SharingRevokeShare` calls `Service.Revoke` and then `Service.Get` of the same row, two ordinary Service calls, never a change to `Revoke`'s own signature. Idempotence carries through unchanged: revoking an already-revoked share still answers `200` with its current, unmodified state, exactly as `Service.Revoke`'s own contract already promised.

**Still out of the merged `build/openapi/speed.yaml` document, and this round re-examined that rather than silently carrying it over.** `PathAccess`'s exclusion was always about raw bytes over a typed frontend SDK having no payoff; the five new `PathShares` operations ARE typed JSON, which is exactly the shape that usually earns a fragment a place in the merge (`notes`, `authn`, `notification`). This round leaves it out anyway, for the same reason `org`'s and `storage`'s own fragments still sit outside it: `go/sharing` has no in-workspace frontend consumer at all yet (no `sharing-ui` package, no host wiring these operations into a page), and joining the merge for zero consumers would cost a real `orval` regeneration and a `@speed/api-sdk` surface nothing exercises -- the identical "measure the cost, and a payoff-free join is not free" discipline root `CLAUDE.md`'s dependency rules apply elsewhere. A future round that ships a frontend surface for share management is where this reasoning should be revisited, not before.

## Reference app: mandatory first consumer

**The reference app is a real, end-to-end HTTP consumer of `go/sharing` as of round 2, now covering both HTTP surfaces as of round 3**, retiring round 1's "No real consumer yet" exception (the compensating godoc `Example` round 1 shipped, `example_test.go`, remains and still passes -- it is simply no longer the *only* proof) and round 2's own `secondSharingService` workaround.

`cmd/server/server.go` wires `sharing.NewModule(db, sharing.WithResourceResolver(...))`, its resolver a small adapter (`sharing_resolver.go`'s `storageSharingResolver`) over the app's own `storageModule.ObjectService()` -- `sharing` never imports `go/storage` itself (`resolver.go`'s own doc comment explains why: the structurally-typed, no-import-edge seam shape this codebase uses throughout), so this composition is entirely the reference app's own, the same way `orgFeatureGate` and `demoOrgSubjectResolver` compose their own seams. The public access route is allowlisted in `tenancy.Middleware` (`sharing.PathAccess`, `GET` only) and marked `routePublic` in `demo_subject.go`'s exhaustive route-guard table, for the identical structural reason `config`'s, `org`'s, `authn`'s and `notification`'s own `routePublic` entries are: an anonymous visitor holding a bearer token has no `Subject` an `rbac` permission check could evaluate at all. The round-3 owner-facing path (`sharing.PathShares`) is gated the opposite way in that same table: `demoRouteGuards[sharingSharesRoutePath]` names `sharingResource` (derived from `sharing.PermissionRead`/`PermissionCreate`/`PermissionRevoke`, mirroring `notesResource`'s and `storageResource`'s own derivation), and `guardModuleRoute` dispatches to a dedicated `sharingPermissionFor` selector rather than the generic `demoPermissionFor` read/write split -- the same `pkiPermissionFor`-style carve-out `demoRouteGuards`' own `pkiRoutePath` entry already established, needed here because `sharing_createShare` and `sharing_revokeShare` are BOTH `POST` requests a method-only split cannot tell apart (`sharingPermissionFor` also checks the request's own path suffix, `/revoke`, which is safe to gate on for the identical reason the path-keyed table lookup itself is: the path is what routed the request here, never a value a caller supplies independently of it).

`cmd/server/sharing_flow_test.go`'s `TestBuildServer_SharingFlow_CreateAccessRevoke_EndToEnd` drives the full acceptance shape end to end, entirely through real HTTP as of round 3: create a share for a real, completed `go/storage` object through `sharing_createShare` (no more second-connection workaround -- see below), confirm it through `sharing_listShares` and `sharing_getShare`, access it as a genuinely unauthenticated visitor would through the real composed HTTP stack (no `Authorization` header, no demo user header), assert the served bytes match the object's own finalized checksum and that the response carries `Cache-Control: no-store`, read the resulting entry back through `sharing_listShareAccessLog`, revoke it (twice, proving idempotence) through `sharing_revokeShare`, and observe the very next access answer 404 `sharing.not_accessible`. A second test, `TestBuildServer_SharingFlow_UnknownToken_Answers404`, proves the access route is genuinely reachable with no `Principal` and no tenant at all -- a request `tenancy.Middleware` would otherwise 403 with `tenancy.tenant_unresolved` on any non-allowlisted path. A third, `TestBuildServer_SharingPermissionGate_EnforcesTheSharingPermissions` (the `sharing` mirror of storage's own `TestBuildServer_StoragePermissionGate_EnforcesTheStoragePermissions`), proves the round-3 permission gate actually closes: the read-only demo user (holding `notes:read` and nothing else) is refused both `POST` and `GET` on `PathShares` with `rbac.permission_denied`.

**Round 2's `secondSharingService` workaround is retired.** It opened a second connection to the running test server's own SQLite file specifically because `Create`/`Revoke` had no HTTP surface yet to drive them through -- the workaround's own doc comment named this explicitly. Round 3's HTTP surface removes the reason for it: every mutation the reference app's flow test performs now goes through the real, composed HTTP stack, gated exactly as a real deployment would gate it, which is a strictly stronger proof than a second connection bypassing the server's own route table ever was.

This module's HTTP layer also caught a real bug during round 2's own development, worth recording unchanged: `Service.AccessPublic` resolves the tenant only inside its own call into `Access`, and never mutates the `*http.Request`'s context that reached the handler -- a first implementation of `Handler.SharingAccessShare` forwarded that same, still-tenant-less context straight into `ResourceResolver.OpenResource`, which made every granted access fail with `ErrResourceUnavailable` the moment the resolver itself needed a tenant (`storage.ObjectService.OpenContent` does). The fix rebuilds the tenant from the granted `Share`'s own row (`share.GetTenantID()`, the `tenant_id` column the tenant-scope plugin already populated when the row was written) before calling the resolver. `TestHandler_SharingAccessShare_ResolverSeesTheShareOwningTenant` (`handler_test.go`) is the unit-level regression test for this exact defect, and the reference app's own flow test is what surfaced it in the first place -- the clearest illustration in this module's own history of why a real HTTP consumer, not only a godoc `Example`, is the standard this repository holds every module to.

## Known limitations

- **No live consumer of the `sharing.share.accessed` event.** `docs/internal/07-platform-services.md` names `go/compliance` (M4) as the eventual subscriber; this module only publishes, per this repository's established publish-now-subscriber-later pattern.
- **`clientIP` (`handler.go`) trusts only the direct connection's `r.RemoteAddr`, never `X-Forwarded-For` or any other caller-supplied header.** This feeds both the access log and `ratelimit.go`'s per-IP rate-limit key, and a spoofable header for either would let an attacker rotate around their own rate limit for free. A host that terminates TLS behind a trusted reverse proxy and wants the proxy's forwarded address instead is expected to normalize `r.RemoteAddr` itself, ahead of this handler -- no per-deployment trusted-proxy configuration exists in this module.
- **No browser-facing password-entry page.** `handler.go`'s route accepts a share's password over `HeaderSharePassword`, but rendering an actual HTML prompt that collects and resends it is presentation-layer work no module in this codebase ships; a real deployment's frontend builds that page itself.
- **`Sweep`'s reaping is row hygiene, not a correctness dependency.** `Share.isLive` is evaluated fresh on every `Service.Access` call regardless of whether a sweep has ever run; `Sweep` only converges an owner-facing listing's `RevokedAt` column onto "yes, this is gone" for rows nothing has looked at since they expired. `shareTokenIndex` rows are never swept or cleaned up either -- see model.go's own doc comment for why that is harmless, not an oversight.
- **No PostgreSQL integration tier.** `go/sharing/internal/testutil.NewPostgres` exists (mirroring `NewSQLite`) so a later round's `integration_test/` package needs no `db.go` of its own, but no such package is shipped yet. This round's SQLite-backed unit suite runs every isolation and CAS-guard assertion against SQLite only, `shareTokenIndex`'s new `AssertNotTenantScoped` suite included.
- **`Service.Access`'s outward-identical-answer property is proven for the reasons this round's code paths can produce (unknown token, revoked, expired, view-exhausted, missing/wrong password) and no others.** A future round adding a new refusal reason to `Access` must extend `TestService_Access_EveryRefusalReasonIsOutwardlyIdentical`'s table alongside it, or the new reason's outward shape goes unverified. That test asserts `Code`/`Status`/`Params` equality only; it does not measure or bound response latency, so `burnSharePasswordCheck`'s constant-time property (`password.go`) is enforced by code review and by every recognized-token refusal path being required to call it, not by an automated timing assertion. (The unknown-token path on the UNAUTHENTICATED surface is deliberately outside that property -- its cheapness is itself pinned by a timing test, `TestService_AccessPublic_UnknownTokenRefusalIsCheap`; see "Tenant resolution for an unauthenticated viewer" above.) The same limitation applies to `handler_test.go`'s HTTP-layer table.
- **This module's HTTP fragment is not part of the merged `build/openapi/speed.yaml` document.** The public access route serves raw bytes, not a typed JSON operation a frontend SDK would meaningfully wrap around; the round-3 owner-facing operations ARE typed JSON but have no in-workspace frontend consumer yet, so joining the orval-driven merge (as notes, authn and notification do) would cost a regeneration nothing exercises -- see "Owner-facing HTTP routes" above for the round-3 re-examination of this reasoning, and the same "no consumer yet" exception `go/pki`'s and `go/integration`'s own unconsumed surfaces carry.
- **`PathShares` has no owner-facing frontend surface (`@speed/sharing-ui` or similar) yet.** The reference app drives it directly over HTTP in `sharing_flow_test.go`; a browser page for managing one's own shares is presentation-layer work no module or package in this codebase ships yet.
- **`sharing_listShares` is not keyset-paginated**, unlike `storage_listObjects`. `Service.List` (and its backing `ShareRepository.listByTenant`) returns every share of the tenant in one call -- a deliberately minimal addition matching this round's own "no new business logic beyond a thin HTTP translation" scope, on the judgment that a tenant's own share count stays small relative to its business data. A future round adding pagination here should follow `storage_listObjects`' own keyset-cursor shape rather than inventing a new one.

## Testing

- **Unit tests**: SQLite only, no Docker required. `go/sharing/internal/testutil` provides `NewSQLite`/`NewPostgres`/`Migrate`, mirroring `go/pki/internal/testutil`'s exact shape.
- `model_test.go` covers `Share.isLive`'s full state matrix (revoked, expired, exactly-at-expiry, view-ceiling reached/exceeded, nil `ExpiresAt`) and both models' `TableName`.
- `token_test.go` covers the entropy floor, unpredictability across a sample, and that leaking one token's hash reveals nothing about another's.
- `password_test.go` covers hash/verify round-tripping, that two hashes of the same password differ (fresh salt), a malformed stored hash reporting an error rather than a false match, and (rules-reinforcement round) that verification honors the cost parameters stored inside a hash (`TestVerifySharePassword_VerifiesUnderStoredCostParams`, `TestService_Access_PasswordHashWrittenUnderOtherParams_StillVerifies`), the constants fallback for a parameter-less PHC, and the refusal of parameter triples argon2 cannot run with (t=0, p=0, m=0) or an unreadable version.
- `repository_test.go` covers both repositories' `tenancytest.AssertIsolated` suites, the token-hash lookup's tenant scoping, `tryRecordView`'s compare-and-swap guard (including a deliberately staged lost race), the expiry-sweep listing, (round 2) `shareTokenIndex`'s `AssertNotTenantScoped` suite, `createWithTokenIndex`'s atomic dual-write, and `tenantForTokenHash`'s tenant-less resolution (including the direct proof that it needs no tenant in `ctx` at all), (round 3) `listByTenant`'s newest-first ordering and tenant scoping, revoked shares included, and (rules-reinforcement round) `tryIncrementView`'s increment/liveness-guard semantics plus its one-tenant scoping proof (`TestShareRepository_TryIncrementView_ScopedToOneTenant`, the isolation test the raw-Exec shape requires), and `markRevoked`'s wins-once-then-idempotent transition semantics with view counts preserved.
- `service_test.go` is this module's largest suite: every one of the five mandatory rules (see above), `Create`'s full validation and defaulting matrix, the sensitive-resource audit emission, the three domain events' publication, `Revoke`/`Get`/`ListAccessLog`'s owner-facing behavior including `-race`-covered concurrent-access tests, (round 2) `AccessPublic`'s own suite -- resolving a tenant from a bare `context.Background()`, the unknown-token/revoked/password-protected refusal paths, and cross-tenant token isolation -- (round 3) `List`'s own suite: every tenant share returned including a revoked one, and cross-tenant isolation, and (rules-reinforcement round) the regression suite: expiry range refusals, access-log metadata truncation and log-write failure surfacing, store-failure classification on both the authenticated and unauthenticated lookups, the store-failure path's log-and-event contract, the unlimited-share concurrency tournament, views surviving a concurrent revoke, and the cheap-unknown-token timing pin. The views-surviving-a-concurrent-revoke regression (`TestService_Access_ConcurrentViewsSurviveRevoke`) was itself found, in the round's own verify pass, to be a deterministic flake under the plain (non-`-race`) runner -- a `GOMAXPROCS=1` run lost 4/4, because the revoke's guarded `revoked_at`-only write could lose the file's write lock past the busy_timeout under exactly the sustained view-write contention the test generates and surface as `sharing.internal_error` -- and the conflict-retry round closed it with the guarded writes' ordered-and-retried path (concurrency.go below -- the in-process `writeMu` ordering is what makes a revoke deterministic under the convoy the test itself generates, the bounded conflict retry the cross-connection backstop); the test is reliably green in plain mode now, `GOMAXPROCS=1` included.
- `concurrency_test.go` (the conflict-retry round) covers `withTxRetry`'s contract deterministically -- retry only on `dbkit.IsRetryableConflict` (SQLite's `SQLITE_BUSY`, PostgreSQL's deadlock/serialization failure), immediate unretried surface of any other error, the `txRetryBudget` attempt bound, and the raw last-conflict exhaustion answer. The retry is the cross-connection half of what keeps the guarded writes of `repository.go` (`tryRecordView`, `tryIncrementView`, `markRevoked` -- each one single-statement `dbkit.WithTenantSession` transaction) green under real contention on the SQLite unit tier; it mirrors `go/org`'s `withRetry` (concurrency.go there) with one deliberate difference: exhausting the budget returns the last conflict error raw rather than a dedicated code, because every caller here already surfaces any store failure as `sharing.internal_error` and a conflict that outlasts the retry is the same internal failure the first conflict would have been -- see concurrency.go's own doc comment for that reasoning in full. The in-process half is `ShareRepository.writeMu` (the same round): `runGuardedWrite` orders this repository's own guarded writes behind it, which is what makes a revoke racing a sustained view-recording storm deterministic on SQLite -- the file-lock convoy such a storm forms can starve a retrying writer past any practical budget under the plain runner's harshest scheduling, and the ordering mutex (the serialization SQLite's single-writer semantics imposes anyway, made orderly) removes this module's own writers from that lottery entirely.
- `ratelimit_test.go` (round 2) covers `rateLimiter`'s injected-override-over-host-KVStore precedence and its fail-closed behavior with no host attached, and `checkCreateRateLimit`/`checkAccessRateLimit`'s `ErrRateLimited` decoration and underlying-store-error wrapping, against a scripted `ratelimit.Limiter` double.
- `handler_test.go` (round 2) covers the HTTP layer directly: `Cache-Control: no-store` on every response shape, the outward-identical-answer property re-proven at the wire (status and body byte-for-byte across six refusal reasons), the password-protected variant's correct-password grant, `ErrResourceUnavailable` on both a nil and a failing `ResourceResolver`, the missing-required-parameter 400, and the tenant-propagation regression the reference app's own flow test first caught (`TestHandler_SharingAccessShare_ResolverSeesTheShareOwningTenant`). Round 3 adds the five `PathShares` operations' own table: token-once creation, the `forever`-refusal reaching the wire unmodified, a malformed request body answering `sharing.invalid_request` before `Service.Create` is ever called, an unknown or cross-tenant share id answering `sharing.share_not_found` on both `sharing_getShare` and `sharing_listShareAccessLog`, an empty tenant's list marshaling as `[]` never `null`, revoke composing `Service.Revoke`+`Service.Get` idempotently, the access log reporting a real access driven through the public route in the same test, and the negative property that a `sharing_getShare` response never contains the bearer token or the plaintext password.
- `cleanup_test.go` covers `Service.Sweep`'s marking behavior and idempotence, that a sweep publishes `EventShareRevoked` once per share it actually transitioned (`TestService_Sweep_PublishesShareRevokedPerReapedShare`), `expirySweepHandler`'s `Handle`/`Type`, and `Module.EnqueueExpirySweep`'s queue-required refusal and task-shape.
- `module_test.go` covers `pkgcore.Module` identity, the dual-dialect migration layout, locale-file parity, `Register`'s full declared surface (bootstrapped through a real `pkgcore.Kernel`, which also proves the locale bundle survives `i18n.Builder.AddModule`'s parity check) including the two mounted routes (`PathAccess` and, as of round 3, `PathShares`) and `OpenAPISpec`'s non-nil fragment, coexistence with another module, the no-I/O contract of `Register`, and that `Register` builds `Handler` from the module's final post-`Option` state (`WithResourceResolver` included).
- `errors_test.go` covers the `hasCode` helper and that every declared error uses the `sharing.<reason>` code convention.
